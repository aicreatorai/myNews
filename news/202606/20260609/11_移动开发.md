## 一、Core AI 取代 Core ML：苹果端侧推理架构的九年之变

### 更新全景

WWDC 2026最重要的开发者变革之一：Core ML正式被Core AI框架接替。Core ML自2017年推出以来，围绕冻结预编译ML模型（图像分类、NLP管道、表格预测）构建，其推理模型假设批量输入、单次输出。Core AI则面向LLM与生成式推理而设计：原生支持流式Token生成、多轮对话持久化上下文、动态路由——应用描述能力需求（延迟、隐私、能力级别），Core AI自动路由到端侧模型、Apple云端模型或用户选择的Extension。

Core ML不会从iOS 27中移除，现有CoreML.framework代码继续运行，但新项目应直接使用Core AI。

### 技术深解

Core AI的开发者API入口是Foundation Models框架，三行Swift代码即可调用：

```swift
import FoundationModels

let session = LanguageModelSession()
let response = try await session.respond(to: "总结这份合同的要点")
```

iOS 27中Foundation Models框架新增能力：
- 更大的基础端侧模型（从Gemini蒸馏，参数量显著提升）
- 扩展上下文窗口
- 端侧微调支持（数据不离开设备，完全本地执行）
- 图像输入：开发者可将图片与文本一并传给端侧模型，处理多模态任务
- 结构化输出、流式响应、工具调用、会话管理保持不变

Core AI动态路由机制：

```swift
// 描述能力需求，Core AI自动选择最优推理路径
let request = ModelRequest(
    prompt: "分析这张X光片",
    requirements: .init(
        privacy: .onDevice,    // 强制端侧推理
        latency: .realTime,    // 低延迟优先
        capabilities: [.vision, .reasoning]
    )
)
let response = try await CoreAI.session.respond(to: request)
```

### 迁移指南

- **现有CoreML集成**：不要立即迁移。iOS 27 Beta期间评估Core AI API，60天内关注迁移路径清晰化，9月公发前完成验证
- **新项目**：直接使用Core AI，不要在Core ML上启动新工作
- **模型转换**：Core ML的.mlmodel格式仍可运行，但新模型应通过Core AI的训练管道输出
- **测试策略**：在非主力设备安装iOS 27 Beta，验证现有CoreML集成无回归

### 生态对比

| 维度 | Core ML | Core AI |
|------|---------|---------|
| 模型类型 | 冻结预编译ML模型 | LLM/生成式模型 |
| 推理模式 | 批量输入→单次输出 | 流式Token生成 |
| 上下文 | 无状态 | 多轮持久化会话 |
| 路由 | 手动选择模型 | 自动动态路由 |
| 多模态 | 需独立管道 | 原生图文混合输入 |
| 微调 | 需重新训练 | 端侧实时微调 |

### 开发研判

Core AI不是渐进式升级，而是推理范式的根本转换。从"编译时确定模型"到"运行时动态路由"的跃迁，意味着iOS应用可以首次在不硬编码模型版本的情况下获得AI能力。对于已经使用Core ML的应用，建议在9月前完成兼容性验证；对于新启动的AI项目，Core AI是唯一正确选择。

## 二、Apple Foundation Models 五模型体系：端侧到云端的完整AI栈

### 更新全景

苹果在WWDC 2026后正式回应"Gemini套壳"质疑，披露Apple Foundation Models（AFM）体系包含5个自研模型，覆盖端侧到云端全场景。每个模型均针对Apple Silicon定制，训练过程使用专有数据，结合Gemini模型蒸馏优化，但苹果强调最终交付完全由苹果代码、苹果技术和苹果数据体系构成，用户不会接触谷歌代码或Gemini智能体。

### 技术深解

AFM体系五模型架构：

| 模型 | 部署位置 | 核心能力 |
|------|---------|---------|
| AFM Core | 端侧 | 基础AI本地操作，轻量推理 |
| AFM Core Advanced | 端侧 | 原生多模态能力，稀疏架构，本地承载复杂AI功能 |
| AFM Cloud | 云端 | 高负载请求处理（Private Cloud Compute认证） |
| AFM Cloud Image | 云端 | 图像生成和编辑 |
| AFM Cloud Pro | 云端 | 智能体工具与最重负载任务 |

端侧多模态调用示例：

```swift
import FoundationModels

// AFM Core Advanced：端侧多模态推理
let session = LanguageModelSession(model: .coreAdvanced)
let image = UIImage(named: "product_photo")!
let response = try await session.respond(
    to: "描述这张商品图片的细节",
    attachments: [.image(image)]
)

// AFM Cloud Image：云端图像生成
let imageSession = ImageGenerationSession()
let generated = try await imageSession.generate(
    from: "一只在月光下奔跑的银色狐狸，水墨画风格"
)
```

端侧微调——数据不离开设备：

```swift
// 基于用户偏好微调端侧模型
let fineTuning = OnDeviceFineTuning(
    baseModel: .coreAdvanced,
    userData: userInteractionHistory,
    epochs: 3
)
let customModel = try await fineTuning.train()
let session = LanguageModelSession(model: customModel)
```

### 迁移指南

- 从Core ML迁移到AFM体系，需重新评估模型部署策略：轻量推理用AFM Core，复杂多模态用Core Advanced
- 云端调用需适配Private Cloud Compute的安全模型
- AFM Cloud Pro的智能体能力需要Extensions SDK配合

### 生态对比

对比Google的Gemini Nano/Pro/Ultra分层，苹果的AFM体系同样采用端云分层但更强调端侧优先——AFM Core Advanced的稀疏架构让复杂多模态任务可以在本地完成，这在安卓阵营中尚无对等方案。

### 开发研判

AFM五模型体系标志着苹果AI从"能力提供"转向"系统级AI基础设施"。端侧微调能力的开放意味着每个用户都可以拥有个性化AI，而这不牺牲隐私——这是对云端AI范式的结构性挑战。开发者应优先探索AFM Core Advanced的端侧多模态能力，减少对云端的依赖和成本。

## 三、SwiftUI Document API 与工业级补齐：从框架到工具箱

### 更新全景

WWDC 2026对SwiftUI的更新不是靠某个单点API带来惊喜，而是通过一组补齐和整合，让它更接近复杂App的日常需求。核心变化包括：全新Document协议支持直接磁盘访问和快照差异比对；DataDetection框架为Text提供智能内容识别；toolbar控制力增强；reorderable和swipeActions适用范围扩大；@State惰性初始化等。

### 技术深解

**Document API**——新的心智模型调整为"可观察文档对象 + 异步快照 + 专用reader/writer"：

```swift
import SwiftUI

// 定义文档类型
struct MarkdownDocument: FileDocument {
    var text: String

    static var readableContentTypes: [UTType] { [.markdown] }

    init(configuration: ReadConfiguration) throws {
        text = try String(contentsOf: configuration.file, encoding: .utf8)
    }

    func fileWrapper(for configuration: WriteConfiguration) throws -> FileWrapper {
        let data = text.data(using: .utf8)!
        return FileWrapper(regularFileWithContents: data)
    }
}

// 使用新的Document API
struct MarkdownEditor: View {
    @Binding var document: MarkdownDocument
    @State private var snapshot: String = ""

    var body: some View {
        TextEditor(text: $document.text)
            .onSnapshot { saved in
                snapshot = saved.text
                // 支持差异比对和undo管理
            }
    }
}
```

**DataDetection框架**：

```swift
import DataDetection

// Text视图自动识别链接、日期、地址等
Text("会议定于2026年7月15日在北京市朝阳区召开，详情见 https://example.com")
    .dataDetection(.automatic)  // 自动识别并高亮可交互内容
```

**其他关键更新**：

```swift
// reorderable扩展到列表、网格和分区
List(items) { item in
    ItemRow(item: item)
}
.reorderable { from, to in
    items.move(fromOffsets: from, toOffset: to)
}

// @State 惰性初始化
@State lazy var heavyObject = ExpensiveCalculator()

// alert/confirmationDialog 支持 Binding<T?>
.alert(item: $error) { err in
    Alert(title: Text(err.localizedDescription))
}
```

### 迁移指南

- Document API替代了旧的ReferenceFileDocument和FileDocument协议组合，新项目应直接采用
- DataDetection框架独立于SwiftUI，需单独import
- reorderable需检查现有onMove实现是否冲突
- @State惰性初始化不改变现有行为，但可优化启动性能

### 生态对比

对比Jetpack Compose的Document/API体系，SwiftUI的Document API更深度整合了文件系统和Observation框架。DataDetection则填补了SwiftUI在文本智能识别上相对Android Linkify的长期空白。

### 开发研判

今年的SwiftUI更新基调务实——Document API解决文档类App的刚需，DataDetection补上文本识别短板，toolbar增强体现macOS应用重视。AnyNavigationTransition已出现但未开放自定义，预计明年将解锁导航转场的深度定制。开发者应关注"补齐"带来的整体效率提升，而非期待某个颠覆性API。

## 六、Kotlin Multiplatform 项目结构重构与Room 3.0：跨平台数据层大一统

### 更新全景

2026年KMP迎来两项重大基础设施升级：JetBrains于5月发布新默认项目结构，将单一composeApp模块拆分为职责清晰的shared + 平台应用模块；Google于3月发布Room 3.0，这是该库的首个重大破坏性版本，专注KMP支持并新增JavaScript/WASM目标平台。KMP采用率从2024年的7%飙升至2026年的23%，生产就绪状态正式移除最大采纳障碍。

### 技术深解

**新默认项目结构**——从composeApp到shared + 平台模块：

```
旧结构：
composeApp/          ← 混合了共享库+多平台应用入口
├── src/
│   ├── commonMain/
│   ├── androidMain/
│   ├── iosMain/
│   └── desktopMain/
└── build.gradle.kts

新结构：
shared/              ← 纯Kotlin Multiplatform库
├── src/
│   └── commonMain/
└── build.gradle.kts
androidApp/          ← Android应用入口（AGP 9.0要求）
├── src/
└── build.gradle.kts
desktopApp/          ← 桌面应用入口
webApp/              ← Web应用入口
iosApp/              ← iOS应用入口（Xcode项目）
```

### 迁移指南

- **项目结构迁移**：使用官方迁移指南，为每个入口点引入新模块
- **AGP 9.0强制要求**：Android应用入口必须与共享代码分离，这是必须迁移项
- **Room 3.0迁移**：主要是更新import引用（包名变更），已有KMP项目迁移较简单
- **Swift Export**：默认启用，Kotlin代码直接导出为Swift而非Objective-C
- **IntelliJ IDEA需更新到2026.1.2+**以支持AGP 9.0

## 七、端侧大模型生产化：从研究Demo到手机端推理的2026里程碑

### 更新全景

2024-2026年间，端侧LLM从研究Demo跃升为可生产部署的能力。Apple Intelligence AFM体系、Microsoft Phi-4 Mini、Google Gemma 3、阿里Qwen 3.5 Small等模型已可在手机上有用地运行。2026年的关键变化：模型蒸馏技术成熟（苹果从1.2T参数Gemini蒸馏端侧模型）、量化方案标准化（4-bit成为端侧标配）、推理框架从专用走向系统级（Core AI / AI Edge / HMAF）。

### 技术深解

**苹果端侧推理栈**——Core AI + AFM Core Advanced：

```swift
// 端侧LLM推理：完全不依赖网络
import FoundationModels

let session = LanguageModelSession(model: .coreAdvanced)

// 多轮对话 + 端侧上下文持久化
session.systemPrompt = "你是一个专业的法律助手，请用简洁的中文回答"

let r1 = try await session.respond(to: "什么是竞业限制协议？")
let r2 = try await session.respond(to: "它的有效期通常是多久？")  // 保持上文语境

// 结构化输出
struct LegalAdvice: Codable {
    let summary: String
    let risks: [String]
    let recommendation: String
}

let advice = try await session.respond(
    to: "分析这份竞业协议的风险",
    generate: LegalAdvice.self
)
```

### 迁移指南

- **iOS**：从Core ML迁移到Core AI，利用Foundation Models框架的简洁API
- **Android**：从TFLite迁移到AI Edge / MediaPipe LLM Inference
- **模型选择**：端侧优先选择1B-3B参数的蒸馏/量化模型，避免直接部署大模型
- **内存管理**：端侧推理占用2-4GB内存，需监控OOM风险
- **离线优先**：设计应用时假设网络不可用，端侧模型作为主要推理路径

| Android | AI Edge | Gemma 3/Phi-4 | 有限 | 需组合管道 |
| HarmonyOS | HMAF | 盘古端侧 | 云端为主 | 系统级 |

### 开发研判

2026年是端侧LLM的生产化元年。三个标志性事件：苹果Core AI将端侧推理从框架级提升到系统级；Phi-4 Mini证明1.5B参数模型可在手机上完成有用工作；Room 3.0等数据层KMP化让端侧AI的数据管道跨平台统一。开发者应重新审视"所有AI都走云端"的架构假设——端侧推理在隐私、延迟、成本三个维度上具有结构性优势，尤其适合个性化、实时性和隐私敏感场景。
