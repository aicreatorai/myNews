### 1. [移动] SwiftUI 2026 更新：可重排容器与文档API上线

> 📍 **导语**（约 120字）：在 WWDC26 上，Apple 为 SwiftUI 带来了 2026 年度最大规模的一次能力扩张，覆盖可重排容器、滑动操作、文档型应用 API、工具栏溢出与 Liquid Glass 刷新。这些更新并非零散补丁，而是把过去需要大量样板代码才能实现的桌面级交互下沉到声明式框架，对 iOS、iPadOS、macOS 乃至空间计算开发者都意味着更低的实现成本与更高的界面上限。

**核心信息**（约 450字）：本次 SwiftUI 更新最值得关注的是交互容器能力的下放。新增 `.reorderable()` 与 `.reorderContainer()` 修饰符，让开发者可以在 List、LazyVGrid 乃至自定义容器中直接加入拖拽重排，无需再依赖第三方拖拽库；`.swipeActions()` 与 `.swipeActionsContainer()` 则把滑动操作从 List 扩展到任意容器，配合 `ForEach` 即可为网格项添加侧滑菜单。这些 API 在 WWDC26 Session 269 中以 `ProjectCell(project).swipeActions { ... }.reorderable()` 的形式给出标准用法，语义清晰且可组合，开发者无需再手写手势识别与位置交换逻辑。

文档型应用模型是另一大重点。SwiftUI 的 `DocumentGroup` 体系新增 `DocumentCreationSource`，允许一个启动场景暴露多个"新建"入口（如空白文档、从照片新建），所选来源通过 `newDocument` 闭包的 `context` 参数传入，从而实现差异化的初始化流程。同时 `WritableDocument` 与 `ReadableDocument` 协议引入了基于快照（snapshot）的异步写入，`DocumentWriter` 与 `DocumentReader` 把磁盘 IO 放到后台，并支持进度上报与多格式导出（如 PNG）。这对笔记、画板、设计类 App 是架构级利好，过去要自己维护文件协调者（file coordinator）与后台写入队列，现在框架原生承担。

工具栏方面，新增 `ToolbarOverflowMenu`、`.visibilityPriority(.high)`、`ToolbarItem(placement: .topBarPinnedTrailing)` 以及 `toolbarMinimizeBehavior(.onScrollDown, for: .navigationBar)`，让开发者在窄屏下把次要操作收进溢出菜单、把分享等关键操作常驻，直接回应了大屏与折叠屏的布局压力。性能层面，AsyncImage 默认启用 HTTP 缓存并支持自定义 `URLRequest` 与 `URLSession`，`@State` 持有的 Observable 类改为惰性初始化，ContentBuilder 类型检查提速，官方称控件与嵌套栈布局均有明显优化，复杂列表的滚动掉帧显著减少。

这些能力需通过 Xcode 27 重新编译采用，旧的 Liquid Glass 退出开关正被移除——意味着这是一次"编译即升级"的渐进迁移，老项目不会断裂，但想保留旧外观的窗口正在关闭。

**判断**（约 190字）：短期看，SwiftUI 正在从"能用"走向"好用"，把桌面与空间计算的复杂交互做成一等公民，存量 App 升级到 Xcode 27 后多数会免费获得 Liquid Glass 刷新与新工具栏行为，几乎零成本提升质感。中长期看，Apple 用声明式 API 持续收编 UIKit 的领地，文档型、可重排、溢出工具栏等模式会成为新应用的事实标准，开发者应尽早把命令式列表逻辑迁移到 `.reorderable()` 等组合式 API，避免后续手工重写。一句话本质：SwiftUI 的边界每一年都在吞噬 UIKit，2026 年吞下的是"复杂交互"这块最后的硬骨头，未来新项目几乎找不到再用 UIKit 写列表的理由。

### 2. [移动] Swift 6.4 与 App Intents 正式取代 SiriKit

> 📍 **导语**（约 120字）：WWDC26 把两条对开发者影响深远的线拧在一起：Swift 6.4 语言层带来工作流级改进，而 Siri 被重建在 Google Gemini 模型之上后，App Intents 成为 App 与系统智能对话的"唯一正道"，SiriKit 进入弃用倒计时。对任何一个接入 Siri 或系统智能的团队，这都是一次必须提前规划的架构迁移，否则新系统能力将无从触达。

**核心信息**（约 450字）：Swift 6.4 的更新重心不在语法革命，而在"工程舒适度"。新增 `anyAppleOS` 可用性简写，可用 `@available(anyAppleOS 27, *)` 一次性覆盖 Apple 全平台，告别对每个系统重复写版本号的样板；允许在 `defer` 中使用 `await`，简化了资源清理中的异步等待；并支持在特定区域抑制警告、在需要严格性的地方把警告提升为错误，这对大型代码库的渐进式严格并发迁移极其实用。诊断层面，针对此前会触发泛型类型检查超时的表达式做了显著改进，长文件编译更稳，大型项目增量构建不再因单点复杂类型而卡死。

更关键的是 Siri 架构转向。新版 Siri 以独立 App 形态出现在 iPhone、iPad、Mac，并内置于 Spotlight，支持多步指令、跨设备 iCloud 同步的会话历史、图像与文档附件。其底层是 Apple 向 Google 授权的约 1.2 万亿参数 Gemini 模型（MoE 架构），简单请求走设备端 Foundation Model，复杂请求路由到 Google Cloud 的 Nvidia Blackwell B200，并启用机密计算加密 GPU 内存，连云运营商也无法以明文读取数据。对开发者而言，App Intents 现在成为 Siri、快捷方式、聚焦与系统智能的统一入口：`@AppEntity` 标注内容实体、`@AppIntent` 标注动作、`IndexedEntity` 接入 Spotlight 索引，WWDC26 明确 SiriKit 进入弃用时钟。

官方还引入隐私清单 API，允许按 intent 声明某次 Siri 交互"可上云"或"必须留在设备端"——这对金融、医疗等受监管数据是直接可用的合规开关，而非单纯的 UX 选项。换句话说，过去在 `INIntent` 里写一套、在快捷方式里又写一套的重复劳动，未来统一收敛到 App Intents 一处声明，系统各处自动复用。

**判断**（约 190字）：短期影响是明确的迁移清单：所有用 SiriKit 的 App 应评估 App Intents 改造，新功能一律走 App Intents，避免投入即将弃用的旧体系。中长期看，App Intents 正在成为 Apple 智能生态的"能力总线"，Widget、快捷方式、聚焦、Siri、甚至未来 Agent 都共用同一套声明，越早把核心动作抽象成 App Intent，越能吃到系统智能的分发红利。Swift 6.4 的 `anyAppleOS` 与警告治理则降低了严格并发的落地门槛，让大团队敢开严格模式。一句话本质：App Intents 不是又一个框架，而是 Apple 把"App 能力"对外开放的标准协议，谁先抽象好自己的能力，谁就先接入系统智能。

### 3. [移动] HarmonyOS 7.0 发布：纯ArkTS运行移除APK兼容层

> 📍 **导语**（约 120字）：2026 年 8 月底，华为面向 Mate 80、Pura 80 等机型推送 HarmonyOS 7.0.0.105 SP6，底层 OpenHarmony 升级至 7.0 Release、API 26.0.0，并正式在手机级标准设备上支持纯 ArkTS 应用运行、移除 Android APK 兼容层。这标志着"纯血鸿蒙"在应用运行时层面彻底告别安卓时代，所有存量兼容方案必须在新版本前完成原生重编。

**核心信息**（约 450字）：OpenHarmony 7.0（Release）启用语义化版本格式（X.Y.Z），取代旧有的带括号 API level 的命名，API 版本定格 26.0.0。本次更新的实质是内核与运行时的重构：方舟运行时（Ark Runtime）垃圾回收策略更新后内存占用下降，后台保活能力增强；系统采用自研安全架构，减少对 Android 漏洞链的依赖，已获 CC EAL5+ 与等保三级认证。最具标志性的是——手机级标准设备支持纯 ArkTS 应用运行，并移除了 Android APK 兼容层，这意味着鸿蒙不再保留"安卓兜底"路径，应用必须真正以 ArkTS 加 ArkUI 原生构建，任何未迁移的旧安卓包将无法在新系统上运行。

配套的工具链同步进化：2026-08-29 华为面向开发者正式发布 HarmonyOS 开发套件 26.0.0 版本，覆盖 DevEco Studio、SDK 与各类 Kit。应用框架层获得更精细的控制能力，例如可获取应用退出原因、控制通知铃声与锁屏通知；界面交互新增动态布局容器、Tabs 嵌套滚动；窗口管理新增标准悬浮窗与按需销毁页面内容；ArkWeb 网页引擎内核从 Chromium 132 升级至 144，并支持 URL 白名单等安全配置；音视频新增 HDR 效果、多屏录制与 Cinepak 编解码，媒体类应用可直接受益。

对存量安卓迁移项目，移除 APK 兼容层意味着"套壳、双框架兼容、临时桥接"等方案彻底失效，必须走 ArkTS 重写或借助 ArkUI-X 做跨平台桥接。华为开发者文档显示，DevEco Studio 的一键打包发布、分布式调试与性能分析已趋于成熟，配合 HMS 服务可替代 GMS 的认证、推送、支付、定位、分析等能力，企业迁移链路已相对完整。对全场景设备（手机、平板、车机、智慧屏、PC），纯 ArkTS 运行也统一了应用模型的底座，分布式能力调用更一致。

**判断**（约 190字）：短期看，纯 ArkTS 运行是鸿蒙生态独立的"分水岭"，所有仍依赖 APK 兼容层的旧应用必须启动原生重编，否则在新版本上无法运行，这是 2026 下半年最紧迫的迁移任务。中长期看，移除兼容层换来了更小攻击面与更可控的安全基线，也为方舟运行时进一步优化腾出空间，有利于鸿蒙在政企、车机、全场景设备的安全叙事。对开发者，技能栈彻底收口到 ArkTS、ArkUI 与 Stage 模型，学习成本一次性沉没后长期受益。一句话本质：鸿蒙用"砍掉兼容层"完成了生态独立最硬的一刀，从此它不再是"另一个安卓"，而是真正自研的操作系统。

### 4. [移动] ArkTS 任务池与 ArkData 增强：鸿蒙并发存储升级

> 📍 **导语**（约 120字）：在 HarmonyOS NEXT 阶段，ArkTS 与 ArkData 两套基础能力同步大幅增强：TaskPool 新增任务组、串行队列与任务监控，ArkData 的 RDB 引入全文检索与只读配置。对鸿蒙原生开发者而言，这是并发模型与本地数据层的一次关键补强，直接降低了复杂后台任务的编写门槛，也为离线优先应用打下地基。

**核心信息**（约 450字）：ArkTS（方舟编程语言）在并发能力上的增强是本次重点。TaskPool 新增任务组（TaskGroup）、串行队列、长时任务、任务取消、宿主通信、任务监听与任务依赖关系，并新增受限 Worker 能力；`SequenceRunner` 可构造全局串行队列，任务执行优先级新增 `IDLE` 表示后台任务。TaskPool 还提供任务监控能力，可对"入队、开始执行、成功、失败"等状态进行回调，便于做后台任务的进度与可观测性，过去只能靠轮询或手写计数器的场景现在框架原生支持。Sendable 体系扩展：`Uint8ClampedArray` 与 `Function` 类型支持 Sendable，JSON 支持 BigInt 解析，这对跨线程传递大对象与回调函数是实打实的可用性提升，减少了序列化拷贝。

数据流方面，ArkTS 新增流基础能力（读、写、双工、转换），并优化了 `TextDecoder`、`buffer`、`uri` 等模块性能。新增的方舟字节码函数命名规则也利于逆向与调试定位，发布后的崩溃栈更易读。

ArkData（方舟数据管理）层面，Preference 新增 BigInt、Object 类型存储与按 key 的变更订阅；RDB 新增 BigInt 支持、`attach`/`detach`/`notContains`、变更通知携带数据 ID、TS 同步 API，并新增 `isReadOnly` 只读配置与 SQL 执行时间统计；更重要的是引入 `@ohos.data.sendableRelationalStore`，使 RDB 支持 sendable 能力，并可在 RDB 中引入支持全文检索（FTS）的动态库——这对本地搜索、笔记、离线邮箱等场景意义重大，不必再引入第三方搜索引擎。UDMF 预定义 UTD 类型从 80 种扩展到 120 种，并支持自定义 UTD。

Ability Kit 新增基于 `ModularObjectExtensionAbility` 的模块化对象，允许应用把自身功能以模块化对象形式开放给其他应用调用，强化了鸿蒙分布式能力的"能力开放"语义，跨应用协同从隐式意图走向显式模块。

**判断**（约 190字）：短期看，TaskPool 的任务组与监控让后台并发从"能跑"变"可观测、可取消"，存量项目应逐步用 TaskPool 替代裸 Worker；RDB 的 FTS 与 sendable 支持则让本地搜索与跨线程数据访问不再需要自行造轮子，开发量明显下探。中长期看，ArkTS 正把"并发安全"做成语言级默认（Sendable 持续扩张），配合 ArkData 的本地智能，为端侧 AI 与离线优先应用打底，未来鸿蒙原生应用会更敢把重逻辑放本地。一句话本质：鸿蒙把"并发加本地数据"两块硬地基在 NEXT 阶段一次补齐，开发者终于不必在基础能力上反复踩坑。

🔗 **来源：** 华为开发者文档（2026，HarmonyOS NEXT 新增和增强特性 os-new-feature-500）/ 华为 DevEco Studio 26.0.0 发布说明（2026-08-29）

### 5. [移动] KMP 跨平台UI稳定：Compose Multiplatform 1.10 与 Koog 代理框架

> 📍 **导语**（约 120字）：Kotlin Multiplatform（KMP）在 2025–2026 年迎来采用率跳升，JetBrains 同步把 Compose Multiplatform 1.10 推进到稳定，并推出 Kotlin 原生的端侧 AI 代理框架 Koog。对想"共享逻辑、保留原生 UI"的团队，KMP 正在成为 Flutter 与 RN 之外的第三条务实路径，尤其适合已有 Kotlin 资产的团队做 iOS 扩张。

**核心信息**（约 450字）：Compose Multiplatform 1.10.0（2026 年 1 月）带来了统一预览、Navigation 3 与稳定的 Hot Reload，且 Compose Multiplatform for iOS 已正式稳定。这意味着同一套声明式 UI 代码可覆盖 Android、iOS、桌面与 Web，而业务逻辑的共享比例通常在 80% 以上。对 Kotlin 团队，这避免了为跨端再学一门 Dart 或 JS，复用既有的协程、序列化与依赖注入体系，迁移心智负担远低于切换到全新语言栈。

JetBrains 在 AI 工具链上的布局是本次最大亮点：推出 Koog 框架，一个用 Kotlin 编写、可在设备端运行并与工具交互的 AI 代理框架；配合 JetBrains 自有的 Mellum（为 Kotlin 微调的 LLM）与 AI 编码代理 Junie，形成"从开发到运行"的本地智能闭环。由于 KMP 直接调用原生 SDK，iOS 侧可用 Core ML、Android 侧可用 ML Kit 与 NNAPI，没有桥接开销，这让端侧推理的集成比 RN 的 NativeModule 路径更直接，也更容易拿到各平台最新的硬件加速能力。

采用数据支撑了这股势头：KMP 使用率在受调开发者中从 2024 年的约 7% 升至 2025 年的约 18%，Kotlin 全球开发者约达 250 万；Compose Multiplatform 的 iOS 稳定让"Kotlin 写全端"从实验走到生产。与 Flutter 相比，KMP 的哲学是"UI 平台原生、逻辑共享"，因此能天然获得各平台的新设计语言（如 iOS 的 Liquid Glass），而无需社区手动重绘；代价是 UI 层需为每端维护，学习曲线对来自 JS 或 Swift 的开发者偏陡，且 SwiftUI 侧的 Compose 仍属较新领域，组件覆盖度不及 Android 侧成熟。在大型工程里，KMP 的代码共享还能显著降低双端业务逻辑分叉导致的缺陷率，这是许多企业最终选型它的决定性因素。

**判断**（约 210字）：短期看，KMP 加 Compose Multiplatform 适合已有 Kotlin 或 Android 团队做 iOS 扩张，Koog 则为"端侧 Agent"提供了少有的语言原生方案，省去在 Kotlin 业务里嵌一套 Python 或 JS 推理服务的割裂，也让端侧智能与既有协程体系天然融合。中长期看，在"共享多少"的光谱上，KMP 占据"重逻辑共享、轻 UI 共享"一端，与 Flutter 的"全自绘"、RN 的"原生组件"形成三角，企业可按团队构成选型，不必再押注单一框架。对招聘市场而言，Kotlin 人才池远大于 Dart，这也是 KMP 在企业级项目里更被青睐的隐性原因。一句话本质：KMP 把"跨平台"重新定义成"跨逻辑"，而非"跨界面"，让原生体验与代码复用不再二选一。

### 6. [移动] Android 17 Beta 4.1 与 Play 开发者验证政策落地

> 📍 **导语**（约 120字）：2026 年 9 月，Android 17 Beta 4.1 开放兼容性测试，聚焦后台音频加固与应用内存上限；同时 Google Play 的新规进入关键窗口——target SDK 36 强制、AAB 格式与面向开发者的身份验证（developer verification）将于 9 月生效。对 Android 开发者，这是平台能力与合规双重收紧的一个月，上架前必须预留适配时间。

**核心信息**（约 450字）：Android 平台侧，Android 17 Beta 4.1（2026-06-01 进入 Beta 通道，9 月持续迭代）突出的新特性包括"后台音频加固"（background audio hardening）与"应用内存上限"（app memory limits），前者约束后台媒体的资源占用与播放行为，后者对低端机与多任务场景的内存使用设了更明确的边界，要求开发者重新审视后台服务、媒体播放与缓存策略，避免被系统强杀。Wear OS 7 也已 stable，带来动态表盘与 Live Updates，手表应用需用官方模拟器验证。

合规侧是更重的负担。2026 年 Google Play 要求新应用与目标更新至少 target API 36（对应 Android 16/17 一代），并以 AAB（Android App Bundle）为唯一上架格式；更关键的是"开发者身份验证"新政于 2026 年 9 月生效——Google 要求账号层面的实名或组织验证，意在压缩恶意批量上架与欺诈类应用。配合欧盟 DMA 下的侧载与第三方商店规则，Android 分发正从"开放上传"走向"可追责上架"。对出海与中小团队，这意味着上架前需预留身份验证与政策适配时间，否则会被拒或下架，尤其是批量马甲包与未实名的个人开发者受影响最直接。值得注意的是，target API 的逐年抬升也迫使开发者持续跟进权限模型与后台限制的变化，技术债不能无限期拖延。

**判断**（约 210字）：短期看，Android 17 的后台与内存约束要求存量 App 做一轮资源治理，Play 的开发者验证则是 9 月必须完成的合规动作，错过窗口将中断上架节奏，尤其是计划当月发版或紧急修复的团队需提前排期。中长期看，Google 用 target API 强制加身份验证把 Android 生态的"准入门槛"抬高，安全与隐私叙事向 iOS 看齐，但代价是上架摩擦上升，小团队与个人开发者的试错成本变高。对依赖多账号矩阵或马甲包买量的商业模式，这套政策是结构性收紧。一句话本质：Android 的"开放"正在被重新定义为"可问责的开放"，分发自由度让位于生态安全，合规能力成为上架的前置竞争力。

### 7. [移动] Flutter 3.47 与 RN 0.87：跨平台新架构全面默认

> 📍 **导语**（约 120字）：截至 2026 年 9 月，跨平台双雄同步进入"生产期"：Flutter 稳定在 3.47.1（Dart 3.13.1），Impeller 渲染引擎在移动与桌面全平台默认；React Native 0.87 默认启用 New Architecture，且自 0.82 起彻底移除旧 Bridge。两者都把历史性能短板补平，选型回归"团队匹配"而非"谁更快"，跨平台正式成为多数 B2C App 的默认起点。

**核心信息**（约 450字）：Flutter 3.47（2026-08-12 发布线，稳定版 3.47.1 于 8 月 19 日）带来三件要事：Impeller 成为 macOS、Windows、Linux 的默认渲染引擎，移动端早已默认，Skia 的 shader 编译卡顿基本成为历史；Material 与 Cupertino 组件库移出核心 SDK，成为 pub.dev 上独立的 `material_ui` 与 `cupertino_ui` 1.0 包，加快 UI 更新并缩减自定义设计系统的包体积；Apple 最低支持抬到 iOS 15 与 macOS 12。Flutter 还通过官方 MCP 服务器把项目暴露给 AI 编码代理，Agentic Hot Reload 与 Widget Previews 稳定化，开发者体验向"AI 协作"演进。实测复杂列表加自定义动画约 58–60fps，中端 Android 冷启动 200–400ms，动画重负载场景优势明显。

React Native 0.87（2026-08）则标志着 New Architecture 全面成熟：自 0.76 起 Fabric、JSI、TurboModules 为新项目默认，0.82 起彻底移除旧 Bridge，JSI 让 JS 直接持有 C++ 对象引用、消除 JSON 序列化开销，TurboModules 按需懒加载显著压低启动内存；Hermes V1 为默认引擎，0.87 将严格 TypeScript API 设为默认。RN 与 npm 生态无缝复用，复杂页面帧率约 52–56fps，与原生差距压缩到 8% 以内，旧架构的卡顿标签被撕掉。值得注意的是，2026 年 6 月起 RN 移交独立 React Foundation 治理，摆脱单一公司控制，社区路线的可预期性增强。

社区数据：Flutter GitHub star 约 17.8 万、RN 约 12.6 万（2026-07）。两者都提供官方 MCP/AI 协作路径，说明跨平台框架已把"AI 辅助开发"视为标配能力而非噱头，对团队招聘与上手速度都有实质助益。从发布的节奏看，Flutter 走季度稳定、RN 约两月一版，可预期性都较高，团队排期风险可控，这也是企业愿意把核心产品押在跨平台上的底气所在。

**判断**（约 210字）：短期看，两个框架都"生产可用、性能持平"，Flutter 胜在 UI 一致性与动画，RN 胜在原生质感与 JS 团队复用；选谁主要看团队语言背景与是否要像素级一致，而不是 benchmark 上的微小差距，招聘到对应语言的人往往比框架特性更关键。中长期看，RN 的独立治理与 Flutter 的"生产期"定位都指向跨平台不再是妥协选项，而是多数 B2C App 的默认起点，原生双端开发将更多留给对性能极致敏感或强平台定制的场景。对预算有限的中小团队，跨平台相对双端原生可省三到五成成本，这笔账在 2026 年依旧成立。一句话本质：跨平台之争从"性能赛"转入"团队赛"，框架成熟度已不再是决策的主要变量，人岗匹配才是。

### 8. [移动] 端侧AI开发选型：Foundation Models与Gemini Nano对比

> 📍 **导语**（约 120字）：2026 年端侧 AI 从"概念"走向"默认路径"：Apple 的 Foundation Models 框架与 Android 的 Gemini Nano（经 AICore）让第三方 App 免推理费、离线可用地调用设备小模型。对移动开发者，选对端侧推理框架，直接决定隐私、成本与体验下限，也决定能否在弱网与离线场景保住核心功能。

**核心信息**（约 450字）：Apple 侧，Foundation Models 框架是原生 Swift API，把 Apple Intelligence 核心的端侧大模型直接开放给第三方 App，支持引导生成（guided generation）、工具调用（tool calling）与多模态提示，且仅在兼容 Apple Intelligence 的设备上运行——这是真实的设备约束，需在代码中做能力检测与降级。更低层的 Core ML 仍为自定义非 LLM 模型（图像分类、音频、领域文本）提供与 Neural Engine、GPU、CPU 的自动硬件调度，模型经 `coremltools` 转成 `.mlpackage` 即可，而 `@available` 下的 Apple Intelligence API（Writing Tools、Image Playground、Siri intent）则无需自带模型，调用系统模型即可获得通用语言与图像能力。

Android 侧，Gemini Nano 经 AICore 以 Generative AI for Android API 暴露（开发者预览，覆盖部分机型），集成模式是先做能力检查、再初始化模型下载、后以本地推理调用；`InferenceMode.PREFER_ON_DEVICE` 标志在本地可用时走端侧、否则回退云端，这种混合策略务实但要求从第一天就设计降级路径，否则低覆盖机型会直接不可用。ML Kit GenAI 则提供开箱即用的摘要、校对、图像描述；自定义模型走 LiteRT（TF Lite 继任者，支持 LiteRT-LM 跑紧凑 LLM）或 MediaPipe 视觉与音频管线。

横向对比：Core ML 在 Apple 硬件上延迟最优（常见视觉任务低于 10ms，借助 ANE），但锁定 iOS 与 macOS；ML Kit 跨 Android 与 iOS、预建 API 上手快，但灵活度低于 Core ML；ONNX Runtime Mobile 适合 PyTorch 训练、跨平台统一运行时。安全上，端侧模型解决了数据出设备的问题，但模型文件可被提取、需静态加密与（可用时）安全 enclave，越狱或 root 设备需有降级方案，不能默认端侧就一定安全。

**判断**（约 210字）：短期看，优先用平台自带 SLM（Foundation Models 与 Gemini Nano）覆盖摘要、改写、标注等通用任务，免去推理费与隐私合规成本；自定义模型再上 Core ML 或 LiteRT，且务必做模型文件静态加密以防提取。中长期看，端侧 AI 会成为移动 App 的"基础能力层"，离线优先、隐私优先的体验将成标配，开发者应把"能力检测加云端降级"做成标准架构，而非临时补丁，否则低覆盖机型会直接功能缺失。对监管行业，端侧推理还能规避数据出境的合规风险，是比云端更稳的选型。一句话本质：端侧 AI 的胜负手不是模型多大，而是"何时下云、何时上云"的调度，调度策略决定体验与成本的天花板。
