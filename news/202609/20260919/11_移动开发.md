### 1. 【SwiftUI 2026年9月更新：ArrangementView 自适应布局与 iPhone Duo 铰链支持】

> 📍 **导语**：Apple 在 2026 年 9 月的 SwiftUI 更新中一次性推出多项面向多形态设备的能力，核心是新增的 `ArrangementView` 自适应布局容器、用于规避硬件遮挡区域的 `ReservedRegion` API，以及针对传闻中的双屏设备 iPhone Duo 的铰链状态监听。这几项更新把 SwiftUI 从"单屏自适应"推向"折叠/双屏形态自适应"，对正在做 iPad、Vision Pro 与未来双屏设备的团队影响最直接。

---

**📱 深度报道**

**▌ 更新全景**：本次 9 月更新隶属于 Xcode 27 之后的 SwiftUI 持续演进线，并未改变声明式范式，而是在布局与硬件感知两个维度补齐能力。`ArrangementView` 提供了一套"主—次"内容自适应排布容器，开发者可用 `arrangementViewStyle(_:)` 选择 `split`（并排）或 `overlay`（层叠）两种风格，并通过 `splitArrangementLayoutRatio` 设置主次视图尺寸比例。`ReservedRegion` 让视图能识别摄像头开孔、铰链等硬件保留区域，使用 `reservedRegions(kind:options:layoutDirectionBehavior:)` 查询相交区域。铰链方面新增 `onHingeChange(isEnabled:_:)` 与 `DeviceHingeContext`，可读取 `.closed`/`.partiallyOpen`/`.fullyOpen` 状态与角度。整体定位是降低多形态设备的布局迁移成本。

**▌ 技术细节深解**：`ArrangementView` 的关键在于它把"环境自适应"内建进布局系统，而非让开发者手写 `GeometryReader` 判断宽度。下面是一段典型的 split 布局配置：

```swift
ArrangementView {
    PrimaryContent()
} secondary: {
    SecondaryContent()
}
.arrangementViewStyle(.split)
.splitArrangementLayoutRatio(
    minHorizontal: 0.3, idealHorizontal: 0.4, maxHorizontal: 0.6
)
.axes([.horizontal])
```

对于铰链，设备姿态变化通过环境值下发，开发者无需手动订阅通知：

```swift
.onHingeChange { isEnabled in
    print("Hinge enabled: \(isEnabled)")
}
// 在子视图中读取
let hinge = DeviceHinge.current
switch hinge.status {
case .fullyOpen:  // 平铺
case .partiallyOpen:  // 半折
default: break
}
```

`ReservedRegion` 的查询返回不透明 `ReservedRegion.ID`，可在坐标空间间追踪，便于在双屏应用里把安全内容推离铰链遮挡区。

**▌ 开发者迁移指南**：本次为增量 API，不破坏现有 `NavigationStack`/`Grid` 代码，最低部署版本需指向包含该更新的 SDK（Xcode 27 构建链）。建议的升级步骤：先为现有多屏/分屏视图引入 `ArrangementView` 替换手写 `HStack`+`GeometryReader` 方案；对带摄像头开孔的页面用 `reservedRegions` 做避让；若计划支持双屏设备，新增 `onHingeChange` 监听并打磨半折态的 UI 过渡。Breaking Changes 方面本次无强制移除，但 6 月更新中 `@State` 已要求改用 `State()` 宏、`ContentBuilder` 统一替代类型特定 builder，需一并确认已迁移。

**▌ 生态与竞品对比**：相比 Jetpack Compose 的 `WindowSizeClass` 与鸿蒙 ArkUI 的栅格与折叠屏适配方案，SwiftUI 此次把"折叠/双屏"作为一等公民直接下沉到布局原语，思路更贴近声明式。社区层面，SwiftUI 在 2026 年已成为新项目默认选择，Dev.to 等社区的"生产可用"讨论热度持续走高，国内掘金、InfoQ 均有跟进教程。

---

**🤖 开发研判**

🔮 **技术趋势**：这是 SwiftUI 从"单屏声明式"走向"全形态声明式"的明确信号，与 iPad 多窗口、Vision Pro 空间计算、未来双屏硬件形成统一布局语言，符合 Apple 平台收敛的趋势。

📊 **开发者决策影响**：存量 App 不必立即重构，但凡是涉及分屏、多窗口或计划登陆双屏设备的项目，现在就该评估用 `ArrangementView` 替代手写自适应逻辑，能显著减少维护成本。新项目建议直接采用。

⚠️ **适配风险**：`ArrangementView` 与 `ReservedRegion` 依赖最新 SDK，若团队需兼容旧系统版本会存在可用性判断问题；双屏铰链 API 目前面向尚未广泛铺货的硬件，存在"写好了设备未普及"的风险。

💡 **学习优先级**：优先掌握 `ArrangementView` 的 split/overlay 两种风格与比例控制 → 其次 `ReservedRegion` 避让策略 → 最后铰链状态机设计；推荐以 Apple 官方 SwiftUI 更新文档与 Dev.to 实战文章为入口。

### 2. 【App Store 欧盟新商务条款10月1日生效：核心技术费改为5%佣金】

> 📍 **导语**：Apple 在 2026 年 8 月 18 日宣布、将于 10 月 1 日生效的欧盟统一商务条款，是 DMA 落地以来最重大的一次商业模式调整：原先争议巨大的"核心技术费（Core Technology Fee, CTF）"被取消，取而代之的是费率更清晰的 5% 佣金结构，并首次把分散的多套欧盟条款合并为单一附件（Attachment 14）。对面向欧盟分发的开发者而言，分发方式与支付路径的选择将直接决定费率。

---

**📱 深度报道**

**▌ 更新全景**：新规以"单一商务条款"取代过去 Alternative Terms Addendum 与 StoreKit External Purchase Link 等多套并存的复杂结构，开发者不再需要在组合矩阵里算账。费率按"分发渠道 × 支付方式"两段计收：App Store + Apple IAP 为 26%（小规模与订阅优惠档可至 15%）；App Store + 替代应用内支付为 20%；App Store 引导至外部网站购买为 15%；替代应用市场 / Web 分发为 5%。此外，开发者选定支付路径后需保持 12 个月不变，以保证条款一致性。该调整是对欧盟委员会 2025 年 4 月裁定 Apple 违反 DMA 反引导义务、罚款 5 亿欧元后的进一步妥协。

**▌ 技术细节深解**：对开发者来说，条款变化落到工程上是 Entitlement 与支付链路的选择。若采用外部购买链接，需在 `Info.plist` 中声明对应 Entitlement 并遵循 UX 规范：

```xml
<key>com.apple.developer.storekit.external-purchase-link</key>
<true/>
```

若走替代应用市场或 Web 分发（5% 档），则需接入市场方的安装与计费凭证体系，并在 App 内做好"App Store 版"与"外部版"的功能/计费分支。StoreKit 2 的 `Transaction` 与 `Product` 仍是统一接口，真正的差异在后端对账与税务处理。

**▌ 开发者迁移指南**：无需改代码即可继续用 Apple IAP（26% 档），但需重新评估是否值得切到 20%/15%/5% 档。迁移要点：① 在 App Store Connect 中确认目标商务条款附件已绑定；② 若启用外部支付/链接，补齐 Entitlement 与合规落地页；③ 重新设计订阅的"12 个月锁定"提示，避免用户中途切换造成对账混乱；④ 欧盟税率与退款规则仍需自行处理。建议中小开发者先用模拟器跑通外部链接 UX，再小流量验证。

**▌ 生态与竞品对比**：相较 Google Play 在 Epic 和解后于 2026 年 6 月 30 日开放的 Billing Choice（美国/EEA/英国 10% 服务费 + 可选 5% 计费费），Apple 的欧盟费率整体偏高但结构更扁平。Epic 等第三方商店借此获得更低分发成本，开发者跨平台定价策略正在重排。国内开发者若仅服务非欧盟市场，本次影响有限，但出海欧洲的项目必须重新建模毛利。

---

**🤖 开发研判**

🔮 **技术趋势**：DMA 驱动的"分发多渠道 + 支付可替代"已成不可逆趋势，平台抽成从"一刀切"转向"按路径阶梯计费"，未来更多地区可能跟进类似结构。

📊 **开发者决策影响**：对欧盟用户占比高的订阅类 App，切到 15% 外部网站档能显著降本，但要权衡 Apple 支付带来的转化与信任溢价；对免费 + 内购型应用，26% 档仍是稳妥默认。建议在 10 月 1 日前完成条款评估与落地页设计。

⚠️ **适配风险**：12 个月锁定意味着选错路径短期内无法回退；外部支付需自行承担欺诈与 PCI 合规；Apple 仍可能在审核中对手动引导文案设限，存在合规灰色地带。

💡 **学习优先级**：先理解 Attachment 14 费率矩阵 → 再掌握外部购买 Entitlement 配置 → 最后建立欧盟分账与税务流程；推荐以 The Useful Apps、Frandroid 的政策解读与 Apple 官方条款为准。

### 3. 【HarmonyOS 7.0 ArkUI 升级：文本选择、2D绘图抗锯齿与 ArkWeb 增强】

> 📍 **导语**：HarmonyOS 7.0 已于 2026 年 9 月 7 日正式发布，在 6.1 基础上对 ArkUI 方舟 UI 框架做了多项面向开发者的实用增强：文本控制器新增可编程选择能力、Canvas 2D 绘图支持运行时开关抗锯齿、ArkWeb 新增模拟点击检测等。这些看似细节的 API 调整，直接解决了长列表文本交互、图形渲染质量与 Web 混合开发调试三类高频痛点。

---

**📱 深度报道**

**▌ 更新全景**：本次升级聚焦"交互精度"与"渲染可控"。在 ArkUI 文本体系，`TextController` 新增 `setTextSelection` 方法，可在非长按场景下主动设置并高亮文本选择区域；在图形体系，`CanvasRenderingContext2D` 与 `OffscreenCanvasRenderingContext2D` 的构造函数已支持 `RenderingContextSettings`，现在进一步允许在构造后修改 `antialias` 属性，随时开关文本抗锯齿；ArkWeb 侧新增 Web 应用模拟点击检测能力，便于自动化测试与无障碍校验。配合 ArkUI 状态管理 V2（`@ObservedV2`/`@Trace`）的成熟，列表渲染控制推荐使用 `Repeat` 替代 `ForEach`。

**▌ 技术细节深解**：`setTextSelection` 让开发者能把"选中并复制"从手势依赖中解放出来，例如点击按钮即选中某段关键信息：

```typescript
// ArkTS
controller: TextController = new TextController()
build() {
  Text(this.content)
    .fontSize(16)
    .copyOption(CopyOptions.Local)
    .controller(this.controller)
  Button('选中摘要')
    .onClick(() => {
      this.controller.setTextSelection({ start: 0, end: 10 })
    })
}
```

Canvas 抗锯齿的运行时开关则对"先渲染后调质量"场景极有用：

```typescript
let settings: RenderingContextSettings = new RenderingContextSettings(true)
let ctx: CanvasRenderingContext2D = new CanvasRenderingContext2D(settings)
// 构造后随时切换
ctx.antialias = false // 关闭文本抗锯齿以提速
```

注意 `setTextSelection` 在 `copyOption` 为 `None` 或 `textOverflow` 为 `MARQUEE` 时无效。

**▌ 开发者迁移指南**：HarmonyOS 7.0 为增量升级，现有 6.1 应用可平滑过渡。建议步骤：① 评估长列表文本交互，用 `setTextSelection` 替代手势依赖逻辑；② 对图表/文字密集的 Canvas 场景引入 `antialias` 动态控制以平衡性能；③ ArkUI 状态管理由 V1 向 V2 迁移，用 `Repeat` 替换 `ForEach`（需 `@ObservedV2`+`@Trace` 配合）；④ DevEco Studio 升级到配套版本并跑通 ArkWeb 模拟点击测试。Breaking 方面，`Stepper`/`StepperItem` 相关修饰器在 6.0.2 已被标记废弃版本变更，需留意后续移除。

**▌ 生态与竞品对比**：相比 SwiftUI 的 `Text` 选中更多依赖系统菜单、Compose 的 `SelectionContainer`，鸿蒙把选择能力以控制器方法暴露，更利于业务主动触发。国内鸿蒙原生应用适配进入加速期，ArkTS + ArkUI 的声明式范式与 Flutter/Compose 思路接近，社区教程（今日头条"人人都是产品经理"系列、华为开发者联盟文档）已较完善。

---

**🤖 开发研判**

🔮 **技术趋势**：鸿蒙 7.0 延续"把系统级能力下沉为细粒度 API"的路线，文本、绘图、Web 三大高频场景的精细化控制，说明华为正补齐原生应用开发的细节体验，对标 iOS/Android 成熟框架。

📊 **开发者决策影响**：存量鸿蒙应用值得在本次大版本窗口顺手接入 `setTextSelection` 与 `antialias` 控制，用户体验增益明显且迁移成本低；新项目应直接采用状态管理 V2 与 `Repeat`，避免后续二次迁移。

⚠️ **适配风险**：`setTextSelection` 的失效边界需逐一验证；`antialias` 运行时切换在低端设备上的性能收益需实测；V1→V2 迁移对大型项目有改造量，建议分模块灰度。

💡 **学习优先级**：先掌握 `TextController.setTextSelection` 与 Canvas `antialias` → 再推进状态管理 V2（`@ObservedV2`/`@Trace`/`Repeat`）→ 最后熟悉 ArkWeb 模拟点击；推荐华为开发者联盟官方文档与《鸿蒙 HarmonyOS 6 应用开发》系列。

### 4. 【Android 17 QPR1 Beta 2：照片选择器强制、作用域存储清理与自适应布局合规】

> 📍 **导语**：Android 17 QPR1 Beta 2 延续了 Google 在隐私与多形态适配上"先软后硬"的一贯节奏，把多项此前"推荐"的能力正式推向 Play 审核与平台行为的强制信号：照片选择器（Photo Picker）绕过将被标记、作用域存储的历史例外进入硬移除倒计时、Health Connect 成为健康数据唯一合规路径、大屏自适应布局合规通过 Play Console 警告落地。对消费类与健身类应用，这是一次明确的迁移时钟。

---

**📱 深度报道**

**▌ 更新全景**：本次 Beta 2 的开发者关键变化集中在三桶：隐私强制升级、自适应布局合规、后台进程收紧。隐私侧，存活到 Android 16 的作用域存储例外被废弃并给出硬移除时间线；Photo Picker 不再是"建议"，目标 API 36 且绕过的应用将在 Play 审核中被标记。健康侧，Health Connect 从可选变为健身/健康类应用的唯一合规数据路径。布局侧，大屏兼容性指南通过 Play Console 质量检查落地警告。后台侧，Android 14 引入的前台服务类型要求进一步收紧，部分原本豁免的服务类型现在需要显式用户同意流。

**▌ 技术细节深解**：对直接申请媒体权限的应用，需迁移到系统 Photo Picker 或带过滤访问的 MediaStore：

```kotlin
// 使用系统 Photo Picker 替代 READ_MEDIA_IMAGES
val intent = PickVisualMediaRequest.Builder()
    .setMediaType(ActivityResultContracts.PickVisualMedia.ImageOnly)
    .build()
pickMedia.launch(intent)
```

作用域存储例外移除意味着过往用 `requestLegacyExternalStorage` 的代码将失效，需全面改用 `MediaStore` 与 `Storage Access Framework`。自适应布局方面，应在 `WindowSizeClass` 基础上补齐折叠/平板分支，避免触发 Play Console 警告。

**▌ 开发者迁移指南**：① 检索项目中的 `READ_MEDIA_IMAGES`/`READ_MEDIA_VIDEO`，改用 Photo Picker 或过滤式 MediaStore；② 复核 `requestLegacyExternalStorage` 与 `manageExternalStorage` 的使用，制定移除时间表；③ 健康类应用审计 Health Connect 接入，替换自定义 provider/传感器直读；④ 用 `WindowSizeClass` 重写大屏/折叠屏布局并跑 Play Console 预检；⑤ 梳理前台服务类型，补用户同意流。Google 的隐私限制"从软警告终成硬门槛"已成定式，建议在稳定版发布前完成。

**▌ 生态与竞品对比**：iOS 侧通过 DMA 与系统级隐私面板收口，Android 则靠 Play 审核 + 平台行为双管齐下。相比鸿蒙在权限上的集中治理，Android 的碎片化使其强制节奏更依赖 Play 这一分发闸门。社区（Kunal Ganglani 等独立博客、Android Police）对此次 Beta 的"软公告→强执行"模式已有充分预警。

---

**🤖 开发研判**

🔮 **技术趋势**：Android 的隐私治理正沿"可选 API → 推荐 → 强制"的经典曲线推进，多形态适配也从"建议指南"转为"审核信号"，平台对开发者的约束力持续增强。

📊 **开发者决策影响**：照片/社交媒体类、健康健身类、后台定位类应用受冲击最大，应立刻启动迁移评估；新项目应默认采用 Photo Picker、Health Connect 与响应式布局，避免上线即踩坑。

⚠️ **适配风险**：作用域存储例外移除可能导致历史文件访问逻辑崩溃；Health Connect 迁移动钟一旦启动，旧数据迁移易出错；大屏警告虽暂非硬拒绝，但按 Google 历史必会升级为硬性要求。

💡 **学习优先级**：先吃透 Photo Picker 与 MediaStore 过滤访问 → 再掌握 Health Connect 数据读写 → 最后补齐 `WindowSizeClass` 响应式布局；推荐 Android Developers 官方迁移文档与 Android Police 政策解读。

### 5. 【Android 17 权限收紧与开发者身份验证：联系人/位置选择器与25美元验身门槛】

> 📍 **导语**：Android 17 在分发与权限两端同步收紧：所有目标 Android 17 及以上的 Play 应用必须使用新的系统联系人选择器与一次性位置"按钮"，持续权限需提交声明；同时自 2026 年 9 月起，认证 Android 设备上的每一款应用（无论是否通过 Play）都必须来自完成身份核验的开发者——需政府证件 + 一次性 25 美元费用。两条线共同把"权限滥用"与"匿名劣质应用"的生存空间进一步压缩。

---

**📱 深度报道**

**▌ 更新全景**：权限侧，Google 把 Android Contact Picker 定位为默认联系人共享方式，用户可只选特定联系人而非交出整个通讯录；`READ_CONTACTS` 等宽泛权限仅保留给能证明功能必需的应用。位置侧引入系统级"位置按钮"，一次性精确位置授予只需一次交互，持续/后台定位需开发者声明。分发侧，Advanced Protection Mode 下仅带 `isAccessibilityTool="true"` 的辅助功能应用可保留 AccessibilityService 深权限，银行木马常用的滥用入口被封；开发者身份验证则要求 9 月起所有安装来源的应用都来自已验身开发者。审核侧，联系人与位置问题自 10 月 27 日起在送审前被标记。

**▌ 开发者迁移指南**：① 检索 `READ_CONTACTS`/`READ_MEDIA*` 等宽泛权限，改为 Contact Picker / Photo Picker；② 持续定位场景准备开发者声明材料，说明业务必需性；③ 辅助功能类应用如确需 AccessibilityService，注册 `isAccessibilityTool="true"` 属性；④ 在 9 月前完成开发者身份验证，否则新应用无法安装到认证设备；⑤ 关注 10 月 27 日前的 Play 预检警告，提前修联系人/位置合规项。

**▌ 生态与竞品对比**：Apple 在欧盟以 DMA 与 Notarization 做分发治理，Google 则以"身份验证 + Play Protect 强制 + 权限收口"组合拳覆盖全球。相较之下，Android 的 25 美元验身与中心化注册被 EFF、F-Droid 等指为对匿名开发者（记者、活动者）的潜在威胁，争议更大但执行更彻底。

### 6. 【Flutter 4.0 发布：Impeller 2.0 渲染引擎与 Dart 4 静态元编程】

> 📍 **导语**：Flutter 4.0 正式落地，是自 3.x 以来最具野心的一次跨平台跃迁：渲染引擎升级到 Impeller 2.0（Vulkan/Metal/WebGPU 全后端）、语言配套 Dart 4.x 引入静态元编程（编译期宏），并把 AI 原生工作流（Agentic Hot Reload、Flutter AI Toolkit）纳入核心。相比被覆盖的 Expo SDK 56 构建链，本次聚焦的是 Flutter 自研引擎与语言层的代际升级，对包体积与帧率有可直接量化的收益。

---

**📱 深度报道**

**▌ 更新全景**：Flutter 4.0 构建于 Google I/O 2026 的 3.44/Dart 3.12 基础之上。Impeller 2.0 把预编译着色器管线扩展到所有平台：Android/Linux 用 Vulkan、iOS/macOS 用 Metal、Web 用 WebGPU。官方基准显示相比 3.44 平均帧渲染时间下降约 35%，复杂动画下维持 120fps，引擎内存占用约降 20%。Dart 4.x 是继 2.12 空安全后最大的语言更新，带来静态元编程（宏），可在编译期生成 JSON 序列化、依赖注入与数据类，免去外部 build_runner；另有密封接口、值类型与增强 FFI。包体积方面 4.0 应用比 3.44 小约 15%。AI 侧 Agentic Hot Reload 通过 Dart MCP Server 让编码代理直接操作运行中的应用。

**▌ 技术细节深解**：Dart 4 的静态元编程让重复样板显著减少，示意如下：

```dart
// 编译期生成序列化/相等/拷贝，无需 json_serializable
@DataClass()
class Article {
  final String id;
  final String title;
  const Article(this.id, this.title);
}
// 等价手写样板由宏在编译期展开
```

Impeller 2.0 在 Android 16（API 36）上借助 Vulkan 1.4 与 HardwareBuffer 原子更新，把动态纹理上传延迟降低约 35%；构建阶段即预编译 SPIR-V 着色器，彻底消除首帧卡顿。WebGPU 后端为 Web 目标带来接近原生的渲染质量。

**▌ 开发者迁移指南**：多数项目可用 `flutter upgrade` 平滑升级，少量 breaking change 已配迁移指南。要点：① 确认 Skia 后端在新项目中已废弃，统一走 Impeller；② Dart 4 对旧模式给出弃用警告，逐步替换手写生成代码；③ 评估 Agentic Hot Reload 与团队 AI 工具链的接入（需 Dart MCP Server）；④ 桌面目标（Win/Mac/Linux）现已与移动端在可访问性、输入、窗口管理上对齐，可顺势推进桌面化。建议先在独立分支验证再全量。

**▌ 生态与竞品对比**：相较 React Native 0.8x 仍在 New Architecture/Fabric 上打磨、Compose Multiplatform 1.12 刚接 Hot Reload MCP，Flutter 4.0 的优势在"自研渲染引擎 + 语言级元编程"带来的确定性能收益。Flutter 官方 2026 路线图还提出 GenUI/A2UI 协议与"即时字节码"以支持真正的 agentic UI，跨平台赛道正从"写一次"转向"AI 动态生成 UI"。

**🤖 开发研判**

🔮 **技术趋势**：Flutter 4.0 标志跨平台框架进入"引擎自研 + 语言内元编程 + AI 原生"的三重合力阶段，性能与开发效率的边界被同时推高，且把 agentic UI 列为下一步路线。

📊 **开发者决策影响**：对追求一致渲染质量与更小包体积的新项目，Flutter 4.0 是强候选；存量 3.x 项目建议在本年度窗口评估升级，享受 15% 体积与 35% 帧率收益。但需评估 Dart 4 宏生态成熟度与团队学习曲线。

⚠️ **适配风险**：Dart 4 宏仍为较新特性，第三方库适配需要时间；WebGPU 后端依赖浏览器支持，旧设备回退路径需验证；Agentic Hot Reload 接入 MCP 对工程隐私与流程有新要求。

### 7. 【移动端端侧AI框架选型2026：Core ML、ML Kit、TensorFlow Lite 与 Gemini Nano 落地】

> 📍 **导语**：2026 年移动端 AI 正从"云端 API 调用"全面转向"端侧推理"。对开发者而言，选型不再只是性能对比，而是生态绑定、设备覆盖与合规成本的权衡：Apple 的 Core ML 在 ANE 上做到个位数毫秒延迟，Google 的 ML Kit 提供跨平台开箱即用能力，TensorFlow Lite 仍是跨平台自定义模型主力，而 Gemini Nano 通过 AICore 以开发者预览形式把生成式端侧推理带到 Android。本文聚焦落地策略而非模型原理，帮团队少走弯路。

---

**📱 深度报道**

**▌ 更新全景**：端侧 AI 的价值集中在四块：实时视觉（植物病害识别、OCR、内容审核）、离线语音指令、个性化推荐（联邦学习不上云）、翻译与多语支持。框架侧，Core ML 通过 `coremltools` 把 PyTorch/TensorFlow 模型转为 `.mlpackage`，自动调度 Neural Engine/GPU/CPU，iPhone 15 Pro 上 224×224 图像分类可低至 15ms；ML Kit 提供文本识别、人脸检测、条码、语言识别等预建 API，支持设备端/云端回退；TensorFlow Lite 以 Task Library 与 Delegates（GPU/NNAPI/XNNPACK）覆盖 iOS/Android；Gemini Nano 经 AICore 暴露 `PREFER_ON_DEVICE` 标志，设备不支持时回退云端。

**▌ 技术细节深解**：Gemini Nano 的接入体现"混合优先"思路，开发者无需关心底层是否在端侧：

```kotlin
val generativeModel = GenerativeModel(
    modelName = "gemini-nano",
    inferenceMode = InferenceMode.PREFER_ON_DEVICE
)
// 设备支持 → 本地推理；不支持 → 自动回退云端
```

Core ML 的典型部署则是转换 + 调度：

```python
# coremltools 转换
import coremltools as ct
mlmodel = ct.convert("model.tf", outputs=[...])
mlmodel.save("MyModel.mlpackage")
```

跨平台（RN/Flutter）侧，RN 用 NativeModule 桥接 Core ML（iOS）与 TFLite（Android），Flutter 则可通过插件调用 ML Kit 与 TFLite；但真正统一的"一次编写端侧 AI"仍不成熟，需按平台分别优化。

**▌ 开发者迁移指南**：① 明确任务是否在 ML Kit 预建 API 覆盖内，若是直接用、省去训练；② 自定义模型优先评估 Core ML（iOS）与 TFLite（Android）双线，或 ONNX Runtime Mobile 做统一格式；③ 引入 Gemini Nano 时必须规划"部分设备覆盖 + 云端降级"路径，不要假设所有用户设备支持 Nano；④ 关注模型体积与电池：实时 AI 务必控制推理频率与上传统计，避免体验崩坏与耗电。建议在 CI 中加入模型大小与延迟基准测试。

**▌ 生态与竞品对比**：Core ML 胜在 Apple 硬件深度集成与最低延迟，代价是生态锁定；ML Kit 胜在零 ML 门槛与跨平台一致；TFLite/ONNX 胜在框架无关与社区库；Gemini Nano 代表"系统级生成式端侧"新方向但覆盖尚不均。Mendios 2026 对比显示 MobileNet 推理 Pixel 8 上 TFLite 约 8ms、iPhone 15 Pro 上 Core ML 约 3ms，选型应基于用户平台分布与任务类型。

---

**🤖 开发研判**

🔮 **技术趋势**：端侧 AI 正从"单框架性能比拼"演进为"系统级能力（Apple Intelligence / Gemini Nano）+ 开发者可选框架"的双层结构，未来一年生成式端侧推理会快速普及，但设备覆盖差异将长期存在。

📊 **开发者决策影响**：iOS 优先项目直接上 Core ML 最划算；跨平台且需标准视觉/NLP 功能优先 ML Kit；自定义模型且要跨平台选 TFLite/ONNX；探索生成式功能可试点 Gemini Nano 但必须做降级。新项目应把"端侧优先、云端兜底"写入架构原则。

⚠️ **适配风险**：Gemini Nano 设备覆盖率不足会导致体验不一致；端侧大模型体积与内存占用可能拖垮中低端机；隐私合规虽因端侧而改善，但自定义模型转换（coremltools）对复杂算子的支持仍有坑。

💡 **学习优先级**：先掌握 ML Kit 预建 API 快速落地 → 再学 Core ML 转换与 TFLite 部署 → 最后试点 Gemini Nano 混合推理；推荐 Studio Krew 端侧 AI 指南、Mendios 框架对比与 Apple/Google 官方 ML 文档。
