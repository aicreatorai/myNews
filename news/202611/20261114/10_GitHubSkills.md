### 1. 【iFixAi：120秒独立审计AI智能体是否越权】

> 📍 **导语**：你的 AI 智能体在演示里样样精通，上了生产却在没人批准的情况下悄悄退了一笔客服经理早先拒掉的退款——这类"它到底有没有按规矩办事"的问题，正在成为智能体落地的最大隐患。ifixai-ai/iFixAi 就是为回答这个问题而生的开源审计工具：它把智能体放进一个仿真出来的业务环境，喂给它真实一天里会遇到的请求（包括故意越界的那些），再由一个"法官"模型给每次回复打分，整个过程宣称不到 120 秒就能给出一份可引用的 A 到 F 评级。截至 2026 年 11 月初，这个 Apache-2.0 协议的 Python 命令行项目已经累积约 4.3 万颗 Star，并在十月中旬冲到过周榜第二，是当下智能体治理（AI governance）赛道里最受关注的新面孔之一。

---

**▌ 它是什么？**

iFixAi 是一个用 Python 写成的开源命令行工具，定位是"智能体运营对齐与保证的独立审计员"。它的核心思路非常朴素：不要只测模型的技术能力，而要测智能体在某个具体业务里、带着具体工具时，到底有没有做它该做的事。项目把审计拆成两种运行方式——既可以由人驱动，也可以让智能体自己审计自己，但官方明确强调，真正"可引用"的评级必须让"法官"模型来自与被测智能体不同的厂商，避免模型给自己改作业。仓库里既提供了 Claude Code、Codex 的插件，也提供了适配 Cursor、VS Code、Windsurf、Zed 等编辑器的技能包，开发者只要在编码环境里说一句"对我的 Agent 跑一次 iFixAi"，它就会自动发现目标 Agent、搭建仿真环境、在扣费前先展示成本、跑完审计并解释发现。开源引擎内置 60 项检查，但一次默认运行只跑 10 项核心套件，结果以 A 到 F 的记分卡形式落到本地 ./ifixai-results/ 目录。

**▌ 它解决了什么问题？**

现有的评测与红队工具几乎都在盯着"技术能力"：首字延迟、Token 效率、提示词注入能否被拦截。这些指标很重要，却回答不了一个更朴素、也更要命的问题——这个具体的 Agent，拿着这些具体的工具，今天到底有没有按组织的业务规则、角色权限和本意行事？绝大多数团队是在演示阶段把 Agent 卖出去，上线后才靠事后日志去"复盘"，而日志只能告诉你它做了什么，没法告诉你它"本不该做"。iFixAi 想补的就是这块盲区：它把"运营保证"塞进评测里，关注 Agent 是否尊重角色、权限、策略和诚实上报。值得一提的是，B01（角色只能用被允许的工具）、B08（不能被人忽悠去索取超出用户自身的权限）和 P01（绝不为无权人执行破坏性操作）是强制底线，只要这三项里有一项没过，总分就被封顶在 60% 以下。对于任何一个准备把 Agent 放到能造成真实伤害的位置、或准备发布一次行为变更的团队，这种两分钟就能跑完的预检，比拖一天的评审更可能被真正用起来。

**▌ 核心原理拆解**

iFixAi 把一次审计建模成"被测系统（SUT）+ 法官"的双角色博弈，并把评判切进五个核心支柱：捏造（Fabrication，即无出处或过度自信的声明、调用了未被授予的工具）、操控（Manipulation，权限提升、提示词注入、投毒检索）、欺骗（Deception，暗藏副目标、静默失败）、不可预测性与不透明（Opacity）。最终字母评级只在这五项的加权平均分上滚动，其中操控一项权重最高、占到 0.35，A 级要求 0.90 以上、低于 0.60 直接判 F。机制上，它先把你的 Agent 装进一个仿真业务环境（官方示例是一个虚构金融科技公司的客服 Agent 画像），再向它发送真实业务会遇到的请求，其中包含专门把 Agent 推过角色边界的越界请求；每一步"被问了什么、Agent 做了什么"都会被记录。关键设计是法官必须来自不同厂商——你只有一把钥匙时可以用 --eval-mode self 做冒烟测试，但报告会明确标注这是"自评"，不具可引用性。另有 28 项"高级预览"检查（破坏、 concealment、脆弱用户照护等）单独报告、永不计入评级，避免污染分数。

**▌ 动手验证**

最快的体验方式是用内置 mock 供应商，无需任何密钥和网络即可在本地看到完整流程：

```bash
# 1. 安装（需要 Python 3.10+）
pip install ifixai

# 2. 一键跑内置 demo Agent 的仿真审计（无需 API Key）
ifixai run --provider mock --eval-mode self --fixture reference.yaml
```

如果你想审计真实 Agent，只要它暴露一个 OpenAI 兼容端点即可直接接入；若用其他协议，补几行 Python 实现 ChatProvider.send_message 即可。把真实 Agent 接进来后，最稳妥的做法是先在虚拟环境里跑 `ifixai setup` 向导，挑好供应商、模型、法官和套件，生成 ifixai.yaml 后再 `ifixai run`，报告会以 JSON 与 Markdown 两种格式落到本地目录，包含一份摘要文件，方便直接贴进 CI 的准入门禁。

**▌ 对比选型**

|------|--------|---------------|----------|
| 关注点 | 业务对齐与权限 | 技术能力与延迟 | 攻击面 |

### 2. 【heretic：免训练改写大模型去审查降谄媚】

> 📍 **导语**：你下载了一个开源权重模型，它却因为你问了一句完全合理的伦理或技术边界问题，就甩出一句"我无法回答"。这种被写进系统指令的审查与废话式谄媚，困扰着无数想真正理解模型能力边界的研究者与开发者。p-e-w/heretic 给出的答案不是微调、不是越狱提示词，而是一套"免训练语言模型修改"数学技术：你给它一个行为示例、一个衡量该行为的评分器，它就去搜索一处足够小的权重编辑来改变行为。项目在 2026 年 11 月 1 日发布 2.0.0 大版本，改用全新的 ARA（Arbitrary-Rank Ablation）方法作为默认，冲上 GitHub 当日 Python 趋势榜首，目前约 4 万颗 Star。它把"改模型行为"从训练流水线降级成一块游戏显卡半小时就能搞定的事。

---

**▌ 它是什么？**

heretic 是一个由 Philipp Emanuel Weidmann（GitHub 昵称 p-e-w）维护的开源工具，协议为 AGPL-3.0，核心口号是"training-free language model modification"——不改权重梯度，而是用"对比示例提示词 + 匹配评分器"的组合去搜一处小的权重编辑。2.0 版本把默认方法从经典的 ablation（方向消融，源自 Arditi 等人 2024 年的论文）切换为作者专门为 heretic 设计的 ARA（Arbitrary-Rank Ablation）。开箱即用能力包括：压制拒绝（去审查，这是默认动作）、减少 slop（那些"空灵""天鹅绒""交响乐"式的紫红废话）、降低 sycophancy（"好问题！""你说得对"式的谄媚）、减弱幽默或调整情绪基调。仓库里附了 config.noslop.toml、config.nosyco.toml、config.nohumor.toml、config.emotions.toml 等现成配置，社区也已在 Hugging Face 上发布了数千个被它修改过的模型。

**▌ 它解决了什么问题？**

绝大多数人只跑开源权重模型：下载、用 Ollama 或 Transformers 加载，然后被动接受模型出厂时附带的那套"人格"。这套人格里的审查指令和谄媚表达，往往不是模型架构本身决定的，而是写进系统提示词的"公司化面具"。问题来了：当你想做安全研究、想压测模型在某个敏感话题上的真实知识、想把底座模型"真正在想什么"看清楚时，这层面具就是噪音。传统做法是做全量微调，需要梯度、数据、算力和一整套训练管线；而 heretic 让你跳过这一切——一台 RTX 3090 上，README 估计处理 Qwen3-4B-Instruct 大约只要 30 到 40 分钟。它真正回答的是那个元问题："这个限制到底来自模型架构，还是来自它的指令？"把模型行为从训练里解放出来，研究者就能更干净地观察底座能力。

**▌ 核心原理拆解**

heretic 的本质是把"修改器（modifier）"与"评分器（scorer）"配对，再用 Optuna 的 TPE 优化器去搜大量参数组合，默认配置跑 100 次试验并保留得分最优者。修改器侧，ARA 是 2.0 新写、现为默认的方法，专门用来在不去手工找"拒绝方向"的情况下编辑模型；经典 ablation（方向消融）仍作为可选项保留，并支持 projected 与 norm-preserving 变体。评分器侧，默认同时最小化两个分数：其一是关键词率，统计回复里出现多少标记短语（拒绝短语、废话词、谄媚语）；其二是 KL 散度，衡量被改模型在正常提示词上相对原模型漂移了多远——这个第二项分数正是为了防止"修好一个行为却搞坏整个模型"。2.0 还新增了 BERT 分类器评分器（用于情绪转向）和基准评分器，并允许你通过继承 Scorer、实现 get_score 来自定义评分器而不碰 heretic 源码。插件架构让"评分器决定目标、修改器应用技术"完全解耦，一次运行可以多个评分器协同、由优化器去求折中。

**▌ 动手验证**

安装即用，对开源权重模型一键改写：

```bash
# 1. 安装（Python 3.10+，PyTorch 2.6+，支持 bnb_4bit 量化降显存）
pip install -U heretic-llm

# 2. 对 Hugging Face 上的开源模型执行默认动作（去审查）
heretic Qwen/Qwen3-4B-Instruct-2507

# 3. 换成"去废话/降谄媚"等目标，需显式指定配置
HERETIC_CONFIG_FILE=config.nosyco.toml heretic Qwen/Qwen3-4B-Instruct-2507
```

注意：默认配置就是去审查，如果不显式换配置，一下午可能就产出一个你没打算要的模型；仓库配置按"当前工作目录下的 config.toml"加载，因此用 HERETIC_CONFIG_FILE 显式指定是更安全的习惯。2.x 不兼容 1.x 的配置文件，升级前需按 docs/migration_v1_to_v2.md 改写。

**▌ 对比选型**

| 维度 | heretic 2.0 | 全量微调 | 提示词越狱 |
|------|-------------|----------|------------|
| 是否需要训练 | 否 | 是 | 否 |
| 持久性 | 改权重持久 | 持久 | 仅单次对话 |
| 硬件门槛 | 单卡游戏显卡 | 多卡集群 | 无 |
| 合规风险 | AGPL 网络拷贝 | 自有 | 易失效 |

### 3. 【nanochat：本地优先的极简开源聊天界面】

> 📍 **导语**：每一次你打开 ChatGPT 或 Claude，都在为每条消息付费，并默认把聊天内容存到别人的服务器上。Karpathy（前特斯拉 AI 总监、OpenAI 联合创始人）推出的 karpathy/nanochat 想证明：强到够用的对话体验，不需要企业级基础设施也能拥有。截至 2026 年 11 月，这个 MIT 协议、核心代码不到一千行的 Python 项目已经累积约 5.97 万颗 Star。它把整条聊天链路收回到你自己的机器上——模型权重下载到本地、推理用你自己的 CPU 或 GPU、界面是纯 HTML/CSS/原生 JavaScript，没有 Electron、没有 React、没有框架负担，首字延迟可以压到 100 毫秒以内，且完全离线、零遥测、零云端调用。它既是"百美元能买到的最佳 ChatGPT"式本地聊天界面，也是 LLM101n 课程里"从分词到训练到对话"的端到端教学代码库。

---

**▌ 它是什么？**

nanochat 是 Andrej Karpathy 把"本地优先、极简、可黑"的 AI 哲学落到实处的代表作。它的聊天界面刻意做得极简：不依赖任何商业服务，没有后端服务器要搭、没有鉴权、没有网络延迟，一切自包含。仓库既包含面向终端的 chat.py 交互会话，也包含一套完整的全栈实现——分词、预训练、微调、评估、推理，以及基于简单 UI 的 Web 服务，让你像用 ChatGPT 一样和自己训出来的模型对话。它还将成为 Eureka Labs 正在开发的 LLM101n 课程的结业项目。官方甚至托管了一个 d34 的样例模型（34 层 Transformer、22 亿参数、用 88B token 训练、总成本约 2500 美元），用来让你直观感受"从零训出来的小模型"长什么样——它会犯很多错、有点天真、幻觉连连，但完全属于你、可配置、可改写、可审计。

**▌ 它解决了什么问题？**

开发者与隐私敏感用户长期被两件事困住：一是成本，SaaS 聊天机器人按条计费，用量一大账单就失控；二是数据主权，每次对话都默认离开本机、落到第三方服务器。市面上 LM Studio、Ollama 这类工具已经把"本地跑开源权重"常态化，但 nanochat 进一步把抽象层压到最低——它是一个单用途、依赖极少的接口，去掉了大型编排框架里常见的复杂性开销。对想理解对话 AI 底层怎么搭的人，它是绝佳的沙盒；对要处理文档、头脑风暴或起草代码又不想数据出机的场景，它是隐私优先的本地助手；对断网环境或强合规要求，它是唯一能离线工作的方案。Karpathy 反复强调"复杂度是可靠性的敌人"，把代码量压到一千行以内，意味着它容易被审计、被修改、被扩展，而不是变成一个黑盒。

**▌ 核心原理拆解**

nanochat 的架构哲学是"本地推理 + 极简界面 + 零框架"。本地推理层使用 llama.cpp 或同类引擎在消费级硬件上跑模型，权重以 GGUF 等量化格式落地，CPU 与 GPU 皆可；界面层完全抛弃 Electron 与前端框架，仅用原生 HTML、CSS 和 vanilla JavaScript，因此页面加载可在一秒内完成、能在任何现代浏览器里跑、且完全离线。Web 服务基于脚本里极轻的 server 模块，把聊天请求直接喂给本地推理后端。更完整的一条链路则是教学用的全栈管线：scripts.base_train 做预训练、scripts.mid_train 做中期训练、scripts.chat_web 起对话 UI，配合 run1000.sh、speedrun.sh 等脚本把"买一台 8×H100 节点、花几小时训一个百美元档模型、再对话"整段自动化。它的简单是刻意的——正因为小，任何人都能读完并动手改，把"复杂即风险"的反面教材写成了代码。

**▌ 动手验证**

最轻量的本地聊天只需三步：

```bash
# 1. 克隆并进入仓库
git clone https://github.com/karpathy/nanochat.git
cd nanochat

# 2. 安装极简依赖（llama-cpp-python）
pip install llama-cpp-python

# 3. 下载一个小型 .gguf 模型放入目录后，直接起终端聊天
python chat.py
```

如果想体验"从零训+聊"的完整链路，可以启动 speedrun.sh 在 8×H100 节点上四小时跑完百美元档训练，再 `python -m scripts.chat_web` 起 ChatGPT 式界面。本地 uv 虚拟环境激活后即可服务，访问节点 IP 加端口即可对话。注意它并不追求追上 GPT-5 级别的模型，定位是"够用、可控、属于你"的本地助手。

|------|----------|----------|--------|

### 4. 【uber/ADR：企业级AI智能体安全防护框架】

> 📍 **导语**：当公司里 Cursor、Claude Code、Codex 这些编码智能体，以及面向客户的 AI 客服智能体被广泛部署后，安全团队面临一个尴尬现实：这些 Agent 成了新的攻击面，而防御手段还停留在"有没有装好 Agent"的层面。uber/ADR（Agentic AI Detection and Response）是 Uber 开源、已在生产环境部署的企业级智能体安全系统，配套论文被 MLSys 2026 接收（arXiv 2605.17380）。它通过"可观测、基准评测、威胁检测、风险预防"四件套，把智能体的一举一动变成可被 SOC 消化的遥测与可被红队验证的基准。截至 2026 年 11 月，仓库约 2.1 万颗 Star，是新兴"智能体安全"品类里最扎实的开源作品之一。

---

**▌ 它是什么？**

ADR 的全称是 Agentic AI Detection and Response，定位为企业级 AI 智能体安全系统，协议 Apache-2.0。它的目标是帮组织守护两类 Agent：一是员工侧的工具（Cursor、Claude Code、Codex 等编码智能体），二是客户侧的 AI 客服等自动化智能体。本次开源放出的是 ADR Sensor（遥测采集库）、ADR-Bench（基准与检测器）和 ADR Detector（双智能体检测器），而用于预部署红队加固的离线 ADR Explorer 引擎暂未开源。仓库组件清晰分层：Discovery 负责清点端点上的 AI 应用、CLI Agent、IDE 扩展、模型运行时和 MCP 服务器，标出未受策略批准的未知面；Sensor 负责跨 macOS、Linux、Windows 采集并归一化 Agent 的意图、工具调用与执行轨迹；Detection 则承载 ADR-Bench 与双智能体检测器。

**▌ 它解决了什么问题？**

传统端点安全看不见"智能体在想什么、调了什么工具、开了什么子 Agent"。当一款编码 Agent 被提示词注入诱导、悄悄去读另一个用户的数据，或者一个未授权的 MCP 服务器被接进来，现有日志往往只记录"执行了命令"，却说不清"为什么"。ADR 解决的正是这个可见性缺口：它把 Agent 的会话日志、工具调用、嵌套子 Agent 会话都收成统一 schema，喂进已有的 SOC 检测管线，让分析师在 Agent 做可疑动作时拿到会话级上下文。更关键的是，它把"端点上到底跑着哪些没被批准的 Agent 和 MCP 服务器"这个影子 AI 问题，变成一次可执行的盘点。对那些"采用 AI 编码智能体的速度远超为其上安全"的组织，ADR 提供了一份有论文背书、可复现、且已在 Uber 真实负载下验证过的起点。

**▌ 核心原理拆解**

ADR 用四个互补能力覆盖智能体安全闭环。其一是可观测（Sensor）：在三大操作系统上采集 Claude Code、Cursor、Codex、GitHub Copilot CLI、DeepSeek Harness、opencode、Claude Desktop 等的遥测，连 Gemini CLI 的会话日志——含工具结果与嵌套子 Agent 会话——也不放过，并归一化进统一 schema。其二是基准（ADR-Bench）：包含 300 余项任务、133 个 MCP 服务器，覆盖全部 17 种智能体攻击技术，给紫队在部署前度量检测器 efficacy 提供标准战场。其三是检测（Detection）：采用两层级架构，先用高召回的 triage 做粗筛，再对可疑会话用更深的"智能体式推理"做精细判断，兼顾成本与召回。其四是预防（Prevention）：能在危险动作发生前阻断——但这一组件未包含在当前开源版本里。值得注意的是，检测质量依赖双智能体 LLM 管线，因此 API 成本与延迟是真实运营考量，两层级 triage 正是为此而设。

**▌ 动手验证**

最快的体验是从 Detection 组件跑起，并可用 llamafirewall 基线做无密钥冒烟：

```bash
# 1. 克隆并进入检测组件
git clone https://github.com/uber/ADR
cd ADR/Detection

# 2. 同步依赖并配置双厂商密钥（judge 与被测不同厂商）
uv sync
export ANTHROPIC_API_KEY="..." OPENAI_API_KEY="..."

# 3. 无密钥冒烟测试（llamafirewall 基线）
python -m adr --detector llamafirewall
```

随后按 docs/REPRODUCIBILITY.md 的完整流程：解压打包基准 → 跑各类检测器 → 绘制论文图表，即可复现 ADR-Bench 的检测结果与论文图。Sensor 端则按 Sensor/README.md 接入端点遥测，把归一化后的 Agent 轨迹送到你的检测管线。

### 5. 【artcraft：面向创作者与影视的AI工艺引擎】

> 📍 **导语**：大多数 AI 图像工具用起来仍像一个"带生成按钮的聊天框"——你打一句提示词，返四张方图，然后祈祷下一次 roll 更好。storytold/artcraft 想走另一条路：把 AI 生成当成"给艺术家的 IDE"。它把自己定义为"面向艺术家、设计师与电影制作人的定向创作引擎"，用 Rust + Tauri 写成原生桌面应用，双协议 MIT 或 Apache-2.0 任选。截至 2026 年 11 月中旬，这个仓库已累积约 4 万颗 Star，并登上 GitHub 当日趋势榜（单日新增约 378）。它不是又一个网页版模型聚合站，而是把构图、分镜、角色摆位、3D 场景这些创作决策，重新交回创作者手里的原生工作台。

---

**▌ 它是什么？**

artcraft 由开源作者 storytold 打造，官方 README 称其为"艺术家的 IDE"与"定向创作引擎（Intentional Crafting Engine）"。与一次性提示词生成不同，它要求你先在画布上"搭场景"：把虚拟角色稳定放在同一个房间里、叠加背景与道具、把一张图转成可旋转的 3D 网格、摆好相机机位，最后再选一个模型去完成这一帧。它内置一份模型目录（README 列出约 62 个横跨图像、视频、音乐音效、3D 网格与高斯泼溅世界的模型），并挂接 Grok、Midjourney、Sora、World Labs 等供应商的钩子；同时也支持画布内与提示词驱动的编辑：描述一处改动，或手绘遮罩做精准 inpaint。最新稳定桌面版 v0.41.0（2026-09-26）提供 macOS 的 .dmg 与 Windows 的 .exe/.msi 安装包，Linux 用户则需从源码构建。

**▌ 它解决了什么问题？**

专业视觉与影视工作者对作品有严苛的标准：镜头语言、分镜设计、色彩氛围、资产连贯性，都不是"再来四张"能解决的。通用生成工具在高质量专业工作流里，往往补不上"可控性"这块短板——角色换一张图就变脸、场景对不上、机位飘忽。artcraft 选择直接面向艺术家、视觉设计师与影视创作者这三类群体，用"定向创作"对抗随机生成：让创作者精准传达审美意志、构图逻辑与艺术细节，使创作过程具备高度确定性与可操作性。它背后是一个不新的开源组织——storytold 账号创建于 2021 年、已有 79 个公开仓库、近 6.9 万粉丝，其另一旗舰 PhotoCraft（同样 Rust 写的开源照片编辑器）已有约 7.8 万 Star，artcraft 把同一套"原生桌面而非网页"的哲学延展到了 AI 视觉创作。

**▌ 核心原理拆解**

artcraft 的工程核心是"先场景、后生成"的工作台而非聊天框。它的能力包括：Image to Location（让虚拟演员稳定待在同一环境、在同一空间规划多个镜头）、2D 与 3D 合成（图层化剪切、背景与道具、可复用的去背元素）、Image to 3D mesh（把静帧转成可摆位取景的网格）、角色摆位与身份迁移（摆好人体模型再引导角色落位）、基于套件（kitbashing）的场景遮挡以确定相机角度与纵深，以及最终的 Image to video 动画化。底层的模型目录是一个"菜单"而非能力保证——目录里部分条目被标记为 disabled 或 restricted，桌面端实际可调用的更少，因此在评估时应当先核对哪些模型当下真实可用。它本身不训练、不托管模型（其 HuggingFace 主页为零模型零数据集），而是用 Rust 写成的创作界面去调用第三方商业 API，生成发生在别人家的基建上、遵循别人的定价与条款。

**▌ 动手验证**

最省事的方式是用打包好的桌面应用，进阶用户可从源码构建：

```bash
# 1. 克隆仓库
git clone https://github.com/storytold/artcraft.git
cd artcraft

# 2. Unix 平台启动开发模式（需 Rust、Node.js、Tauri CLI）
./script/artcraft/unix_dev.sh
# 或指定端口：ARTCRAFT_DEV_PORT=6200 ./script/artcraft/unix_dev.sh
```

普通用户直接到 getartcraft.com 或 GitHub Releases 下载 v0.41.0 的 .dmg/.exe，安装后从一条文本生图提示词起步，再逐步进入画布与 3D 场景工具；想看可视化导览可先看完 README 链接的官方两分钟演示。需要提醒的是，首次接入任何 API 前应到仓库页核对模型清单的可用状态，避免把"目录里的 62 个"误当成"今天能调的 62 个"。

### 6. 【semantica：图原生AI问责基础设施】

> 📍 **导语**：大多数 AI 智能体是跑在嵌入向量上的，而不是跑在"意义"上——它们存的是相似度分数，没有结构、没有关系、更没法解释"为什么得出这个结果"。在贷款审批这类高风险、受监管场景里，这个缺陷直接变成合规暴露：监管机构六个月后问你"当初为什么通过"，你需要一份精确到每一步推理链的审计报告。semantica-agi/semantica 的定位正是"图原生上下文与可问责 AI 系统基础设施"，它把企业数据 ingest 后抽取关键，构建 Context Graph 与知识图谱（KG），再在其上跑图分析与因果推理，并把每一次决策的溯源（provenance）原生化地记录下来。这个 MIT 协议的项目在 2026 年 8 月曾登顶 GitHub Trending 第一，目前约 1.2 万颗 Star，最新 v0.7.0 把核心依赖从 44 个压到 22 个，明显更轻。

---

**▌ 它是什么？**

semantica 是一个面向 AI/ML 平台团队的开发者优先知识基础设施，MIT 协议、Python 写成。它的主张是做"LLM、向量库与 Agent 框架底下的语义/上下文层"——一套确定性基础设施：图谱构建、推理与溯源都不依赖 LLM（需要模型时才用，且厂商中立，OpenAI、Anthropic、Gemini 等皆可通过 semantica.llms 接入）。它把碎片化的企业数据转成结构化、可查询的 Context Graph 与知识图谱，承载的是业务上下文而非单纯数据结构。配套的本体（Ontology）与受控词表（OWL、SHACL、SKOS）把"某个实体对业务意味着什么、它的定义、关系与规则"显式化，而不只是它的嵌入向量。决策溯源与审计轨迹不是附加产品，而是从结构中"免费"掉落的能力——在监管者能追问的领域，同一套让 Agent 变聪明的结构，也给你一句干脆的"为什么"。

**▌ 它解决了什么问题？**

它针对的是"嵌入即记忆"的根本局限：相似性检索能召回相关片段，却说不清片段之间的关系、业务定义与适用规则，更给不出"这个决策基于哪些事实、经过什么策略、完整执行轨迹如何"。对金融、医疗、法律、政府等受监管行业，这等同于把合规风险埋进黑盒。semantica 的解法是把"决策智能层"做成一等图节点而非临时日志：每一个 AI 决策都作为图谱里的节点，支持按先例搜索、因果关联追踪，并可叠加本体与合规规则。它明确区分"系统级可解释"而非"基础模型内部可解释"——它不暴露也不重建 LLM 内部推理（那对任何外部系统都是不透明的），而是解释模型之外的事物：喂进去的上下文、产出的决策、它的溯源、相关关系、应用的策略与完整执行轨迹。这对需要回答"AI 为什么这么做"的合规、风险与审计团队，是结构性的答案。

**▌ 核心原理拆解**

数据从 Sources 经 Ingest→Parse→Normalize→Split→Extract→Conflict Detection→Deduplication 等九阶段管线，最终生成可查询的 Knowledge Graph；其上叠加 Ontology（OWL/SHACL/SKOS）、Reasoning Engine（Datalog/SPARQL/Rete 规则引擎）与遵循 W3C PROV-O 的溯源记录。关键设计是"确定性优先"：图谱构建、推理与溯源都不需要 LLM，实体与关系抽取既可用纯模式规则（无模型密钥也能跑），也可在配置模型后调用 LLM。决策记录 API 是差异化所在——Agent 把每个选择连同其推理与置信度写入图谱，后续查询能拉出相似的历史决策、追踪哪些事实喂进了它们。生态上还提供插件包（适配 Claude Code、Cursor、Codex、pi、Windsurf、Cline、Continue、VS Code、OpenClaw）、基于 React 19 + Sigma.js 的浏览器知识探索器（可缩放实时图、按时间线回放、审查每个决策的因果链），以及一个 MCP 服务器让编码助手直接读图谱。v0.7.0 还新增层级社区 GraphRAG、模式引导抽取与来源感知的事实维护与信任分级。

**▌ 动手验证**

从零起步最简路径是装好基础包、用小批文档先用模式抽取器验证输出，再加存储后端：

```bash
# 1. 安装含探索器的最小包（核心依赖已压到约 22 个）
pip install "semantica[explorer]"

# 2. 启动本地图工作台（默认 http://127.0.0.1:8000）
semantica-explorer --graph my_graph.json

# 3. 仅用库做模式抽取（无需模型密钥）
python -c "from semantica import extract; extract.from_documents(['a.pdf','b.md'])"
```

建议先用库而非服务器：装基础包、用模式抽取器从少量文档建小图、确认输出后再接模型供应商；当内存图超出单进程时，再加一个存储后端 extra（Neo4j、FalkorDB、Apache AGE、Neptune 等皆可选）。需要可追溯"Agent 为何这样选"的团队，应优先用它的决策记录 API，而不是只用它做向量检索。
