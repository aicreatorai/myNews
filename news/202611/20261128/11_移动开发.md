### 1. 【iOS 27.3 Beta 2 适配：Safari 竖排标签页与自适应深色模式】

▌ **导语**

2026 年 11 月 17 日，苹果向开发者推送了 iOS 与 iPadOS 27.3 的第二个开发者预览版 Beta 2，内部版本号为 24C5049d，距离首个 Beta 发布恰好十三天。同一批放出的还有 macOS 27.3 Beta 2（26C5047e）、watchOS 27.3 Beta 2（24S5296d）、visionOS 27.3 Beta 2（24N5298d）以及 tvOS 27.3 Beta 2，各平台的更新节奏保持同步。与上一版主要围绕 Siri AI 的能力开放不同，这一版把改动落在了开发者每天都会碰到的界面层：Safari 的竖排标签页布局、自适应深色模式、重新回归的健康 App，以及折叠形态 iPhone Duo 的横向可达性。对移动开发团队来说，这些看似细碎的系统界面变化，往往比一个宏大的新框架更需要提前适配，因为它们直接改变页面的可用宽度、手势识别区域和深色模式下的可读性。年末这段密集的测试版节奏，实际上是给正式版之前的兼容性验证留出的窗口。

▌ **核心信息**

Safari 这次新增的竖排标签页把标签从页面顶部移到了屏幕左侧，在 iPadOS 的大屏场景下尤为实用，它改变了网页内容区的横向可用宽度，也意味着依赖固定宽度断点或绝对定位的页面需要在窄栏模式下重新检查布局。自适应深色模式则是在系统开启深色模式时，自动把原本不支持深色模式的网站即时调暗，这对只用默认白色背景、没有声明配色方案的老站点影响最直接。开发者可以用标准的配色声明主动接管，避免被浏览器接管后产生图片反色或对比度不足的问题。

```css
:root { color-scheme: light dark; }
@media (prefers-color-scheme: dark) {
  body { background: #121212; color: #ededed; }
  img { filter: none; } /* 避免自适应调暗把图片一起反色 */
}
```

系统应用层面，此前在 27.2 测试版中被撤回的全新健康 App 重新回归，并带来基于 Apple Intelligence 的洞察标签与健康年龄估算；Siri AI 的跨应用动作范围扩展至日历、文件、邮件、地图、信息、音乐、备忘录、照片、提醒事项、Safari、快捷指令与天气等系统应用。折叠屏 iPhone Duo 获得横向可达性支持，用户在折叠状态下从左右边缘滑动可把内容向另一侧偏移；Apple Music 新增 Selfie Sing。桌面端 macOS 27.3（代号 Golden Gate）把原生实时活动放进菜单栏，且不再局限于配备灵动岛的新款 MacBook Pro，非灵动岛机型同样可用。

▌ **影响判断**

对 Web 与 hybrid 团队，竖排标签页和自适应深色模式都不是可选关注项。前者意味着断点测试要新增一个更窄的视口档位，后者意味着那些从来没写过深色样式的页面会第一次被系统强行调暗——图片、图标、广告位和图表在被自动反色后是否还能看清，需要真机逐一核对，主动声明配色方案比被动接受系统处理更稳妥。对原生开发者，横向可达性引入的边缘滑动与已有的侧滑返回、抽屉手势存在冲突风险，凡是把关键操作放在屏幕左右边缘的页面，都要在折叠形态下重做手势优先级。健康 App 的洞察与健康年龄估算若后续向第三方开放数据入口，会牵涉到 HealthKit 授权文案与隐私清单的更新，值得提前梳理。菜单栏实时活动为 macOS 端带来了新的展示面，做跨端消息或出行类应用的团队可以先做技术预研。需要提醒的是，这套变化目前只存在于开发者预览版，苹果的推送节奏很快，正式版的功能范围仍可能调整，建议把适配工作放在测试分支，用 Xcode 27 配套验证，不要基于 Beta 行为修改线上关键路径。

### 2. 【Flutter WebAssembly 可选启用：重型 Widget 帧率翻倍与内容哈希部署】

▌ **导语**

在 11 月 11 日随 Dart 3.14 一起发布的 Flutter 3.50 里，Web 端拿到了两项足以改变部署方式的更新：WebAssembly 进入可手动开启的阶段，以及构建产物支持内容哈希。根据跨平台开发地图的整理，Safari 26.2 以上与 Firefox 147 以上现在可以通过 web/flutter_bootstrap.js 选择启用 WebAssembly，官方在重型 Widget 基准测试中给出的结果是帧率超过 JavaScript 模式的两倍，不过目前仍需手动配置，后续版本才会默认开启。同一版本还把 flutter build web --web-content-hash 带进构建链，为静态资源长期缓存铺路。对做 Flutter Web 或同一套代码多端投放的团队，这两项变化把性能与缓存工程的主动权交回到了开发者手里。

▌ **核心信息**

WebAssembly 的开启点在 Web 引导脚本里，构建时需先产出对应的产物，再在引导配置中选择加载 WebAssembly 版本；官方明确 Safari 26.2+ 与 Firefox 147+ 才具备条件，因此面向存量浏览器的项目不能简单全局切换，而要保留 JavaScript 回退路径。帧率翻倍的数据来自重型 Widget 基准，中等复杂度的业务页面收益可能没有这么明显，是否值得开启应以真实页面测量为准。内容哈希这项更新解决的是发版后用户拿到旧资源的老问题：加上 --web-content-hash 后，JS、WebAssembly 与资源文件名都会带内容哈希，同时 flutter_bootstrap.js 同步更新，带哈希的静态资源可以设置长期缓存，入口文件继续用 no-cache。

```bash
flutter build web --web-content-hash --wasm
# 产物：main.dart.js -> main.<hash>.js，入口 flutter_bootstrap.js 更新引用
```

与 Web 更新并行的是旧 JS 互操作接口的弃用流程：dart:html、dart:js、dart:js_util 与 package:js 已进入弃用列表，团队可以用 --no-deprecated-js-interop 提前扫描项目和依赖，为 WebAssembly 适配排雷。Material 与 Cupertino 的旧入口也同期弃用，新项目默认引用独立的 material_ui 包，已有项目可执行自动迁移命令后再检查自定义主题与本地化委托。移动端这边，3.50 调整了 iOS 触控调度，官方实测 60Hz 设备减少约十六毫秒输入延迟、120Hz ProMotion 设备减少约八毫秒，并修复了 iOS 27 真机调试的白屏与偶发启动崩溃。

▌ **影响判断**

对已经把 Flutter Web 用于管理后台、活动页或对外营销站的团队，内容哈希是优先级最高的一项：它几乎不改动业务代码，却能显著改善缓存命中率和版本一致性，尤其适合配合 CDN 做长期缓存，建议先在测试环境验证哈希文件名与入口文件的缓存策略是否匹配。WebAssembly 则要克制，帧率收益集中在重型场景，而浏览器版本门槛和初始化开销意味着必须保留回退，最好通过特性检测而非用户代理判断来分流。旧 JS 互操作接口的弃用容易被忽视，很多第三方包仍依赖这些库，升级前用扫描命令列一份依赖清单，比到编译失败时再排查省时得多。横向对比来看，React Native 的 Web 支持一直不是主线，Kotlin Multiplatform 的 Web 能力也仍在推进，Flutter 在跨端一致性上的积累让它成为多端投放团队更现实的选择，但这些优势同样要求团队维护更严格的构建与缓存规范。生产项目仍建议按大版本观察策略推进，先建测试分支跑通依赖、插件适配和构建回归，再安排切换窗口。

### 3. 【KMP 多平台库新增 .kar 发布格式：91MB 压缩到 23MB】

▌ **导语**

Kotlin 2.5.0 RC 在 11 月 11 日跟进发布，除了把 Swift Export 推进到 Beta，还给多平台库的发布链路带来一个容易被忽略但影响深远的变化：除 JVM 与 Android 之外，多平台产物现在可以打包成单个 .kar 文件。这是一种经过 XZ 额外压缩的 ZIP 归档，作用是让库作者在新增目标平台时不必持续增加发布文件数量。官方文档给出的 cryptography-kotlin 案例很直观：整个多模块项目从 7539 个文件、91MB 降到 1036 个文件、23MB。对维护 KMP 共享库的团队，这项更新把发布产物的管理成本压了下来，也把依赖消费侧的体验往前推了一步。

▌ **核心信息**

.kar 的定位是发布格式而非运行时格式，它把多个目标的产物收拢进一个归档并通过 XZ 进一步压缩，因此新增 target 时不会让仓库里的产物数量线性膨胀。官方特别说明，发布 .kar 目前仍是实验能力，但所有项目已经可以消费这种产物，这意味着主要受影响的是库作者，普通业务项目更多是被动受益。与之配套的是 2.5.0 RC 的另外几项变化：未使用返回值检查器进入稳定状态并默认开启，过去调用函数后忽略返回值只能靠代码评审发现，现在编译器可以直接给出检查；实验性的 full value classes 允许一个值类包含多个属性，通过 -Xfull-value-classes 启用，能自动生成 equals、hashCode 与 toString，但暂不提供 componentN 与 copy。

```kotlin
// 库作者侧：在 Gradle 中启用实验性 .kar 发布
kotlin {
    explicitApi()
    // 新增 target 时，产物数量不再随平台线性增长
}
// 消费侧按常规依赖声明即可，无需感知归档格式
```

工具链门槛也同步抬高，Beta2 的日志把最低 Gradle 版本提高到 8.14.x、最低 AGP 提高到 8.8.2，RC 文档还明确 JDK 17 以下会直接报错，临时退出开关计划在 2.5.20 或 2.6.0 移除。Swift Export 的配置入口从旧写法调整为 export { swift { } }，声明的依赖会自动导出，不再要求逐个显式调用，RC 还修复了 Swift package 在 Release 构建中链接失败的问题。做 iOS 共享库的团队可以用 RC 验证导出与链接流程，生产项目则继续以 2.4.21 这类稳定版为基线。

▌ **影响判断**

对库作者，.kar 最直接的价值是仓库体积和产物管理：从 91MB 降到 23MB 不只是省空间，更意味着镜像同步、依赖解析和构建缓存的压力都会下降，对国内团队自建制品库尤其友好。但实验性标签意味着它没有稳定性承诺，正式发布流程里贸然切换可能遇到工具链不兼容，建议先在内部测试制品里跑一轮完整发布与消费验证，确认消费侧无需额外配置后再推广。对业务项目，返回值检查器默认开启会在升级后带来一批新告警，这些告警不一定都是缺陷，但逐条确认比统一关闭更稳妥，否则会错过真正被忽略的返回值。工具链版本的抬高则要求 CI 环境同步更新 JDK 与 Gradle，否则会在构建早期就失败，这类环境改动最好和项目升级分开提交，便于回滚定位。横向看，Kotlin Multiplatform 正在同时解决发布格式、iOS 互操作和编译器检查三件事，整体方向是降低共享逻辑落地的工程摩擦；与之相比，Flutter 靠单一语言统一两端，React Native 则在清理旧架构，三条路线的竞争焦点已经从能不能跨端转向跨端之后的维护成本。需要留意的是，2.5.0 仍处于预发布阶段，官方文档未确认的变化不应拿来指导生产升级，做决定时应以已写进文档的内容为准。

### 4. 【uni-app x 5.33 补齐资源热更新与支付宝小程序：uvue 默认 TypeScript】

▌ **导语**

在跨平台框架月度盘点里，uni-app x 的更新往往不像 Flutter 或 Kotlin 那样抢眼，但它的两次小版本迭代刚好打在国内团队最在意的两个点上：资源热更新和小程序渠道。根据整理，uni-app x 发布了 5.33.2026102401 与 5.34.2026102909 两个版本，前者增加 Android 与 iOS 蒸汽模式下的 wgt 资源热更新、支付宝小程序、uasm 插件和 CSS 动画，并把 uvue 脚本默认切换为 TypeScript；后者集中修复编译器、Web、Android、iOS 与鸿蒙侧的问题。对做多端投放、尤其是要同时覆盖 App 与多家小程序的团队，这组更新把发版节奏和类型安全同时往前推了一格。

▌ **核心信息**

wgt 资源热更新是这次最关键的能力。它把界面资源与逻辑脚本打成资源包下发，Android 与 iOS 的蒸汽模式下可以在不整包更新的情况下替换资源内容，适合活动页、配置化模块和文案修正这类高频变更场景。它的边界同样清楚：涉及原生能力、权限声明或引擎本身的变化仍要整包发布，热更新不能当作绕过审核的通用通道。支付宝小程序的补齐则让渠道覆盖更完整，过去需要单独维护一套支付宝小程序代码的团队，有机会把它收进同一套工程。uasm 插件与 CSS 动画扩展了表现层能力，uvue 脚本默认使用 TypeScript，意味着新项目从一开始就能拿到类型检查，老项目也可以按文件逐步迁移，而不是一次全量改写。

```jsonc
// manifest.json 中按平台配置资源更新地址
{
  "app": {
    "android": { "steam": { "wgtUpdateUrl": "https://example.com/wgt/android" } },
    "ios": { "steam": { "wgtUpdateUrl": "https://example.com/wgt/ios" } }
  }
}
```

5.34 的修复清单覆盖编译器、Web、Android、iOS 与鸿蒙，其中鸿蒙侧的修复对正在做鸿蒙适配的团队值得单独关注：跨平台框架对鸿蒙的支持往往滞后于主力平台，编译与运行时问题集中在这一版本得到处理，可以借机把鸿蒙端纳入常规回归。社区维护节奏上，这两个版本分别在十月下旬放出，月度盘点把它们和 Flutter 3.50、React Native 0.88.1、Kotlin 2.5.0 RC 放在同一张升级清单里，说明跨平台生态在年末整体进入了迁移验证期，版本多的时候升级顺序更不能乱。

▌ **影响判断**

对国内业务团队，资源热更新的现实价值在于缩短迭代周期：活动页改文案、运营配置调整这类需求不必再等一次完整发版，但必须配套版本校验、回滚和灰度机制，否则一次错误的资源包就可能让线上页面整体失效，热更新链路的安全设计比功能本身更重要。支付宝小程序的补齐则改变了渠道成本账，一套代码覆盖更多小程序的吸引力在于减少重复开发，但各平台的审核规则与能力差异仍在，发布前仍要做渠道专项测试。uvue 默认 TypeScript 对团队结构是渐进友好的，新成员更容易在类型提示下写对代码，老项目则应按模块迁移，避免一次大范围改动带来的回归风险。横向对比，Flutter 官方没有通用的热更新方案，React Native 侧的 CodePush 类方案需要额外接第三方服务，uni-app x 把热更新放进框架内，是它在国内生态里的差异化优势，代价是生态与文档深度不如国际主流框架。需要提醒的是，这次更新中鸿蒙相关的是修复而非新特性，把它当成鸿蒙原生能力的替代品并不合适，真正关键的鸿蒙特性仍要靠原生侧适配来实现。

### 5. 【LiteRT-LM 0.19.1 接入 Gemma 4 多模态：端侧大模型流式推理落地】

▌ **导语**

端侧大模型的工具链在 11 月又往前走了一步。根据端侧 AI 工具盘点的整理，LiteRT-LM 的 v0.19.1 于 2026 年 11 月 6 日发布，新增 Gemma 4 的图像与音频输入，并改进了 Artisan GPU 上的视觉处理。这个版本把端侧推理从纯文本带向真正的多模态：手机本地可以接收图片和语音，配合工具调用与流式输出，构造离线问答、图片理解或语音交互功能。官方文档列出 Android、iOS、Web、桌面与 IoT 支持，Flutter 侧目前通过社区维护的 flutter_gemma 接入，并不是 Google 官方的 Flutter 包。对想在不上传数据的前提下做智能功能的团队，这条链已经从概念验证走向可交付的工程方案。

▌ **核心信息**

LiteRT-LM 的定位是把文本、图片、语音模型放到设备本地运行，减少请求云端的等待和数据外传。它支持工具调用与函数执行，可以让模型请求一次工具调用、由应用执行对应函数、再把结果返回给模型，从而完成多步骤任务；同时支持流式输出与多模态输入，覆盖 Gemma、Llama、Phi、Qwen 等模型家族，并在可用时调用 GPU 与 NPU 加速。在 Flutter 工程里的典型分工是原生层负责加载模型、Dart 层负责展示流式结果，两端通过事件通道桥接。

```dart
// Flutter 侧：Dart 只消费流式结果，模型加载留在原生层
final stream = FfiGemma.generateStream(prompt: userInput);
await for (final token in stream) {
  setState(() => answer += token); // 逐 token 刷新，避免长请求白屏
}
```

官方列出的支持面包括 Android、iOS、Web、桌面与 IoT，但 Flutter 接口由社区维护的 flutter_gemma 提供，项目 Apache-2.0 许可，仓库约 6848 星（11 月 10 日核对）。风险点也很明确：模型体积、内存峰值与 GPU 后端差异必须在目标真机上实测，0.x 版本的接口仍可能调整，iOS 与 Android 语言绑定的成熟度也不一致，接入前要分别验证两端的集成路径。同类工具里，llama.cpp 胜在 GGUF 模型生态与灵活性，ExecuTorch 依托 PyTorch 生态与硬件后端，MNN 与 ncnn 在包体和传统视觉推理上有积累，Core ML 则是 Apple 生态的原生选项。

▌ **影响判断**

对 Flutter 团队，LiteRT-LM 0.19.1 的多模态更新把可做的产品形态拓宽了：离线图片理解适合相册类功能，语音输入适合车载或运动场景，而流式输出能让用户先看到部分结果，避免长请求期间的白屏等待。真正决定体验的仍是工程细节，模型体积和首帧加载时间要在目标机型上反复测，必要时做量化压缩、按场景拆分小模型并配合后台预加载，否则用户第一印象就会毁在进度条上。因为 Flutter 接口来自社区包，团队要评估维护活跃度和版本跟进节奏，把它当成一个需要自己兜底的依赖，而不是官方保证稳定的能力。隐私是端侧推理最硬的卖点，人脸、声纹、证件等敏感数据不必离端，但也意味着模型文件与推理日志本身要纳入数据治理，不能因为走本地就跳过合规审查。选型上，如果团队以 Android 为主且追求灵活换模型，llama.cpp 更合适；如果已经在 PyTorch 生态里，ExecuTorch 的迁移成本更低；LiteRT-LM 的优势在于工具调用和多模态的成套支持，适合想快速搭起端侧智能体的项目。需要强调的是，0.x 阶段的接口变动是真实成本，建议把调用层封装在独立模块里，减少后续升级对业务代码的冲击。

### 6. 【端侧 AI Agent 框架选型：llama.cpp、ExecuTorch 与 LiteRT 三足鼎立】

▌ **导语**

端侧智能体该用什么框架，11 月的调研数据给出了一个比较清晰的图景。Parse.gl 的框架调研显示，在面向移动端轻量智能体的候选中，llama.cpp 以约 67% 的提及率领先，ExecuTorch 约 57%，LiteRT 约 53%，三者形成第一梯队；Core ML 约 45%、MediaPipe 约 39% 更多出现在以 Android 为主的部署讨论里。与框架份额同样重要的是一条工程结论：推理运行时与智能体编排层是两件事，前者负责把模型跑起来，后者负责记忆、会话状态、工具选择、函数执行与多步骤流程。对于移动端，更务实的做法是让推理运行时处理模型执行，把编排层保持得足够轻。

▌ **核心信息**

调研给出的默认推荐是 LiteRT-LM，理由是它同时具备工具调用、多模态输入和硬件加速，能在 iOS 与 Android 上运行，并覆盖 Gemma、Llama、Phi、Qwen 等模型家族。它内置了智能体工作流能力：模型可以请求一次工具调用，应用在自身代码里执行对应函数，再把结果回传给模型，从而闭环一个多步骤任务。需要注意的是，各语言绑定的成熟度不同，iOS 与 Android 的集成路径要在投入前分别验证。llama.cpp 的强项是灵活性，它支持 GGUF 量化模型、对内存与 GPU 卸载有细粒度控制，是成熟的 C/C++ 推理引擎；代价是工具路由、状态管理和记忆这些智能体基础设施要自己搭。ExecuTorch 的优势在 PyTorch 生态与硬件后端，适合已经处在 PyTorch 训练链路里的团队；MLC-LLM 偏编译式 GPU 部署，Core ML 则是 Apple 平台的原生选择。

```
选型速记：
  推理层   -> LiteRT-LM / llama.cpp / ExecuTorch / Core ML
  编排层   -> 轻量自研：记忆 + 状态 + 工具路由 + 多步流程
  避坑     -> 不要把重型 Agent 框架整个搬进手机
```

工程约束同样决定了选型。行业分析指出，实时字幕、语音打断这类场景超过约两百毫秒的往返就会被用户感知为卡顿，隐私敏感数据离端会触发更严格的处理要求，日活百万级产品的云端推理成本会直接压在毛利上，因此合理的架构往往是端云协同：高频、轻量、隐私敏感的任务放端上，需要世界知识的复杂任务交给云端，中间用统一调度层分流。iOS 侧要留意模型体积与首帧加载，常见做法是量化压缩、按场景拆分成小模型并结合后台预加载；Android 侧的关键词则是适配，芯片与系统版本的碎片化要求按档位实测。

▌ **影响判断**

对移动团队来说，这份调研最有价值的不是排名，而是把选型问题拆成了两层。先选推理运行时，再决定编排层要不要自己写，这个顺序能避免一个常见误区：把服务端那套重型智能体框架整体搬进手机，结果内存和功耗先撑不住，模型还没跑稳。推理运行时方面，LiteRT-LM 胜在成套能力，llama.cpp 胜在灵活可控，ExecuTorch 胜在生态衔接，三者没有绝对优劣，应按团队已有的模型资产和目标机型来定。编排层则建议从最小集合开始，先把记忆、会话状态、工具路由和多步流程跑通，再逐步加能力，避免为了概念完整而引入不必要的复杂度。端云协同的调度层是另一个容易被低估的工作，它不是简单的网络判断，而要综合延迟、隐私等级、电量与成本做分流，设计好了能同时改善体验和账单。适配风险集中在真机差异上，模型大小、内存峰值、GPU 后端和温控策略都必须按目标档位测量，实验室数据不能直接外推到线上全量机型。长期看，端侧智能体正在从能跑走向好用，工具调用与多模态会成为标配，团队现在投入的价值不在于追某个框架的版本号，而在于把推理、编排、调度三层的边界划清楚，让后续替换其中一层时不必推倒重来。

### 7. 【Now in Android 工程范式：Compose 模块化与 Baseline Profile 性能基线】

▌ **导语**

当跨平台框架的热闹集中在版本号上时，Android 原生阵营把注意力放回了工程范式本身。根据开发者读物的整理，Now in Android 作为一套完整的 Kotlin 与 Jetpack Compose 应用样例，把架构与模块化的学习路径、测试替身、截图测试和启动性能基线放在同一个工程里展示。它不是一个可以照搬的业务模板，而是一份可直接对照的工程约束清单：数据层接口怎么写、截图测试怎么组织、启动基线怎么建立，都能在仓库里找到对应实现。对想提升工程质量的 Android 团队，这个项目的价值在于把 Compose、模块化与性能测试收进同一套实践，而不是分散在若干篇最佳实践文章里。

▌ **核心信息**

Now in Android 展示的关键实践有几类。第一是架构与模块化，它用清晰的模块边界把数据层、领域层和界面层拆开，新成员可以直接对照一个列表页从数据接口到界面状态的完整链路。第二是测试，仓库里包含 Hilt 测试替身、Roborazzi 截图测试与 Macrobenchmark，前者解决依赖注入下的隔离测试，中间那项把界面回归变成可比对的代码，后者负责真实设备上的性能测量。第三是 Baseline Profile，它与 Macrobenchmark 配合，把关键用户旅程的启动与滚动性能固化成可回归的基线，避免每次发版都靠主观感受判断快不快。

```kotlin
// 基线配置示例：把关键启动路径纳入 Baseline Profile
baselineProfile {
    // 覆盖冷启动与首次进入列表页等高频旅程
}
```

平台与最低要求方面，仓库要求最新稳定的 Android Studio，当前版本清单声明 Kotlin 2.3.0 与 AGP 9.3.2，具体 API level 以锁定提交的 convention plugin 为准。社区数据上，仓库约 22005 星、Apache-2.0 许可，最近在 11 月 4 日更新，最新发布版本为 0.1.1。读物也提醒了接入成本：阅读成本低，照搬成本高，它包含演示数据和特定模块边界，不能直接当成业务后端或发布配置。同一份整理里还提到 Firebase Apple SDK 的动向，AI Logic 与 Crashlytics、App Check、推送和数据服务被放进同一套接入面，且 2026 年 10 月之后的新版本不再发布到 CocoaPods，应优先规划 Swift Package Manager 迁移。

▌ **影响判断**

对 Android 团队，Now in Android 最值得借鉴的是把性能基线工程化这一思路。很多团队的性能优化停留在某次专项治理，发版几次后又退化回去，Macrobenchmark 加 Baseline Profile 的组合能把关键旅程的启动与滚动表现固化下来，每次提交都能看到是否变慢，这比事后追查卡在哪里有效得多。截图测试则适合解决 Compose 重构中的视觉回归，尤其是多主题、多字体缩放场景下，靠人工点检很难覆盖全。需要清醒的是，照搬整套模块结构往往会带来额外成本，这个项目的模块边界服务于它的演示数据，业务项目更适合先从一个列表页开始，对照数据层接口、截图测试和启动基线这三件事做局部落地，验证收益后再扩展。Firebase Apple SDK 放弃 CocoaPods 的信号则提醒跨端团队，依赖管理工具的迁移迟早会落到自己头上，Apple 侧应尽早评估 SPM 路径，AI Logic 的数据边界与失败降级也要单独验证，不能因为和其他服务同处一个接入面就默认行为一致。横向对比，Kotlin Multiplatform 与 Flutter 解决的是共享逻辑的覆盖问题，而这类原生工程范式解决的是单端质量的下限，两者并不冲突；对一个同时维护多端的团队，共享层之外仍需要各端把测试与性能基线做扎实，否则跨端的一致性会被单端的劣质体验抵消。
