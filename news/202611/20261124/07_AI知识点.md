### 1. 【QDA量化配方自动搜索：智能体用KL散度几分钟筛出最优低比特方案】

▌ **导语**
2026 年 11 月中旬，MIT 与 NVIDIA 联合放出论文 QDA（arXiv:2611.23388），把大模型低比特量化里最"手艺人"的一环——量化配方设计——交给智能体自动完成。过去 W4A16、W4A8、W3A16 每种精度组合都要专家手工调整流程，换一个模型就得从头再来；QDA 让智能体在多轮迭代里自己构建、测试候选方案，每次搜索只消耗 64 GPU 小时，在三种精度设置下分别把最强公开配方甩开 0.9、1.4 和 2.2 分。这条知识点拆的就是"让 AI 给自己调量化参数"这件事为什么可行、又凭什么快，以及它把量化工程的成本结构改成了什么样。

▌ **它是什么**
QDA 可以理解为"量化配方发现智能体"。它不是一个全新的量化算法，而是套在现有 PTQ（训练后量化）方法库外面的搜索框架：输入是一个待量化模型和目标精度（比如 NVFP4 W4A4），输出是一份可直接部署的量化配方——包括每层用什么量化器、哪些权重保留高精度、校准数据怎么取。它内置公开 PTQ 方法库，智能体不必逐个移植代码库，而是像搭积木一样组合不同方法。在 320B MoE 模型 GLM-5.3-Flash 上，QDA 搜出的 NVFP4 W4A4 配方恢复了 FP8 精度的 98.3%，比厂商最佳 checkpoint 的 96.9% 还高 1.4 个百分点，且产出的 checkpoint 直接跑在现有 serving kernel 上，不引入额外推理开销。换句话说，它搜出来的东西不是论文里的漂亮数字，而是能直接上线跑的权重。

▌ **它解决了什么问题**
量化落地的最大成本不在"压权重"，而在"试错"。传统做法给一个量化后模型打分要烧掉数十 GPU 小时，专家一天试不了几种配方，模型一换又从零开始，这使得低比特量化长期停留在少数拥有大集群的团队手里。QDA 把单次评估成本从"数十小时"压到"几分钟"，本质是把效果验证这一步从昂贵的大生成任务换成便宜的散度测量，于是搜索空间可以放大几个数量级。它同时解决两个痛点：一是配方随模型、精度漂移，专家经验难以迁移；二是量化后模型容易出现重复循环、长文本退化，光看困惑度根本发现不了。把这两件事自动化，才让"每个模型都有自己的最优配方"从口号变成可执行的流程。

▌ **原理拆解**
整个框架分四步。第一步是候选生成：智能体读取模型结构与目标精度，从方法库里挑选量化器、分组策略与校准样本，拼出一份候选配方，再调用现成 PTQ 流程产出量化模型。第二步是快速打分，也是最关键的创新：不再让量化模型完整跑一遍基准生成，而是在一组智能体"没见过"的推理轨迹上，测量量化模型与原始模型输出之间的 KL 散度——散度越小说明输出分布保持得越好，一次评分几分钟即可完成。第三步是复核：把 KL 散度最低的少数候选拿去做长文本生成，专门检测重复循环这类分布指标抓不到的退化。第四步是迭代，把复核结果写回上下文，下一轮调整配方，整个循环约 64 GPU 小时收敛。这里有一个极易踩坑的设计要点：评估轨迹必须与搜索阶段用过的轨迹隔离，否则智能体会过拟合到校准样本上，KL 散度看着漂亮，真实任务却崩掉。QDA 用"未见轨迹"这一约束，把散度指标变成了可信的代理目标。

▌ **动手验证**
可以做一个最小复现。准备一个 7B 左右的开源模型与一段校准语料，先固定 FP16 基线，再对同一模型跑 W4A16 与 W4A4 两档。第一组实验测评分成本：分别记录完整生成打分与 KL 散度打分各自的 GPU 时长，预期后者快一个数量级以上。第二组测排名一致性：把 KL 散度排序前五的配方拿去做长文本续写，看是否出现重复循环，验证散度与真实退化的相关性。第三组测防过拟合：故意把校准轨迹同时用作评估轨迹，观察 KL 散度是否虚低、长文本表现是否反而更差。操作思路可以写成：取未见轨迹→原模型与量化模型各跑一次→算 token 分布 KL→排序→长文本复核→回写配方。务必控制变量，模型、精度、校准集、serving kernel 全部冻结，只改配方，否则任何数字都不可比。

▌ **对比选型**
与专家手调相比，QDA 的优势是跨模型可迁移、搜索成本低，代价是需要维护方法库与评估轨迹集；专家手调在单一模型上可能更快摸到极限值。与纯困惑度筛选相比，KL 散度对分布保持更敏感，但必须配长文本复核补盲。与 NVFP4、GPTQ、NF4 这类具体量化算法相比，QDA 不在同一层——它是"选算法与配参数"的上层框架，两者是组合关系而非替代关系。选型建议：只有一两个模型且追求极致压缩，手工调参足够；要同时维护多模型、多档精度，或对长文本退化敏感，就该引入自动配方搜索。落地前优先确认产出的 checkpoint 能被现有 serving kernel 直接吃下，否则省下的搜索成本会被重新适配的工程量全部吃掉。

### 2. 【PD分离与PPD动态路由：Agent多轮工具调用下把Turn2+首Token延迟压低68%】

▌ **导语**
华为云开发者社区在《2026 年的 LLM 推理：在内存墙上跳舞》里给出一个判断：2026 年推理优化的胜负手，已经从"换更快的内核"变成"按请求形状动态开关策略"。其中最有代表性的是 PD 分离——把 prefill 和 decode 拆到不同 GPU 池——以及它在新负载下长出来的 PPD 动态路由。尤其当 Agent 进入多轮工具调用，每一轮 append-prefill 都要重新走一遍前缀，PD 分离不再是简单的是非题，而成了按轮次、按上下文长度、按网络能力连续调节的策略空间。这条知识点讲的就是这套"在哪里算"的选择为什么比"算得多快"更决定体验。

▌ **它是什么**
PD 分离指 Prefill-Decode Disaggregation：prefill 阶段计算量大、并行度高，对算力敏感；decode 阶段逐 token 生成、受显存带宽限制，对延迟敏感。把两者放到不同 GPU 池，可以让 prefill 的批量计算不再打断 decode 的连续批处理，从而压住尾延迟。PPD 则是在此基础上加了一层动态路由：按 SLO 权重决定第二轮及以后的 append-prefill 是否留在 decode 节点本地处理，如果跨池搬运 KV 的代价高于本地重算，就干脆不分离。这套思路把"在哪里 prefill"从一个架构标签降级为运行时决策，意味着同一个系统对不同请求可以给出不同答案。

▌ **它解决了什么问题**
传统同池部署里，一个长提示的 prefill 会插队打断正在进行的 decode batch，导致其他请求的尾延迟突然膨胀——在用户侧就表现为"话说到一半卡住"。PD 分离理论上能缓解，但代价是 KV 缓存跨池传输成本随上下文长度线性增长，跨数据中心还要依赖 RDMA 网络。Agent 场景更棘手：一个任务可能调用十几次工具，每次 append-prefill 都触发跨池 KV 传输，省下的首 token 时间会被传输开销吃回去。PPD 要解决的正是这个"省了又吐回去"的悖论——让系统按轮次和上下文长度判断该不该分离，从而在多轮工具调用中依然守住延迟收益，而不是只在第一轮好看。

▌ **原理拆解**
先看收益侧。prefill 与 decode 的资源特征天然互补：前者吃算力、后者吃带宽，混跑时两种利用率都上不去；分离后各自可独立扩缩容，prefill 池堆算力卡，decode 池堆高带宽卡。实测 PD 分离可把 TTFT 改善到 1.4 至 2.3 倍水平，跨数据中心的专门方案在 RDMA 加持下可达 2.3 倍改善。再看成本侧，搬运 KV 的字节数与上下文长度成正比，长上下文场景下传输可能比重算还贵。PPD 的判定逻辑因此引入 SLO 权重：当请求对首 token 延迟敏感且上下文较短，走跨池 prefill；当上下文已经很长或网络带宽不足，就在 decode 节点本地处理 append-prefill。华为云给出的实测是 Turn 2 之后的 TTFT 降低约 68%。这一切成立的前提是"长前缀、短增量、高并发"——正是 Agent 负载的典型形状。原文还强调一个方法论：先冻结模型、精度、并行拓扑、输入输出长度分布和 SLO，再去比较任何数字，脱离这个约束集的优化在 2026 年已经很难被认真对待。

▌ **动手验证**
搭一个两节点小集群即可验证。用 vLLM 或类似引擎分别起 prefill 与 decode 实例，固定同一模型、同一量化精度、同一并行拓扑。第一组测同池基线：记录长提示请求到来时，并发 decode 请求的 P99 延迟曲线，观察是否被 prefill 打断。第二组测 PD 分离：记录 TTFT 改善倍数与 KV 传输耗时，把上下文长度从 4K 拉到 128K，画两条曲线找交叉点，交叉点之后跨池反而不划算。第三组模拟 Agent 多轮：每轮追加约 2K token 的工具返回，对比全程跨池与 PPD 动态路由的端到端耗时，预期第二轮之后 PPD 开始反超。注意冻结输入输出长度分布与 SLO 阈值，否则数字不可比。还可以补一组：关掉 RDMA 或限速网络，看动态路由是否自动把更多轮次改为本地处理。

▌ **对比选型**
与同池连续批处理相比，PD 分离换来尾延迟稳定性，代价是 KV 传输与运维复杂度，适合长提示、高并发且网络条件好的场景。与 KV 缓存量化相比，两者正交：一个改"在哪里算"，一个改"存多细"，完全可以叠加。与投机解码相比，PD 分离优化首 token 延迟与尾延迟，投机解码优化 decode 阶段的 token 经济性，关注点不同。选型上，短对话、低并发用同池足够；Agent 工作流、工具调用密集且已具备同机房高速网络，值得上 PD 分离；多轮场景务必加动态路由，否则收益会被 append-prefill 的传输开销抵消。下一步值得追踪的是自适应投机解码与动态 PD 路由的组合——当系统能在"猜多少、在哪里 prefill、压到几位"之间连续调节，优化单位才真正从模型下沉到请求。

### 3. 【Loop-9B循环权重复用：32层物理层跑出56次计算，4bit量化把权重压到4.9GB】

▌ **导语**
商汤科技在 11 月 17 日晚发布并开放 SenseNova Loop-9B 的权重与代码，给出一条与"堆参数"相反的路径：不增加物理层，而是让同一批中间层权重被反复执行。模型总参数约 9B，通过 Loop 结构把 32 个物理解码层扩展为 56 次层计算，再配合流形约束超连接（mHC）在小参数规模下扩展计算深度；4bit 量化后权重约 4.9GB，部署显存可低至 10GB 以内。这条知识点讲的是"循环计算深度"这笔账怎么算，以及为什么它对私有化与本地部署格外友好，又为什么它不是免费的午餐。

▌ **它是什么**
Loop-9B 的核心是 Looped Transformer：传统 Transformer 每层权重只在前向传播里用一次，循环结构则让同一组层被多次调用，用时间换空间——参数量不变，但单次推理的有效计算深度增加。官方说法是 32 个物理层扩展为 56 次层计算，推理等效参数约 14.6B。mHC（流形约束超连接）负责在多次循环之间稳定信号，避免深层复用带来的激活爆炸或偏移累积。模型支持文本与图像输入、文本输出，上下文最高 512K token。4bit 量化后权重约 4.9GB，这意味着一张消费级显卡或 10GB 级显存就能把它跑起来，寒武纪、沐曦等国产算力平台在发布首日完成 Day 0 适配，说明这套结构对推理栈的改动是可控的。

▌ **它解决了什么问题**
大模型部署的痛点是能力与显存绑定：想要更强推理就得塞更多参数，显存门槛水涨船高。Loop-9B 证明，在固定参数预算下通过复用权重增加计算深度，能拿到接近更大模型的效果。这对私有化部署意义重大——企业不必为 27B 模型配高显存卡，9B 的权重就能在边缘设备上提供接近的能力，让数据不出内网的本地助手真正可行。另一个问题是长上下文：512K token 的窗口配上低显存占用，让本地文档分析、长会话 Agent 变得现实。商汤公布的数据显示，在 Agent 与数据分析评测中，NL2Repo 得 41.36，接近 Qwen3.8-27B 的 44.60；AIDABench 得 65.31，反超后者的 65.01。这类"小权重、长上下文"的组合，正好命中私有化场景对成本与合规的双重诉求。

▌ **原理拆解**
拆解成三层。第一层是循环结构：设定循环次数 k，前向传播时把中间层重复执行 k 次，每次输入是上一次输出与原始嵌入的某种组合；参数量只算一次，计算量却近似乘以 k，这就是等效参数大于物理参数的来源，也是"用时间换空间"的具体含义。第二层是 mHC：普通残差连接在多轮堆叠后会累计偏移，mHC 把超连接约束在流形上，相当于给每轮循环加了一条稳定轨道，使加深计算深度时不至于数值发散——这是循环结构能work的关键前提，没有它，多轮复用很快就会退化。第三层是 4bit 量化：把权重从 BF16 压到 4bit，体积缩到约四分之一，9B 参数落到 4.9GB；配合 KV 缓存的低精度存储，整体显存压到 10GB 以内。三者叠加的效果是参数效率、计算深度与部署门槛同时改善，但代价也清楚：多轮循环直接增加单次推理延迟，所以这条路线天然适合显存受限、对绝对延迟不敏感的场景。

▌ **动手验证**
可以在单卡环境做对照实验。第一组固定参数量，比较循环次数 k 取 1、2、3 时在推理基准上的得分，验证加深计算深度是否真能换来能力，同时记录延迟与显存占用，画出收益曲线，找到收益开始变平的拐点。第二组固定 k，比较 BF16 与 4bit 量化下的精度差与显存差，重点观察长上下文任务上是否有退化。第三组测长上下文：把输入从 32K 拉到 512K，观察首 token 延迟与显存峰值，确认 10GB 预算是否撑得住。需要注意循环次数不是越多越好，mHC 的稳定性也有边界；建议用同一批提示做多次采样取均值，避免偶然性。若没有 9B 模型，也可先在更小的模型上实现 Looped Transformer 的基本思路，观察循环带来的收益与延迟曲线。

▌ **对比选型**
与直接训练更大模型（如 27B）相比，Loop-9B 用参数效率换部署范围，代价是多轮循环带来的延迟，适合显存受限但能容忍稍高延迟的场景。与投机解码相比，一个改模型结构、一个改解码流程，两者可以叠加使用。与 NVFP4 这类量化方案相比，4bit 量化只是 Loop-9B 落地的最后一公里，不是它的核心创新。选型建议：云端高并发服务追求吞吐，仍应优先考虑大参数 MoE 或专用推理优化；边缘、本地、私有化场景且需要长上下文，可以优先考虑这类循环小模型。评估时别只看参数量，要看"等效计算深度、量化后权重体积、上下文长度"三项组合起来是否匹配你的硬件预算与延迟要求。

### 4. 【ReAct推理行动交织：Agent规划模块如何把复杂目标拆成可执行子任务】

▌ **导语**
当 AI Agent 从演示走向生产，最容易被忽略的是它内部那个朴素的循环：想一步、做一步、看结果、再想一步。三个皮匠报告在梳理 2026 年主流 Agent 技术时，把这套认知闭环拆成感知、规划、行动、记忆四大模块，并明确指出规划模块正是通过 ReAct 或 Chain-of-Thought 等算法把复杂目标拆解为子任务。ReAct 不是新概念，却是理解 Agent 为什么能办事的钥匙——它把推理和行动编织进同一条轨迹，让模型边想边调工具，而不是想完再一次性执行。理解它，才能理解上层框架到底在编排什么。

▌ **它是什么**
ReAct 是 Reasoning 加 Acting 的缩写，核心是让模型交替生成思考（Thought）与行动（Action），再根据工具返回的观察（Observation）继续下一步。一条典型轨迹是：思考"我需要先查销售额"→行动"调用 SQL 工具"→观察"返回三行数据"→思考"数据有异常，再查上个月"→如此循环，直到模型判断任务完成并给出答案。它与纯 Chain-of-Thought 的区别在于：思维链只在脑子里推演，ReAct 把外部工具结果实时接回推理链，因此能纠正凭记忆瞎猜的错误。在四模块框架里，ReAct 主要落在规划与行动的交界处，向上承接目标分解，向下连接 Function Calling 与 MCP 工具调用，是承上启下的枢纽。

▌ **它解决了什么问题**
纯思维链有两个硬伤：一是知识停留在训练截止日期，查不到实时数据；二是中间步骤的错误无法被外部信号纠正，一步错步步错。ReAct 用行动观察回路把外部世界拉进来，让模型借助工具获取事实、验证假设，等于给推理装上了现实校准器。它还解决任务太大不知从哪下手的问题：把复杂目标拆成一串可执行的子动作，每一步只面对一个小决策，大幅降低规划难度。2026 年的框架生态也围绕这个循环分化——LangGraph 用图编排管理条件路由，AutoGen 用消息驱动多 Agent 对话，CrewAI 用角色加任务加团队做快速原型，Microsoft Agent Framework 主打企业级数据流工作流。理解 ReAct，就看懂了这些框架共同编排的那个基本单元。

▌ **原理拆解**
从提示结构看，ReAct 把轨迹写成固定的少样本模板：每个示例包含若干轮思考、行动、观察，模型学会模仿这种交替格式。从决策机制看，每一步模型都要在继续思考和调用工具之间做选择，这个选择由当前观察决定——信息不足就发起工具调用，信息足够就收敛到答案。从错误恢复看，工具返回的错误码本身成为下一轮观察，模型据此换一种查询或换一个工具，这构成最朴素的自我修正闭环。从上下文管理看，轨迹不断追加会膨胀，因此工程上通常配压缩或摘要机制，只保留关键观察，否则长任务会撑爆上下文窗口。值得注意的是 ReAct 与反思类机制的分工：ReAct 负责边做边看，Reflexion 类机制负责做完复盘，两者在不同时间尺度上工作；华企网校的架构解析也把规划决策层与评估反思层列为相邻但独立的层级，这正是生产架构里两个分开的组件。

▌ **动手验证**
用一个需要两步以上工具调用的任务做验证，例如查某产品上月销售额并与目标比较，若未达标再给出原因假设。第一组跑纯思维链，观察模型是否编造数据、是否能发现异常。第二组跑 ReAct，给模型 SQL 查询与计算器两个工具，记录思考、行动、观察的完整轨迹，看它是否会先查数、再比较、最后下结论。第三组故意让第一个工具返回错误码，看模型能否在下一轮换查询而不是卡死或重复同样的错误调用。评估指标建议看三项：任务完成率、工具调用轮数、错误恢复成功率。操作思路是维护消息列表，若模型输出行动则执行工具并把观察追加回列表，循环直到模型输出最终答案。注意给工具设置超时与权限边界，避免 ReAct 陷入无限调用循环把预算烧光。

▌ **对比选型**
与纯思维链相比，ReAct 多了工具交互，正确率上限更高，但轮数与 token 成本也更高，简单事实问答不必上 ReAct。与先规划后执行这类方案相比，ReAct 更灵活但更容易陷入局部试错，长程任务可以把两者结合：先出大纲，再用 ReAct 逐步填充。与 Reflexion 相比，ReAct 是执行时循环，Reflexion 是任务后复盘，可叠加成执行、复盘、再执行的三阶段。框架选型上，快速原型用 CrewAI，复杂条件路由用 LangGraph，多 Agent 对话用 AutoGen，企业级部署用 Microsoft Agent Framework。所有这些框架的共同前提是工具接口标准化——这正是下一条知识点要讲的 MCP 协议的价值所在。

### 5. 【MCP纵向总线与A2A横向总线：智能体工具调用与跨体协作的分层协议】

▌ **导语**
在 Agent 技术栈里，2026 年最值得记住的一组对照是 MCP 与 A2A。三个皮匠报告把两者概括成两条总线：MCP 管 Agent 与工具之间的纵向连接，由 Anthropic 主导；A2A 管 Agent 之间的横向协调，由 Google 主导。白嫖计的开发者工具页进一步注明，A2A 现归 Linux 基金会治理。两者不是竞争关系而是互补分层，2026 年 6 月双方还发布了融合草案。这条知识点拆的就是这套纵向插工具、横向找同伴的分层协议，以及它为什么成了生产架构的默认骨架。

▌ **它是什么**
MCP（Model Context Protocol）是一个开放协议，标准化 AI 模型与外部工具、数据源之间的通信，常被比喻成 AI 世界的 USB-C 接口。它采用客户端与服务端架构：任何工具或数据源实现一个 MCP Server，对外暴露标准化的资源（可获取的数据）与工具（可执行的操作）；AI 应用如 Claude Desktop、Cursor 内置 MCP Client，负责发现并连接服务端。A2A（Agent2Agent Protocol）由 Google 发起，让不同厂商的智能体相互发现、通信、委托与协商。一个典型生产架构是：编排 Agent 通过 A2A 把任务委派给专家 Agent，后者再通过 MCP 调用数据库、API 与文件系统，两条总线各司其职。

▌ **它解决了什么问题**
MCP 解决的是 N 个模型乘以 M 个工具的集成爆炸：没有统一协议时，每种模型接每种工具都要写适配代码；有了 MCP，工具方只需实现一次服务端，应用方只需实现一次客户端。华企网校把它总结为解耦与集成——业务团队独立维护自己的财务数据服务端、库存管理服务端，AI 应用团队不改核心代码就能让模型获得新能力。A2A 解决的是跨组织、跨厂商的 Agent 协作：不同框架、不同公司造的 Agent 要互操作，需要一套共同语言。如果只有 MCP，Agent 能干活但彼此孤立；只有 A2A，Agent 能对话却没有手脚。两者叠加才构成完整技术栈，缺一条都会在某处卡住。

▌ **原理拆解**
MCP 的工作流程分三步：发现、调用、返回。客户端连接服务端后先获取能力清单，知道有哪些资源与工具可用；模型在推理中决定调用某个工具，客户端发出标准化请求；服务端执行并把结构化结果回传，模型再转成自然语言。关键在于结构化——工具输入输出都有 schema，大幅减少模型臆测参数的错误。A2A 的抽象层次更高：它定义 Agent Card 用于能力发现、Task 对象用于任务生命周期管理、Artifact 用于交付产物。在分层架构里，A2A 是横向总线，负责把任务在 Agent 之间路由；MCP 是纵向总线，负责每个 Agent 往下钻到具体工具。2026 年 6 月的融合草案在 Linux Foundation 治理下把两者纳入同一框架，避免协议打架。安全侧则形成五道闸方法论：出站默认拒绝、副作用分级、模型外校验、速率熔断、全量审计与紧急关闭——当 Agent 从回答问题走向自主办事，风险从内容安全扩展到行为安全，这五道闸就是行为边界。

▌ **动手验证**
搭一个最小 MCP 闭环：写一个只暴露两个工具的服务端（比如查天气、查汇率），用支持 MCP 的客户端连接，让模型回答一个需要两次工具调用的问题。第一组观察能力发现是否正确、参数是否按 schema 填充。第二组故意传错参数，看服务端是否返回结构化错误、模型能否据此纠正而不是硬编。第三组做解耦验证：把服务端换成另一套实现但保持接口不变，确认客户端无需改一行代码。A2A 侧可以跑两个不同框架的 Agent，让一个通过 A2A 把子任务委派给另一个，观察任务状态流转与产物回传。验证时重点记录三项：接入新工具的代码改动量、跨 Agent 委派的成功率、高权限工具是否被审计日志覆盖。若发现工具调用缺少结构化错误返回，优先补 schema 而不是靠提示词补救。

▌ **对比选型**
MCP 与 A2A 是分层互补而非二选一：单个 Agent 调工具只需 MCP，多 Agent 跨组织协作才需要 A2A。与 Function Calling 相比，MCP 把工具接口外置成标准协议，可复用、可发现，而 Function Calling 更贴近模型原生但绑定具体厂商。与 LangGraph、AutoGen 等框架相比，MCP 与 A2A 属于协议层，框架属于编排层，框架的客户端与服务端通常实现这些协议。选型建议：新系统优先选支持 MCP 的工具与客户端，避免自研适配；需要多 Agent 协作时引入 A2A 并检查治理归属；高权限工具务必配齐五道闸。注意协议仍在演进，融合草案意味着接口细节可能调整，生产环境应锁定版本并关注 Linux Foundation 的治理动向。

### 6. 【MCP长期记忆工具：Mem0与Supermemory如何让Agent跨会话记住用户事实】

▌ **导语**
Agent 的记性在 2026 年成了一条独立赛道。Zaira Labs 的《MCP Agent Memory Tools (2026)》盘点了 8 个通过 MCP Server 提供记忆能力的工具，AI Automation Library 的 11 月 22 日 Agent Toolkit 清单也把 Basic Memory、Supermemory 列在记忆与上下文栏目。值得注意的是，这些工具把记忆做成可插拔的 MCP 端点——Claude Code、Cursor、Codex 都能指向同一个记忆层。这条知识点讲的是：为什么记忆层要从框架里剥离出来、用 MCP 暴露，以及 Mem0、Supermemory 这类工具各适合什么场景，有哪些必须提前知道的局限。

▌ **它是什么**
MCP 长期记忆工具指以 MCP Server 形式对外提供持久记忆的服务：Agent 通过标准协议读写记忆，而不是在每个框架里各写一套。Zaira Labs 盘点的主要包括：Basic Memory，把记忆存成本地 Markdown 笔记，可用 Obsidian 打开，通过 MCP 供客户端读写；claude-mem，用异步 hook 与本地 worker 把会话摘要与带时间戳的观察记成可检索记忆；Cognee，把向量相似、图关系遍历、关键词匹配三种检索合在一个查询里；Mem0，提供托管的向量与图基础设施做事实提取与检索；Supermemory，从对话中学习事实与用户画像并在下一轮返回；Hyperspell，把查询结果限制在精简高亮与结构化文档框内以控制 token 消耗。它们共同的特点是接口标准化、后端可替换。

▌ **它解决了什么问题**
框架内置记忆最大的问题是锁死：换客户端就得重来，记忆也难以审计与迁移。把能力做成 MCP Server 后，记忆变成独立、可检查、可替换的一层，这也是本地优先路线受欢迎的原因——Basic Memory 的笔记是你能直接打开编辑的纯文本，Agent 知道什么一目了然。第二个解决的是跨会话遗忘：没有记忆层，Agent 每次会话都从零开始，重复问同样的问题、重复犯同样的错。第三个解决的是检索方式单一：只靠向量最近邻会漏掉关系型问题，Cognee 的三库模型把图关系补上；只存向量难以溯源，Mem0 与 Cognee 保留来源链接，让 Agent 能引用事实出处而不是空口下结论。

▌ **原理拆解**
从数据流看，记忆工具通常分三阶段。写入阶段：从对话或文档中用一个 LLM 抽取事实、生成用户画像、建立实体关系，这一步带来可变延迟，是 Zaira Labs 明确提醒的注意点。存储阶段：Basic Memory 用纯文件，Cognee 默认 SQLite 加 LanceDB 加嵌入式 Ladybug，Mem0 用托管向量与图库，不同后端决定并发能力与部署形态。检索阶段：向量负责概念相似，图负责关系遍历，关键词负责精确匹配，混合检索在单一查询里完成。MCP 在这一切外面套了一层统一接口：客户端只需知道端点地址，不必关心后端是文件还是图数据库。局限同样清晰——Basic Memory 本地模式是单机，团队要同步得靠付费云版；claude-mem 需要 Node.js、Bun、uv 等运行时；Cognee 的嵌入式 Ladybug 用文件锁，不适合并发写；抽取与建图依赖模型调用，延迟不稳定，对亚毫秒级 SLA 不友好。

▌ **动手验证**
用两个客户端指向同一个记忆服务端做验证。第一组写入记忆：让 Claude Code 通过 MCP 写入一条用户偏好，再用 Cursor 连接同一端点检索，确认跨客户端可见，这是协议解耦的直接证据。第二组测溯源：让 Agent 回答一个需要引用来源的问题，检查返回是否带来源链接，对比 Mem0 与纯向量方案的差别。第三组测混合检索：构造一个只有图关系才能答对的问题，看 Cognee 是否比纯向量检索更准。第四组测局限：用两个并发进程同时写 Cognee，观察是否出现锁冲突；同时记录事实抽取的延迟分布，看是否满足业务 SLA。评估维度建议用 LongMemEval、LoCoMo 这类长记忆基准，但要注意厂商自己公布的分数需独立复核。若追求可控，Basic Memory 的纯 Markdown 最适合先上手。

▌ **对比选型**
Basic Memory 胜在透明、可编辑、零外部依赖，适合个人与本地优先场景，代价是单机、图能力弱。claude-mem 适合编码会话复盘与决策追溯，代价是运行时依赖较重。Cognee 适合需要关系遍历与溯源的复杂知识网络，代价是三库模型的复杂度与并发限制。Mem0 适合托管、多用户、跨会话画像，代价是要依赖其云或自托管图基础设施。Supermemory 把文档搜索与事实记忆合一，适合不想维护两套管道的团队，但其自我报告的基准分数需谨慎看待。Hyperspell 适合对 token 预算敏感且需要权限继承的企业场景。共同建议：先明确要本地可控还是跨端共享，再选后端；无论选哪个，都通过 MCP 端点接入，保留未来替换的余地。
