### 1. 【inference-optimisation-skill 实测：把爬山调参写成标准流程，本地大模型提速不再靠玄学】

> 📍 **导语**：本地跑模型的人大多经历过这种场景：改一个参数快了，再改一个反而慢了，最后凭感觉留下一组说不清为什么的配置。2026-11-25 的开源热榜上，sybil-solutions/inference-optimisation-skill 以 2.6K Star 冲到榜首，它做的事很克制——把"用爬山法找最优推理参数"写成一套智能体能照着执行的标准流程。这个技能用 MIT 许可发布，主打 Claude Code 生态，标签是 agent-skill、benchmarking、claude-code。它值得关注不是因为提出了新算法，而是把调参这件玄学活变成了可复现、可交接的工程步骤。对任何在本地硬件上榨性能的人来说，这种把隐性经验显性化的工具，正在改变优化工作的组织方式。

**▌ 它是什么？**
这是一个 Agent Skill，即一个装有 SKILL.md 与配套脚本的目录，被 Claude Code 之类的编码智能体按需加载。它把本地大模型推理提速的流程固化下来：先确定要调的参数空间（如 batch size、量化方式、KV cache 策略、线程数、投机解码的草稿长度），再用爬山法系统搜索——从一个基准配置出发，每次只改动一个变量，跑一遍基准测试，若指标变好就接受该改动，否则回退，直到再也找不到改进空间。整个过程有记录、有日志、有最终配置快照。开发者要做的只是把"帮我优化这个模型的推理速度"交给智能体，剩下的由技能里的步骤驱动。它不是运行时库，不参与推理本身，而是给智能体一份"怎么调参"的操作手册，因此不绑定某一款推理引擎，只要能跑评测脚本就能用。

**▌ 它解决了什么问题？**
本地推理调参的痛点有三。第一是缺乏流程：多数人靠翻博客、抄别人的配置，别人的机器和模型一换就失效。第二是不可复现：改了参数、跑快了，却没记下改了什么，过两周想复现已经说不清。第三是维度多：batch、量化、线程、缓存、投机解码互相耦合，人肉一次试一个组合，组合数很快爆炸。这个技能把"搜索—评测—接受或回退—记录"写进技能文件，让智能体按统一节奏跑，等于给调参装了实验记录本。对企业场景，它还解决交接问题：新同事不用读懂老工程师的经验直觉，照着技能产出的配置快照和基准报告就能接手。过去一周 Star 涨到 2.6K，说明这种把经验变成流程的做法击中了普遍痛点——调参不该是少数人的手艺，而应是任何人可执行的标准动作。

**▌ 核心原理拆解**
核心是两件事：参数空间的显式化与爬山搜索的纪律化。输入是你的模型、硬件与评测脚本；技能先读环境，生成候选参数清单；然后进入循环：① 固定当前配置，跑基准，记录延迟与吞吐；② 从候选清单里挑一个参数做一个小步改动；③ 再跑基准，与基线比；④ 若提升超过阈值则接受并更新基线，否则回退；⑤ 重复直到遍历完参数或达到迭代上限；⑥ 输出最优配置与完整实验日志。关键设计是"单变量改动 + 明确接受准则"，避免多参数同时变化导致无法归因。评测环节一般接现成的 benchmark 工具，技能只负责编排与判定，不重复造轮子。另一个设计是技能随仓库更新：调参经验被版本化，团队可以 fork 后加入自己硬件的参数模板。输出不只是一组数字，还有"为什么这么选"的证据链，这正是它与一次性脚本的根本差别。

**▌ 动手验证**
以 Claude Code 为例：① 克隆仓库，把技能目录放到项目的 .claude/skills/ 下；② 用 /plugin marketplace add 指向仓库并安装该技能；③ 准备一份最小评测脚本，能输出首字延迟与 tokens/s；④ 对智能体说"用 inference-optimisation-skill 优化 ./models/xxx 的推理参数，迭代上限 20 次"；⑤ 观察它生成实验日志与最终配置。预期结果：得到一份带基线与对照的配置快照，日志里能看到每次改了哪个参数、指标变化、是否被接受；在你自己的硬件上复现出比初始配置更好的吞吐。注意：先在小模型、短基准上试跑，确认评测脚本稳定后再放大搜索范围，否则会把噪声当成提升；每轮基准要多跑几次取中位数。

**▌ 对比与选型**

| 维度 | 手动调参 | 通用调参脚本 | 本技能 |
|------|---------|-------------|--------|
| 流程纪律 | 靠自觉 | 固定脚本 | 标准流程 |
| 记录可追溯 | 常缺失 | 部分有 | 完整日志 |
| 团队协作 | 难交接 | 一般 | 可共享模板 |

手动胜在灵活，适合探索性实验；通用脚本胜在跑得快，但团队难共享上下文；本技能胜在流程标准化与可交接，适合多人协作、需要审计调参过程的团队。适用场景：本地部署 LLM 的小团队、需要在固定硬件上榨性能的应用、要把调优经验沉淀成资产的工程组织。若你只是临时跑一次 demo，手动改两个参数更快；若要把调参变成团队里谁都能执行的标准动作，技能化更划算。

### 2. 【t8y2/dbx 拆解：25MB 单文件管百种数据库，MCP server 三级权限划清智能体边界】

> 📍 **导语**：2026-11-24 的 AI Agent GitHub Digest 里，一个用 Rust 写的数据库管理工具被反复提及：t8y2/dbx，31,188 Star，当日仍涨 34 颗。它把 100 多种数据库（MySQL、PostgreSQL、MongoDB、ClickHouse 等）塞进一个 25MB 的跨平台文件，还内建 AI SQL 助理。真正让安全团队感兴趣的是它单独发布的 MCP server：把智能体能做的事拆成只读、可写、高风险写入三级权限。这个设计回应了当下最现实的问题——当 Claude Code、Cursor 这类工具要连生产库，边界应该怎么划。对既要效率又要合规的团队来说，权限分级比功能多少更值得关注。

**▌ 它是什么？**
dbx 是一个跨平台数据库客户端，Rust 编写，单一可执行文件约 25MB，覆盖上百种数据库与数据源。你可以把它理解成轻量版 DBeaver 加内置 AI 助手再加可插拔的 MCP 服务。除了常规的浏览表结构、写 SQL、看结果，它把连接配置集中管理，并对外暴露一个独立的 MCP server，让编码智能体直接复用 dbx 里已经配好的连接，而不必在每个 agent 里重新填一遍 host、端口、账号。项目采用 Apache-2.0 许可，代码托管在 GitHub，最近一周出现在多份 Agent 生态日报里。它的定位不是"又一个 GUI 客户端"，而是数据库连接的单一事实源加智能体访问入口，把人和机器对数据库的访问统一到一处管理。

**▌ 它解决了什么问题？**
第一个痛点是工具碎片：开发机上装着 DBeaver、psql、mongo shell，连接信息散落在各处，换个 agent 又要重新配置一遍。第二个痛点是 AI 写 SQL 的落地断层：智能体能生成语句，却不知道连到哪个库、用哪个账号，落地时还要人工复制粘贴。第三个痛点最关键——权限粗放：很多 MCP 数据库服务器一旦接上就是全权限，智能体一条 DELETE 就能改生产数据。dbx 把权限做成三档，等于给"让 AI 碰数据库"这件事装了闸门。对 DBA 来说，这意味着可以让智能体只读排查问题，写操作需要显式切换配置；对开发者来说，本地和生产的连接可以在同一个界面里分级管理，避免误把生产库当成测试库操作。

**▌ 核心原理拆解**
架构上分三层。最底层是统一连接层，把不同数据库的协议差异封装起来，对外提供一致的连接描述（类型、地址、凭据、TLS 设置），这也是 25MB 体积能支持多种库的原因——共用一套抽象，协议按需加载。中间层是查询执行层，负责 SQL 编辑、结果渲染、事务与超时控制。最上层是两个消费者：GUI 前端与 MCP server。MCP server 的权限分级是关键设计：只读档只允许 SELECT 类语句；可写档开放 INSERT、UPDATE；高风险写入档才放开 DROP、TRUNCATE 等破坏性操作，并建议配合确认机制。智能体通过 MCP 调用时，拿到的是被当前档位约束的工具集，而不是数据库的全权句柄。输入是 agent 的 SQL 请求，处理是经过权限过滤的语句执行，输出是结构化结果或拒绝原因，整个链路把权力关进了配置的笼子。

**▌ 动手验证**
① 从 GitHub Releases 下载对应平台的单文件二进制，赋予执行权限后启动；② 在连接管理界面新增一个测试库连接，先设为只读档；③ 按仓库文档把 MCP server 配置到 Claude Code 或 Cursor 的 mcp 配置里，指向 dbx 的 server 命令；④ 让智能体"列出该库所有表并统计行数"，预期能返回结果；⑤ 再让它执行一条 DROP TABLE 测试语句，预期被权限层拒绝并给出明确提示；⑥ 确认无误后再把可写档用于开发库。预期结果：同一个连接配置在 GUI 和智能体两边共用，只读档下任何写操作都被挡住，日志里能看到被拒绝的语句。注意：不要把高风险写入档用于生产连接，除非有独立的审批与备份流程。

**▌ 对比与选型**

| 维度 | dbx | DBeaver | 通用数据库 MCP |
|------|-----|---------|---------------|
| 体积 | 25MB 单文件 | 较大 | 视实现 |
| 权限 | 三级分档 | 账号级 | 多为一刀切 |
| AI 集成 | 内建加 MCP | 插件 | 需自配 |

选型建议：需要让编码智能体安全访问数据库、又希望连接配置统一的人选 dbx；只做人工查询且要极全的数据库特性，DBeaver 更成熟；只想快速给单一场景加 MCP 入口，轻量通用 MCP 服务器够用。适用场景：多数据库环境的开发者、希望在 CI 与本地共用连接定义的小团队、对智能体写操作有合规要求的组织。

### 3. 【sous-labs/songe 上手：旁听你的纠正与重试，夜里把本地模型蒸馏成私人适配器】

> 📍 **导语**：你有没有注意过，自己每天纠正 AI 的那些话其实很值钱——"不对，这里要用我们的写法""别用这个库，换那个"。2026-11-25 开源热榜上一个叫 sous-labs/songe 的项目（675 Star，Apache-2.0）决定把这些纠正攒起来：它在你本机旁听日常操作中的纠正与重试，夜里自动把这些数据蒸馏成一个个性化小适配器，全程不出本机。这个思路把个人偏好从每次都要重复写的提示词，变成模型层面的一份增量权重。它代表的是一类新工具：不求模型更大，只求模型更像你。对个人开发者和重视数据隐私的团队，这个方向尤其有吸引力。

**▌ 它是什么？**
songe 是一个本地运行的学习代理，项目自述叫"本地模型的私人教练"。它不替换你正在用的编码智能体，而是以旁路方式观察交互：当你修改 AI 的产出、删掉它给的方案、反复重试同一类任务时，它把这些纠正信号记录下来。到了空闲时段（比如夜里），它用这些信号对本地模型做轻量蒸馏，产出一个小型适配器——常见的形态是 LoRA 之类的小权重，加载后让基础模型更倾向于按你的习惯回答。整个过程在本机完成，音频、代码、提示词都不上传。它不是通用训练框架，而是把"从日常纠正到个性化适配器"这条链路自动化、后台化的工具，让模型随着使用时间慢慢长出你的习惯。

**▌ 它解决了什么问题？**
提示词工程的天花板很明显：你写再多"请用我们团队的命名规范"，模型也会在长对话里忘掉，而且每次开新会话都要重来。微调传统方案又太重——要准备数据集、写训练脚本、占一块 GPU 半天。多数人的纠正信号就这样白白流失了。songe 填补的正是中间的空白：把"你每一次说不"的瞬间自动变成训练数据，把微调变成后台任务。另一个痛点是隐私：把代码和纠正记录发到云端训练服务，很多团队不允许；songe 强调全程本机，让数据不出门。对独立开发者，它意味着模型会随使用时间越来越懂你；对团队，它可以把资深工程师的纠正沉淀成一份可共享的偏好适配器，把个人经验变成组织资产。

**▌ 核心原理拆解**
流程可以拆成四段。① 信号采集：旁路监听智能体的会话与文件改动，把"用户否决—用户改写后的版本"配对成样本对，同时记录重试次数这类隐式反馈。② 样本筛选：不是所有纠正都值得学，临时笔误或一次性的需求要过滤掉，只保留反复出现的偏好模式；这一步决定了适配器会不会学歪。③ 蒸馏训练：用筛选后的样本对本地模型做参数高效微调，只更新少量适配器权重，基础模型保持不动，因此成本低、可回滚。④ 加载与验证：把新适配器挂回智能体，在下一次交互里验证偏好是否被遵守，效果不佳就丢弃或降低权重。关键设计是后台批处理加小步更新：不打断白天工作，每次只学一点点，避免一次性把偶发行为固化。输出物是一份版本化的适配器及其来源样本摘要，方便追溯与回滚。

**▌ 动手验证**
① 按仓库说明用 pip 或 cargo 安装 songe，并指定一个本地模型路径；② 配置监听目录或会话来源，让它能看到你的编码智能体产出与你的改动；③ 白天正常使用，刻意对几类输出做纠正（比如统一日志格式）；④ 触发一次夜间任务（或按文档手动运行 songe distill），观察它生成的样本数量与适配器文件；⑤ 把适配器加载到你的智能体配置里，再提同类需求，看输出是否更贴近你的写法。预期结果：样本报告里能看到被反复纠正的模式，适配器加载后同类错误的复现率下降。注意：先在小样本上验证，避免它把一次性的实验性改动当成长期偏好；涉及敏感代码时确认数据确实只在本地处理。

**▌ 对比与选型**

| 方式 | 反复写提示词 | 手动微调 | songe |
|------|-------------|---------|-------|
| 数据成本 | 每次重写 | 需整理数据集 | 自动采集纠正 |
| 隐私 | 依赖云端上下文 | 视方案 | 全程本机 |
| 适合 | 轻量偏好 | 固定大改 | 长期习惯沉淀 |

选型建议：偏好简单、每次会话都很短的人，写清楚提示词就够；需要一次性大幅改变模型行为（如换领域），手动微调更可控；想让模型随时间越来越贴合个人习惯，且能接受本地算力开销，songe 的自动化最有价值。适用场景：个人开发者、对数据出境有顾虑的团队、希望把资深成员经验固化成适配器的小组织。

### 4. 【MCP 两周年新演进：Skills over MCP 让工具自带说明书按需加载，长任务与风险审批写进协议】

> 📍 **导语**：2026-11-24，Model Context Protocol 迎来开源两周年，Anthropic 一并抛出四项更新：Skills over MCP 进入公测，Tasks 与 Elicitation 正式可用，File Uploads 即将推出。多家技术媒体报道称，MCP 每月 SDK 下载量已超 7 亿次、连接 Claude 的连接器超过 1 万个。这次更新的意义不在某个功能多炫，而在它改写了工具与智能体的关系：过去服务器只告诉模型"我能做什么"，现在还能附上"该怎么做"的说明书，而且说明书随服务器一起版本化。对开发者来说，这是从写工具到写工作流的转变，也意味着工具作者的责任边界被重新划定。

**▌ 它是什么？**
Skills over MCP 是 MCP 规范及其官方扩展的一部分：一个 MCP 服务器除了暴露工具（tools），还可以发布技能（skills），即分步工作流、最佳实践或某个组织专属的操作手册。Claude 只在任务确实需要时才加载某个技能，从而压低上下文占用；服务器更新时技能同步更新，用户无需单独安装。Tasks 允许服务器把耗时操作（甚至完整的智能体循环）放到后台跑，Claude 继续处理别的事，稍后再取结果；状态包含 working、input required、completed、failed、cancelled。Elicitation 让服务器在执行中途暂停，通过表单或链接向用户要输入或审批，再接着往下走。File Uploads 则让 PDF、表格、图片绕过上下文窗口直达服务器，目前仍在原型阶段，尚未定档。

**▌ 它解决了什么问题？**
第一个问题是"会调用不等于会用"。工具清单只描述能力，不描述次序与禁忌，开发者只能把流程知识塞进每一条提示词，结果是不一致、难维护。Skills 把这部分知识从提示词搬到服务器侧，随 API 绑定一起版本化。第二个问题是长任务阻塞：CI 流水线、深度调研动辄几分钟，过去一个工具调用没结束，智能体就什么都干不了；Tasks 把它变成可轮询的后台作业。第三个问题是危险操作缺闸门：删仓库、跑破坏性 SQL、创建付费资源，过去靠提示词里反复叮嘱"先问我"；Elicitation 把"先问一句"做成协议级原语。对工具作者，这三项意味着不必再为每家客户端重复实现编排逻辑；对使用者，意味着更少的坏调用和更少的手动提示，流程一致性显著提升。

**▌ 核心原理拆解**
从数据流看，技能是一份带触发条件的指令文档：服务器在握手阶段声明可用技能及其简短描述，Claude 判断当前任务匹配时才把完整内容载入上下文，用完即弃，这正是按需加载降低上下文占用的机制，Anthropic 称在多服务器场景可省百分之八十五以上的上下文开销。Tasks 的核心是任务句柄：服务器立刻返回 task id，之后客户端用同一 id 查询状态，断线重连也能恢复。Elicitation 的核心是暂停—恢复语义：服务器抛出需要输入的请求，带上表单或链接，用户响应后从中断点继续，而不是重启整个流程。三者都写进开放规范，意味着任何兼容 MCP 的客户端都能实现，不绑定某一家产品。注意边界：Skills 内容是服务器提供者写的指令，会随服务器更新悄悄改变，因此需要像审查依赖一样审查服务器来源。

**▌ 动手验证**
① 确认你用的 Claude 或 Claude Code 版本已开启 Skills over MCP（Pro、Max、Ultra 默认开启，Team 需管理员开启）；② 在 Claude Code 的斜杠菜单里查看 server:skill 形式的技能列表，确认服务器技能已注册；③ 找一个提供技能的测试服务器，先只读地让它列出技能说明，检查指令是否可信；④ 让智能体执行一个需要多步工作流的任务，观察它是否在恰当时机加载技能；⑤ 用 Tasks 提交一个耗时操作，确认拿到 task id 后智能体能继续响应其他问题；⑥ 触发一个需要 Elicitation 的操作（如删除测试资源），确认流程会停下来等你确认。预期结果：技能按需出现而非一开始就塞满上下文，长任务不阻塞对话，危险动作前有明确确认步骤。

**▌ 对比与选型**

| 能力 | 更新前 | 更新后 | 注意 |
|------|-------|-------|------|
| 工具描述 | 只说什么 | 附说明书 | 说明书需审查 |
| 长调用 | 阻塞等待 | 后台 task id | 需轮询 |
| 危险操作 | 提示词叮嘱 | 协议级暂停 | 兼容客户端 |

选型建议：工具作者应优先把重复出现的工作流做成技能随服务器发布；使用者要评估服务器可信度，尤其是技能会随更新变化这一点。适用场景：多 MCP 服务器并存导致上下文吃紧的团队、需要长时间后台任务的工作流、对付费或破坏性操作有审批要求的组织。File Uploads 尚未定档，不建议纳入生产依赖。

### 5. 【GitHub Actions workflow lockfiles 上手：给浮动版本标签上锁，让 CI 供应链可复现】

> 📍 **导语**：如果你在 workflow 里写过 uses: actions/checkout@v7，就埋着一个隐患：@v7 是一个可以被移动的版本标签，掌控该仓库的人或攻破它的人能把标签指向任意代码，而你的 CI 会带着 secrets 运行它。2026 年 10 月 GitHub Actions workflow lockfiles 正式可用，11 月的多份实践指南都在强调它：通过 gh actions-lock 生成 .github/workflows/actions.lock，把可读的标签引用锁定到具体提交。这是继最小权限、pin 到 SHA 之后，CI 供应链安全的又一块拼图，而且它把可复现性变成了可提交、可审查的文件，让安全与可读性不再二选一。

**▌ 它是什么？**
workflow lockfile 是一个记录"workflow 里每个 action 实际对应到哪个 commit SHA"的文件，默认路径是 .github/workflows/actions.lock。它的工作方式类似包管理器的锁文件：YAML 里你继续写易读的 @v7，锁文件里记下该标签解析出的完整 40 位 SHA；CI 运行时按锁文件解析，确保今天跑的和上周审过的代码是同一份。GitHub 提供 CLI 扩展 gh actions-lock 来生成与更新它，Dependabot 也能在升级 action 时同步改锁文件条目。它不是新的权限机制，而是把"pin 到 SHA"这条最佳实践从手工注释变成工具化、可审查的流程，让供应链安全不再依赖开发者的自觉。

**▌ 它解决了什么问题？**
第一是可读性与安全性的矛盾：pin 到 SHA 最安全，但满屏 40 位哈希难以审阅；保留 @v7 易读，却把信任交给了标签持有者。锁文件让两者兼得——人读标签，机器按 SHA。第二是不可复现：同一个 workflow 今天绿、下周红，往往是因为某个 action 的标签被移动；锁文件把这个变量固定下来。第三是审查与合规：安全团队可以审一份锁文件的 diff，清楚看到"这次升级把 checkout 从 SHA A 换到 SHA B"，而不是在 YAML 里翻注释。第四是与 Dependabot 协同：自动化升级提案会同时更新标签与锁文件，升级不再破坏 pin，省去手工改哈希的麻烦。

**▌ 核心原理拆解**
整个机制是解析、记录、锁定、更新四步。解析阶段，gh actions-lock 扫描 .github/workflows/ 下的 YAML，收集所有 uses 引用（包括复合 action 内部引用的子 action）。记录阶段，把每个引用解析为规范仓库与完整 SHA，写入 actions.lock，并保留版本号作为注释。锁定阶段，运行时先读锁文件，把标签映射为 SHA 再拉取执行，因此标签移动不会影响实际执行的代码。更新阶段，Dependabot 或 Renovate 升级 action 时同时改 YAML 标签与锁文件条目，保持两者一致。关键设计是标签作为人读接口、SHA 作为机器执行依据的分离；它和 OIDC 短时凭据、最小权限是互补关系——锁文件管代码来源，权限与 OIDC 管运行时能力，两者叠加才完整。

**▌ 动手验证**
① 安装 GitHub CLI 扩展：gh extension install 对应仓库（按官方文档），得到 gh actions-lock 命令；② 在项目根目录运行 gh actions-lock generate，检查生成的 .github/workflows/actions.lock，确认每个 uses 都有对应 SHA；③ 把锁文件提交进仓库，并在 CI 里加一步校验，确保 workflow 变更时锁文件同步更新；④ 配置 Dependabot 的 github-actions 生态为每周检查，让升级提案自动带上锁文件改动；⑤ 模拟一次标签被指向新提交的场景，确认 CI 仍按锁文件中的 SHA 执行。预期结果：workflow 执行不再受上游标签移动影响，审查时能直接 diff 锁文件看到 action 变更。注意：锁文件不保证 action 本身安全，第三方 action 仍需人工审阅代码。

**▌ 对比与选型**

| 策略 | 可读性 | 供应链安全 | 维护成本 |
|------|-------|-----------|---------|
| 直接用 @tag | 高 | 低 | 低 |
| 手工 pin SHA | 低 | 高 | 高 |
| lockfile | 高 | 高 | 中 |

选型建议：个人项目可用 @tag 换省事；涉及生产部署、处理 secrets 或合规要求的仓库，应采用 lockfile 并配 Dependabot；极端场景可在 lockfile 之外再人工复核关键 action。适用场景：多仓库的团队 CI、需要审计 action 变更的组织、希望今天绿下周也绿的可复现构建。注意私有仓库的 Actions 分钟额度与 runner 倍率（Linux 1 倍、macOS 10 倍），锁文件管不了成本问题。

### 6. 【antialgorithm 拆解：一条专治AI第一反应最平庸的技能，怎么让模型跳出首个答案】

> 📍 **导语**：让模型起名、想点子、做 Logo，它给出的第一版往往最安全、最平均、也最没记忆点——这是因为解码过程天然偏向高概率的平庸选项。2026-11-25 开源热榜上，mankidev/antialgorithm 以 834 Star 进入前列，标签是 agent-skills、claude-code、claude-code-plugin。它是一条 Agent 技能，专门在创意工作里引导模型跳过第一个、最平均的选择，去挖更有辨识度的方案。它不靠换模型，也不靠玄学提示词，而是把反向算法式的思考步骤写成智能体可执行的流程。对苦于 AI 方案千篇一律的创作者，这是一个值得试试的思路。

**▌ 它是什么？**
antialgorithm 是一个可安装的 Agent Skill，本质是一份 SKILL.md 加少量脚本，供 Claude Code 等编码智能体按需加载。它面向的是创意类任务：命名、点子发散、Logo 与海报构思、界面设计。它的核心主张是：模型的第一反应通常是训练语料里最常见、概率最高的那个答案，而创意恰恰要求远离分布中心。因此技能会引导智能体先识别最平庸的答案长什么样，再主动绕开它，沿着不那么显然的方向生成候选，最后再收敛到可用方案。它不是图像生成器，也不替代设计工具，而是插在你提需求与模型给方案之间的一层思维约束，让创意过程多一道刻意的反向步骤。

**▌ 它解决了什么问题？**
创意任务里的 AI 输出有两个典型毛病。一是同质化：不同人用同一工具、同一提示，拿到的是近乎相同的方案，因为都落在概率分布的同一处峰值。二是过早收敛：模型给出一个看似合理的答案后就停止探索，用户只能在这个基础上小修小补。传统应对方式是反复调提示词、换模型、加大温度，但成本高且不稳定。antialgorithm 把反平庸做成可复用的流程：每次创意任务都按同一套步骤先拆解平庸模式、再强制发散、最后筛选。对独立开发者和小团队，这意味着不再依赖某个人会写创意提示词，任何人调用技能都能得到有差异度的候选，创意产出变得更可复制。

**▌ 核心原理拆解**
流程大致四段。① 触发与识别：技能被加载后，先让模型描述对这个需求最常规、最不出错的答案是什么，把平庸基线显性化。② 反向约束：明确要求后续候选不得与基线同构，从命名方式、隐喻角度、目标受众等维度强行换轨。③ 发散采样：产生一批候选，允许它们不那么稳妥，甚至故意保留一点点怪异；这一步靠的是改变思考路径而非单纯调高温度。④ 收敛筛选：按辨识度、可用性、契合度三个维度给候选打分，留下少数几个既特别又能用的方案。关键设计是先定义要避开什么，再生成，比"请更有创意"这种模糊指令可执行得多。技能随仓库更新，团队可以把自己行业的平庸套路清单补进去，让反向约束越来越精准。

**▌ 动手验证**
① 在 Claude Code 里通过插件市场安装该技能，确认斜杠菜单能看到它；② 给一个具体任务，比如"给一款记账 App 起名，要年轻、好记"；③ 先不加载技能问一次，记录模型给的第一版名字；④ 再加载技能问同样问题，观察它是否先列出了记账、钱包、小账本这类平庸方向并主动绕开；⑤ 比较两轮候选的差异度与可用性；⑥ 把技能产生的候选直接拿去做一轮小范围用户投票，验证辨识度是否真的提升。预期结果：第二轮出现明显不同于第一版的命名方向，且至少有 2 到 3 个既特别又能用的候选。注意：它提升的是差异度而非绝对质量，最后仍需人工判断方案是否真正合适。

**▌ 对比与选型**

| 方式 | 直接生成 | 调高温度 | antialgorithm |
|------|---------|---------|--------------|
| 差异度 | 低 | 中且随机 | 中高且可控 |
| 可复用 | 无关 | 低 | 高 |
| 适合 | 快速出稿 | 临时发散 | 创意工作流 |

选型建议：只要一个能用的方案，直接生成最快；想快速感受随机性，调温度够用；需要稳定产出不撞脸的创意候选，并把流程沉淀给团队，用技能更合适。适用场景：品牌命名、营销点子、UI 与海报构思、任何容易落入套路的内容创作。它不适合严肃的事实性问答或需要严格规范的场景，在那里平庸反而是正确选择。
