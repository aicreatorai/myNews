### 1. 【六大编码Agent选型：Claude Code到OpenCode怎么挑】

> 📍 **导语**：2026年11月，编码Agent已从"补全下一行"进化为能读整个仓库、跨文件改代码、自己跑命令的自主执行体。真正让人纠结的不再是"要不要用"，而是"用哪一个"。Stride AI Academy 在11月22日把 Claude Code、Codex、Cursor Agent、Copilot agent mode、Gemini CLI 与 OpenCode 六款主流工具按官方文档逐项对齐，AI Digest 又在11月20日补充了各自的最新版本动作。这一条不堆参数，而是从"你在什么环境、愿意付多少钱、要交给它什么任务"三个问题出发，给一张能直接照着挑的选型图。

**▌ 它是什么？**

编码Agent是一类能读取项目、跨文件编辑、调用终端命令直到任务完成的程序，与只给单行建议的补全插件有本质区别。截至2026年11月，六款代表工具分别是：Anthropic 的 Claude Code，跑在终端、VS Code、JetBrains、桌面端与网页；OpenAI 的 Codex，覆盖 ChatGPT 网页与桌面、CLI、IDE 扩展和云端；Anysphere 的 Cursor Agent，内置于 Cursor 编辑器，也能以 agent CLI 形式在终端运行；GitHub 的 Copilot agent mode，驻扎 VS Code、CLI 与云端；Google 的 Gemini CLI，纯终端运行；以及开源 MIT 协议的 OpenCode，支持终端、桌面、手机三端。它们共同的目标是把"描述需求"直接变成"提交可用的改动"。

**▌ 它解决了什么问题？**

传统 AI 编程助手最大的尴尬是"只说不做"——它告诉你第42行该怎么写，却不会真的去改那十个相关文件。编码Agent把这段距离补齐：你给它一个目标，它自己规划步骤、找到相关代码、动手修改、运行测试，直到验收通过。但六者的侧重并不相同。Claude Code 与 Codex 走"订阅制全覆盖"路线，一个订阅打通聊天与完整Agent；Cursor Agent 把Agent塞进编辑器，配 Tab 自动补全，适合离不开 IDE 的开发者；Copilot agent mode 对免费用户开放，是零成本试水的入口；Gemini CLI 绑定 Code Assist 许可，面向已采购 Google 工作区的团队；OpenCode 则完全免费、无需账号，并声称接通200多家模型供应商，是隐私与成本敏感场景的备选。选型的核心矛盾，就是"模型能力上限"与"付费方式、部署环境"之间的取舍。

**▌ 核心原理拆解**

六款工具的差距主要落在三个维度。第一是模型供给：Claude Code 只用 Claude 系列，按 API 计费时 Opus 5.5 每百万 token 输入4美元、输出20美元；Cursor 周池覆盖自家的 Grok 4.7、4.6、4.5 与 Composer 2.5，Claude、GPT、Gemini 需升级到 Premium 并按 API 列表价从预付额度扣费；Codex 在11月把 GPT-6.2 Sol 设为默认模型。第二是运行时形态：Claude Code 有后台会话与 Remote Control，Codex 提供 codex exec --remote 连到已有 app server，Copilot 靠 Agent Host 在窗口关闭后继续跑长会话。第三是治理：Agentic Workflows 在 Free、Team、Enterprise 上都提供只读沙箱、安全输出与威胁检测，这正是把Agent放进生产流程的前提。理解这三层，才知道"哪个更强"这个问题本身没有意义——脱离环境与预算谈能力，等于空谈。

**▌ 动手验证**

最低成本的验证路径是先装免费的那一个。OpenCode 无需账号即可试用200多家供应商里的免费模型；Copilot Free 层可直接体验 agent mode；想试 Claude Code 可在终端执行 curl -fsSL https://claude.ai/install.sh | bash，Codex 用 curl -fsSL https://chatgpt.com/codex/install.sh | sh，Cursor 用 curl https://cursor.com/install -fsS | bash。装好后别急着跑大任务，给三者同一个边界清晰的小需求，例如"给当前仓库补一个参数解析函数并写单元测试"，记录三项数据：交接成本（你写了多少提示词）、失败模式（它在哪一步跑偏）、人工收口时间（你花多久验收）。预期结果是：同一任务在不同Agent上的返工率差异，往往比宣传文案里的"能力提升百分比"更能说明问题。跑完这一轮，你就有了一把属于自己的尺子。

**▌ 对比与选型**

| 决策维度 | Claude Code / Codex | Cursor Agent | Copilot / Gemini CLI / OpenCode |
|---------|----------|----------|--------|
| 适合任务 | 跨文件重构、长会话 | 编辑器内高频迭代 | 零成本试水、隐私场景 |
| 不适合任务 | 只想单点补全 | 无 IDE 的纯终端 | 追求最强模型上限 |
| 学习成本 | 中 | 低 | 低到中 |
| 价格 | Pro 20美元/月起 | Plus 8美元/月起 | 免费或需许可 |

适用建议：已在 ChatGPT 或 Claude 订阅生态里的人，直接用对应的 Codex 或 Claude Code 边际成本最低；深度依赖 IDE、追求 Tab 补全体验的选 Cursor Agent；团队已有 GitHub 工作区的先用 Copilot Free 验证流程，再决定是否升级；对数据出内网敏感的个人开发者，OpenCode 配本地模型是现实选项。

### 2. 【Prompt不返工四招：给参照物、拆任务、划禁区、定验收】

> 📍 **导语**：很多人学了一堆"大师级提示词模板"，真到用的时候还是返工，原因往往不是模板不够华丽，而是没把四件最基本的事交代清楚。LuoLuo Wiki 在11月整理的工作提示词指南，与71muke在11月23日发布的 CREAT 框架指南，不约而同指向同一个结论：把上下文、任务边界、验收标准说清楚，比背一百个模板都管用。这一条把两套来源共通的部分提炼成四招，招招能直接套进你明天要发的那条指令里。

**▌ 它是什么？**

"不返工四招"是一套给 AI 下指令的通用写法，由四个动作组成：给上下文和参照物、一次只交代一件事、说清不要做什么、给出验收标准。它不是某个模型的专属咒语，而是跨 Claude、GPT、Gemini 都稳定生效的结构化表达习惯。CREAT 框架把它进一步固化成五个要素——Context 背景、Role 角色、Expected Output 预期输出、Accuracy 准确度、Task 任务——本质仍是"把隐含在脑子里的前提，翻译成模型能读到的显式约束"。学会这四招，等于把每次碰运气的对话，变成可复制的工程动作。

**▌ 它解决了什么问题？**

AI 返工有两个高发场景。第一种是"形容词轰炸"：你对着对话框刷一屏"大气、自然、有网感"，结果出来的东西完全不是想要的——因为人类很难纯靠文字讲清抽象风格，AI 更不会读心。给参照物这招就是解药：写代码时指明具体文件路径与已有组件，例如"照着 src/components/Card.tsx 里的间距和圆角来写"；写文案时贴一两段你满意的旧稿，明说"学它的句子长短和语气，不要学它的鸡汤结尾"。第二种是"八百字大礼包需求"：一口气让 AI 重构导航、加暗黑模式、换登录接口、改版权年份，结果改到后半段时前半段细节已被挤出注意力，越聊上下文越乱，页面一崩你根本查不清是哪一件事搞炸的。拆任务这一招要求先对齐方案再动手，小步提交、一步一验。

**▌ 核心原理拆解**

四招背后是一个共同的工程原理：模型的注意力是有限资源，未被显式约束的地方就是它自由发挥的空间。第一招用参照物替代抽象形容词，本质是把"风格"这个高维概念压缩成可直接模仿的低维样本，降低歧义。第二招"一次一件事"针对的是上下文衰减——多任务并行时，早期指令的权重会被后续内容稀释，且出问题后难以定位责任，拆解后每一步都能独立回滚。第三招"划禁区"是在提示词里前置负面约束，例如"只改 PricingCard.tsx 及其样式文件，不要动数据库表结构，不要改已有 API 字段名，不要自动执行 git commit"，把"热心的顺手优化"挡在门外；涉及高危命令时还应配合工具层面的权限规则兜底。第四招"定验收标准"要求先说清怎样算完成，例如"跑通 npm test 且无新增告警"，让模型有明确终点。参数层面，写代码、数据提取、分类、事实核查这类严谨任务，把 Temperature 设在0.1到0.3能明显减少自由发挥。

**▌ 动手验证**

以"整理一份会议纪要"为例走一遍。Step 1：打开你常用的 AI 工具，新建一个对话，不要直接丢逐字稿。Step 2：输入一段带变量的固定模板——"# Role 你是一位互联网大厂项目经理。# Task 把下方逐字稿整理成结构化纪要。# Input Data {{会议逐字稿}}。# Output Format：1. 核心结论，用三句话总结共识；2. 待办事项，用表格列出任务描述、负责人、截止时间；3. 讨论细节，按议题分类"。Step 3：把真实逐字稿填进变量，观察输出是否严格按三段结构展开；若它自作主张加了解释段落，就在下一轮补一句"不要输出模板外的任何内容"。Step 4：迭代时只改一处约束，例如把"三句话"改成"一句话"，验证它是否精确响应。Step 5：把这份调好的模板存进 Notion 或 Obsidian，下次开完会直接套用。预期结果是30秒内产出一份分工明确的专业纪要，且格式稳定可复用。

**▌ 对比与选型**

| 场景 | 四招通用写法 | 单一大师模板 | 不写提示词 |
|------|------------|------------|----------|
| 跨模型迁移 | 稳定通用 | 常需重写 | 看运气 |
| 结果可预期 | 高 | 中 | 低 |
| 上手成本 | 需练几次 | 复制即用 | 零 |
| 适合任务 | 反复型工作 | 一次性任务 | 简单问答 |

建议把每周重复频率最高的前三件事——周报汇总、客户邮件回复、会议纪要——先沉淀成"填空题模板"，再逐步加入负面约束与验收标准。需要长期生效的背景，写进项目的 CLAUDE.md 或 AGENTS.md，避免每次手动重贴。

### 3. 【Copilot浏览器实操：/plugin装browser use驱动Chrome】

> 📍 **导语**：让 AI 帮你操作网页，过去要么靠脆弱的 DOM 选择器脚本，要么靠截图猜按钮位置。GitHub 在2026年11月17日把 Copilot browser use 推到公开预览，让 Copilot 直接驱动你已经登录的 Chrome；AI Digest 在11月20日把这条更新收进当日摘要，Stride AI Academy 又在11月22日的六款Agent对比里确认了它的入口位置。这意味着填表、查页面状态、跑前端冒烟测试这类"必须真浏览器才能干"的活，第一次有了开箱即用的Agent路径。这一条讲清它怎么装、能干什么、边界在哪。

**▌ 它是什么？**

Copilot browser use 是 GitHub Copilot 的一项公开预览能力，允许 Copilot Agent 通过插件驱动用户本机已签入的 Chrome 浏览器，完成点击、填表、读取页面内容等操作。它的入口有四个：Copilot CLI（在命令行执行 /plugin 后选择 browser use）、Copilot 桌面应用、VS Code 以及 JetBrains 系列 IDE。与"无头浏览器加自动化脚本"不同，它复用你真实的登录态和 Cookie，因此那些需要账号才能看到的内部系统、需要验证码或二次校验的页面，理论上都能直接接管。它属于 Copilot 更广义的 agent mode 的一部分——后者已在 VS Code、CLI 与云端铺开，免费层即可体验。

**▌ 它解决了什么问题？**

第一，解决"登录态难题"。传统网页自动化最大的坑是认证：脚本能打开页面，却进不去需要登录的后台。Copilot browser use 直接借你已签入的 Chrome，绕开了这一步。第二，解决"多入口割裂"。过去 CLI 里写的自动化和 IDE 里的调试是两套东西，现在同一插件在 CLI、桌面应用、VS Code、JetBrains 四处通用，上下文不再断裂。第三，解决"Agent 只会改代码不会验页面"。Copilot Agent Merge 已经能修复 PR 上失败的检查和合并冲突，而 browser use 补上了"打开真实页面看效果"这一环。对前端开发者来说，改完样式让Agent自己打开预览、确认按钮没被遮挡，比人工切窗口省事得多，也更不容易漏掉只在真实交互下才暴露的问题。

**▌ 核心原理拆解**

它的工作机制可以拆成三层。最上层是插件协议：Copilot CLI 通过 /plugin 挂载 browser use 插件，插件向 IDE 与桌面端暴露统一的"浏览器操作"工具接口，因此四个入口调用的是同一套能力。中间层是会话与权限：Agentic Workflows 在 Free、Team、Enterprise 计划上都提供只读沙箱、安全输出与威胁检测，browser use 在此框架内运行，写操作会受限。最底层是浏览器控制：Agent 读取页面可访问性树而非纯截图，据此定位按钮与输入框，再复用已有的用户配置文件发起交互。理解了这三层就知道，它的可靠性上限取决于页面结构是否语义清晰——一个满是 div 假按钮的页面，再强的Agent也会看走眼。这也正是后面要讲的 stitch-skills 想根治的问题，两者恰好构成"验"与"写"的两端。

**▌ 动手验证**

Step 1：确认本机已安装 GitHub Copilot CLI 与 Copilot 订阅，在终端进入交互环境。Step 2：输入 /plugin，在插件列表中选择 browser use 并启用；预期提示为插件已挂载。Step 3：确保 Chrome 已登录你要操作的站点，例如在测试环境后台保持会话。Step 4：给一条边界清晰的任务，例如"打开 localhost:3000 的登录页，用测试账号登录，检查仪表盘首屏是否有控制台报错，并把报错原文贴回来"。Step 5：观察Agent的每一步操作，重点看它能否正确定位输入框、是否会误点广告位；发现跑偏就用自然语言立刻叫停并补充约束，例如"只操作表单区域，不要点击任何横幅"。Step 6：任务结束后检查它是否如实回报"无报错"而非编造结果。预期结果是你在终端里拿到一份页面级验证报告，而全程没有手动打开浏览器。

**▌ 对比与选型**

| 维度 | Copilot browser use | 无头脚本 Playwright | 人工点验 |
|------|------------|------------|--------|
| 登录态 | 复用已登录 Chrome | 需自管 Cookie | 天然具备 |
| 可复现性 | 中 | 高 | 低 |
| 上手成本 | 低 | 高 | 低 |
| 适合任务 | 内部系统抽查 | 回归测试 | 一次性验收 |

适用建议：需要快速验证"登录后才能看到的页面"时优先 browser use；要把验证固化进 CI、要求每次结果完全一致时用 Playwright；纯视觉审美判断仍交给人工。注意它是公开预览，能力边界可能随版本调整，关键流程别只依赖单一路径。

### 4. 【Google开源stitch-skills：SKILL.md治过时前端码】

> 📍 **导语**：让 AI 写个网页弹窗，它却还在用十年前的 jQuery 事件绑定，甚至自己硬刻一堆会挡住屏幕阅读器的 div 假按钮——这是几乎每个用过编码Agent的前端开发者都经历过的无奈。2026年11月，Google Labs 与 Chrome 团队先后在 GitHub 开源了 google-labs-code/stitch-skills 与 GoogleChrome/modern-web-guidance，把"设计稿转组件"和"跨浏览器现代网页规范"打包成可动态加载的技能库。AI 邮报在11月做了专门报道，AI Digest 同月也记录了 deferred tool loading 成为三家厂商共同方向的趋势。这一条讲的是一套可能改变"提示词写法"的开放标准。

**▌ 它是什么？**

stitch-skills 与 modern-web-guidance 是两套遵循 SKILL.md 开放标准的技能库。SKILL.md 又称 Agent Skills，是一种模块化的"专业说明书"格式：把某个领域的规范、示例和约束写成结构化文档，让不同厂商的编码Agent都能直接读取并按需动态加载。stitch-skills 偏设计侧，负责把 Stitch 设计稿转换成符合规范的组件；modern-web-guidance 偏规范侧，把最新的 Web API 与跨浏览器兼容要求注入Agent。两者都通过 Stitch MCP 与Agent连接，官方明确支持 Claude Code、Cursor、Gemini CLI 以及 Antigravity，用一行指令即可把能力灌进现有工作流。

**▌ 它解决了什么问题？**

根因是大型语言模型训练数据的时间落差。模型学到的前端写法往往落后于浏览器现状若干年，于是生成的代码里充斥已被淘汰的 CSS Hack 和臃肿的 JavaScript 依赖；更隐蔽的问题是语义缺失——Agent 为了让界面"看起来像按钮"，会用 div 加事件监听伪造交互控件，结果屏幕阅读器读不出来，无障碍直接崩掉。过去开发者只能在提示词里反复叮嘱"用现代写法、注意可访问性"，但这类叮嘱每次都要重写、且很容易被长上下文稀释。把规范写成 SKILL.md 技能库后，约束从"每次口头交代"变成"一次安装、全局生效"，且由官方团队维护更新，个人不必追着浏览器版本跑，团队协作时也能保证所有人拿到同一套标准。

**▌ 核心原理拆解**

这套方案的关键在"按需加载"四个字。第一层是标准统一：SKILL.md 定义了一种与厂商无关的描述格式，同一份技能文件能被 Claude Code、Cursor、Gemini CLI 等不同宿主解析，避免了过去"一个工具一套插件"的重复劳动。第二层是 MCP 桥接：Agent 通过 Stitch MCP 服务器获取技能内容，设计系统与 Web 规范作为外部上下文注入，而不是塞进模型权重——这既解决了时效问题，也让规范可审计、可回滚。第三层是延迟加载（deferred tool loading）：AI Digest 在11月20日记录到 Gemini API 已预览 tool retrieval、Pydantic AI 加入 ToolBridge，三家厂商都在把工具与 MCP 的 schema 推迟到真正需要时才载入。这背后的权衡很清晰：全量塞入会吃掉宝贵的上下文窗口，按需检索则用一次额外查找换取更低的 token 成本与更高的相关度。理解了这层，就能明白 SKILL.md 不只是"一份更长的提示词"，而是一种把知识外置、按用即取的架构。

**▌ 动手验证**

Step 1：在终端克隆 google-labs-code/stitch-skills 与 GoogleChrome/modern-web-guidance 两个仓库到你的项目目录。Step 2：按各自 README 把技能文件放进Agent能识别的 skills 目录，或按官方说明通过 MCP 配置接入 Stitch 服务。Step 3：在 Claude Code 或 Gemini CLI 中输入一条明确任务，例如"按 modern-web-guidance 规范，把这张设计稿转成弹窗组件，使用原生 dialog 元素并确保键盘可聚焦"。Step 4：对比安装技能前后的输出，重点看三处：是否还在手写事件绑定、是否用语义化标签、样式是否依赖过时 Hack。Step 5：若Agent未自动加载技能，用 /skills 或对应命令确认技能已启用，并在提示中显式点名技能名。预期结果是同一模型在装上技能后，生成的页面在语义化与无障碍上出现可观测的改善，而不是靠你逐条纠正。

**▌ 对比与选型**

| 维度 | SKILL.md 技能库 | 手写长提示词 | 微调模型 |
|------|------------|------------|--------|
| 更新成本 | 官方维护即取即用 | 每次重写 | 高 |
| 跨工具复用 | 强 | 弱 | 中 |
| 适合任务 | 规范密集的前端 | 一次性需求 | 稳定垂直域 |
| 上手成本 | 中 | 低 | 高 |

适用建议：前端团队应把 design system 与可访问性规范沉淀为 SKILL.md，一次投入长期复用；个人开发者遇到"AI 又写出过时代码"时，先查有没有对应官方技能库，再考虑手写长提示。需要注意技能库依赖宿主支持按需加载，老版本Agent可能无法自动触发。

### 5. 【阿里开源Open Code Review：CLI本地代码审查上手】

> 📍 **导语**：当Agent写的提交量暴涨，代码审查就成了新瓶颈。AI Digest 在11月20日的摘要里提到一组数字：Anthropic 的合并量从2026年5月每天约2500次涨到9月每天超过30000次，每天产生约2500万次 CI 检出；同一天，摘要还记录了一个免费的本地替代方案——阿里的 Open Code Review，Apache-2.0 协议，既能当 CLI 用，也能当技能装。IndiaNIC 在11月21日的开源简报里把这类"把安全与审查能力塞进本地 IDE"的工具列为当周重点。这一条讲的是怎么把开源审查工具接进自己的仓库，而不是把代码传到别人的云上。

**▌ 它是什么？**

Open Code Review 是阿里巴巴开源的本地代码审查工具，采用宽松的 Apache-2.0 协议。它有两种使用形态：一是命令行工具，通过 npm install -g @alibaba-group/open-code-review 全局安装后，在仓库里执行 ocr review 即可对当前改动发起审查；二是技能包，通过 npx skills add alibaba/open-code-review 装进支持 Agent Skills 的编码Agent，让审查能力成为工作流的一环。它的定位是"免费、本地、可自托管"的审查层，与商业扫描器形成互补：后者往往把代码送到云端分析，前者把审查留在开发者的机器上，对数据出境有顾虑的团队尤其合适。

**▌ 它解决了什么问题？**

第一，解决"审查吞吐跟不上提交量"。当大部分提交来自Agent，人工逐行看 Diff 变得不现实；Open Code Review 让你在合并前先跑一轮机器审查，把明显问题拦下来。第二，解决"代码出内网的合规顾虑"。金融、政企等场景不允许源码上传第三方服务，本地 CLI 形态天然满足这条红线。第三，解决"商业工具太重"。IndiaNIC 同期提到的 Claude-BugHunter 把红队与漏洞情报带进本地 IDE，但这类工具往往依赖较重的扫描引擎；Open Code Review 用一条 npm 命令即可安装，对中小团队更友好。第四，解决"审查结论不一致"。把审查规则写成工具配置，比依赖每个人凭经验看代码更稳定，也便于新人快速达到团队的质量基线。

**▌ 核心原理拆解**

理解它的价值，要先看大厂是怎么做Agent代码审查的。AI Digest 记录的 Anthropic 实践是：每个 PR 都经过多Agent的AI审查——并行的 bug 猎手、投票步骤，只把被确认的发现贴出来，再叠加一次安全扫描，未关闭的发现会阻塞合并；人工审批按风险分级，低风险零审批、普通改动一人、最危险路径两人，且Agent的批准永远不能替代人类；审查轮次上限设为三轮以保证收敛。Open Code Review 把类似的"机器先筛、人做终审"思路做成开源工具：CLI 读取 git diff，按规则集检查常见问题，输出结构化发现；技能形态则进一步让编码Agent在写代码时就调用它自查。要点在于，机器审查的目标不是取代人，而是把人的注意力集中到真正高风险的那部分改动上，让有限的人工审阅时间产生最大价值。

**▌ 动手验证**

Step 1：在终端执行 npm install -g @alibaba-group/open-code-review 完成全局安装，用 ocr --version 确认可用。Step 2：进入一个已有 git 仓库，故意做一处可疑改动，例如把一个空值判断删掉，并 git add 暂存。Step 3：执行 ocr review，让它审查当前暂存区的改动；预期输出是一份包含问题定位与说明的发现列表。Step 4：若你的Agent支持技能，执行 npx skills add alibaba/open-code-review 把它装进项目，然后让Agent在提交前自查，观察它是否主动调用审查工具。Step 5：核对它报出的发现是否真实，记录误报数量；把误报多的规则按比例调整或关闭。Step 6：确认它不会自动执行 git commit 或修改超出范围的文件——这正是"划禁区"原则在工具层的体现。预期结果是你在合并前多了一道可重复的机器关卡，而人工审查时间明显下降。

**▌ 对比与选型**

| 维度 | Open Code Review | 商业云扫描 | 纯人工 Review |
|------|------------|------------|-------------|
| 代码是否出本机 | 否 | 是 | 否 |
| 部署成本 | 一条 npm 命令 | 账号加配置 | 零 |
| 适合任务 | 提交前自查 | 全仓合规 | 高风险终审 |
| 规则可定制 | 中 | 高 | 依赖个人 |

适用建议：把 Open Code Review 放在开发机的提交前环节，作为第一道机器关卡；涉及密钥泄露、许可证合规等需要全局规则的场景，仍应配合商业工具；最终合并决定永远留给人。

### 6. 【Gemini CLI 0.69上手：/stats热力图加/model切模型】

> 📍 **导语**：Gemini CLI 在11月迎来了0.69.0版本，AI Digest 在11月20日的摘要里记下了两个最实用的变化：/stats 命令加入热力图，让你一眼看出 token 都用在了哪；/model 命令可以切换所用模型。同一份摘要也留下一个悬而未决的问题——Gemini CLI 当时仍不支持 Gemini 4 模型。Stride AI Academy 在11月22日的六款Agent对比里则确认了它的定位：纯终端运行、主要面向已采购 Code Assist 标准版或企业版的团队。这一条不谈参数跑分，只讲怎么把这两条命令用进日常，把上下文和成本看清楚。

**▌ 它是什么？**

Gemini CLI 是 Google 推出的终端编码Agent，属于六款主流编码Agent中唯一"纯终端、无编辑器依赖"的一档。v0.69.0 提供两项新能力：/stats 以热力图形式展示用量分布，/model 用于在会话内切换可用模型。它背后依托 Gemini 系列模型，官方定位是配合 Code Assist 标准版或企业版许可使用；对没有该许可的个人用户，Stride AI Academy 的对比表提示需要改走 Antigravity CLI 等替代路径。除了编码，Gemini 家族近期还扩展了工具调用能力：Gemini API 在11月预览了 tool retrieval，把工具与 MCP 服务器的 schema 推迟到真正需要时才加载，与延迟加载的大方向一致。

**▌ 它解决了什么问题？**

第一，解决"token 花在哪不知道"。长会话跑下来，开发者常有一种模糊的浪费感——明明没做多少事，上下文却快满了。/stats 热力图把消耗按时间或会话段可视化，让"感觉"变成"数据"。第二，解决"模型选错导致效果差"。不同任务适配不同模型，过去切换往往要重启会话或改配置，/model 把它变成会话内的一个动作。第三，解决"工具描述吃掉上下文"。Gemini API 的 tool retrieval 与三家厂商共同推进的延迟加载思路一致：与其把所有工具的 schema 一次性塞进提示词，不如先只给索引，需要时再取详情，这对动辄挂几十个 MCP 工具的Agent尤其关键。第四，解决"实时信息准确性"。Gemini 擅长带实时性的查询，配合"注明日期、要求引用核验"的用法，能明显降低过时答案的比例。

**▌ 核心原理拆解**

要把 /stats 与 /model 用好，得先理解上下文工程的账本。上下文是模型下一步回答所依赖的材料，包括对话历史与工具调用结果；会话越长，占用越高，输出质量越容易下滑。/stats 热力图的本质是把这份账本按维度摊开，让你看到哪个阶段消耗异常——例如一段反复失败的调试往往吃掉最多 token，这时该做的不是继续硬聊，而是开新会话并把已确认的结论写进项目文件。/model 的原理则是会话级模型热切换：同一份上下文在不同模型下推理，适合用便宜模型做机械性任务、用强模型做架构决策。再往外一层，tool retrieval 与延迟加载改变的是"工具描述何时进入上下文"——按需加载用一次检索换取更低的固定开销，本质与 SKILL.md 技能库一脉相承。把这三件事连起来看，11月的工具演进方向就清楚了：让上下文每一格都花在刀刃上。

**▌ 动手验证**

Step 1：在终端安装 Gemini CLI 并用有权限的账号登录，确认版本为 v0.69.0 或更高。Step 2：开启一段真实任务，例如"阅读当前项目 README 并列出三个可改进点"，让它产生足够的工具调用与对话轮次。Step 3：输入 /stats，观察热力图输出的用量分布，记录峰值出现在哪个阶段；预期能看到一段明显偏高的消耗带。Step 4：输入 /model 查看可用模型列表，切换到另一个模型后问同一个问题，对比答案质量与耗时。Step 5：结合 Gemini 擅实时信息的用法做一次对照：在提示中注明具体日期、用自然对话语气、把复杂任务拆成子任务、要求对关键事实给出引用，观察答案是否更可靠。Step 6：对热力图暴露的高消耗段，尝试清理无关上下文或开新会话重问，再查一次 /stats 验证是否下降。预期结果是你第一次拥有了"用量—质量"的对应关系，而不是凭感觉调参。

**▌ 对比与选型**

| 维度 | Gemini CLI | Claude Code / Codex | Cursor Agent |
|------|------------|----------|----------|
| 运行形态 | 纯终端 | 多端覆盖 | 编辑器内置 |
| 实时信息 | 强 | 中 | 中 |
| 许可要求 | Code Assist 许可 | 订阅制 | 订阅制 |
| 适合任务 | 带时效性查询 | 长会话重构 | 编辑器内迭代 |

适用建议：已采购 Google 工作区许可、又常做实时信息查询的团队，Gemini CLI 的边际成本最低；若你的任务以长会话重构为主，Claude Code 或 Codex 的多端与后台会话更顺手；个人用户若没有 Code Assist 许可，按对比表提示改走 Antigravity CLI。另需注意"Gemini CLI 是否支持 Gemini 4"在11月20日的摘要里仍是开放问题，升级前先看官方发布说明。
