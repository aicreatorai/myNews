### 1. 【cloudflare/security-audit-skill：多阶段安全审计技能】（⭐ 约 69K）

> 📍 **导语**（80-100字）：Cloudflare 在 2026-11 周榜以约 1.07 万新增 Star 冲上前列，把"多阶段安全审计"打包成可被编码智能体动态加载的技能。过去安全审查要么靠人工逐行看、要么靠静态扫描器报一堆误报；这个技能让 Agent 像资深安全工程师一样分阶段、可验证地审代码，输出机器可读结论，今天值得关注是因为安全能力正从外挂工具变成 Agent 内建技能。

---

**▌ 它是什么？**

cloudflare/security-audit-skill 是一个用 JavaScript 编写的编码智能体技能（Skill），它的定位不是又一个独立的扫描器，而是一套可以被 Claude Code、Codex 这类编码智能体在需要时动态加载的"安全审计工作流"。一个技能本质上是一个文件夹，里面装着指令、脚本与资源，智能体在匹配到"审计这段代码""检查这个 PR 有没有漏洞"这类意图时自动启用。Cloudflare 把它做成多阶段（multi-phase）流程：先划定范围、再逐层深入、最后给出带证据的结论，而不是一次性抛出上千条告警。它属于 Agent Skills 生态，强调"被智能体调用"而非"人去打开一个网站"。

**▌ 它解决了什么问题？**

开发者做安全自查长期陷入两头难的困境。一端是人工审查，资深安全工程师极度稀缺、成本高昂，普通开发者写完功能往往只跑一遍 lint 就提交，隐藏的注入、越权、密钥泄露等问题往往到线上才暴露。另一端是传统静态应用安全测试（SAST）工具，它们确实能扫，但报告里充斥着低置信度的告警，开发者要在噪声里淘金，久而久之干脆不再看报告。更麻烦的是，大多数工具只告诉你"这里可能有毒"，却给不出可复现的证据和修复建议。security-audit-skill 的切入点正是"可验证、机器可读"——它要求每条发现都附带独立验证过的事实，让结论可以被 CI 直接消费，而不是堆在人的收件箱里等待人工分拣，从根本上解决了"扫得出、用不上"的老问题。

**▌ 核心原理拆解**

核心原理可以拆成"分阶段推进"与"机器可读证据"两条主线，理解的关键在于它把安全专家的思考过程固化成了可重复执行的剧本。第一阶段是范围界定，技能会先读懂目标仓库或改动集，识别出真正需要处理的函数、接口与数据流入口，避免一上来就全量扫描浪费上下文窗口。第二阶段进入逐层审查，它不像传统规则引擎那样只做正则匹配，而是让智能体扮演攻击者视角，沿着"用户输入如何进入系统、在哪里被拼接进查询或命令、又被谁执行"这条链路去推理可能的利用点。第三阶段是独立验证，这是它区别于普通聊天式审计的核心：对于每一条疑似漏洞，技能会尝试用确定性的方式（例如构造最小复现、检查配置开关、读取依赖版本）确认问题确实存在，而不是凭模型直觉下结论。第四阶段产出结构化报告，发现项被写成带严重级别、位置、证据和修复建议的机器可读格式，可以直接被流水线解析、被工单系统消费。整个原理的精髓在于让审查结果不随对话随机波动，且每一次审计都能被审计、被比对，使安全审查从艺术变成工程。

**▌ 动手验证**

动手验证前，先确认你本地已装有支持技能加载的编码智能体（如 Claude Code）。最轻量的方式是直接拉取该技能仓库并放入智能体的技能目录：把 cloudflare/security-audit-skill 仓库克隆到本地后，将里面的技能文件夹链接到你的 agents 配置目录，重新打开会话即可被识别。验证是否生效的最快办法，是新建一个故意含有典型缺陷（比如字符串拼接的 SQL、未校验的用户输入透传到命令执行）的示例文件，然后在智能体里发出"审计这个文件"的指令。你会看到它先列出审查范围，再逐条指出问题位置并附上可复现证据，最后给出一份结构化清单。你可以把这次输出与人工判断对照，确认其命中率；也可以把它接入本地 CI，每次提交自动跑一遍，验证它能否稳定复现同样的结论。若想确认技能版本，可查看仓库的提交记录与发布标签，确保用到的是最新审计逻辑，从而验证整套机制确实可用而非摆设。

### 2. 【paperclip：把一群跑着的 Agent 当团队来管】（⭐ 约 112K）

> 📍 **导语**（80-100字）：paperclipai/paperclip 以约 11.2 万 Star 成为本周 Agent 生态里"管理派"的代表，它要解决的不是"怎么造一个 Agent"，而是"怎么管一群已经在跑的 Agent"。过去团队引入智能体后，任务谁派、进度谁跟、花销谁控、出问题谁批，全靠群聊和表格；paperclip 把这套管理变成自带界面的应用，今天值得关注是因为 Agent 正被当"同事"用，而同事得有人管。

---

**▌ 它是什么？**

paperclipai/paperclip 是一个开源的"智能体项目管理"应用，用 TypeScript/Node.js 编写，本周总 Star 约 11.2 万。它的定位很新：当一个公司里已经跑着一群 Agent（Claude Code、Codex、Gemini CLI、Cursor、OpenCode 等），paperclip 充当它们的"调度与治理中枢"——负责任务分配、进度追踪、花费统计与审批流。技术上它用 Node.js + React + 内嵌 PostgreSQL，自带 ACPX（Agent Communication Protocol Extended）协议并兼容标准 MCP，能连接 Slack、GitHub 审查机器人、Notion、Railway 等外部服务，是一个面向"Agent 队伍"的控制平面而非单一工具。

**▌ 它解决了什么问题？**

许多团队现在的状态是：Agent 不是没有，而是太多了，且各自为政。一个需求拆给前端 Agent、后端 Agent、测试 Agent，谁在干、干到哪了、花了多少 token、需不需要人审批，信息散落在不同聊天窗口和只读文档里，负责人每天像救火队长一样到处追问。更现实的是成本：Agent 按调用计费，没有统一视图根本不知道钱花哪了，预算超支往往事后才发现。paperclip 的切入点是"把 Agent 当员工队伍来管理"——它提供统一的任务面板，把派活、跟进、核算、审批收进一个应用，让负责人从"追着 Agent 问"变成"看一眼面板就知道全局"，把混乱的多头协作收敛成可计划、可度量的工程化管理。

**▌ 核心原理拆解**

核心原理是"统一接入 + 任务编排 + 治理视图"三层，关键在于把管理智能体从临时约定升级成工程化的控制平面。接入层通过标准 MCP 以及自研的 ACPX 协议，把不同厂商、不同形态的 Agent 都纳管进来，无论你用的是 Claude Code 还是 Codex，都能以统一身份注册到平台，屏蔽了底层差异。任务层把业务需求拆成可分配的工作项，指派给具体 Agent 或人类，并记录每个工作项的状态机（待办、进行中、待审批、完成），让协作有清晰的生命周期。治理层是它最有价值的部分：实时聚合所有 Agent 的进度、token 消耗与花费，形成可下钻的报表；审批流让敏感动作（如合并代码、调用付费接口）必须人工放行。底层用内嵌 PostgreSQL 自动建库，npx 一条命令即可本地起服务，数据留在自己机器。整个原理的精髓在于让一支 Agent 队伍像真实团队一样可被计划、可被度量、可被问责，而非一群无法追溯的散兵。

**▌ 动手验证**

动手验证非常轻量，前提是本机装好 Node.js。执行 `npx paperclipai@latest onboard --yes`，这条命令会自动拉起本地界面与 API，并完成内嵌 PostgreSQL 的初始化，无需你手动配置数据库。启动后打开本地面板，第一步验证"纳管"：把你已经在使用的一个编码智能体（例如 Claude Code 或 Codex）按文档接入，确认它出现在 Agent 列表里。第二步验证"派活与跟进"：在面板新建一个任务并指派给该 Agent，观察任务状态是否随 Agent 执行实时变化。第三步验证"治理"：查看花费与进度报表是否正常汇总，确认成本可见。整个自托管免费，适合想先在小范围试水的团队；官方也规划了云端托管选项，等需要时再迁移即可，从而完整验证其管理闭环是否真正成立。

**▌ 对比与选型**

| 对比维度 | paperclip | 群聊+表格 | 厂商自带控制台 |
|---------|--------|-------|-------|
| 多厂商纳管 | 是（ACPX+MCP） | 否 | 仅自家 |
| 花费可见 | 聚合报表 | 散落 | 部分 |
| 自托管 | 免费支持 | 无 | 多数不 |
| 适合场景 | 多 Agent 团队 | 极简试用 | 单一生态 |

选型建议：多厂商、多 Agent 的团队用 paperclip；只用单一厂商工具可先用官方控制台；临时小用表格也够。

### 3. 【Scrapling：为 Agent 内置 MCP 服务的网页抓取框架】（⭐ 约 100K）

> 📍 **导语**（80-100字）：D4Vinci/Scrapling 本周以约 8.3k 新增 Star 跻身前列，这个 Python 抓取框架的看点不是"又能爬了"，而是把 MCP 服务直接打进了包里。过去 Agent 想抓网页，要么手搓解析脚本、要么外接一堆中间件；Scrapling 这次升级让 Claude Code 等智能体一条命令就能调用它，今天值得关注是因为"Agent 怎么触达真实网络"正成为新战场，原生 MCP 化是解法之一。

---

**▌ 它是什么？**

D4Vinci/Scrapling 是一个用 Python 编写的高性能网页抓取框架，2024 年 10 月发布，定位是"从单个请求到全量爬取都能搞定"的一站式工具。它的特别之处在 2026 年 11 月的这次更新：框架内置了一个 MCP 服务器和一个 Agent Skill，让任何支持 MCP 的编码智能体无需自定义封装，就能直接调用它的抓取能力。换句话说，Scrapling 从"给人用的库"升级成了"给 Agent 用的工具"。它提供三种抓取器，覆盖从简单到最难的场景，并自带对抗反爬的指纹伪装层，是少数把"硬骨头抓取"和"原生 Agent 接口"合二为一的框架。

**▌ 它解决了什么问题？**

让 Agent 获取实时网页数据一直是个麻烦事。最简单的情况是目标网站结构规整、没有反爬，几句 requests 就能拿下；但真实世界里大量站点有 TLS 指纹检测、Cloudflare 人机校验、动态渲染，普通脚本一碰就被拦。开发者以往要自己维护一整套绕过逻辑，再写适配层把结果喂给 Agent，工程成本高且脆弱。Scrapling 的切入点是"开箱即用的硬骨头能力 + 原生 Agent 接入层"：它自带能伪造 TLS 指纹、说 HTTP/3 的隐身客户端，能驱动真实 Chromium，还宣称能过 Cloudflare 的 Turnstile 校验；更重要的是，这些能力现在通过 MCP 直接暴露给智能体，省掉了中间所有的胶水代码，让 Agent 第一次能像调用本地函数一样去抓网页。

**▌ 核心原理拆解**

核心原理分"抓取内核"和"Agent 接入层"两段。抓取内核提供三类抓取器：其一是隐身 HTTP 客户端，它通过伪造浏览器指纹、支持 HTTP/3 来绕过基于 TLS 特征的拦截；其二是基于 Playwright 驱动真实 Chromium 的渲染型抓取器，专门对付需要执行 JavaScript 才能看到内容的页面；其三是号称能清除 Cloudflare Turnstile 与中间页校验的 StealthyFetcher，针对最强反爬。内核之上是一层自研的 TLS/HTTP3 指纹伪装模块，让请求在服务器看来像来自真实浏览器而非脚本。Agent 接入层是本次更新的灵魂：框架把 MCP 服务器直接打包进库，安装 scrapling[ai] 后执行一条命令即可启动服务，智能体通过标准 MCP 协议调用"抓取某 URL"这样的工具，框架在背后自动选择最合适的抓取器。整个原理的精妙在于把"抓得动"和"叫得动"两件事合成一个包——开发者不再需要分别维护抓取引擎与 Agent 适配层，印证了 Agent 生态缺的不是抓取技术本身，而是让 Agent 能直接调用它的那一层。

**▌ 动手验证**

动手验证从安装开始，执行 `pip install "scrapling[ai]"` 拉取带 Agent 能力的版本，再跑 `scrapling install` 把浏览器依赖装好，随后用 `uvx scrapling mcp` 或官方容器镜像启动 MCP 服务。验证接入是否成功，可在支持 MCP 的编码智能体配置里把该服务登记为工具源，然后对它说"抓取这个网页并把正文摘要给我"。你会看到智能体无需任何自定义代码，直接通过 MCP 调用 Scrapling 完成请求、渲染或绕过校验、返回结构化内容，从而验证原生接入确实生效。想进一步验证抗反爬能力，可以挑一个带 Cloudflare 校验的站点做对照：普通脚本失败，而 Scrapling 的 StealthyFetcher 能拿到内容，差异一目了然。注意遵守目标站点的 robots 与法律边界，仅用于你有权访问的数据，确保验证在合规范围内进行。

**▌ 对比与选型**

| 对比维度 | Scrapling | 传统爬虫库 | 现成 MCP 抓取服务 |
|---------|--------|-------|-------|
| 抗反爬 | 强（指纹/Chromium） | 弱 | 视服务而定 |
| Agent 接入 | 原生 MCP | 需自封装 | 已封装 |
| 部署 | 本地/容器 | 本地 | 云端 |
| 适合场景 | 硬骨头+Agent | 简单采集 | 快速集成 |

选型建议：硬反爬又想接 Agent 选 Scrapling；简单采集用传统库；只想快速集成可选托管服务。

### 4. 【pingdotgg/t3code：把多个 Agent 编排成可控工作流的智能体控制面】（⭐ 约 52K）

> 📍 **导语**（80-100字）：pingdotgg/t3code 本周以约 1.54 万新增 Star 登上周榜前列，它把自己定位为"智能体的控制面"——不是又一个聊天框，而是把多个 Agent 编排成可控工作流的中枢。过去让 Agent 协作，要么靠人来回复制粘贴，要么在代码里硬编码编排逻辑；t3code 提供的是一套声明式、可观测的编排层，今天值得关注是因为当 Agent 数量变多，"怎么管、怎么看、怎么收尾"比"能不能跑"更关键。

---

**▌ 它是什么？**

pingdotgg/t3code 是一个面向智能体的控制面（control plane）项目，用 TypeScript 编写，本周总 Star 约 5.2 万、单周新增约 1.5 万。它的核心不是替你执行具体任务，而是充当多个 Agent 之间的"调度与协调中枢"：你用声明的方式描述任务流程、依赖关系与出口，t3code 负责把它们落到具体的 Agent 上运行，并把这些运行过程变成可观察、可干预的状态。它更像是 Agent 世界的"工单系统 + 编排器"，让分散的自动化能力被统一编排，而不是任由各个 Agent 各跑各的、互不通知。

**▌ 它解决了什么问题？**

当团队只用一个 Agent 时，问题还简单；可一旦并行跑起多个 Agent（前端、后端、测试、文档各一个），麻烦就来了：谁先谁后、谁等谁、失败了怎么回滚、结果往哪汇总，全都成了一团乱麻。很多人用脚本把 Agent 调用串起来，但脚本没有状态、没有可视化、出错只能看日志硬猜。t3code 的切入点正是"可控的工作流"：把多 Agent 协作从即兴发挥变成有向图，每个节点是一步动作，边是依赖与数据流向，运行时有统一面板可看进度、可暂停、可在某个节点人工介入。这让 Agent 协作第一次有了类似 CI/CD 那样的工程管理感，把"一群散兵"组织成"一支有指挥部的队伍"，极大降低了多智能体系统的运维心智负担。

**▌ 核心原理拆解**

核心原理是"声明式工作流 + 运行时编排 + 可观测状态"，关键在于把编排逻辑与执行逻辑解耦。首先是声明层，你用配置文件或代码描述一张有向图：哪些步骤、彼此的依赖关系、每个步骤由哪个 Agent 执行、产出如何传递给下一步。其次是编排运行时，t3code 读取这张图，按拓扑顺序调度各 Agent，处理并行分支、失败重试与超时，并在某个节点需要人拍板时挂起等待。第三是可观测层，运行时把每一步的输入、输出、耗时、状态都记录为可查询的对象，前端控制面据此画出实时进度与依赖关系。整条链路的关键设计在于"解耦"——你改流程只动声明，不动各个 Agent 的实现；反过来 Agent 升级也不影响整体编排。它本质上把多 Agent 系统从"即兴对话"变成"可重复、可审计的工程结构"，让复杂自动化的成败不再依赖某次对话的临场发挥，而是落在稳定的调度框架上。

**▌ 动手验证**

动手验证的第一步是把 pingdotgg/t3code 仓库拉到本地并安装其 CLI 或依赖，按其文档初始化一个工作区。随后写一段最小工作流声明：定义两个串行步骤，第一步调用一个 Agent 读取某份文档并提取要点，第二步把要点交给另一个 Agent 生成摘要，并声明第二步依赖第一步的输出。验证编排是否生效，可在控制面或命令行启动该工作流，观察它是否按依赖顺序执行、能否在第一步完成后才触发第二步，并在面板里看到两步各自的状态与产物，从而确认依赖调度真实可用。进一步验证可加入一个"人工审批"节点——让工作流在发布前暂停等待你确认，确认后继续，验证其可干预能力。若某步故意制造失败，观察它能否按配置重试或安全中止，确认编排的健壮性，完整跑通后再考虑接入真实业务。

### 5. 【OpenMausBot：为 Agent 提供沙箱虚拟机的开源 Grok 替代】（⭐ 约 21K）

> 📍 **导语**（80-100字）：milind-soni/OpenMausBot 本周以约 8.3k 新增 Star 冲进周榜前列，它把"给机器人一个能跑代码的虚拟机"做成开源方案，对标闭源的 Grok Bot。过去想让 Agent 自动干真实任务，要么被困在聊天框里只能生成文本，要么直接给本机权限吓得人不敢用；OpenMausBot 给每个 Bot 一台隔离的虚拟机，今天关注的是：Agent 正从"会说话"走向"会动手"，而隔离执行是这条路的底座。

**▌ 它是什么？**

milind-soni/OpenMausBot 是一个用 TypeScript 编写的开源项目，定位是"可运行虚拟机的开源 Grok Bot 替代"。它的核心创新不是又训练了一个对话模型，而是给聊天机器人配了一台虚拟机——Bot 在虚拟机里拥有完整的运行环境，可以安装依赖、执行脚本、读写文件、调用外部服务，像一个真正坐在电脑前的操作员。项目把"对话"和"执行"解耦：模型负责理解和规划，虚拟机负责落地动作，二者通过明确的接口通信。它同时也强调多智能体协作，可以编排多个 Bot 分工完成更复杂的任务，是 Agent 从"文本生成器"迈向"可执行操作员"的典型代表。

**▌ 它解决了什么问题？**

当前大多数 AI 助手卡在一个尴尬的位置：它们能写出一段 Python 代码，却没法真正替你运行它、验证它、把结果存下来；它们能建议你"去网站点这个按钮"，却连不上浏览器。想让 Agent 真正自动化，最简单的办法是给它本机 Shell 权限，但这等于把家门钥匙交给一个会幻觉的程序，风险极高。OpenMausBot 的解法是用"虚拟机"做安全边界：Bot 的所有动作都被关在一台隔离机器里，即使它执行了危险指令，破坏范围也仅限于这台虚拟机，宿主系统、个人文件、云凭证都安然无恙。这让普通开发者第一次能以接近零信任的成本，让 Agent 去"实操"而不是只"建议"，把自动化从演示变成可用。

**▌ 核心原理拆解**

核心原理是"对话模型 + 隔离运行时"的双层架构，精髓在于把执行风险锁死在沙箱里。第一层是对话与规划，OpenMausBot 接收用户的自然语言请求，由底层大模型拆解为一系列可执行步骤，并决定每一步要调用什么能力。第二层是虚拟机运行时，这是它真正的护城河：系统为当前会话拉起一台轻量虚拟机，预装好操作系统、运行时和常用工具链，Bot 的每一步动作（装包、跑脚本、改配置、访问网络）都在这台机器内发生。第三层是反馈闭环，虚拟机把命令的输出、文件的变化、网络的响应回传对话层，模型据此判断下一步，形成"想—做—看—再想"的循环，直到任务完成。整条链路的关键设计在于"隔离"与"可观测"：隔离保证单台虚拟机被攻破或误操作也不会波及其他；可观测保证每一步都有日志，方便开发者事后审计与调试。它还支持把多个 Bot 放进同一台或不同虚拟机里协作，原理上相当于给一支自动化小队每人配了一间带监控的工位。

**▌ 动手验证**

动手验证的第一步是在本机装好容器或虚拟机支撑环境（项目依赖容器类运行时来隔离），随后克隆 milind-soni/OpenMausBot 仓库并按文档启动服务，将你的模型 API Key 配置进环境变量。验证能否跑通的最快方式是发一条"在虚拟机里新建一个目录、写一段 hello world 脚本并运行它，把输出返回给我"的指令。你会看到 Bot 在隔离环境里真实执行了创建、写入、运行三步，并把结果回传，而你的本机文件系统中找不到任何新建目录——这恰好验证了隔离生效。进一步验证可以给它一个会出错的脚本，观察它能否在虚拟机内捕获异常而不影响宿主；也可以接一个真实任务（如自动整理下载文件夹），确认自动化链路端到端可用，从而证明沙箱方案既安全又能真正干活。

|---------|--------|-------|-------|
| 执行能力 | 虚拟机内实操 | 仅文本 | 本机实操 |
| 安全性 | 隔离沙箱 | 无风险 | 高风险 |

### 6. 【hermes-agent：覆盖桌面与 Android Termux 的跨平台 CLI 智能体】（⭐ 约 261K）

**▌ 它是什么？**

NousResearch/hermes-agent 是一个跨平台的命令行智能体（CLI agent），用 Python 编写、采用 MIT 许可，本周总 Star 约 26.1 万。它把自己做成"一套安装覆盖全部形态"的 Agent：在同一份安装里，你既能选择底层模型、配置网关（通过 Telegram、Discord 等消息应用入口），也能并行启动多个子 Agent 协作，还附带一个设置向导降低上手门槛。它支持 Linux、macOS、Windows 三大桌面系统，更特别的是通过签名 APT 仓库把支持下探到 Android/Termux，让手机也能跑完整的 Agent，是一个强调"随人走"的跨端运行时而非单一桌面工具。

**▌ 它解决了什么问题？**

当下大多数编码智能体 CLI 止步于桌面：你在笔记本上用得顺手，一到通勤的手机、出差只带平板的场景就抓瞎，要么没有客户端，要么功能残缺。另一类痛点是"入口单一"——很多 Agent 只能在你敲命令的终端里对话，无法接入你日常待着的聊天软件，导致自动化没法融入既有协作流。hermes-agent 的切入点正是"跨端 + 多入口"：它让同一个 Agent 既能在桌面命令行跑，也能在安卓上跑，还能通过消息网关变成"在群里 @ 一下就干活"的同事，把 Agent 从固定工位解放到任意设备，让自动化真正融入用户的全场景工作流而非被绑死在一台机器上。

核心原理是"单一运行时 + 多形态接入 + 子 Agent 并行"，关键把"设备差异"和"入口差异"都收敛到一层运行时之下。其一是运行时统一，hermes-agent 把模型选择、上下文管理、工具调用收敛进一个可执行体，不同操作系统只是它的部署目标而非分叉版本，因而桌面与移动端共享同一套逻辑。其二是入口网关，它通过配置把 Agent 接到 Telegram、Discord 等消息平台，消息进来后由本地运行时接管、执行、再把结果推回聊天窗口，实现"聊天软件即操作台"。其三是并行子 Agent，面对复杂任务时，主 Agent 能把子任务分发给多个子 Agent 并发执行，再汇总结果，原理类似把一个大任务拆给一支小队。最后是移动适配，它通过签名 APT 仓库把运行所需打包进 Termux 可装的包，使安卓设备无需从源码折腾即可获得与桌面一致的能力。整条链路的重点是让 Agent 真正随人走，而不是被锁在某个特定环境里。
