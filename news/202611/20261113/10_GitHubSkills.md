### 1. 【rea：Agent 驱动的自动化逆向工程利器】（⭐45万）

> 📍 **导语**：在 2026 年 11 月第二周 GitHub 飙升榜上，morluto/rea 以单周新增约 2.2 万 Star 登顶 AI 类仓库增速第一，累计 Star 逼近 45 万。它把过去依赖资深安全研究员手工调试的逆向工程，交给多 Agent 协作的自动化流水线，从观察应用外在行为一路钻到原生机器码，把动辄数周的逆向周期压缩到小时级，引发红队与独立开发者强烈关注。

---

**▌ 它是什么？**
rea（Reverse Engineer Anything）是一个开源的、以 Agent 为核心引擎的逆向工程框架。它并非传统一锤子买卖式的反编译工具，而是一套"把逆向任务拆成多步、由不同专长的 Agent 接力完成"的工作流系统。最上层的协调者 Agent 先制定逆向计划，调用擅长动态分析的 Agent 观察程序运行时的行为、网络请求与文件改动，再调用擅长静态分析的 Agent 解析二进制结构、符号与汇编指令，最后由擅长总结的 Agent 把零散发现汇编成人类可读的报告。它既可针对桌面应用，也能深入原生二进制、固件乃至移动端安装包。

**▌ 它解决了什么问题？**
逆向工程的门槛一直很高：一是工具链割裂，IDA、Ghidra、objdump、Wireshark 各管一段，中间全靠人脑拼接；二是知识门槛陡，读懂反汇编需要数年积累；三是耗时巨大，一个中等规模闭源程序完整逆向往往要好几周。rea 解决的核心痛点是"把割裂的工具和隐性知识封装进可复用的 Agent 角色"。过去你要手动在动态沙箱跑程序、抓包，再切到反编译器对照，现在只需描述目标，rea 的多个 Agent 自动分工：行为 Agent 负责跑起来观察，静态 Agent 负责拆解结构，关联 Agent 负责两路证据交叉印证，最终产出带调用链和可疑点的报告。这让只有基础开发能力的人也能在数小时内拿到过去需专家团队交付的逆向结论。

**▌ 核心原理拆解**
rea 的架构可以理解为一个"多 Agent 流水线 + 证据库"的闭环系统，其原理在于把逆向拆成可并行、可验证的子任务，并由协调层统一编排：

```
输入: 目标程序/二进制/固件 + 用户的逆向目标描述
  ↓
协调 Agent: 拆解目标 → 生成逆向计划与子任务清单
  ↓
行为 Agent: 在沙箱中动态运行 → 采集行为、网络、文件痕迹
  ↓
静态 Agent: 解析二进制/反汇编 → 提取符号、控制流、字符串
  ↓
关联 Agent: 交叉印证两路证据 → 定位关键逻辑与可疑点
  ↓
报告 Agent: 汇总成带调用链的可读报告 + 置信度标注
```

第一个关键设计是把"动态观察"与"静态拆解"解耦成两个独立 Agent，避免单一模型在长上下文里迷失。第二个关键设计是引入一个共享的"证据库"（evidence store），行为 Agent 和静态 Agent 都把发现写入同一份结构化证据，关联 Agent 据此做交叉验证，从而抑制幻觉——这对安全场景尤为关键，因为错误结论可能带来致命后果。第三个关键设计是协调层用"目标驱动"而非"步骤驱动"编排：用户只说"我想知道它把用户数据发去了哪里"，rea 就自动决定先动态抓包还是先静态找加密函数，而非死板按固定顺序执行。这种"分而治之 + 证据闭环"的原理，正是它能把专家级任务平民化的根本原因。

**▌ 动手验证**
rea 的最小可运行验证从安装与一次轻量目标分析开始（请仅在合法授权范围内使用）：

```bash
# 1. 克隆并安装（需 Python 3.11+ 与可用的 LLM 密钥）
git clone https://github.com/morluto/rea
cd rea && pip install -e .

# 2. 配置 Agent 使用的模型端点（支持 OpenAI/本地兼容 API）
export REA_MODEL_ENDPOINT="https://api.openai.com/v1"
export REA_API_KEY="你的密钥"

# 3. 对目标程序发起行为+静态联合逆向，输出 Markdown 报告
rea analyze ./target_app --goal "定位它对外发送的数据字段" \
     --out report.md
```

运行后会得到一份 `report.md`，含行为 Agent 抓到的外连地址、静态 Agent 还原的发送函数调用链，以及关联 Agent 标注的置信度。初次体验建议先用自己编译的示例程序，确认流水线跑通后再挑战真实目标。

**▌ 对比与选型**
| 维度 | rea | Ghidra | IDA Pro |
|------|-----|--------|---------|
| 核心思想 | 多 Agent 自动逆向 | 免费反汇编平台 | 商业反编译 |
| 上手成本 | 描述目标即可 | 需学界面与脚本 | 贵且陡峭 |
| 自动化 | 高，端到端 | 低，偏手动 | 中，靠插件 |
| 适用人群 | 开发者/安全新手 | 逆向工程师 | 专业研究员 |
| 选型建议 | 快速理解黑盒 | 深度静态分析 | 工业级逆向 |

### 2. 【claude-mem：让每个 Agent 跨会话记住上下文】（⭐11.5万）

> 📍 **导语**：thedotmack/claude-mem 在 2026 年 11 月周榜中以约 6.4k 周新增 Star、累计 11.5 万 Star 稳居前列。它瞄准所有 AI 编程助手共同的软肋——"金鱼记忆"：每次新开会话 Agent 把过去忘光，开发者不得不反复粘贴背景。claude-mem 给 Agent 装一套"记忆外脑"，在会话中捕获一切行为、用 AI 压缩成精炼记忆，并在未来会话自动注入相关上下文，兼容 Claude Code、Codex、Gemini、Copilot、OpenCode 等主流 Agent。

---

**▌ 它是什么？**
claude-mem 是一个用 TypeScript 编写的开源持久化记忆系统，定位为"面向每一种 Agent 的跨会话上下文层"。它的工作分三步：捕获（capture）、压缩（compress）、注入（inject）。捕获阶段监听并记录 Agent 会话中做过的所有动作——读过的文件、执行的命令、做出的决策；压缩阶段调用模型把冗长原始记录提炼成高信噪比的"记忆条目"；注入阶段当 Agent 开启新会话时，依据当前任务相关性把最匹配的若干记忆自动塞回上下文窗口。本质上，它把"项目的隐性知识"从人的脑子里挪到了可检索、可累积的存储里。

**▌ 它解决了什么问题？**
它解决的根本问题是 Agent 的"上下文失忆"带来的重复劳动与理解偏差。没有记忆层时，一个 Agent 上午帮你重构了支付模块，下午你新开会话问"为什么这里要这样改"，它已完全不记得上午决策，只能重新读代码猜意图，轻则答非所问，重则改坏之前成果。对团队而言问题更明显：不同成员、不同时间启动的 Agent 各自为政，无法共享"这个项目踩过哪些坑"的经验。claude-mem 解决的就是这类"知识无法跨会话、跨角色沉淀"的痛点。实测中，把长期维护的仓库接上 claude-mem 后，重复解释背景的时间显著下降，Agent 在新会话也能直接延续上次的修改思路，相当于给每个 Agent 配了一位"永远在岗、过目不忘"的搭档。

**▌ 核心原理拆解**
claude-mem 的原理可概括为"写时全量捕获、存时语义压缩、读时相关注入"三段式，核心在于把记忆当作一等公民来管理：

```
输入: Agent 会话中的行为流（文件读写/命令/决策）
  ↓
捕获层: 全量记录原始行为事件到本地存储
  ↓
压缩层: 调用 LLM 把原始事件归纳为记忆条目（带标签/时间戳）
  ↓
检索层: 新会话启动时，按当前任务做语义匹配
  ↓
注入层: 将 Top-K 相关记忆写回上下文，Agent 无缝续接
```

第一个关键是"全量捕获但不全量注入"：写时尽量保留细节，读时只挑相关的，避免上下文被无关历史淹没。第二个关键是压缩层用模型做"摘要式记忆"而非简单日志堆叠，让存储体积可控、检索信号更干净。第三个关键是它做成"与具体 Agent 无关"的适配层——通过统一中间表示对接不同厂商的 Agent，因此 Claude Code 还是 Codex 都能即插即用。原理上它借鉴人类记忆的"编码—存储—提取"三阶段，但用确定性存储加语义检索替代人脑模糊回忆，从而既稳又准。此外，claude-mem 在压缩层会对记忆条目做去重与冲突检测，当同一事实在不同会话被多次记录时，它保留最新且置信度最高的版本，避免记忆库被重复条目撑爆。检索层也不只是关键词匹配，而是用嵌入向量做语义召回，因此你用不同措辞提问，它仍能命中同一条记忆。正是这种"写宽读窄、压缩去重、语义召回"的组合，让记忆层在长周期项目里越用越聪明，越积越准。

**▌ 动手验证**
把 claude-mem 接到正在用的 Agent 上只需几步，下面以兼容 Claude Code 为例：

```bash
# 1. 安装（需要 Node 18+）
npm install -g @thedotmack/claude-mem

# 2. 初始化项目记忆存储
claude-mem init ./your-project

# 3. 启动伴随进程，自动捕获后续会话行为
claude-mem watch --agent claude-code

# 4. 新开会话时，让 Agent 读取相关记忆
claude-mem recall "支付模块上次怎么改的" --inject
```

前两步建立本地记忆库，第三步开启后台监听，第四步在需要时把记忆注入新会话。验证效果最简单的办法：今天让 Agent 改一处逻辑，明天新会话直接问"昨天为什么这么改"，若它能准确复述，说明记忆层已生效。记忆文件建议一并纳入版本管理，方便团队共享。

**▌ 对比与选型**
| 维度 | claude-mem | Letta | Mem0 |
|------|-----------|-------|------|
| 定位 | 通用记忆层 | 带记忆的 Agent | 记忆服务 |
| 接入成本 | 低，即插即用 | 中，需改写 | 中，需 API |
| 跨 Agent | 强，多厂商 | 自有体系 | SDK 集成 |
| 存储位置 | 本地优先 | 可自托管 | 云/自托管 |
| 选型建议 | 给现有 Agent 加记忆 | 从头造 Agent | 服务化记忆 |

### 3. 【worktrunk：为并行 Agent 管好多分支工作区】（⭐1.2万）

> 📍 **导语**：max-sixty/worktrunk 在 2026 年 11 月周榜中以约 2.3k 周新增 Star、累计 1.2 万 Star 入选。它解决"多 Agent 并行干活"时代被严重低估的工程难题：当三四个编码 Agent 同时在一个仓库改代码，分支怎么开、怎么隔离、怎么合并，传统 Git 工作流会瞬间乱成一团。worktrunk 用 Rust 命令行把 Git worktree 的创建、切换、清理做成可编排操作，让每个 Agent 拥有隔离工作区又能在需要时干净汇合。

---

**▌ 它是什么？**
worktrunk 是一个用 Rust 实现的命令行工具，专门管理 Git worktree，目标用户是"需要让多个 AI Agent 并行工作的开发者"。Git worktree 本身是个冷门但强大的特性：它允许同一个仓库被检出到多个目录，每个目录是不同的分支，却共享同一份 .git 对象库。worktrunk 把这套原本需要记一堆命令的操作，封装成直观子命令——一键开工作区、给工作区贴标签、按标签批量切换、干掉没用的工作区。它不产生新概念，只是让 worktree 真正好用，从而成为并行 Agent 工作流里那个"分身管理器"。

**▌ 它解决了什么问题？**
它解决的痛点是并行 Agent 场景下的"工作区冲突"。设想你同时让 Agent A 修登录 bug、Agent B 加导出功能、Agent C 做重构，如果三者都在同一工作目录改，最后谁先提交、谁把谁的覆盖，根本说不清。过去开发者要么手动 `git worktree add` 一个个建，要么干脆串行跑 Agent——既慢又易错。worktrunk 解决的就是这个：它让每个 Agent 拿到独立工作区，彼此改动物理隔离、互不踩踏；合并时再逐个工作区审查。对于一天跑十几轮 Agent 任务的重度用户，它把"开分身—收回成果"的循环从分钟级降到秒级，也大幅降低把不同任务代码混在一起的事故率。

**▌ 核心原理拆解**
worktrunk 的原理建立在"Git worktree 即隔离单元"这一事实上，并用 CLI 把生命周期管理自动化：

```
输入: 一条并行任务描述（如"三个 Agent 各改一个模块"）
  ↓
编排层: 为每个 Agent 计算独立分支名与目录
  ↓
工作树层: 调用 git worktree add 生成隔离目录
  ↓
执行层: 各 Agent 在各自目录独立开发，互不干扰
  ↓
回收层: 任务完成后批量 prune/merge，清理残留
```

第一个关键是"以 worktree 而非分支别名"做隔离——因为 worktree 是真实目录，Agent 不需要任何特殊感知，像在普通仓库里工作即可。第二个关键是标签化（tagging）：worktrunk 给每个工作区打上语义标签（如 task-login、task-export），用户不必记一长串分支名，用标签就能整体切换或回收。第三个关键是用 Rust 重写带来的速度——创建、列举、清理成百上千个工作树也几乎零延迟，这对"Agent 高频开合工作区"的场景至关重要。原理上它没发明新范式，而是把 Git 既有能力的"最后一公里"打磨顺滑，让并行 Agent 真正落地。此外，worktrunk 在创建工作树时会自动沿用主仓库的远程与钩子配置，保证每个分身都能正常拉取与推送，不会因为目录隔离而丢失 git 元数据。它还提供安全的清理策略：未被合并或仍有未提交改动的工作区默认被保护，只有在显式确认后才 prune，避免误删进行中的 Agent 成果。对于需要在 CI 里动态开合工作树的场景，worktrunk 也能以非交互方式调用，把"开分身—跑 Agent—收成果—清分身"固化成流水线的一步。

**▌ 动手验证**
用 worktrunk 给两个并行任务各开一个工作区，验证隔离效果：

```bash
# 1. 安装（Rust 工具链）
cargo install worktrunk

# 2. 为"修复登录"任务开一个隔离工作区
worktrunk new login-fix --branch feat/login-fix

# 3. 为"新增导出"任务再开一个，彼此互不影响
worktrunk new export-add --branch feat/export

# 4. 列出当前所有工作区与标签
worktrunk list

# 5. 任务结束，清理已合并的工作区
worktrunk prune --merged
```

运行 `worktrunk list` 会看到两个独立目录，分别挂不同分支；在 login-fix 目录改文件，export 目录完全不受影响。这便直观证明并行 Agent 的工作区隔离已生效。

**▌ 对比与选型**
| 维度 | worktrunk | 手动 worktree | Git 分支 |
|------|-----------|--------------|----------|
| 隔离粒度 | 目录级 | 目录级 | 同目录切换 |
| 管理成本 | 低，标签化 | 高，记命令 | 中 |
| 并行友好 | 强 | 弱 | 弱 |
| 适合场景 | 多 Agent 并行 | 偶尔多任务 | 单人开发 |
| 选型建议 | Agent 流水线 | 临时隔离 | 传统协作 |

### 4. 【spec-kit：规格驱动开发的官方上手工具包】（⭐14.9万）

> 📍 **导语**：github/spec-kit 在 2026 年 11 月周榜中以约 4k 周新增 Star、累计 14.9 万 Star 稳居前列。它来自 GitHub 官方，定位是"帮你用规格驱动开发（SDD）起步的工具包"。在 AI 编程普及的今天，常见失败模式是开发者直接让 Agent 写代码却没讲清需求，结果生成代码方向跑偏、返工不断。spec-kit 先逼你把"要做什么、为什么、验收标准"写成结构化规格，再交给 Agent 实现，把最大不确定性源头提前消除。

---

**▌ 它是什么？**
spec-kit 是 GitHub 推出的开源工具包，用 Python 编写，目标是把"规格驱动开发"这套方法论变成可执行的日常流程。它不是一个运行时框架，而是一组脚手架与约定：当你启动新功能，spec-kit 引导你依次产出需求规格（requirements）、设计规格（design）与任务清单（tasks）三类文档，并放到约定目录结构里。随后无论是人类还是 AI Agent，都能基于这些规格开工，且每一步有据可依。它本质上给"先想清楚再写代码"提供了一套标准化模板与校验，让规格成为团队和 Agent 之间共同的语言。

**▌ 它解决了什么问题？**
它解决的是"需求模糊导致 AI 编程失控"的痛点。没有规格时，你给 Agent 一句"做个用户登录"，它可能凭想象补出一整套你并不想要的字段、流程和依赖，改起来比自己写还累。更糟的是，当多人或多 Agent 协作，每个人对"登录"的理解都不同，最终产物互相矛盾。spec-kit 解决的就是这类"源头不清、下游全乱"的问题：它强制在写代码前先产出可读、可审、可版本化的规格，把"做什么、不做什么、怎么算完成"钉死。社区反馈里，接上规格驱动后，Agent 一次性产出可用代码的比例明显提升，评审时扯皮也大幅减少，因为验收标准一开始就写在了规格里。

**▌ 核心原理拆解**
spec-kit 的原理是把"开发"重新定义为"规格的逐步精化"，用目录约定与模板把抽象方法论落地：

```
输入: 一个功能想法或一句话需求
  ↓
需求规格: spec-kit 引导列出目标、用户、边界与验收点
  ↓
设计规格: 拆解模块、接口、数据流与关键技术决策
  ↓
任务清单: 把设计拆成可勾选、可并行的具体任务
  ↓
执行层: 人类或 Agent 按 tasks 实现，对照规格验收
```

第一个关键是"三文档分层"：需求回答 why、设计回答 how、任务回答 what to do，三者职责清晰，避免把决策混在一团。第二个关键是"约定优于配置"——spec-kit 用固定目录与文件名让规格可被工具自动发现，Agent 不需要额外指令就能找到上下文。第三个关键是它把规格当成"活文档"：实现中若发现设计有问题，回头改规格而非偷偷改代码，保证文档与实现始终同步。原理上它顺应了"AI 擅长执行、不擅长猜意图"的特点，用结构化规格填补了人与 Agent 之间的语义鸿沟。此外，spec-kit 在生成三文档时会做一致性校验：设计规格里的接口必须能追溯到需求规格里的某条验收点，任务清单里的步骤必须能映射回设计模块，任何悬空项都会在 `spec-kit show` 里被高亮，强迫你在写码前补齐全。它还能把这些规格导出成 Agent 可消费的上下文包，使得同一个规格既能给人评审，也能直接喂给编码 Agent，真正做到"一份规格、两路消费"。这种把验收标准前置并强制可追溯的设计，是 SDD 区别于"先写码后补文档"的根本所在。

执行后项目里会出现 `requirements/`、`design/`、`tasks/` 三个目录与对应文档。把 `tasks/export-csv.md` 交给编码 Agent，它就能严格按规格实现，并在完成后对照需求里的验收点自测。验证 SDD 价值的最快方式：故意写一份模糊需求和一份精确规格，分别让 Agent 实现，对比返工次数差异。

### 5. 【Dexto：配置驱动的 Agent 开发工具包与编排框架】（⭐新上榜）

> 📍 **导语**：Truffle AI 于 2026 年 11 月 10 日发布开源项目 Dexto，迅速进入 AI Agent 工具热度视野。它定位为"构建 AI Agent 与 Agentic 应用的开放工具包（harness）"，最大卖点是"配置驱动"：用一份配置文件声明 Agent 需要的能力，Dexto 就帮你把会话管理、工具编排、记忆这些脏活累活接好。它原生支持 50 多种大模型，并内置对 MCP 的集成，既能拼装自己的 Agent，也能复用海量现成 MCP 工具服务器，降低从零搭建门槛。

---

**▌ 它是什么？**
Dexto 是一个开源的 Agent 开发工具包（harness+toolkit），核心哲学是"用配置代替胶水代码"。传统上，你想做一个能调用搜索、读写文件、记住历史的 Agent，得亲手把模型 API、工具函数、记忆存储、会话状态一个个接起来，光样板代码就劝退一半人。Dexto 把这些能力做成开箱即用的内置模块：会话管理维护多轮上下文，工具编排把外部能力注册进来并按需调用，记忆模块负责跨轮次上下文保留。你只要写一段 YAML 或配置文件声明"我要哪些工具、用哪个模型、记忆存哪"，Dexto 就组装出一个可运行的 Agent。

**▌ 它解决了什么问题？**
它解决的痛点是"造 Agent 太碎、太重复"。没有这类工具包时，每个团队都在重复造轮子：今天接 OpenAI、明天换 Gemini，又得重写一遍工具调度；想加记忆，又得自己设计存储结构。更麻烦的是模型厂商繁多，硬编码绑定某一家就会被锁死。Dexto 解决的就是这类"集成成本高、迁移成本高"的问题：配置驱动让换模型只改一行，50+ 模型开箱支持；MCP 集成让你不必自己写工具，直接挂载社区现成的服务器；内置的会话与记忆模块省去了最烦人的状态管理。对想快速验证 Agent 想法的独立开发者和小团队，它把"从想法到可运行 Agent"的起步时间从数天压到数小时。

**▌ 核心原理拆解**
Dexto 的原理是"声明式配置 + 运行时编排器"，把 Agent 的能力组装从代码层抬升到配置层：

```
输入: 一份 Agent 配置（模型/工具/记忆/会话策略）
  ↓
加载层: 解析配置，实例化所选模型适配器
  ↓
注册层: 把声明的工具与 MCP 服务器注册进工具总线
  ↓
编排层: 运行时按消息循环调度工具调用与记忆读写
  ↓
会话层: 维护多轮状态，输出结构化响应
```

第一个关键是"模型适配抽象"：Dexto 内部对 50+ 模型做了一层统一接口，配置里写 `model: gemini-xxx` 还是 `model: gpt-xxx` 对上层逻辑透明，换模型不碰业务代码。第二个关键是"工具总线 + MCP"：它既支持自带工具函数，也支持通过 MCP 协议挂载外部服务器，工具发现与调用走统一路径。第三个关键是把"会话"和"记忆"当作一等公民内置，而非事后补丁——会话层管理多轮上下文窗口，记忆层决定哪些信息跨轮保留。原理上它把"Agent = 模型 + 工具 + 记忆 + 编排"这个公式标准化，让开发者像搭积木一样拼装，而不是每次重写底层。此外，Dexto 在编排层内置了失败重试与工具调用的护栏：当某个工具抛出异常或返回不符合预期时，编排器会依据配置决定重试、降级还是把错误如实回传给模型，避免一次工具故障拖垮整轮对话。它也对 MCP 服务器的连接做健康检查，断线时自动重连并在状态栏提示，保证挂载的外部工具始终可用。对于需要把 Agent 嵌进现有产品的团队，Dexto 还暴露了流式输出与中间步骤钩子，让你能在 UI 上实时展示 Agent 的思考与工具调用过程，而不必自己实现那套复杂的事件管道。

### 6. 【Agent Relay：自托管的 AI 编程任务看板与编排器】（⭐新上榜）

> 📍 **导语**：Agent Relay 于 2026 年 11 月 11 日作为开源、可自托管项目发布，并迅速进入 AI Agent 热度榜。它最特别的是从同一套代码库长出两个产品：面向开发者的 Dev Boards（AI 编程 Agent 的任务看板）和面向普通用户的 BeeZilla（消费者级编排器）。前者给编码 Agent 一张"持久任务黑板"，让 Agent 认领、推进、交接任务；后者让不懂代码的人用大白话描述目标，由系统引导到草稿审批，补上"Agent 跑起来后谁来管任务、管进度"的运维空白。

---

**▌ 它是什么？**
Agent Relay 是一个开源、可自托管的 Agent 编排平台，核心由两部分组成。Dev Boards 是一块"为 AI 编码 Agent 设计的持久任务看板"：它不像普通 issue 系统只给人看，而是提供一组"Agent 专属动词"，让 Agent 能自己读任务、认领任务、更新进度、标记完成，相当于给 Agent 配了一个共享工作台。BeeZilla 则是面向非技术用户的消费级编排器，用户用自然语言描述目标，BeeZilla 引导你确认需求、生成执行草稿，再由底层 Agent 去落地。两者共享同一套任务与权限底座，使技术团队和业务方能在同一系统里对接。

**▌ 它解决了什么问题？**
它解决的是"Agent 有了，但任务没人管"的协作断层。单个 Agent 很强，但当你有一支由多个 Agent（甚至多个团队）组成的"Agent 舰队"，谁来分派任务、谁记录做到了哪一步、出错时怎么回滚，就成一团乱麻。过去要么靠人在聊天群里手动协调，要么把 Agent 硬塞进为人类设计的项目管理工具，后者因缺少"Agent 可操作的接口"而水土不服。Agent Relay 解决的正是这个：Dev Boards 用 Agent 能直接读写的任务结构，把分派、认领、推进、交接全流程自动化；BeeZilla 则把业务方的模糊目标转译成 Agent 可执行的草稿。对于想让 Agent 真正进生产、而非停留在 demo 的团队，它补上了"任务编排与治理"这块关键拼图。

**▌ 核心原理拆解**
Agent Relay 的原理是"把任务建模成 Agent 可直接操作的持久对象，并区分技术/业务两类入口"：

```
输入: 开发者任务 或 业务方自然语言目标
  ↓
Dev Boards: 任务写成 Agent 可读的持久对象 + 专属动词
  ↓
BeeZilla: 自然语言 → 需求澄清 → 生成可执行草稿
  ↓
调度层: 把草稿/任务分派给对应 Agent 并跟踪状态
  ↓
反馈层: 进度回写看板，人工在审批点介入
```

第一个关键是"任务对象化"：Dev Boards 里的任务不是给人看的文字，而是带状态机、可被 Agent 通过 API/动词操作的实体，Agent 能 `claim`、`progress`、`done`，状态变化实时可见。第二个关键是"双入口同底座"：开发者走 Dev Boards 的精细控制，业务方走 BeeZilla 的自然语言引导，但最终都落到同一套任务与权限模型，避免两套系统打架。第三个关键是"人在回路的审批点"：BeeZilla 生成草稿后必须人工确认才执行，把自主权留在人手里。原理上它把"Agent 编排"从隐藏在代码里的硬编码，提升为可观测、可治理的共享看板。此外，Agent Relay 在底座层实现了细粒度的权限模型：Dev Boards 上的每个动词（claim、progress、done）都可绑定到特定 Agent 身份与角色，防止越权操作或任务被重复认领；BeeZilla 则把业务方的目标与底层执行草稿做双向可追溯，任何一次自动执行都能回放到"谁提的需求—生成了什么草稿—谁批的—Agent 做了什么"。这套"对象化任务 + 身份权限 + 执行回放"的机制，让一支 Agent 舰队即便规模扩大，治理成本仍维持在可控水平，而不是陷入混乱的群组消息流。

**▌ 动手验证**

# 2. 打开看板，创建一个编码任务
