### 1. 【visionOS 27 Spatial Preview：Mac 向 Vision Pro 流式渲染 3D 内容】

> 📍 **导语**：WWDC26 平台综述披露，SwiftUI 与空间计算进一步打通，新增 Spatial Preview 框架，允许开发者在 Mac 上把 3D 模型流式推送到身边的 Apple Vision Pro 进行实时预览，无需反复打包安装。该能力配合 RealityView 与 CompositorServices，显著降低空间应用的设计验证成本，是 visionOS 27 最值得 SwiftUI 开发者关注的原生能力之一。

---

**📱 深度报道**

**▌ 更新全景**
在本次平台更新中，Apple 将 SwiftUI 的 3D 与空间能力做了系统化升级。WWDC26 综述提到，SwiftUI 在 visionOS 26/27 上新增了 Widgets 支持，并引入 Spatial Preview 框架（流式预览），让 Mac 应用可以把 stereo 内容渲染到 Vision Pro 的共享空间中。RemoteImmersiveSpace 作为 macOS 场景类型，可通过 CompositorServices 在 Vision Pro 上渲染立体内容，同时保留 hover 效果与输入事件。对开发者而言，这意味着"写一次 SwiftUI 视图、在 Mac 与头显间无缝流转"的体验进一步落地。

**▌ 技术细节深解**
Spatial Preview 的核心是把 Mac 作为算力源、Vision Pro 作为显示终端，通过本地网络流式传输 3D 场景。开发者仍用熟悉的 `RealityView` 描述内容，再挂接会话即可：

```swift
import SwiftUI
import SpatialPreview

struct ProductViewer: View {
    var body: some View {
        RealityView { content in
            if let model = try? await ModelEntity.load(named: "chair") {
                content.add(model)
            }
        }
        // 把当前场景从 Mac 流式推送到 Vision Pro 的共享空间
        .spatialPreview(session: .macToVision)
    }
}
```

与之配套，`RealityKit` 实体现在遵循 `Observable`，SwiftUI 视图可直接观察实体属性变化；`View` 上新增的 attachment 组件、动画同步与 `binding to components` 让 SwiftUI 与 RealityKit 的"友谊"更紧密。早期采用者可在 Xcode 27 的 Device Hub 中一键选择目标头显进行预览。

**▌ 开发者迁移指南**
现有 visionOS 应用若仍用旧版 `ImmersiveSpace` 写法，可逐步迁移到 `RemoteImmersiveSpace` 以复用 Mac 算力；引入 `SpatialPreview` 需部署目标不低于 visionOS 26，且 Xcode 27 的 Spatial Preview 工具链仅支持 Apple Silicon Mac。建议在 CI 中单独保留 visionOS 模拟器构建任务，避免头显缺失阻塞流水线。注意：流式预览依赖同一 Apple ID 下的本地网络授权，企业内网需放开 mDNS 与本地回环端口。

**▌ 生态与竞品对比**
相比 Meta Horizon 的单独编辑器与 Unity 的 XR 插件链，Apple 把空间预览直接嵌入 SwiftUI 与 Xcode，降低跨工具切换成本。社区反馈显示，Unity 仍是重度 3D 游戏首选，但产品展示、电商预览等轻量空间场景正快速向原生 SwiftUI 迁移。国内不少零售与汽车 App 已将"AR 看车/看家居"从 WebAR 迁回原生 RealityKit，以获得更稳定的帧率与更低的发热。

---

**🤖 开发研判**

🔮 **技术趋势**：空间计算正从"独立头显应用"走向"Mac 与头显协同"，SwiftUI 成为跨平面与空间的统一 UI 语言，这符合 Apple 多端融合的长期路线。

📊 **开发者决策影响**：做电商、教育、工业设计类 App 的团队，现在就值得引入 `RealityView` + Spatial Preview 做原型，验证"在手机/平板上看、在头显里审"的工作流；纯 2D 业务可暂缓。

⚠️ **适配风险**：头显保有量仍有限，投入需评估 ROI；流式预览的网络与功耗约束在弱网环境会明显劣化，第三方渲染中间件（如自定义 Metal 管线）与 Spatial Preview 的协同尚不成熟。

💡 **学习优先级**：先掌握 `RealityView` 基础与实体观察，再学 `RemoteImmersiveSpace` 与 `CompositorServices`，最后接入 Spatial Preview 会话管理；官方 WWDC26 "Better Together: SwiftUI & RealityKit" 是最佳起点。

### 2. 【Apple Core AI 与 Foundation Models 框架：端侧模型运行与 App Intents 集成】

> 📍 **导语**：WWDC26 综述显示，Apple Intelligence 被"从零重建"，底层换用与 Gemini 技术相关的全新 Apple Foundation Models，并新增 Core AI 框架用于在 App 内运行端侧模型。Foundation Models 框架扩展至图像输入与云模型支持，App Intents 则把应用能力暴露给 Siri 与自然语言交互，Dynamic Profiles 让开发者用更少代码构建 AI Agent 与技能。

---

**📱 深度报道**

**▌ 更新全景**
本次重建包含三条主线：一是 Foundation Models 框架能力扩展，支持图像输入并可调用开发者选定的云模型；二是全新 Core AI 框架，内置于操作系统、针对 Apple Silicon 优化，专门在 App 内运行端侧模型；三是 App Intents 与 View Annotations——后者让用户对屏幕上可见内容直接提问并操作。Dynamic Profiles 被定位为"用更少代码构建 AI 智能体与技能"的机制，可在运行时切换工具与指令。整体目标是把端侧推理与系统级智能深度缝合。

**▌ 技术细节深解**
Foundation Models 框架面向已启用 Apple Intelligence 的 iOS 26+/macOS 26+ 设备，零配置即可做文本生成、摘要、结构化输出。结合 App Intents，可把业务动作声明为可被自然语言触发的意图：

```swift
import AppIntents
import FoundationModels

@AssistantIntent(schema: .business)
struct SummarizeOrderIntent: AppIntent {
    @Parameter(title: "订单备注") var note: String
    func perform() async throws -> some IntentResult & ProvidesDialog {
        let session = LanguageModelSession()
        let result = try await session.respond(
            to: "把下面订单备注提炼成一句话摘要：\(note)"
        )
        return .result(dialog: Dialog(result.content))
    }
}
```

Core AI 则面向需要内置自有模型的场景，由系统调度 Neural Engine，开发者无需关心模型加载与算力分配。对于超出端侧能力的前沿任务，可通过 `Dynamic Profiles` 把请求路由到开发者接入的云模型。

**▌ 开发者迁移指南**
若此前依赖旧版 `NaturalLanguage` 或自建 ONNX 推理，可先评估 Foundation Models 是否满足（文本/摘要/分类类任务基本覆盖）；需要自定义视觉或音频模型时再引入 Core AI + Core ML。App Intents 需把原有 SDK 调用改写为 `@AssistantIntent` 标注的 struct，并保持 `@Parameter` 类型与系统语义对齐。最低部署目标建议锁定 iOS 26，旧系统回退到云端或本地规则。

**▌ 生态与竞品对比**
与 Android 的 AI Edge / MediaPipe、Google Play 的 Gemini Nano 路线相比，Apple 把端侧模型与 App Intents 深度耦合，强调"系统即 Agent 运行时"。优势是隐私与离线，短板是跨平台复用差。国内开发者更关注鸿蒙的盘古端侧与意图框架，但 App Intents 的声明式范式对 iOS 业务 App 仍是首选。

---

**🤖 开发研判**

🔮 **技术趋势**：端侧小模型 + 系统级 Agent 编排将成为 iOS 应用标配，App Intents 正从"快捷指令"升级为"应用能力总线"。

📊 **开发者决策影响**：新项目应默认把核心动作封装为 App Intents，便于未来被 Siri/Agent 调用；存量项目可做增量改造，优先标注高频操作（下单、搜索、分享）。

⚠️ **适配风险**：Foundation Models 对中文长上下文与复杂推理仍有限；云模型路由会引入网络与合规成本；不同区域 Apple Intelligence 可用性与模型版本不一致，需做能力探测与降级。

💡 **学习优先级**：先学 App Intents 声明与 `@Parameter`，再练 Foundation Models 的 `LanguageModelSession` 与 Tool 协议，最后研究 Core AI 自定义模型部署；参考 Apple「On-Device AI」开发者指南与 WWDC26 相关 session。

### 3. 【ArkUI 渲染更新机制升级：NODE 函数级 Diff 与逻辑 UI 分离】

> 📍 **导语**：鸿蒙官方文档显示，ArkUI 的 UI 更新机制迎来关键升级：声明式开发的 Diff 算法从 COMPONENT/ELEMENT 树形对比，升级为单节点 NODE 的函数式更新。同时逻辑与 UI 分离把跨端流转的 7 个步骤压缩到 2 个，跨端迁移与协同代码量可降低 40% 以上。这是鸿蒙原生应用性能与开发效率的双重跃迁。

---

**📱 深度报道**

**▌ 更新全景**
ArkUI 作为鸿蒙声明式 UI 框架，本次升级聚焦两件事：其一是渲染层，编译器生成特定函数把 UI 组件更新与数据变更做细粒度绑定，Diff 不再遍历整棵树，而是按单节点 NODE 做函数式更新；其二是工程层，逻辑与 UI 分离通过数据双向绑定传递页面变化，把"跨端流转"从 7 步简化为 2 步。配合 Stage 模型的十几种 Extension 扩展服务，后台进程调度更有序，前台资源供给更有保障。

**▌ 技术细节深解**
函数级 NODE 更新的收益体现在状态变更时的局部刷新。以下 ArkTS 组件在 `count` 变化时，框架只更新该 NODE 而非重建子树：

```typescript
@Entry @Component struct Counter {
  @State count: number = 0;
  build() {
    Column() {
      Text(`当前计数: ${this.count}`)
        .fontSize(20)
        .onClick(() => { this.count++; })
      Button('增加').onClick(() => { this.count++; })
    }
  }
}
```

`@State` 触发的更新会被编译为针对该节点的函数调用，避免 ELEMENT 树的整体 diff。逻辑 UI 分离则允许把状态管理抽到独立模块，界面仅消费数据，显著降低多端（手机/平板/车机）复用时的重复代码。官方称跨端迁移与协同开发代码量可降低 40% 以上。

**▌ 开发者迁移指南**
从旧版类 Web 范式（HML/CSS/JS）迁移的项目，应按 ArkTS 声明式重写，利用 `@State/@Prop/@Link` 完成状态绑定；评估现有自定义组件是否依赖整树重建，改为细粒度状态可获渲染提速。DevEco Studio 的 `apiCompatibilityCheck` 可帮助发现 ArkTS API 兼容性缺口。建议在 CI 中开启严格模式，提前拦截不规范的跨端写法。

**▌ 生态与竞品对比**
相比 SwiftUI 的 `@State` 与 Jetpack Compose 的 `mutableStateOf`，ArkUI 的 NODE 函数级更新在"一次开发多端部署"场景下更强调跨设备一致性；与 Flutter 的 Element/Widget 树 diff 相比，单节点函数式更新减少了树遍历开销。国内 HarmonyOS NEXT 原生应用占比快速提升，ArkUI 已成为鸿蒙生态的事实标准 UI 方案。

---

**🤖 开发研判**

🔮 **技术趋势**：声明式 UI 正从"树 diff"走向"节点函数级更新"，渲染确定性与性能可预测性成为框架竞争焦点，鸿蒙借此强化多端统一体验。

📊 **开发者决策影响**：新鸿蒙项目应直接采用 ArkTS 声明式 + 逻辑 UI 分离架构；存量 HML 项目建议排期迁移，尤其性能敏感页面优先。

⚠️ **适配风险**：细粒度更新要求开发者正确划分状态作用域，错误使用 `@State` 跨组件共享仍会引发不必要刷新；C++ 自绘制（XComponent）与 Web 组件混合场景下，NODE 更新边界需谨慎处理。

💡 **学习优先级**：掌握 `@State/@Prop/@Link/@Provide` 状态体系 → 理解 NODE 函数级更新原理 → 实践逻辑 UI 分离与跨端流转；参考华为开发者联盟 ArkUI 官方文档与 HarmonyOS NEXT 技术白皮书。

### 4. 【鸿蒙一次开发多端部署：断点系统与栅格布局的响应式适配】

> 📍 **导语**：鸿蒙 NEXT 的"一次开发，多端部署"依赖统一的响应式布局体系。官方与社区资料梳理出四大技术支柱：弹性单位 vp/fp、12 列栅格 GridRow/GridCol、断点 Breakpoint（sm/md/lg/xl）与自适应布局引擎。开发者无需为圆形表盘、折叠屏、车机等特殊形态编写多套布局，即可实现一致且自适应的界面呈现。

---

**📱 深度报道**

**▌ 更新全景**
鸿蒙把多端适配拆成"底层分布式 + 界面响应式"两层。界面层由 ArkUI 提供标准化适配规则：vp（虚拟像素）按屏幕密度自适应、fp（字体像素）跟随系统字号；GridRow/GridCol 以 12 列栅格按比例分配空间；Breakpoint 预设 sm（手机）、md（平板）、lg（智慧屏）、xl（车机）等断点，依据屏幕宽度自动切换布局。自适应布局引擎进一步处理圆形屏、超宽屏等特殊形态，理论上免去了多套布局代码。

**▌ 技术细节深解**
断点系统通过监听屏幕宽度自动切换导航形态，是"一次开发多端部署"最直观的一环：

```typescript
@Entry @Component struct ResponsiveNav {
  @StorageProp('breakpoint') bp: string = 'sm';
  build() {
    GridRow() {
      GridCol({ span: { sm: 12, md: 6, lg: 4 } }) {
        if (this.bp === 'sm') {
          BottomNavigation() // 手机：底部导航
        } else {
          SideNavigation()   // 大屏：侧边导航
        }
      }
    }
  }
}
```

`BreakpointSystem.onBreakpointChange` 在宽度跨断点时回调，配合 `GridCol` 的 `span` 按设备分配列数，实现"小屏单列、大屏多列"。弹性单位 vp/fp 保证不同分辨率下尺寸与字体一致，避免传统 px 适配的错位与模糊。

**▌ 开发者迁移指南**
从 Android 多 APK / iOS 多 Storyboard 思路迁移的团队，应放弃"为每类设备单独布局"，改为"单一响应式布局 + 断点分支"。建议在 DevEco Studio 中开启多设备预览（手机、折叠屏、平板、车机模拟器）逐个断点验证。注意圆形屏（手表）需显式处理安全区与极短宽高比，避免内容被裁切；车机 xl 断点要兼顾驾驶场景的触控热区放大。

**▌ 生态与竞品对比**
对比 Flutter 的 `LayoutBuilder` + `MediaQuery`、Compose 的 `WindowSizeClass`，鸿蒙的 Breakpoint 体系把断点命名与栅格直接内置，降低适配心智负担。优势在于与分布式软总线协同，流转时布局随设备自动重排；短板是生态组件库仍少于 Flutter/Compose，部分三方控件需自行做断点适配。

---

**🤖 开发研判**

🔮 **技术趋势**：响应式断点正成为跨端框架的标配，鸿蒙将其与分布式流转深度绑定，"设备切换即布局重排"会成为多端应用的默认预期。

📊 **开发者决策影响**：鸿蒙项目立项时应把"断点矩阵"列为设计输入，而非事后适配；UI 组件库选型需确认其对 sm/md/lg/xl 的内置支持。

⚠️ **适配风险**：复杂业务页在断点切换时可能出现状态丢失或动画跳变；折叠屏展开/合拢的连续变化不是离散断点，需用 `onBreakpointChange` 之外的连续监听补充；低端设备栅格重排可能带来额外测量开销。

💡 **学习优先级**：先理解 vp/fp 与栅格模型 → 熟练使用 Breakpoint 与 GridRow/GridCol → 掌握自适应布局与特殊形态（圆形/折叠）处理；参考鸿蒙官方「一次开发多端部署」指南与社区实战示例。

### 5. 【Jetpack appfunctions 1.0 beta：把 App 能力开放给端侧 AI 助手】

> 📍 **导语**：Android Developers 于 2026-10-21 发布 Jetpack `appfunctions` 1.0.0-beta01，允许应用把功能与数据以标准化方式暴露给设备端 AI 助手，让助手能发现并直接执行任务。该库引入 KSP 编译器插件、与 MCP 命名规范对齐的 `instructions` 字段，标志着 Android 正把"App 能力总线"交给端侧智能体调用。

---

**📱 深度报道**

**▌ 更新全景**
`appfunctions` 的核心意图是让 AI 助手能在设备上发现并执行 App 功能。1.0.0-beta01 相比 alpha13 做了多项 API 调整：`AppFunctionName` 从 `metadata` 包迁移到根包；`AppFunctionAppMetadata.description` 重命名为 `instructions`，XML 属性同步改名以对齐 MCP 命名约定；`AppFunctionResourceContainer` 与 `AppFunctionTextResource` 标记为 `@ExperimentalAppFunctionsApi`；并修复了 Java 库脱糖环境下 `java.time` 参数反序列化失败等问题。依赖引入需配合 KSP 编译器插件。

**▌ 技术细节深解**
声明一个可被 AI 助手调用的函数，使用 `@AppFunctionDeclaration` 标注，并通过 KSP 自动生成元数据：

```kotlin
// build.gradle.kts
ksp("androidx.appfunctions:appfunctions-compiler:1.0.0-beta01")
implementation("androidx.appfunctions:appfunctions:1.0.0-beta01")

// 业务代码
@AppFunctionDeclaration("com.example.order.query")
fun queryOrder(
    @AppFunctionParameter("orderId") orderId: String
): OrderResult {
    return repository.findOrder(orderId)
}
```

编译器插件会把函数签名、参数约束（如 `AppFunctionStringValueConstraint` 的 `patternMatchers`）写入元数据，端侧助手据此理解能力边界并生成调用。测试侧提供 `AppFunctionTestRule` 与 `AppFunctionServiceEntryPoint` 支持，便于在单元测试中模拟助手调用。

**▌ 开发者迁移指南**
从 alpha 升级需注意破坏性变更：`description` → `instructions` 的字段改名、`AppFunction` 注解重命名为 `AppFunctionDeclaration`、`ObserveAppFunctionsEvent` → `AppFunctionsChangeEvent`。建议先在小范围"查询类"能力（订单、库存、日程）上试点，确认助手调用准确率后再扩展写操作。最低需 AGP 9 与 Kotlin 2.0+ 工具链，CI 需启用 KSP 并校验生成产物。

**▌ 生态与竞品对比**
与 iOS 的 App Intents、鸿蒙的意图框架类似，Android 用 `appfunctions` 把 App 能力暴露给系统智能体，三者殊途同归。差异在于 Android 明确对齐 MCP 命名，利于与跨平台 Agent 协议互通；而 Apple 的 App Intents 更封闭但系统整合更深。对国内开发者而言，appfunctions 的端侧执行模型契合隐私合规趋势，但需等待 Android 系统助手在国内机型的落地进度。

---

**🤖 开发研判**

🔮 **技术趋势**：端侧 AI 助手调用 App 能力正成为移动 OS 的通用能力层，"App 即工具（App-as-Tool）"将重塑入口形态，搜索与图标启动或被自然语言指令部分替代。

📊 **开发者决策影响**：新功能上线时应同步评估是否暴露为 appfunctions，尤其是高频查询与标准化操作；存量 App 可制定"能力清单"逐步开放，提升被系统助手召回的概率。

⚠️ **适配风险**：能力暴露带来权限与滥用面扩大，需严格约束写操作的确认与回滚；beta 阶段 API 仍可能变动，`@ExperimentalAppFunctionsApi` 标注项不宜用于生产；不同 Android 版本对 appfunctions 的系统级支持不一致，需做能力探测。

💡 **学习优先级**：理解 appfunctions 元数据模型 → 掌握 `@AppFunctionDeclaration` 与 KSP 插件 → 实践 `AppFunctionTestRule` 测试与 MCP 对齐；参考 Android Developers「appfunctions」发布说明与 Jetpack 文档。

### 6. 【Ionic 9 与 Capacitor 8：Web 技术栈跨端移动化的新进展】

> 📍 **导语**：跨端开发指南与官方资料显示，Ionic Framework 9.0.0 已于 2026-08-19 成为最新生产版本，Capacitor 8 则在新 iOS 项目默认启用 Swift Package Manager 并支持 Android edge-to-edge。对于以 Web 技术栈为核心的团队，Ionic + Capacitor 提供了一条"把成熟 Web 能力快速分发到 iOS/Android"的轻量跨端路径，与 Flutter/RN 形成差异化互补。

---

**📱 深度报道**

**▌ 更新全景**
Ionic 的定位是"Web-first 团队的移动化捷径"：用标准 Web 技术（HTML/CSS/TS）写 UI，再通过 Capacitor 把 Web 包进原生壳并调用原生能力。Capacitor 8 的关键变化包括：新 iOS 项目默认使用 Swift Package Manager 管理依赖（替代 CocoaPods），并加入 Android edge-to-edge（全面屏沉浸）支持。Ionic 9 延续组件库的现代化，强化与主流前端框架的协同。整体看，Ionic 不追求自绘引擎，而是让 Web 开发者"用最熟悉的栈"触达移动端。

**▌ 技术细节深解**
Capacitor 的桥接模型让 Web 代码在原生 WebView 中运行，同时通过插件访问原生 API。判断运行环境并调用原生能力的典型写法：

```typescript
import { Capacitor } from '@capacitor/core';
import { LocalNotifications } from '@capacitor/local-notifications';

if (Capacitor.isNativePlatform()) {
  // 仅在原生壳中调用，避免 Web 端误用
  await LocalNotifications.schedule({
    notifications: [{ title: '提醒', body: '任务到期', id: 1 }]
  });
}
```

Capacitor 8 默认 SPM 意味着 iOS 依赖解析更快、与 Xcode 15+ 工具链更契合；Android edge-to-edge 则要求开发者适配系统栏沉浸，避免内容被状态栏/导航栏遮挡。Ionic 9 的组件已针对该模式做了安全区内边距处理。

**▌ 开发者迁移指南**
从 Capacitor 7 升级到 8，需确认原生项目已迁移到 SPM（移除 Podfile 相关步骤），并检查 Android 的 `android:fitsSystemWindows` 与沉浸适配；Ionic 9 对旧版组件若有废弃，按官方迁移指南逐项替换。建议保留 Web 端独立构建，Capacitor 仅作为"分发层"，这样 Web 站点、PWA 与原生 App 可共享同一份业务代码，最大化复用。

**▌ 生态与竞品对比**
与 Flutter（自绘 Impeller）、React Native（New Architecture + Hermes）相比，Ionic/Capacitor 的优势是 Web 人才池巨大、上手成本最低，短板是复杂动画与原生质感的还原度弱于自绘方案。适合内容型、工具型、企业内部 B2B SaaS 应用；对像素级品牌一致或重度图形场景，Flutter 更合适。NativeScript 9.1 虽也走 TS + 原生 API 路线，但人才池更小。

**🤖 开发研判**

🔮 **技术趋势**：跨端框架正分化为"自绘派（Flutter）""原生桥接派（RN）""Web 封装派（Ionic/Capacitor）"三足鼎立，团队将按人才栈而非性能唯一维度选型。

📊 **开发者决策影响**：已有 React/Vue/Angular 与 Web 资产的团队，Ionic 9 + Capacitor 8 是成本最低的"移动化"路线；若未来要桌面/嵌入式，再评估 Flutter 更划算。

⚠️ **适配风险**：WebView 性能天花板在长列表与高频交互场景明显；Capacitor 8 的 SPM 默认化要求原生工程现代化，老项目迁移有摩擦；iOS 对 WebView 能力与隐私（如追踪）持续收紧，需关注 App Store 审核口径。

💡 **学习优先级**：夯实 Web 基础（组件化、响应式）→ 学 Capacitor 插件模型与原生桥接 → 掌握 iOS SPM 与 Android edge-to-edge 适配；参考 Ionic 官方文档与 Capacitor 8 发布公告。

### 7. 【端侧 AI 推理工程化：Core ML 量化、MLX Swift 与 Android AI Edge 选型】

> 📍 **导语**：多份移动 AI 工程指南指出，2026 年端侧推理已成为严肃移动产品的"标配"。iOS 侧以 Core ML（量化/调色板化）+ MLX Swift 运行开源 LLM 为主，Android 侧由 AI Edge（TensorFlow Lite 继任者）与 MediaPipe LLM Inference API 承担，配合 NNAPI 硬件加速。工程化重点落在模型转换、4-bit 量化、KV-cache 管理与功耗热控。

---

**📱 深度报道**

**▌ 更新全景**
端侧 LLM 的工程路径已相对清晰：先用 `coremltools` 或 Hugging Face exporter 把模型转为目标格式（`.mlpackage` / `.tflite`），再做量化压缩。Core ML 支持 4-bit 权重量化以适配移动端内存；MLX Swift 则面向 Apple Silicon 以最高吞吐运行 Llama/Mistral/Qwen/Gemma 等开源模型，适合研究与原型。Android 侧 Google AI Edge（TFLite 继任者）借 NNAPI 调用 NPU/GPU，MediaPipe LLM Inference API 已支持 Gemma 2B 等级小模型并自动处理分词与 KV-cache。

**▌ 技术细节深解**
把 Hugging Face 模型转 Core ML 并量化是关键一步，典型脚本：

```python
import coremltools as ct
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

tok = AutoTokenizer.from_pretrained("microsoft/phi-2")
model = AutoModelForCausalLM.from_pretrained("microsoft/phi-2").eval()
example = tok("Hello world", return_tensors="pt")
traced = torch.jit.trace(model, (example["input_ids"], example["attention_mask"]))

mlmodel = ct.convert(
    traced,
    inputs=[ct.TensorType(name="input_ids", shape=example["input_ids"].shape)],
    compute_precision=ct.precision.FLOAT16,
    minimum_deployment_target=ct.target.iOS17,
)
mlmodel = ct.models.neural_network.quantization_utils.quantize_weights(mlmodel, nbits=4)
mlmodel.save("phi2.mlpackage")
```

性能参考：iPhone 16 Pro（A18 Pro）跑 3B 模型约 8–12 tokens/s、7B 约 3–5 tokens/s；Android 旗舰（骁龙 8 Gen 3）3B 约 5–8 tokens/s。工程上需限制生成长度、本地缓存高频回复、优先用 NPU 并做热节流回退云端的混合路由。

**▌ 开发者迁移指南**
云端 LLM 应用要下沉到端侧，先做模型选型（3B 以内优先），用 4-bit 量化把体积压到可分发范围；iOS 用 Core ML + MLX Swift 双轨（Core ML 生产、MLX 研究），Android 用 AI Edge + MediaPipe。务必在真机做功耗与温控压测，连续推理会快速发热降频。混合架构建议以置信度路由：低置信度走云端、高置信度走端侧，兼顾隐私、延迟与质量。

**▌ 生态与竞品对比**
iOS 的 Core ML 与 Neural Engine 整合最深、量化工具链成熟；Android AI Edge 胜在设备基数大、NNAPI 通用；跨平台可选 PyTorch Mobile / ONNX Runtime。相比纯云方案，端侧推理延迟近零、可离线、隐私好，但受限于设备算力与电池。MLX Swift 在 Mac 微调工作流上独树一帜，是 iOS 团队做端侧原型的高效选项。值得注意的是，端侧与云端并非替代关系，而是分层协作：端侧兜住高频、低敏、强实时的请求，云端承接复杂推理，二者通过统一的能力网关编排，才能兼顾体验、成本与合规。

---

**🤖 开发研判**

🔮 **技术趋势**：端侧小模型 + 混合路由将成为移动 AI 的标准架构，4-bit 量化与 NPU 调度是工程基本功，"端侧负责快、云端负责强"成为共识。

📊 **开发者决策影响**：2026 年起新移动产品应把"是否端侧推理"纳入架构评审；从单点功能（输入法预测、图片分类）起步，再扩展到端侧 LLM 摘要/对话。

⚠️ **适配风险**：量化会损失精度，关键任务需评估质量红线；不同芯片 NPU 算子支持不一，模型可能回退 CPU 导致卡顿；电池与发热是体验硬约束，无热控策略的产品易在真实场景翻车。

💡 **学习优先级**：学模型转换与量化（coremltools / AI Edge）→ 掌握 KV-cache 与混合路由 → 真机功耗压测与降级策略；参考 Apple Core ML 文档、Google AI Edge 指南与端侧部署工程教程。
