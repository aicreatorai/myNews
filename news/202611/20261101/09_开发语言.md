# 09_开发语言

### 1. 【TypeScript 7.0 原生编译器重写提速构建】

> 📍 **导语**：TypeScript 在 2026 年迎来关键转折。3 月发布的 6.0 是现存 JavaScript 代码库上的最后一个版本，扮演着连接 5.9 与即将到来的 7.0 的桥梁角色；而 7.0 最引人注目的变化，是用 Rust 完全重写的原生编译器（社区代号 tsgo），目标把大型代码库的增量类型检查速度提升一个数量级。对拥有数百万行 TS 的前端团队而言，这将直接改变 CI 时长与本地开发体验，让"类型即文档"的代价大幅下降。

**▌ 它是什么？**：TypeScript 是微软 2012 年推出的、为 JavaScript 添加静态类型系统的超集语言。7.0 的"原生编译器"并非语法层面的新特性，而是编译器后端的彻底替换：原先基于 Node.js 的解释型 checker 被用 Rust 重写，并通过 Node API 暴露与旧版一致的能力。开发者日常调用的 `tsc`、语言服务、编辑器插件，在 7.0 下会调用同一个 Rust 编译核心。6.0 阶段已预先调整了泛型调用中函数表达式的类型检查方式，并扩展了导入断言语法的弃用路径，为迁移扫清障碍，使 5.9→7.0 的过渡尽量平滑。

**▌ 它解决了什么问题？**：随着前端工程规模膨胀，TypeScript 编译慢成为普遍痛点。大型单体仓库（如 VS Code、Angular、Mono 系项目）全量类型检查动辄数十秒甚至数分钟，CI 队列因此被拉长；本地保存时的类型反馈延迟也拖慢了"编辑—报错—修复"的循环。旧编译器是单线程、基于 JS 堆的，难以利用多核与零拷贝内存。7.0 重写后，类型检查从解释执行走向原生机器码，结合并行化与更高效的数据结构，让类型检查从"等待"变成"瞬时"，尤其利好超大规模代码库与单体仓库。

**▌ 核心原理拆解**：新编译器的核心是把 TypeScript 的语义模型——符号表、类型关系、约束求解——从 JS 对象迁移到 Rust 的带所有权的值类型上。类型节点不再是一棵散落在 GC 堆上的对象图，而是紧凑的结构体数组，访问局部性更好；类型等价与子类型判断用并查集与缓存键去重，避免重复推导。Rust 版本还把绑定图（module graph）建模为可并发遍历的结构，多个文件可以并行解析与绑定。与此同时，社区构建系统（如复刻版 ttsc、ts-rust）已验证"编译期 Lint"的可行性——在类型检查的同时收集代码异味，把 ESLint 的部分规则下沉到编译器层，进一步压缩工具链总耗时。

**▌ 动手验证**：想提前体验原生后端，可安装社区预览并对比耗时：
```bash
# 使用基于 Rust 的 TypeScript 编译器预览（tsgo）
npm install -D @typescript/native-preview
npx tsc --version   # 查看是否进入原生后端
```
在 `tsconfig.json` 中保持常规严格配置即可：
```json
{
  "compilerOptions": {
    "strict": true,
    "module": "node16",
    "target": "es2022"
  }
}
```
对同一个项目分别用 6.0 稳定线与 7.0 预览跑 `tsc --build`，Mergify 等团队已实测在超大仓库上有数量级提升。注意：7.0 仍是预览，生产环境建议暂留 6.0 稳定线，待官方 GA 后再切换。

**▌ 对比与选型**：
| 维度 | TS 6.0（JS 后端） | TS 7.0（Rust 原生） | 替代：Bun 内置检查器 |
| 启动/检查速度 | 基线 | 大幅提升（大型仓倍数级） | 快，但生态覆盖弱 |
| 内存占用 | 高（JS 堆） | 低（原生栈） | 低 |
| 编辑器体验 | 成熟 | 预览中 | 部分支持 |
| 稳定性 | 生产可用 | 预览 | 实验 |
选型：追求极致 CI 速度的团队可试点 7.0 预览；求稳则停留在 6.0 并等待官方 GA。Bun 内置类型检查器虽快，但对完整 TS 语义覆盖仍弱，适合脚本型项目而非大型工程。

### 2. 【Java 26 携 HTTP/3 与结构化并发落地】

> 📍 **导语**：Java 在 2026 年 3 月 17 日发布第 26 版（Oracle JDK 26），这是一个六个月节奏下的短期支持（STS）版本，继承 2025 年 9 月的 LTS 版本 JDK 25。本次更新把 HTTP/3 支持、结构化并发第六次预览、向量 API 第十一次孵化，以及 G1 垃圾收集器的吞吐优化带到开发者面前，并移除了早已废弃的 Applet API，持续向"更安全、更高并发、更贴近现代硬件"演进。

**▌ 它是什么？**：JDK 26 是 Oracle 按六个月发布节奏推出的特性版。它延续 Project Loom（虚拟线程）、Project Panama（外部函数接口 FFM）与 Project Valhalla（值类型）的集成路线。HTTP 客户端 API 首次正式支持 HTTP/3（基于 QUIC），结构化并发进入第六次预览，向量 API 继续孵化，G1 收集器通过减少内部同步来提升多核吞吐。同时，对用深度反射修改 final 字段的行为给出警告，收紧安全边界，并移除了 Java Applet API 这一历史包袱。移除 Applet 不仅清理了长期无人维护的遗留代码，也减少了潜在攻击面与维护者负担，使 JDK 的整体体积与攻击面进一步收敛，让新版本更聚焦于现代并发与云原生场景。

**▌ 它解决了什么问题？**：传统 Java 在高并发场景中受限于"一个请求一个线程"的模型，虚拟线程虽已在 JDK 21 落地，但把多个相关任务的生命周期绑定在一起的"结构化并发"仍需库层样板。JDK 26 把相关任务纳入同一作用域，父任务取消时子任务自动清理，避免线程泄漏与上下文丢失。HTTP/3 则解决队头阻塞与弱网下的连接恢复问题；G1 的同步削减直接转化为吞吐提升，对延迟敏感的服务意义明显；移除 Applet 也减少了潜在攻击面。此外，JDK 26 引入的提前时对象缓存（ahead-of-time object caching）能序列化部分已初始化的堆对象，使后续 JVM 启动跳过重复的常量池解析与类预置，缩短冷启动时间，对 Serverless 与容器化部署尤为关键。对 final 字段深度反射的警告，则堵住了攻击者通过 setAccessible 篡改不可变对象（如密钥、配置）的经典绕过路径，把安全加固前移到语言层。

**▌ 核心原理拆解**：结构化并发的核心是 `StructuredTaskScope`，它把一组子任务当作一个整体：作用域关闭时，未完成的子任务被取消，已完成的异常被聚合为单一失败。这与 Go 的 errgroup、Kotlin 的 coroutine scope 思路一致，但用 Java 的异常模型表达。HTTP/3 实现建立在 JDK 的 DatagramChannel 与 QUIC 握手之上，把多路复用流映射到 HttpClient 的异步响应。向量 API 则通过 `FloatVector` 等类型把 SIMD 操作暴露给 Java，由 HotSpot 在运行时映射到 AVX/NEON 指令，无需写 JNI；提前时对象缓存则改进了 HotSpot 的启动与预热时间。向量 API 经第十一次孵化后已覆盖主流浮点与整数形态，配合 HotSpot 的自动循环向量化，使 Java 在数值计算上逐步逼近原生 C 的性能，为科学计算与 ML 推理的 Java 化提供基础。

**▌ 动手验证**：用结构化并发把"取用户信息"与"取订单"绑定在同一作用域：
```java
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    var user   = scope.fork(() -> fetchUser(id));
    var orders = scope.fork(() -> fetchOrders(id));
    scope.join();            // 等待两者都结束
    scope.throwIfFailed();   // 任一失败则抛异常
    return new Profile(user.get(), orders.get());
}
```
在 JDK 26 中需用 `--enable-preview` 开启结构化并发预览，并用同一版本号编译运行。HTTP/3 则直接在 `HttpClient.newBuilder().version(HttpClient.Version.HTTP_3).build()` 中声明，无需改业务代码。

**▌ 对比与选型**：
| 特性 | JDK 25 (LTS) | JDK 26 (STS) | 备注 |
| 支持周期 | 长期（数年） | 6 个月 | 生产选 LTS |
| 结构化并发 | 第五次预览 | 第六次预览 | 仍预览 |
| HTTP/3 | 不支持 | 支持 | 新能力 |
| G1 吞吐 | 基线 | 优化 | 免费红利 |
选型：新项目可先用 JDK 25 LTS 保稳定；想尝鲜 HTTP/3 与并发预览的团队可在非关键链路试用 26，等 JDK 27/29 LTS 再固化。需要长期支持的系统应避免 STS 版本直接上线。

### 3. 【WebAssembly 组件模型打通跨语言边界】

> 📍 **导语**：WebAssembly（Wasm）已从"浏览器里的 C/C++"成长为跨语言、跨平台的通用二进制格式。2026 年，组件模型（Component Model）与 WASI 标准化的推进，让不同语言编译出的模块可以像乐高一样组合；µcad 等工具更把整个几何引擎压进 5MB 的 WASM 二进制，直接在浏览器里跑起 CAD 领域语言，展现出"一次编译、处处沙箱运行"的潜力。

**▌ 它是什么？**：WebAssembly 是一种可移植的字节码，最初为在浏览器中以接近原生速度运行非 JS 语言而设计。组件模型在其之上引入"接口类型"与 Wit 接口定义语言，使一个用 Rust 写的模块能调用另一个用 C 或 AssemblyScript 写的模块，而无需共享内存布局。WASI 则是系统调用层面的标准，让 Wasm 脱离浏览器也能访问文件、网络、时钟等能力，并以能力（capability）方式做最小权限授权，成为服务端 Wasm 的事实地基。

**▌ 它解决了什么问题？**：传统跨语言调用要么靠进程间通信（慢、易错），要么靠 FFI（脆弱、类型不安全）。Wasm 组件模型把"二进制接口"标准化，让模块之间只通过声明好的 Wit 接口交互，语言、编译器、运行时不耦合。WASI 则解决"Wasm 出浏览器后如何安全访问系统资源"：每个模块只拿到被显式授予的文件描述符或端口，天然抵御路径遍历与权限滥用，使插件系统、边缘函数、多语言微服务可以共享同一套隔离与权限模型。更重要的是，组件模型让同一份能力可以被多种语言实现、被多种语言消费，供应商锁定被打破：今天用 Rust 写的压缩组件，明天可被 Go 或 C 写的宿主直接复用，而无需重写，这从根本上改变了跨语言协作的经济账。

**▌ 核心原理拆解**：Wasm 模块是栈式虚拟机的指令序列，所有控制流在线性内存之外，沙箱隔离由运行时强制。组件模型把多个核心模块（core module）包成一个"组件"，在边界处插入适配代码，把一种语言的线性内存表示转换成另一种语言理解的值类型。Wit 描述函数签名、类型与资源，编译期生成两端的 glue code。WASI 的 capability 模型体现在：宿主传给模块的不是一个"整个文件系统"，而是一个已经打开的目录句柄；模块想读别的路径会被拒绝，因为手里没有对应能力，这从机制上消除了越权。

**▌ 动手验证**：用 Rust 编译一个 Wasm 组件并查看体积：
```bash
rustup target add wasm32-wasip1
cargo build --target wasm32-wasip1 --release
ls -lh target/wasm32-wasip1/release/*.wasm
wasmtime run target/wasm32-wasip1/release/demo.wasm
```
若想做跨语言组合，可安装 `wasm-tools` 与 `wit-bindgen`，把 Rust 组件暴露的 Wit 接口绑定到另一门语言调用。µcad 的实践也证明：把编译器与几何引擎打进约 5MB 的 WASM，外面包一层约千行 TypeScript，就能在浏览器里提供可交互的 CAD 体验。

**▌ 对比与选型**：
| 维度 | WebAssembly | 原生动态库(.so/.dll) | 容器(Docker) |
| 隔离性 | 强（沙箱） | 弱（同进程） | 强（OS 级） |
| 启动 | 毫秒级 | 微秒级 | 秒级 |
| 跨语言组合 | 组件模型标准化 | ABI 脆弱 | 进程级 |
| 体积 | 小（MB 级） | 小 | 大（百 MB） |
选型：边缘函数、插件系统、浏览器内重型计算优先 Wasm；需要与宿主共享复杂状态或极致启动速度的，仍可用原生库；完整环境隔离则继续用容器。

### 4. 【Gleam 以类型安全冲击 BEAM 函数式生态】

> 📍 **导语**：在 BEAM 虚拟机（Erlang 的运行时）上，一门叫 Gleam 的年轻语言正快速积累人气。Stack Overflow 2025 开发者调查显示，Gleam 以 70% 的"想继续用"admire 率首次上榜便冲到第二，仅次于 Rust。它用静态类型补齐了 Erlang/Elixir 动态类型的短板，又完整保留了 BEAM 久经考验的轻量进程并发与容错能力，被称为"最像 Rust 的 Erlang 方言"。

**▌ 它是什么？**：Gleam 是一门编译到 Erlang（targeting BEAM）的静态类型函数式语言，语法受 Rust 与 Elm 影响，强调可读性与编译期错误。它最终编译成高效的 Erlang 代码，因此能直接复用 OTP 框架、数十年的 BEAM 并发遗产，以及现成的 Erlang/Elixir 生态库。Gleam 的类型系统支持代数数据类型、模式匹配、类型推断，以及无空指针的 `Result`/`Option` 设计，把"运行时才发现的错误"尽量前置到编译期。Gleam 还内建了测试框架与格式化工具，强调"开箱即用"的工程体验；其包管理器通过约束式版本策略保证依赖可重现，避免 BEAM 生态常见的依赖漂移。社区虽年轻，但已在 Web 后端、CLI 工具与嵌入式网关场景出现生产案例。

**▌ 它解决了什么问题？**：Erlang/Elixir 的"让它崩溃（let it crash）"哲学与轻量进程非常擅长构建高可用系统，但动态类型意味着很多错误要等到运行时才暴露，重构大型系统时缺乏编译器这一道护栏。Gleam 把编译期类型检查带进 BEAM 世界：改一处数据结构，编译器会精确指出所有需要同步修改的调用点，把重构风险压到最低，同时不牺牲 BEAM 的并发与分布式优势，让新手也能安全地驾驭电信级可靠性。对初创团队尤其友好：不必先啃下 Erlang 晦涩的语法与宏系统，也能享受"五个九"可用性背后的监督树（supervisor tree）与热代码升级（hot code swap），把电信级可靠性平民化。

**▌ 核心原理拆解**：Gleam 编译器先把源码解析成带类型标注的 AST，再进行 Hindley-Milner 风格的类型推导与统一（unification），任何类型不匹配都在编译期报错。随后通过 Erlang 后端把类型擦除后的程序降译成等效的 Erlang 函数与模块——类型只存在于编译期，运行时仍是 BEAM 原生的轻量进程与消息传递。因为产物就是标准 Erlang，Gleam 与 Elixir/Erlang 可以无缝互操作：Gleam 代码能调用既有 Erlang 库，反之亦然，团队可渐进迁移而非推倒重来，学习曲线也因类型护航而显著低于纯 Erlang。Gleam 的编译器本身用 Rust 实现，构建速度快、错误提示贴近人类语言，进一步降低了 BEAM 的入门门槛，让有前端背景的开发者也能顺利过渡到函数式并发世界。

**▌ 动手验证**：用 Gleam 写一个安全的除法并模式匹配错误：
```rust
// gleam 代码
pub fn safe_divide(a: Int, b: Int) -> Result(Int, String) {
  case b {
    0 -> Error("divide by zero")
    _ -> Ok(a / b)
  }
}

pub fn main() {
  let assert Ok(x) = safe_divide(10, 2)
  io.println(int.to_string(x))
}
```
安装 Gleam 工具链（`gleam init` / `gleam run`）即可在本地 BEAM 上运行，类型错误会在 `gleam check` 阶段被拦下，无需等到运行期。

**▌ 对比与选型**：
| 维度 | Gleam | Elixir | Erlang |
| 类型系统 | 静态强类型 | 动态 | 动态 |
| 语法友好度 | 高（类 Rust） | 高（类 Ruby） | 中 |
| 生态复用 | 复用 BEAM 全生态 | 原生 | 原生 |
| 学习曲线 | 低（类型护航） | 中 | 较高 |
选型：新团队从零搭建 BEAM 服务、且希望编译期安全的，Gleam 是优选；已有 Elixir/Erlang 资产的，可在关键模块渐进引入 Gleam，用类型护栏守住核心逻辑。

### 5. 【Swift 6.3 增强 C 互操作与跨平台构建】

> 📍 **导语**：苹果主导的多平台语言 Swift 在 2026 年 3 月发布 6.3 版本，重点增强与 C 语言的互操作性，并改进跨平台构建工具。新增的 `@c` 属性允许把 Swift 函数与枚举直接暴露给 C 代码，Swift 包管理器也集成了统一构建引擎，让 Linux/Windows 等非苹果平台上的 Swift 开发体验更一致，并强化了对 Android SDK 的调用支持，拓宽了 Swift 的边界。

**▌ 它是什么？**：Swift 是苹果 2014 年推出的现代系统语言，兼顾性能与表达力，2015 年开源后逐步走向服务端、Linux 与 Windows。6.3 版本在既有并发模型（Swift 6 引入的严格数据隔离）之上，补齐了与 C 生态对接的最后一公里：`@c` 属性让 Swift 声明能以 C ABI 暴露，包管理器引入统一构建引擎以抹平各平台差异，并强化了对 Android SDK 的调用支持，使 Swift 在安卓侧的原生能力更进一步，向真正的跨平台系统语言迈进。

**▌ 它解决了什么问题？**：大量底层库、操作系统接口与硬件 SDK 仍用 C 暴露。过去 Swift 调用 C 需要繁琐的 bridging header 与手工类型映射，反向让 C 调用 Swift 几乎不可能，限制了 Swift 在系统编程与跨平台场景的渗透。6.3 的 `@c` 属性能把 Swift 函数、枚举原样呈现为 C 符号，使 Swift 编写的模块能被既有 C 工程直接链接；统一构建引擎则降低了"在 macOS 编译通过、到 Linux 却失败"的摩擦，减少平台特例与维护负担。借助 @c，Swift 现在能无缝嵌入既有的 C 大型工程（如图形、音视频、驱动），作为渐进式现代化的一层，而不必重写整个代码库；这对希望引入 Swift 安全特性的 C 老项目意义重大。

**▌ 核心原理拆解**：`@c` 的本质是给 Swift 声明附加 C 链接属性与 C 兼容的命名/调用约定（cdecl），编译器在生成符号时绕过 Swift 的 name mangling，输出 C 链接器能识别的扁平符号。对于枚举，`@c` 要求其原始值类型与布局与 C 的 enum 对齐，从而保证内存兼容。包管理器的统一构建引擎则把原本分散在 `swift build` 与各平台 Xcode/CMake 集成中的配置收拢成单一模型，用同一个依赖图解析与产物描述驱动不同后端的编译，减少平台分支，提升可重现构建能力。统一构建引擎还带来可重现构建（reproducible builds）的收益：同一份源码在不同机器上产出字节一致的产物，方便供应链审计与缓存命中；配合 Swift 6 的严格并发隔离，跨平台团队的编译与并发正确性同时得到保障。这一设计使 Swift 既能在苹果生态内保持现代语法，又能在系统底层与数十年 C 代码安全共存，避免推倒重来的迁移成本。

**▌ 动手验证**：把一个 Swift 函数暴露给 C：
```swift
// Swift 侧
@c
public func add(_ a: CInt, _ b: CInt) -> CInt {
    a + b
}

@c
public enum Status: CInt {
    case ok = 0
    case error = 1
}
```
编译为静态库后，C 侧即可 `#include` 生成的头文件并直接调用 `add` 与 `Status`。跨平台构建则直接用 `swift build` 统一引擎，无需为 Linux/Windows 单独维护脚本，显著降低持续集成的复杂度。

**▌ 对比与选型**：
| 维度 | Swift 6.3 | Objective-C | Rust(FFI) |
| C 互操作 | @c 双向暴露 | 原生互操作 | extern 块 |
| 内存安全 | 编译期所有权+ARC | 手动/ARC | 所有权 |
| 跨平台 | 官方改进中 | 仅苹果 | 强 |
| 生态 | 苹果为主 | 苹果遗留 | 跨域广 |
选型：苹果生态与服务端 Swift 团队应优先升级 6.3 以获取 C 互操作红利；纯跨平台系统库仍在考量 Rust，但 Swift 在苹果链路上的整合度无人能及。

### 6. 【Mojo 以 Python 语法重写 AI 原生计算】

> 📍 **导语**：在 AI 算力成为核心生产力的 2026 年，由 Modular 公司打造的 Mojo 试图用"Python 语法、系统级性能"填补 AI 原生语言的空白。它在保留 Python 易写性的同时，引入强类型、编译期优化与显式并行，目标是在张量计算与推理引擎这类热点上，既不让开发者写 C++，也不牺牲运行效率，把"胶水层"与"性能内核"合二为一。

**▌ 它是什么？**：Mojo 是一门面向 AI 与高性能计算的新兴语言，由 Chris Lattner（LLVM、Swift 作者）团队创立的 Modular 推出。它兼容 Python 语法的一个子集，让熟悉 Python 的开发者几乎零成本上手，同时加入了所有权语义、强类型、编译期元编程（`fn` 与 `struct` 的值语义）以及内建 SIMD 与并行原语。Mojo 可被编译为高效机器码，也能与现有 Python 生态互操作，把慢速循环用 Mojo 重写后嵌入 Python 调用。Mojo 还提供了 `tensor` 与 `mlir` 级别的原语，允许开发者在语言内表达多维内存布局与编译期形状推导，把算子优化从运行时推迟到编译期，减少内核启动开销。其与 Modular 的推理引擎深度集成，可作为部署链路的统一前端。

**▌ 它解决了什么问题？**：Python 是 AI 世界的"胶水层"，但其解释执行与 GIL 让它在计算密集的核心循环上成为瓶颈，团队往往被迫把热点用 C++/CUDA/Rust 重写，带来巨大的开发与维护割裂。Mojo 的诉求是：让同一门语言既能写易读的模型脚本，又能写贴近硬件的高性能内核，消除"Python 调 C++"的二元割裂，并借助编译期优化把张量算子速度推向接近手写底层代码的水平，降低 AI 工程师的全栈门槛。此外，Mojo 的强类型让张量维度、数据类型在编译期被校验，减少 PyTorch 中常见的运行时 shape mismatch 错误，把调试从"跑起来才报错"推进到"写错就红杠"。

**▌ 核心原理拆解**：Mojo 的类型系统区分 `def`（Python 动态语义）与 `fn`（强类型、值语义、显式错误返回），后者在编译期做严格检查并支持零成本抽象。它通过 `let`/`var` 的明确可变性与 `struct` 的值类型避免隐藏别名，配合编译器自动向量化把循环映射到 SIMD 指令。Mojo 的并行原语（如 `parallelize`）在语言层表达数据并行，运行时映射到多线程而无需手动管理锁。最关键的互操作来自它直接复用 Python 对象模型的能力：Mojo 函数可被 Python `import`，共享同一解释器，从而避免跨进程序列化开销。这种"同一门语言贯通脚本与高性能内核"的定位，正是 Mojo 区别于 Julia、Rust 等竞品的核心卖点，也让 AI 团队不必在易用性与性能之间二选一。

**▌ 动手验证**：一个 Mojo 的并行求和片段：
```mojo
fn parallel_sum(data: Span[Int]) -> Int:
    let mut total = 0
    @parallelize(data.len(), |i| {
        total += data[i]
    })
    return total
```
安装 Modular 的 Mojo SDK 后，用 `mojo run example.mojo` 即可执行；想把 Python 提速，可把热点写成 `fn` 再在 `.py` 里 `from example import parallel_sum` 调用。注意 Mojo 仍处早期，生态（尤其第三方库）远不及 Python 成熟，适合在性能敏感且可控的模块中小步试水。

**▌ 对比与选型**：
| 维度 | Mojo | Python+C扩展 | Rust |
| 上手成本 | 低（类 Python） | 中（需学 C/FFI） | 高 |
| 热点性能 | 高（编译原生） | 高（C 部分） | 极高 |
| 生态成熟度 | 早期 | 极成熟 | 成熟 |
| AI 框架整合 | 进行中 | 完整 | 部分 |
选型：AI 基础设施团队可小步试水 Mojo 重写推理热点；通用业务与科研仍以 Python 为主，性能瓶颈用 pyo3/Rust 桥接更稳，待 Mojo 生态成熟后再扩大使用面。
