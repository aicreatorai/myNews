# 移动开发

### 1. 【Swift Testing 框架落地：XCTest 迁移与结构化测试新范式】

> 📍 **导语**：Apple 在 WWDC26 的 Session 267《Migrate to Swift Testing》中系统给出了从 XCTest 平滑过渡到现代测试框架的官方路径，Xcode 27 起测试框架互操作（Interoperability）默认开启，Swift Testing 的断言失败可在 XCTest 中冒泡、反之亦然。对仍停留在 XCTestCase 继承体系的存量 iOS 项目而言，这意味着无需推倒重来即可引入 @Test、#expect、参数化测试与 Traits 标签体系，是 2026 年 Swift 工程化最值得落地的改动之一。

---

**📱 深度报道**

**▌ 更新全景**：Swift Testing 基于 Swift 宏（Macro）重构了测试体系，核心由 @Test、@Suite、#expect、#require 四个原语构成，彻底取代 XCTest 中数量繁多、语义重复的 XCTAssertEqual / XCTAssertTrue / XCTAssertNil 等数十个 API。在 Xcode 27 中，测试框架互操作提供 Limited、Complete、Strict、None 四种模式：Limited 仅告警跨框架问题，Complete 保留错误并默认用于新项目，Strict 会对跨框架问题直接崩溃，None 临时关闭报告。Swift 6.4 工具链下，旧版 Swift Package 默认启用 Limited 模式。值得强调的是，Swift Testing 与原生 Swift Concurrency 深度整合，测试函数可直接 async/await，Sendable 违规会在编译期被发现。

**▌ 技术细节深解**：最直观的变化是断言语法统一。以下是一个从 XCTest 迁出的真实对照：
```swift
// Before (XCTest)
final class PriceTests: XCTestCase {
    func testDiscountedTotal() {
        XCTAssertEqual(Price.total(subtotal: 20, discount: 5), 15)
    }
}
// After (Swift Testing)
import Testing
@Test func discountedTotal() {
    #expect(Price.total(subtotal: 20, discount: 5) == 15)
}
```
参数化测试用 @Test(arguments:) 自动展开为独立子测试，失败时精确定位到具体输入；Traits 体系则让大规模项目可按标签过滤：
```swift
extension Tag { @Tag static var paywall: Self }
@Suite("Paywall VM") struct PaywallTests {
    @Test(.tags(.paywall), .timeLimit(.minutes(1)))
    func resolvesProduct() async throws { /* ... */ }
}
```
CI 中可用 `swift test --filter-tag paywall --skip-tag slow` 实现分层执行，这是 500+ 测试用例项目的效率关键。

**▌ 开发者迁移指南**：官方推荐增量迁移而非整体重写。同一测试 Target 可同时容纳 XCTest 与 Swift Testing，但 Swift Testing 测试不能塞进 XCTestCase 类内部。保留 XCTest 的场景包括 UI 自动化（XCUIApplication）、性能测试（XCTMetric）与 Objective-C 异常测试。落地节奏建议：新测试一律用 @Test 写；改动到的旧文件顺手迁；UI 与性能指标测试留在 XCTest。CI 侧注意 Fastlane scan 需升级到 2.225+，GitHub Actions 使用 xcodebuild 时加 -skipMacroValidation 避免宏签名弹窗，Swift Testing 默认并行执行会暴露共享可变状态的隐患，应修状态而非关并行。

**▌ 生态与竞品对比**：相较 JUnit（Android）、Jest（前端），Swift Testing 的宏驱动语法与编译期诊断更现代；与 XCTest 是渐进替代关系而非竞品。社区活跃度高，Hacking with Swift、Swift 官方论坛与多家中文公众号已产出迁移速查卡，国内团队采用门槛低。

---

**🤖 开发研判**

🔮 **技术趋势**：测试框架从"类继承 + 命令式断言"走向"宏 + 表达式断言 + 标签化组织"，与 Swift 6 严格并发检查形成合力，是 Apple 平台工程化成熟度的标志。

📊 **开发者决策影响**：所有新项目应立即采用 Swift Testing；存量项目本季度即可启动增量迁移，风险可控。对招聘市场，掌握参数化与 Traits 的工程师更受青睐。

⚠️ **适配风险**：并行执行可能触发隐藏的测试顺序依赖；XCTest 与 Swift Testing 混用若模式配置不当会出现吞错。UI 与性能测试短期内无法迁出，需双框架长期共存。

💡 **学习优先级**：先掌握 @Test/#expect 与参数化，再学 Traits/标签过滤，最后理解互操作模式与 CI 集成。推荐 WWDC26 Session 267 与 theswiftk.it 迁移指南。

### 2. 【HarmonyOS 7 ArkUI 引入沉浸式光感与 ArkData 数据能力升级】

> 📍 **导语**：华为在 HarmonyOS 设备开发文档与"新增和增强特性"清单中披露，ArkUI 自 API 版本 26.0.0 起引入"沉浸式光感（Immersive Light Sense）"体验体系，同时 ArkData 在 HarmonyOS NEXT 阶段对 Preference、RDB、UDMF 等模块做了大量新增与增强。对鸿蒙原生开发者而言，这两项更新分别补齐了高级视觉表达与本地结构化数据能力，是 HarmonyOS 7 应用质感与数据层升级的关键抓手。

---

**📱 深度报道**

**▌ 更新全景**：沉浸式光感由"沉浸式系统材质（Immersive System Material）"与"沉浸式空间动画（Immersive Spatial Animation）"两大能力组成，跨越从视觉层到感知层的全链路。系统材质提供从 ULTRA_THIN 到 ULTRA_THICK 五档风格，自动随系统深浅色模式与设备算力调节；空间动画则包含非线性形变、边缘光流与粒子动画三类，分别作用于 AlertDialog、CustomDialog、ActionSheet、Menu、Slider 等组件。ArkData 方面，Preference 新增 BigInt、Object 类型存储与按 key 订阅变更；RDB 支持 BigInt、attach/detach、notContains、变更通知携带数据 ID、TS 同步 API，并新增 isReadOnly 配置；UDMF 预定义 UTD 类型由 80 种扩展到 120 种，并支持应用自定义 UTD。

**▌ 技术细节深解**：启用沉浸式光感只需声明开启，组件背景、边框、阴影即由系统材质统一管理：
```ts
// 开启后组件自动获得光感材质，无需逐项设置背景
@Component
struct MenuCard {
  build() {
    Column() {
      Text('菜单项')
    }
    .backgroundBlurStyle(BlurStyle.ULTRA_THICK) // 对应 THICK 材质
  }
}
```
RDB 全文检索与 sendable 能力是数据层亮点，新增 @ohos.data.sendableRelationalStore 模块使关系型数据库支持 sendable，可在并发任务间安全传递；RDB 还支持引入 fts（全文搜索引擎）动态库，适合笔记、文档类应用本地检索。

**▌ 开发者迁移指南**：沉浸式光感为增量能力，旧项目无需改动即可编译，新项目可在对话框、菜单、搜索框等场景按风格档位渐进启用，注意 ULTRA_THICK 多用于对话框、THIN 用于搜索框。ArkData 变更多为新增 API，存量代码兼容；但使用 isReadOnly、sendableRelationalStore、fts 动态库需将 compileSdk 提升到对应 API 26 版本，并验证低版本设备降级路径。

**▌ 生态与竞品对比**：相较 SwiftUI 的材质与 Material Design 3 的动态色彩，鸿蒙沉浸式光感更强调"光与影"的拟物质感与跨设备一致。社区侧，CSDN 鸿蒙开发者社区已整理出 ArkUI 增强特性清单，国内开发者适配热情高。

---

**🤖 开发研判**

🔮 **技术趋势**：鸿蒙正从"功能可用"走向"质感对标 iOS/Android"，沉浸式光感是设计语言成熟化的信号，预计将带动一批元服务视觉改版。

📊 **开发者决策影响**：新项目应把光感材质纳入设计规范；数据密集型应用可借 ArkData RDB 全文检索与 sendable 能力简化本地存储架构，降低对三方数据库的依赖。

⚠️ **适配风险**：光感效果依赖设备算力，低端机可能降档；ArkData 新 API 在 NEXT 之前的版本不可用，需做版本分支。过度使用 ULTRA_THICK 可能造成性能与耗电压力。

💡 **学习优先级**：先学 ArkUI 装饰器与状态管理，再攻沉浸式光感五档材质与空间动画，最后掌握 ArkData RDB/UDMF 新 API。推荐华为开发者联盟官方文档与 CSDN 鸿蒙社区。

> 📍 **导语**：Google 在 Android Developers 博客宣布，Gemini 3 Pro 模型现已接入最新版 Android Studio（Otter / Narwhal Feature Drop），Agent 模式正式进入稳定版，可为开发者处理添加功能、生成单元测试、修复缺陷等复杂多阶段任务。与此同时，新版内置 XR Android Emulator 与 Jetpack XR 项目范本，标志着 Android 开发首次拥有可落地的端到端 AI 代理与沉浸式应用开发底座。

---

**▌ 技术细节深解**：Agent Mode 的工作流体现"人主导、AI 执行"：

**▌ 开发者迁移指南**：升级到 Narwhal Feature Drop / Otter 3 即可启用，无需改动源码。建议团队在设置中配置 Gemini API Key 以获得长上下文；把 .idea 中的 Rules 入库共享。本地模型适合银行、医疗等敏感代码场景。注意 Agent 自动提交 PR 前务必人工 review，免费模型上下文短，大型项目优先 BYOK。

**▌ 生态与竞品对比**：相较 Xcode 27 的智能体编码升级与 GitHub Copilot，Android Studio 的 Agent Mode 更强调"跨文件批量改动 + Gradle 闭环 + 规则固化"，且本地/远程模型可选。Pocket FM 等早期采用者报告开发耗时节省约 50%，Kakao 借 Prompt API 将下单完成时间缩短 24%、新用户转化提升 45%。

### 4. 【微信小程序 Skyline 渲染引擎普及：跨端框架与性能新基准】

> 📍 **导语**：微信在 2026 年把自研的 Skyline 渲染引擎确立为新建小程序的强制推荐标准，逐步淘汰老旧 WebView 渲染。多端 SDK 已支持 Skyline，开发者可结合 Beta 版本体验。与此同步，uni-app、Taro 等跨端框架成熟，一套代码编译到微信、抖音、支付宝等多平台成为主流。对中小商家与跨端团队，这既是性能基准的跃升，也是开发成本结构的重构。

---

**📱 深度报道**

**▌ 更新全景**：Skyline 的核心是放弃浏览器 WebView 内核，改用类原生渲染管线。官方与第三方实测数据一致：首屏加载比 WebView 快约 66%，内存占用降 35%~50%（多页面共享一个渲染引擎实例），长列表滚动帧率稳定在 50fps 以上，setData 跨线程通信延迟降低一半以上。包体方面同等功能代码包体积缩小约 30%，首页打开稳定进入 200ms 内的秒开区间。多端 SDK 接入要求 Android SDK ≥ 1.2.0、iOS SDK ≥ 1.2.5，并在 project.miniapp.json 勾选 Skyline，Android 侧还需勾选 XWeb 模块。

**▌ 技术细节深解**：架构差异决定性能。WebView 是双线程——JS 跑在 AppService、UI 跑在 WebView，每次 setData 都要序列化跨进程传输；Skyline 改为 AppService + 独立渲染线程 + Raster 线程的三线程模型，直连高效数据通道。它解锁了 WebView 做不到的能力：
```js
// Worklet 把 JS 跑在渲染线程，动画不受主线程阻塞
worklet.runOnRenderThread(() => {
  // 手势协商、自定义路由动画
});
```
Worklet 动画丢帧率降低约 70%，手势协商让地图缩放与页面滚动不再打架，WXSS 预编译成二进制使运行时解析比 WebView 快 5 倍以上。迁移支持按页面或分包粒度开启，老项目从非关键页逐步切，新页面默认开启。

**▌ 开发者迁移指南**：Taro 开启需三条基线同时满足——Taro ≥ 3.6.0、微信开发者工具 ≥ 1.06.2308140、基础库 ≥ 2.29.0。注意 Skyline 只作用于微信小程序端，H5 等端渲染链不同；生命周期钩子触发时机有变，依赖旧时序的逻辑要迁到 Taro 页面级钩子。微信官方预警：老版本 WebView 小程序 2027 年起逐步限制流量分发，2026 年上新/改版门店与商城必须切 Skyline。

**▌ 生态与竞品对比**：相比 React Native、Flutter 的原生渲染，Skyline 是平台内渲染管线升级，无需替换框架即可获原生级体验。uni-app、Taro 借 Skyline 与条件编译把"一套代码多端发布"成本砍掉一半以上，成为中小企业首选，纯性能党才考虑 Flutter。

---

**🤖 开发研判**

🔮 **技术趋势**：小程序渲染正从"WebView 套壳"转向"类原生管线"，Skyline 与跨端框架融合将成 2026-2027 标配，WebView 旧栈进入淘汰倒计时。

📊 **开发者决策影响**：新小程序应直接以 Skyline 为基线；存量商城、门店类项目本季度排期迁移。跨端团队用 uni-app/Taro + 条件编译可省 40% 以上开发量，人力成本腰斩。

⚠️ **适配风险**：2027 流量限制是硬约束，不迁将失分发；Skyline 生命周期与 WebView 不同，老代码时序依赖易出隐性 Bug；低端安卓机需真机验证。

💡 **学习优先级**：先读微信开放文档 Skyline 支持指南，再练 Taro/uni-app 按页灰度，最后掌握 Worklet 与手势协商。推荐微信开放文档与 aiproducthub 实测。

### 5. 【React Native 新架构全面强制：Expo SDK 55 弃用旧桥接与迁移实战】

> 📍 **导语**：React Native 的新架构（New Architecture）已从"可选"变为"强制"。React Native 0.82 起彻底移除关闭开关，Expo SDK 55（基于 RN 0.83）成为最后可禁用新架构的版本之后的完全体，旧版 Bridge 架构将无法获得 iOS 27 兼容补丁。对仍停留在 RN 0.73 及更早版本的团队，2026 年 11 月被普遍视为迁移截止线，否则将面临用户可见的构建与兼容问题。

---

**📱 深度报道**

**▌ 更新全景**：新架构由两大支柱构成。TurboModules 用 JSI（JavaScript Interface）取代 Bridge 的 JSON 序列化，实现同步、带 C++ 类型安全的原生调用，原生调用开销从 Bridge 的 15~40ms 降到微秒级；Fabric 渲染器直接同步 JS 与原生 UI 树，支持并发渲染，消除复杂滚动与动画中的帧延迟。版本时间线：RN 0.76 默认开启新架构，0.82 移除关闭开关，Expo SDK 52 起新项目默认新架构、SDK 54 是最后可禁用版本、SDK 55 及以后完全运行其上。Expo SDK 58 已带 iOS 27 与 Xcode 27 支持并放弃 iOS 15 及以下。

**▌ 技术细节深解**：迁移中最常遇到的 Breaking Change 是 UIManager 直接调用失效，需改用 Reanimated 3+ 的 useAnimatedRef 与新 measure API：
```js
// 旧 Bridge 写法（新架构下不再工作）
UIManager.measure(findNodeHandle(ref), (x, y) => {});
// 新架构写法
import { useAnimatedRef, measure } from 'react-native-reanimated';
const ref = useAnimatedRef();
const m = measure(ref); // 返回 {x, y, width, height}
```
第三方库若无 TurboModule 支持将直接编译失败，迁移前务必在 React Native Directory 核对每个库的 New Architecture 状态；Objective-C 无 JSI 绑定的原生模块需迁移，这是耗时最长的部分。

**▌ 开发者迁移指南**：推荐序列——先在旧架构上升级到最新 SDK 并发布，再在开发构建中经 app.json 设 newArchEnabled: true，跑完整 QA（含支付墙、深链、推送、后台音频），经 EAS 内测一周后推广生产。切勿把 SDK 升级与架构切换合并一次做。Release 时用构建级特性开关而非运行时切换，可同时发新旧架构包到不同轨道比对崩溃率；OTA 更新在确认前保留旧架构，翻转标志时务必提升 runtime version。

**▌ 生态与竞品对比**：相较 Flutter 的 Impeller 统一引擎、KMP 的共享逻辑，RN 新架构的补齐使其在复杂动画与手势场景逼近原生。社区阻力主要来自三方库，但 Expo 官方兼容矩阵已覆盖首方模块，2026 年生态基本就绪。

---

**🤖 开发研判**

🔮 **技术趋势**：新架构是 RN 与原生体验鸿沟收敛的终局，Bridge 时代落幕。未来 RN 将更深度借力 JSI 与 C++ 类型安全。

📊 **开发者决策影响**：新项目无架构选择余地，直接新架构；存量项目若处于维护期且无人强制，可缓一两个 SDK，但依赖库弃用旧支持时应立刻迁。

⚠️ **适配风险**：第三方库无 TurboModule 支持会编译失败；Fabric 的 C++ 断言崩溃（props 与 spec 不匹配）需重点盯崩溃报告；架构无法运行时切换，回滚需预留旧架构包。

💡 **学习优先级**：先审计依赖库 New Architecture 状态，再学 TurboModules/JSI 与 Reanimated 3 迁移，最后掌握 EAS 灰度发布。推荐 React Native 官方 New Architecture 文档与 72Technologies 实战。

### 6. 【SwiftData 持久化框架：模型迁移与 CloudKit 云同步实战】

> 📍 **导语**：SwiftData 作为 iOS 17+ 的 Swift 原生持久化层，在 2026 年随 Swift 6.2 / iOS 26 进一步成熟，支持类继承、#Unique、#Index、CloudKit 同步与基于 VersionedSchema / SchemaMigrationPlan 的版本化迁移。对追求本地优先（Local-First）体验的 iOS 团队而言，如何用 SwiftData 既享受轻量迁移便利、又稳妥接入 CloudKit 跨设备同步，已成为生产落地的核心课题。

---

**📱 深度报道**

**▌ 更新全景**：SwiftData 用 @Model 标注类（自动生成 PersistentModel / Observable / Sendable），@Attribute 提供 .externalStorage、.unique、.spotlight、.allowsCloudEncryption 等选项，@Relationship 支持 deleteRule 与 inverse。查询用 @Query、#Predicate、FetchDescriptor。迁移分两层：轻量迁移（加带默认值属性、移除属性、用 @Attribute(originalName:) 重命名）自动完成；超出范围则需 VersionedSchema + SchemaMigrationPlan 做分阶段迁移，支持 .lightweight 与 .custom（带 willMigrate / didMigrate 闭包）。CloudKit 同步通过 ModelConfiguration(cloudKitDatabase: .automatic) 或 NSPersistentCloudKitContainer 启用。

**▌ 技术细节深解**：典型版本化迁移代码结构如下：
```swift
enum AppSchemaV1: VersionedSchema {
  static var versionIdentifier = Schema.Version(1, 0, 0)
  static var models: [any PersistentModel.Type] { [Entry.self] }
}
enum AppSchemaV2: VersionedSchema {
  static var versionIdentifier = Schema.Version(2, 0, 0)
  static var models: [any PersistentModel.Type] { [Entry.self, Tag.self] }
}
enum AppMigrationPlan: SchemaMigrationPlan {
  static var schemas: [any VersionedSchema.Type] { [AppSchemaV1.self, AppSchemaV2.self] }
  static var stages: [MigrationStage] { [migrateV1toV2] }
  static let migrateV1toV2 = MigrationStage.lightweight(
    fromVersion: AppSchemaV1.self, toVersion: AppSchemaV2.self)
}
let container = try ModelContainer(for: SchemaV2.Entry.self,
  migrationPlan: AppMigrationPlan.self)
```
CloudKit 同步默认采用"最后写入者胜"的冲突策略；SwiftData 在 2026 年仍未暴露应用层冲突解决钩子，合并发生在 NSPersistentCloudKitContainer 层。启用云同步只需在 ModelConfiguration 指定云数据库，无需自行打包模型：
```swift
let config = ModelConfiguration(
  schema: schema,
  cloudKitDatabase: .automatic) // 自动选择用户私有云数据库
let container = try ModelContainer(for: schema, configurations: config)
```
离线场景下 SwiftData 自动在联网后续传同步，开发者只需监听 NSPersistentStoreRemoteChange 通知刷新 UI，@Query 宏亦会自动刷新。冲突的工程化解法通常是"按字段存 modifiedAt 时间戳做字段级合并"或"追加式日志（类 CRDT）"，后者以存储与查询复杂度换取零冲突。

**▌ 开发者迁移指南**：CloudKit 顺序铁律——先在开发环境更新 CloudKit schema 并提升 Production，再提交 App 更新，否则引用新 schema 的记录会同步失败。生产库部署后字段不可删改，只能加，故 schema 应视作公开 API 设计。轻量迁移务必在真机用上一版本数据库实测；@Query 默认主线程抓取大数据集会阻塞，需用 fetchLimit 与 sortDescriptors 限制。后台批量导入应建独立 ModelContext 于后台 actor。

**▌ 生态与竞品对比**：相较 Core Data 的样板代码、Realm 的私有协议，SwiftData 以 Swift 原生语法与编译期安全取胜，但生产坑洼多在迁移与 CloudKit 边界。社区已形成 Local-First 实战共识：追加式（append-only）数据模型可天然规避冲突。在跨平台对标上，Android 侧对应 Room + DataStore，鸿蒙侧对应 ArkData 的 RDB/Preference，三者理念相近但 API 形态迥异，团队若做双端需各自适配。SwiftData 的 @Query 与 SwiftUI 深度绑定，是其在 Apple 生态内的独特优势。

---

**🤖 开发研判**

🔮 **技术趋势**：Local-First 与隐私优先成为 iOS 数据层主流，SwiftData + CloudKit 组合将持续增强，版本化迁移工具链是 Apple 下一步重点。

📊 **开发者决策影响**：新 App 应直接以 SwiftData 为持久化底座；Core Data 存量项目可渐进迁移。多人共享数据需评估 CloudKit 私有库是否够用，否则另选同步层。

⚠️ **适配风险**：迁移计划版本标识符不匹配会静默失效、导致数据损坏；CloudKit 生产 schema 不可回退；冲突解决能力缺失需靠数据建模规避。

💡 **学习优先级**：先掌握 @Model / @Query，再学 VersionedSchema 与 MigrationPlan，最后攻 CloudKit 同步与冲突建模。推荐 CoddyKit、3Nsofts 与 Smart Kiitös 实战文章。

---

### 7. 【鸿蒙端侧 AI 与意图框架：元服务接入 Intents Kit 实现智慧分发】

> 📍 **导语**：HarmonyOS 的 Intents Kit（意图框架）是一套系统级意图标准体系，把应用/元服务内的业务功能智能分发到小艺对话、小艺搜索、小艺建议等系统入口，这一过程即"智慧分发"。结合鸿蒙端侧 AI（轻量化盘古大模型、MindSpore Lite 推理、方舟引擎与星盾安全），开发者可在不切换应用的前提下，让用户以自然语言或模糊表达直接触发服务，是 2026 年鸿蒙原生智能的核心落点。

**📱 深度报道**

**▌ 更新全景**：元服务接入意图框架与传统应用一致，分"意向、开发、验证、上架"四步，提供习惯推荐、事件推荐、技能调用、本地搜索等方案。系统入口覆盖小艺对话、搜索、建议三大场景，当前开放旅游、视频、新闻、音乐等垂域。端侧 AI 侧，HarmonyOS 7 实现盘古端侧大模型 30B 参数落地，方舟引擎在 HDC 2026 搭载性能大模型、端侧推理延迟降 40% 以上；HMAF 2.0 智能体框架支持能力模块的注册、发现与编排，并首次开放 GUI 操控能力，使模块可像人一样操作界面元素。

```ts
@Component
```

**▌ 生态与竞品对比**：相较 Apple App Intents 把动作喂给 Siri/Shortcuts，鸿蒙意图框架更强调"服务找人"的场景化推荐与元服务免安装即点即用。星盾安全获 HPIC 端云全链路 AI 安全认证，敏感数据本地隔离优于纯云方案。

### 8. 【Android 端侧 AI 落地：Gemini Nano 经 ML Kit GenAI 接入与 LiteRT 推理】

> 📍 **导语**：2026 年移动端 AI 的关键转折是"端侧推理"从可选项变为默认项。Apple 以 Foundation Models 框架开放设备端模型，Google 则通过 AICore 系统服务把 Gemini Nano 暴露给 Android 应用，开发者经 ML Kit GenAI API 即可调用摘要、校对、改写、图像描述等能力；自定义模型走 LiteRT（原 TensorFlow Lite）与 MediaPipe。对 Android 团队，真正的问题不再是"上不上端侧"，而是"哪些任务留端侧、哪些回落云端"。

---

**📱 深度报道**

**▌ 更新全景**：Gemini Nano 运行在 AICore——Android 系统级服务，负责模型下载与更新，应用自身不打包模型，AICore 隔离每次请求且不保留输入输出。Android 应用经 ML Kit GenAI API 触及：Prompt API（自定义文本/多模态提示）、文章或对话摘要、短消息校对与改写、图像短描述、语音识别转写。能力上限由设备硬件与令牌限制决定，超限或老设备经 Firebase AI Logic 回落 Gemini Flash / Pro。自定义模型侧，Core ML（iOS）与 LiteRT（Android）承载分类、视觉、传感器等专用小模型，Wear OS 与 IoT 场景受益最大。

**▌ 技术细节深解**：ML Kit GenAI 的调用形态简洁，且天然离线、零边际成本：
```kotlin
// 通过 ML Kit GenAI 调用 Gemini Nano 摘要（示意）
val options = GenerativeModelOptions.Builder()
    .setModelName("gemini-nano")
    .build()
val model = GenerativeModel.get(options)
model.generate("把这段对话总结为三条要点：$input")
    .addOnSuccessListener { summary -> /* 端侧完成，无需联网 */ }
```
混合架构是 2026 共识：高频、隐私与延迟敏感任务（摘要、智能回复、分类、实体抽取、转写、本地数据语义检索）留端侧；需前沿推理或新鲜知识的长尾回落云端。跨平台（RN/Flutter）需经原生模块桥接，因为系统模型无 JS API，Expo Go 也无法直接调用。

**▌ 开发者迁移指南**：接 Gemini Nano 先确认设备支持 AICore 并启用；用 ML Kit GenAI 标准化 API 起步，避免自打包大模型。自定义模型用 LiteRT 量化（8-bit/4-bit）以适配 NPU/神经网络 API，注意小模型精度与设备覆盖的权衡。务必设计云端回落路径与 OTA 模型更新，使更好模型无需发版即可下发。

**▌ 生态与竞品对比**：相较 Apple Foundation Models（约 30 亿参数、原生 Swift API、支持工具调用与 Guided Generation），Gemini Nano 经系统服务共享、不膨胀 APK；Core ML 在 iOS 单平台性能无敌，LiteRT 跨平台成熟。Mendios 评测中 MobileNet 在 Pixel 8 推理约 8ms、iPhone 15 Pro 的 Core ML 约 3ms。

---

**🤖 开发研判**

🔮 **技术趋势**：端侧 AI 成为移动 OS 的内置能力而非外接聊天框，2026 年"先平台模型、后自定义、再云端"的决策序列已基本成型，混合路由是第一等架构关注点。

📊 **开发者决策影响**：Android 新功能应优先评估 Gemini Nano + ML Kit 是否满足，省去模型运维与隐私审查；敏感行业（金融、医疗）可用本地/远程模型可选项满足合规。

⚠️ **适配风险**：端侧模型仅覆盖新旗舰（NPU+内存门槛），长尾设备必回落云端；跨平台层无 JS API，需原生桥接且无法跑在 Expo Go；令牌与推理速度随设备波动。
