### 1. 【口喷鸡Blurt开源输入法：边操作边吐槽自动生成修复清单】

**导语：**
给编码 Agent 提反馈，最费劲的往往不是"说不清问题"，而是"说清问题还得配图、写复现步骤、标代码位置"。截一张图粘过去、再打字描述怎么触发、最后翻代码找可能出错的文件，一套下来十几分钟，还没开始真正修。开源的口喷鸡（Blurt）把这件事压缩成一个动作：你一边操作软件一边张嘴吐槽，它把语音、截图和屏幕文字揉在一起，自动整理成带截图、复现步骤和疑似代码位置的事项清单，还能直接交给 Claude Code、Codex 这类 Agent 按条去修。它是 AGIHunt 面向 Agent 时代做的多模态输入法工具，主打 Vibe Coding 场景。本篇从技术层拆解它的语音听写、截图标注、录屏走查与 Agent 修复闭环，帮你判断它值不值得常驻在工具栏里。

**它是什么：**
口喷鸡（Blurt）是一款开源的多模态输入法工具，定位是"Agent 时代的输入层"，服务于 Vibe Coding 这类需要频繁在人与机器之间递信息的场景。它把几种输入动作收进快捷键：按 fn 语音听写，字直接打进光标处，支持"说中文打英文"，也能一键把零散口述整理成清单；按 ⌥A 截图标注，框选后可画圈画框并同时语音描述，截图会悬挂在屏幕上、可拖拽发送；按 ⌥C 或 ⌥T 屏幕取字，对选不中的文字框选即 OCR 复制，或直接译成英文；按 ⌥V 语音备注，最长十分钟，适合速记；按 ⌥R 录屏走查，边操作边口头吐槽，Agent 会把过程拆成带截图、复现步骤、疑似代码位置的事项清单。事项能像刷短视频一样逐条审核，导出飞书多维表格、GitHub Issues 或 Markdown；选中一条还能让 Claude Code、Codex 按 git worktree 修复，改完标"待验证"，人确认后合并。它也提供 MCP 接口，任何 Agent 都能读写事项库。安装上，官网提供 Mac 版，也可把一行安装脚本交给编码 Agent 自动完成；默认用 macOS 自带听写即可运行，追求准确率可下载本机模型或填云端识别与润色服务的密钥。

**它解决了什么问题：**
给 Agent 报一个界面问题，传统流程要跨三道坎。第一道是表达成本：光说"这个按钮点了没反应"没用，得补截图、说清哪一步触发、大致哪段代码负责，信息在脑子、屏幕和编辑器之间来回搬运。第二道是上下文丢失：截图存在相册、复现步骤写在便签、代码位置靠记忆，几件事散落各处，Agent 拿到的是残缺描述，修不对再返工。第三道是闭环断档：问题报出去就石沉大海，没状态、没验证、没归档，下次遇到同类问题又得从头讲。口喷鸡用多模态输入压低第一道坎，语音、截图、屏幕文字一次采集，不必切换工具重组信息；用结构化事项清单解决第二道坎，每条自带截图、复现步骤和疑似代码位置，上下文是打包好的；用审核导出与修复闭环补上第三道坎，事项有"待验证"状态、可导出到团队工具、能直接派给编码 Agent 改，人只做确认。它把"汇报问题"从一项手工活，变成一段可复用的口述流程。

**核心原理拆解：**
它的链路可以拆成四层。第一层是输入采集层，把麦克风语音、屏幕截图、框选区域和 OCR 结果统一收进来；默认走 macOS 自带听写，也可切换到本机模型或云端识别加润色，准确率与隐私由你权衡。第二层是跨模态对齐层，这是关键：你在截图上画圈的同时说话，系统把这一时刻的语音描述与圈选区域绑定，再用屏幕取字补齐界面上选不中的文字，于是图、话、字指向同一个目标，而不是三份互不关联的材料。第三层是事项结构化层，Agent 把对齐后的素材整理成固定字段，即截图、复现步骤、疑似代码位置，生成可逐条审核的事项库，并通过 MCP 暴露给外部 Agent 读写，状态在"待验证"与"已合并"之间流转。第四层是修复执行层，选中事项后由 Claude Code、Codex 在独立 git worktree 里改动，避免污染主工作区，改完回到清单等人确认。理解这四层你会明白，它的价值在于把"人怎么描述问题"和"Agent 怎么接收问题"接在一起；而语音识别准确率与截图圈选的精度，直接决定事项清单能不能直接用。

**动手验证：**
建议按下面流程实测。第一步，只测语音听写：按 fn 说一段带专业术语的中文，看它能否正确落字、能否做到"说中文打英文"，这是最基础的可用性门槛。第二步，测跨模态绑定：打开一个你有问题的页面，按 ⌥A 框选问题区域并同时语音描述，检查生成的截图是否真的悬挂可拖拽、描述有没有跟对应区域绑在一起，而不是各说各的。第三步，走完整链路：按 ⌥R 录屏走查一遍复现过程，看 Agent 拆出的事项清单是否包含截图、复现步骤和疑似代码位置三样，缺哪样就说明哪一环没对齐。第四步，选一条事项派给 Claude Code 在 worktree 里修，确认改动没有落到主分支、改完状态是否变成"待验证"，再导出成 Markdown 或 Issues 看格式是否完整。验证要点：听写是否准、图文是否对齐、三要素是否齐、修复是否隔离。踩坑提醒：首次使用要在系统设置里手动开启麦克风与辅助功能权限；语音素材可能包含敏感信息，涉密界面别随手录屏；Agent 给出的"疑似代码位置"只是线索，合并前仍要人工过一遍改动。

**对比选型：**
| 维度 | 口喷鸡 Blurt | 普通截图加聊天 | 单纯录屏工具 |
|------|------|------|------|
| 输入 | 语音加截图加取字 | 手动贴图打字 | 只录画面 |
| 结构化 | 自动出事项清单 | 需自己写清楚 | 无清单 |
| 修复 | 接 Agent 隔离改 | 手动改 | 不涉及 |

### 2. 【Gemini Canvas草图转应用：拍张手绘就能跑的可编辑网页】

**导语：**
很多想法是先有画面、后有名字的：你在笔记本上画了个打卡格子、一个按钮、几行标签，心里清楚它该长什么样，却说不出每个部件叫什么，更不知道从哪行代码开始。2026 年 11 月 5 日，Google 更新了 Gemini 的 Canvas，把一张手绘草图的照片变成可运行、可编辑的应用：拍照上传、选 Canvas、问一句"能不能把这个写成应用"，几秒钟后预览窗口里就有一个能点的初版。免费登录用户也能试。本篇从技术层拆解它的图像理解、意图翻译、代码生成与迭代闭环，帮你看清这种"以画代入"的方式适合什么场景，以及分享链接那个容易被忽略的坑。

**它是什么：**
Canvas 是 Gemini 里用来写文档和代码的区域，最早于 2025 年 3 月 18 日上线，此前你要用文字描述应用，2026 年 11 月 5 日的更新把输入换成了照片：一张手绘的应用草图、习惯追踪器或游戏棋盘，都能作为起点。用法是三步：上传草图照片，在工具菜单里选 Canvas，输入"Can you code this app?"并发送，应用就出现在对话旁的预览窗口里。你可以在预览里点按钮、在输入框里打字试用，再用两种方式修改：一是对话，用大白话描述改动让 Gemini 重写代码；二是 Code view，逐行自己改。免费登录用户可用，Google AI Pro 与 Ultra 另加 Gemini 3 和百万 token 上下文，适合应用长成多文件之后。有一个必须知道的前提：用你草图搭出来的应用，拿到链接的人都能编辑里面的数据，分享前要想清楚。

**它解决了什么问题：**
从想法到原型有三个常见障碍。第一个是表达障碍：擅长视觉思考的人在说出"组件名"之前就知道界面该是什么样，纯文字描述反而把想法压扁。第二个是环境障碍：哪怕只想验证一个小点子，也要配编辑器、装依赖、起服务，门槛挡住了大量非开发者。第三个是跨度障碍：从一张草图到能点能改的东西，过去要么找人做，要么自己啃代码。Gemini Canvas 用照片当输入解决第一个障碍，画出来就能被读懂；用免配置、直接在预览里试解决第二个障碍，不必搭环境；用几分钟出第一版解决第三个障碍，让验证想法这件事变轻。它不追求替你做完整产品，而是把"脑子里那张图"快速变成一个能讨论、能点选的对象。

**核心原理拆解：**
它的工作流可以拆成四层。第一层是图像理解，模型读取照片里的布局、按钮和标签，这一步直接受草图质量影响：深色笔比浅铅笔清楚，白纸比横线纸好，给按钮写上"Add habit""Reset week"这类动作标签能显著提高识别率。第二层是意图翻译，把"Can you code this app?"这类自然语言指令翻译成生成任务，确定要产出的是可交互的应用而非静态图。第三层是代码生成与预览，系统写出代码并在对话旁渲染出可点击的预览，你可以即时试错。第四层是迭代闭环，改动走两条路：对话描述由模型改代码，或进代码视图手动改；出错时打开 Show console 看日志，把报错原文粘回对话让模型修。理解这四层你会明白，它的上限取决于草图有多清楚、改动描述有多具体；把"改一处"说成"把 Add habit 按钮变绿、移到列表下方、打卡后刷新仍在"，比笼统说"好看点"有效得多。

**动手验证：**
建议按下面流程实测。第一步，画一张习惯追踪器：每个格子代表一天，配一个打卡按钮，用深色笔在白纸上标注"Add habit"和"Reset week"，避免横线干扰。第二步，拍照上传，在工具菜单选 Canvas，输入"Can you code this app?"发送，观察预览里按钮和格子有没有按草图落位。第三步，在预览里实际点按钮、在输入框打字，刷新页面看打卡状态是否保留——这是判断它有没有把交互逻辑写进去的关键。第四步，用一条具体的后续指令迭代，例如把 Add habit 按钮变绿并移到列表下方、打卡后刷新仍保持、习惯名用更大字体，看模型是否逐项落实。第五步，故意触发一个错误，打开 Show console 看日志，把报错粘回对话让它修。验证要点：布局识别是否准、标注是否被读懂、状态能否持久化、报错能否修。踩坑提醒：分享链接会让人编辑应用数据，别放敏感内容；复杂草图先简化再上传；免费版的具体额度官方未公布，量大的任务先小规模试。

**对比选型：**
| 维度 | Gemini Canvas | 对话生成应用 | 低代码平台 |
|------|------|------|------|
| 输入 | 手绘照片 | 文字描述 | 拖拽组件 |
| 上手 | 免配置预览 | 需说清结构 | 要学平台 |
| 数据 | 链接者可编辑 | 看工具而定 | 权限可控 |

### 3. 【llama.cpp 1.0落地：本地文档助手升级前先跑回归测试】

**导语：**
本地文档助手跑得好好的，一升级底层推理运行时，答案就开始跑偏：检索到的段落对不上、内存占用突然翻倍，可你说不清是运行时变了还是模型换了。llama.cpp 1.0 把这件事摆到台面上：它和配套的 ggml 进入稳定语义版本管理，让"这次升级会不会破坏我的调用"有据可依。但稳定版本不等于输出不变，官方明确说它不承诺延迟、内存占用或回答行为保持一致。本篇从技术层拆解版本契约、接口边界、回归集与变更归因四层，帮你建立一套升级前的自检动作，让本地助手的每次改动都可回退、可解释。

**它是什么：**
llama.cpp 1.0 不是聊天应用，而是很多本地 AI 助手底层的推理运行时；这次发布把 llama.cpp 与 ggml 广泛使用的本地推理接口纳入稳定的语义版本管理。对你的意义在于：应用依赖的是运行时的接口、构建配置和跨硬件行为，语义版本让你能判断一次升级是修补、加功能还是破坏性变更。官方给出的判断清单很具体：你的应用实际调用了哪些接口、一次依赖更新该怎么分类、模型加载和典型请求是否照常、你的应用瞄准的是哪个发行版、在目标硬件和构建上行为如何。一个务实建议是生产环境用固定版本，而不是追踪最新开发提交，除非某个必要修复非它不可。还要记住一条边界：稳定版本管理承诺的是版本号含义清楚，不是延迟、内存或输出行为永远不变，所以验证这件事依然落在你自己身上。

**它解决了什么问题：**
本地助手的维护有三个老毛病。第一个是升级像开盲盒：运行时一更新，接口、构建配置、行为都可能变，出问题只能回滚碰运气。第二个是接口边界模糊：你以为只用了两三个函数，实际上依赖了一堆没意识到的行为，升级后悄悄失效。第三个是归因困难：同时换了运行时和模型，效果变差却不知道是谁的锅，下次还是重蹈覆辙。llama.cpp 1.0 用语义版本解决第一个毛病，让破坏性变更在版本号上就有信号；用"盯住你实际调用的接口"解决第二个毛病，把测试范围收敛到真正依赖的部分；用小回归集加单一变量原则解决第三个毛病，先动运行时跑一遍、再换模型跑一遍，谁导致退化一目了然。它把本地助手的升级从凭感觉，变成有清单、有对照的工程动作。

**核心原理拆解：**
它的管理逻辑可以拆成四层。第一层是版本契约，语义版本用版本号的变化提示是否含破坏性变更，让你在升级前先判断风险等级，而不是盲目追新。第二层是接口边界，重点是"你的应用实际调用的接口"，而非运行时暴露的全部能力；把依赖面收窄，回归测试才做得完。第三层是回归集，官方建议本地文档助手至少保留一组小样本，覆盖文档检索、答案生成和峰值内存三个维度，升级前后各跑一次做对照。第四层是变更归因，每次只改一个变量，先升运行时、再换模型，并在目标硬件与构建上分别验证，这样才能把退化定位到具体改动。理解这四层你会明白，稳定版本带来的不是"免测"，而是"可判断、可对照、可回退"；真正保住体验的，是你自己维护的那组回归样本。

**动手验证：**
建议按下面流程实测。第一步，记录当前锁定的 llama.cpp 版本和你应用实际调用的接口清单，这是后续对照的基线。第二步，搭一个很小的回归集：一份固定文档、一条固定检索问题、一次固定生成请求，并记录峰值内存，跑一遍存下结果。第三步，先只升运行时到 1.0 的固定发行版，模型不动，重跑回归集，看检索、生成、内存三项是否出现明显退化。第四步，再把模型作为单一变量替换，重跑同一组回归，判断变化来自模型还是运行时。第五步，在目标硬件和构建配置上各确认一次行为一致，避免只在开发机上通过。验证要点：接口是否仍兼容、检索生成是否稳定、内存是否可控、退化能否归因。踩坑提醒：稳定版本不承诺延迟和输出行为不变，别把"能跑"当成"没变"；生产环境用固定版本而非最新提交；每次改动都保留可回退的版本，出问题能立刻切回去。

**对比选型：**
| 维度 | 固定版本加回归 | 追最新提交 | 只用云API |
|------|------|------|------|
| 可回退 | 有基线可切 | 难定位 | 由厂商管 |
| 成本 | 本地可控 | 本地可控 | 按量计费 |
| 验证 | 自己跑回归 | 靠运气 | 无需自测 |

### 4. 【Graphed UGC Studio：用Agent批量产出竖屏视频广告】

**导语：**
短视频广告要测的是"哪句话让人停下手指"，可每试一版脚本都意味着写稿、找人、录制、剪辑一轮下来，创意还没验证完，预算先烧掉大半。Graphed 推出的 UGC Studio 想把这个循环压扁：它是一个能挂在 Claude、ChatGPT、Cursor 上的 Agent 技能，从你的网站读懂产品、写出广告脚本，再渲染成竖屏口播头像视频，官方口径约每三十秒四美元八。对需要大量测试短形式创意的团队来说，这相当于不用预约创作者就能先跑出一批变体。本篇从技术层拆解它的网站理解、脚本生成、渲染合成与批量变体链路，帮你判断它适合放在投放流程的哪一段，以及成本该怎么算才不失真。

**它是什么：**
UGC Studio 是 Graphed 发布的一个技能，可运行在 Claude、ChatGPT 和 Cursor 等 Agent 环境中。你给它一个网站，它先读懂页面上的产品信息，写出广告口播脚本，再渲染成竖屏的口播头像视频，也就是常见的 speaking-head 风格。成本方面，公开信息给的是约每三十秒视频四美元八，这个价格让它在"批量出创意变体"这件事上有吸引力：不必为每个版本单独预约创作者和拍摄档期。它面向的是需要高频测试短形式广告的营销和内容团队，尤其适合先把一批便宜的变体跑出来、筛出有效方向再考虑精制的流程。要清楚它的定位是快速出量大批量素材，而不是替代完整的品牌制作，搞清楚这点才不会用错地方。

**它解决了什么问题：**
批量试广告创意有三个卡点。第一个是脚本与制作割裂：写文案的人对着空白页憋脚本，拍视频的人再照着念，中间反复沟通，一版改动要来回好几轮。第二个是单条成本高：请创作者、约场地、录制剪辑，每条都按人力计价，导致团队不敢多试，只敢押几个"看起来稳"的方向。第三个是变体出得慢：营销要测的是钩子、口吻、卖点排序的不同组合，可传统流程一次只能出一条，测完一轮已经过了窗口。UGC Studio 用网站驱动脚本把第一个卡点接上，产品信息从页面来，不必从头口述卖点；用按秒计价把第二个卡点摊薄，先出便宜版本再决定要不要精修；用批量变体解决第三个卡点，同一卖点能快速跑出多版对照。它把创意测试从重制作，变成轻量、可并行的尝试。

**核心原理拆解：**
它的链路可以拆成四层。第一层是网站理解，Agent 读取产品页并抽取卖点、定位和语气，这一步的质量取决于页面信息是否清晰结构化，页面写得含糊，脚本也跟着含糊。第二层是脚本生成，按短广告的结构组织开头钩子、痛点、卖点和行动号召，产出可直接念的口播稿。第三层是渲染合成，把脚本转成竖屏口播头像视频，涉及口型、字幕和画面节奏的对齐。第四层是批量变体，围绕同一产品更换钩子和口吻，一次生成多版用于对照测试。理解这四层你会明白，它省下的是"从文案到成片"的制作人力，而策略层面的卖点选择仍要人来定；另外那每三十秒的报价只是单价，衡量成本要看"跑出一条能用的广告"总共花了多少，把失败的变体也算进去。

**动手验证：**
建议按下面流程实测。第一步，挑一个信息写得清楚的产品页，把链接交给挂在 Claude 上的技能，让它先只出脚本，检查卖点有没有抓对、有没有把页面没说的功能编进去。第二步，渲染一条三十秒样片，记录实际花费，确认它与公开报价是否一致。第三步，围绕同一产品换开头钩子和口吻，再出两到三版，把几条摆在一起看差异是否真的落在你想测的变量上。第四步，检查成片的口播与画面是否同步、字幕有没有写错产品名，这些小错在批量里会被放大。第五步，先小批量投一轮，看哪一版的完播和转化更好，再决定要不要对胜出版本做精制。验证要点：卖点是否准确、单价是否真实、变体是否有效、成片是否可用。踩坑提醒：口播头像涉及肖像与代言合规，商用前确认授权；公开价格只是参考口径，别直接当成你团队的真实成本；先用小批量试水再放量。

|------|------|------|------|
| 出量 | 批量变体快 | 一条一轮 | 偏单条创意 |
| 成本 | 按秒计价 | 人力为主 | 按量计费 |
| 脚本 | 从网站生成 | 人工写 | 需另写 |

### 5. 【Notion AI长时Agent：后台任务跑24小时还帮省九成积分】

**导语：**
知识库接了 AI 之后，最让人憋屈的往往不是它不会做，而是做一半就停、跑起来积分飞涨、想连个外部工具还得手工倒腾。Notion AI 的一轮更新把这三件事一起摆上桌：单个任务交给自主 Agent 后可以连续跑最长二十四小时；智能模型路由按任务挑选合适模型，官方宣称能把积分消耗压低九成；同时支持 MCP，可以连接 HubSpot、Cursor 等一百五十多个外部工具。本篇从技术层拆解它的长任务编排、模型路由、外部连接与知识上下文四层，帮你判断哪些工作适合丢给后台长跑、哪些仍需人在关键节点把关，也提醒你厂商口径的省钱幅度得自己核算。

**它是什么：**
Notion AI 这次更新包含三项能力。第一项是长时自主 Agent，单个任务最长可连续运行二十四小时，适合那种资料量大、步骤多、没法一次聊完的活。第二项是智能自动模型路由，系统按任务复杂度选择模型，目标是减少积分消耗，官方给出的说法是最高可省九成，注意这是厂商口径，不是独立实测。第三项是支持模型上下文协议，也就是 MCP，让 Notion 工作区能以标准方式对接一百五十多个外部工具，举例包括 HubSpot 和 Cursor。三者叠加的意义在于：知识库不再只是一个会被问答的仓库，而能变成一个后台持续干活、按成本挑模型、还能把手伸到外部工具的协作节点。它面向的是已经把资料沉淀在 Notion、又希望自动化往前再走一步的团队。

**它解决了什么问题：**
把知识库用成自动化中枢有三个拦路虎。第一个是任务长度受限：很多整理、汇总、跟进类工作不是一轮对话能完成的，Agent 跑到一半就停，人还得守着继续，等于没解放。第二个是成本不透明：不管任务难易都用最强模型，积分哗哗地烧，团队用几次就不敢用了。第三个是信息孤岛：知识在 Notion，项目在别处，客户数据在第三方工具，Agent 想串起来却没有标准通道，只能靠人搬运。长时 Agent 解决第一个拦路虎，把连续执行的时间窗拉到二十四小时；模型路由解决第二个，让简单任务用便宜档，复杂任务再上强模型；MCP 解决第三个，用统一协议对接大量外部工具。它把 Notion 从"能问的知识库"推向"能后台执行的工作台"。

**核心原理拆解：**
它的机制可以拆成四层。第一层是长任务编排，Agent 在后台推进任务并维护状态，使跨时段、多步骤的工作得以连续进行，但长跑也意味着偏离方向的风险累积，需要明确的验收标准和人工检查点。第二层是模型路由，系统按任务复杂度分配模型以节省积分，这里要清醒：九成是官方宣称的最优情形，真实节省取决于你的任务结构，简单任务占比越高越接近这个数。第三层是外部连接，MCP 提供标准化接口，把 Notion 与外部工具连起来，避免为每个工具单独写集成。第四层是知识上下文，Notion 里的页面作为背景材料供 Agent 引用，资料的组织质量直接影响产出。理解这四层你会明白，它的强项是让知识库动起来，而"省钱"和"不跑偏"都要靠你设定边界：给长任务明确的完成标准，给成本宣称留一个实测对照。

### 6. 【Factory Droid Script Mode：一次脚本跑完上百次工具调用】

**导语：**
让 Agent 干活，慢往往不是慢在"想"，而是慢在"一次次开口要工具"：读一个文件发一次请求，查一次数据库再发一次，几十步下来大半时间花在来回往返和重复计费上。Factory 推出的 Droid 1.0 想把这个开销一次性砍掉：它引入 Script Mode，让 Agent 不再逐个发工具请求，而是执行一段脚本，在单次模型请求里完成上百次工具动作。官方基准称效率最高提升约两成，运营成本也更低。本篇从技术层拆解它的工具抽象、脚本执行、错误定位与 SDK 集成四层，帮你看清它真正省的是什么、什么场景下反而要谨慎，以及如何用可控的方式验证收益。

**它是什么：**
Droid 1.0 是 Factory 推出的 Agent 运行引擎，核心是名为 Script Mode 的程序化工具调用方式。传统模式下，Agent 每用一次工具就要和模型往返一次；Script Mode 改为让 Agent 写并执行脚本，在一个脚本里完成数百次工具动作，从而减少模型往返次数和相应的延迟与费用。Factory 给出的基准结果是效率最高提升约两成，同时降低运营成本，不过这是厂商在自身基准下的口径，迁移到你的任务还要实测。集成方面，团队可以通过 Droid SDK 把它接入桌面、终端或自研应用，不必局限于某一个界面。它面向的是工具调用密集、步骤高度重复的场景，比如批量改配置、批量整理文件、跨系统对账这类"动作多、决策少"的活，理解这个定位有助于判断它能不能帮到你。

**它解决了什么问题：**
程序化调用要解决三个问题。第一个是往返开销：每次工具调用都要模型参与一次，延迟叠加、费用叠加，步骤越多越明显。第二个是重复劳动：很多自动化任务的步骤是固定的，却要模型一步步重新决定，既慢又容易在中间走偏。第三个是复用困难：一套跑通的流程往往绑死在具体对话里，换个任务又得从头来。Script Mode 用脚本把多次动作收进一次执行解决第一个问题，往返少了，延迟和费用自然下降；用"脚本即流程"解决第二个问题，固定步骤写进脚本，模型只管关键决策；用可保存、可调用的脚本单元解决第三个问题，同一套流程能在不同任务里复用。它把 Agent 从"边想边做"，补上"想清楚后一口气做完"的能力。

**核心原理拆解：**
它的机制可以拆成四层。第一层是工具抽象，把各类工具调用包装成脚本可编排的单元，这是程序化调用的前提。第二层是脚本执行，Agent 在单次请求里运行脚本、连续完成数百次动作，省下的是模型与工具之间的往返开销，而不是模型推理本身，所以收益在动作密集的任务上最明显。第三层是错误与定位，脚本一次性跑很多步，中途出错必须能定位到具体动作并支持重试或回滚，否则一个错误会污染整批结果。第四层是 SDK 集成，通过软件开发工具包把能力接进桌面、终端或自研应用，便于嵌入现有工作流。理解这四层你会明白，它真正的价值是把"多次往返"变成"一次执行"；但脚本写错时影响也会被放大，因此先在只读或可回滚场景试用，比一上来就对生产数据动手要稳妥得多。

**动手验证：**
建议按下面流程实测。第一步，挑一个动作密集但只读的任务，比如批量读取一组文件并统计信息，分别在普通模式和 Script Mode 下各跑一次，记录耗时和模型费用。第二步，对比两组数字，看往返减少是否真的带来下降，并把官方约两成的提升幅度当成参考而不是承诺。第三步，故意在脚本里放一个错误步骤，观察能否定位到具体动作、失败后是否影响前面已完成的动作，检验错误处理能力。第四步，用 SDK 在终端里把同一脚本接进你自己的命令行流程，确认集成不是只停留在演示界面。第五步，确认脚本可以保存复用，换个数据集跑同一套动作是否照常工作。验证要点：耗时费用是否下降、错误可否定位、SDK 是否可用、脚本能否复用。踩坑提醒：官方提升幅度来自自身基准，别直接套到你的任务；脚本影响面大，先只读后写入、先小批后大批；涉及破坏性动作时保留回滚方案。

|------|------|------|------|
| 调用 | 单脚本数百次 | 每次往返一次 | 无模型决策 |
| 适合 | 动作密集任务 | 需逐步决策 | 流程完全固定 |
| 风险 | 错误被放大 | 慢但可控 | 需自己写逻辑 |
