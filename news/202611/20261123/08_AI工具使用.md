### 1. 【T3 Code v0.1.7：子代理审批收进父线程的开源控制台】

**▌ 导语**：2026年11月，多个本地编程智能体同时开工已成常态，但"谁批谁的任务"成了新麻烦。开源项目 T3 Code 在11月4日放出 v0.1.7，把子代理审批收进父线程，管理员还能用 Windows 组策略统一下发客户端规则。它本身不写代码，而是当一层控制台，让你在一个线程里盯着 Claude Code、Codex、Cursor 等已认证宿主派出去的活。项目仍处于早期，作者在说明里直言可以预期会有问题，但方向很实在：并行执行的瓶颈正从"生成"转向"审批与治理"，谁能把这两件事做顺，谁就拿到下一阶段的效率红利。

**▌ 它是什么**：T3 Code 是 MIT 协议的智能体控制界面，定位是"管智能体的智能体"。v0.1.7 新增父线程里的子代理审批——派出子任务后，子代理的关键动作不必跳到新窗口确认，而是在父线程里排队等人点头；同时加入一次性任务调度、可分享的线程链接、按供应商或模型过滤用量、Windows 组策略，以及对 Kiro 的 beta 支持。它要求本机已安装并认证一个宿主，比如 Claude Code、Codex 或 Cursor，靠订阅或 API key 工作，可从桌面、网页或移动端操作。作者明确提醒项目早期，适合愿意尝鲜并自行兜底的团队，而不是拿来当免维护的生产基础设施。

**▌ 它解决了什么问题**：多智能体并行时最怕两件事。一是审批散落各处，人在几个终端和网页之间来回切，漏批一次就让子任务卡死或误执行；T3 Code 把审批收拢到父线程，等于给并行任务装了一个统一红绿灯。二是用量失控，几个代理各自调用不同模型，账单一片模糊；按供应商与模型过滤用量，让消耗第一次变得可拆解。可分享线程链接解决"我把进度发给同事看"的协作痛点，对方点开链接就能跟进而不必装全套环境。Windows 组策略则让管理员一次性下发客户端规则，不必逐台机器配置。它不替代宿主，而是补上宿主普遍缺的那一层：人群协同、权限收敛与可审计。

**▌ 原理拆解**：核心是把"线程"做成权限与审计的单位。父线程持有全局上下文和审批队列，子代理以子线程形式挂在下面，只拿到完成自己那一小块所需的最小上下文；凡涉及写文件、执行命令、对外提交等动作，子线程先把意图上报，父线程按预设规则决定自动放行还是挂起等人。一次性调度让"只在某个时间点跑一次"的任务不必常驻后台，跑完即销毁，减少资源占用与误触发。按供应商与模型过滤用量，本质是在调用层加了一层标签与计量，把不同宿主的账单口径先归一再看差异。Windows 组策略把客户端规则下沉到操作系统管理通道，适合公司设备统一管控。Kiro beta 则说明它在往多宿主兼容走，避免绑死在某一家。

**▌ 动手验证**：第一步在本机装好并登录一个宿主，确认订阅或 API key 可用，再部署 T3 Code 控制端。第二步建一个父线程，派两个只读子任务——比如"列出某仓库里所有待办注释"和"统计某目录的文件类型"，故意把其中一个设为需要审批，观察它是否真的在父线程里排队、而不另开窗口。第三步点开可分享链接，用另一个浏览器无登录访问，确认同事能否只看不改地跟进进度。第四步设一条一次性调度，让某个任务在指定时间跑一次，事后检查是否没有重复执行。第五步切到用量过滤，按供应商和模型分别看消耗，核对是否与宿主的账单口径一致。全程记录审批平均等待时间，和没有控制台时对比；若等待反而变长，说明把太多低风险动作也设成了需审批，应放宽自动放行范围。

**▌ 对比选型**：如果你是单人开发、一次只跑一个代理，这层治理是多余的，直接用宿主自带的界面更轻。它适合的是已经把多个本地代理铺开、又需要统一审批与审计的小团队。与 IDE 内置的多代理面板相比，它更偏控制面而非编写面，好处是不绑定某一家编辑器；与自建脚本调度相比，它省掉重复造轮子，代价是项目早期、文档薄、可能有问题，生产环境要留人工兜底。选型时先看三件事：你的宿主是否在支持列表、审批能否按动作粒度配置、用量数据能否导出对账。若这三点不满足，宁可继续用各宿主原生界面，等它成熟再接，别为一个控制台引入新的故障点。

### 2. 【agent-desktop v1.2.0：把桌面操控开放成MCP工具】

**▌ 导语**：让 AI 操作桌面，常见做法是截图给模型看、再用坐标去点，慢且容易被界面变化骗到。Vercel 的 agent-desktop 在11月5日更新到 1.2.0，把56个操作命令通过 stdio 暴露成 MCP 工具：带 MCP 客户端的智能体可以直接读系统无障碍树，拿到的是 JSON 结构，再按元素引用操作，而不是靠像素匹配。这把"看屏幕"换成了"读结构"，对做图形界面自动化的团队是个拐点。它本身不含模型和智能体循环，只提供可靠的手和眼，正好补上许多智能体"能想不能做"的短板。

**▌ 它是什么**：agent-desktop 是一个桌面控制服务器，1.2.0 新增 agent-desktop mcp stdio 服务器，把原有的56个命令行操作包装成标准 MCP 工具，任何兼容 MCP 的客户端都能按名字调用。同时加入 --stdin 输入，把敏感文本放进标准输入而不是进程参数，避免密钥出现在命令行历史里；macOS 端新增容器列表的行选择。运行需要 macOS 13 以上、Windows 10 1809 以上或 Ubuntu 24.04 以上，并授予系统无障碍权限，被调用的应用也要暴露可用的无障碍树。它不自带模型或循环，只负责三件事：读树、定位、执行，把判断交给外面的智能体。

**▌ 它解决了什么问题**：它解决截图式桌面自动化的三大痛点。一是脆弱，按钮位置一变、分辨率一换，坐标就失效；读无障碍树拿的是语义元素，应用换皮肤不影响定位。二是慢，截图、传图、模型识别一整套链路延迟高，而 JSON 树可以直接被客户端解析，省掉图像往返。三是泄密，把密钥写在命令行参数里会留在 shell 历史与进程列表，--stdin 让敏感文本走管道进来，用完即散。对需要跨多个原生应用批量操作的场景，比如批量填表、批量导出、跨应用搬运数据，它把人肉点击变成可编排、可复用的工具调用，一次调通就能反复跑，而不是每次重新训练模型看一遍屏幕。

**▌ 原理拆解**：关键在三层转换。第一层是权限与采集：拿到系统无障碍权限后，把当前窗口的控件层级、名称、状态序列化成 JSON，相当于给桌面生成一份可查询的语义快照。第二层是工具化：56个命令按 MCP 规范暴露，每个有明确的输入输出，客户端不必自己拼 shell 命令；元素引用只在当前快照内有效，避免跨快照误用导致点错控件。第三层是执行与回流：客户端拿到引用后发出点击、输入等动作，服务器执行并把结果回传，形成闭环。1.2.0 的 --stdin 把敏感输入从参数位挪到标准输入，属于执行层的隐私加固；macOS 行选择则解决列表容器里"到底选哪一行"的歧义。三层都不涉及智能决策，因此稳定性和可测试性都比较好。

**▌ 动手验证**：第一步在 macOS 或 Windows 机器上装好 1.2.0，给终端授予无障碍权限，用一个熟悉的应用打开测试窗口。第二步启动 MCP 服务器，用支持 stdio 的 MCP 客户端连上，先只调用"列出可用工具"，确认56个命令都被正确注册。第三步调用读取无障碍树的工具，把返回的 JSON 存下来，找到目标按钮的名字和引用，确认它和屏幕上的控件一一对应——这一步是验证"读结构"是否可靠的关键。第四步执行点击或输入，用 --stdin 传入一段敏感文本，事后检查 shell 历史和进程列表里是否留有明文。第五步故意改变窗口尺寸再读一次树，看元素引用是否仍能定位；若失败，说明应用没有暴露稳定的无障碍树，应换应用或退回人工。全程记录一次跨应用操作的耗时，和截图方案对比。

**▌ 对比选型**：和纯截图加坐标的方案比，它在界面稳定、控件语义清晰的应用上又快又稳，但前提是应用愿意暴露无障碍树；一些自绘界面的应用树是空的，这时它反而无能为力。和传统 RPA 工具比，它更偏开发者友好的协议层，不提供录制回放和流程设计器，学习门槛在 MCP 客户端一侧。选型时先确认三件事：目标应用的无障碍树是否可读、你的客户端是否支持 stdio MCP、部署系统版本是否在支持列表内。若只是偶尔操作桌面，系统自带快捷键和几行脚本更省事；一旦要把它接进智能体反复调用，这套"读树—引用—执行"的协议化方案才显出长期价值。

### 3. 【Antigravity Orchestrator：贵模型规划审查便宜模型写代码】

**▌ 导语**：编程智能体越跑越长，一个问题开始刺眼：贵的模型全包全程，成本高；便宜的模型独自扛复杂任务，又容易卡住。Google 在11月18日为 Antigravity 加入 Orchestrator 模式，把角色拆开——Neon 负责规划与审查，Hydrogen 负责写代码、跑测试，卡住时再交回 Neon。官方说在默认 High 思考档下，每任务成本比 Carbon 低约三成。它不等于新模型本身，而是一种把模型放进流水线的分工方式，值得任何按任务付费的团队认真算一笔账，也提醒大家别再默认"一个模型干到底"是最优解。

**▌ 它是什么**：Antigravity 是 Google 的编程智能体工作环境，提供应用、命令行与 IDE 扩展三种入口。11月18日起，在 AI Pro 与 Ultra 订阅里，Neon 成为新对话的默认模型；Orchestrator 模式则进一步明确分工：Neon 先拆解任务、给出计划，并在关键节点审查；更便宜的 Hydrogen 接管具体编辑与测试执行；一旦 Hydrogen 判断自己卡住，控制权交回 Neon 重新规划。Antigravity 内可用上下文最高到512K token。免费版和 AI Plus 订阅用不到这套组合。它的本质是把"一个模型干到底"改成规划者与执行者分离，让每个模型只做自己性价比最高的那一段。

**▌ 它解决了什么问题**：它解决按任务付费场景下成本与可靠性的拉扯。全用强模型，简单改动也在烧高价 token；全用便宜模型，遇到需要权衡架构或调试死循环的任务就反复兜圈。Orchestrator 让强模型只出现在最值钱的两个环节——开头定方向、结尾做审查，中间大量机械编辑与测试交给便宜模型，从而把单位任务成本压下来。卡住回退机制则补上便宜模型能力不足的短板：不是让它硬试到底，而是把上下文交回规划者重新拆解。对要批量处理中小改动、又必须保证交付质量的团队，这相当于给流水线配了一个便宜但可靠的工头，既能压成本，又不至于把质量完全交给运气。

**▌ 原理拆解**：这套模式建立在"规划昂贵、执行便宜"的假设上。规划阶段，Neon 读取需求与代码上下文，输出分步计划与验收标准，这一步决定方向，错了后面全废，所以值得用强模型。执行阶段，Hydrogen 按计划逐步改文件、跑测试，它的上下文被限制在单个步骤所需范围，既省 token 也减少干扰。审查阶段，Neon 对执行结果做差异核对，发现偏离计划就打回。回退触发是关键设计：当执行者连续失败或检测到自己进入循环，主动把状态摘要交还规划者，避免在低能力模型上空转。512K 上下文上限让长任务的历史得以保留，规划者能带着前因后果重新决策，而不是从头猜一遍；这也是它比简单"大小模型轮流答"更耐用的原因。

**▌ 动手验证**：第一步确认订阅档位：AI Pro 或 Ultra 才看得到 Neon 与 Orchestrator，免费或 AI Plus 账号可跳过。第二步在 Antigravity 里新建一个对话，先单独用 Neon 跑一个中等复杂度任务，记下耗时与账单里的 token 消耗作为基线。第三步开启 Orchestrator，换成同类型任务，观察输出是否先给出计划、再进入执行、最后有审查结论，确认角色分工真的发生。第四步故意给一个含糊需求，看 Hydrogen 卡住时是否回退给 Neon 重规划，记录回退次数与最终结果是否仍可用。第五步把上下文拉长到接近上限，检查计划阶段是否仍记得前面几轮的决定。最后按同样任务跑三次取平均，对比单位任务成本是否接近官方所说的三成降幅；若没降，多半是任务太简单、规划环节占比过低，不值得这套分工。

**▌ 对比选型**：和全程一个强模型比，Orchestrator 在步骤多、执行重的任务上更省，但简单问答反而多了规划开销，不如直接用便宜模型。和全程便宜模型加人工审查比，它把审查自动化了，代价是必须信任规划者的判断；规划者一旦误判方向，后面执行得越快错得越远。和需要自己写调度脚本的多模型方案比，它省去编排工作，代价是绑定在 Antigravity 生态里，模型选择与上下文受订阅档位限制。选型时先算一笔账：你的任务里规划性决策和机械执行的比例如何，前者占比越高，分工收益越小；执行越重、重复越多，越适合这套模式。官方成本数字来自自家测量，务必拿自己的真实任务跑基线再决定切换。

### 4. 【Granola会议记录：把讨论变成带责任人的决策台账】

**▌ 导语**：会议里最容易丢的不是内容，而是"谁在什么时候之前做什么"。2026年11月的多份效率工作流清单里，Granola 被反复列为会议记录类工具的代表：它把录音转成文字，再自动整理出决策、行动项和待澄清的问题，人只需在会后核对一遍就能分发。和传统录音笔比，它的价值不在转写本身，而在把散乱讨论收敛成可执行的台账。对每周开十几场会、会后还要亲手整理纪要的人来说，这往往是最容易被低估的省时环节，也是把会议从"开完就散"变成"开完能追"的关键一步。

**▌ 它是什么**：Granola 是一款会议记录助手，开会时在后台录音并转写，结束后给出结构化纪要：做出了哪些决定、每项行动的责任人和截止时间、哪些问题还没定论。它通常通过日历接入会议，开始前提示参会者正在录音，结束后把结果交给人审阅。在多份2026年11月的工作流指南里，它和 Fathom、Fireflies 被归为同一类"会议到笔记再到任务"的工具，差别在于 Granola 更强调把对话组织成决策与行动点，而不是只给一份逐字稿。它解决的是这条链路里的第一环：完整、可回查的捕获，让后面的整理和分发有可靠的原材料。

**▌ 它解决了什么问题**：它解决三个老问题。一是记录失真：人工记纪要时边听边筛，常常漏掉争论中的关键前提；完整转写让人会后能回查原话，谁说过什么一目了然。二是行动项悬空：讨论完大家各散，没人说得清谁负责什么；自动抽取责任人加截止时间，把模糊共识变成可追踪条目。三是重复劳动：同一场会要同时写纪要、发回顾邮件、往任务工具里录条目；一份结构化结果可以分别喂给邮件和项目工具，不必重写三遍。它也划清了边界：AI 只做提取与起草，绝不替人编造截止时间或指派责任，凡有歧义的对话一律标为开放问题等人确认，把判断权留在人手里。

**▌ 原理拆解**：流程分四段。第一段是采集：经日历触发录音，转写成带时间标记的逐字稿，好处是任何结论都能回溯到原话。第二段是结构化抽取：模型在逐字稿上识别三类信息——明确决定、带责任人与期限的行动项、未决问题；判断依据是话语中的承诺与确认信号，而不是凭空推断。第三段是人审：主持人核对抽取结果，删掉误判、补上漏项，这一步不可省，因为语气和上下文常常决定一句话到底算不算承诺。第四段是分发：确认后的行动项进入任务工具，摘要发给参会者。指南里反复强调一条底线——不要让 AI 根据含糊对话发明截止日期或指派责任人，宁可留空让人补，也不能让虚假的确定性流进项目台账。

**▌ 动手验证**：第一步选一场真实会议，提前在日历里连好 Granola 并告知参会者正在录音，这是合规与信任的基本动作。第二步会后打开转写稿，随机挑三条结论，回听对应音频核对是否逐字准确，验证可回溯是否真的成立。第三步看自动抽取的行动项，逐条检查责任人、动作、截止时间三要素是否齐全；凡是从含糊对话里猜出来的期限，一律删掉改成开放问题。第四步把确认后的条目复制进你的任务工具，给每条补上负责人，再让助手起草一封简短的回顾邮件发给参会者，检查邮件里是否出现原文没有的承诺。第五步连续跑两周，统计每次会后整理耗时，和过去手写纪要对比。若抽取质量不稳，先改进会议习惯——发言时明确说谁在何时前做什么，比换工具更有效。

**▌ 对比选型**：和 Fathom、Fireflies 比，Granola 同样做转写与纪要，差异更多在交互与整理风格上，建议用你最常开的那类会议各试一次再定。和通用的录音加转写方案比，它多了结构化抽取与分发，省掉自己再问一遍助手的步骤；代价是要把会议内容交给第三方，敏感会议须先确认数据政策。和直接在通用助手里粘贴逐字稿比，它胜在自动化触发和原话回溯，通用助手胜在灵活、可随时改提示。选型时先想清楚三件事：你的会议是否允许录音、纪要最终要流向哪个任务工具、是否需要逐字回溯。若团队里有明确的保密要求，宁可用本地转写加人工整理，别把便利放在合规之前。
