### 1. 【Go 1.27 正式推出 encoding/json/v2：默认严格、反序列化提速 10 倍】

> 📍 **导语**：Go 1.27 起，标准库新增的 encoding/json/v2 与 jsontext 结束实验、正式可用。v2 默认拒绝非法 UTF-8 与重复键、字段名大小写敏感、nil 切片输出空数组，并把底层实现换成更快的零拷贝解码路径，反序列化最快可达旧版十倍。最关键是 v1 已改由 v2 实现，同一程序可渐进混用，升级几乎没有迁移成本。

---

**💻 深度解析**

**▌ 它是什么？**
encoding/json/v2 是 Go 官方团队历时一年多打磨的新一代 JSON 处理标准库，随 Go 1.27 正式进入标准库，同时提供底层的 jsontext 包用于精细控制令牌流。它并非简单修补旧版，而是重写了解码器与编码器：解码路径采用零拷贝扫描，直接在输入字节上做状态机解析，避免旧版反复分配临时对象与字符串；编码器则重排缓冲策略，减少系统调用。官方文章由 Michael Pratt、Joe Tsai 等人于 2026 年 11 月 4 日发布，明确说明 v2 与 v1 可在同一二进制中并存，旧包 encoding/json 的实际实现已经切换到 v2，因此即便不改动任何 import，程序也能自动获得一部分性能与更严格的安全校验。

**▌ 它解决了什么问题？**
在旧版 encoding/json 中，默认行为过于宽松：重复键静默保留最后一个、非法 UTF-8 字节被替换而非报错、字段名大小写不敏感导致歧义映射、nil 切片被编码为 null 而非 []。这些行为在微服务互操作、外部不可信数据接入时埋下大量隐性 bug。性能上，旧版解码在大结构体与深层嵌套下需要多次内存分配与反射调用，成为高频接口的瓶颈。Before 是"宽容但慢、易踩坑"，After 是"严格且快、默认安全"：重复键直接报错、非法 UTF-8 拒绝、大小写敏感、nil 切片输出空数组，反序列化速度最高提升十倍，且通过 jsoniter 风格的不分配令牌读取把 GC 压力降到最低。

**▌ 核心原理拆解**
v2 的核心是一套基于状态机的零拷贝解码器。旧版先把 JSON 文本扫描成一系列需要分配的中间结构，再经反射填充目标；v2 直接在原始字节上做单遍扫描，用状态机识别对象、数组、字符串、数字与字面量，遇到字段名时通过预计算的偏移表直接定位结构体字段，跳过逐字符反射查找。对于数字，v2 不再无条件转成 float64 再转回，而是保留原始字节按需解析，避免精度损失与多余分配。jsontext 包在更底层暴露令牌流，允许开发者手写高吞吐的流式处理。严格性方面，解码器在扫描阶段就校验 UTF-8 合法性并检测重复键，一旦发现即返回错误，而不是把脏数据带进内存。编码端则采用可增长的栈上缓冲，减少堆分配。由于 v1 的 Unmarshal 与 Marshal 被重定向到 v2 实现，旧代码无需改动即可受益，而需要精细控制的部分可显式 import v2 或 jsontext，实现按调用点的渐进迁移。

**▌ 动手验证**
最小可运行示例：在 Go 1.27 下用 v2 解析一份带重复键的 JSON，观察默认报错行为。
```go
package main

import (
    "fmt"
    "strings"
    "encoding/json/v2"
)

type User struct {
    Name string `json:"name"`
}

func main() {
    data := `{"name":"a","name":"b"}` // 重复键
    var u User
    err := json.Unmarshal([]byte(data), &u)
    fmt.Println(u, err) // 默认严格：返回重复键错误
    _ = strings.TrimSpace
}
```
将 import 改回 v1 时会静默取最后一个值，对比即可体会严格性差异。实际迁移建议在 CI 中先用 v2 跑一轮解析未知来源数据，捕获此前被旧版吞掉的脏数据。

**▌ 对比选型**
| 维度 | encoding/json/v2 | 旧版 v1 | jsoniter |
|------|--------|-------|----------|
| 核心思想 | 零拷贝状态机+默认严格 | 反射+宽容 | 代码生成+宽容 |
| 适用场景 | 可信/不可信数据通用 | 历史项目兼容 | 极致吞吐旧项目 |
| 性能 | 反序列化最高 10 倍 | 基准 1x | 约 2-5 倍 |
| 学习成本 | 几乎零（API 兼容） | 零 | 低 |
| 生态 | 官方标准库 | 官方标准库 | 第三方社区 |

### 2. 【Python 3.15 移除 GIL：自由线程时代真正到来（PEP 703）】

> 📍 **导语**：Python 3.15（预计 2026 年 10 月发布）把长期悬而未决的全局解释器锁移除正式落地，基于 PEP 703 的偏置引用计数、不可变对象与线程安全内存管理，让 Python 首次拥有真正的多线程并行能力。官方估计在多核密集场景下性能提升超过三成，这意味着"Python 不会真并行"的世纪难题终于被攻破。

---

**💻 深度解析**

**▌ 它是什么？**
全局解释器锁（GIL）是 CPython 中一把保护解释器内部状态的全局互斥锁，它强制任意时刻只有一个线程执行字节码，导致即便在多核机器上，纯 Python 的多线程也无法利用多核。PEP 703 由 Sam Gross 主导提出，目标是在不破坏现有 C 扩展生态的前提下，让 CPython 可以在编译时关闭 GIL，进入"自由线程"（free-threaded）模式。Python 3.15 将此能力从实验选项提升为可正式启用的构建形态：官方提供不带 GIL 的解释器二进制，开发者无需改动业务代码即可让 CPU 密集型任务跨核并行。这是 Python 三十余年历史上影响最深远的一次并发模型变革，被社区称为"无 GIL 时代"的真正开端。

**▌ 它解决了什么问题？**
Before 阶段，凡是想榨干多核算力的 Python 用户，被迫绕开原生线程：要么用 multiprocessing 起多个进程、承担序列化与内存翻倍的代价，要么把热点塞进 C 扩展或用 asyncio 做协作式并发（后者对 CPU 密集无能为力）。GIL 让"开个线程就能加速"的直觉在 Python 里彻底失效，成为 AI 训练、数值计算、Web 后端并发的长期痛点。After 阶段，自由线程解释器让多个 Python 线程真正同时运行在不同核上，CPU 密集型循环、数据预处理、推理前处理都能线性扩展，官方基准显示整体提速超过三成，部分并行场景收益更高，且不再需要为跨进程通信写大量样板。

**▌ 核心原理拆解**
移除 GIL 的关键是重构 CPython 的对象生命周期与内存可见性模型。第一支柱是偏置引用计数（biased reference counting）：绝大多数对象的引用计数只被创建它的线程修改，计数更新被本地化，只有跨线程共享时才走到慢路径的全局哈希表，从而把原子操作的代价压到最低。第二支柱是不可变对象与"永生对象"（immortal objects）：小整数、None、True 等全局单例被标记为永生，引用计数永不归零，彻底规避并发争用。第三支柱是线程安全的内存管理：字典、列表等容器在并发读写时用细粒度锁或 RCU 式结构保护，垃圾回收的循环检测改为可并行的安全点机制。编译器与标准库同步梳理了所有非线程安全的全局状态，C 扩展则通过新版稳定 ABI 声明自己是否支持无 GIL 模式。整套设计的核心思路是"默认单线程零开销、共享才付出成本"，既保住单线程性能，又打开多核之门。

**▌ 动手验证**
在启用了自由线程的 Python 3.15 中，用 threading 直接并行计数，观察多核利用率。
```python
import threading

counter = 0
def worker(n):
    global counter
    for _ in range(n):
        counter += 1

ts = [threading.Thread(target=worker, args=(200_000,)) for _ in range(4)]
for t in ts: t.start()
for t in ts: t.join()
print(counter)  # 自由线程下可正确收敛到 800000
```
对比带 GIL 的旧版，同样代码在单核串行；自由线程版能用满四核，墙上时间显著缩短。注意需安装官方 free-threaded 构建并用 `python3.15t` 运行。

**▌ 对比选型**
| 维度 | Python 3.15 自由线程 | multiprocessing | asyncio |
|------|--------|-------|----------|
| 核心思想 | 去 GIL 真并行 | 多进程绕过锁 | 协作式单线程并发 |
| 适用场景 | CPU 密集并行 | 重度并行+隔离 | IO 密集 |
| 性能 | 多核线性扩展 | 内存翻倍 | 不加速 CPU |
| 学习成本 | 几乎零改动 | 中（序列化） | 高（回调/await） |
| 生态 | 扩展逐步适配 | 成熟 | 成熟 |

### 3. 【tsrs：Cloudflare 用 Rust 移植 TypeScript 编译器，类型检查提速 8 倍】

> 📍 **导语**：2026 年 11 月 6 日，Cloudflare 联合 VoidZero 与 Owner.com 开源 tsrs——一个用 Rust 重写的 TypeScript 编译器，在 Oxc 工具链中孵化。它的看点不只是性能（类型检查最高快 8 倍、内存降约 70%、可经 WASM 运行），更是生产方式：由以 Claude Opus 5.5 为核心的智能体完成移植，并以 TypeScript 官方 15197 条一致性测试作为"写对了"的验收标准。

---

**💻 深度解析**

**▌ 它是什么？**
tsrs 不是从零发明新语言的编译器，而是把 TypeScript 官方编译器 tsc（用 TypeScript 编写、运行在 Node.js 上）的既有行为移植到 Rust。它的核心约束不是"设计更好的类型系统"，而是"与 tsc 逐字节保持一致的行为语义"。项目由 Cloudflare 在 Oxc（高性能 JavaScript/TypeScript 工具链）生态中孵化，作者 Max Schwenk 自述"没手写一行代码"，全程由 AI 智能体驱动完成从 TS 到 Rust 的迁移。语言规范仍由 TypeScript 团队主导，tsrs 定位为可替换的高性能执行后端，而非方言分支。它既能作为命令行工具在本地加速大型仓库的类型检查，也能编译成 WASM 在浏览器与 Cloudflare Workers 中运行，对冷启动敏感的边缘场景尤为友好。

**▌ 它解决了什么问题？**
Before 阶段，tsc 在超大型单体仓库上做全量类型检查会消耗数十秒甚至更久，根因有三：一是它运行在 V8 垃圾回收之上，庞大的类型对象图带来明显 GC 停顿；二是 tsc 本质单线程，无法利用多核并行符号解析；三是 Node.js bundle 在 Workers 冷启动慢。After 阶段，tsrs 用 Rust 的所有权在编译期确定大部分内存生命周期，绕开 GC 停顿；用 rayon 并行迭代器在文件级并行化类型检查；用 Rust 编译成 WASM 后大幅压缩加载时间。官方口径为同线程数下类型检查最高提速 8 倍、内存省约 70%（一个 3.7 万文件的单体仓库从 80 秒/19GiB 降到 7 秒）；第三方独立实测为 5.3 倍、内存省 72%、产物与诊断逐字节一致。即便对比更新的 TypeScript 7.1 beta，优势仍约 2.7 倍。

**▌ 核心原理拆解**
tsrs 的工程本质是把 tsc 二十多年积累的语义边界逐条对齐到 Rust 实现。TypeScript 的类型系统有大量"反直觉"的边缘案例：条件类型的分配规则、infer 的推断顺序、strictNullChecks 下的窄化行为等，任何重写都必须精确复刻，否则会出现"看起来对但类型结果不同"的隐性 bug。因此团队没有追求重写算法，而是让 AI 智能体基于 tsc 现有行为生成 Rust 骨架，并辅以人工与智能体协同校对。性能加速来自三条 Rust 特性：一是可控内存布局消除 GC 停顿；二是数据级并行把符号解析摊到多核；三是 WASM 后端缩短边缘运行时加载。验收机制是决定性创新——直接用 TypeScript 官方 15197 个一致性测试作为"正确性"的判定边界，把"AI 写的编译器对不对"变成可自动裁决的问题。TypeScript 团队已表示 tsrs 中的部分优化被吸收进 7.1，印证了这种"竞争式移植"对上游的正向溢出。

**▌ 动手验证**
在支持 WASM 或原生 Rust 工具链的环境下体验 tsrs 的类型检查加速（示意）：
```bash
# 安装后对一个大型 TS 工程做类型检查
npx tsrs check ./src
# 对比官方 tsc
npx tsc --noEmit ./src
# 观察输出：诊断信息应逐字节一致，耗时显著下降
```
注意 tsrs 仍处于实验阶段，已知细节差异（如退出码与 tsc 不同）可能影响现有 CI 脚本，落地前需在流水线中做一致性回归。

**▌ 对比选型**
| 维度 | tsrs (Rust) | tsc (TS/Node) | TypeScript 7.1 |
|------|--------|-------|----------|
| 核心思想 | AI 移植+WASM 加速 | 官方参考实现 | 官方下一代 |
| 适用场景 | 超大仓库/边缘 | 通用 | 通用渐进升级 |
| 性能 | 最高 8 倍 | 基准 1x | 约 3 倍 |

### 4. 【Evergreen 语言：把形式化验证做成编译器出厂设置的可证明安全系统语言】

> 📍 **导语**：2026 年 11 月，新系统语言 Evergreen 上线自举编译器，主打"把形式化验证从外部插件变成语言出厂设置"。它用 Rust 自举，却宣称比 Rust 更安全：通过 where/ensures 契约、内存平面（memory planes）机制与零开销证明擦除，让编译器在编译期直接承担定理证明义务，试图在系统编程与高保障软件之间架起一座新桥。

---

**💻 深度解析**

**▌ 它是什么？**
Evergreen 是一种面向高保障系统软件的新兴编程语言，其核心主张是把形式化验证内建进编译器前端，而不是像 Dafny、F* 那样作为验证导向语言、也不像 Verus、Kani 那样作为 Rust 之上的外部工具。它用 Rust 编写自举编译器，但设计目标直指"比 Rust 更可证明的安全"。语言允许开发者把契约与不变量直接写在代码旁：用 where 声明前置条件与类型约束（例如定义非零类型 NonZero 时要求输入不等于 0），用 ensures 声明后置条件，这些约束会变成编译器必须检查的证明义务。此外它引入"内存平面"机制追踪显式布局、所有权与借用引用，使编译器能静态推导出变量值的等式事实，从而把内存安全与逻辑正确性一起在编译期钉死。

**▌ 它解决了什么问题？**
Before 阶段，追求可证明正确的系统软件只有两条窄路：要么选 Dafny/F* 这类验证语言，得到强保证却牺牲了系统级生态（无法直接写内核模块、驱动、裸金属代码）；要么在 Rust 上挂载 Verus、Creusot、Kani 等验证工具，复用生态却要忍受借用编码与语法摩擦、验证与编译两套流程脱节。After 阶段，Evergreen 试图把"写代码"和"写证明"合进同一套语法与同一次编译：契约、归纳引理与理想数学计算（ideal）和业务代码混合书写，由内建证书内核统一检查，证明通过后被彻底擦除，不拖累最终二进制。这让高保障场景（航天、医疗、密码学组件）既能享受接近系统语言的底层控制，又不必在生态与验证之间二选一。

**▌ 核心原理拆解**
Evergreen 的编译期验证与代码擦除管线分三步。第一步是源码混合编写：开发者在同一文件里写业务执行代码、where/ensures 契约，以及把机器类型（如 usize）映射到理想整数做数学比对的 ideal 计算。第二步是内部证书内核检查：由 verify.rs 生成证明义务、kernel.rs 做核心逻辑校验、certificate.rs 做证书重放，整个过程不调用外部重型证明器（如 Z3 之外的庞大求解器），而是用自研轻量内核保证可重放。第三步是证明擦除与产出：编译器保留纯粹机器指令，擦除契约、归纳引理与幽灵计算，后端与分配器本身虽未验证，但用户代码区的逻辑正确性已被静态钉死。内存平面的关键设计是：当通过可变引用 *cell = 10 修改后，编译器能直接推导出原变量值等于 10 的静态事实，把"运行时才可能发现的状态不一致"前移到编译期。需要清醒看到，官方自举文档已承认原始设计中的部分特性尚未完全落地，后端与分配器信任链仍有缺口，工程现实与营销口号存在温差。

**▌ 动手验证**
体验 Evergreen 的契约式非零类型（示意语法，基于官方演练场）：
```evergreen
// 定义非零整数类型，编译器强制前置条件
type NonZero = int where self != 0;

fn safe_div(a: int, b: NonZero) -> int
    ensures result == a / b
{
    a / b
}

// 调用时若传入可能为 0 的值，编译器拒绝
let x: NonZero = 5;      // 通过
let y = safe_div(10, x); // 编译期验证 result == 2
```
这种写法让"除以零"在编译期成为不可表达的错误，而非运行时崩溃。

| 维度 | Evergreen | Rust + Kani | Dafny |
|------|--------|-------|----------|
| 核心思想 | 验证内建编译器 | 外部验证工具 | 验证导向语言 |
| 适用场景 | 系统级高保障 | Rust 生态验证 | 算法证明 |
| 性能 | 零开销擦除 | 验证期开销 | 运行期开销 |
| 学习成本 | 中（契约语法） | 高（证明编写） | 高（全验证） |

### 5. 【GraalVM LLVM Runtime 托管模式：在 GC 堆上安全跑 C/C++ bitcode】

> 📍 **导语**：GraalVM 的 LLVM Runtime（Sulong）提供一种"托管执行模式"，通过 lli --llvm.managed 把 C/C++ 编译出的 LLVM bitcode 跑在垃圾回收堆上。它禁止调用原生代码与访问原生内存，所有内存由 GC 管理，越界访问不再是不确定行为而是可拦截的运行时异常，为在异构平台上安全运行遗留原生代码提供了新范式。

---

**💻 深度解析**

**▌ 它是什么？**
GraalVM 是一套支持多语言的高性能运行时，其 LLVM Runtime（项目名 Sulong）能够直接执行 LLVM bitcode，从而把 C、C++、Rust、Fortran 等语言编译到统一的中间表示后由 GraalVM 托管。所谓"托管执行模式"通过 lli 工具的 --llvm.managed 选项启用：开启后，LLVM bitcode 中的内存分配全部发生在 GraalVM 的托管堆上，由垃圾收集器统一管理。需要明确的前提是，托管模式仅存在于 Oracle GraalVM，社区版不可用——这在 suite 配置中体现为 sulong 将 nativemode 与 managed 划分为不同发行组件。在该模式下，程序与 GraalVM 支持的其他语言（Java、Python、JS 等）一样"纯托管运行"，获得了和高级语言同等的内存安全保障。

**▌ 它解决了什么问题？**
Before 阶段，原生模式下的 C/C++ bitcode 越界访问是典型的未定义行为（undefined behavior），可能静默破坏相邻内存、引入难以复现的安全漏洞，且无法跨架构移植——同一份二进制必须针对每个平台重新编译。After 阶段，托管模式对指针算术做了收窄：指针运算仅在 C 标准允许范围内可行，溢出被阻止，无法通过越界访问触达不同分配，所有非法访问都产生运行时异常而非未定义行为。同时，托管模式在 GraalVM 内部模拟一个虚拟的 Linux/AMD64 操作系统，配套 musl libc 与 libc++，使得所有代码只需为该虚拟系统编译一次，即可在 GraalVM 支持的任何架构或操作系统上运行，并通过虚拟化系统调用路由到合适的 GraalVM API，实现真正的"一次编译、处处运行"。

**▌ 核心原理拆解**
托管模式的安全来自三层约束。第一层是内存归属：所有分配进入 GC 堆，原生内存与原生代码调用被禁止，从根本上消除了悬垂指针与原生堆破坏的可能。第二层是指针算术收窄，编译器在 lowering 阶段把 C 的指针运算限制在合法分配边界内，任何越界都被转换为受控的异常抛出，而不是放任硬件去读相邻字节。第三层是虚拟操作系统抽象，GraalVM 拦截 bitcode 中的 syscall 指令，将其重定向到托管的 GraalVM API，从而让原本依赖具体 OS 系统调用的 C 程序能在任意 GraalVM 平台上执行。代价是：所有要运行的代码必须被编译为 bitcode（不能直接跑机器码原生库），且托管模式目前仅 Oracle 发行版提供。这种设计特别适合需要安全运行不可信或遗留 C/C++ 组件、又希望跨平台部署的场景，例如把科学计算库、加密组件嵌入多语言微服务而无需担心内存安全黑洞。

**▌ 动手验证**
用 GraalVM 的 lli 以托管模式运行一段 C 程序（示意）：
```c
// hello.c
#include <stdio.h>
int main() {
    int a[3] = {1,2,3};
    printf("%d\n", a[1]);  // 合法访问
    return 0;
}
```
编译与运行：
```bash
clang -emit-llvm -c hello.c -o hello.bc
lli --llvm.managed hello.bc   # 在 GC 堆上托管执行
```
若把 a[1] 改成 a[100] 越界访问，托管模式会抛出运行时异常而非静默崩溃，直观展示与原生模式未定义行为的差异。

**▌ 对比选型**
| 维度 | GraalVM 托管模式 | 原生 C 运行 | WASM 沙箱 |
|------|--------|-------|----------|
| 核心思想 | GC 堆+异常拦截 | 裸内存 | 线性内存沙箱 |
| 适用场景 | 跨平台安全跑 C | 性能极致 | 浏览器/边缘 |
| 性能 | 有 GC 开销 | 最快 | 中 |
| 学习成本 | 低（clang 编译） | 零 | 中 |
| 生态 | Oracle 版限定 | 全平台 | 广泛 |

### 6. 【Java JDK 28 引入 Value Class：Valhalla 项目把对象变成扁平值类型】

> 📍 **导语**：Java 周刊披露，JDK 28 已开启约 30 个核心类的 Value Class 兼容警报，标志 Valhalla 项目长期攻坚的值类型正式落地。Value Class 让对象摆脱对象头与身份（identity），以扁平值的方式内联存储，消除指针间接与内存膨胀，在数值计算、高频数据结构与向量化场景中带来显著的性能与内存收益。

---

**💻 深度解析**

**▌ 它是什么？**
Value Class 是 Project Valhalla 的核心产出，目标是在 Java 类型系统中引入"值类型"——一种没有对象身份、按内容相等、可被扁平内联存储的类。传统 Java 对象无论多小都带一个对象头（通常 12-16 字节）并经由指针间接引用，导致海量小对象（如复数、坐标、货币金额）产生巨大内存与缓存压力。Value Class 通过 language 层面的修饰，告诉 JVM 该类型的实例可以按值扁平布局在宿主对象或数组里，而非各自独立堆分配。JDK 28 中约 30 个核心类开始发出 Value Class 兼容警报，说明标准库自身正在逐步迁移到这一新形态，为生态铺路。这与更早的 primitive class、inline class 等提案一脉相承，是 Java 近十年来最重要的内存模型演进之一。

**▌ 它解决了什么问题？**
Before 阶段，用普通类表达"轻量值"（如 Point、Complex、Money）时，每个实例都是带身份的独立堆对象，即便两个对象字段完全相同也被视作不同实体，既浪费内存又拖慢访问（多一次指针解引用、更差的缓存局部性）。大量这类对象还会加重 GC 负担。After 阶段，Value Class 去掉身份，两个字段相同的实例被视为相等的值，JVM 可将其字段直接内联进数组或外层对象，形成连续紧凑的内存布局，缓存命中率提升、GC 压力骤降，且语言层面保证按内容比较。对于数值密集、向量化、高频交易与大数据结构场景，这意味着更低延迟与更高吞吐，同时保持 Java 既有的类型安全与易用性，无需退回手写原生布局或改用基础类型数组的笨拙写法。

**▌ 核心原理拆解**
Value Class 的实现依赖 JVM 层面的扁平化布局与去身份语义。编译器在类文件层面标记该类型为值类型，运行时的对象布局阶段不再为其分配独立对象头与标识哈希，而是把字段直接嵌入持有者。数组由此从"指针数组"变为"值数组"，连续内存带来可向量化与缓存友好的访问模式。语言层面，Value Class 禁止与身份相关的操作（如非法的同步锁、基于 == 的引用比较被重新定义为内容比较），从语法上杜绝误用。JDK 28 的"兼容警报"机制则是一种平滑过渡策略：当标准库或用户代码中的某些类即将转为 Value Class 时，编译器提前对依赖旧身份语义的用法发出告警，给生态留出适配窗口。配合同期 JDK 27/28 的 AOT 缓存多层迭代训练、ZGC 启动提速 40% 等改进，Value Class 成为 Java 在内存效率与启动性能上整体追赶值类型语言（如 Rust 结构体、C# ref struct）的关键拼图。需要提醒的是，值类型并非银弹——涉及大量可变状态或强身份语义的实体仍应使用普通类，误用反而会带来语义困惑。

**▌ 动手验证**
在启用了 Valhalla 预览的 JDK 28 中声明一个值类型（示意语法）：
```java
// 声明一个无身份的点值类型
value class Point {
    int x;
    int y;
    Point(int x, int y) { this.x = x; this.y = y; }
}

Point a = new Point(1, 2);
Point b = new Point(1, 2);
System.out.println(a == b); // 值类型下按内容比较，输出 true
```
对比普通类，同样的 a 与 b 在 == 下会是 false（引用不同），值类型让"相等的值就是相等"成为语言默认。

**▌ 对比选型**
| 维度 | Java Value Class | 普通 Java 类 | C# ref struct |
|------|--------|-------|----------|
| 核心思想 | 扁平值、去身份 | 堆对象、有身份 | 栈上值类型 |
| 适用场景 | 轻量值/数值结构 | 实体/有状态对象 | 高性能值封装 |
| 性能 | 内存紧凑、缓存友好 | 指针间接、GC 压力 | 零分配 |
| 学习成本 | 低（语法简单） | 零 | 中 |
| 生态 | JDK 28 起步 | 成熟 | .NET 成熟 |
