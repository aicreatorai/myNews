### 1. 【MoE混合专家：路由器给每个词元只挑几个专家】

> 📍 **导语**：2026 年的前沿模型几乎清一色转向了混合专家架构——Gemini 3.5、GPT-5.5、DeepSeek V4 都被报道采用 MoE。它让万亿参数模型的单次查询成本，可以接近一个两千多亿参数的稠密模型。"参数越多反而越省"这个反直觉现象，正是理解当代大模型架构的钥匙。这一期我们拆开路由器，看它如何做到按词元动态选路。

---

**🧠 深度解析**

**▌ 它是什么？**

MoE（Mixture of Experts，混合专家）把 Transformer 块里那个"什么都会、但每次全部开动"的前馈网络（FFN），替换成多个更小的专家子网络，外加一个路由器（Router）。对每个词元，路由器只挑少数几个专家（例如 8 个里选 2 个）参与计算，其余专家保持休眠。它**不是**几个独立模型投票，也不是把模型按用户切分，而是在同一个模型内部、以词元为粒度动态选择计算路径。适用边界很清楚：当总参数量很大、训练数据充足、显存与带宽足以容纳全部专家权重时收益显著；模型本身很小、或逻辑链高度耦合的任务上收益有限。历史脉络是：1991 年 Jacobs 等人提出"局部专家混合"，2017 年 Transformer 出现后被引入，2020 年 GShard 把它推到千亿级，到 2026 年成为前沿模型的默认架构。它与当下热点的关联在于，DeepSeek V4、Gemini 3.5 这些被反复讨论的模型，靠 MoE 同时拿到了"大知识容量"和"低单查询成本"。

**▌ 它解决了什么问题？**

Before：稠密模型每生成一个词元都要把全部参数跑一遍，参数越多推理越贵，"知识容量"和"推理成本"被死死绑在一起，想更聪明就得付更多钱。After：MoE 把"总参数"与"激活参数"解耦——总参数可以堆到万亿级别以获得知识容量，但每个词元只激活一小部分，推理成本近似一个中等规模的稠密模型。量化来看，有报道称采用 MoE 架构的 130 亿参数模型，推理速度可以媲美 340 亿参数的稠密模型；某研究团队提出的动态权重分配算法，让专家利用率从 68% 提升到 92%，另有稀疏门控机制把跨专家通信量降低了 40%。最近的典型案例是 DeepSeek V4：用 MoE 把总参数推到前沿水平，同时保持较低的单查询成本。换句话说，MoE 解决的是"如何在可承受的推理预算下，换来尽可能大的模型容量"这一核心矛盾。

**▌ 核心原理拆解**

**第一层：直觉理解。** 把 MoE 想成一家专科医院——医院里有 384 位医生（总参数），但每位病人只进 8 人的诊室（激活参数）；分诊护士（路由器）根据病情挑出合适的医生。医院的整体知识储备极其庞大，但每个病人只为真正服务他的那几位医生付费。这就是"总参数很大、激活参数很小"的含义。

**第二层：技术流程拆解。** 输入词元向量 → 门控网络（一个小型线性层加 Softmax/Top-K）为每位专家打分 → 取分数最高的 K 位专家（如 K=2）→ 把词元送给这 K 个专家的 FFN 分别计算 → 按门控权重把结果加权求和，得到该层输出 → 进入下一层。关键参数包括：专家数 E（常见 8、16、64 甚至更多）、每词元激活数 K、容量因子 capacity factor（决定每位专家最多处理多少词元，防止拥堵），以及训练时附加的负载均衡损失系数。为什么要加负载均衡？因为若没有约束，路由器会把所有词元都送给同几位"明星专家"，其余专家饿死，模型容量被浪费。

**第三层：公式与核心机制。** 门控分数通常写成 softmax(W_g·x)，表示词元 x 分配给各专家的概率，该层输出为 Σ_i G_i(x)·E_i(x)，其中 G_i 是第 i 位专家的门控权重，E_i 是专家网络本身的输出。这里不必死记公式，关键是理解两件事。一是"稀疏激活"：Top-K 操作把其余专家的权重置零，计算量只与 K 有关、与总专家数 E 无关，这正是省算的根源。二是"负载均衡"：训练目标里加入辅助损失，把词元尽量均匀摊到各位专家，避免赢家通吃。工程上还有"专家并行"难题——不同专家分布在不同 GPU 上，词元需要经 All-to-All 通信送到目标卡再送回，稀疏门控正是为了压低这块通信开销，这与前馈层的计算节省共同构成了 MoE 的完整收益。

**▌ 动手验证**

用 transformers 加载一个开源 MoE 模型，观察它的专家配置，直观感受"总参数大、激活少"：

```python
from transformers import AutoModelForCausalLM
m = AutoModelForCausalLM.from_pretrained("Qwen/Qwen1.5-MoE-A2.7B")
print(m.config.num_experts, m.config.num_experts_per_tok)  # 专家数 / 每词元激活数
```

注意：该模型总参数约 14B，但每个词元只激活约 2.7B；首次加载需下载较大权重，显存不足可加 `device_map="auto"` 自动分片，或换更小的 MoE 模型。预期输出类似 `60 2`，即 60 位专家中每位词元只选 2 位。

**▌ 对比与选型**

| 对比维度 | MoE | 稠密模型 | 知识蒸馏 |
|---------|--------|-------|-------|
| 核心思想 | 按词元挑专家激活 | 全部参数每次都算 | 大模型教小模型 |
| 适用场景 | 大参数量与高并发 | 中小规模易部署 | 端侧轻量化 |
| 性能表现 | 总参大激活少 | 稳定可预测 | 接近教师模型 |
| 学习成本 | 高需并行通信 | 低 | 中 |
| 生态成熟度 | 前沿主流 | 最成熟 | 成熟 |

### 2. 【可验证奖励RLVR：用答案对错当奖励练模型】

> 📍 **导语**：2026 年，"强化学习"取代单纯堆参数，成为提升模型推理能力的主力。传统 PPO 曾让代码生成的 Pass@1 从 32% 提升到 58%，而更新的一股思路干脆抛开人工标注和奖励模型，用"编译是否通过、数学答案是否正确"这类可由程序判定的信号来训练模型。这就是 RLVR，它正在重塑推理模型的训练范式。

---

**🧠 深度解析**

**▌ 它是什么？**

RLVR（Reinforcement Learning with Verifiable Rewards，可验证奖励强化学习）指用"能被程序自动判定对错"的任务作为奖励来源来训练模型，而不是依赖人类偏好打分。典型的可验证信号包括：代码能否编译并跑通单元测试、数学题的最终答案是否等于标准答案、形式化证明是否通过检查器。它**不是** RLHF 的简单别名——RLHF 依赖人类偏好数据和奖励模型（RM），RLVR 依赖客观验证器，信号来源稀缺但几乎没有主观噪声。适用边界清晰：适合有明确正确答案的领域（代码、数学、逻辑、棋类）；开放式写作、审美偏好这类难以程序化验证的场景并不适用。历史脉络是：从 PPO 加 RLHF（InstructGPT）确立人类反馈路线，到 DeepSeekMath 提出 GRPO 省去价值网络，再到 2026 年 RLVR 成为推理模型训练的主流范式，整体趋势是"奖励从主观走向客观"。当下的热点关联是，DeepSeek、Kimi 等推理模型大量使用可验证奖励与合成智能体数据来闭环训练。

**▌ 它解决了什么问题？**

Before：RLHF 需要先雇人对成对的回答标注"哪个更好"，再用这些偏好训练一个奖励模型，最后用 PPO 优化生成策略；链条长、成本高、周期慢，而且人类偏好带有主观噪声，模型容易学会"讨好标注者"而不是"给出正确答案"。After：把奖励交给验证器——跑一遍单元测试、对一遍标准答案，对错分明、标准一致，而且可以无限扩展。量化来看，某技术方案显示：监督微调阶段用人类标注建立基础能力，再经奖励模型与 PPO 多轮迭代，代码生成的 Pass@1 指标从 32% 提升到 58%；RLVR 则进一步省掉奖励模型环节，直接用自动验证信号优化。最近的案例是 Kimi K2 用 MuonClip 优化器防止注意力 logits 爆炸、GLM-5 用 Slime 框架提升异步强化学习吞吐，这些基础设施的改进都服务于"可验证奖励"这条闭环。

**▌ 核心原理拆解**

**第一层：直觉理解。** 把模型训练想象成刷题备考。RLHF 像请老师逐份写主观评语"这篇作文更好"，不同老师标准可能不同；RLVR 则像用自动阅卷机批选择题——只要有标准答案，机器就能判对错，且永不疲倦、标准统一。后者不需要老师全程参与，规模化训练因此成为可能。

**第二层：技术流程拆解。** 收集带可验证答案的题目（数学题、代码题）→ 模型对每道题采样生成多个候选答案 → 验证器逐个打分（通过单测得 1，否则得 0）→ 用组内相对优势（例如 GRPO：用同一题多个答案奖励的均值和方差作为基线，省掉价值网络）→ 用策略梯度更新模型参数 → 重复迭代。关键参数包括：每题采样数 G、相对优势的计算方式、KL 散度惩罚系数（防止模型为拿高分而跑偏到胡言乱语），以及批量大小。

**第三层：公式与核心机制。** RLVR 的核心思想是"相对优势 A_i = (r_i − mean(r)) / std(r)"——把某个答案的原始奖励 r_i，减去同一道题其他答案的平均分，再除以标准差，得到"相对这道题它有多好"的标准化信号。这样即使题目难度不同，也能公平比较。GRPO 的关键洞察是：既然能对同一问题采样一组答案并互相比较，就不必再训练一个价值网络（critic）来估计基线，显存占用和工程复杂度大幅下降。RLVR 的另一面挑战是"奖励稀疏"——较难的题目上多数采样可能全错，没有正信号可学，因此要靠大规模采样、课程学习（先易后难）和高质量题目筛选，才能保证训练持续有效。

**▌ 动手验证**

用 TRL 库的 GRPOTrainer 配一个自定义奖励函数，判断生成答案是否等于标准答案：

```python
from trl import GRPOTrainer
def reward(completions, answer, **kw):
    return [float(c.strip() == a.strip()) for c, a in zip(completions, answer)]
# GRPOTrainer(model=模型, reward_funcs=[reward], args=参数).train()
```

注意：需要准备带 `answer` 字段的数据集，奖励函数必须返回与 completions 等长的列表；首次运行建议减小 `max_completion_length`，防止显存溢出。预期：训练日志中奖励均值随步数上升，说明模型越来越多地生成正确答案。

**▌ 对比与选型**

| 对比维度 | RLVR | RLHF | DPO |
|---------|------|------|-----|
| 奖励来源 | 程序自动验证 | 人类偏好加RM | 偏好对直接优化 |
| 适用场景 | 代码数学逻辑 | 开放对话 | 偏好对齐 |
| 性能表现 | 客观可无限扩展 | 主观有噪声 | 简单稳定 |
| 学习成本 | 中需验证器 | 高需标注 | 低 |
| 生态成熟度 | 快速崛起 | 成熟 | 成熟 |

### 3. 【稀疏注意力与线性注意力：给长上下文降复杂度】

> 📍 **导语**：长上下文的头号拦路虎，是注意力的 O(n²) 复杂度——序列长度翻倍，计算量翻四倍。2026 年有两条降本路线被反复提及：稀疏注意力只挑重要的词元去算，线性注意力用核方法把复杂度压到 O(n)。有开源实现称长文本处理效率提升 3 倍，结构化稀疏在保持 85% 准确率的前提下把 FLOPs 降低 60%。这两条路线值得放在一起看。

---

**🧠 深度解析**

**▌ 它是什么？**

标准自注意力要求每个词元与全部历史词元两两计算相关度，复杂度随序列长度平方增长。稀疏注意力（Sparse Attention）让每个词元只关注一个子集——可以是固定模式、滑动窗口，或按内容挑出重要的词元，跳过大量无关配对；线性注意力（Linear Attention）则用核函数近似 softmax，把"先算 n×n 注意力矩阵再乘 V"重排成"先把 K、V 聚合成固定大小的状态再逐词元查询"，复杂度降到 O(n)。它们**不是**简单截断上下文——稀疏是结构化或动态地选取，线性注意力是数学上的等价变形而非粗暴删除内容。适用边界在于：超长文档、长视频、长对话收益明显；短序列上优势不明显，甚至可能因近似带来精度损失。历史脉络是：从 Transformer 的稠密注意力，到 Sparse Transformer、Longformer（滑动窗口加全局词元）、Performer 与 Linear Transformers（核近似），再到 2026 年与 MoE 叠加，同时优化注意力层和前馈层的开销。

**▌ 它解决了什么问题？**

Before：处理一段十万 token 的文档，稠密注意力要计算约一百亿次词元配对，显存和耗时都难以承受，长上下文沦为"塞得进去却算不起"的摆设。After：稀疏注意力把配对数压到次平方甚至线性，线性注意力把每一步计算固定化，让超长序列真正可用。量化来看，某开源项目实现的线性注意力以 O(n) 复杂度使长文本处理效率提升 3 倍；结构化稀疏注意力则在保持 85% 准确率的前提下，把 FLOPs 降低 60%。最近的案例是：不少 2026 年的开源模型把稀疏注意力与 MoE 叠加，实现对注意力层和前馈网络的双重省算，让"百万 token 窗口"从宣传指标变成可运行的工程能力。

**▌ 核心原理拆解**

**第一层：直觉理解。** 稠密注意力像在全校花名册里逐一比对，找出所有可能相关的人；稀疏注意力像只翻你常联系的那几十个人；线性注意力则像先把全班同学的特征汇成一份"班级摘要"，新同学来时只对这份摘要提问，而不必逐个比对。三者省算的方式不同，但目标一致：避免无谓的全量配对。

**第二层：技术流程拆解。** 输入 Q、K、V 三个矩阵 → 稀疏分支按预设模式生成稀疏掩码 M（滑动窗口、块稀疏或 Top-k 检索），只在掩码允许的位置计算 QKᵀ 并做 softmax，再乘以 V 得到输出；线性分支则用核函数 φ 做近似，按 φ(Q)·(Σφ(K)ᵀV) / (φ(Q)·Σφ(K)) 的形式计算，把全局聚合项 Σφ(K)ᵀV 以增量方式维护。关键参数包括：窗口大小、块大小、Top-k 数量、核函数类型（如 elu 加一），以及是否保留局部稠密窗口来兜底精度。

**第三层：公式与核心机制。** 稀疏注意力的核心是"信息冗余假设"——真实序列里绝大多数词元对当前词元无关，丢掉它们损失很小；设计要点是既让每个词元看得到局部上下文（不丢近处信息），又保留少量全局词元接收整体信息。线性注意力的核心公式思想是"结合律重排"：softmax(QKᵀ)·V 难以拆分重排，但若用核函数 φ 使 exp(q·k) ≈ φ(q)·φ(k)ᵀ，就能先把所有 φ(k)ᵀv 累加成一个矩阵，再乘 φ(q)，复杂度从平方降为线性。代价是近似会引入误差，而且在因果生成场景下需要维护前缀和，工程实现更精细。因此实际系统常把两者混用：局部用稠密注意力保精度，远处用稀疏或线性降成本。

**▌ 动手验证**

用 transformers 切换不同注意力实现的模型，对比长序列上的耗时与显存（示意）：

```python
from transformers import AutoModel
m = AutoModel.from_pretrained("google/performer")  # 核近似的线性注意力模型
out = m(input_ids).last_hidden_state  # 输入长度可设为 512 与 4096 对比
```

注意：不同模型的接口不同，Performer 依赖核近似，Longformer 则依赖 `attention_mask` 配置滑动窗口；只有对比 512 与 4096 两种长度，线性/稀疏的优势才显现，短序列上未必更快。预期：在 4096 长度时，线性或稀疏实现的显存占用明显低于标准稠密模型。

**▌ 对比与选型**

| 对比维度 | 标准注意力 | 稀疏注意力 | 线性注意力 |
|---------|--------|-------|-------|
| 核心思想 | 全量 pairwise | 只算子集 | 核近似重排 |
| 适用场景 | 短序列 | 长文档 | 超长序列 |
| 性能表现 | O(n²) | 次平方 | O(n) |
| 学习成本 | 低 | 中 | 高 |
| 生态成熟度 | 最成熟 | 常用 | 研究为主 |

### 4. 【Agent分层记忆：工作情景语义程序四层各司其职】

> 📍 **导语**：为什么同一个智能体用久了越来越"懂你"，却又会在长任务里忘记早期的约定？差别往往不在模型更聪明，而在记忆系统。2026 年的生产级智能体普遍把记忆拆成短期上下文、工作记忆（向量检索）与长期持久化三层，有的还进一步细分出情景、语义、程序记忆。这一期讲清"存、取、忘"三件事。

---

**🧠 深度解析**

**▌ 它是什么？**

智能体记忆（Agent Memory）是把"模型权重之外的信息"按保留时长与用途分层存储、按需加载的机制。常见的三层划分是：短期记忆（当前对话的上下文窗口）、工作记忆（任务过程中通过向量检索临时取回的文档与中间结果）、长期记忆（用户画像、历史任务轨迹、企业知识库，落在数据库中）。更细的划分还会区分：情景记忆（历史成功或失败的案例）、语义记忆（外部事实，由 RAG 支撑）、程序记忆（沉淀下来的标准工作流，便于同类任务复用）。它**不是**"模型记住了你"——对话过程中模型权重并未更新，所谓"记住"靠的是把历史重新塞回上下文，或从外部检索回来。适用边界是多轮、长链路、跨会话的任务，单次问答用不上。历史脉络是：从早期聊天机器人固定上下文，到 RAG 引入外部检索，再到 2026 年分层记忆加显式记忆策略（存什么、存多久、谁能读）成为生产标配。

**▌ 它解决了什么问题？**

Before：把所有信息一股脑塞进上下文——塞少了健忘，塞多了又会"上下文腐化"，导致推理质量下降且 token 成本飙升；对话窗口一关，此前的约定全部丢失。After：分层按需取用——短期放当前会话，长期落库保存，需要时再检索回来。量化来看，有研究明确指出：过度填充上下文会退化推理质量，而检索不足又会让智能体反复犯同一个错误；三层记忆让"该留的留下、该取的取回"成为可控工程。最近的案例是：2026 年的生产架构普遍为记忆配置显式策略（保留期限、可存数据类型），并用向量库保存历史上成功的方案与用户偏好，使智能体在下次任务中直接复用。

**▌ 核心原理拆解**

**第一层：直觉理解。** 把智能体记忆想成人的记忆系统——短期记忆是你此刻脑中想的事（当前对话），工作记忆是你桌上摊开的资料（临时检索来的文档），长期记忆是你脑子里的知识与笔记本（用户画像、历史经验）。人不会把整座图书馆背下来，而是需要时去查；智能体同理，靠分层与检索而非"全记住"。

**第二层：技术流程拆解。** 用户请求到达 → 短期记忆加载当前会话历史 → 规划模块判断还需要哪些信息 → 工作记忆经向量检索取回相关文档或历史案例 → 把这些内容注入上下文供模型推理 → 调用工具执行 → 把结果与可复用结论写入长期记忆（如用户偏好、成功方案）→ 下次会话再检索复用。关键参数包括：上下文窗口上限、检索的 Top-k 数量、记忆写入阈值（什么值得存）、TTL 保留期限、向量维度与相似度阈值。

**第三层：公式与核心机制。** 记忆系统的核心是"存、取、忘"三件事的策略化。存：并非所有对话都值得保存，只把可复用的结论、偏好、成功轨迹结构化写入，避免噪声堆积。取：用 Embedding 向量相似度检索，Top-k 控制注入量，防止挤占推理空间；检索结果若不相关，反而会干扰判断，因此生产系统常分库存储、加元数据过滤，并让规划模块显式决定是否读取。忘：给记忆设置 TTL 和容量上限，定期蒸馏或淘汰过期条目，防止库无限膨胀。真正的工程难点是检索召回率——取回的内容要既相关又精简；这决定了智能体是"过目不忘"还是"记了一堆没用的东西"。

**▌ 动手验证**

用 langchain 搭配向量库，搭建一个最小的"写入—检索"长期记忆闭环：

```python
from langchain_community.vectorstores import FAISS
from langchain_openai import OpenAIEmbeddings
vs = FAISS.from_texts(["用户偏好靠窗座位"], OpenAIEmbeddings())
print(vs.similarity_search("订机票要注意什么", k=1)[0].page_content)
```

注意：真实运行需要配置 API key；示例只演示"写入—检索"闭环，生产环境还要补充 TTL 与元数据过滤。预期输出为"用户偏好靠窗座位"，说明这条长期记忆被成功召回。

**▌ 对比与选型**

| 对比维度 | 短期记忆 | 工作记忆 | 长期记忆 |
|---------|--------|-------|-------|
| 核心思想 | 上下文窗口 | 向量检索临时取 | 数据库持久化 |
| 适用场景 | 当前对话 | 任务中查资料 | 跨会话复用 |
| 性能表现 | 快但容量小 | 灵活看召回 | 持久但需维护 |
| 学习成本 | 低 | 中 | 高 |
| 生态成熟度 | 成熟 | 成熟 | 快速完善 |

### 5. 【Prefill与Decode：大模型推理的两段人生与访存瓶颈】

> 📍 **导语**：同样的大模型，为什么第一个字要等半秒、后面却飞快吐字？答案藏在推理的两个阶段里。央广网把训练比作划龙舟、把推理解作连锁餐厅；推理内部又分"读题"式的预填充和"作答"式的逐词解码，二者的算力瓶颈完全不同。理解这一点，才算真正理解推理成本与延迟从何而来。

---

**🧠 深度解析**

**▌ 它是什么？**

Prefill（预填充）是一次性并行处理用户输入的全部提示词，计算每个词元的 K/V 并生成第一个输出词元，它决定了首字延迟（TTFT）；Decode（解码）是随后逐个生成词元的自回归循环，每一步都依赖前面所有结果，它决定了每秒输出词元数（TPS）。它们**不是**两次独立调用，而是同一次请求内部的两个阶段；也不是训练——推理全程权重冻结，不更新任何参数。适用边界在于所有自回归生成场景：理解它才能做对的优化——短提示场景要优化 prefill，长输出场景要优化 decode。历史脉络是：早期人们把推理当作一次简单的前向计算，随着 KV 缓存与批处理调度机制出现，业界才明确区分出两阶段各自的硬件瓶颈，并分别设计优化方案。

**▌ 它解决了什么问题？**

Before：把推理当黑盒，只知道"慢"，优化无从下手；要么一味堆硬件，要么盲目缩短提示词。After：拆成 prefill 与 decode 之后就能对症下药——prefill 拼计算能力，decode 拼显存带宽和调度效率。量化来看，以 H100 芯片运行一个 700 亿参数模型为例，每生成一个词元、把参数从显存读一遍约需 21 毫秒，而实际计算只需约 0.07 毫秒，两者相差 300 倍——解码阶段是"读权重"而非"算数"主导。再比如批处理"拼单"：读一遍参数，同时为几十个用户各生成一个词元，效率可以提高几十倍。最近的案例是：2026 年推理算力成为需求主体，推理引擎普遍采用连续批处理（continuous batching）来提升吞吐，正是源于对 decode 阶段访存瓶颈的认识。

**▌ 核心原理拆解**

**第一层：直觉理解。** 推理像一场考试——prefill 是"读题"，一次性把整道题看完，可以并行；decode 是"作答"，一个字一个字地写，后一个字必须等前一个写完。读题快不快看眼力（算力），写字快不快看手速（显存带宽）。而"拼单"则像坐公交车：多载几位乘客，人均成本更低，但为了凑人，先上车的乘客要多等一会儿。

**第二层：技术流程拆解。** 请求到达 → 分词器把文本转成 token ID（词表通常在 3 万到 12 万之间）→ Prefill 阶段：GPU 并行矩阵乘，对全部提示词计算自注意力并填满 KV 缓存，产出第一个词元（这段耗时即 TTFT）→ Decode 循环：用最新词元查询 KV 缓存算出 logits → 采样（温度与 top-p）选出下一个词元 → 把新词元的 K/V 追加进显存中的 KV 缓存 → 重复，直到生成停止符或达到上限 → 反分词后流式返回给用户。关键指标包括：TTFT、TPS、KV 缓存占用量、批大小与 gpu_memory_utilization。

**第三层：公式与核心机制。** 核心是"瓶颈转移"这四个字——prefill 是计算受限（compute-bound），大矩阵乘法可以把算力跑满；decode 因为每步只算一个词元、却要把全部权重读一遍，变成访存受限（memory-bandwidth-bound）。因此优化手段完全不同：优化 decode 要靠增大批大小摊薄权重读取成本、靠量化缩小权重体积、靠 PagedAttention 管理 KV 缓存碎片。这也解释了两个常见现象：为什么长对话更吃显存（KV 缓存随对话长度线性增长），以及为什么代码补全要少拼单（追求低延迟）、批量处理文档却要多拼单（追求高吞吐）。推理效率一半取决于芯片，一半取决于调度。

**▌ 动手验证**

用 vLLM 观察两阶段的真实指标（示意）：

```python
from vllm import LLM, SamplingParams
llm = LLM(model="Qwen/Qwen2.5-0.5B")
out = llm.generate(["解释预填充与解码"], SamplingParams(max_tokens=32))
print(out[0].outputs[0].text)
```

注意：vLLM 会在日志中打印 TTFT、TPS 与 KV 缓存占用；把 `max_tokens` 调大可以观察 decode 阶段耗时如何增长；显存不足时调小 `gpu_memory_utilization`。预期：首字延迟与后续每个字的生成延迟明显不同，正好印证两阶段瓶颈的差异。

**▌ 对比与选型**

| 对比维度 | Prefill | Decode | 训练 |
|---------|--------|-------|-----|
| 核心思想 | 并行读题 | 逐词作答 | 更新权重 |
| 适用场景 | 长提示 | 长输出 | 模型生产 |
| 性能表现 | 计算受限 | 带宽受限 | 算力密集 |
| 学习成本 | 中 | 中 | 高 |
| 生态成熟度 | 成熟 | 成熟 | 成熟 |

### 6. 【缩放法则：算力数据参数可预测地换能力】

> 📍 **导语**："再堆多少算力才能更强？"Scaling Laws 给出了可预测的答案。它把模型能力（通常用测试损失衡量）与参数量、数据量、算力预算三者联系起来，让前沿实验室能在训练开始前就预估最终效果。有实验显示，数据量从 100B token 提升到 500B，数学推理准确率提升了 27%。这条规律如何指导真实的预算决策？

---

**🧠 深度解析**

**▌ 它是什么？**

缩放法则（Scaling Laws）描述模型规模、训练数据量、计算预算与模型能力之间可预测的幂律关系。核心发现是：在其他条件做了最优分配的前提下，按比例扩大参数与数据、增加算力，损失会按可预测的规律下降。它**不是**"参数越多一定越好"的口号——如果数据或算力不匹配，单纯堆参数会陷入过拟合或造成浪费；它也不是严格意义上的物理定律，而是经验规律，可能随架构和数据质量改变。适用边界是指导预训练的资源分配、判断投入产出比，但不能预测某些能力在特定规模的突然涌现。历史脉络是：2020 年 Kaplan 等人提出原始缩放法则，2022 年 DeepMind 的 Chinchilla 研究修正了"参数与数据应等比例增长"的结论，指出此前大量模型训练不足；到 2026 年，缩放法则已成为前沿实验室的预算规划工具，并与强化学习、合成数据协同使用。

**▌ 它解决了什么问题？**

Before：训练前沿模型是一场"烧钱赌博"——花几千万美元跑完才知道效果到底如何，资源该往哪里投（多堆参数还是多喂数据）几乎全凭经验直觉。After：用缩放法则提前拟合，给定算力预算就能反推出较优的参数量与数据量组合，把赌博变成规划。量化来看，某实验显示数据量从 100B token 提升到 500B 时，数学推理任务的准确率提升 27%；另有报道指出，随着万卡集群部署，一个 1750 亿参数模型的训练时间从 21 天缩短到 72 小时，单位参数训练能耗降低 55%——这说明算力基础设施的升级也在改写缩放曲线的位置。最近的案例是：强化学习与高质量数据集的协同效应获得验证，但缩放法则依然是为模型能力定基线的出发点。

**▌ 核心原理拆解**

**第一层：直觉理解。** 缩放法则很像"健身收益曲线"——训练量（算力）乘以合理配比（参数与数据）能稳定换来"力量"（能力）增长，而且增长是可预测的：投入翻倍，收益按固定比例提升，而不是随机跳变。正因可预测，实验室才敢在训练前就定下预算。

**第二层：技术流程拆解。** 先固定计算预算 C → 用经验公式估算该预算下的最优参数量 N 与数据量 D（近似 N∝C^a、D∝C^b，二者大致等比例增长）→ 据此设计模型规模与语料规模 → 用一系列小规模实验拟合"损失—算力"曲线 → 外推到大规模，预测最终表现 → 正式训练中持续监控是否符合预期。关键参数包括：计算预算 C（以 FLOPs 计）、参数量 N、token 数 D，以及 Chinchilla 给出的经验比例（大约每个参数配 20 个 token）。

**第三层：公式与核心机制。** 其形式常写作 L(N, D) ≈ A/N^α + B/D^β + E。用自然语言翻译：模型能力（损失）的改善来自两个可相加的收益项——模型变大（第一项变小）和数据变多（第二项变小），但存在一个下限 E（数据噪声、任务本身的难度决定的不可约误差）。关键洞察是"最优分配"：算力固定时不能只堆参数或只堆数据，要按一定指数比例同步增长才能让损失最小，这正是 Chinchilla 修正"大模型训练不足"的理论依据。局限同样重要：幂律描述的是平均趋势，无法预测涌现这类非线性跳变；而且高质量数据、强化学习与合成数据会改变曲线的位置，因此缩放法则是规划基线，而不是万能公式。

**▌ 动手验证**

用一组小规模模型的（参数量，损失）数据点拟合幂律趋势，体会"规模越大损失越低"：

```python
import numpy as np
N = np.array([1e7, 1e8, 1e9]); L = np.array([3.2, 2.4, 1.9])
a, c = np.polyfit(np.log(N), np.log(L), 1)  # 拟合 log L = a*log N + c
print("幂律指数:", a, "外推10B损失:", np.exp(a*np.log(1e10)+c))
```

注意：真实拟合需要同分布、同等训练规模的数据点，示例仅演示方法；幂律外推存在误差，不能当作精确预测。预期：指数 a 为负值，符合"规模越大、损失越低"的规律。

**▌ 对比与选型**

| 对比维度 | 缩放法则 | Chinchilla | 涌现能力 |
|---------|-------|-------|-------|
| 核心思想 | 幂律可预测 | 参数数据等比 | 阈值后突变 |
| 适用场景 | 预算规划 | 训练配比 | 能力分析 |
| 性能表现 | 平滑下降 | 更省算力 | 非线性跳变 |
| 学习成本 | 中 | 中 | 高 |
| 生态成熟度 | 成熟 | 成熟 | 研究中 |
