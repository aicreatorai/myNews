### 1. 【Compose Multiplatform 1.13 RC：内容尺寸自适应回传 SwiftUI】

**导语**：
JetBrains 在 2026 年 11 月 18 日放出 Compose Multiplatform 1.13.0-rc01 预发布版本，Gradle 插件坐标为 org.jetbrains.compose 1.13.0-rc01，标签 v1.13.0-rc01。对同时维护 Swift 主工程与共享界面的团队来说，这一版最值得关注的变化不是又多了几个控件，而是 Compose 画面第一次能够回答宿主 SwiftUI 提出的尺寸询问：当共享界面被嵌进 SwiftUI 的 representable 容器时，它可以把自己按内容计算出的尺寸回传给外层布局，开发者不必再在桥接层手填一个写死的高度数字。同一版本还把 ComposeUIView 与 ComposeUIViewConfiguration 提升为稳定 API，并为 iOS 补上密码的原生保存与自动填充提示。由于这是候选发布版而非稳定版，建议先放在独立分支上验证，但演进方向已经足够明确。

**核心信息**：
1.13.0-rc01 的四项重点中，与 iOS 直接相关的是内容尺寸自适应与密码自动填充，另外两项 WebGL 互操作和 AppCDS 桌面启动加速并不作用于 Swift 宿主。尺寸回传的关键在于系统向 Compose 发出 sizeThatFits 询问时，新接口允许声明 preferredSizeReportingStrategy，让共享界面报告自己的首选尺寸；不过该策略类型与属性在 rc01 仍标注为 @ExperimentalComposeUiApi，默认的 SizeThatFits 路径则不需要任何策略代码即可工作。密码方面，PlatformImeOptions 其实在 1.12.2 就已存在，这次新增的是触发系统原生保存与填充对话框的行为，对登录、支付等表单是体验层面的实质改进。语言基线也随之抬升：1.13 把 Kotlin 升级到 2.4.20，Kotlin/Native 目标的最低版本为 2.4.0，若同时编译 JS 或 Wasm 目标则需要 2.4.20。仍停留在更低版本的团队，升级前要先对齐整个多平台工程的 Kotlin 线，避免 native 目标与 web 目标出现版本错位。

**影响判断**：
这条更新把共享界面在 iOS 上到底该多大，从人工约定变成了可协商的布局协议，长期看会显著降低 SwiftUI 与 Compose 混编的维护成本。对已经采用 KMP 的团队，建议本周就把 1.13.0-rc01 拉到独立分支，重点回归带列表、弹层与键盘避让的页面，因为尺寸回传会直接影响滚动内容高度的计算；同时验证密码自动填充在真机与模拟器上的表现差异。对还在观望的团队，这版释放的信号是 JetBrains 正把 iOS 集成从能跑推向好用，KMP 作为共享业务逻辑方案的可行性进一步增强。风险点在于候选版的实验标记：带 @ExperimentalComposeUiApi 的策略接口后续仍可能改名或调整语义，生产环境应优先走无需策略代码的默认路径，并为 rc 到 stable 之间的差异预留一次完整回归窗口。

### 2. 【WebKit 开放全局隐私控制 API：GPC 开关决策权下放给 App】

**导语**：
Apple WebKit 团队于 2026 年 11 月 18 日宣布，iOS、iPadOS、visionOS 与 macOS 27 新接入一组全局隐私控制（Global Privacy Control，GPC）接口，App 可以针对自己加载的网页决定是否发出用户选择退出信息共享与跨情境定向广告的信号。这不是系统级的一刀切开关，而是把决策权交给开发者：默认关闭，是否向用户呈现该选项、如何呈现，都由 App 自己实现。对内置 WKWebView 或 SwiftUI WebPage 的应用来说，这是一次需要主动设计而非被动适配的合规能力更新，也意味着隐私偏好表达第一次有了标准化的原生通道。

**核心信息**：
新接口在两个框架中各有一个对应属性：基于 WKWebView 的 App 使用 WKWebpagePreferences.globalPrivacyControlEnabled，默认值 NO；使用 Swift WebPage API 的 App 使用 WebPage.NavigationPreferences.isGlobalPrivacyControlEnabled，默认值 false。二者都支持 iOS、iPadOS、Mac Catalyst、macOS 与 visionOS 27.0 以上，tvOS 与 watchOS 不在列表内。设置位置是在导航策略回调中，每次页面开始加载时由 App 读取用户偏好并写入该属性，随后放行导航；一旦开启，WebKit 会为主框架、子框架及其子资源统一发送 Sec-GPC: 1 请求头，并向页面脚本暴露 navigator.globalPrivacyControl。Apple 的说明引用了 W3C GPC 规范工作草案与加州 CCPA 关于通过 GPC 退出出售或共享个人信息的条款，但没有附加法律意见。官方博客给出了 WKWebView、Swift WebPage 与 Objective-C 三套示例代码，模式一致：在 decidePolicy 回调里根据用户保存的偏好设值，再允许导航继续。

**影响判断**：
对有内嵌网页、登录页或广告 SDK 的 App，这组接口提供了一条比自行注入请求头更规范的合规路径，尤其适合面向加州等司法辖区提供服务的产品。落地建议分三步：先确认目标用户所在地区的法律要求，再在设置中提供清晰的 GPC 开关并持久化用户选择，最后在导航策略回调里把偏好传给 WebKit 并做一次抓包验证。需要清醒认识到，开启 GPC 不会改变网站的实际行为，它只是表达偏好，是否被尊重取决于对方；同时它也只覆盖 WebKit 加载的内容，原生模块与第三方 SDK 的数据流需要单独治理。风险在于默认值关闭带来的以为已经合规的错觉，以及不同系统版本支持范围不一致，旧系统仍需自行处理。建议把 GPC 状态纳入隐私清单与合规审计，而不是当作一次性改动。对同时运营国内外双版本的团队，还要留意同一套 WebView 封装在两地合规要求下的差异化配置，避免把面向加州的逻辑误投放到其他市场，或因编译宏切换遗漏了 GPC 开关的初始化。更重要的是，应把用户偏好与请求头实际发出情况做成可观测日志，在灰度阶段抽样核对，确认代码路径确实按预期工作，而不是停留在接口已接入的层面。

### 3. 【React Native 0.89 RC 清理旧架构 API：New Architecture 成唯一路径】

**导语**：
React Native 0.89 RC1 在 2026 年 11 月进入候选阶段，而当前稳定版仍是 10 月 27 日跟进的 0.88.1。与以往新增几个组件的版本不同，0.89 的主线任务是拆掉旧架构的最后残余：一批仅服务于旧桥接模式的 API 被移除，同时要求项目显式声明对 @react-native/community-cli-plugin 的依赖。官方把 0.88.1 定位为无用户侧破坏性变更的版本，0.89 则明显拉开了升级跨度。对于仍在旧架构上跑生产包的团队，这是必须排期的一次迁移，而不是可选的尝鲜，因为兼容层一旦被移除，回退路径也随之消失。

**核心信息**：
要理解这次清理，需要先看清 New Architecture 的现状。新架构用 JavaScript Interface 取代异步桥接，让 JavaScript 能直接调用原生方法而不经过序列化；Fabric 负责渲染，TurboModules 按需加载，Hermes 引擎自 0.84 起已是 iOS 与 Android 的默认选择。到 0.87 时最后一个 TurboModules 开关被移除，TurboModules 进入常开状态；旧架构在 0.82 就已不再是可选路径，遗留的 opt-out 标志被忽略。因此 0.89 删除的并不是可回退的功能，而是早已失效的兼容层。除此之外，0.88 系列已经默认切换到 Web 风格事件分发、支持可变字体与 iOS SceneDelegate，这些行为变化会在 0.89 的回归中被进一步固化。对 Expo 用户而言，Expo SDK 58 内置 React Native 0.88，新项目起点相对干净；而 0.89 预计在 12 月 7 日发布，届时稳定版才会真正落到这条线上，生产项目仍需再观察一段时间。

**影响判断**：
这次升级的成本主要落在第三方库而非业务代码：任何封装了旧架构桥接的原生模块都可能在新版下失效，尤其是事件相关与自定义原生视图。建议按三步推进：先在测试分支升级到 0.88.1，把事件分发、可变字体和 iOS SceneDelegate 跑通；再盘点依赖树，确认每个原生库都声明支持新架构；最后用 0.89 RC 做一次完整回归，观察在无旧架构可用时是否仍有隐藏依赖。对已经享受新架构收益的团队，这次清理是降低长期维护负担的好事；对重度依赖老旧插件的项目，则要预留替代或自维护的人力。风险点在于 0.89 仍是候选版，API 移除清单可能在稳定前微调，生产升级应等到 12 月正式版并观察一段时间。跨端选型上，这也说明 RN 的演进重心已从追平原生体验转向收敛架构、降低复杂度。对于把 0.88 视为长期基线的团队，还需关注社区插件的维护活跃度——那些只声明支持旧架构、长期未更新的库，往往就是这次迁移中最先报错的环节，提前建立替代清单比临时抱佛脚更稳妥。此外，升级前用自动化脚本扫描全部原生模块对新架构的适配声明，能显著降低回归阶段的排查成本。

### 4. 【CocoaPods 进入只读倒计时：SwiftPM 编译缓存提案补位】

**导语**：
Swift 社区 11 月更新中有一条容易被忽略却影响面很广的时间表：经过两年过渡期，CocoaPods 将于 2026 年 12 月 2 日起停止接收新 Pod 与版本更新，进入只读模式。老项目不会立刻构建失败，但任何希望通过 CocoaPods 引入新版本依赖的路径都将被关闭。与此同时，Swift 包管理器一侧连续通过了几项针对现代工作流的提案，包括构建性能调试与编译缓存。一边是老牌依赖管理器退场，一边是 SwiftPM 补齐工程化短板，工具链的接力已经进入倒计时，依赖管理迁移从可选项变成了有截止日期的必选项。

**核心信息**：
只读的具体含义是：已有的 Pod 版本仍可正常解析与下载，存量工程可以继续构建，但无法再发布新版本或新增 Pod。这对仍在用 CocoaPods 管理私有组件库的中国团队尤其关键——内部二进制 Pod 若还有迭代计划，必须在 12 月 2 日前完成迁移或改走其他分发渠道。SwiftPM 的补位来自几个已被接受的提案：SE-0545 聚焦构建性能调试，帮助定位耗时环节；SE-0547 引入 SwiftPM 编译缓存，让重复构建不再每次从零开始；还有 SE-0560 提出按 Debug、Release 等构建配置引入条件依赖，解决同一依赖在不同配置下需要不同版本的场景。这些能力的共同背景，是开发流程的结构性变化：当智能体并行工作、测试覆盖持续膨胀时，编译与测试时间从个人不太在意变成团队级瓶颈，可观测性与缓存成为刚需。SwiftLee 也在 11 月 18 日的周刊里提醒读者认真评估迁移，不要等到只读生效后才被动应对。

**影响判断**：
CocoaPods 退场不会造成一夜之间的构建灾难，但会逐步抬高并发包维护成本，建议把它当作一次有明确节点判据的工程改造来排期。可执行的路线是：先用现有工程列出全部直接依赖，按有 SwiftPM 支持、仅二进制、私有库三类分流；优先把有官方 SwiftPM 支持的公共依赖迁走，二进制依赖评估 XCFramework 直引，私有库则尽快发布为 SPM 包。迁移过程中要重点回归资源包、module 配置与由于依赖传递规则不同而引起的符号冲突。对新人而言，直接以 SwiftPM 作为默认选择即可，不必再为新项目引入 CocoaPods。风险在于历史较久的 Objective-C 依赖可能没有维护者提供 SPM 支持，这类依赖需要内部接管。把迁移窗口放在 12 月 2 日之前，是避免被动的最稳妥做法。

### 5. 【Xcode 编译缓存断点变灰：LLDB 虚拟路径映射排查】

**导语**：
Xcode 27.1 之后，一些启用 Tuist 编译缓存的团队遇到了诡异现象：App 能正常构建和运行，但断点全部变灰，怎么打都不触发。开发者 Lee YoungJun 在 2026 年 11 月的分享中给出了结论——问题不在缓存本身，而是调试信息里的源文件路径缺少 LLDB 映射。为了让编译缓存不依赖工程的绝对路径，Xcode 27 会把调试信息中的源文件路径替换成 /^src 之类的虚拟前缀；如果 LLDB 不知道 /^src 对应本机哪个目录，自然无法把断点落到源码上。这是一个典型的工具链升级后看似无关、实则致命的小坑，往往在真正需要调试时才暴露。

**核心信息**：
复现路径相当清晰：开启 Tuist 编译缓存，构建并运行 App，观察断点呈灰色且无命中。排查时要理解 Xcode 27 的虚拟前缀机制——它把源码路径抽象化，使同一份缓存产物可在不同机器上命中，代价是调试信息里不再有真实路径。Tuist 会生成一份包含缓存配置的 LLDB 初始化文件，但出问题的版本缺少 target.source-map 设置，于是映射链条断在最后一环。解决办法只需补一条 LLDB 命令，把 /^src 指回工程实际目录，断点即可恢复。值得注意的是，这类问题往往不会被编译错误提示，只在调试阶段暴露，因此很容易被误判为缓存不可用而回退整个加速方案。它也与 Swift 生态近期对构建效率的关注形成呼应：当并行智能体与更大测试集成为常态，编译缓存几乎是必选项，配套的可观测性和调试链路必须一起验证，否则提速的收益会被调试失效抵消，反而拖慢整体节奏。

**影响判断**：
对已启用或计划启用编译缓存的团队，这条经验的价值在于把能构建与能调试拆成两个独立验收项。建议在引入缓存后立刻做一次断点冒烟测试：在业务关键路径下断点、单步、查看变量，确认 LLDB 映射正确，再进入日常开发。若团队自研缓存方案或使用第三方工具，应主动检查生成的 LLDB 初始化文件是否包含 target.source-map，并在 CI 与本地两台环境分别验证。对仍未采用编译缓存的团队，这不必成为劝退理由——虚拟路径映射是一次性配置，配好之后长期受益。风险点在于 Xcode 小版本升级可能改变虚拟前缀的格式或初始化文件生成逻辑，每次升级后都应重跑断点检查。把这条纳入升级清单，比出问题再排查要省时得多，也与 SE-0547 的缓存提案形成实践上的呼应。

### 6. 【SwiftUI inspector 自适应面板：宽屏侧栏窄屏弹出式的适配坑】

**导语**：
SwiftUI 的 inspector 是一个自适应上下文面板：在宽屏布局中它以侧栏形式与主内容并排出现，在紧凑环境里则自动收起为弹出式卡片。这个本应提升适配效率、且在 iPhone Duo 这类折叠屏设备上大有用武之地的组件，近期被开发者 Natascha Fadeeva 在 iOS 27.2 上实测发现若干行为并不如预期。相比被反复讨论的 .sheet，inspector 的曝光度一直不高，但正是这种低关注度高用途的组件，一旦踩坑就很难找到现成答案，需要开发者自己把行为边界摸清楚。

**核心信息**：
实测列出的差异集中在几个方面：其一，用下滑手势关闭 inspector 后，它可能无法正常再次打开，需要额外的状态处理才能恢复；其二，通过 inspectorColumnWidth 指定的宽度可能完全不起作用，布局仍由系统决定；其三，通过 Binding 改变选中 detent 时，面板高度不会像普通 .sheet 那样动态跟随，而是保持原样。这些表现说明 inspector 并不是换了个位置的 sheet，它有自己独立的呈现与状态管理逻辑，直接照搬 sheet 的经验会失效。与此同时，社区还在讨论相邻的玻璃态组件 GlassEffectContainer：它能让 Liquid Glass 元素相邻时自然合并与形变，配合 glassEffectUnion、glassEffectID 与 glassEffectTransition 控制分组与转场；有开发者实测发现两个相距 12pt 的形状需要把 spacing 调到约 24pt 才开始接触，而 glassEffectID 在某些跨位置形变中反而会造成动画跳变。这两类细节共同指向一个事实：新控件的行为边界需要靠实测确认，而不是照搬文档示例。

**影响判断**：
对正在为折叠屏、iPad 分屏或多场景适配做技术选型的团队，inspector 仍然值得采用——它的自适应本质在可用空间频繁变化的设备上比固定 sheet 更有优势，但必须把上面几个坑写成项目内的使用规范。具体建议是：不要依赖手势关闭后的自动重开，自己做状态兜底；不要把 inspectorColumnWidth 当作精确控制手段，把它当作提示；不要期望 Binding 改 detent 能实时改高度，必要时重建整个 inspector。测试策略上，必须在真机折叠状态、横竖屏切换和 iPad 分屏三种场景分别验证。风险在于这些行为属于系统实现细节，后续版本可能修正也可能固化，因此建议封装成团队内部的统一组件，把差异收敛到一处。学习优先级上，先掌握 inspector 与 sheet 的适用边界，再研究 GlassEffectContainer 的合并规则，比追逐每一个新 API 更有性价比。

### 7. 【Google Antigravity 走进 Android Studio：ACP 协议接入原生 IDE】

**导语**：
Google 的智能体 Antigravity 正在从独立 IDE 走向开发者已有的工作环境。按 2026 年 11 月 15 日核对的官方文档，Android Studio 通过 Bring Your Own Agent 机制在稳定版中集成 Antigravity，JetBrains 系列 IDE 通过 JetBrains AI 安装，Xcode 则通过 Intelligence 面板接入。连接的核心是 ACP（Agent Client Protocol）：IDE 作为客户端与智能体通信，开发者不必再为用智能体而切换工具。对 Android 开发者而言，最直接在 Android Studio 的 Agent 窗口选择 Google Antigravity 并登录即可，若列表中缺失，IDE 会自动安装，配置入口集中在 Settings 中统一管理。

**核心信息**：
Android Studio 侧的操作路径是：升级到支持 Rabbit 2 的稳定版，打开 Agent 窗口，从列表选择 Google Antigravity，按提示登录；也可以在 Settings → Tools → AI → Agents 中统一管理已安装的智能体。官方文档建议用一个真实场景试水，比如让智能体分析项目里的 Gradle 构建错误。JetBrains 侧要求 IntelliJ 系列 IDE 为 2026.2.1 或更高版本，在 JetBrains AI → Settings → Agents 中搜索并安装 Antigravity，再在 AI Chat 里选择它；若 IDE 提示缺少 AI Assistant 插件，需先安装以打开 AI Chat。Xcode 侧门槛是 macOS 上 Xcode 27 beta 6 以上，路径为 Xcode → Settings → Intelligence，选择获取 Antigravity 并登录；需要手动配置 ACP 时，可安装 Antigravity CLI，用 which agy 取得绝对路径，在 Add an Agent 中把 Command 填为该路径、Arguments 填 acp。官方特别提醒 Xcode 的配置不会展开 ~ 符号，也不会读取 shell 的 PATH，必须写绝对路径。

**影响判断**：
把智能体嵌进既有 IDE 的意义，在于把换工具用智能体变成在原工作流里用智能体，这对调试构建错误、解释陌生代码、生成可审阅的 diff 这类高频任务尤其有价值。对 Android 团队，建议先在非关键分支试 Gradle 错误分析与文件解释，确认智能体对工程上下文的理解程度，再逐步扩大到代码改动；由于改动以 diff 形式呈现，人工审阅仍然是必要关卡。对同时在 iOS 与 Android 之间切换的开发者，ACP 带来的统一接入方式意味着一套智能体配置可跨 IDE 复用，但 Xcode 的 PATH 限制和 beta 版本要求需要单独记录。风险点在于能力边界：智能体生成的代码质量依赖项目上下文与提示质量，直接合入主分支并不稳妥；此外 JetBrains 与 Xcode 的版本门槛较高，老环境升级成本要纳入评估。把 ACP 当作工具链演进的方向来理解，比把它当成某个 IDE 的附加功能更有长期价值。对团队管理者而言，还可以把智能体辅助纳入代码评审规范：要求所有由智能体生成或大幅改写的代码都附带清晰的改动说明与人工复核记录，既不因噎废食地拒绝工具，也不把质量把关完全交给自动补全。随着 ACP 在更多 IDE 中落地，这类跨工具的协作规范会比单一 IDE 的操作技巧更耐用。
