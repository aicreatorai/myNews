### 1. 【vercel-labs/agent-browser：给 AI 智能体用的浏览器自动化命令行工具】（⭐ 48.4K）

> 📍 **导语**（80-100字）: agent-browser 是 Vercel 开源、用 Rust 编写的浏览器自动化命令行工具，专门面向 AI 智能体设计。它把浏览器变成模型可以亲手操作的"眼睛和手"，解决了让大模型稳定驱动网页的难题，是 Agent 从"只能聊"走向"能干活"的关键一环，值得关注。

---

▌ 它是什么

agent-browser 是 Vercel 实验室推出的一款开源命令行工具，定位非常明确：它不是给人用的浏览器，而是"给 AI 智能体用的浏览器"。它的底层用 Rust 编写，以单个二进制文件的形式分发，提供一组面向大语言模型的原子操作接口，让 Agent 能够像人一样打开网页、点击按钮、填写表单、滚动页面、截取屏幕并抽取页面上的结构化内容。在 Vercel 的 Agent 工具版图里，它与此前已经热门的 agent-desktop（Computer Use 命令行工具）形成互补：agent-desktop 负责"操控整个操作系统桌面"，agent-browser 则把火力集中在"操控浏览器"这一最常被 Agent 调用的高频场景上。它在本周 GitHub Trending 周榜中以约 4.8 万星标、单周新增两千余星的成绩进入前列，说明"让模型驱动浏览器"已经成为开发者最迫切的需求之一。

▌ 它解决了什么问题

过去一年，让 AI 操作浏览器主要有两条路，但都不够好。第一条路是用截图加坐标点击的视觉方案，模型先看懂截图再预测点击位置，这种方式对分辨率、页面布局极其敏感，稍微错位就点错按钮，而且速度慢、成本高。第二条路是引入 Playwright、Puppeteer 这类通用端到端测试框架，它们功能强大，但本质上是给测试工程师写的，需要开发者写大量胶水代码，并不适合直接被 Agent 当作"工具"来调用。agent-browser 的出现正是为了填平这道沟：它把"打开网页、读内容、点元素、填表单"这些动作封装成一套简洁、稳定、可被模型直接调用的命令与工具，让开发者不必再为了驱动一个浏览器而搬出整套 E2E 测试栈。对于需要自动填表、自动比价、自动巡检网页、自动做网页可用性测试的场景，它把门槛降到了最低。

▌ 核心原理拆解

agent-browser 的核心并不神秘，它建立在浏览器底层的 DevTools 协议（CDP）之上。所谓 CDP，就是 Chrome 等浏览器暴露给外部程序的一套调试接口，可以远程控制页面的导航、DOM 操作、网络请求和运行时状态。agent-browser 用 Rust 封装了这套协议，向上层暴露成一组对模型友好的命令，比如打开某个网址、查询页面上符合某条件的元素、点击元素、输入文本、等待某个条件成立、把页面内容抽取成干净的 Markdown 或结构化数据。Rust 的选型带来了两个直接好处：一是单二进制、无运行时依赖，下载就能跑；二是内存安全与高并发下的低延迟，适合被 Agent 在循环里反复调用。更重要的是，它的设计哲学是"CLI 优先 + 可被 MCP 调用"，这意味着它既能在终端里手动调试，也能无缝接入 Claude、Cursor 等支持工具调用的智能体，成为 Agent 工作流里的一个标准节点。

▌ 动手验证

想亲自试一下非常简单。由于是 Rust 项目，你可以从项目的发布页下载对应平台的预编译二进制，也可以通过 Rust 工具链自行构建。最直观的体验路径是：先在终端启动 agent-browser 并让它打开一个网页，例如执行打开目标站点、截图保存、再抽取正文内容的命令序列；你会看到它返回的是已经清理过的页面文本，而不是满屏的导航栏和广告。把它接进智能体时，通常的做法是在 Agent 的工具配置里声明 agent-browser 提供的几个动作，然后让模型在需要"看网页"或"操作网页"时自行选择调用。对于想做网页自动化测试的人，你可以用它写一个脚本：打开登录页、填入测试账号、点击登录、断言跳转成功，整套流程不需要写一行 Playwright 代码。验证是否成功的标准也很朴素：模型能否在少样本提示下稳定完成"打开—读取—点击—回填"的完整闭环。

▌ 对比选型

| 工具 | 语言/形态 | 面向人群 | 关键差异 |
| --- | --- | --- | --- |
| agent-browser | Rust / CLI | AI 智能体 | 原生面向 Agent，轻量单二进制 |
| Playwright | Node/Python | 测试工程师 | 功能全但需写代码，偏重 |
| Puppeteer | Node | 前端开发者 | 仅 Chrome 系，需编程 |
| Browser Use | Python | Agent 开发者 | 偏 Agent 框架，重依赖 |

如果你只是想让模型"能开网页、能点按钮"，agent-browser 是最轻、最顺手的选择；若你需要写一套完整的回归测试套件，Playwright 仍是更成熟的底座。

### 2. 【D4Vinci/Scrapling：覆盖单请求到大规模爬取的 Python 网页抓取框架】（⭐ 99.9K）

> 📍 **导语**（80-100字）: Scrapling 是一个用 Python 编写的网页抓取框架，自称能"从单个请求到全规模爬取"一肩挑。它把反爬对抗、动态渲染、智能抽取统一进一套 API，解决了爬虫项目长期碎片化、难维护的痛点，本周以近十万星标、单周新增八千余星冲上 Trending 前列。

---

▌ 它是什么

Scrapling 是一个定位相当"贪心"的 Python 爬虫框架，它的口号是处理"从单个请求到全规模爬取"的一切抓取需求。换句话说，它既想当 requests 那样随手一发请求的轻量工具，又想当 Scrapy 那样能撑起全站分布式爬取的重型引擎。项目用 Python 实现，提供了类似 Scrapy 的管道式 API，同时吸收了 requests 与 httpx 的简洁风格，让初学者也能在几行代码内完成一次抓取。它在本周 GitHub Trending 周榜中总星标接近十万，单周新增超过八千星，是榜单里增长最猛的项目之一，也反映出"高质量、抗反爬的网页数据获取"依然是开发者永恒的需求。

▌ 它解决了什么问题

网页抓取这件事，看似简单，实则处处是坑。第一是反爬：现代网站普遍部署了验证码、行为风控、指纹识别，传统爬虫一上来就被封。第二是动态渲染：大量内容由 JavaScript 在浏览器里跑出来，单纯拉 HTML 源码拿到的是空壳。第三是结构不稳定：页面改版、类名随机化，写死的解析规则随时崩。第四是规模问题：从抓一个页面到抓一整个站点，架构完全不同。过去这些痛点要用好几个工具拼：requests 抓静态页、Playwright 跑动态页、BeautifulSoup 解析、再自己写调度与去重。Scrapling 的野心就是把这条碎片化的链路收拢成一套框架，让你在"小规模随手抓"和"大规模系统爬"之间用同一套心智模型切换，不必每次都重新搭轮子。

▌ 核心原理拆解

Scrapling 的核心思路是"自适应解析加反检测抓取"。在抓取层，它内置了对 JavaScript 渲染页面的支持，能够在需要时启动无头浏览器获取真实渲染结果，也能在页面是静态时直接走轻量 HTTP，避免无谓的性能浪费。在对抗反爬方面，它内建了指纹伪装、请求节奏控制、代理轮换等机制，尽量让流量看起来像真人。在抽取层，Scrapling 提供了智能提取能力，可以根据页面结构自动定位目标字段，而不要求你精确定位每一个 CSS 选择器。它用类似 Scrapy 的"抓取管道"概念组织代码：你定义要抓什么、怎么清洗、存到哪里，框架负责调度、并发与重试。这种设计让它在保持 Python 易用性的同时，具备了向大规模爬取扩展的能力，是一个典型的"小用轻、大用稳"的框架。

▌ 动手验证

上手 Scrapling 的方式很 Pythonic。安装后，你可以先用最轻量的"单请求"模式：给定网址，让它返回解析后的页面对象，再用它提供的属性或选择器提取标题、价格、正文等字段，整个过程不需要启动浏览器。当你需要抓一个列表页下的成百上千个详情页时，可以切换到它的管道模式，定义起始 URL、解析回调函数与数据导出器，框架会自动处理请求队列、并发与失败重试。验证效果最直观的办法是找一个带反爬的电商或论坛页面，分别用传统 requests 和 Scrapling 去抓，对比是否被拦截、是否拿到渲染后的真实内容。你也可以观察它是否能自动适应页面结构的微小变动——这正是它区别于老一代解析库的核心卖点。

▌ 对比选型

| 工具 | 擅长 | 短板 | 适用 |
| --- | --- | --- | --- |
| Scrapling | 单请求到爬取一体、抗反爬 | 生态较新 | 全场景爬虫 |
| Scrapy | 大规模分布式爬取 | 动态页需配合 | 企业级爬虫 |
| BeautifulSoup | 纯解析、极简 | 不负责抓取 | 解析已有 HTML |
| Playwright | 动态渲染精准 | 重、慢、贵 | 渲染型抓取 |

如果你希望"一个框架管所有抓取场景"，Scrapling 是当下最值得试的新选择；若你已经有一套成熟的 Scrapy 体系，则可以作为轻量补充。

### 3. 【milind-soni/OpenMausBot：给聊天机器人用的开源虚拟机运行环境】（⭐ 19.6K）

> 📍 **导语**（80-100字）: OpenMausBot 是一个开源项目，定位为"带虚拟机的 Grok Bot 开源替代方案"，让聊天机器人不只是生成文本，而是能在隔离的虚拟机里真正执行代码与任务。它把"会聊"和"会做"打通，并以隔离保障安全，是 Agent 执行层的有趣探索。

---

▌ 它是什么

OpenMausBot 的标签很直白：一个"带虚拟机的开源聊天机器人替代方案"。它的核心主张是，聊天机器人不应该只停留在"吐出一段文字建议"，而应该能够真正动手执行——运行代码、调用工具、完成多步任务。为了实现这一点，OpenMausBot 给机器人附带了一个虚拟机运行环境，bot 可以在这个隔离空间里安全地执行命令和脚本，再把结果回馈给用户。它是用 TypeScript 编写的，本周在 GitHub Trending 周榜中以约一万九千星标、单周新增七千余星的成绩崭露头角。从定位上看，它瞄准的是"让对话式 AI 具备可执行能力"这一越来越热门的方向，可以被理解为对闭源方案的开源平替。

▌ 它解决了什么问题

我们身边的大部分聊天机器人有一个共同的尴尬：它们很会"说"，但几乎不能"做"。当你让一个普通 bot 帮你跑一段数据处理、生成一张图表、或者自动整理一批文件时，它通常只能给你一段代码让你自己去跑。这种"知行分离"极大限制了对话式 AI 的实用性。更麻烦的是，一旦真的让 bot 执行代码，安全问题立刻浮现：在宿主机上直接跑不可信代码等于开门揖盗。OpenMausBot 要解决的正是这一对矛盾：既要让 bot 能执行，又要让执行发生在隔离、可丢弃的虚拟机里，从而把风险关进笼子。对于想搭建"既能对话又能动手"的个人助手或自动化机器人的开发者，它提供了一条现成的、开源可审计的路径。

▌ 核心原理拆解

OpenMausBot 的架构可以理解成"对话前端 + 隔离执行后端"两部分。对话前端负责接收用户的自然语言指令，并把它们翻译成可被执行的任务；执行后端则是一个独立的虚拟机运行时，bot 产生的代码或命令被送到这里运行，运行结果再回传给对话层。虚拟机的隔离性意味着：即使执行的代码出错、甚至带有恶意，影响也被限制在这一临时环境内，不会波及宿主系统。用 TypeScript 实现则让它天然适合接入 Web 与 Node 生态，便于部署成一个可被远程调用的机器人服务。从更广阔的视角看，它属于"代码沙箱 + Agent"这一范式——和专门的代码执行沙箱（如 E2B、Daytona）思路相通，但 OpenMausBot 更聚焦"聊天机器人"这一具体场景，把对话、执行、反馈闭环打包在了一起。

▌ 动手验证

想本地体验，一般的路径是先把仓库克隆到本地，安装 TypeScript 项目的依赖，然后按照说明启动机器人服务并接入你选择的模型或消息平台。接入之后，你可以试着给 bot 下达一个需要执行的小任务，例如"帮我算一下这组数字的平均值并画个图"，观察它是不是真的在虚拟机里跑了一段代码、再把结果返回给你，而不是仅仅回复一段示例代码。验证安全隔离的办法也很直接：让 bot 执行一条会试图访问宿主文件系统的命令，确认它无法越出虚拟机边界。对开发者而言，真正有价值的验证是：它能否把"多轮对话里的意图"稳定地映射成"可执行的任务"，并且失败时能优雅回退，而不是把错误甩给用户。

▌ 对比选型

| 方案 | 形态 | 隔离 | 定位 |
| --- | --- | --- | --- |
| OpenMausBot | 聊天机器人+VM | 虚拟机隔离 | 对话式可执行 bot |
| 普通 Chatbot | 纯文本 | 无 | 只聊不做 |
| E2B | 代码沙箱 | 强隔离 | 通用代码执行 |
| AutoGPT 类 | Agent 框架 | 视实现 | 自主任务 |

如果你要的是"一个能动手聊天的机器人"且希望开源可控，OpenMausBot 值得一试；若你只需要把任意代码丢进沙箱跑，专门的代码沙箱更专业。

### 4. 【Donchitos/Claude-Code-Game-Studios：把 Claude Code 变成 49 个智能体的游戏开发工作室】（⭐ 37.5K）

> 📍 **导语**（80-100字）: Claude-Code-Game-Studios 是一个开源项目，把单个 Claude Code 改造成拥有 49 个 AI 智能体、72 个工作流技能、并模仿真实游戏工作室层级结构的完整开发体系。它解决了个人用 AI 做游戏时"缺乏分工与协作"的难题，本周以三万七千余星标登上 Trending。

---

▌ 它是什么

Claude-Code-Game-Studios 是一个用 Shell 组织的开源项目，它的想法相当壮观：与其让一个人对着一个 Claude Code 会话慢慢磨游戏，不如把 Claude Code 升级成一整个"游戏开发工作室"。这个项目预置了 49 个 AI 智能体、72 个工作流技能，以及一套完整、刻意模仿真实游戏公司层级结构的协调系统。从策划、美术、程序到 QA，现实工作室里有的角色分工，这里都用对应的 Agent 与技能来对应。它在本周 GitHub Trending 周榜中以约三万七千星标、单周新增五千余星的成绩上榜，说明"用多智能体协作完成复杂创作"正从概念变成可下载的模板。

▌ 它解决了什么问题

一个人想用 AI 做一款游戏，最常见的瓶颈不是"模型不够聪明"，而是"没有组织"。你可能会让同一个会话既写剧情、又画原画、又敲代码、又做测试，结果上下文越堆越乱，各个工种的产出互相打架，没人统筹。真实游戏工作室之所以有策划、美术、程序、QA 的分工，正是因为复杂创作需要专业化与协作。Claude-Code-Game-Studios 正是把这套组织智慧搬进了 AI 工作流：它用多个职责单一的 Agent 替代一个啥都干的会话，用 72 个技能覆盖各工种的标准动作，再用协调系统负责任务的拆解、派发与交接。对个人开发者和小团队来说，这相当于免费雇了一支"虚拟工作室"，显著降低用 AI 从零做游戏的协作复杂度。

▌ 核心原理拆解

这个项目本质上是在 Claude Code 既有的"子智能体（subagent）+ 技能（skill）"机制上做了一层厚重的领域封装。Claude Code 本身支持把一个大任务拆给多个子 Agent 并行或串行处理，也支持加载预设的技能来规范某类工作的做法。Claude-Code-Game-Studios 做的，是把游戏开发这条业务线彻底"角色化"：49 个 Agent 各自对应一个岗位（比如系统设计师、关卡策划、像素美术、着色器程序、自动化测试），72 个技能则把这些岗位的日常动作沉淀成可复用的流程。协调系统负责把"做一个能跑的 2D 平台游戏"这样的大目标，逐级分解到具体岗位、再由岗位调用对应技能去产出，并在岗位之间传递资产与文档。它是一种"组织即提示词"的思路——把管理真实团队的层级结构，翻译成智能体之间的调用与交接关系。

▌ 动手验证

使用它的典型流程是：先把仓库克隆到本地，按照 README 完成工作室配置的初始化，让你的 Claude Code 加载这套角色与技能定义；然后像给工作室老板下brief 一样，用自然语言描述你想做的游戏，例如"做一个俯视角的像素风roguelike，三关，带 Boss"。接下来你会看到协调系统把目标拆给不同 Agent，各 Agent 调用对应技能去产出策划文档、美术资源、代码片段与测试用例，并在彼此之间交接。验证它是否好用的关键，不是看它生成了多少文件，而是看这些文件之间是否"对得上"：美术输出的尺寸程序能不能直接用、策划定的数值代码有没有实现、QA 发现的 bug 有没有回流到对应岗位。对想动手的人，建议先从一个极小的游戏原型开始，体会分工带来的秩序感。

▌ 对比选型

| 方案 | 分工 | 门槛 | 适用 |
| --- | --- | --- | --- |

### 5. 【astral-sh/ruff：用 Rust 编写的高性能 Python 代码检查与格式化工具】（⭐ 38K+）

> 📍 **导语**（80-100字）: ruff 是由 Astral 公司用 Rust 打造的下一代 Python 代码检查器与格式化工具，以数十倍于传统工具的速率为 Python 项目提供 lint 与格式化。它正在取代 flake8、black、isort 等多款老牌工具，是近年最受欢迎的开发者效率工具之一，本周再次进入 Trending 视野。

---

▌ 它是什么

ruff 是一个用 Rust 编写的现代 Python 工具链，它把"代码检查（lint）"和"代码格式化（format）"两件开发者每天都要做的事，合并进一个极速、一体化的命令行工具里。在它出现之前，一个规范的 Python 项目往往要同时装 flake8（查错）、black（格式化）、isort（导包排序）、pydocstyle（文档规范）等好几款工具，各自有配置、各自跑一遍，既慢又容易冲突。ruff 的目标就是"一个工具顶替这一整抽屉"。它由 Astral 公司主导开发，凭借 Rust 带来的性能优势，在很多项目上比传统 Python 实现的工具快上十倍到上百倍。它已经积累了极高的社区采用率，是近两年开发者效率工具里最具代表性的开源项目之一。

▌ 它解决了什么问题

Python 社区的"工具碎片化"是个老问题。一方面，代码风格与规范靠一堆各管一摊的小工具拼凑，配置散落、版本互相掣肘；另一方面，这些工具大多是纯 Python 实现，在大仓库里跑一次全量检查可能要几十秒甚至更久，开发者被迫减少检查频率，规范也就形同虚设。ruff 直击这两个痛点：第一，它把 lint 规则、导入排序、格式化、甚至部分重构能力统一进一个二进制，配置一处搞定；第二，Rust 实现让它在百万行级别的项目上也能秒级完成检查，把"规范检查"从负担变成顺手的事。对团队而言，ruff 还意味着"统一标准"——不必再为用 black 还是用 yapf 争论，ruff format 给出确定性结果，CI 里一键收敛全队风格。

▌ 核心原理拆解

ruff 之所以快，根源在于它用 Rust 重写了 Python 代码的分析与改写全流程。它首先用一个叫 Ruff 自己的解析器（基于 tree-sitter 风格的解析思路）把 Python 源码解析成抽象语法树与 token 流，然后在同一遍遍历里并行执行成百上千条 lint 规则，而不是像老工具那样反复读文件、反复解析。格式化部分则借鉴了业界成熟的格式化算法，但用 Rust 实现以保证速度。由于是单一二进制、几乎零启动开销，它在编辑器里做"保存即检查"时几乎无感延迟。更重要的是，ruff 的规则集刻意兼容并超越了 flake8 的插件生态，许多老规则被重新实现，开发者迁移时几乎不用改习惯。Astral 还围绕它构建了整套 Python 工具矩阵（如 uv 包管理器），ruff 是其中承上启下的效率基石。

▌ 动手验证

接入 ruff 非常轻量。你可以用 Python 的包管理器安装它，也可以直接下载它的独立二进制。最常用的两条命令是检查与格式化：运行检查命令会扫描项目里的 Python 文件并列出违规项，运行格式化命令则会就地把代码改成统一风格。由于速度极快，很多人把它同时接进两处：一是编辑器插件，做到"边写边提示"；二是 CI 流水线，作为合并前的强制关卡。验证它是否生效的最直接方式，是故意写一段风格混乱、导入乱序、还有个未使用变量的代码，然后跑一遍，看它是否准确指出问题并能一键修复。对老项目迁移，建议先用它的兼容规则集并行运行一段时间，确认无误后再彻底替换掉旧工具链。

▌ 对比选型

| 工具 | 语言 | 速度 | 覆盖 |
| --- | --- | --- | --- |
| ruff | Rust | 极快 | lint+format+ |
| flake8 | Python | 慢 | 仅 lint |
| black | Python | 中 | 仅 format |
| pylint | Python | 慢 | lint 深 |

如果追求"一个工具管齐下、又快又稳"，ruff 已基本是 Python 项目的默认答案；若你需要极深的逻辑级静态分析，pylint 仍可作为补充。

### 6. 【floci-io/floci：轻量免费的开源 AWS 本地模拟器替代】（⭐ 本周新上榜）

> 📍 **导语**（80-100字）: floci 是一个用 Java 编写的开源项目，定位为"轻量、免费版的 AWS 本地模拟器替代方案"。它让开发者在本地就能模拟云上的存储、队列、函数等服务，解决依赖真实云账号、本地无法离线联调的痛点，是后端与基础设施开发者的实用新工具，本周新登上 Trending。

---

▌ 它是什么

floci 是一个本周新进入 GitHub Trending 视野的开源项目，它的自我定位非常务实：做一个"轻量、免费的 AWS 本地模拟器替代方案"。所谓 AWS 本地模拟器，指的是一类能够在你自己的电脑上模拟亚马逊云服务的工具，让你不连真云、不开真实账号，也能开发和测试那些依赖云存储、消息队列、无服务器函数的应用。floci 用 Java 实现，主打的是"轻"和"免费"——相比官方那套偏重、且部分能力绑定账号生态的本地模拟套件，floci 试图用更小的 footprint 和完全开源免费的方式，把本地云模拟这件事重新做一遍。对大量在本地写代码、只想快速验证"我的代码能不能正确读写对象存储、能不能正确发消息"的开发者来说，这类工具是日常刚需。

▌ 它解决了什么问题

做云原生或后端开发的工程师几乎都踩过同一个坑：代码里写的是"往 S3 传文件""往 SQS 发消息""触发一次 Lambda"，但本地根本没有这些服务，你要么硬连真实云账号（产生费用、还可能误删线上数据），要么把代码改来改去加一堆"本地分支"。官方提供的本地模拟器虽然能用，但普遍偏重、启动慢、依赖多，而且有些能力仍和云账号生态绑得紧，对只想快速联调的开发者来说杀鸡用牛刀。floci 想解决的正是这种"本地联调摩擦"：提供一个轻量、免费、开箱即用的本地云模拟环境，让开发者在断网或不想碰真实云的情况下，也能把依赖云服务的逻辑跑通、测通。它降低的是"从写代码到验证通过"之间的距离，对提升后端开发迭代速度有直接帮助。

▌ 核心原理拆解

floci 的核心思路是"在本地复刻云服务的接口语义"。云服务的价值很大一部分在于它那套稳定、文档完善的 API 契约——你的代码只认 API，不关心背后是谁实现的。floci 正是利用这一点：它在本地用 Java 实现了一套与 AWS 主要服务（如对象存储、消息队列、函数计算等）接口兼容的轻量实现，让原本指向云端的 SDK 调用，改个端点就能指向本地。存储类服务通常用一个本地目录或内存结构来模拟桶与对象；队列类服务则维持一个本地的消息缓冲与投递机制；函数类则在本地的轻量运行时里执行你提交的代码包。关键在于接口兼容——只要契约一致，应用代码几乎不用改。相比官方模拟器动辄拉起一整套容器化组件，floci 选择用更精简的实现覆盖最常用的那部分能力，从而换来"轻"与"免费"。

▌ 动手验证

要在本地试用 floci，典型的步骤是先获取它的运行包（由于是 Java 项目，通常以可运行的包或容器镜像形式提供），启动本地模拟服务，然后把你的应用配置里指向云端的端点改成本地地址，例如把对象存储的 endpoint 指向 floci 监听的本地端口。接下来，你可以用应用原本的逻辑做一轮读写：上传一个文件再看能否下载回来，发一条消息再看能否被消费，触发一次函数看是否执行。验证成功的标准很朴素：原本依赖云服务的代码，在零云账号、零费用的前提下跑出了和连真云一致的行为。对后端开发者，最有价值的验证是把它接进单元测试与集成测试，让 CI 在本地就能跑通"云依赖"相关的用例，而不必在流水线里偷偷连真实云。

| --- | --- | --- | --- |
| floci | 轻量开源 | 轻 | 免费 |
| 官方模拟器 | 官方套件 | 重 | 免费但重 |

| 第三方模拟 | 各异 | 不一 | 部分收费 |

若你追求"轻、免费、本地即开即用"，floci 是值得关注的新选项；若你需要覆盖 AWS 几乎全部服务的完整语义，官方模拟器覆盖面仍更广。
