### 1. 【RoPE旋转位置编码：让Transformer看懂词序与相对距离】

> 📍 **导语**：RoPE（Rotary Position Embedding，旋转位置编码）是当今主流开源大模型 Llama、Qwen、ChatGLM 乃至 DeepSeek 的"坐标系统"。2026-10 连续多篇论文把它推到聚光灯下：arXiv:2610.28385 的 RACE 用 RoPE 对齐的 KV Cache 压缩，在 256K 上下文把推理 FLOPs 降 47.8%；arXiv:2610.26722 的 VO-rotations 则证明 RoPE 风格的旋转能让两层 Transformer 完美完成"复制并正确终止"这一长期失败任务。为什么一个位置编码值得反复研究？因为它直接决定模型能不能理解"谁在谁前面""隔了多远"，也是长上下文外推的地基。

---

**🧠 深度解析**

**▌ 它是什么？**（概念与边界）
RoPE 是一种把"位置信息"通过旋转矩阵注入注意力计算的方法：它对每个 token 的 query 和 key 施加一个与位置相关的旋转，使二者点积只依赖于它们的相对距离。常见误区是把它当成简单的绝对位置编号——其实 RoPE 编码的是"相对位置"。它的适用边界是：在预训练长度内稳定，超出则需外推。历史上，位置编码从 Transformer 原版的正弦/可学习绝对位置，演进到 ALiBi 距离偏置，再到 2023 年 Su 等人提出的 RoPE；如今 DeepSeek、Qwen、Llama 全系列都依赖它。

**▌ 它解决了什么问题？**（Before → After）
没有 RoPE 之前，绝对位置编码对长序列外推能力差，相对位置感知弱，模型难以泛化到训练未见过的长文本。RoPE 之后，q、k 的旋转角度差天然编码相对距离，外推与长上下文能力大幅提升。具体例子：Qwen2.5-1M 靠 RoPE 缩放把窗口拉到百万；RACE 在 256K 上下文、50% KV 保留下，吞吐提升 1.79 倍、首 token 延迟（TTFT）降 43.2%、GPU 显存降 28.1%——这意味着同一个模型，仅靠更好的位置编码利用方式就能显著提速降本。

**▌ 核心原理三阶拆解**
**第一层：直觉理解**——想象两个向量是钟面上的指针，相对位置就是指针夹角；把 q 和 k 各自按位置转一定角度，它们点积时角度差刚好等于"隔了多少个 token"，注意力于是天然知道距离远近，而不关心绝对在第几个位置。

**第二层：技术流程拆解**——输入 token 位置 m → 对 q、k 每个维度对 (2i, 2i+1) 施加二维旋转矩阵 R(θ_m)，其中 θ_m = m·θ_i，θ_i 由频率基底决定 → 旋转后的 q'、k' 做点积 → 点积结果只依赖 (m−n) 这一相对距离，与绝对位置无关。训练时学到的频率基底在预训练长度内保持稳定，这是外推可行的前提。

**第三层：公式与核心机制**——数学上 RoPE 把位置 m 编码为旋转，使得 ⟨R(m)q, R(n)k⟩ = f(q, k, m−n)，即内积仅是相对位移的函数。关键设计是：低频维度转得慢（捕捉长程结构）、高频转得快（捕捉局部细节）；外推时通过缩放低频旋转率（LongRoPE / YaRN）把未见过的远距"压缩"回已训练区间，这正是长上下文扩展的核心。RACE 进一步证明：只有保留完整的"旋转对"（rotary pair）做坐标选择，才能无重建、无专用 kernel 地兼容 RoPE。

**▌ 动手验证**（最小可运行示例）
用 transformers 直接观察 RoPE 配置，并给出长上下文微调示例：
```python
from transformers import AutoConfig
cfg = AutoConfig.from_pretrained("Qwen/Qwen2.5-7B-Instruct")
print(cfg.rope_scaling, cfg.max_position_embeddings)  # 查看原生 RoPE 设置
# 长上下文微调示例（YaRN 缩放）
rope = {"rope_type": "yarn", "factor": 4.0,
        "original_max_position_embeddings": 32768}  # 原 32K → 约 128K
```
注意：`rope_scaling` 仅在确有长输入的服务开启，否则短文本可能受损；改 `factor` 后需重新评估短任务表现。

**▌ 对比与选型**
| 维度 | RoPE | ALiBi | 正弦绝对 |
|------|------|-------|---------|
| 核心思想 | 旋转注入相对位置 | 分数加距离偏置 | 固定/可学习 |
| 外推能力 | 优秀(配插值) | 非常优秀 | 差 |
| 适用场景 | Llama/Qwen/DeepSeek | 长上下文原生 | 早期Transformer |
| 训练成本 | 中 | 低 | 低 |

### 2. 【线性与稀疏注意力：突破Transformer二次复杂度瓶颈】

> 📍 **导语**：标准注意力的计算量和显存随序列长度平方增长——100 万 token 的注意力矩阵约 1 万亿个元素，是字面意义的"算不起"。2026 年，稀疏与线性注意力成为突破这一瓶颈的主战场：DeepSeek V3.2-Exp 的 DSA、Kimi Linear 的 KDA（KV Cache 减 75%、百万上下文吞吐 6 倍）、MiniMax-01 把"闪电注意力"与 softmax、MoE 融合成 456B 模型，以及 arXiv:2610.28385 的 RACE 用降维注意力把 256K 推理 FLOPs 降 47.8%。理解这条技术线，等于理解长上下文"读得起"的底层逻辑。

---

**🧠 深度解析**

**▌ 它是什么？**（概念与边界）
线性/稀疏注意力是一类把 O(n²) 复杂度降到 O(n) 或 O(n·w) 的注意力变体。误区是认为它们只是"更差的近似"——其实是在不同子空间做精度/效率权衡。边界是：线性层记忆容量固定，通常需保留少量全注意力层做精确检索。历史上从 Performer/Linear Transformer，演进到 Lightning Attention，再到混合架构（稀疏+线性+全注意力并存）。2026 年的工程实践进一步表明，纯线性架构单独使用会丢失精确检索能力，因此 Kimi Linear、MiniCPM-SALA 都采用"线性层负责全局效率、少量全注意力层负责精确检索"的混合设计，这已成为长上下文架构的主流折中，而非简单二选一。

**▌ 它解决了什么问题？**（Before → After）
此前全注意力在长文档上显存爆炸、延迟不可接受（Qwen 团队测算 7B 模型直接处理 100 万 token 时 MLP 激活占 71GB）。之后，稀疏注意力只算最相关 token、线性注意力用固定状态压缩历史。例子：Kimi Linear 的 KDA 在百万上下文解码吞吐最高 6 倍；RACE 在 256K、50% KV 保留下 1.79 倍吞吐、TTFT 降 43.2%、GPU 显存降 28.1%。长上下文终于从"放得下"走向"读得起"。

**▌ 核心原理三阶拆解**
**第一层：直觉理解**——全注意力像给每对新老朋友都单独写一封信（O(n²)）；稀疏注意力只给"最聊得来"的几位写信；线性注意力则把所有人压缩进一份固定大小的"会议纪要"，以后只更新纪要、不再翻旧信，成本与长度脱钩。

**第二层：技术流程拆解**——输入序列 →（稀疏）轻量索引器给历史 token 打分，挑 Top-k 做精细注意力 /（线性）用核函数或状态矩阵把 key-value 累积成固定维度状态 S → 当前 query 只与 S 交互 → 输出。DeepSeek DSA 先索引再精选；MiniCPM-SALA 把 InfLLM-V2 高保真稀疏与 Lightning Attention 全局效率结合，形成 9B 混合架构。

**第三层：公式与核心机制**——线性注意力的核心是把注意力重写为 φ(q)φ(k)ᵀv 的低秩/核形式，状态 S = Σ φ(k_i)v_i 随长度线性累积而不随 n 增长；稀疏则通过块内+块间重映射（DCA 思路）把远距离拉回已训练范围。代价是线性层会遗忘或混淆久远细节，所以混合架构保留少量全注意力层专责精确检索；RACE 则证明降维必须保留完整旋转对才能兼容 RoPE，否则需运行时重建、徒增解码 FLOPs。值得注意的是，RACE 的降维并非简单剪枝，而是基于"query-key 联合激活能量"挑选旋转对，理论证明该准则最小化校准相关的上界，因此在不重建、不专用 kernel 的前提下即可折叠进权重，这是它与传统结构化剪枝的本质区别，也解释了为何它在 256K 上下文仍能保持语言建模与零样本任务的竞争力。

**▌ 动手验证**（最小可运行示例）
用 transformers 开启 FlashAttention（硬件支持时）；稀疏/线性需专用实现：
```python
from transformers import AutoModelForCausalLM
model = AutoModelForCausalLM.from_pretrained(
    "deepseek-ai/deepseek-v3.2-exp",  # 示意
    attn_implementation="flash_attention_2")
# 稀疏/线性（DSA、KDA）需 vLLM 等框架的 Day0 支持，并非原生 transformers 开关
```
注意：线性/稀疏主要降成本，不自动保证识别准确率，选型须同时看效率数字与长上下文评测。

**▌ 对比与选型**
| 维度 | 全注意力 | 稀疏(DSA) | 线性(KDA) |
|------|---------|----------|----------|
| 复杂度 | O(n²) | O(n·k) | O(n) |
| KV显存 | 大 | 中 | 小(固定) |
| 长程精度 | 高 | 高 | 中(需混合) |
| 成熟度 | 主流 | 新(DeepSeek) | 新(Kimi) |

### 3. 【长上下文Lost in the Middle：百万Token为何读不懂中间信息】

> 📍 **导语**：标称 100 万 token 的旗舰模型，在大海捞针（NIAH）测试里几乎全部满分，可一旦任务需要跨三段推理的"链式查找"，差距立刻拉开：2026 年一项 1M-token 评测显示 Gemini Pro、Claude 到 512K 仍保持 80%+ 准确率，而 GPT-5.5、Qwen3.6-plus 在 512K→1M 之间断崖崩盘。更隐蔽的是"Lost in the Middle"——信息藏在长文本中段时模型容易忽略。窗口能放下，不等于模型能用好，这正是长上下文工程必须正视的第二层问题。

---

**🧠 深度解析**

**▌ 它是什么？**（概念与边界）
"Lost in the Middle"指模型对长输入首尾信息利用充分、对中段信息利用不足的现象，是长上下文能力失败的可见形态之一。误区是以为 NIAH 满分就代表真能读长文。边界是：问题不只在中段位置，更在证据"分散度"与"推理深度"。历史上从 NIAH → RULER（加多针/多跳/聚合）→ LURCH（分解为证据范围/分散度/推理深度）→ Context Rot，评测方法越来越逼近真实失效。

**▌ 它解决了什么问题？**（Before → After）
此前仅用 NIAH 单针检索评估，掩盖了多跳与分散证据的失败。之后，RULER 用 17 个模型测试发现多数在 32K 后随长度明显掉点、仅约一半满意；LURCH 在 6550 题上证明证据分散度、推理深度与表现强负相关；Context Rot 显示输入越长表现越不可靠。例子：Agent 监控研究中，危险动作藏在 80 万 token 无害记录后，被漏判次数是单独出现时的 2–30 倍——这是真实长记录场景的代价。

**▌ 核心原理三阶拆解**
**第一层：直觉理解**——把长文档想象一摞文件，模型像阅卷老师，对开头结尾的卷子看得最细，中间那叠容易扫一眼就过；这不是看不见，而是"注意力权重"被首尾吸走，中段信号被稀释。

**第二层：技术流程拆解**——评测设计 → 控制变量（任务难度不变只加长度 / 把多根针分散放置 / 要求多跳串联）→ 记录各长度、各位置准确率 → 发现中段与分散证据处掉点。生产侧缓解：在长记录里定期插入提醒，可部分缓解漏判；更好的后训练也可能进一步改善。

**第三层：公式与核心机制**——LURCH 把难度拆成三维：证据范围（evidence scope）、证据分散度（dispersion）、推理深度（reasoning depth），三者均与表现负相关；Context Rot 指出模型并非均匀使用上下文，且部分推理类评测不控制目标任务位置，导致可能忽略位置相关失败。结论性经验：标称窗口的 60%–70% 才是可靠质量区，选型和评估第一步是用接近真实任务的方式测，而非看窗口标称值。这也解释了为何厂商自报的"百万上下文"在真实多跳任务上常翻车——标称窗口只是容量上限，而 LURCH 三维与 Context Rot 才是质量下限的探针；在长记录里每隔一段插入提醒可部分缓解漏判，但更根本的解法仍是更好的后训练与检索编排。

**▌ 动手验证**（最小可运行示例）
用 RULER 风格自测本地长上下文模型的多针+多跳能力：
```python
# 伪代码：多针 + 多跳检索评测（非单针 NIAH）
needles = [("key1","v1"),("key3","v3"),("key5","v5")]
ctx = build_long_context(needles, filler_tokens=200_000)
prompt = "按出现顺序拼接 key1,key3,key5 的值："
print(ask_model(ctx, prompt))  # 期望稳定返回 "v1v3v5"
```
注意：自测要用接近真实任务的多跳/分散证据，而非单针 NIAH，否则会高估能力。

**▌ 对比与选型**
| 维度 | NIAH | RULER | LURCH |
|------|------|-------|-------|
| 测什么 | 单针检索 | 多针/多跳/聚合 | 范围/分散/深度 |
| 暴露中段 | 弱 | 中 | 强 |
| 适用 | 下限测试 | 综合能力 | 失效归因 |
| 局限 | 仅词面 | 仍偏检索 | 题量有限 |

### 4. 【长上下文位置编码扩展：从8K到百万Token的窗口拉长术】

> 📍 **导语**：一个只在 8K 文本上训练过的模型，硬塞进 100 万 token，就像让只在 A4 纸上练题的人突然面对一面墙大的答题卡——坐标感会崩溃。主流模型靠 RoPE 提供位置信号，但推理时遇到训练未见的超大相对距离，注意力就会失真。2026 年，"位置编码扩展"已成一整套工程：YaRN 进入 NVIDIA NeMo RL 训练框架，LongRoPE 在 llama.cpp / vLLM / Ollama 全面落地，Qwen2.5-1M 用分阶段配方把窗口拉到百万。

---

**🧠 深度解析**

**▌ 它是什么？**（概念与边界）
长上下文位置编码扩展，是不从头重训、通过调整位置编码把短上下文预训练模型扩展到更长窗口的方法族。误区是以为标称"支持 100 万 token"多等于"原生训练到 100 万"。边界是：外推治"越界"，治不了"训练没学好"。历史上从线性插值 → NTK-aware → YaRN → LongRoPE → DCA / StRing，思路从"均匀压缩"演进到"频率感知"与"分块重映射"。这类方法共同的前提是"不从头训练"，因此特别适合已有开源权重、想用现成模型拉长窗口的团队，成本最低、见效最快，但治的是"越界"而非"训练时没学好"，这一点必须与训练配方配合使用。

**▌ 它解决了什么问题？**（Before → After）
此前扩展上下文意味着从头重训，成本高到 prohibitive（单张 H200 训 400 万 token 上下文已是极限优化）。之后，RoPE 缩放让 4K 模型处理 1M 文档，质量损失最小、单遍推理、零重训。例子：Qwen2.5-7B 配 DCA 在 1M passkey 任务接近满分；Llama 3.1 从 8K 经 YaRN 扩到 131K；LongRoPE 让 4K 训练模型达 1M，无需新权重。

**▌ 核心原理三阶拆解**
**第一层：直觉理解**——RoPE 像给每个位置发一把"距离尺"，训练只见过短尺范围内的刻度；遇到超长距离，把尺子按比例"压缩"（缩放低频旋转率），让远距落回已熟悉的刻度区间，相对位置直觉不破。

**第二层：技术流程拆解**——选方法 → 调 `rope_scaling`（YaRN：`factor=4.0, original_max_position_embeddings=32768` → 约 128K）→ 或在推理期用 DCA 分块+块间重映射 / StRing 平移充分训练的位置覆盖欠学位置 → 配合分阶段训练（Qwen：4K→256K，RoPE 基底 1 万→1000 万；SFT 先短后长；RL 只用 8K 内）。实际工程里，静态缩放对所有输入一律生效，短文本也可能受影响，因此框架普遍建议只在确有长输入的服务开启；而 Qwen 的分阶段配方还专门保留短指令 SFT，防止长文本能力把短任务表现挤掉，这是"拉长窗口"最容易被忽略的代价。

**第三层：公式与核心机制**——RoPE 把位置 m 旋转，角度随维度频率不同；长程靠低频维度，扩展时只拉伸低频旋转率（L_new/L_train 倍），保留相对位置直觉。LongRoPE 进一步"选择性"拉伸关键维度；DCA 不改缩放而是把超训练距离重映射到已训练范围；StRing 指出有效长度常不到训练长度一半（分布左偏），故平移补齐。质量在超过训练长度约 48 倍后即使 LongRoPE 也退化，需续训或混合 ALiBi。

**▌ 动手验证**（最小可运行示例）
在 vLLM 用 YaRN 启动长上下文模型：
```bash
vllm serve Qwen/Qwen2.5-7B-Instruct-1M \
  --tensor-parallel-size 4 --max-model-len 1010000 \
  --enable-chunked-prefill --max-num-seqs 1
```
注意：官方常需定制分支；7B/1M 至少 120GB 显存（多卡合计），14B 至少 320GB；`rope_scaling` 仅长输入服务开启，短文本服务勿开。

### 5. 【端侧小模型部署：把大模型塞进手机本地离线跑】

> 📍 **导语**：2026 年，把大模型装进手机本地离线运行已从极客玩具变成日常配置。PromptQuorum 2026-10-19 的对比显示：旗舰机（8GB+ RAM）上 Q4_K_M 量化的 Phi-4 Mini（3.8B）在 iPhone 17 Pro 跑出 13–18 tok/s，是最聪明的可用小模型；6GB 旧机用 Qwen3 1.7B 或 SmolLM 2 1.7B 也能连贯作答。无需联网、无调用费、隐私不出端，端侧小模型正在重构"AI 该在哪算"的答案。

---

**🧠 深度解析**

**▌ 它是什么？**（概念与边界）
端侧小模型指参数 0.6B–9B、可离线在手机/PC/边缘设备运行的轻量大模型。误区是"小模型=能力差到不可用"——Phi-4 Mini 的 MMLU 达 69%，每参数推理最强。边界是：复杂多步推理仍弱于云端旗舰；多模态仅 Gemma 3 4B 等少数支持图像。历史上从 TinyLlama → Llama 3.2 3B → Phi-3.5/4 Mini → Gemma 3 / Qwen3 1.7B → SmolLM 3，端侧模型持续变强。值得注意的是，端侧模型的能力边界仍在快速上移，2026 年已经出现支持图像的 Gemma 3 4B 与端侧视觉描述能力，说明"端侧"不再是纯文本的代名词，而是逐步覆盖多模态的本地智能，未来拍照即问答、本地相册检索都将在设备内完成。

**▌ 它解决了什么问题？**（Before → After）
此前所有推理走云端，有延迟、有按调用计费、有隐私出域风险、断网即失效。之后，本地 4–8 tok/s 起的响应、一次性下载后零边际成本、数据不出设备。例子：Phi-4 Mini 在 8GB RAM 旗舰可用；Gemma 3 1B 在 4GB RAM 老机（如 iPhone SE3）也能出 1–2 段连贯回答；Fora Soft 指出端侧推理仅耗几毫瓦、无云调用费，一次性成本只是模型下载带宽（约 $0.01–0.10/用户）。对开发者而言，端侧部署还意味着无需搭建和维护推理服务器，迭代周期从"申请配额—联调—上线"压缩到"本机跑通即交付"，这对独立开发与边缘场景尤为关键，也让离线优先的产品形态成为可能。

**▌ 核心原理三阶拆解**
**第一层：直觉理解**——云端大模型像中央厨房，每点一道菜都要配送；端侧小模型像随身饭盒，一次做好后随时吃，不依赖网络也不花配送费，只是菜单略精简，但胜在随时可用、隐私自留。

**第二层：技术流程拆解**——选模型（按 RAM 档：旗舰 8GB+ 选 3B–4B 的 Q4_K_M；中端 6GB 选 1.7B；入门 4GB 选 1B）→ 量化（Q4_K_M 保约 95% 质量、体积 1/4）→ 选运行时（llama.cpp / MLC LLM / Ollama）→ 下载 GGUF → 本地推理。Google 侧走 LiteRT-LM，已支持 Gemma 4 E2B/E4B/12B、Phi-4-mini、Qwen3。

**第三层：公式与核心机制**——端侧瓶颈是 RAM 而非算力，模型体积须控制在目标 RAM 的约 30% 以内；Q4_K_M 用 4-bit 非对称量化在质量与体积间取平衡，Q5/Q6 仅 12GB+ 设备用。持续生热会降速，故长会话选更小模型而非更大。仅 Gemma 3 4B 等支持图像，其余多为文本；SmolLM 2 1.7B 在所有参考机型上速度最快，Qwen3 1.7B 是多语最强（35+ 语言）。从成本视角看，开放权重模型让企业可以微调、合并并内部分发而不必签 API 合同，训练数据也永不离开本机，隐私合规叙事天然成立；这也正是端侧小模型在医疗、法律等敏感场景受欢迎的原因。Fora Soft 同时指出，持续生成会发热降速，所以长会话的正确答案是"换更小模型"而非"换更大模型"，RAM 与芯片的档位比模型参数规模更决定体验。

```bash

```

### 6. 【端侧推理运行时与量化：手机跑大模型的Q4_K_M标准】

> 📍 **导语**：选好了端侧小模型，下一步是"怎么让它真正跑起来"。2026 年的端侧推理栈已高度分化：Google 把新功能集中在 LiteRT-LM（原 MediaPipe LLM API 转维护），跨平台可用 ONNX Runtime Mobile 或 llama.cpp 的 GGUF，Apple 走 Core ML。而"量化标准"里，Q4_K_M 几乎成了移动端默认——保留约 95% 原始质量、体积仅 1/4。理解运行时与量化的分工，才能避开"模型下完了却跑不动"的坑。

---

**🧠 深度解析**

**▌ 它是什么？**（概念与边界）
端侧推理运行时是负责把模型权重加载、执行前向计算并调用 NPU/GPU/CPU 的软件层；量化则是把 FP16 权重压成 4-bit / INT8 以省显存。误区是"量化=质量腰斩"——Q4_K_M 仅损约 5%。边界是不同运行时支持的模型格式不同（GGUF vs LiteRT vs Core ML）。历史上从 MediaPipe → LiteRT-LM；llama.cpp GGUF；MLC LLM；ExecuTorch（边缘 IoT），各自锁定不同生态。二者配合决定了"模型能不能在目标设备落地"：量化决定体积与精度，运行时决定能否调用芯片算力；任何一环不匹配，都会陷入"模型下完却跑不动"的典型困境，因此在选型阶段就要把模型格式与运行时一并规划。一个常见误区是只看参数规模选模型而忽略 RAM 档位，事实上 8GB RAM 是 3B–4B 模型的实际下限、12GB 才够 Q5_K_M，盲目追求大参数只会让设备频繁交换内存、体验反而更差，正确做法是按目标设备 RAM 倒推可运行的模型与量化档。

**▌ 它解决了什么问题？**（Before → After）
此前原始 FP16 的 7B 模型需约 14GB，手机根本放不下也跑不动。之后，Q4_K_M 把 7B 压到约 4GB 量级，配合运行时在 8GB RAM 设备流畅跑。例子：Fora Soft 指出 Gemma 4 E2B 2.58GB、E4B 3.65GB（LiteRT-LM）；视觉模型 INT8 仅 4–200MB；Whisper tiny INT8 约 75MB、旗舰机 1.5–2 倍实时。运行时把算子委托到 NPU，无 NPU 时 LiteRT GPU 加速通常胜出。

**▌ 核心原理三阶拆解**
**第一层：直觉理解**——运行时像手机的"翻译官"，把模型语言翻成芯片指令；量化像把高清图存成压缩包——体积小了，肉眼几乎看不出差别，但传输和存储都轻松，推理时再解压计算。

**第二层：技术流程拆解**——拿到模型 → 转格式（GGUF 给 llama.cpp / LiteRT 给 Android / Core ML 给 iOS）→ 量化（bitsandbytes nf4 或 GGUF Q4_K_M）→ 选运行时加载 → 用 NPU/GPU 委托加速。MediaPipe 现维护态，新项目建议 LiteRT-LM；跨端一致性用 ONNX Runtime Mobile 或 llama.cpp。

**第三层：公式与核心机制**——量化用低比特表示权重：Q4_K_M 把权重按块（k）做 4-bit 非对称量化并保留重要均值（M），在压缩率与精度间取优；Q5_K_M / Q6_K 精度更高但体积更大，仅 12GB+ 设备用。运行时通过"算子委托"把算子映射到 NPU；无 NPU 时 LiteRT GPU 加速器通常胜出（视觉任务），ONNX Runtime Mobile 紧随 PyTorch 导出之后。需要强调的是，量化与运行时是两层独立决策：先选量化档（Q4_K_M 默认、Q5/Q6 仅 12GB+ 设备），再选运行时（GGUF 通用最强、LiteRT-LM 锁 Google 栈、Core ML 锁 Apple 栈、ONNX Runtime Mobile 求跨端一致）。量化档位的选择本质是精度与体积的交易：Q4_K_M 已能保留约 95% 质量，对绝大多数端侧任务足够，盲目上 Q6 只会浪费本就紧张的 RAM，反而挤掉模型本身的容量空间。MediaPipe LLM API 自 2026 起仅维护，新功能只进 LiteRT-LM，新项目应直接基于后者；而 ExecuTorch 则面向 Raspberry Pi、Jetson 等 IoT 边缘设备的 INT8 部署，与手机端形成互补的端侧版图。

```bash

./llama-quantize m.gguf m-q4km.gguf Q4_K_M
./llama-cli -m m-q4km.gguf -p "你好"

```
