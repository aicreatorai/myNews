### 1. 【FP4量化训练与Rollout对齐：让强化学习在低精度下不丢性能】

> 📍 **导语**：大模型后训练里，强化学习（RL）最烧钱的不是参数更新，而是反复生成 Rollout 样本。把 Rollout 压到 FP4 能省下大量显存与算力，但低精度并非把 BF16 模型训完再量化那么简单——训练路径与推理路径走的是两套量化，二者不一致会让策略看到的行为和真实数据分布发生偏移。2026 年 10 月发布的 TRACE 框架提出"训练—Rollout 量化对齐"，在四个大规模 MoE 模型上用全 FP4 Rollout 匹配 BF16 性能，最高提速 5.4 倍。这篇把这套思路讲透。

---

**🧠 深度解析**

**▌ 它是什么？**
TRACE（Train-Rollout Quantization Alignment）是一种面向强化学习的量化感知训练方法，核心目标是让"训练时模型用的低精度"与"部署/Rollout 时模型实际跑的低精度"尽可能一致。它不是一个单纯的压缩 trick，而是一种把量化当作训练约束来设计的范式。一个常见误区是认为"只要训练用高精度、推理用低精度，事后量化即可"——对 RL 而言这恰恰会出问题，因为策略要持续采样，训练看到的分布必须与 Rollout 真实分布对齐。它的边界是：对推理服务（非 RL 训练）场景，传统 PTQ/训练后量化已足够；TRACE 的价值集中在 RL 后训练这条高成本链路上。它的诞生背景是 MoE 大模型 RL 成本激增，业界急需把 Rollout 这件最贵的事变便宜。

**▌ 它解决了什么问题？**
Before：现有 FP4 RL 方案分别优化"训练路径量化"和"Rollout 路径量化"，各自局部误差小，但两条路径算出来的结果可能差很多。RL 依赖当前策略持续采样，这种路径差会让训练行为与实际生成数据分布偏移，拖累策略优化。After：TRACE 用 Rollout 侧的量化结果回过头指导训练侧的 FP4 舍入决策，直接压缩两条量化路径的差异。具体收益：在四个大 MoE 模型上，权重+激活+KV 缓存全 FP4 的 Rollout 匹配 BF16 Rollout 表现，最高提速 5.4 倍，且最终 FP4 效果优于"先 BF16 训练再事后量化"。例如一个长程 RL 任务，原本 BF16 Rollout 受显存与 KV 缓存限制，改用 TRACE 的全 FP4 链路后，硬件负担大幅下降而性能不掉。

**▌ 核心原理三阶拆解**
**第一层：直觉理解**——把训练模型和部署模型想成同一个厨师的"练习版"和"上菜版"。如果练习时用精装灶台、上菜时用便携炉，手感就会错位。TRACE 的做法是让厨师在练习时，就按便携炉的真实火候来练，这样上菜时不会翻车。

**第二层：技术流程**——输入为全精度 MoE 策略；步骤1，正常跑一次 Rollout，但这次 Rollout 用 FP4（权重、激活、KV 缓存全低精度）；步骤2，把这次 FP4 Rollout 实际产生的量化结果记录下来；步骤3，在训练侧的反向更新里，用这些 Rollout 量化结果来约束 FP4 的取整（rounding）决策，而不是独立选舍入；步骤4，选择性地缓存更深层网络的尾数与缩放信息，降低指导信号带来的存储与通信开销；输出为与 FP4 Rollout 对齐的训练策略。

**第三层：核心机制**——关键在于"取整对齐"：低精度量化的误差主要来自四舍五入（round-to-nearest）的选择，TRACE 让训练侧的舍入尽量贴近部署侧真正使用的低精度行为，而不是各自最小化自己的局部重构误差。配合选择性缓存，避免为所有中间信息付存储代价。

**▌ 动手验证**
下面用 bitsandbytes 演示"4-bit 加载"这一低精度基石（FP4 目前多为研究方向，4-bit NF4 已可实操）：
```python
import torch, bitsandbytes as bnb
from transformers import AutoModelForCausalLM, AutoTokenizer
# 以 4-bit NF4 加载，模拟低精度 Rollout 的基座
model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Llama-3-8B",
    quantization_config=bnb.nn.Linear4bit(compute_dtype=torch.bfloat16),
    device_map="auto")
tok = AutoTokenizer.from_pretrained("meta-llama/Llama-3-8B")
out = model.generate(**tok("解释量化对齐", return_tensors="pt").to("cuda"), max_new_tokens=32)
print(tok.decode(out[0]))  # 注意：TRACE 进一步要求训练侧舍入贴合此低精度路径
```
注意：bitsandbytes 提供 NF4/INT4 落地能力；TRACE 的"训练—Rollout 对齐"是在此之上的研究性扩展，需按论文复现。

**▌ 对比与选型**
| 对比维度 | TRACE(FP4对齐) | 普通PTQ | 事后量化 |
|---------|--------|-------|-------|
| 核心思想 | 训练贴合Rollout | 仅压缩部署 | 训后转低精 |
| 适用场景 | RL后训练 | 推理服务 | 通用部署 |
| 性能表现 | 匹配BF16 | 略有损 | 易偏移 |
| 学习成本 | 较高 | 低 | 低 |
| 生态成熟度 | 研究阶段 | 成熟 | 成熟 |

### 2. 【分块对齐混合精度量化AlignQuant：把精度选择贴着GPU架构走】

> 📍 **导语**：混合精度量化想给重要的权重大权重、不重要的给小权重，但"局部精度自由"常和 GPU 的存储/计算单元打架——精度边界不匹配，压缩收益就转化不成真实加速。2026 年 10 月发布的 AlignQuant 提出以 GPU 兼容的二维权重瓦片（tile）作为精度分配、存储和执行的统一单元，在 3B~14B 模型上较 BF16 最高提速 2.5 倍，并覆盖最长 64K 上下文。这篇讲清它怎么把"灵活"和"规整"拧到一起。

---

**🧠 深度解析**

**▌ 它是什么？**
AlignQuant 是一种训练后量化（PTQ）方法，核心创新是用"二维权重瓦片"作为统一单元来同时承载三件事：精度分配、紧凑存储、实际执行。它属于细粒度混合精度量化的进阶版。一个常见误区是把混合精度量化想成"对每个权重单独挑比特数"——GPU 根本不这么算，它是按块（tile）读写和计算的，逐权重精度只会让硬件无所适从。AlignQuant 的边界是：它专门解决"精度选择如何与 GPU 存储/计算对齐"的工程难题，对模型结构本身不做改动。它的历史脉络来自 GPTQ/AWQ 等 PTQ 方法，那些方法证明了"按敏感度分配精度"有效，但没解决与硬件执行单元的匹配；AlignQuant 补上了这最后一环。

**▌ 它解决了什么问题？**
Before：细粒度混合精度量化虽能灵活分配精度，但局部精度选择常和 GPU 常规存储与计算单元冲突，精度边界不匹配限制了"压缩→加速"的转化。After：AlignQuant 让每个瓦片只存一种选定表示，阶段专用内核复用打包后的模型，把低位权重展开做 INT8 计算。具体量化收益：在四个 3B~14B 模型上，保持质量的同时生成速度较 BF16 最高提升 2.50 倍，评测覆盖三种 GPU 与最长 64K token 上下文。例如一个 14B 模型在长上下文推理时，传统混合精度因对齐差只能拿到部分加速，AlignQuant 通过瓦片对齐让加速稳定兑现。

**▌ 核心原理三阶拆解**
**第一层：直觉理解**——混合精度量化像给书架每层决定放精装还是平装书，但 GPU 是"按固定尺寸的木箱"搬书的。如果书的高度不规整，箱子装不满也搬不动。AlignQuant 的做法是让每箱书统一规格（瓦片内同表示），箱子就能严丝合缝地搬，速度自然上来。

**第二层：技术流程**——输入为全精度 LLM 权重；步骤1，以 GPU 兼容的二维权重瓦片为单元划分权重；步骤2，在输出通道内按敏感度灵活分配精度；步骤3，联合预填充/解码校准，用"量化激活下的投影输出扰动 + 语言模型损失梯度"加权评分，评估精度降级影响；步骤4，相位归一化评分在模型级存储预算约束下，优先给任一阶段重要的瓦片更高精度；步骤5，每瓦片仅存一种表示，阶段内核复用打包模型并展开低位权重做 INT8 计算；输出为对齐 GPU 的低精度模型。

**第三层：核心机制**——关键在于"共享瓦片单元"：精度分配、存储格式、执行内核三者共用同一个 tile 划分，既保留局部精度灵活性，又满足 GPU 的规整执行要求。相位归一化评分解决了"预填充"和"解码"两阶段对精度敏感度不同"的分配难题。

**▌ 动手验证**
下面用 PyTorch 演示"按块（tile）做对称量化"的核心思想（AlignQuant 在此之上加 GPU 对齐与校准）：
```python
import torch
def tile_quant(w: torch.Tensor, bits=4, tile=128):
    # 以 tile 为单元做对称量化，模拟 AlignQuant 的瓦片划分
    out = torch.zeros_like(w)
    for i in range(0, w.numel(), tile):
        blk = w.flatten()[i:i+tile]
        s = blk.abs().max() / (2**(bits-1)-1)  # 缩放因子
        out.flatten()[i:i+tile] = (blk/s).round()*s   # 取整再还原
    return out
w = torch.randn(512, 512)
wq = tile_quant(w); print((wq-w).abs().mean().item())  # 块内共享缩放，误差可控
```
注意：真实 AlignQuant 还需校准与阶段专用内核，以上仅演示 tile 划分的直觉。

| 适用场景 | GPU高效推理 | 通用PTQ | 保护重要权 |

### 3. 【分布鲁棒量化：为什么最小化重构损失反而害了低比特模型】

> 📍 **导语**：权重-only 训练后量化（PTQ）几乎都靠"最小化重构损失"来保住低精度下的模型质量，但 2026 年 10 月一篇 arXiv 论文（2610.11226）指出：被重构损失偏爱的那些权重，未必带来更好的模型表现。换句话说，死磕 MSE 反而可能害了低比特模型。这篇把"重构损失误导"这一现象和它的分布鲁棒性解法讲清楚，帮你少踩量化坑。

---

**🧠 深度解析**

**▌ 它是什么？**
这篇工作研究的是低比特大模型量化中的"重构损失陷阱"：在权重-only PTQ 里，我们通常用最小化重构误差（如 MSE）来选量化参数，论文证明，最小化该损失所青睐的权重，并不一定产生更好的下游任务表现。它提出用"分布鲁棒性优化（DRO）"思路来替代单纯重构最小化。一个常见误区是以为"重构误差越小，量化模型越好"——论文恰恰反驳了这一点。它的边界是：针对低比特（如 2/3/4-bit）权重-only PTQ 场景，对高比特或激活量化影响较小。它的脉络承接 GPTQ/AWQ 等以重构为核心的方法，提醒社区"重构好≠任务好"，属于量化方法论的纠偏。

**▌ 它解决了什么问题？**
Before：PTQ  pipeline 把"重构损失最小化"当成质量保真的金标准，工程师调量化参数时盯着 MSE 往下压。After：论文揭示该目标与真实任务性能并不单调相关，并给出分布鲁棒优化方法来对齐"任务表现"而非"重构误差"。量化收益：避免把算力浪费在压低一个并不等价于模型能力的指标上，从而在同等比特下拿到更稳的任务表现。例如一个 3-bit 量化的小模型，按传统 MSE 最小化的权重选择可能在某层重构很好，但下游准确率反而掉点；改用分布鲁棒视角后能缓解这种"看似更优实则更差"的情况。

**▌ 核心原理三阶拆解**
**第一层：直觉理解**——考试前你反复练"抄写工整度"（重构误差），以为字越工整分越高，但阅卷老师看的是"答对没有"（任务表现）。工整和答对相关却不等价，过度优化工整反而挤占了真正该练的。量化里"重构损失"就是那个工整度指标。

**第二层：技术流程**——输入为全精度权重与校准数据；步骤1，传统方法在每一层求解"最小化量化重构 MSE"的舍入；步骤2，论文观察到被 MSE 偏爱的权重分布与任务敏感权重分布不一致；步骤3，引入分布鲁棒性优化，把目标从"单点重构"改为"在最坏分布偏移下仍稳健"；步骤4，用该鲁棒目标重选量化参数；输出为任务表现更稳的低比特权重。

**第三层：核心机制**——关键在于区分"重构域"和"任务域"：MSE 度量的是数值逼近，而任务性能取决于权重在非线性变换后的决策边界贡献。分布鲁棒优化通过在参数选择时考虑分布偏移的最坏情形，抑制了"重构好看但任务脆弱"的权重。

**▌ 动手验证**
下面用 PyTorch 演示"重构误差小 ≠ 任务影响小"的直觉（用敏感度近似代替真实任务评估）：
```python
import torch
def recon_err(w, wq): return (w-wq).pow(2).mean()        # 重构损失
def task_proxy(w, wq): return (w*wq).sum()/w.abs().sum() # 伪任务敏感度
w = torch.randn(256); q = (w*127).round()/127
print("重构误差", recon_err(w,q).item(), "任务代理", task_proxy(w,q).item())
# 不同舍入策略下两者并不单调一致，正是论文要提醒的陷阱
```
注意：以上为概念演示；真实评估需在下游任务上验证，而非只看 MSE。

| 核心思想 | 最坏分布稳健 | 最小重构 | 二阶补偿 |
| 适用场景 | 极低比特 | 通用 | 通用PTQ |
| 性能表现 | 任务更稳 | 易掉点 | 中 |

### 4. 【多智能体RAG协作：检索、验证与编排的专业分工】

> 📍 **导语**：朴素 RAG 是"嵌入—检索—塞进提示词"三步曲，2026 年已显得过时。当下的主流是 Agentic RAG：智能体主动规划、反思、跨多步检索并使用工具，而不是一次性向量查找。微软 Azure 已将其列为参考架构，JADE、HERA 等新框架通过联合优化与经验驱动编排报告了 38%+ 的基准增益。这篇讲清多智能体 RAG 怎么把"检索"拆成专业分工，以及它真实的收益与代价。

---

**🧠 深度解析**

**▌ 它是什么？**
多智能体 RAG 是在检索增强生成中引入多个职责分离的智能体：有的负责语义检索、有的查结构化数据库、有的做网页搜索、有的做验证与综合。它对应 Anthropic 总结的五大智能体工作流模式——路由（Routing）、并行化（Parallelization）、编排器—工作者（Orchestrator-Workers）、评估器—优化器（Evaluator-Optimizer）、提示链（Prompt Chaining）。误区是以为"加几个 agent 就一定更好"——协调复杂、延迟与 token 成本都会上升。它的边界是：适合多域研究助手、复杂分析等需要多跳推理的场景；简单问答用单智能体更划算。脉络上它从朴素 RAG → 反思式 RAG → 多智能体 RAG 演进，把"记忆"与"规划"内置进系统。

**▌ 它解决了什么问题？**
Before：朴素 RAG 一次性把文档塞进上下文，遇到"对比三家公司财报"这类复杂查询会力不从心，也无法动态判断是否检索不足。After：多智能体把任务拆成子任务并行检索后综合，使复杂查询准确率显著提升、多跳推理成为可能、系统动态适配不同领域。量化收益：JADE 与 HERA 报告通过联合优化与经验驱动编排获得 38%+ 的基准增益；企业文档与会议记录处理是其最佳试验场——上百场会议后，静态检索无法跨会议综合，而带验证与推理步骤的 Agentic 检索才可靠。代价是协调复杂、计算开销大、延迟增加，需要权衡。

**▌ 核心原理三阶拆解**
**第一层：直觉理解**——朴素 RAG 像一个人既当采购又当写手还当校对，忙中出错；多智能体 RAG 像组建小团队：采购专员找资料、分析师判相关性、写手组织答案、审校把关质量，各司其职。

**第二层：技术流程**——输入为用户复杂查询；步骤1，规划（Planning）把任务拆为可管理子任务，每子任务对应一次独立检索；步骤2，路由（Routing）对输入分类分发到不同链路；步骤3，工具使用（Tool Use）让智能体动态决定调向量库、SQL、网页还是推荐系统；步骤4，多智能体并行执行后由编排器聚合；步骤5，评估器—优化器循环迭代优化输出；输出为综合答案。

**第三层：核心机制**——关键在于"职责分离 + 编排图"：每个 agent 只持特定工具权限，编排器按查询复杂度动态拆分而非预先固定子任务，验证 agent 对低相关文档执行查询改写与补充检索，从机制上抑制幻觉。

**▌ 动手验证**
下面用 sentence-transformers + 函数化角色演示最小多智能体 RAG 骨架（真实可跑）：
```python
from sentence_transformers import SentenceTransformer
model = SentenceTransformer("all-MiniLM-L6-v2")
def retriever(q, docs):                       # 检索员角色
    qe = model.encode(q); de = model.encode(docs)
    return [docs[i] for i in qe@de.T.argsort()[-2:][::-1]]
def synthesizer(q, ctx): return f"基于{ctx}回答：{q}"  # 生成员角色
docs = ["量子计算利用叠加态", "Transformer依赖注意力"]
print(synthesizer("什么是量子计算", retriever("量子计算", docs)))
# 多智能体版再叠加 verifier 改写查询与 orchestrator 拆分，即可扩展
```
注意：生产需加验证 agent 与重排，避免近重复查询浪费上下文。

| 核心思想 | 专业分工协作 | 单次检索 | 一agent管全部 |
| 适用场景 | 复杂多跳 | 简单问答 | 中等复杂度 |

### 5. 【角色分离的检索智能体KnowForge：用硬约束换可测量的质量增益】

> 📍 **导语**：大多数生产 RAG 仍依赖"检索—阅读"单循环，而多智能体框架常让模型自己决定何时搜、何时读、何时停，消融实验显示这会产生大量近重复查询和过早综合。2026 年 10 月 MetaStack AI 的 KnowForge（arXiv 2610.13128）提出"严格角色分离"架构，把搜索和阅读拆成专属 agent，在多模态文档问答上较基线提升 7~11 F1，且无需微调。这篇讲清它怎么用"硬架构边界"把质量增益变得可测量。

---

**🧠 深度解析**

**▌ 它是什么？**
KnowForge 是一种面向大规模异构文档（含文本、图像、表格的 PDF）检索增强问答的"严格角色分离"架构。它不把全部工具权限交给一个自调度模型，而是把工作硬性划分为：只负责搜索的 Locator、只负责精读的 Deep Reader，以及二者之间由确定性代码调度的桥接（bridge）。误区是以为"agent 越多越智能"——KnowForge 的核心论点是失败模式不是缺 agent，而是缺"哪个 agent 能用哪个工具"的约束。它的边界是多模态长文档 QA；脉络上它站在 2024-2025 多智能体 RAG 工作的对面，主张用确定性编排图替代模型自调度。

**▌ 它解决了什么问题？**
Before：单智能体 RAG 让一个 LLM 调用同时管检索、阅读、综合，或让多智能体自调度，导致近重复查询和过早综合，浪费上下文与延迟。After：KnowForge 硬隔离角色，Locator 只用搜索、Reader 只用阅读，强制系统显式决策"证据池是否够"再停止搜索。量化收益：在 3B 激活的自托管 MoE（Qwen3.6-35B-A3B）上，全开放域 M3DocVQA F1 达 47.5、MultiHop-RAG 73.5、MMLongBench-Doc 47.0，较最接近已发表基线提升 7~11 分；并在 4 轮 Locator 后出现离散性能台阶后趋于平稳。它还开源了全部基准语料、提示词与运行代码便于复现。

**▌ 核心原理三阶拆解**
**第一层：直觉理解**——把"找资料的人"和"读资料的人"彻底分开，且中间加一道"够不够"的硬性检查闸门。找的人不能顺手读，读的人不能顺手找，避免一个人边找边读边下结论的混乱。

**第二层：技术流程**——每问固定序列：步骤1，一个或多个 Locator 轮次，对索引语料发查询返回带类型的段落、图像、表格；步骤2，桥接裁判（代码级检查，非另一个 LLM）在首跳证据池不足时强制触发二次检索；步骤3，Deep Reader 在合并后的类型化、有大小上限的证据池上精读；步骤4，合成器带格式检查输出。证据池合并时显式标注类型并硬性封顶，防止无界注入拖垮阅读质量。

**第三层：核心机制**——关键是"硬架构边界 + 确定性桥接"：工具权限按角色硬隔离（runner 代码层强制），桥接裁判用启发式而非学习式触发，把"何时停搜开始读"从涌现策略变成可检视的编排图，从而把质量增益归因于结构设计而非玄学。

**▌ 动手验证**
下面用函数演示 KnowForge 的"角色硬隔离 + 桥接裁判"骨架：
```python
def locator(q, corpus): return corpus.search(q)          # 仅搜索，禁止阅读
def bridge_judge(pool): return len(pool) < 3             # 确定性闸门
def reader(pool): return summarize(pool)                 # 仅阅读，禁止搜索
pool = locator("模型量化", corpus)
if bridge_judge(pool): pool += locator("低比特 PTQ", corpus)  # 强制二跳
print(reader(pool))   # 角色不可越权，证据池封顶防膨胀
```
注意：真实实现需类型化证据池与大小上限，以上演示职责分离核心。

**▌ 对比与选型**
| 对比维度 | KnowForge | 单智能体RAG | 自调度多智能体 |
|---------|--------|-------|-------|
| 核心思想 | 硬角色分离 | 一agent全管 | 模型自调度 |
| 适用场景 | 多模态长文档 | 简单问答 | 复杂检索 |
| 性能表现 | +7~11 F1 | 基线 | 易冗余 |
| 学习成本 | 中 | 低 | 高 |
| 生态成熟度 | 新研究 | 成熟 | 成熟 |

### 6. 【单智能体、多智能体与层级式RAG：三种架构怎么选】

> 📍 **导语**：选 RAG 架构时，很多人凭感觉堆复杂度。2026 年 10 月开源项目 Agent-RAG 用一个 FastAPI 服务把三种范式——单智能体、多智能体、层级式——接到同一套底座上并排对比，混合检索（BM25+稠密向量 RRF 融合）+ 三路重排 + 上下文工程一应俱全。这篇用它的对照结论，帮你按业务复杂度选对架构，避免"复杂架构的增益抵不过延迟与费用"。

---

**🧠 深度解析**

**▌ 它是什么？**
Agent-RAG 项目把三种 RAG 架构范式实现在同一仓库里做对照：单智能体（检索+生成基础问答）、多智能体（检索员、分析员、生成员、评审员协作）、层级式 A-RAG（规划器+多粒度检索+验证）。它配套混合检索（BM25 关键词 + 稠密向量，按 RRF 倒数排名融合）、三档重排器（CoE 交叉编码器 / LLM 打分 / 轻量关键词重叠）、以及做 token 预算管理、段落去重与抽取式压缩的上下文工程模块。误区是"层级式一定最强"——项目明确提醒复杂架构带来的 token 成本与延迟需自行权衡。它的边界是教学/选型参考，生产化需自行评估；脉络上它是把业界讨论的架构差异落成"可跑的活教材"。

**▌ 它解决了什么问题？**
Before：开发者想比较三种架构得分别搭三套系统，成本高且难保证底座一致，选型全靠猜。After：Agent-RAG 一个仓库并排跑三种架构，同一查询下直接看到回答差异，还能量测"自家业务到底需要哪种复杂度"。量化收益：多智能体把职责拆开（检索员找、分析员判、生成员写、评审员把关），代价是调用次数与延迟上升；层级式引入规划器先判复杂度再选检索粒度，复杂问题拆子查询逐个击破。项目还内置 HyDE、step-back、多查询分解三种改写策略，对长尾问题召回有实际帮助；但三路重排与多智能体链路会显著增加 token 成本。

**▌ 核心原理三阶拆解**
**第一层：直觉理解**——单智能体像"一个人包办"，多智能体像"科室协作"，层级式像"先开会有计划再分工"。人少事简单用包办，事多且杂才上协作与计划。

**第二层：技术流程**——以层级式为例：步骤1，规划器判断问题复杂度；步骤2，简单问题直接单检索，复杂问题拆成子查询；步骤3，多粒度检索（BM25+向量 RRF 融合）；步骤4，重排器（CoE/LLM/关键词）三选一过滤；步骤5，上下文工程做 token 预算与去重压缩；步骤6，验证环节补漏；输出为答案。单智能体则压缩为"检索→生成"一步。

**第三层：核心机制**——关键在于"复杂度驱动的分级"：不是无脑上最复杂架构，而是让规划器按问题难度决定检索粒度与是否拆分，配合 RRF 融合与重排把"召回"和"精准"都拉满，再用上下文工程控制成本，形成可解释的成本—质量权衡。

**▌ 动手验证**
下面用函数演示"按复杂度路由到不同架构"的选型骨架：
```python
def route(query, planner):
    if planner.is_simple(query): return single_rag(query)      # 单智能体
    sub = planner.decompose(query)                             # 层级式拆分
    ev = [multi_agent_rag(s) for s in sub]                     # 多智能体并行
    return synthesize(ev)
print(route("今天天气", planner))      # 简单→单智能体，省token
print(route("对比三家公司财报", planner))  # 复杂→层级+多智能体
```
注意：真实部署先用自家数据对比"增益是否抵得过延迟与费用"再决定架构。
