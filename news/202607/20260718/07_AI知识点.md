# AI知识点

### 1. 【MCP协议2026大修订：让AI智能体从"会对话"升级到"能执行"】

> 📍 **导语**：过去两年，开发者给每个大模型单独写一套 Function Calling 适配层，遇到企业级复杂场景就暴露出"N×M 集成地狱"、上下文割裂、权限失控三大短板。2026 年 7 月，MCP（Model Context Protocol）迎来问世以来最大一次系统性修订，候选规范将于 7 月 28 日正式发布。它正从"连接工具"转型为可规模化部署、全链路可治理的生产级智能体基础设施。理解 MCP，是理解 2026 年 AI Agent 为何能真正"干活"的关键。

---

**🧠 深度解析**

**▌ 它是什么**
MCP（Model Context Protocol，模型上下文协议）是一套由 Anthropic 于 2024 年底提出、2026 年走向稳定的开放标准，用来把"大模型"和"外部工具/数据"之间的对接规范化。你可以把它理解成 AI 时代的 USB-C 接口：过去每个 AI 应用要接数据库、文件系统、SaaS，都得自己写一套私有适配代码；有了 MCP，只要双方都遵守同一套协议，插上就能用。一个常见误区是把它等同于传统 API——API 只定义"怎么调用"，而 MCP 还定义了"工具的能力描述（Tool）、稳定知识（Resources）、任务方法（SKILL）、以及调用轨迹如何被审计"，是一整套上下文与治理语义。它的适用边界是：凡是需要 Agent 安全、可控、可追溯地操作真实业务系统的场景都适用；纯粹的单次问答则没必要引入。

**▌ 它解决了什么问题**
Before：某企业需要让 Agent 同时连工商库、合同库、订单系统，3 个 AI 应用 × 5 个系统 = 15 套适配器，每新增一个系统所有应用都要改代码，且 API Key 直接绑定、权限像"上帝视角"。After：统一 MCP Server，客户端自动发现 197 个工具并按业务边界分类，调用全程带 OAuth 授权与 W3C 链路追踪。腾讯云实测指出，传统 Function Calling 在企业级场景暴露三大致命缺陷，而 MCP 1.0 稳定版让钉钉、飞书等平台能密集发布原生 Server，彻底打通模型与数字资产的"最后一公里"。最近企查查已搭建 9 个 Server、197 个工具、27 个 SKILL 的企业数据基座，正是这一范式的落地样本，让每个结论都能回到确定主体与可追溯来源。

**▌ 核心原理拆解**
**第一层：直觉理解**——MCP 就像一栋智能办公楼的统一门禁与工位系统：每个房间（工具）在物业处登记了"能干什么、归谁管、怎么申请"，任何员工（Agent）入职后都能查到地图并按规定使用，而不是每人私配一把万能钥匙。

**第二层：技术流程拆解**——请求不再绑定会话（取消 session sticky），每个请求自包含全部上下文 → 网关做能力发现与限流 → 执行多轮交互任务（标准化任务引擎）→ 输出附带完整 JSON Schema 与链路追踪 ID。关键参数是无状态架构、能力发现缓存、OAuth 委托。

**第三层：公式与核心机制**——核心机制是"自包含请求 + 分层能力治理"：服务端无需锁定固定机器承载会话，天然适配云原生弹性扩容；Resources 提供稳定知识（术语表、数据字典），SKILL 把多个 Tool 编排成业务流程，全局约束守住"实体锚定、当前与历史分离、引用纪律"的可信边界。

**▌ 动手验证**
用官方 Python SDK 连一个本地文件系统 Server：
```python
from mcp import ClientSession, StdioServerParameters
import asyncio

async def main():
    params = StdioServerParameters(command="npx", args=["-y", "@modelcontextprotocol/server-filesystem", "/tmp"])
    async with stdio_client(params) as (r, w):
        async with ClientSession(r, w) as session:
            await session.initialize()
            tools = await session.list_tools()      # 能力发现
            print([t.name for t in tools.tools])     # 输出可用工具列表
asyncio.run(main())
```
注意需先 `pip install mcp` 并安装对应 server；`list_tools()` 返回的正是"能力发现"机制，无需硬编码工具名。

**▌ 对比与选型**
| 对比维度 | MCP | Function Calling | 传统 API |
|---------|------|------|------|
| 核心思想 | 统一上下文协议 | 模型私有适配 | 点对点调用 |
| 适用场景 | 多系统Agent | 单模型单工具 | 固定集成 |
| 治理能力 | 强(审计/限流) | 弱 | 中 |
| 生态成熟度 | 快速成长期 | 各厂商分裂 | 成熟 |

### 2. 【端侧小模型实战：把27B大模型塞进手机与嵌入式开发板】

> 📍 **导语**：2026 年 7 月，端侧 AI 迎来"iPhone 时刻"：PrismML 发布的 Bonsai 27B 通过三值与 1-bit 极端量化，把原本 54GB 的模型压到 3.9GB，首次让 27B 级别推理能在 iPhone 17 Pro 的内存预算内原生运行；与此同时 Qwen-1.5B 被部署进不到 200 元的 M5Stack 开发板，全程离线。当边缘 AI 推理市场首次超越云端训练，理解"如何在手机和开发板上跑大模型"已成为每个 AI 工程师的硬技能。

---

**🧠 深度解析**

**▌ 它是什么**
端侧小模型（On-device Small Model）指的是直接运行在手机、开发板、车载芯片等终端设备上、无需依赖云端推理的大语言模型。它不等于"小模型"三字那么简单——今天讨论的端侧模型，既包括 1.5B 这类原生小模型，也包括通过极端量化把 27B 旗舰"瘦身"后塞进手机的产物。常见误区是认为端侧必然"很笨"：实际上借助 INT4/FP8 混合量化与结构化剪枝，端侧模型已能在保持 90% 以上能力的同时把显存压到 1/5。其适用边界是：对延迟、隐私、弱网可用有强要求的场景（如离线语音助手、工业现场语义理解）最适合；需要海量知识或超长推理的任务仍应交由云端。值得补充的是，端侧与云端并非替代关系而是协同关系——业界提出的"端云协同"范式让手机端先做一次轻量理解与预处理，再把真正困难的子任务卸载到云端，既保住了隐私与实时性，又借云端补齐了知识广度，这也是 2026 年边缘 AI 推理市场规模首次超越云端训练后的主流落地形态。

**▌ 它解决了什么问题**
Before：一个 27B 模型 FP16 约 54GB，只能在多卡服务器上跑，手机根本无法承载，AI 能力被锁在云端，断网即瘫痪、数据要上传、单次调用都要付 API 费用。After：Bonsai 27B 的 1-bit 版仅 3.9GB，在 12GB 内存的 iPhone 17 Pro 上原生运行；Qwen-1.5B 在 M5Stack 上启动 1.8 秒、单轮响应 3.2 秒、全程离线。据实测，Bonsai 27B 1-bit 保留了全精度基线约 90% 的综合能力，三值版约 95%。这意味着"AI 终端化"从 PPT 概念变成可触摸的现实：你的手机在没有网络时也能跑一个 27B 级别的智能体。

**▌ 核心原理拆解**
**第一层：直觉理解**——把大模型塞进手机，就像把一套百科全书压缩成口袋本：不是删掉知识，而是用更省空间的编码方式记录同样的干货，代价是极端压缩时个别细枝末节会变模糊。

**第二层：技术流程拆解**——原始权重(FP16) → 量化映射(1-bit/三值把每个参数从 16 位压到 1~2 位) → 结构适配(重写计算路径、重映射内存) → 端侧推理引擎(MLC-LLM / llama.cpp / ONNX Runtime Mobile)加载执行。关键参数：比特宽度、是否保留缩放因子、KV Cache 管理。

**第三层：公式与核心机制**——核心机制是低比特表示：用极少量 bit 近似全精度权重，配合感知量化训练(QAT)补偿精度损失；Bonsai 还原生支持推测解码(speculative decoding)加速，并在 262K 上下文下保持可用。

**▌ 动手验证**
用 llama.cpp 在本地跑一个量化模型：
```python
from llama_cpp import Llama
llm = Llama(model_path="bonsai-27b-1bit.Q4_0.gguf", n_ctx=4096, n_gpu_layers=0)
out = llm("用一句话解释什么是端侧AI", max_tokens=64)
print(out["choices"][0]["text"])
```
注意：手机端需用 MLC-LLM 交叉编译；`n_gpu_layers=0` 表示纯 CPU 推理，内存不足时可调小 `n_ctx`。

**▌ 对比与选型**
| 对比维度 | 端侧小模型 | 云端大模型 | 本地服务器 |
|---------|------|------|------|
| 核心思想 | 终端运行 | 远程调用 | 内网部署 |
| 适用场景 | 离线/隐私 | 复杂任务 | 企业内网 |
| 性能表现 | 中等 | 最强 | 强 |
| 学习成本 | 中 | 低 | 中 |

### 3. 【向量检索与Embedding：用稠密向量让语义搜索不再"字面对不上"】

> 📍 **导语**：传统关键词搜索要求"字面对得上"，用户搜"怎么退订会员"却搜不到文档里写的"取消订阅方法"，因为字面不匹配。2026 年 7 月，腾讯云 PostgreSQL tencentdb_ai 1.4 把 RAG 封装进一行 SQL，而跨语言 RAG 研究 TR-RAG 也揭示了检索器质量决定生成上限。这一切的基础，都是把文本变成"向量"再做相似度检索。理解 Embedding 与向量检索，是看懂今天所有知识库问答的底层钥匙。

---

**🧠 深度解析**

**▌ 它是什么**
Embedding（嵌入）是把文字、图片等离散对象映射成一串固定长度浮点数的技术，这串数字就是"向量"，它在高维空间里的几何距离代表语义相似度。向量检索则是用一个查询向量去数据库里找"距离最近"的若干向量。一个常见误区是以为向量检索就是"模糊搜索"——其实它衡量的是语义而非字符重叠：搜"小狗"能召回"宠物狗的照片描述"，尽管字面毫无重合。需要强调的是，向量检索并不是要取代数据库，而是与关键词检索形成互补：工业级方案普遍采用"稠密+稀疏"混合检索，用 BM25 兜底字面命中、用向量兜底语义召回，再用 Reranker 融合排序，这样才能兼顾"精确"与"相关"。适用边界：非结构化文本/图像的语义召回最适合；需要精确字段匹配（如订单号）的场景仍应交给结构化查询。

**▌ 它解决了什么问题**
Before：关键词搜索在"退订会员"vs"取消订阅"之间束手无策，召回率随同义词、口语化表达骤降；企业知识库里 30% 的有效答案因措辞不同而被漏掉。After：向量检索把"意思相近"纳入匹配，腾讯云 tencentdb_ai 1.4 让用户用一行 `rag()` 函数即可完成"向量化→TopN 召回→Prompt 拼装→生成"全链路，把过去要写四段 SQL 的胶水代码收进一个调用。TR-RAG 的研究进一步证明，检索器与排序质量直接决定跨语言 RAG 的证据正确性。最近 tencentdb_ai 1.4 已用于企业内部知识库问答、客服辅助、合同审查等场景，显著降低接入门槛。

**▌ 核心原理拆解**
**第一层：直觉理解**——Embedding 像是给每句话发一张"语义坐标卡"：意思接近的话，坐标挨得近；意思无关的话，隔得很远。检索就是在一张巨大的星图上找离你最近的点。

**第二层：技术流程拆解**——文本 → Embedding 模型编码成向量 → 写入向量库(如 pgvector)并建立索引(IVF/HNSW) → 查询文本同样编码 → 近似最近邻(ANN)搜索返回 TopK → 拼接上下文送大模型。关键参数：向量维度(768/1024/1536)、距离度量(余弦/内积)、索引类型。

**第三层：公式与核心机制**——核心是余弦相似度：sim = (A·B)/(‖A‖‖B‖)，值越接近 1 越相似。为提升精度常配合 Reranker（交叉编码器）做精排，以及倒数排名融合(RRF)把多路召回结果合并，TR-RAG 还引入教师正则化强化学习优化检索器。

**▌ 动手验证**
用 sentence-transformers 生成向量并做最近邻检索：
```python
from sentence_transformers import SentenceTransformer
import numpy as np
m = SentenceTransformer("BAAI/bge-small-zh-v1.5")
q = m.encode("怎么退订会员")
docs = m.encode(["取消订阅的方法","今天天气","退款流程"])
sims = (q @ docs.T) / (np.linalg.norm(q)*np.linalg.norm(docs,axis=1))
print(np.argsort(-sims))   # 输出最相似文档下标
```
注意中文场景优先选 bge/m3e 等中文模型；维度不一致会报错。

**▌ 对比与选型**
| 对比维度 | 稠密向量检索 | 关键词检索 | 知识图谱 |
|---------|------|------|------|
| 核心思想 | 语义相似 | 字面匹配 | 关系遍历 |
| 适用场景 | 语义问答 | 精确查找 | 多跳推理 |
| 性能表现 | 高召回 | 高精准 | 中 |
| 学习成本 | 中 | 低 | 高 |

### 4. 【多Agent编排架构：用角色分工与共享记忆把复杂任务拆给智能体团队】

> 📍 **导语**：单个大模型再强，面对"调研竞品→写报告→做PPT→发邮件"这类长链任务也会顾此失彼。2026 年，多 Agent 编排成为 Agent 开发的主流范式：让多个各有所长的智能体像项目组一样分工协作。从微软 AutoGen 到腾讯云的 Agentic RAG 设计，再到本周论文对 Agent 能力组件的系统评测，都在指向同一结论——复杂任务的解法不是"更大的模型"，而是"更好的编排"。

---

**🧠 深度解析**

**▌ 它是什么**
多 Agent 编排（Multi-Agent Orchestration）是指用一个"总控"或"协作协议"把多个具备不同角色、工具、记忆的智能体组织起来，共同完成单个智能体难以搞定的复杂任务。它常被误认为只是"多开几个 ChatGPT 窗口"——其实真正的编排包含角色定义、消息路由、共享上下文与终止条件。一个典型形态是"经理 Agent"接到任务后拆解给"研究员""程序员""审稿人"等子 Agent。适用边界：任务可清晰拆解为子目标、且子目标间有依赖或需专长分工时最有效；简单一次性问答用单 Agent 即可。

**▌ 它解决了什么问题**
Before：让一个 Agent 又搜资料又写代码又做质检，容易在长链中"记混"或"中途跑偏"，且无法并行，耗时随步骤线性增长。After：编排架构让研究员并行检索、程序员实现、审稿人独立校验，腾讯云在 Agentic RAG 设计中指出，两轮检索迭代即可捕获 95% 的增益，更深循环收益有限——说明"会规划、会评估"的编排比无脑加轮次更重要。本周论文综述也强调，Agent 评测正从"看任务完成"深入到"诊断能力组件"。最近微软 AutoGen 等框架已让多 Agent 对话成为生产级能力，企业可据此搭建稳定的协作流水线。

**▌ 核心原理拆解**
**第一层：直觉理解**——多 Agent 编排就像拍电影：导演(总控)定目标，编剧、摄影、剪辑各司其职，彼此通过"场记本"(共享记忆)对齐进度，最后由导演判断是否杀青。

**第二层：技术流程拆解**——总控 Agent 接收目标 → 拆分子任务并分配角色 → 各子 Agent 带专属工具/记忆执行(可并行) → 通过共享黑板(Blackboard)或消息总线交换中间结果 → 总控评估是否达标，未达标则重规划 → 输出最终结果。关键参数：角色数、上下文共享粒度、最大迭代轮次。

**第三层：公式与核心机制**——核心机制是"分解-委派-汇聚"循环，常结合 ReAct(推理+行动交替)模式：Thought 决定下一步、Action 调用工具、Observation 回收结果。为防失控，通常设最大步数与一致性校验作为终止条件。

**▌ 动手验证**
用 AutoGen 起一个双 Agent 对话：
```python
import autogen
cfg = {"model": "gpt-4o", "api_key": "YOUR_KEY"}
boss = autogen.AssistantAgent("boss", llm_config=cfg)
worker = autogen.AssistantAgent("worker", llm_config=cfg)
grp = autogen.GroupChat(agents=[boss, worker], messages=[], max_round=5)
m = autogen.GroupChatManager(groupchat=grp, llm_config=cfg)
boss.initiate_chat(m, message="调研MCP协议并给出落地建议")
```
注意：`max_round` 控制轮次防死循环；生产环境需为各 Agent 配置不同系统提示与工具。

**▌ 对比与选型**
| 对比维度 | 多Agent编排 | 单Agent | 工作流引擎 |
|---------|------|------|------|
| 核心思想 | 角色协作 | 单体执行 | 固定步骤 |
| 适用场景 | 复杂长链 | 单一任务 | 确定流程 |
| 性能表现 | 高灵活 | 中 | 高稳定 |
| 学习成本 | 高 | 低 | 中 |

### 5. 【DPO与GRPO对齐：用偏好数据训练出更听话的大模型】

> 📍 **导语**：2022 年之前，让模型"更符合人类偏好"主要靠 RLHF，需要训练一个独立的奖励模型再跑强化学习，流程繁琐且容易崩溃。2023 年 DPO 把这件事简化成一次监督式分类，2024 年 DeepSeek 提出的 GRPO 又让数学推理类训练不再依赖 critic 网络。2026 年，DPO/GRPO 已成为开源模型对齐的事实标准，理解它们就理解了"为什么今天的模型更听话"。

---

**🧠 深度解析**

**▌ 它是什么**
DPO（Direct Preference Optimization，直接偏好优化）与 GRPO（Group Relative Policy Optimization，组相对策略优化）都是"对齐"技术——让模型输出更符合人类期望，而非仅仅预测下一个字。DPO 的核心洞见是：偏好数据里已经隐含了奖励信号，不必单独训练奖励模型，直接优化策略即可。一个常见误区是以为 DPO 和 SFT（监督微调）是一回事——SFT 学"标准答案长什么样"，DPO 学"两个答案里哪个更好"。GRPO 则是把 PPO 里的 Critic 网络去掉，用一组采样回答的相对得分做基线。适用边界：有人类偏好/可验证对错的数据时最合适；纯无标注语料仍靠预训练。需要指出的是，DPO 与 GRPO 并非互斥：前者擅长用人类偏好数据做通用风格对齐，后者擅长在答案可被程序化验证（如代码能跑通、数学题答案正确）的场景里定向强化推理能力，工程实践中常常先用 SFT 打底、再用 DPO 调风格、最后用 GRPO 刷推理，形成三段式对齐流水线。

**▌ 它解决了什么问题**
Before：RLHF 要先训奖励模型(RM)，再用 PPO 强化学习微调策略，两套模型、四阶段流程，奖励模型易"过优化"导致胡说（奖励黑客）。After：DPO 把流程压成"偏好数据 + 一次分类式损失"，Rafailov 等在原论文中证明其与 RLHF 等价却更稳定。GRPO 进一步省掉 Critic，DeepSeek-R1 用它在数学/代码推理上取得突破，训练显存与稳定性显著改善。最近 2026 年的多篇对齐研究（如把可验证奖励当分类标签的 RLVR 变体）都可视为这条路线的发展，说明"用偏好/可验证信号直接对齐"已成主流。

**▌ 核心原理拆解**
**第一层：直觉理解**——DPO 像老师改卷：不给你打具体分数(奖励模型)，而是直接说"这篇比那篇好"，模型就照着"好"的方向调；GRPO 则像小组互评，拿一组答案互相比较，相对优秀的才被鼓励。

**第二层：技术流程拆解**——收集偏好对(更好回答 y_w / 更差回答 y_l) → 同时加载参考模型(冻结)与策略模型 → 用偏好损失拉大两者在参考模型下的对数概率差 → 反向传播更新策略。GRPO 改为：对一个问题采样多组回答 → 按得分分组 → 组内相对优势做策略梯度。

**第三层：公式与核心机制**——DPO 损失本质是二元交叉熵的变体，用参考模型做"锚"防止策略跑太远；GRPO 用组内均值与标准差归一化优势，避免了对 Critic 的依赖，这正是它比 PPO 省显存的关键。

**▌ 动手验证**
用 TRL 库跑一次 DPO：
```python
from trl import DPOConfig, DPOTrainer
from datasets import load_dataset
data = load_dataset("trl-lib/ultrafeedback-bin")["train"]
trainer = DPOTrainer(model="Qwen/Qwen2-1.5B", ref_model="Qwen/Qwen2-1.5B",
                     args=DPOConfig(output_dir="./dpo", max_length=512), train_dataset=data)
trainer.train()
```
注意需准备"prompt / chosen / rejected"三字段数据；`ref_model` 通常复用基座以防偏移。

**▌ 对比与选型**
| 对比维度 | DPO | GRPO | RLHF(PPO) |
|---------|------|------|------|
| 核心思想 | 偏好分类 | 组相对策略 | 奖励+强化 |
| 适用场景 | 通用偏好 | 可验证推理 | 复杂偏好 |
| 性能表现 | 稳定简洁 | 推理强 | 上限高 |
| 学习成本 | 低 | 中 | 高 |

### 6. 【Agent应用落地评测：用benchmark给智能体的真实能力画清边界】

> 📍 **导语**：2026 年，Agent 从"能演示"走向"能交付"，但一个尴尬问题是：很多 Agent demo 看起来惊艳，放到真实长链任务却频频翻车。本周多篇论文（DexVerse 机器人基准、UniClawBench Agent 评测）都在做同一件事——把 Agent 的能力拆成可测量的组件，诚实暴露真实水位。理解如何评测 Agent，比盲目堆功能更能决定它能不能上线。

---

**🧠 深度解析**

**▌ 它是什么**
Agent 评测（Agent Evaluation）是一套衡量智能体在真实任务中"能不能做对"的方法体系，它不只看最终答案，更看规划、工具调用、记忆、自我纠错等能力组件。常见误区是拿"聊天流畅度"当 Agent 能力强弱——流畅不等于能干。一个典型评测会构造带可验证结果的任务（如"打开订单系统查状态并邮件通知"），再记录成功率、步骤效率、出错恢复率。适用边界：凡是准备把 Agent 放进生产环境的团队都必须评测；纯玩具 demo 可暂不苛求。还需注意，评测集本身会"过时"——当模型在新数据上训练后，旧 benchmark 分数会虚高，因此成熟的团队会保留一份内部、不公开的"留存集（hold-out）"作为真实能力探针，避免被公开榜单的过拟合假象误导。

**▌ 它解决了什么问题**
Before：企业被一段剪得最好的 demo 视频打动就上线，结果发现跨任务、跨实体泛化极差——DexVerse 基准显示，Diffusion Policy、OpenVLA、π₀.₅ 等主流方法在 19 个机器人任务上平均在线成功率仅 0.34。After：系统性 benchmark 把"通用操作"从口号变成可测量目标，诚实说出"当前成功率 34%"比粉饰 demo 更有价值。本周论文综述指出，Agent 评测正从"看任务完成"深入到"诊断能力组件"，UniClawBench 把任务拆成能力维度逐一打分。最近这股"给能力画边界"的思潮，正推动 Agent 从营销驱动转向工程驱动，让团队知道模型到底行不行。

**▌ 核心原理拆解**
**第一层：直觉理解**——评测 Agent 像考驾照：不只看你能不能把车开动，还要分项测倒车、侧方、夜间灯光，任何一项挂科都不发照。

**第二层：技术流程拆解**——定义任务集(覆盖多场景/多实体) → 设定可验证的完成判据 → 让 Agent 跑任务并记录轨迹(用了哪些工具、走了几步) → 按能力组件打分(规划/检索/执行/恢复) → 汇总成功率与失败模式。关键参数：任务多样性、判据严格度、轨迹可追溯性。

**第三层：公式与核心机制**——核心机制是"乘积空间评估"：用 任务×实体×视觉 的组合空间暴露泛化短板，而非挑最好片段；通过组件级诊断定位是"规划错"还是"工具错"，从而指导改进而非笼统调参。

**▌ 动手验证**
用简单脚本统计 Agent 在多任务上的成功率：
```python
import numpy as np
results = [1,0,0,1,0,1,0,0,1,0]   # 1=成功 0=失败
print("成功率:", np.mean(results))  # 输出 0.4
# 进一步按能力组件分组统计，定位薄弱项
```
注意：真实评测需可验证判据(如文件确实生成、订单状态确实变更)，不能靠人工"看着像对"。

**▌ 对比与选型**
| 对比维度 | 组件级benchmark | 端到端成功率 | 人工评审 |
|---------|------|------|------|
| 核心思想 | 诊断能力 | 看结果 | 主观判断 |
| 适用场景 | 迭代优化 | 验收 | 早期 |
| 性能表现 | 高信息量 | 直观 | 灵活 |
| 学习成本 | 高 | 低 | 中 |
