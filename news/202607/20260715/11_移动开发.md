### 1. 【SwiftUI实时活动（Live Activities）2.0与灵动岛新交互：ActivityKit全场景升级】

> 📍 **导语**: 在 iOS 26 / iPadOS 26 中，Apple 将 Live Activities 升级至 2.0：灵动岛支持用户直接操作、单应用并发实时活动从 2 个放宽到 5 个、ActivityKit Widget 引入关键帧动画，并首次把实时活动带到 iPad 锁屏。WWDC26 进一步公布横向灵动岛布局、Apple Watch / CarPlay 小型呈现与 LiveActivityIntent，让"不打开 App 也能操作"成为系统级常态，对电商、出行、外卖类应用的交互重构影响深远。

---

**📱 深度报道**

**▌ 更新全景**: Live Activities 2.0 适用 iOS 26 / iPadOS 26 及以上。核心变化有四点：① Live Activity Intents——用户可在灵动岛内直接触发 App 定义的 App Intents 完成操作，无需进入 App；② 并发上限从每应用 2 个提升至 5 个；③ ActivityKit Widget 支持关键帧动画（keyframe animations）；④ iPadOS 首次在锁屏支持实时活动。WWDC26 披露的 iOS 27 方向进一步引入横向灵动岛布局（通过 `isDynamicIslandLimitedInWidth` 环境值判断）、`supplementalActivityFamilies([.small])` 以适配 Apple Watch 与 CarPlay 小型呈现，以及 `LiveActivityIntent` 类型。数据层面，iOS 26 放宽了更新频率限制，Xcode 26 的灵动岛预览趋于稳定，进入门槛显著低于此前版本。

**▌ 技术细节深解**: Live Activities 本质是 WidgetKit 的扩展，UI 用 SwiftUI 编写，生命周期由 ActivityKit 管理。关键设计是 `ActivityAttributes` 区分静态属性与动态 `ContentState`；iOS 27 新增的 `LiveActivityIntent` 让"快速操作"脱离 App 完成。示例：

```swift
struct DeliveryAttributes: ActivityAttributes {
    public struct ContentState: Codable, Hashable {
        var status: DeliveryStatus
        var estimatedArrival: Date
        var progress: Double
    }
    var orderID: String
    var shopName: String
}

// 灵动岛展开视图（节选）
DynamicIsland {
    DynamicIslandExpandedRegion(.leading) { Text("🛵") }
    DynamicIslandExpandedRegion(.trailing) { Text(timerInterval: dates) }
    DynamicIslandExpandedRegion(.center) { Text(state.status.rawValue) }
}

// iOS 27 用户操作意图
struct ConfirmPickupIntent: LiveActivityIntent {
    var activityID: String
    static var title: LocalizedStringResource = "确认取货"
    func perform() async throws -> some IntentResult {
        try await DeliveryAPI.confirm(activityID)
        return .result()
    }
}
```

更新通过 `activity.update(using:)` 或 APNs 推送令牌完成；共享场景用 broadcast channel，私密场景用 push token（注意 broadcast 不能启动 Live Activity）。

**▌ 开发者迁移指南**: 现有项目需：① 在 `.entitlements` 中加入 ActivityKit 与推送权限；② 注册 push token 并上传后端；③ 为 iPadOS 新增锁屏布局；④ iOS 27 用 `isDynamicIslandLimitedInWidth` 处理横向灵动岛，并用 `supplementalActivityFamilies` 覆盖 Watch/CarPlay；⑤ 务必设置 `staleDate` 避免过期 UI 滞留。建议先在 Xcode 26 模拟器验证，再用 TestFlight 灰度。Breaking 点：旧版超出 2 个并发的兜底逻辑需重写。

**▌ 生态与竞品对比**: 相比 Android 的 Ongoing Activity、鸿蒙万能卡片，Apple Live Activities 强在灵动岛硬件载体与系统级呈现，弱在多应用并发时的屏幕空间。社区已有 50M+ 下载量独立开发者的生产实践沉淀，国内电商/出行团队普遍已接入，迁移成本中等。

---

**🤖 开发研判**

🔮 **技术趋势**: Live Activities 正从"展示状态"走向"在系统层完成操作"，与 App Intents、Siri、Action Button 形成闭环，是 Apple Intelligence 时代 App 外交互的核心载体。

📊 **开发者决策影响**: 外卖/出行/赛事类应用应立即规划接入；新项目从 Day 1 采用 `LiveActivityIntent` 设计。技能上要求掌握 WidgetKit + SwiftUI + App Intents 三者协同。

⚠️ **适配风险**: 推送更新存在静默失败比例，需监控 delivery 回执；漏设 `staleDate` 会导致锁屏显示过期信息被投诉；横向灵动岛在 beta SDK 命名未稳定前需做兼容判断。

💡 **学习优先级**: ① ActivityAttributes/ContentState 建模 ② 灵动岛四态布局 ③ LiveActivityIntent ④ APNs 推送更新链路。资源：Apple Developer《Live Activities essentials》(WWDC26)、ActivityKit 官方文档。

### 2. 【Swift Charts 3 引入三维图表与@Animatable：声明式数据可视化跃迁】

> 📍 **导语**: iOS 26 / macOS / visionOS 26 中，Swift Charts 迎来史上最大升级——首次支持 Chart3D 三维图表，开发者可在三维空间绘制数据、配置相机/光线/材质；同时 SwiftUI 新增 `@Animatable` 宏，把视图、修饰符、文本渲染器、形状的动画能力以声明式自动合成。两项更新共同把"声明式数据可视化"推向新的表现力层级，对金融、健康、科学类 App 的图表体验意义重大。

---

**📱 深度报道**

**▌ 更新全景**: 本次升级含两条主线。其一，Chart3D 将 2D 图表中熟悉的 PointMark、轴标记、标签等概念完整带入 3D 视图，支持散点图、曲面图（数学函数图），并可配置相机角度、光线与材质、渲染属性。其二，SwiftUI 新增 `@Animatable` 宏，自动合成 `animatableData` 以遵循 `Animatable` 协议；配合 `@AnimatableIgnored` 排除不可动画属性。iOS 26 的 SwiftUI 还整体拥抱 Liquid Glass 设计语言、引入 WebView 与基于 AttributedString 的富文本编辑，与图表升级形成统一的设计体系。

**▌ 技术细节深解**: Chart3D 只需把 `Chart` 改为 `Chart3D`，`PointMark` 随即支持 Z 值，并用 `ZAxisLabel` 标注第三轴。示例：

```swift
Chart3D {
    ForEach(penguins) { p in
        PointMark(
            x: .value("Beak", p.beakLength),
            y: .value("Flipper", p.flipperLength),
            z: .value("Weight", p.bodyMass)
        )
        .foregroundStyle(by: .value("Species", p.species))
    }
}
.axis3D(x: .visible, y: .visible, z: .visible)
.chart3DScale(x: 0.8, y: 0.8, z: 0.8)

// @Animatable 形状动画
@Animatable
struct CoolShape: Shape {
    var width: CGFloat
    var angle: Angle
    @AnimatableIgnored var isOpaque: Bool
    func path(in rect: CGRect) -> Path { /* 使用 width/angle */ Path() }
}
```

`@Animatable` 让 `width` 与 `angle` 平滑过渡，而 `isOpaque` 被排除，避免无意义的中间态。

**▌ 开发者迁移指南**: 现有 2D 图表几乎无需改动即可作为子图嵌入 3D 场景；引入三维坐标时注意为 Z 轴补充数据源与标签。采用 `@Animatable` 时，原手写 `animatableData` 的样板可删除，仅保留 `@AnimatableIgnored` 标注。最低部署需 iOS 26 / visionOS 26；在旧系统上 3D 特性不可用，需 `if #available` 兜底到 2D。

**▌ 生态与竞品对比**: 相较 ECharts、Victory（React Native）等第三方图表库，Swift Charts 的优势是原生成就、与 SwiftUI 状态流深度绑定、零额外依赖；短板是生态插件与深度定制仍落后于 Web 图表生态。国内团队多用于原生数据看板与可穿戴端呈现。

---

**🤖 开发研判**

🔮 **技术趋势**: 3D 图表 + 声明式动画标志着 SwiftUI 可视化正从"静态呈现"迈向"可探索的空间数据"，与 visionOS 空间计算路线高度契合。

📊 **开发者决策影响**: 健康/健身、金融行情、科研类 App 应优先评估 3D 图表；新项目可直接采用 `@Animatable` 简化动画代码，降低维护成本。

⚠️ **适配风险**: 3D 图表的性能与可访问性（如 VoiceOver 描述）需额外打磨；老设备回退逻辑若缺失会导致运行崩溃；复杂相机交互的学习曲线偏高。

💡 **学习优先级**: ① Chart3D 坐标与标记 ② 相机/材质配置 ③ `@Animatable` 宏 ④ 2D→3D 渐进迁移。资源：Apple Developer《将 Swift Charts 扩展成三维图表》(WWDC2025)、InfoQ 中文《iOS 26 的 SwiftUI 拥抱 Liquid Glass》(2026-07)。

### 3. 【鸿蒙元服务（原子化服务）开发范式：ASCF框架与服务中心分发革命】

> 📍 **导语**: 在 HDC 2026（6 月 13 日）元服务分论坛上，华为披露鸿蒙元服务已汇聚超 2.4 万家合作伙伴，负一屏月活突破 1.9 亿，并发布服务分发增长平台 SDG、鸿券通等能力。元服务以"免安装、一次开发多端部署"为核心，依托 ASCF 开发框架（高码+零代码）与万能卡片，正在把应用分发从"商店下载"重构为"服务随需而至"，是鸿蒙生态 2026 年最值得移动开发者跟进的方向。

---

**📱 深度报道**

**▌ 更新全景**: 元服务是 HarmonyOS 的轻量化服务形态，具备无需下载安装、一次开发多端部署等特性，覆盖鸿蒙 6.0 及以上并兼容历史版本。HDC 2026 公布的分发体系已接入负一屏、小艺、浏览器、智能短信等系统入口，并整合账号、扫码、支付、位置、地图等履约能力。开发侧，鸿蒙基于 ASCF 框架提供高码开发与零代码开发两套方案：高码方案支持主流小程序存量资产转换与自动化代码迁移，零代码方案（联合码上飞）面向中小商户，显著降低适配成本。

**▌ 技术细节深解**: 元服务由"元服务（Meta-Service）逻辑最小单元 + 万能卡片（Universal Card）+ 分布式服务框架"三大支柱构成。能力在 `module.json5` 中声明，包名格式须为 `com.atomicservice.[appid]`。示例：

```json
// module.json5（节选）
{
  "module": {
    "name": "entry",
    "type": "atomicService",
    "deviceTypes": ["phone", "tablet", "wearable"],
    "abilities": [{
      "name": "FoodOrderAbility",
      "srcEntry": "./ets/entryability/EntryAbility.ts",
      "description": "$string:food_order_desc",
      "skills": [{ "entities": ["entity.food.order"], "actions": ["ohos.want.action.viewData"] }]
    }]
  }
}
```

万能卡片支持 1×1（手表）到 4×4（智慧屏）多尺寸自适应，并通过分布式数据管理（DDM）实现跨设备状态同步；30 天未使用自动清理，资源零残留。

**▌ 开发者迁移指南**: 新项目需在 AppGallery Connect 先创建元服务获取 AppID，再以 `com.atomicservice.[appid]` 命名创建 DevEco Studio 工程。已有小程序团队可用 ASCF 框架做存量转换，避免 ArkTS/ArkUI 与 ASCF 混合开发（二者技术路线不兼容）。上架前用"元服务体检工具"评分，发布邀请测试收集反馈。注意资产包首次按需下载通常 <5MB，启动 <300ms。

**▌ 生态与竞品对比**: 相比 iOS App Clip、Android Instant App，鸿蒙元服务强在多端流转与系统级入口密度（负一屏/小艺/碰一碰），弱在 iOS/Android 的跨平台复用性。国内餐饮、出行、金融、赛事行业已规模落地。

---

**🤖 开发研判**

🔮 **技术趋势**: 元服务代表"以服务为中心"的分发范式，AI 搜索与场景感知（如出境自动聚合当地服务）将使其成为鸿蒙商业化的核心抓手。

📊 **开发者决策影响**: 中小商户与轻量工具类团队应优先用零代码 ASCF 入局；中大型团队评估高码 ASCF 做小程序资产转换，复用存量降低迁移成本。

⚠️ **适配风险**: ArkTS 与 ASCF 路线不可混编，技术选型需一次定调；系统入口推荐算法带来的流量波动需运营侧配合；跨设备能力协商（如车机无摄像头降级）需显式处理。

💡 **学习优先级**: ① 元服务工程创建与 module.json5 ② 万能卡片多尺寸 ③ ASCF 框架资产转换 ④ 分布式状态同步。资源：华为开发者联盟《元服务开发旅程》、IT之家《HDC 2026：AI 重塑服务分发逻辑》(2026-06-16)。

### 4. 【Jetpack Compose Navigation 3 类型安全导航与 Material 3 Expressive 设计语言】

> 📍 **导语**: 在 Google I/O 2026，Android 团队宣布 Material 进入"Compose-first"时代：MDC-Android（Material Views 1.14.0）成为 Views 库最终稳定版并转入维护模式，后续特性全部聚焦 Material Compose。同步推出的 Navigation 3 以纯声明式、类型安全、返回栈完全透明为核心，并深度集成 Material 自适应库；Material 3 Expressive 也将随 Compose 1.5.0 转正，Android 大屏适配由此进入状态驱动导航新阶段。

---

**📱 深度报道**

**▌ 更新全景**: Navigation 3 是仅适配 Compose 的独立库，最新稳定版 `navigation3-runtime` / `navigation3-ui` 为 1.1.0（Wear OS 另有 `compose-navigation3`）。它彻底移除 NavController、NavGraph 与 XML 导航图，由 BackStack、NavDisplay、NavEntry、NavKey 四大组件构成。Material 侧：Material Views 1.14.0 把 M3 Expressive 带到 Views（Expressive 主题、列表组件、强调字阶、11 个组件的表达式样式），随后进入维护模式；2026 下半年 Compose 1.5.0 将把 M3 Expressive 实验 API 转正，并引入 Styles API（更新样式时跳过组合阶段以提升性能）。

**▌ 技术细节深解**: Navigation 3 用可序列化的密封类定义路由，传参不再依赖 Bundle，从类型层面杜绝 Key 写错与转换异常。返回栈即普通状态列表，可自由增删清空。示例：

```kotlin
@Serializable
sealed interface Screen : NavKey {
    @Serializable data object Home : Screen
    @Serializable data class Details(val itemId: String) : Screen
}

val backStack = rememberNavBackStack(Screen.Home)
NavDisplay(
    backStack = backStack,
    sceneStrategies = listOf(rememberSwipeDismissableSceneStrategy())
) {
    entry<Screen.Home> {
        HomeScreen(onOpen = { id -> backStack.add(Screen.Details(id)) })
    }
    entry<Screen.Details> { key ->
        DetailsScreen(itemId = key.itemId, onBack = { backStack.removeLastOrNull() })
    }
}
```

Wear OS 还可注入 `rememberSwipeDismissableSceneStrategy()` 实现滑动返回。

**▌ 开发者迁移指南**: 在 `build.gradle` 添加 `navigation3-runtime` / `navigation3-ui` 依赖即可，无需 XML。Android 17（Target SDK 37）起，sw>600dp 设备将忽略 `screenOrientation`，强制支持横竖旋转与自由窗口——Navigation 3 的状态驱动模型正为此而生。建议新项目直接采用 NavDisplay，老项目从 Navigation 2 平滑迁移，先用 sealed 路由替换导航图。

**▌ 生态与竞品对比**: 相较 iOS 的 NavigationStack、Flutter 的 Navigator 2.0，Navigation 3 的最大差异是"返回栈透明化"与自适应库深度集成，天然适配折叠屏双页布局。社区已有中文实战指南 widespread，国内大厂在折叠屏适配中优先采纳。

---

**🤖 开发研判**

🔮 **技术趋势**: Compose-first 是 Android UI 开发的终局信号，Views 库停更意味着新特性只在 Compose 出现；状态驱动导航将成为大屏/折叠屏时代的标配。

📊 **开发者决策影响**: 新项目应直接基于 Compose + Navigation 3 + M3 Expressive；存量 Views 项目评估迁移节奏，至少在新功能上采用 Compose。技能上需掌握密封类路由与自适应导航套件。

⚠️ **适配风险**: Android 17 强制大屏适配会直接击穿未做横屏处理的单竖屏 App，导致黑边与配置变更崩溃；Navigation 3 与旧 Fragment 体系并存项目需清理导航双栈；M3 Expressive 实验 API 在转正前存在命名变动。

💡 **学习优先级**: ① Navigation 3 四大组件 ② 密封类类型安全路由 ③ M3 Expressive 主题 ④ Styles API 与自适应导航。资源：Material Android 官方博客《Material Android is Compose-first》(2026)、掘金《Jetpack Navigation3 超详细入门实战指南》(2026)。

### 5. 【React Native 0.81 与 Expo SDK 55：新架构强制化与端到端构建提速】

> 📍 **导语**: React Native 0.81 默认面向 Android 16（API 36），强制 Edge-to-Edge 全屏布局、引入预编译 iOS 框架使构建提速最高 10×，并彻底移除 JSC 引擎；Expo SDK 54 随附 RN 0.81，而 Expo SDK 55（2026 年 2 月，基于 RN 0.83）则彻底删除 Legacy Architecture——新架构不可逆。对仍停留在旧架构的团队，这是一次必须规划的强制迁移，也是 RN 走向"成熟期"的里程碑。

---

**📱 深度报道**

**▌ 更新全景**: RN 0.81 的三项关键变化：① 默认 targetSdk 36，Android 16 要求内容延伸至状态栏/导航栏下方（Edge-to-Edge），新增 `edgeToEdgeEnabled` Gradle 属性仅影响旧版 Android；② `StatusBar` 的 `translucent` 等属性弃用，官方推荐 `react-native-safe-area-context`；③ iOS 原生库以预编译二进制发布（`RCT_USE_PREBUILT_RNCORE=1`），构建最高快 10×，JSC 被完全剔除、仅保留 Hermes。Expo 侧：SDK 54 随附 RN 0.81 与预编译 iOS 框架；SDK 55 使用 RN 0.83，Legacy Architecture 被移除（`newArchEnabled: false` 将被忽略）。RN 0.82 是首个完全运行于新架构的版本。

**▌ 技术细节深解**: 新架构消除旧 Bridge 的 JSON 序列化瓶颈，原生调用从约 200ms 降至 2ms，TurboModules 懒加载使原生交互快约 80%。迁移核心是去掉 `newArchEnabled` 开关：

```json
// app.json（SDK 55 起该字段应直接删除）
{
  "expo": {
    // "newArchEnabled": false  ← 在 SDK 55 被忽略，必须删除
  }
}
```

```bash
npx expo install expo@^55.0.0 --fix   # 升级并修依赖
npx expo-doctor                        # 校验 New Architecture 兼容性
npx expo prebuild --clean              # 重新生成原生代码
```

`expo-doctor` 接入 React Native Directory，能在构建前标出每一个不兼容/未验证的第三方库。

**▌ 开发者迁移指南**: 已在 SDK 54 启用新架构的团队可平滑升级；SDK 53 及更早需先 53→54 再 54→55。须在升级前运行 `expo-doctor` 校验依赖（典型拦路虎：Redux、i18n、CodePush、Reanimated v3→v4）。截至 2026 年 1 月，约 83% 的 SDK 54 EAS Build 项目已用新架构；尚未迁移的约 17% 实际运行在自 2025 年 6 月冻结、无安全补丁的代码路径上。

**▌ 生态与竞品对比**: 相较 Flutter（自绘引擎）、KMP（原生共享逻辑），RN 借新架构在"Web 技术栈 + 接近原生性能"之间取得平衡；Expo 的"开箱即用"进一步放大了 AI 编程语料优势。生产迁移报告显示冷启动快 43%、渲染快 39%、内存降 26%。

---

**🤖 开发研判**

🔮 **技术趋势**: 新架构强制化宣告 RN "兼容旧世界"时代结束，Fabric/TurboModules 成为唯一正途，并发特性（Suspense、useTransition）得以按设计运行。

📊 **开发者决策影响**: 生产 App 若仍 `newArchEnabled: false`，等于运行在未打补丁的废弃路径，应立即排期升级。新项目直接用 Expo SDK 55 + RN 0.83，无需考虑回退。

⚠️ **适配风险**: 第三方库兼容性是最主要风险，`expo-doctor` 不可跳过；Edge-to-Edge 会改变既有安全区布局，旧版沉浸式状态栏代码需重写；预编译框架牺牲了部分源码级调试便利性。

💡 **学习优先级**: ① 新架构原理（Fabric/TurboModules）② expo-doctor 依赖校验 ③ Reanimated v4 与手势 ④ Edge-to-Edge 安全区适配。资源：Expo 官方《React Native's New Architecture》(2026)、The React Native Rewind《Expo 54, RN 0.81》(2026-07-15)。

### 6. 【Capacitor 7 与 Tauri Mobile：轻量 Web 技术栈跨移动端开发新进展】

> 📍 **导语**: 2026 年跨端版图中，Web 混合派以 Capacitor 与 Tauri Mobile 为代表持续扩张：Capacitor 主线已演进至 8.x（2025-12 GA、2026-05 稳定 8.3.4、9.0 进入 alpha），Tauri 2.0+ 把 Rust 驱动的极轻量外壳从桌面带向移动端。二者让 React/Vue/Svelte 等 Web 项目以"加一层原生壳"的方式低成本进入 App Store 与 Google Play，成为 RN/Flutter/KMP 之外的高性价比选择，尤其适合工具类、内容展示与物联网控制场景。

---

**📱 深度报道**

**▌ 更新全景**: Capacitor 定位为"Web Native 应用的跨平台原生运行时"，用 JS/HTML/CSS 生成 iOS、Android 与 PWA，核心是"原生壳 + 系统 WebView + JS↔原生 bridge"三件套，兼容 Cordova 插件。`cap init` → `cap add ios/android` → 自定义 Plugin 即可。当前 8.x 进一步现代化原生构建链，支持 `server.url` 远程加载与 live reload。Tauri 2.x 则以 Rust 为后端，前端任意框架，产物仅几 MB；移动端借助系统 WebView 容器，并通过 Rust commands 暴露原生能力，内存与线程安全由语言层保障。

**▌ 技术细节深解**: Capacitor 的插件 API 让 Web 代码直接调用原生功能，自定义插件在 Swift/Java 中仅几行即可暴露给 JS。示例：

```swift
// MyAwesomePlugin.swift
@objc(MyAwesomePlugin)
public class MyAwesomePlugin: CAPPlugin {
    @objc public func doNative(_ call: CAPPluginCall) {
        let alert = UIAlertController(title: "Title",
            message: "Please Select an Option", preferredStyle: .actionSheet)
        // ... 组装并 present
        call.resolve(["ok": true])
    }
}
```

```ts
// Web 侧调用
import { MyAwesomePlugin } from '@my-org/capacitor-awesome';
const r = await MyAwesomePlugin.doNative();
```

实践中，Enclave 项目用同一份 React Web 包分别嵌入 Capacitor 7（移动）与 Tauri 2（桌面）外壳，三者共享 `../app/dist`，原生能力由各端少量插件暴露，UI 与业务逻辑零重复。

**▌ 开发者迁移指南**: 已有 Web 项目 `npm install @capacitor/cli @capacitor/core && npx cap init` 即可起步；需为 iOS/Android 配置原生工程与签名。Tauri Mobile 需 Node + Rust + 移动编译环境（建议 Node 18/20 LTS）。注意：复杂定制 UI 动画（如游戏化界面）在纯 WebView 下仍有性能天花板，应将核心动效收敛到平台原生或克制实现；硬件密集调用（双目摄像头、BLE）不宜强行复用 Web 层。

**▌ 生态与竞品对比**: 相较 RN（映射原生组件）/ Flutter（自绘）/ KMP（原生共享逻辑），Capacitor/Tauri 的优势是 Web 资产最大复用与极小体积，短板是渲染依赖 WebView、性能上限偏低。2026 选型矩阵显示：AI 编程高语料场景 RN(Expo) 更优，炫酷动画选 Flutter，企业原生底座选 KMP，轻量小工具选 Tauri Mobile。

---

**🤖 开发研判**

🔮 **技术趋势**: Web 混合派正借 Rust（Tauri）与现代 WebView 性能回升"翻红"，与端侧 AI（如 WebGPU 推理）结合，有望成为轻量智能小工具的优选载体。

📊 **开发者决策影响**: 内部工具、IoT 控制台、内容型 App 可优先评估 Capacitor/Tauri 以降低 10× 开发成本；对极致性能与像素级一致有要求的项目仍选 Flutter/KMP。

⚠️ **适配风险**: WebView 版本碎片化（尤其 Android System WebView）导致行为不一致；iOS WKWebView 与 Android 容器 API 差异需桥接层抹平；离线资源更新与审核政策（remote 加载）需合规评估。

💡 **学习优先级**: ① Capacitor 工程初始化与插件机制 ② Tauri commands 与原生暴露 ③ WebView 性能与离线策略 ④ 与端侧 AI 的 Web 集成。资源：Capacitor 官网（2026）、CSDN《移动跨端 App 开发汇总》(2026)、zread.ai《Capacitor Mobile and Tauri Desktop Shells》(2026)。
