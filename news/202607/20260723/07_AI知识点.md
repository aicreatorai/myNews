### 1. 【注意力机制Attention：Transformer用相关性权重让模型学会抓重点】

> 📍 **导语**：你每次和 ChatGPT、Claude、Gemini 对话，背后都跑着同一个发动机——Transformer。而在 Transformer 内部真正起作用的"灵魂零件"是自注意力机制（Self-Attention）。它让模型在处理每个词时，能同时"看一眼"整段话里所有其他词，并自动判断谁和谁相关。没有它，现代大语言模型既不可能理解"指代"，也不可能并行训练到万亿参数。想真正读懂 2026 年的 AI，必须先搞懂注意力。

---

**🧠 深度解析**

**▌ 它是什么？**
注意力机制是一种"按内容相关性分配权重"的信息聚合方法。最直白的理解：当模型处理句子里的某个词时，它不为所有词一视同仁，而是给每个词算一个"相关分数"，再把其他词的信息按这个分数加权融合进来。一个常见误区是以为注意力等于"记忆"——其实它只是在当前这一步做一次性加权，并不跨步存储。它的适用边界是：只要数据里存在"谁和谁相关"的结构（文本、图像像素、蛋白质序列都算），注意力就有用；但纯顺序排列、彼此无关的任务，它反而多余。历史上，2017 年 Google 论文《Attention Is All You Need》用注意力彻底取代了 RNN 的循环结构，开启了大模型时代。

**▌ 它解决了什么问题？**
**Before → After 对比**：在注意力出现前，模型用 RNN/LSTM 逐词阅读，像透过一个小窗户看书，读到结尾常忘了开头，且无法并行训练。有了注意力后，任意两个词之间可以"一步直达"建立联系，无论距离多远。具体例子：句子"The trophy didn't fit in the suitcase because it was too big"中的"it"指代奖杯；若把"big"换成"small"，"it"就变成手提箱——注意力会根据上下文自动重算权重。最近知名模型如 GPT、Claude、Gemini、Llama、Mistral 全部基于注意力；据 teknoding 2026 年文章，注意力让训练速度提升数个数量级，并直接解锁了现代 AI 的"理解指代"能力。

**▌ 核心原理三阶拆解**
**第一层：直觉理解**——把注意力想象成在图书馆读论文：RNN 像助理大声朗读并不断把摘要写在一张越来越挤的卡片上，读到结论时开头早已模糊；Transformer 则像你把整篇论文摊在桌上，读任何一句都能瞬间翻回前面任意一句核对关联。这种"一次性看全、按需取重点"就是自注意力。

**第二层：技术流程拆解**——输入文本先切分为 token 并转成 embedding；然后每个 token 通过可学习矩阵生成三个向量：Query（我在找什么）、Key（我提供什么标签）、Value（我贡献什么信息）。流程为：① 用当前 token 的 Query 与所有 token 的 Key 做点积得原始分数；② 除以 √d 缩放后用 softmax 归一化成"百分比"，所有值相加为 1；③ 用这些百分比对全部 Value 加权求和，得到融合上下文后的新表示。多头注意力（Multi-Head）只是把这套匹配并行跑多次，不同头分别捕捉主谓一致、指代、情感等不同关系，最后拼接。

**第三层：公式与核心机制**——注意力分数本质是 softmax(QKᵀ/√d)V。√d 的作用是防止维度 d 变大时点积数值过大、把 softmax 推入梯度极小的饱和区。归一化保证权重之和为 1，使模型"在全部信息里分配注意力预算"。代价是它要对 n 个 token 两两计算，复杂度 O(n²)，这也是长文本昂贵的根因（unrot.co 2026 详解）。

**▌ 动手验证**
用 PyTorch 原生接口即可复现单头注意力，注意输入形状为 (序列长, 批量, 维度)：
```python
import torch
import torch.nn.functional as F

x = torch.randn(5, 1, 16)          # 5个token, 批量1, 维度16
q = x @ torch.randn(16, 16)        # Query
k = x @ torch.randn(16, 16)        # Key
v = x @ torch.randn(16, 16)        # Value
scores = q @ k.transpose(-2, -1)   # (5,5) 两两打分
weights = F.softmax(scores / 16**0.5, dim=-1)
out = weights @ v                  # 加权融合后的新表示
print(out.shape)                   # 预期 torch.Size([5, 1, 16])
```
注意：真实模型用 MultiheadAttention 并叠加多个 block；若维度不匹配会报矩阵乘法错误。

**▌ 对比与选型**
| 对比维度 | 自注意力 | RNN/LSTM | 卷积CNN |
|---------|--------|---------|---------|
| 核心思想 | 全局加权关联 | 逐步传递隐状态 | 局部滑窗提取 |
| 适用场景 | 长程依赖序列 | 短序列流式 | 局部特征图像 |
| 性能表现 | 可并行,O(n²) | 串行慢,O(n) | 并行,O(n·k) |
| 学习成本 | 中 | 低 | 低 |
| 生态成熟度 | 极高 | 老旧 | 高 |

### 2. 【KV缓存量化TurboQuant：把推理显存压到六分之一的精度无损术】

> 📍 **导语**：训练一次大模型贵在一次性，但"服务"它贵在 forever——每多一个用户、每长一段上下文，GPU 显存就被 Key-Value 缓存（KV Cache）持续吞噬。2026 年，随着上下文窗口突破 10 万 token、推理模型还要先生成超长思维链，KV 缓存成了部署成本里最顽固的那块。Google 的 TurboQuant 与 TriAttention 等工作给出了"压到六分之一甚至十分之一、且几乎零精度损失"的实战答案，这是每个做推理部署的人必须懂的省钱术。

---

**🧠 深度解析**

**▌ 它是什么？**
KV 缓存量化，是把 Transformer 每层的 Key、Value 向量从高精度（如 16 位浮点）压缩成低位宽（如 2.5–3 位）表示的技术。一个误区是以为"量化=粗糙丢信息"；其实现代方法通过极坐标变换与校正位，做到了肉眼不可察的无损。它的边界是：只压缩缓存、不动模型权重，因此部署时"即插即用"，不需重新训练。据 mlq.ai 的 LLM 架构指南，KV 缓存常常是大模型推理阶段真正的瓶颈，而非算力本身；GQA、MLA 等结构也正是为缩小它而生。

**▌ 它解决了什么问题？**
**Before → After 对比**：没有 KV 量化时，一个 32B 模型在 96K token 上下文下，仅 KV 缓存就要吃掉 30+ GB 显存，单卡根本扛不住；而且上下文越长，每层成本约按平方增长——96K 比 32K 贵约 9 倍（danilchenko 2026 测算）。用了 TurboQuant 后，每个缓存项压缩约 6 倍，从 16 位降到 2.5–3 位，在 Needle-in-a-Haystack、LongBench、RULER 等基准上零精度损失；TriAttention 用三角函数驱逐不重要的 Key，进一步把显存降到约 1/10.7。效果上，社区在 RTX 4090 上对 Gemma 3 4B 跑到 2 位精度、输出与原版逐字符一致。

**▌ 核心原理三阶拆解**
**第一层：直觉理解**——KV 缓存像模型边读边记的"课堂笔记"，每读一个词就记一页。笔记越写越厚，桌子（显存）就放不下。量化相当于把每页笔记用速记符号重写，厚度只剩六分之一，但关键信息没丢；极坐标法更像把"方位+距离"分开记，角度可共用一本全局字典，省掉大量冗余标注。

**第二层：技术流程拆解**——① 推理时每层产生 K、V 向量，原本以 FP16 存；② TurboQuant 先做随机旋转，把数值分布规整，再把直角坐标 (x,y) 转成极坐标 (角度, 模长)；③ 角度用单个全局码本量化、模长低位宽存储，Key 上再加 1 位 Johnson-Lindenstrauss 校正层抵消误差放大；④ 注意力计算时反量化回近似值参与 softmax(QKᵀ)V。整个过程无需校准数据、无需按模型单独配置。

**第三层：公式与核心机制**——核心是降低每个缓存条目的比特数 b，使显存 ∝ n·b。极坐标变换的关键收益是"角度分布可预测→全局码本通用"，绕开了旧方法卡在约 2.6 倍就掉点的元数据和缩放因子开销。TurboQuant 在 H100 注意力核上可达约 8 倍加速（针对 logit 计算环节）。

**▌ 动手验证**
HuggingFace 文本生成已支持 KV 量化开关，可用如下方式启用（需安装对应优化内核）：
```python
from transformers import AutoModelForCausalLM, AutoTokenizer

tok = AutoTokenizer.from_pretrained("meta-llama/Llama-3.2-3B")
model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Llama-3.2-3B",
    torch_dtype="auto",
    # 开启 KV 量化(示意, 具体参数依版本)
    quantization_config={"kv_cache": {"bits": 4, "method": "polar"}},
)
txt = tok("长上下文摘要：", return_tensors="pt")
out = model.generate(**txt, max_new_tokens=64)
print(tok.decode(out[0]))   # 预期输出连贯摘要
```
注意：并非所有版本都原生支持，需确认 transformers 与对应 Triton/MLX 内核版本；量化位宽过低时超长上下文可能掉点。

**▌ 对比与选型**
| 对比维度 | TurboQuant量化 | 无损不量化 | TriAttention驱逐 |
|---------|--------------|----------|---------------|
| 核心思想 | 极坐标低位存储 | 全精度缓存 | 丢弃弱Key |
| 适用场景 | 长上下文推理 | 短上下文 | 超长上下文 |
| 性能表现 | 6倍压缩零损 | 显存最大 | 10.7倍省显存 |
| 学习成本 | 中 | 低 | 中 |
| 生态成熟度 | 社区实现中 | 原生 | 较新 |

### 3. 【RLHF人类反馈对齐：用偏好排序把模型调教成听话助手】

> 📍 **导语**：预训练让模型"读了全世界书"，但它未必"说人话"、未必符合你的偏好。2026 年上线的 GPT-5、Claude Opus 4、DeepSeek-V4 等前沿模型，背后都跑着一条"预训练→监督微调→偏好对齐"的流水线。而把模型从"能说"变成"说得让人满意"的关键一环，就是 RLHF（基于人类反馈的强化学习）。理解它，你就懂了为什么今天的 AI 既聪明又有分寸。

---

**🧠 深度解析**

**▌ 它是什么？**
RLHF 是用"人类偏好"作为奖励信号来微调模型的方法。简单说：先收集一批"同一个问题，两个回答，人标哪个更好"的数据，训一个奖励模型（Reward Model）学着给人喜好打分；再用强化学习（通常是 PPO）让模型生成回答、根据奖励模型的分数调整参数，逐步偏向高偏好输出。一个误区是以为 RLHF 在"教知识"——它不传授新事实，只调整"表达方式与价值取向"。边界上，它擅长让回答更安全、更有用、更礼貌，但奖励模型本身的偏见会被放大，且依赖大量高质量标注。

**▌ 它解决了什么问题？**
**Before → After 对比**：只有预训练+指令微调（SFT）时，模型常答非所问、语气生硬甚至冒犯。据京东云 2026 年通识文章，RLHF 让模型输出"符合人类偏好"——比如更礼貌、更精准。今日头条 2026 年技术拆解指出，2026 年新趋势是 RLHF 正被 RLVR（可验证奖励强化学习）部分替代：用自动化校验（如数学答案是否对）代替人工标注，成本暴跌、效果暴涨，在数学/代码/科学计算上精度直接拉满。南方科技大学等 2026-04 的 SPPO 研究（arXiv:2604.08865）也显示，推理训练里传统 PPO 的"打分员"存在尾部效应，单次采样新范式可把训练提速约 5.9 倍。

**▌ 核心原理三阶拆解**
**第一层：直觉理解**——把训练模型想成调教一个实习生：你不用逐字教他写每句话，只需在他交稿后圈出"这段好、那段差"，他慢慢就摸准你的口味。RLHF 就是把这种"好/差"反馈系统化、规模化。

**第二层：技术流程拆解**——① 收集同一 prompt 的多个回答，由人排序（A>B>C）；② 训奖励模型，输入回答、输出标量分数，使其排序与人工一致；③ 用 PPO：模型生成回答 → 奖励模型打分 → 用打分做优势估计更新策略，同时加 KL 约束防止跑太偏；④ 迭代多轮，得到对齐后的模型。现代流水线还叠加 DPO、GRPO、SimPO 等更轻量的偏好优化。

**第三层：公式与核心机制**——PPO 的优化目标是最大化 E[奖励] 减去 β·KL(新策略‖旧策略)，β 控制"别偏离原模型太远"。奖励模型则用 Bradley-Terry 模型把"人偏好 A 而非 B"的概率写成 sigmoid 形式训练。RLVR 的精髓是用"答案是否可验证正确"作奖励，省掉人工偏好标注这一最贵步骤。

**▌ 动手验证**
用 TRL 库可跑通最小化 RLHF/DPO 流程（DPO 更省算力，无需单独奖励模型）：
```python
from trl import DPOConfig, DPOTrainer
from transformers import AutoModelForCausalLM, AutoTokenizer

model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen3-0.6B")
ref = AutoModelForCausalLM.from_pretrained("Qwen/Qwen3-0.6B")
tok = AutoTokenizer.from_pretrained("Qwen/Qwen3-0.6B")

# preference_data: [{"prompt":..,"chosen":..,"rejected":..}, ...]
trainer = DPOTrainer(model, ref, args=DPOConfig(output_dir="./dpo"),
                     train_dataset=preference_data, tokenizer=tok)
trainer.train()   # 预期 loss 下降, 模型更偏好 chosen 风格
```
注意：DPO 数据必须是成对的"优选/劣选"，且偏好差距要明显，否则训练不稳。

**▌ 对比与选型**
| 对比维度 | RLHF(PPO) | DPO | RLVR |
|---------|----------|-----|------|
| 核心思想 | 奖励模型+RL | 直接偏好损失 | 可验证奖励 |
| 适用场景 | 通用对齐 | 轻量对齐 | 数学/代码 |
| 性能表现 | 效果好成本高 | 稳且省 | 推理暴涨 |
| 学习成本 | 高 | 中 | 中 |
| 生态成熟度 | 成熟 | 成熟 | 上升中 |

### 4. 【扩散解码Mercury：用扩散模型替代逐字生成把推理提速十倍】

> 📍 **导语**：2026 年你用过的几乎每个大模型，都在"一个字一个字"地生成——第 50 个 token 必须等第 49 个。这种自回归（Autoregressive）范式给速度钉了一个天花板，再多硬件也破不了。Inception Labs 的 Mercury 用扩散语言模型（Diffusion LM）把整套思路翻过来：像图像去噪一样，并行把一段随机噪声"雕琢"成通顺文本，在 Blackwell 上跑到 1009 token/秒，约 10 倍于主流自回归模型。这是解码范式的潜在分水岭。

---

**🧠 深度解析**

**▌ 它是什么？**
扩散解码，是用"从噪声逐步去噪"替代"逐词预测"的文本生成方法。它借鉴了 Stable Diffusion 的图像生成思路：先采一段随机噪声作为初始草稿，再用模型在多步（通常 8–16 步）里去不断细化、纠正，最终输出完整连贯的句子。一个误区是以为"并行生成=胡写"；实际上扩散模型每一步都在审视全局、统一修正，天然支持"中间补写"和内置纠错。边界上，它更适合对连贯性要求适中、对速度极敏感的场景；在最难基准上质量仍略逊于顶级自回归模型，但差距在快速缩小。

**▌ 它解决了什么问题？**
**Before → After 对比**：自回归模型在 H100 上最快约 150–200 token/秒，因为每个 token 都依赖前一个，硬件并行度被锁死。Mercury 用扩散一次性生成整段，danilchenko 2026 测评显示 Mercury 2 在 Blackwell 上达 1009 token/秒、端到端延迟约 1.7 秒，约为 Claude 4.5 Haiku、GPT-5 Mini 的 10 倍，且在 AIME 2025 拿到 91.1 分，进入"具备推理能力"梯队。能力上，扩散还天生支持"文本中间填充（infilling）"和逐步纠错——这是从左到右模型做不到的。

**▌ 核心原理三阶拆解**
**第一层：直觉理解**——自回归像书法家一笔一画写对联，写错一笔后面全歪；扩散像雕塑家面对一块石头，整体反复打磨，哪不满意修哪，最后整体成形。前者顺序不可破，后者可并行、可回改。

**第二层：技术流程拆解**——① 随机初始化一段含全部位置的噪声序列；② 模型读取当前序列，预测"每处应是什么 token"的去噪方向；③ 按步长更新所有位置，逐步降低噪声；④ 重复 8–16 步直到收敛为可读文本；⑤ 输出完整序列。由于所有位置同步更新，吞吐由"步数"决定而非"长度"，突破了自回归的串行墙。

**第三层：公式与核心机制**——扩散语言模型训练时学习逆转一个逐步加噪过程：给定干净文本 x₀，按调度加噪得 x_t，模型预测噪声 εθ(x_t,t)；推理时从 x_T~N(0,I) 出发，反复 x_{t-1}=去噪一步，直到 x₀。关键是"算术强度高"——GPU 张量核心持续满载，不用干等内存读取，这正是它快的本质。

**▌ 动手验证**
扩散 LM 尚不如自回归生态成熟，可用 Inception 提供的推理接口体验（示意）：
```python
from inception import MercuryLM

model = MercuryLM.from_pretrained("inception/mercury-2")
# 并行去噪生成整段, 而非逐字
text = model.generate("用一句话解释扩散模型：", steps=12)
```

### 5. 【长上下文片段级执行：训练推理一致的ICML2026可扩展方案】

> 📍 **导语**：让模型读完整本书、答出书中细节，是 2026 年最卷的能力之一。但有个隐蔽坑：很多"长上下文"方法只在推理时限制注意力窗口，训练时却仍用全上下文——模型在训练时被惯出"随时能看全文"的习惯，一到推理被关进片段就水土不服，稳定性和泛化双双下跌。ICML 2026 的一篇工作提出"训练-推理一致的片段级执行"，从根上消除这道语义鸿沟，是做超长文档系统的必读思路。

---

**🧠 深度解析**

**▌ 它是什么？**
片段级执行（Segment-level Execution）是把超长序列切成固定大小片段、逐段处理，且只在相邻片段间传递一个固定大小的"携带 KV 尾部"的方法。它强调"训练时就要用和推理完全相同的受限前向语义"，而不是训练全看、推理半看。一个误区是以为"上下文越长=塞更多 token 就行"；其实若训练/推理执行语义不一致，模型会过度依赖训练时可见、推理时不可见的信息。它的边界：适合超长文档、流式输入；片段内仍是完整因果注意力，跨片段信息通过受限接口流动。

**▌ 它解决了什么问题？**
**Before → After 对比**：传统做法推理用窗口注意力或片段执行，训练却保留全上下文注意力，造成"执行语义鸿沟"——模型对训练可用、推理不可用的信息产生依赖，长上下文下稳定性变差。据转专 AI 对 ICML 2026 论文的梳理，该工作让模型从训练起就以受限片段式前向学习，推理时不再"不适应"。在成本侧，danilchenko 2026 测算：上下文从 32K 拉到 96K，每层成本约涨 9 倍；片段级执行把跨片段信息流约束在固定通道（如 128 token 的携带 KV 尾部），显存随长度近似线性而非平方增长。

**▌ 核心原理三阶拆解**
**第一层：直觉理解**——把读长书想成接力：每章读完后，只把"最关键的几句话"传给下一章，而不是把整章搬过去。这样既记住了要点，又不至于背包越背越重。片段级执行就是给每章规定"只能带走固定大小的笔记"。

**第二层：技术流程拆解**——① 输入切分为固定大小 segment；② 处理当前段时，仅对段内 token 做因果自注意力；③ 段处理完，保留其 KV 缓存的一个固定尾部 C（如 128 token），作为唯一可微分跨段接口传给下一段；④ 下一段注意力可访问该尾部获取前文线索；⑤ 训练时引入截断反向传播（TBPTT），梯度只沿最近 K 次携带尾部回传，与推理约束完全一致。

**第三层：公式与核心机制**——核心是"状态转换语义一致"：携带尾部 C_{i-1} 在训练与推理中以完全相同方式参与第 i 段前向，且是唯一带梯度的跨段状态。TBPTT 把梯度链限制为最近 K 步，使训练时的信息流范围与推理时对齐，从根本上消除"训练看见、推理看不见"的依赖，从而提升长上下文稳定性。

**▌ 动手验证**
在支持长上下文分块的推理框架中，可用如下思路开启片段执行（示意）：
```python
import torch

# 伪代码: 逐段处理并传递固定大小 KV 尾部
carry_kv = None
for seg in split_long_text(text, seg_size=2048):
    out, carry_kv = model.segment_forward(
        seg, carried_kv=carry_kv, carry_len=128  # 仅携带128 token尾部
    )
    print(out.shape)   # 每段输出, 显存不随总长平方增长
```
注意：真实实现需模型原生支持 segment API；carry_len 过小会丢远程信息，过大则失去省显存意义，需按任务调参。

**▌ 对比与选型**
| 对比维度 | 片段级执行 | 全上下文注意力 | 窗口注意力 |
|---------|----------|-------------|-----------|
| 核心思想 | 受限跨段接口 | 全序列关联 | 固定滑动窗 |
| 适用场景 | 超长流式 | 中等长度 | 中长文本 |
| 性能表现 | 近线性显存 | O(n²)显存 | 中 |
| 学习成本 | 中 | 低 | 低 |
| 生态成熟度 | 研究前沿 | 成熟 | 成熟 |

### 6. 【测试时训练In-Place TTT：把MLP改造成推理期可更新动态记忆】

> 📍 **导语**：传统大模型是"先训练、后部署"的静态体：上线后权重冻结，面对源源不断的流式新任务只能靠提示词硬撑。2026 年字节跳动 Seed 与北京大学提出 In-Place TTT（就地测试时训练），思路很巧——不破坏预训练主干，而是把现成的 MLP 层"就地"改造成推理期可更新的"快速权重"，让静态模型获得动态记忆与演化能力。这对超长上下文、个性化定制场景，是一条"以小博大"的新路。

---

**🧠 深度解析**

**▌ 它是什么？**
In-Place TTT 是一种测试时训练范式：在模型推理阶段，把 Transformer 里已有的 MLP 投影矩阵"复用"为可随输入更新的快速权重（Fast Weights），配合专为语言建模设计的前向对齐目标，使模型在不重训、不破坏主干的前提下，对当前上下文动态适应。一个误区是以为它要"重新训练整个模型"——恰恰相反，它只唤醒现有层的潜力，权重更新局限于 MLP 内部。边界上，它擅长处理无限长上下文与高度定制化流式任务；但更新需前向对齐目标配合，工程实现比普通推理复杂。

**▌ 它解决了什么问题？**
**Before → After 对比**：静态范式下，模型权重固定，遇到持续流入的新信息只能靠上下文窗口"临时装"，窗口一满就遗忘。据腾讯云 2026 年对 In-Place TTT 的解读，该方法让现有大模型以"即插即用"方式获得动态推理演化能力，在超长上下文任务性能大幅提升。类比很形象：一座商用大楼靠"原位改造"把普通隔断升级为可重配智能空间，而不是一改需求就推倒承重墙重建——TTT 正是大模型的不推倒重建术。

**▌ 核心原理三阶拆解**
**第一层：直觉理解**——普通模型像一本印好就不再改的百科全书，新事只能写便签贴边上，便签满了就丢。TTT 像给这本书的某些页装上"可擦写膜"，读到新内容时就地更新这几页，既记住了新信息，又没重印整本书。

**第二层：技术流程拆解**——① 推理时输入流式到达，模型照常走注意力层；② 进入 MLP 层时，不再用固定权重，而是用当前上下文通过一个轻量更新规则调整投影矩阵，得到"快速权重"；③ 用更新后的权重完成本步计算，并借前向对齐目标保证更新方向利于后续语言建模；④ 状态随流持续演化，形成跨步动态记忆；⑤ 主干注意力与预训练权重保持冻结，训练成本几乎为零。

**第三层：公式与核心机制**——核心是把 MLP 权重 W 视为状态，按隐藏状态 h 做一步梯度式更新 W←W−η·∇ℒ_align(W;h)，其中 ℒ_align 是使快速权重与语言建模目标一致的前向对齐损失。关键设计是"原位"：复用既有矩阵而非新增庞大模块，因此参数量与推理开销增量极小，却换来随输入演化的记忆能力。

**▌ 动手验证**
概念上可用 PyTorch 模拟"快速权重"更新（示意）：
```python
import torch

W = torch.randn(16, 16, requires_grad=False)   # 原MLP权重(冻结)
h = torch.randn(16)                             # 当前隐藏状态
# 前向对齐: 用隐藏状态对W做一步就地更新
loss = (W @ h).pow(2).mean()                    # 示意对齐目标
g = torch.autograd.grad(loss, W, retain_graph=True)[0]
W_fast = W - 0.01 * g                           # 快速权重更新
print(W_fast.shape)                             # 预期 torch.Size([16, 16])
```
注意：真实 In-Place TTT 需模型原生支持快速权重与前向对齐目标；上式仅为机制示意，不可直接替换生产推理。

| 适用场景 | 超长/流式定制 | 通用固定 | 新领域 |
