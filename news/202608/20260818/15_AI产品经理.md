### 1. 【模型分层与路由：用"高频执行、复杂推理、专业多模态、确定性工具"四层取代"一个最强模型"】

> 📍 **导语**：2026 年 7 月 31 日 DeepSeek 更新 V4-Flash-0731、随后 GPT-5.6 发布，两件事把同一个产品问题推到台前——**AI 产品经理最该学的不是"追哪个模型最强"，而是"做模型分层"**。DeepSeek 那篇文章的判断很直接：企业不再需要让一个最强模型处理所有任务，而是要建一套由高频执行模型、复杂推理模型、专业多模态模型和业务工具共同组成的分层体系；GPT-5.6 那篇则补了一刀：没有能力分层的产品，会把所有请求压成同一种成本结构，低价值任务被过度服务、高价值任务又缺少保障，最后既不好定价也不好解释价值。对 PM 来说，模型是否最强只是技术指标，模型能否稳定进入业务流程才是产品指标。

**▌ 它是什么**

模型分层（Model Layering / Tiered Routing）是把"一个模型入口"拆成按任务特性分流的多层架构，让正确的任务交给正确的模型。最常被引用的四层划分是：**第一层高频执行模型**，负责意图识别、参数收集、文档摘要、信息抽取、内容分类、JSON 结构化输出、普通工具调用，核心是响应速度、稳定性、并发与成本，DeepSeek V4-Flash 这类高性价比模型最适合放这一层；**第二层复杂推理模型**，处理多约束方案设计、高难度代码分析、复杂业务规则判断、长链路任务规划，以及第一层多次失败后的升级，调用频率低但对推理质量要求高；**第三层专业多模态模型**，处理图片识别、设计稿审核、视频音频理解、图像与 3D 生成；**第四层确定性工具与人工审核**，包括价格计算器、数据库、搜索引擎、订单系统、支付系统、风险规则引擎和人工客服，负责业务结果的准确性与可追溯。落到工程上，成熟做法是"智能分层路由"：用户请求先经语义缓存（命中直接返回，延迟 <30ms、成本近 0），未命中再经一个 7B 以下或 BERT 类的轻量分类器（耗时 <20ms）判断复杂度，路由到对应 Tier，超时或错误自动 Fallback 到下一层。

**▌ 它解决了什么问题**

第一，解决"全员高配"与"全员低配"两个极端：前者体验好但成本跑不通，后者压住价格却交付不住关键任务。第二，解决产品无法定价——没有任务路由规则，你就说不清每个功能到底消耗多少智能资源。第三，解决能力错配：把会议纪要整理成三点结论也上最强模型是在浪费钱，用半年销售数据生成管理层复盘却用便宜模型是在透支信任。第四，解决护城河误判——当强模型越来越容易获得，真正稀缺的能力变成系统设计、成本治理、质量兜底和链路控制，而非"接了最新模型"。第五，解决风险敞口——高风险、不可逆、直接影响用户决策的任务必须保留强模型兜底甚至人工审核，低风险高频任务则可以激进压成本。第六，解决路由决策本身成为新瓶颈——分类器必须极致轻量（<20ms），否则省下的 Token 又赔给延迟。第七，解决"默认最强模型"的路径依赖，让 PM 把"这个任务需要多强的智能才刚刚好"变成可设计的参数。第八，解决跨场景成本不可观测，把单请求成本、月度预算、缓存命中率、Token 效率放进同一张账本。

**▌ 原理拆解**

原理一：小模型真正的价值不是"便宜一点"，而是让 AI 能力可以被分层部署，像分工明确的组织。原理二：路由不是拍脑袋，而是有数据支撑——IPR 这类智能提示路由框架预测不同模型面对不同请求的质量表现，在接近强模型质量前提下成本可降低 43.9%、路由延迟控制在 150ms 内；BOute 把模型选择与 GPU 资源配置一起优化，相同性能目标下服务成本降 15%–61%、平均降 38%。原理三：便宜模型不能替产品承担所有质量风险，Qwen2.5-3B 这类小模型做前门路由时独立判断准确率仍有缺口，所以必须配强模型兜底。原理四：置信度驱动升级——分类器输出置信度 <0.85 时自动升到更高 Tier，平衡成本与准确性。原理五：路由规则应由 PM 定义，按"用户对智商敏不敏感、哪些场景容忍不了愚蠢"切分场景，像切蛋糕一样清楚。原理六：数据分级优先于模型选择——先按合规要求约束模型清单，再在清单内选，便利不能覆盖合规。原理七：单模型用户一年可能多付 5–10 倍且结果更差，多模型按任务路由（快任务用 Flash/Haiku、难任务用 Opus/旗舰）才是 2026 的默认打法。原理八：先优化提示词再升级模型，路由自动化的前提是分类器稳定，否则人工每请求选模型反而更慢。

### 2. 【RAG 知识库产品化：把检索质量当成产品指标，用分块、重排与知识隔离治理幻觉源】

> 📍 **导语**：2026 年一批 Agent 评估框架文章反复指向同一个被低估的变量——**grounding quality（ grounding 质量）**。agent-context.org 那篇企业级评测框架排名说得很直白：大多数评测框架给生成步骤打分、却把检索当黑盒，于是"答案质量"高分可能掩盖一个正在喂模型过时或无关片段的检索层；**最贵的评测失败往往是检索失败，你让 Agent 锚定在什么上面，和你怎么给它打分同样重要**。换句话说，RAG 不是接一个向量库就完事的功能，而是一个需要被当成产品来设计、被当成指标来衡量的"知识产品面"。对 AI PM 来说，检索质量就是产品质量的一部分，而不是算法团队的私事。

**▌ 它是什么**

RAG 知识库产品化，是把"检索＋知识库"从技术组件提升为有明确质量契约的产品能力。它至少包含四件产品该管的事：**分块策略**（chunk around 有意义的段落而非固定字数，带元数据）、**重排**（rerank 后再取最相关 3–5 段进上下文，而非 Top20 全塞）、**知识隔离**（按业务线做物理分库，防止跨业务召回污染）、**新鲜度与刷新机制**（定义每个知识源的时效与刷新周期）。devtoollab 那份 2026 开发者指南把它纳入"上下文工程"的 Select 与 Compress 两步：Select 是只拉当前查询最相关的 3–5 块，Compress 是对冗长工具输出和检索结果做轻量提取后再入上下文。它还给出一条硬规则——当上下文窗口达到 70%–80% 容量就触发压缩（摘要历史、丢弃低相关块、压缩工具输出），否则会在推理中途撞顶导致退化。

**▌ 它解决了什么问题**

第一，解决"幻觉来自缺事实"——如果正确答案根本不在上下文里，那是检索或知识设计问题，不是模型问题。第二，解决"检索到了但模型不听话"——无关信息过多会主动拉低输出质量，dump 一切进窗口是用噪声稀释信号。第三，解决"lost in the middle"——相关事实若落在长上下文中部，准确率可下降 30% 以上，硬约束必须放在系统提示前 200 token，当前用户消息放末尾。第四，解决跨业务知识污染：一个零售问答召回了金融条例，比没召回更危险。第五，解决"评测全绿但答案全红"——LangSmith 会忠实告诉你 Agent 对过时上下文很"忠实"，绿分背后是红答案，只有检索可观测才能诊断。第六，解决长上下文误解：100万 Token 不等于把资料全塞进去，上下文越长成本越高、无关信息越多。第七，解决知识时效失控：产品规则变了，知识库没更新，场景会从"可用"掉回"胡说"。第八，解决 RAG 与生成的责任纠缠——把检索质量单独量化，才能定位"是检索错了还是模型推理错了"。

**▌ 原理拆解**

原理一：检索看精度（precision）而非只看召回（recall），三个高度相关段落通常胜过二十个松散相关。原理二：重排是性价比最高的单点优化，把 Top10/20 压到 Top3 常能"少即是多"，woshipm 成本文也用 Rerank 取 Top3 印证。原理三：上下文窗口是"工作台"不是"仓库"，放当前任务需要的工具，其余存索引；更大窗口不自动等于更好产品。原理四：知识按业务线物理隔离从源头防污染，比事后过滤更稳。原理五：新鲜度与衰减——昨天的需求比六个月前的重要，当前会话行为比终身平均重要，需时间戳与刷新机制。原理六：压缩不是"总结对话"那么简单，是有纪律的有损压缩，刻意丢掉该丢的、保留决策所需。原理七：工具输出是上下文失控最常见来源，每次工具返回都应先做轻量提取再回上下文。原理八：检索失败是最贵的失败，因为它 silent 地喂错料，评测分数却可能正常，必须用可观测的检索层＋新鲜内容才能诊断。

**▌ 动手验证**

**第一步（知识分库清单）**：按业务线列出知识域，标注是否物理隔离、共享白名单、更新负责人与刷新周期（如政策类日更、产品文档周更）。

**第二步（分块与重排规范）**：

| 项目 | 规范 |
| --- | --- |
| 分块单位 | 有意义段落／章节，非固定字数 |
| 元数据 | 来源、日期、业务线、版本 |
| 召回 | 向量＋BM25 混合 |
| 重排 | rerank 后取 Top3–5 进上下文 |
| 时效 | 标注新鲜度，过期自动降权 |

**第三步（检索质量评测集）**：从生产日志抽 ≥100 条真实问题（含长尾/边界），每条标"应召回的正确文档 ID"，指标 = 命中率（是否召回正确答案）＋噪声率（无关块占比），红线圈定 <90% 命中。

**第四步（跨业务召回巡检）**：每周跑一次"干扰测试"——在 A 业务问题里混入 B 业务文档，验证是否被错误召回，命中即冻结该知识域交叉权限。

**第五步（Grounding 评测）**：抽 100 条已回答样本，人工标"结论是否都能在引用文档中找到"，grounding 失败率红线 5%，连续两周超标触发检索层重构。

**▌ 对比选型**

| 维度 | 长上下文直塞（无 RAG） | RAG 作为功能（接向量库） | RAG 产品化（分块＋重排＋隔离＋评测） |
| --- | --- | --- | --- |
| 事实准确性 | 低（易编） | 中 | 高（可锚定） |
| 跨业务污染风险 | 高 | 中 | 低（物理隔离） |
| 成本 | 极高（全量 Token） | 中 | 低（精准召回） |
| 可诊断性 | 弱 | 弱（黑盒） | 强（检索可观测） |
| 时效管理 | 无 | 弱 | 强（刷新机制） |
| 最大风险 | 幻觉失控 | 检索黑盒致绿分红 | 评测集覆盖不足 |

### 3. 【AI Agent 评估体系：基础能力、任务执行、业务效果三层指标加归因闭环】

> 📍 **导语**：skillgen 那篇 2026 Agent 评测框架开宗明义：**评估要解决的是"真正重要的东西"，而不是漂亮的 benchmark 分数**。它举了一个让很多团队心惊的事实——大多数团队对自己"能跑的"Agent 做周一时才发现，在真实任务上成功率不到 60%。hellobit 那篇面向 AI PM 的文章更狠：Agent 评估最核心的不是"打高分"，而是"知道错在哪、为什么错、下一步优化什么"。对 AI PM 来说，Agent 评估体系不是上线后的装饰，而是和护栏并列的质量地基——LLM 是概率性的，同样输入每次输出都不同，靠"感觉能用"上线，只会在生产环境用客诉换来静默回归（silent regression）。

**▌ 它是什么**

AI Agent 评估体系是把"Agent 到底行不行"从主观感受变成可量化、可归因、可回归的系统。它通常分三层看：**第一层基础能力指标**，看 Agent 本身答得对不对稳不稳——准确性（有无幻觉）、完整性（关键点是否覆盖）、相关性（是否跑偏）、稳定性（同类问题多次测试是否一致）；**第二层任务执行指标**，Agent 不只是"会说"还要"能做成"——工具调用准确率、参数提取准确率、任务总体完成率、流程成功率、异常恢复率（工具失败/参数不足/知识缺失时能否正确兜底）；**第三层业务效果指标**，PM 最该盯的不是模型分而是业务价值——是否提升处理效率、降低人工成本、缩短业务闭环时间、降低风险差错率、提升满意度与转化率。**最关键的是归因闭环**：评估不仅要告诉你"做得好不好"，还要告诉你错在哪类环节（意图识别错／检索漏召／工具调用错／多轮上下文丢失／应转人工未转），否则优化只能盲改。

**▌ 它解决了什么问题**

第一，解决概率性带来的不可复现——非确定性产品不能靠"试两个例子感觉更好"调试。第二，解决静默回归——改了提示词或模型，只有某一类输入变差，上线后才从客诉发现。第三，解决"分数高但没价值"——Agent 内容分高、工具顺，却没产生业务价值，仍不算成功。第四，解决优化无抓手——只知道"这里效果不好"却不知根因，最后变成碰运气式乱改。第五，解决长链路错误被平均掩盖——Agent 多步执行，任一步错都会累积或恢复，单一准确率看不出。第六，解决评测与生产脱节——公开 benchmark（GAIA/WebArena/AgentBench）用真实环境，但静态不模拟工具间歇失败与模糊指令，必须跑内部生产派生评测。第七，解决成本黑盒——成本突增往往是 Agent 在挣扎，成本本身就是质量信号。第八，解决人机分工模糊——95% 自动评测＋5% 人工评审（边界/失败/高成本/随机校准）才能兼顾规模与判断。

**▌ 原理拆解**

原理一：Agent 评估比 LLM 评估难一个量级，它测的是一串决策、工具调用、状态变化的序列，错误会复利也会自愈。原理二：从最小评测集开始——20 条真实失败样本就能让"变好/变坏"可见，不必等完美平台。原理三：评估栈分阶段——第 1 周记任务完成日志摸清基线，2–3 周捕获每一步轨迹（调用了什么工具、传了什么参、遇到什么错），第 4 周做自动重放当回归测试，第 2 月加单任务成本追踪，第 3 月做安全红队。原理四：三个核心指标胜过一切——任务成功率、单任务成本、用户升级率（需人工接管比例），它们比任何 benchmark 都更说明生产就绪度。原理五：归因分类必须前置——意图识别/检索召回/工具调用/参数提取/多轮上下文/安全边界/应转人工未转，每一类对应不同优化动作。原理六：轨迹（trajectory）是最值钱的调试资产，多智能体还要分层轨迹定位哪个 Agent 失败。原理七：LLM-as-judge 方便但有方差，必须写清 rubric 并尽量用人工标注校准。原理八：评测是回归测试不是一次性——每次改提示词/模型/工具都跑同一数据集对比分数，像测试代码一样资产化。

**▌ 动手验证**

**第一步（20 条最小评测集）**：从真实日志与客诉收 10–20 个"跑错"的输入，覆盖正常/缺失/口语化/矛盾/越界/工具失败/高风险，每条标预期结果与判定口径。

**第二步（三层指标卡）**：

| 层 | 指标 | 口径 | 当前 | 目标 |
| --- | --- | --- | --- | --- |
| 基础能力 | 准确性/稳定性 | 无幻觉且多次一致 | — | ≥95% |
| 任务执行 | 任务完成率 | 走通到最终结果比例 | — | ≥90% |
| 业务效果 | 人工兜底率 | 转人工/总会话 | — | ≤15% |

**第三步（归因分类表）**：每条失败标到 8 类根因之一，周会只讲 Top3 根因及对应动作（如"检索漏召→修重排"）。

**第四步（回归流水线）**：把评测集接入 CI，每次提示词/模型变更自动跑全量并出 diff，平均分涨但某 8 例跌即阻断合并。

**第五步（评分 rubric）**：LLM-as-judge 写明评分维度与权重，关键用例用人工标注校准，避免评判模型自身方差误导。

**▌ 对比选型**

| 维度 | 公开 benchmark（GAIA/WebArena） | 内部生产派生评测 | 在线监控 |
| --- | --- | --- | --- |
| 反映真实环境 | 中（静态） | 强（真实流量） | 最强（实时） |
| 发现静默回归 | 弱 | 强（回归测试） | 强 |
| 成本/可落地 | 低（直接跑） | 中（需建集） | 中（需埋点） |
| 归因能力 | 弱 | 强 | 中 |
| 适用阶段 | 选型参考 | 每次变更门禁 | 上线后常态 |
| 最大风险 | 静态不模拟故障 | 评测集覆盖不足 | 指标通胀 |

### 4. 【AX（智能体体验）设计：当 Agent 成为产品的新用户，PM 如何重画授权与责任边界】

> 📍 **导语**：2026 年 8 月 6 日 Cloudflare 发布了一款反常的浏览器 Kitesurf——它从一开始就不是为人设计的，Agent 在乎的是 Token 数量、上下文窗口、性能和成本，而不是标签页与像素渲染。人人都是产品经理那篇以此为信号点破了一个趋势：**产品的直接使用者，开始不再只有人**。Agent 会读取信息、改变订单状态、甚至触发支付和提交，它已经成为产品的一类新用户。但危险结论也随之而来：既然 Agent 能操作，是否也该替人决定？文章的态度很明确——至少现阶段不愿意，担心的是它替人做不可逆决定、后果却由人承担。这正是 AX（Agent Experience）要回答的：产品怎样被 Agent 理解、调用和操作，人又怎样授权、确认、监督并在出问题时重新接管。

**▌ 它是什么**

AX（Agent Experience，智能体体验）是当 Agent 成为产品的"用户"时，PM 必须补上的新设计维度。它和 UX 的关系不是替代而是扩展：UX 解决"人怎样使用产品"，AX 同时解决两件事——**产品怎样被 Agent 理解、调用和操作**，以及**人怎样授权、确认、监督并在出问题时重新接管**。落到实践有两个关键动作：一是 **agent-first 构建顺序**——先建 MCP 工具/技能（干净接口、结构化输入输出、不假设人在环），再把人类 UI 当成薄薄一层盖上去，Monte Carlo 就是这么做的，结果架构更 disciplined；二是 **信任栈（trust stack）**——legible reasoning paths（解释决策路径）、bounded agency（明确边界、不静默升级自主权）、goal transparency（让用户知道 Agent 优化什么）、contestability and override（无摩擦退出）、governance by design（日志与审计内建）。再配合 **自主等级 L1–L5**：L1 建议人执行、L2 沙箱执行待人批准、L3 自主运行但事后回顾、L4 约束内自治仅异常通知、L5 全委托——多数企业产品要同时支持多档（常规任务 L4、金融交易 L2、新情况 L1）。

**▌ 它解决了什么问题**

第一，解决"Agent 自己找上门"——Monte Carlo  telemetry 显示 25 个客户账号、130 个用户已通过 Claude Code/Cursor 连进来，没有文档没有推广，PM 不设计 AX 就被绕过。第二，解决信任不是"感觉"而是"权限系统"——Agent 不信任你的品牌，它信任你的护栏（清晰权限、完全可审计、伦理内建）。第三，解决扩展方式不同——人本 UX 线性扩展，AX 要通过干净 API、协商协议、编排实现指数扩展。第四，解决对齐风险——只优化速度效率的 Agent 会无视上下文，PM 要把"编码意图"变成反馈环。第五，解决责任错位——能力越强，操作权、决定权、责任三者边界越要重画，不可逆动作必须留在人侧。第六，解决"无界面≠无设计"——看不见的界面设计的是契约、边界、升级路径、审计轨迹。第七，解决委托 UX 缺失——人需要理解 Agent 在做什么、批准高风险动作、必要时干预。第八，解决价值发现——剥掉仪表盘问"Agent 到底需要从我这不什么"，常能痛苦地看清产品真实价值。

**▌ 原理拆解**

原理一：agent-first 不是杀死仪表盘，而是改变构建顺序，顺序比想象中更重要。原理二：为 Agent 建的能力天生有干净接口与结构化 IO，之后包 UI 是站在实心基础上；反过来先建屏再补 API 往往要推倒重来。原理三：信任 = 护栏不是品牌，可审计是自治与信任之间缺失的桥。原理四：bounded agency——清晰限制、绝不静默升级自主权，是信任栈核心。原理五：目标透明与可争议/可接管，是人愿意放手的前提。原理六：治理内建（日志审计）从第一天就做，不是事后 bolt-on。原理七： graduat 自治——同一产品对不同任务支持不同自主等级，金融交易 L2、常规 L4、新情况 L1。原理八：六模式贯穿全程——事前 Intent Preview（行动前秀计划）与 Autonomy Dial（用户设独立度）、事中 Explainable Rationale 与 Confidence Signal、事后 Action Audit & Undo 与 Escalation Pathway。

**▌ 动手验证**

**第一步（AX 就绪清单）**：

| 检查项 | 是否 | 说明 |
| --- | --- | --- |
| 结构化 MCP/工具接口 | □ | 干净输入输出，无人在环假设 |
| 权限模型（能/不能） | □ | 明确 off-limits |
| 审计轨迹 | □ | 谁调了什么、结果、可回滚 |
| 降级/停机开关 | □ | 异常可停 |
| 人类接管路径 | □ | 一键夺回 |

**第二步（自主等级映射）**：把每个 Agent 动作映射到 L1–L5，例如"搜索比价 L4／填写表单 L3／支付提交 L1（人批准）／改订单状态 L2"。

**第三步（委托 UX 六模式落地）**：事前加 Intent Preview＋Autonomy Dial，事中加 Explainable Rationale＋Confidence Signal，事后加 Action Audit&Undo＋Escalation Pathway，缺一项不许上线自主能力。

**第四步（信任栈落地）**：写清五层——决策路径可解释、自主权有界不静默升级、目标透明、可争议可接管、治理内建日志。

**第五步（演练）**：注入"Agent 欲执行不可逆支付"，验证是否触发 L1 人批准、是否留审计、是否可被一键接管。

### 5. 【人机信任与自主权设计：用"好奇窗口"与自我决定理论破解 AI 产品的"被替代感"】

> 📍 **导语**：WAIC 2026 现场，一篇讲"好奇模式"开关的文章点破了一个被效率叙事掩盖的代价：智能体手机追求把"想知道答案"的间隔压缩到趋近零，0.8 秒出结果，用户还没进入"想知道"的状态就已经"知道了"——**这不是效率提升，而是好奇窗口被关闭**。另一边，一项全球 AI 普及调研显示 81% 的人认可 AI 价值，却有 85% 担心门槛高或自己用不好；某电商客服引入 AI 后设立"AI 训练师"岗，解决率从 65% 跃到 89%、团队满意度提升 28%。两条线索指向同一件事：AI 产品不能只优化"快"和"省"，更要设计人的**自主权与信任感**，否则用户要么被当成被监控者，要么把 AI 当替代威胁。对 PM 来说，这是 2026 最被低估的产品心理维度。

**▌ 它是什么**

人机信任与自主权设计，是把"人是否感到自己掌控、是否信任并愿意使用 AI"当成可设计的产物，而非体验的副产品。它有两个抓手：**一是"好奇窗口"与探索权**——神经科学发现多巴胺奖励峰值不在获得答案时，而在"预期即将获得、但还没获得"的那 150–300 毫秒窗口；把这段窗口压到零，用户失去的是探索过程与选择权。产品应区分场景：写代码时你要的是验收式完成（关窗合理），体验型/学习型场景则要有意保留"不知道"的空间，甚至给一个"好奇模式"开关。**二是自我决定理论（SDT）三需求**——自主感（autonomy）、胜任感（competence）、归属感（relatedness）。协和医院"智慧影像系统"不自动出诊断，而是给医生"决策树"式交互、最终判断权留给医生，信任度从 34% 升到 79%；制造业把产线 AI 拆成 200 多个可定制模块、工人自主组合工作流，态度从抗拒变依赖、效率提升 41%。核心观念：把 AI 建议从"必须执行"改为"参考选项"，人从被监控者变成系统优化者。

**▌ 它解决了什么问题**
