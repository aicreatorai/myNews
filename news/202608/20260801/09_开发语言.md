### 【Java 25 正式发布：分代 Shenandoah 转正与精简源文件落地】

#### 导语
Java 25（即 JDK 25）沿着 OpenJDK 每半年一次的特性发布节奏于 2026 年走入生产视野，整版共纳入 18 个 JEP。它延续了自 Java 21 以来的"实验转正"主线：把前几个版本中以预览或实验形态出现的底层能力，逐个固化成默认即可用的产品级特性。对一线开发者最实在的红利集中在三处——低延迟垃圾回收更易开启、对象头更省内存、写小工具或脚本时能少敲大量样板导入。本文以分代 Shenandoah 转正、紧凑对象头落地、模块导入声明三条主线，拆解这一版到底改了什么、为什么改，并给出可亲手运行的验证步骤，帮助你在升级前建立清晰的预期。

#### 它是什么
Java 25 是 OpenJDK 社区的最新功能版，由 JEP（JDK Enhancement Proposal）机制驱动其演进。本版代表性 JEP 包括：JEP 521 将分代 Shenandoah 垃圾回收从实验特性提升为产品特性；JEP 519 将紧凑对象头从实验特性转为正式能力；JEP 511 模块导入声明（import module M）正式定稿，允许一次性导入某模块导出的全部公共顶层类型；JEP 513 灵活构造器主体（Flexible Constructor Bodies）正式定稿，允许在构造器中先执行语句再显式调用 super；JEP 518 为 JFR 引入协作式采样以降低安全点偏置；JEP 520 为 JFR 增加方法计时与追踪事件；JEP 503 移除 32 位 x86（Linux）移植。这些改动大多不破坏既有源代码，却显著改善了运行时表现与开发体验。

#### 解决什么
它主要解决三类长期痛点。第一，延迟敏感型服务（如交易、风控、实时推荐）希望在不牺牲吞吐的前提下把 GC 停顿压到极低，分代 Shenandoah 让"频繁回收短命对象"成为默认友好行为，省去手写一堆实验开关。第二，堆内存占用与对象头膨胀长期困扰大规模部署，紧凑对象头把对象头从 96–128 位压到 64 位，直接提升部署密度与缓存局部性。第三，Java 入门与脚本化门槛偏高，初学者常被 public static void main(String[] args) 劝退，模块导入声明与精简构造器让小工具、算法原型更接近"写即所得"，也让教学演示与快速验证更顺手，降低语言的初始认知负担。

#### 原理拆解
分代 Shenandoah 的理论基石是"弱分代假说"：多数对象朝生夕死，而存活久的对象往往长期驻留。Shenandoah 原本对整个堆做并发标记与整理，虽停顿极短，但回收年轻对象时并不比回收老年对象更高效。分代模式把堆划为年轻代与老年代两个区域，回收精力集中投向年轻代，从而以更低开销回收大量短命对象，并保留极低暂停时间与无停顿整理的特性。紧凑对象头则重塑了 HotSpot 中对象头的内部布局：把 mark word 与类型指针（klass）压缩进 64 位，减少每个对象固定的内存税，进而降低整体堆占用并提升数据局部性。模块导入声明在编译期把整模块导出包的公共类型一次性纳入作用域，等价于自动展开若干 import 语句，但语义上更贴近"按模块聚合 API"的现代组织方式，减少样板且不易遗漏。

#### 动手验证
先安装 JDK 25（以 SDKMAN 为例，也可从 Adoptium 或 Oracle 官网下载）：
```bash
sdk install java 25.0.1-oracle
sdk use java 25.0.1-oracle
java -version   # 应显示 25
```
开启分代 Shenandoah 与紧凑对象头（注意 25 已不需要 UnlockExperimentalVMOptions）：
```bash
java -XX:+UseShenandoahGC -XX:ShenandoahGCMode=generational \
     -XX:+UseCompactObjectHeaders -jar myapp.jar
```
体验模块导入声明（JEP 511）的最小示例，把过去多行 import 收敛为按模块导入：
```java
import module java.base;
import module java.io;
public class Demo {
    public static void main(String[] args) throws IOException {
        Path p = Path.of("hello.txt");
        List<String> lines = List.of("hi", "java25");
        Files.write(p, lines);
        System.out.println(lines.size());
    }
}
```
随后用 `javac Demo.java && java Demo` 编译运行，观察文件生成与控制台输出，验证模块导入声明确实把 java.base、java.io 的公共类型一次性纳入了作用域。

#### 对比选型
若追求极致低延迟且堆很大，分代 Shenandoah 与 ZGC 都是候选；Shenandoah 优势在于并发整理且对堆大小不敏感，ZGC 则以亚毫秒停顿著称但实现更复杂。G1 仍是默认且最稳的通用选择，适合多数业务系统。非分代 Shenandoah 在超大堆且对象寿命分布均匀时仍有价值。版本策略上，Java 21 是长期支持版（LTS），Java 25 适合想提前吃新特性、且能接受非 LTS 半年节奏的团队；生产环境升级前建议在预发环境充分验证紧凑对象头与分代 GC 的兼容性，并确认第三方库没有依赖被移除的 32 位 x86 平台。

### 【Lua 5.5 正式发布：增量 GC 与紧凑数组重塑轻量脚本引擎】

#### 导语
Lua 5.5 是这门以"轻量、可嵌入"著称的脚本语言的最新主版本，由 PUC-Rio 与 Lua.org 维护，沿 MIT 许可发布。它在保持极小体积与极简语法的同时，针对内存与垃圾回收做了自 5.0 以来最务实的一轮底层重构：更紧凑的数组、增量式的大 GC 周期、以及显式全局变量声明等提升安全性的语法增强。对于把 Lua 用作游戏脚本、嵌入式配置或插件逻辑层的团队，这一版意味着更低的运行时开销与更可控的代码质量，也让这门老牌嵌入语言在资源受限场景里更具竞争力。

#### 它是什么
Lua 5.5 相对 5.4 的主要变更包括：引入显式全局变量声明；for 循环变量变为只读；浮点数以十进制打印且精度足以被原样读回；构造函数支持更多层级；新增 table.create；utf8.offset 额外返回字符的结束位置；支持外部字符串（使用 Lua 未管理的内存）；新增 C API luaL_openselectedlibs 与 luaL_makeseed；主要垃圾收集阶段改为增量完成；大型数组采用更紧凑的表示（内存约减少 60%）；解释器 lua.c 动态加载 readline；静态（固定）二进制改进；dump 与 undump 复用全部字符串；辅助缓冲区在构造最终字符串时复用内部缓冲。整体上，这是一次"底层数据结构和运行时管理"双线并进的系统性更新。

#### 解决什么
它解决三大现实问题。其一，大型表与数组的内存膨胀：紧凑数组让大表内存下降约 60%，对数据密集与嵌入式场景直接降本。其二，长运行程序的 GC 卡顿：把最耗时的标记阶段从"一口气完成"拆成可中断、可恢复的小步，把原本几百毫秒的停顿拆成若干毫秒级小停顿，对游戏、UI、实时音视频至关重要，能有效减少可感知的卡顿。其三，隐式全局变量导致的难以察觉的 bug：显式声明在解析期就能捕获拼写错误与意外的全局写入，提升大型项目的可维护性与代码规范程度，降低协作成本。

#### 原理拆解
增量式 GC 的核心是"把标记工作切片"。Lua 的回收原本在标记阶段会持续占有主线程，直到整堆标记完成才放行；5.5 改为执行一小段标记后主动挂起，让宿主程序继续推进几步，再回来补做一点标记，如此往复，从而保证任何单次停顿都很短，且整体吞吐基本不受影响。紧凑数组则重新审视了 table 内部数组部分的存储：当数组元素基本同构且规模大时，采用更紧凑的编码与更少的对齐填充，从而把"大数组用约 60% 更少内存"从口号变成实测结果。外部字符串通过 lua_pushexternalstring 把由 C 侧管理内存的文本"包装"成 Lua 字符串对象，Lua 自身不负责其生命周期，于是实现零拷贝数据传递，降低内存峰值与复制开销，特别适合游戏引擎纹理路径、网络报文等场景。

#### 动手验证
从源码安装 5.5（也可通过包管理器或 luaorg 发布的官方 tarball）：
```bash
curl -L https://www.lua.org/ftp/lua-5.5.tar.gz | tar zx
cd lua-5.5 && make linux-readline test   # macOS 用 make macosx
sudo make install
lua -v   # 应输出 Lua 5.5
```
体验只读 for 变量与浮点精确打印、utf8.offset 结束位置的示例：
```lua
local sum = 0
for i = 1, 5 do      -- i 在循环体内只读，重复赋值会报错
  sum = sum + i
end
print(sum)           -- 15

local s = "Hello 世界"
local start_idx, end_idx = utf8.offset(s, 7)  -- 第7个字符'世'的起止位置
print(string.sub(s, start_idx, end_idx))      -- 世
```
观察增量 GC 行为可用 `collectgarbage("step", n)` 主动驱动单步回收，或通过 `collectgarbage("count")` 在循环前后对比内存变化，直观感受增量回收对停顿的平滑作用。

#### 对比选型
与 LuaJIT 相比，官方 Lua 5.5 胜在语义新鲜、GC 现代、与上游同步，而 LuaJIT 在纯计算上常更快但停留在 5.1 语义。与 Python 嵌入相比，Lua 体积与启动开销更小，适合作为配置或逻辑层；但生态与库丰富度远不及 Python。与 JavaScript（通过 QuickJS 等）嵌入相比，Lua 的 C 互操作与极简表模型更轻。选型建议：资源受限、需嵌入、逻辑不复杂 → Lua 5.5；需要庞大生态或数值科学 → 另选其语。若既有项目跑在 LuaJIT 且对性能极度敏感，可暂缓迁移并评估 5.5 的 GC 改良是否覆盖你的痛点。

### 【Haskell GHC 9.14：线性类型与 SPECIALISE 表达式推进类型系统】

#### 导语
GHC 9.14 是 Glasgow Haskell Compiler 在 2026 年的重要功能版，由 GHC 团队发布并配套了详尽的 release notes。它在类型系统、线性类型、特化编译与错误信息等方面带来一连串打磨，既照顾学术严谨也照顾生产可用。对用 Haskell 写高保证系统的团队（金融、区块链、高可靠基础设施）而言，这一版降低了不少日常摩擦，同时把社区期待已久的能力往前推进了一步，让"编译期证明资源安全"这件事更贴近真实工程。

#### 它是什么
GHC 9.14.1 的显著语言变更包括：GHC 提案 493 允许在 SPECIALISE 编译指示里写表达式，并支持多特化合并声明（旧的多特化语法被弃用，将在 9.18 移除）；线性类型（LinearTypes）下记录字段可声明为非线性；coerce 的类型推断更聪明，对含 Coercible 约束的歧义类型更主动地求解；-Wincomplete-record-selectors 纳入 -Wall；OverloadedRecordUpdate 的 setField 参数顺序按提案 583 翻转；foreign import 接受多行字符串；ExplicitNamespaces 允许在导入导出列表里使用 data 命名空间说明符；-Wdata-kinds-tc 弃用，未开启 DataKinds 而提升数据类型到 kind 现在直接报错；MonadComprehensions 隐含 ParallelListComp；RequiredTypeArguments 允许在 GADT 构造器类型里写可见 forall。编译器层面还改进了堆溢出时的错误提示，并增强 SIMD（x86 NCG 的 SSE/AVX）。

#### 解决什么
它解决几类长期摩擦。其一，特化（SPECIALISE）过去只能按类型参数特化、且多特化语法笨拙，现在可按表达式特化并合并声明，让性能关键函数的专门化更精准、更省心。其二，线性类型自 9.0 引入后一直偏实验，记录字段只能线性，限制了它在混合数据里的可用性；现在字段可非线性，让"部分字段需要资源线性、部分不需要"的数据类型能自然表达。其三，不完整的记录选择器等警告纳入 -Wall，能在编译期揪出更易被忽视的潜在崩溃点；coerce 歧义推断改善则减少"明明能推出却报错"的沮丧，让 newtype 包装层的零成本抽象更顺滑。

#### 原理拆解
SPECIALISE 的本质是让编译器为特定类型（或现在的特定表达式）生成一份特化后的展开代码，从而避免字典传递与多态开销。允许表达式特化意味着不仅能特化 f @Int，还能特化 f @Int False 这样带值参数的形态，对结合 newtype 与具体运行时常量的场景尤其有用。线性类型用多重性（Multiplicity）kind 区分 'One 与 'Many：当记录字段标注 %'Many 时，该字段在构造器中的多重性为 Many，于是构造器类型变为 Rec :: Int %'Many -> Char %1 -> Record，既保留对 x 的常规多次使用，又对 y 维持一次性消费的资源约束。coerce 改善则来自类型检查器在遇见 Coercible 约束时，主动把"看似歧义"的类型变量视为由约束决定，从而省去人工标注，减少噪音错误。

#### 动手验证
用 ghcup 安装并切换（也可通过系统包管理器或 Haskell 工具栈）：
```bash
ghcup install ghc 9.14.1
ghcup set ghc 9.14.1
ghc --version   # 应输出 9.14.1
```
体验线性记录字段（需开启 LinearTypes 扩展）：
```haskell
{-# LANGUAGE LinearTypes #-}
data Record = Rec { x %'Many :: Int, y :: Char }
-- 构造器类型：Rec :: Int %'Many -> Char %1 -> Record
use :: Record %1 -> (Int, Char)
use (Rec a b) = (a, b)   -- a 可多次使用，b 必须恰好消费一次
```
体验 SPECIALISE 表达式（提案 493 的新语法）：
```haskell
{-# SPECIALISE f @Int False :: Int -> Char #-}
```
随后用 `ghc -O2 Demo.hs` 编译，可通过 -ddump-simpl 观察特化后的展开代码，确认表达式特化确实生效、相关多态字典被消除。

#### 对比选型
与 GHC 9.12（当前稳定维护线，仍有 9.12.x bugfix）相比，9.14 提供更现代的类型能力与线性类型改进，但生产系统若求稳可暂留 9.12。与早期 9.0–9.10 相比，9.14 在特化、警告与 SIMD 上明显进步。若项目大量依赖已被翻转的 OverloadedRecordUpdate 语义，升级需改动 setField 参数顺序。总体建议：新项目直接用 9.14；存量大型代码库先在 CI 跑全量测试再迁移，并关注 -Wall 新增的 -Wincomplete-record-selectors 是否把库编译成失败，必要时用 -Werror=no-incomplete-record-selectors 临时抑制。

### 【OCaml 5.4：不可变数组、原子记录字段与标记元组落地多核时代】

#### 导语
OCaml 5.4 是 INRIA 主导的工业级函数式语言的最新功能版，5.4.0 于 2025-10-09 发布、5.4.1 于 2026-02-17 作为安全加固版推出，而 4.14.3 仍作为长期支持（LTS）线并行维护。自 5.0（2022-12）引入多核域（domains）与用户态效应处理器（effect handlers）以来，OCaml 在并发与可扩展性上彻底现代化。5.4 延续这一方向，带来标记元组、不可变数组、原子记录字段与一批新标准库模块，对需要强类型安全与原生性能的团队是稳健的升级。

#### 它是什么
OCaml 5.4 的主要语言特性包括：标记元组（labelled tuples），如 (x:42, y:0)；不可变数组类型 'a iarray 与对应 Iarray 标准库模块；数组字面量语法 [| e1; ...; en |] 现在可在表达式与模式中表示 'a array、'a iarray 与 floatarray；原子记录字段（用 [@atomic] 标注），通过 Atomic.Loc 子模块做原子操作；四个新标准库模块 Pair、Pqueue、Repr、Iarray；恢复"退出时内存清理"模式以便 C 驱动程序反复重启运行时；新增 Linux/macOS 原生代码性能剖析手册章节；三十余个新标准库函数、近一打改进的错误信息、约五十个 bug 修复。底层还有 ARM64 帧指针与 macOS perf 改进，使 Apple Silicon 上的性能分析更可靠。

#### 解决什么
它针对几类现实需求。其一，不可变数组填补了 OCaml 长期缺失的"编译期可知不可变的大块顺序数据"抽象，配合 Iarray 模块让纯函数式批量数据操作更安全、也更易被编译器优化。其二，原子记录字段把无锁并发原语下沉到记录层面，多域程序无需为单个字段引入整块原子引用或锁，降低并发数据结构的心智负担。其三，标记元组让返回多值或临时聚合更可读、可在模式里按名解构，减少位置参数的误用。其四，Pqueue（优先队列）、Repr（基于内存表示的相等/比较）等模块的标准化，减少了每个项目重复造轮子的成本，也统一了社区约定。

#### 原理拆解
OCaml 的并发模型以"域（domain）"为单位，每个域有自己的运行时，域间通过效应处理器做轻量协作式并发。原子记录字段在编译期把某字段标记为需原子访问，生成的代码通过 Atomic.Loc.get/compare_and_set（配合 [%atomic.loc t.field] 内建扩展）访问，并禁止在模式匹配里直接读原子字段——因为读发生的时机难以静态判定，强制显式读取可避免隐蔽的数据竞争。不可变数组则从类型层面区分 array（可变）与 iarray（不可变），数组字面量语法依上下文类型消歧，默认假定 'a array；这让编译器在确认不可变后可做更激进的常量折叠与数据共享。标记元组在元组上附加字段名，解构时可用 (x:42, y:0) 形式，提升大元组的自说明性与可维护性。

### 【Erlang/OTP 28：严格推导、zip 生成器与抗量子密钥交换】

#### 导语
Erlang/OTP 28 是爱立信主导的"为并发、容错、热升级而生的函数式语言与运行时"的最新主版本，配套 OTP 28.4（2026-03-04）与 28.5（2026-04-23）等维护包。它在语言层引入了严格的列表推导生成器、zip 生成器、名义类型（Nominal Types）与任意进制浮点字面量，并在运行时、SSL、公共密钥与 JIT 上做了大量打磨。对电信、消息中间件、分布式数据库等"永远在线"系统，OTP 28 进一步降低了错误率并补强了后量子时代的传输安全。

#### 它是什么
OTP 28 的新语言特性包括：按 EEP 70 新增严格生成器（strict generators），模式不匹配即抛异常而非静默跳过；按 EEP 73 扩展列表推导支持 zip 生成器（如 [A+B || A <- [1,2,3] && B <- [4,5,6]] 得 [5,7,9]）；编译器对多种错误给出"did you mean …?"建议；实现 EEP 69 名义类型，可用其编码不透明类型（opaque types），并改进 Dialyzer 的不透明警告；按 EEP 75 支持任意进制浮点字面量。编译器/JIT 方面：别名分析更快且不那么保守，records 与二进制构造可在更多场景被优化；re 模块改用 PCRE2；新增 erlang:hibernate/0；按 EEP 76 允许进程接收优先级消息；实验性原生调试器 API；erl -noshell 新增 raw/cooked 子模式。公共密钥/SSL：替换老旧 ASN.1 模块，SSL 大幅优化吞吐与延迟。OTP 28.5 起默认密钥交换改为 mlkem768x25519-sha256（抗量子的混合算法）。

#### 解决什么
它解决几类痛点。其一，列表推导里生成器模式不匹配时旧版会"静默丢弃"，掩盖逻辑 bug；严格生成器把这类问题变成显式异常，更早暴露错误。其二，zip 生成器让"多序列逐位配对"成为语言原生能力，省去手动 zip 与嵌套推导，代码更直白。其三，名义类型让不透明抽象更难被意外破坏，Dialyzer 检查更准，跨模块封装更可靠。其四，后量子密钥交换默认开启，为长期安全未雨绸缪，避免未来量子计算对已抓包流量的威胁。其五，别名分析与二进制构造优化直接降低序列化密集服务的 CPU 占用，提升单节点吞吐。

#### 原理拆解
严格生成器改变列表推导的语义：当生成器模式无法匹配某个元素时，旧行为是跳过该元素（像过滤器），新行为是抛出 badmatch 类异常，迫使开发者显式表达"是否允许不匹配"。zip 生成器借 && 连接多个生成器，运行时把它们当作长度对齐的并行迭代，按索引一一配对后代入模板，因此 [A+B || A <- X && B <- Y] 在长度一致时得到逐位相加的结果。名义类型在类型层面引入"名义"而非"结构"的等价判定：即便两个类型结构相同，只要名字不同就视为不同，从而让不透明类型在跨模块边界真正封装，外部无法借结构相等钻空子。PCRE2 替换 PCRE 则是正则表达式引擎的现代化，带来更好的 Unicode 处理与更健康的维护状态。

```bash
. ~/otp28/activate
erl -eval 'erlang:display(otp_release), halt().' -noshell   # 输出 "28"
```

#### 对比选型
与 OTP 27 相比，28 在语言层变化更明显（严格生成器、zip、名义类型），且默认开启抗量子密钥交换，迁移时需核对 SSL/SSH 配置与既有推导是否依赖"静默跳过"语义。与 Elixir（构建于 BEAM 之上）相比，Erlang 更贴近运行时原语，Elixir 提供更丰富的语法糖与生态。与 Go、Akka 等并发模型相比，BEAM 的"进程即轻量独立单元 + 监督树"在容错与热升级上独树一帜，但单节点计算吞吐不及原生编译语言。选型建议：电信、IM、分布式存储、需要不中断升级 → OTP 28；纯计算密集 → 另选其语，或把计算下沉到 NIF/C 节点。

### 【F# 9 正式随 .NET 9 交付：可空类型、.Is* 属性与推导性能飞跃】

#### 导语
F# 9 是微软 .NET 平台上函数式优先语言的重大更新，随 .NET 9 交付，定位为"更安全、更健壮、更高效"。它在可空引用类型、判别联合的 .Is* 属性、列表/数组推导性能、结构体判别联合字段共享等方面做了可见的改进，并大幅强化了 IDE 工具与诊断体验。对用 F# 写领域模型、数据分析与云原生服务的团队，F# 9 让"用类型表达意图"这件事更顺、跑得也更快，进一步拉近了函数式优雅与工业落地的距离。

#### 它是什么
F# 9 的关键特性包括：可空引用类型（如 string | null），以类型安全方式处理来自 C# 库的 null；判别联合自动生成 .Is* 属性（如 contact.IsEmail）以替代手写匹配；部分活动模式现在可返回 bool 而非 option；列表/数组推导中的 for x in xs -> … 被显著优化（数组提速最高约 10×，分配降至 ⅓–¼）；结构体判别联合中同名同类型字段可共享内存，缩小结构体积（如从 60 字节降到 16 字节）；整型区间（start..finish、start..step..finish）的循环被更广泛优化，提速 1.25×–8×；C# 集合表达式可初始化 F# 的 list 与 set；解析器恢复（parser recovery）改进，编辑中途代码也能保持高亮；诊断信息更精准；CustomOperationAttribute 新增无参构造器；新增 --realsig+ 编译开关修正私有成员被写成 internal 的问题；Visual Studio 中 live buffers 默认开启，免去保存即可获得类型反馈。

#### 解决什么
它解决几类日常摩擦。其一，与 C# 互操作时 null 悄悄渗入导致运行期空引用：可空引用类型把"可能为 null"显式标进类型，编译器在匹配后消除 null 分支，把空检查前移。其二，判别联合每次都要写 match 判断分支类型，样板冗长：.Is* 属性一行即知所属分支，提升可读性。其三，列表/数组构造在大集合时曾是性能短板：新优化把数组推导提速最高约 10 倍、分配降到原来的四分之一，对数值与数据管道直接见效。其四，大型结构体判别联合内存浪费：字段共享把 60 字节压到 16 字节，对高频值类型意义重大，减少 GC 压力与缓存占用。

#### 原理拆解
可空引用类型沿用了 .NET 的 nullability 注解，F# 在类型检查器里为 "T | null" 引入可空联合，匹配时一旦某分支 binding 了非 null 结果，检查器便在该分支后消除 "null" 可能，从而把空检查前移。列表/数组推导优化来自编译器对 for x in xs -> e 这类"纯映射"形态的特殊识别：不再走通用的 IEnumerable 迭代分配，而是直接生成数组/列表构造循环，减少中间枚举器与装箱。结构体判别联合字段共享则利用"多 case 同名字段在内存布局上可重叠"的事实，把原本因字段名不同而各自占位的布局合并，前提是字段同类型——这样既保留按名访问，又压低整体尺寸。整型区间优化把 start..finish 在更多整数类型与步长下编译成定长计数循环而非惰性序列，避免闭包与迭代器分配。
