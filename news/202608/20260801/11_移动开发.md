### 【Swift 6.4 非拷贝泛型与类型化抛出：系统编程更安全】

#### 导语
Swift 6.4 在 WWDC26 随 iOS 27 一同亮相，是 Swift 语言在 6.x 系列里的又一次「工效学 + 系统编程」双线升级。过去 Swift 6 主打严格并发安全，迁移成本高；6.4 把重心放在让日常编码更顺手、同时把非拷贝类型（noncopyable types）与所有权系统推向可用，让系统级与高性能场景也能享受内存安全。对移动开发者而言，这意味着用更少的样板、更明确的语义写出更安全的代码，而不必推倒重来。

#### 它是什么
Swift 6.4 是 Apple 在 2026 年 6 月发布的 Swift 语言版本，随 Xcode 27 与 iOS 27 开发者测试版一同提供。它的更新可分成两层：一层是「日常工效学」，包括用 `anyAppleOS` 压缩冗长的 `@available` 可用性属性、用 `@diagnose` 精确控制编译器弃用警告、用双冒号模块选择器（Module Selectors，如 `Rocket.SaturnV`）解决同名 API 的歧义；另一层是「高性能与安全」，围绕非拷贝类型、所有权系统（Ownership System）、可迭代协议（Iterable Protocol）与借入/可变访问器（Borrow/Mutate Accessors）展开，并在错误处理表达上延续对精确语义的追求，`@diagnose` 让弃用与错误警告能被精确分级与控制。

#### 解决什么
第一，并发迁移摩擦。6.4 通过更友好的诊断让开发者逐步采用严格并发，而不是一次性重写。第二，模块命名冲突。当多个库导出同名类型时，模块选择器让消歧不再依赖脆弱的点语法。第三，系统编程安全。非拷贝类型让你能在不引入引用计数开销的前提下表达「唯一拥有」的语义，适合文件句柄、锁、GPU 资源等必须精确控制生命周期的对象。第四，标准库补强。新增任务取消保护（task cancellation shield）、字典 `mapKeyedValues`、基于 Swift System 的新 `FilePath` 类型，让跨平台路径处理更正确。

#### 原理拆解
非拷贝泛型的核心是所有权系统。传统 Swift 值类型靠复制保证独立，但某些资源（如文件描述符）不能复制只能移动。`noncopyable` 类型被编译器禁止隐式复制，只能通过移动语义转移所有权；Iterable Protocol 则让非拷贝元素也能被集合遍历，Borrow/Mutate Accessors 让你可以声明「只读借入」或「可变借入」而不触发复制。`@inline(always)` 与 `@specialized` 给性能敏感代码提供优化器控制；`@C` 属性打通 Swift 与 C 的互操作；Subprocess 1.0 提供类型安全的子进程管理。Swift Testing 也获得升级：`Issue.record` 可设严重级别，重复跑测试直到通过，便于定位偶发失败。

#### 动手验证
想要体验 6.4，可安装 Xcode 27 测试版，新建一个命令行包：

```swift
// 定义一个不可拷贝的资源包装
struct Handle: ~Copyable {
    let fd: Int32
    consuming func close() { /* 释放 fd */ }
}
// 用模块选择器消歧
import Rocket
let saturn = Rocket.SaturnV()   // 明确指向 Rocket 模块
```

在 Xcode 27 中把部署目标设为 iOS 27，即可使用 `anyAppleOS` 与 `@diagnose`：

```swift
@available(anyAppleOS, deprecated: 1.0, message: "改用新版 API")
@diagnose(.warning, .deprecated) func legacy() {}
```

也可运行 `swift test --repeat-until-pass` 复现并定位偶发测试。

#### 对比选型
与 Swift 6.3 相比，6.4 的并发模型没有引入破坏性变更，重点在诊断与库；与 Rust 的 ownership 相比，Swift 的非拷贝类型更轻量、可选采用，不强制全局所有权标注。对移动 App 开发，直接用 6.4 的新诊断与标准库即可，无需重写业务代码；对需要底层资源管理的 SDK，则有必要引入 noncopyable 类型消除运行期错误。在实际工程中，建议把 noncopyable 类型用于明确「一次性资源」的场景（如文件、锁、GPU 纹理句柄），并在公开 API 上用 `consuming` 标注转移语义，避免调用方误用导致编译失败。对于绝大多数业务 App，6.4 的价值更多体现在日常诊断与标准库补强：用 `anyAppleOS` 精简跨平台可用性声明、用 `@diagnose` 把即将废弃的接口以警告而非错误形式提示、用新的 `FilePath` 与 `mapKeyedValues` 减少手写胶水代码。综合来看，Swift 6.4 是一次「少改动、多收益」的平滑升级。

### 【Android 16 的 Live Updates 实时通知与 Material 3 Expressive 设计落地】

#### 导语
Android 16（API 36，内部代号 Baklava）于 2026 年通过 AOSP 季度发布模式推送，是 Google 转向「主干稳定 + 每半年大版本」后的重要一站。对开发者而言，它既带来了预测回退（Predictive Back）的强制化、面向进度的 Live Updates 通知，也带来了更精细的触觉、自适应刷新率与隐私沙盒能力，配合 Material 3 Expressive 设计语言，让 Android 应用的交互与视觉同步进化。

#### 它是什么
Android 16 是 Google 在 2026 年发布的 Android 大版本，AOSP 源码于当年第二、四季度分别发布。它在开发者面向的变更清单中引入：预测回退动画默认开启（`enableOnBackInvokedCallback` 默认 true，`OnBackPressed`/`KeyEvent.KEYCODE_BACK` 被忽略，需迁移到 `OnBackInvokedCallback`）、进度聚焦通知（Progress-focused notifications，即 Live Updates）、`finishAndRemoveTaskCallback` 与 `moveTaskToBackCallback` 等新回退 API、进阶触觉 API（可定义振幅与频率曲线）、自适应刷新率（`hasArrSupport()`/`getSuggestedFrameRate`）、系统触发分析（system-triggered profiling）、ADPF 中的 CPU/GPU Headroom API，以及 AGSL 自定义图像效果（`RuntimeColorFilter`/`RuntimeXfermode`）。

#### 解决什么
第一，回退手势一致性。强制预测回退后，所有 App 的返回动画与系统一致，避免各做各的割裂体验。第二，长任务可见性。Live Updates 让外卖、导航、打车等「用户发起的旅程」在通知栏获得更高优先级与更醒目的进度展示，提升留存与信任。第三，性能可观测。Headroom 与系统触发分析让游戏/重负载应用能按需调度算力并自动采集冷启动、ANR 等 trace。第四，无障碍与隐私。LE Audio 助听器相关 API、隐私沙盒（Privacy Sandbox）持续集成，强化包容与合规。

#### 原理拆解
预测回退的本质是把「返回」从 Activity 级别的回调改为系统手势驱动的回调（`OnBackInvokedCallback`），系统动画优先于应用自定义逻辑，因此老旧的 `OnBackPressed` 在 Android 16 目标应用中被忽略。Live Updates 则是一组带有进度语义的通知渠道，系统据其「进行中」的状态提升排序与展示位置。自适应刷新率依赖平台在 ARR 下向应用暴露建议帧率，应用据此选择更省电或更流畅的档位。AGSL（Android Graphics Shading Language）`RuntimeColorFilter` 让你用着色器在绘制调用上直接套用阈值、棕褐、色相饱和等效果。值得一提的是，Android 16 还把 16 KB 页面大小（16 KB page size）作为重点适配项，并对通用 Bootloader（GBL）与可配置音频政策（CAP）做了底层增强；这些改动虽然偏系统层，却直接影响应用的兼容性与内存占用。对于面向大屏、车机与 IoT 形态的开发者，Android 16 还引入了标准化的媒体质量框架 MediaQuality，让流媒体应用能动态查询并套用硬件的音视频画像。系统触发分析（ProfilingManager）的工作方式是：应用先注册感兴趣的触发条件（如冷启动、reportFullyDrawn、ANR），系统随后在对应时机自动启停 trace，并把结果回写到应用数据目录，开发者无需手动埋点即可拿到生产级性能快照。16 KB 页面大小则要求原生库重新编译以匹配新的内存对齐，未适配的 SO 在部分设备会出现崩溃，因此需尽早用兼容模式验证。

#### 动手验证
在 build.gradle 将 targetSdk 设为 36，迁移返回逻辑：

```java
@Override
public void onCreate(Bundle s) {
    super.onCreate(s);
    getOnBackInvokedDispatcher().registerOnBackInvokedCallback(
        OnBackInvokedDispatcher.PRIORITY_DEFAULT,
        () -> { /* 处理返回 */ });
}
```

启用进度通知（Kotlin）：

```kotlin
val progress = NotificationCompat.Builder(ctx, CHANNEL_ID)
    .setContentTitle("配送中").setProgress(100, percent, false)
    .setOngoing(true).setCategory(Notification.CATEGORY_PROGRESS).build()
```

并在 Manifest 适配 edge-to-edge（移除 `windowOptOutEdgeToEdgeEnforcement`）。

#### 对比选型
与 Android 15 相比，16 把预测回退从「可选」变为「默认强制」，迁移成本集中在返回逻辑；与 Material 3 Expressive（设计层）配合，视觉冲击力更强但需 Compose 1.11+。对存量 Java 工程，优先级是回退迁移与边缘到边缘适配；对新建项目，直接以 16 为目标并采用 Live Updates 能显著提升体验。

### 【Flutter 3.45 发布：Impeller 渲染与 Dart 宏能力再升级】

#### 导语
Flutter 在 2026 年保持着极高发布节奏：继 3.44 稳定版把 Impeller 设为默认渲染器之后，3.45 测试版于 2026 年 5 月 22 日释出（配套 Dart 3.13.0-103.1.beta），随后 3.46、3.47 beta 在 6—7 月接连到来。对于跨平台移动开发者，Flutter 3.45 这批预览的核心看点在于 Impeller 渲染器的持续打磨、Web/Wasm 路线推进，以及 Dart 宏（macros）能力的进一步成熟。

#### 它是什么
Flutter 3.45.0-0.1.pre 是 Google 于 2026-05-22 发布的 Flutter 测试版，对应 Dart SDK 3.13.0-103.1.beta。从发布节奏看，Flutter 正以约每数周一个 beta 的速度迭代（3.45 于 5 月、3.46 于 6 月、3.47 于 7 月 14 日）。Impeller 作为新一代渲染后端，自 3.44 起成为默认渲染器，3.45 继续修复着色器编译、纹理与动画方面的稳定性；Dart 3.13 则承接此前版本引入的宏系统实验，让数据类、序列化等样板代码可在编译期自动生成。

#### 解决什么
第一，渲染一致性。Impeller 预编译着色器，消灭 Skia 时代首次运行掉帧与「着色器卡顿」，让 iOS/Android 滚动与转场更稳定。第二，Web 性能。Wasm（WebAssembly）目标让 Flutter Web 获得接近原生的启动与运行表现，弥补 JavaScript 编译的不足。第三，开发效率。Dart 宏把 JSON 序列化、相等判断、数据类样板从手写转为声明式，减少出错面。第四，多平台统一。一套代码同时覆盖移动、Web、桌面与嵌入式，降低团队维护成本。第五，协作一致性。Flutter 的 Widget 即文档理念让 UI 结构与代码一一对应，新成员阅读源码即可还原界面，降低沟通成本。第六，热更新体验。3.45 继续优化 hot reload 对状态对象的保留，并在 DevTools 中提供更清晰的重建树视图，帮助定位不必要的重绘。对于团队同时存在 Web 与移动端的需求，Wasm 目标让同一份 Dart 代码在浏览器里也能复用绝大部分业务逻辑，避免重复造轮子。从工程角度看，3.45 的 beta 节奏也反映了 Flutter 团队对质量的取舍：先以预览通道验证 Impeller 在更多 GPU 与驱动组合下的表现，再滚动到稳定版，避免再次出现大面积着色器回退；Dart 3.13 同期还改进了 analyzer 的内存与速度，使大型工程的编辑期诊断更跟手。

#### 原理拆解
Impeller 在构建期为每个绘制操作预生成 Metal/OpenGL/Vulkan 着色器，运行期直接调用，避免运行期 JIT 编译造成的掉帧；它与 Flutter 的图层树（Layer Tree）直接对接，把 Widget 树的差量计算与光栅化解耦。Dart 宏基于编译期元数据与增强的 analyzer，通过 `augment` 关键字在生成阶段注入代码，且能感知类型信息，因此比传统代码生成器更安全。Flutter 的 hot reload 仍基于增量内核快照，使 UI 改动即时可见且不丢状态。

```

```

#### 对比选型
与 3.44 稳定版相比，3.45 是特性预览而非稳定版，生产项目建议等稳定通道；与 React Native 新架构相比，Flutter 的自绘渲染在复杂动画上更可控，但包体更大；与原生开发相比，Flutter 牺牲部分平台原生感换取开发效率。选型上，追求一致视觉与高效迭代的中大型跨端项目优先考虑 Flutter。对于小团队或个人开发者，Flutter 的丰富 pub.dev 生态与热重载能显著缩短从想法到上架的周期；若产品高度依赖原生平台独家能力（如复杂系统级蓝牙、特定硬件 SDK），则应在关键模块预留 Platform Channel 或原生插件接口，以避免后期被渲染层限制卡住。总体而言，3.45 这类预览版本最适合用于验证新渲染器与新宏能力，待其滚动进入稳定通道后再纳入生产依赖。

### 【HarmonyOS 8 新特性：端侧智能与分布式能力全面跃迁】

#### 导语
2026 年 7 月，华为终端 BG 陆续剧透全新一代 HarmonyOS 8，称其已进入核心研发收尾阶段，定位为「适配未来数年空间计算、端侧 AI、全屋智联的全新底层系统」。继 HarmonyOS 7 普及系统级 AI 智能体后，8 代把 AI 原生算力、全域跨端无缝流转、空间沉浸式交互作为三大突破，标志着纯血鸿蒙从「能用」走向「好用且智能」。

#### 它是什么
HarmonyOS 8 是华为规划的下一重大版本，聚焦三大能力：其一是全栈 AI 原生架构，把 AI 算力、大模型调度与智能体框架写入系统底层；其二是跨端流转全面增强，分布式软总线升级到 3.0；其三是空间沉浸式交互。据公开信息，鸿蒙智能体升级到 3.0，独创分布式算力池技术，可让手机、平板、智慧屏、车载设备的闲置 AI 算力互通共享；系统支持百亿级盘古大模型本地离线运行，并面向开发者开放 40 余项系统级 AI 原生权限。

#### 解决什么
第一，端侧智能的算力瓶颈。过去部分 AI 功能依赖云端、受网络与隐私约束；8 代通过本地大模型与分布式算力池，让修图、翻译、行程规划等高频操作离线即可完成，官方称本地 AI 任务执行成功率约 95%。第二，多设备协同门槛。分布式软总线 3.0 带宽提升 4 倍、延迟降低 30%，让「跨设备像同一台设备」成为默认体验。第三，开发门槛。自然语言即可开发智能服务，降低中小开发者进入鸿蒙生态的成本。第四，生态规模。截至披露时，鸿蒙终端超 6600 万台、原生应用突破 40 万款，8 代意在进一步扩容。

#### 原理拆解
AI 原生架构的核心是把模型推理与系统调度深度耦合：盘古大模型以量化形态常驻端侧，应用通过统一智能体框架发起请求，系统按当前设备负载在本地与分布式算力池间调度。分布式软总线 3.0 在传输层做了协议与带宽优化，使文件、画面、PPT 能在终端间「无感流转」——手机上的演示文稿可秒传车载屏继续编辑，电视画面能直接拖到平板续看。空间沉浸式交互则结合新型悬浮底栏、沉浸光感与主题色自定义，强化个性化。

### 【SwiftUI iOS 27 的自定义布局协议与共享元素转场 API】

#### 导语
SwiftUI 在 iOS 27 迎来近年最大的一次框架升级。WWDC26 上 Apple 展示了更高效的布局渲染、可重排容器、跨容器滑动操作，以及统一的结果构建器 ContentBuilder。对 Swift 开发者而言，这意味着更少的手写样板、更快的类型检查，以及更顺滑的自适应与转场体验——多数改进在重新编译即可获得，无需改写业务逻辑。

#### 它是什么
iOS 27 的 SwiftUI 新增一组围绕「容器交互」与「布局性能」的 API：可重排容器（`reorderable()` 与 `dragContainer`/`dragContainer(for:itemID:in:)`）、跨容器滑动操作（`swipeActionsContainer()` 让 `.swipeActions` 脱离 List 限制）、文档型 App 新架构（`WritableDocument`/`ReadableDocument`、`DocumentWriter`/`DocumentReader` 替代旧的 `FileDocument`，并支持磁盘直写）、工具栏增强（`ToolbarOverflowMenu`、`.visibilityPriority(.high)`、`topBarPinnedTrailing`、`.toolbarMinimizeBehavior(.onScrollDown)`）、导航转场（`.navigationTransition(.crossFade)` 与 zoom）、以及基于 item 绑定的 `.confirmationDialog(_:item:)`/`.alert(_:item:)`。底层还有 `@ContentBuilder` 统一各类结果构建器，显著改善复杂视图的类型检查性能。

#### 解决什么
第一，拖拽重排的成本。过去 List/网格重排要写大量手势与状态代码，如今一行 `reorderable()` 即可；且首次支持 watchOS 与自定义容器。第二，滑动操作碎片化。`swipeActionsContainer` 让 ScrollView、LazyVStack、自定义布局都能用熟悉的手势。第三，类型检查慢。复杂嵌套 Section/Group/ForEach 曾让编译器遍历大量重载路径，ContentBuilder 把多种 builder 收敛为单一路径，构建速度提升明显。第四，文档型 App 性能。磁盘直写与懒加载子视图（预取内容）让大文档滚动与打开更跟手。第五，文档型 App 的工程复杂度。过去用 FileDocument 处理大文件时，内存与磁盘同步容易出问题；新的 WritableDocument/ReadableDocument 把磁盘读写逻辑（DocumentWriter/DocumentReader）与数据模型解耦，并支持多入口的新建文档（DocumentCreationSource），让 Markdown、代码、笔记类应用能更安全地处理大文件。第六，确认弹窗的样板。基于 item 绑定的 `.confirmationDialog(_:item:)` 与 `.alert(_:item:)` 用单一数据驱动弹窗，告别分散的 `@State Bool` 海洋。这些 API 大多通过 Xcode 27 的 Agent 技能（agent skills）对外赋能：开发者可用 `xcrun agent skills export` 把 SwiftUI 专家技能导出为 Markdown，导入到自己的工作流或其他工具中，由编码代理引导采用新 API 并校验性能与正确性，使框架升级与工具链形成闭环。

#### 原理拆解
`reorderable()` 与 `dragContainer` 配合，把「可拖拽项」与「放置容器」解耦：`dragContainer` 声明某容器接受哪些 itemID，`draggable(containerItemID:)` 在容器内部标记可拖元素，系统负责动画与数据重排。ContentBuilder 的本质是让 ViewBuilder、TableRowContent 等 builder 共享同一初始化器，编译器不再为每个嵌套选项穷举重载，从而减少类型检查分支。`@State` 改为惰性初始化（lazy init）后，`@Observable` 对象只在真正需要时才创建，降低启动与内存开销。`AsyncImage(request:)` 则把 URLRequest 控制权交给开发者，支持自定义缓存与会话。

#### 动手验证
用 Xcode 27 将部署目标设为 iOS 27，体验重排与转场：

```swift
List(items) { item in
    Text(item.title)
}
.reorderable(in: $items)   // 一键开启拖拽重排

NavigationStack {
    DetailView()
        .navigationTransition(.crossFade)  // 内置淡入淡出转场
}
```

工具栏固定关键项：

```swift
.toolbar {
    Button("保存") { }
        .visibilityPriority(.high)          // 空间不足也常驻
}
```

并开启 Live Preview 的交互式缩放，实时验证自适应布局。

#### 对比选型
与 UIKit 相比，SwiftUI 在声明式与跨平台复用上更优，但极端自定义仍可能回到 UIKit（iOS 27 也新增了适配 iPhone 镜像的 UIKit 布局）。与 Jetpack Compose、Flutter 相比，SwiftUI 与系统深度集成（Liquid Glass、各平台统一）。对新建 Apple 平台 App，优先 SwiftUI；对已有 UIKit 大型工程，可按「新界面用 SwiftUI、旧界面用 NSHostingView 包装」渐进迁移。在真实项目里，建议把 SwiftUI 作为新功能与独立界面的默认选择，把既有的 UIKit/AppKit 视图通过托管容器嵌入，从而在享受声明式红利的同时保留对底层控件的完全控制；对于需要精细手势与自定义转场的高交互页面，可结合 `.navigationTransition` 与 `matchAnimatableData` 实现共享元素动画，使页面间切换更接近系统级原生过渡。总体而言，iOS 27 的 SwiftUI 升级是一次「重编译即受益、新 API 按需取」的渐进式演进，风险可控。

### 【React Native 2026 性能优化：从 Hermes 引擎到并发渲染提速实践】

#### 导语
到 2026 年，React Native 的「新架构」（New Architecture）已从 0.76 的默认选项演变为 0.82 起唯一可用的架构——旧的基于 JSON 桥接的旧架构被彻底移除。对移动团队而言，性能优化的主战场已经从「是否迁移」转为「如何把 Hermes 引擎、Fabric 渲染、TurboModules 与 React Compiler 组合到极致」。本文聚焦可落地的提速实践。

#### 它是什么
React Native 新架构由三大支柱构成：JSI（JavaScript Interface）用直接内存引用取代异步 JSON 桥接，让 JS 与原生代码同步互调；Fabric 是新渲染器，支持并发渲染、同步布局测量与按优先级更新；TurboModules 是懒加载的原生模块，按需初始化而非启动时全量加载。配合 Hermes V1（自 0.82 起必需、0.84 起作为默认引擎）与 React Compiler（自动记忆化），整体性能相较旧架构有量级提升。生产迁移数据显示冷启动快约 43%、渲染快约 39%、内存低约 26%。

#### 解决什么
第一，桥接卡顿。旧架构每次 JS↔原生调用都需序列化/反序列化，快速列表滚动与手势密集界面会掉帧；JSI 消除该瓶颈，跨线程调用延迟下降约 40 倍。第二，启动慢。TurboModules 懒加载把首屏不需要的模块延迟到使用时，中低端 Android 上 TTI 缩短 30–50%。第三，重渲染。React Compiler 与 FlashList 减少不必要的 JS 线程工作，稳定 60fps。第四，包体与字节码。Hermes 在构建期把 JS 编译为字节码（.hbc），降低运行期解析开销。第五，依赖审计成本。旧架构迁移的最大障碍是第三方库，2026 年约 85% 的主流包已兼容新架构，其余仍走互操作层（interop layer）保证可增量迁移——即先让老 Paper 组件在新架构下原样运行，再逐组件替换。第六，调试可见性。配合 Hermes 调试器与 React Native 的新性能面板，开发者可以直观看到 JS 线程、UI 线程与原生模块的耗时分布，精准定位掉帧根因。需要强调的是，Bridgeless 模式（0.78 起默认）已彻底移除旧桥接对象，JavaScript 侧的错误处理、定时器与全局事件发射器全部经由 JSI 在原生层运行，因此新架构下不再有「桥接初始化」这一耗时阶段；React Compiler 通过对组件与 Hook 的自动记忆化，消除大量因内联对象、内联回调导致的重复渲染，把 60fps 的预算留给真正的交互。

#### 原理拆解
JSI 让 JS 持有 C++ 宿主对象的直接引用，调用免序列化；Fabric 的并发渲染把布局与绘制移到合适线程，手势响应走主线程以保证跟手；TurboModules 通过 Codegen 从 TypeScript 接口生成带类型安全的原生绑定，且只在首次访问时加载。Bridgeless 模式（0.78 起默认）彻底移除桥接对象，错误、定时器、全局事件都经 JSI 原生运行。FlashList（Shopify）通过复用视图实例（类似 UICollectionView/RecyclerView）而非反复挂载卸载，使大数据列表滚动稳定 60fps——前提是提供正确的 `estimatedItemSize`。

#### 动手验证
在 Expo（SDK 52+）中一行开启新架构：

```json
// app.json
{ "expo": { "newArchEnabled": true } }
```

裸 RN（0.79+）在 Android 的 gradle.properties：

```properties
newArchEnabled=true
```

iOS 的 Podfile：

```ruby
ENV['RCT_NEW_ARCH_ENABLED'] = '1'
```

开启后用 `npx react-native-new-arch-helper check` 校验依赖兼容性；运行 Hermes 运行时自检：

```js
const isHermes = () => typeof HermesInternal !== 'undefined';
```

并用 FlashList 替换 FlatList：

```jsx
<FlashList data={items} estimatedItemSize={80}
  renderItem={({item}) => <Row {...item} />} />
```

#### 对比选型
与 Flutter 自绘相比，RN 复用原生组件、包体更轻、Web 代码复用更好，但极致自定义 UI 需更多原生模块；与原生（Swift/Kotlin）相比，RN 上限略低但开发效率与人才池占优。与 Capacitor 等 Web 容器相比，RN 是真原生组件而非 WebView，体验更佳。选型上，已有 React/JS 团队、追求双端一致与快速迭代的项目，RN 新架构 + Hermes V1 + FlashList 是 2026 年的高性价比组合。
