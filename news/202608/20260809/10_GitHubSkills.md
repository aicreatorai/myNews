### 1. 【airllm：单层加载推理让 4GB 显卡也能跑 70B 大模型】（⭐ 约 2.83 万 Star，日增约 1,716）

> 📍 **导语**
>
> 大模型推理这两年一直卡在同一道物理门槛上：显存。你想在本地跑一个 70B 的模型，第一件事不是写代码，而是查一下自己那张卡有多少 GB——然后放弃。绝大多数开发者手里是一张 8GB 甚至 4GB 的消费级显卡，而一个 70B 模型即便按 4bit 量化也要塞进几十 GB，差距是数量级的，不是"优化一下"能抹平的。
>
> lyogavin/airllm 给出的解法很反直觉：既然装不下整个模型，那就一次只装一层。它把推理过程从"整模型常驻显存"改成"逐层加载、算完即换"，显存压力的上界从"模型总大小"降到"单层大小"。README 给出的示例是单张 4GB GPU 跑 70B、8GB 跑 Llama 3.1 405B。2026-08-04 的 Trending daily 上它显示 27,097 星、2,973 forks、窗口新增 1,085 星；到 08-05 的日报里已经涨到 28,255 星、当日新增 1,716，排在榜单第 8。对手里没有大显卡、却想真正摸一摸超大模型的人，这是个值得花半小时验证的项目。

**▌ 它是什么**

airllm 是一个大模型推理的显存优化层，主语言是 Python（仓库以 Jupyter Notebook 为主要展示形式）。它不是一个新模型，也不是一套新的量化算法，而是改写了"模型权重如何进出显存"这一环。你照常用 Hugging Face 的方式加载模型，它在底下把模型按层拆开、逐层调度。

它和常见的"量化压缩"路线是两种思路。量化（4bit/8bit）是把每个参数变小，模型整体还是要一次性放进显存，压到极限也有下界；airllm 是把"同时在显存里的东西"变少，它不改变参数精度，而是改变时间与空间的交换比例——用更多的加载时间，换取显存占用的大幅下降。两者也不互斥：README 提到可以叠加 4bit/8bit 压缩，只是需要额外安装 bitsandbytes。

它和"用 CPU/内存卸载"的方案（把部分层放到内存或磁盘）思路接近，但 airllm 把这件事做成了默认工作方式而非兜底手段：它在第一次推理时就会把原始模型拆成逐层文件落盘，之后每次推理按需读取。这也解释了它的代价所在——省下来的是显存，付出去的是磁盘空间和加载时间。

**▌ 它解决了什么问题**

真实场景是这样的：你想评估一个 70B 开源模型在你业务语料上的表现，只是想跑几十条样本看看输出质量。走 API 的话，数据要出本机、还要按 token 付费；租一张 A100 按小时计费，为了几十条样本开机器又不划算；用本地 8GB 显卡，模型压根加载不起来，报错就是一行冷冰冰的 CUDA out of memory。这个"评估门槛"把大量个人开发者和小团队挡在了大模型能力之外——他们不是要做生产推理，只是想验证一下"这个模型到底行不行"。

没有分层加载时，可选路径基本只有三条：换更小的模型（但你想验证的恰恰是大模型的能力）、掏钱租卡（为一次性验证付固定成本）、走云 API（数据出本机）。airllm 补上的是第四条：在你已有的机器上，慢一点，但确实能跑起来。它把"我没有大显卡"这个硬约束，从"不可能"变成"一个可测量的时间成本"。

值得强调的是它改变的是可行性而非性能。逐层加载意味着每生成一个 token 都要把所有层轮流搬进搬出显存，吞吐必然远低于全量常驻。所以它的价值场景很明确：离线批处理、能力验证、短文本生成、教学演示——而不是给线上服务做实时推理。理解这一点，才不会用错地方然后失望。

**▌ 原理拆解**

```
加载阶段: 原始模型权重
  ↓
预处理: 首次推理时按 Transformer 层拆分，逐层落盘为独立文件
  ↓
推理循环（对每一层 i）:
    从磁盘/内存读入第 i 层权重 → 搬进 GPU 显存
      ↓
    执行第 i 层前向计算，输出激活值
      ↓
    释放第 i 层权重显存，保留激活值传给第 i+1 层
  ↓
输出: 逐 token 生成结果（显存峰值 ≈ 单层权重 + 激活值）
```

理解 airllm 的关键是"显存峰值由谁决定"。常规推理里，显存峰值 = 全部权重 + KV 缓存 + 激活值，权重那一项是绝对大头且无法回避；分层加载把权重项从"全部"变成"当前这一层"，于是峰值坍缩到一个跟模型总规模几乎无关的量级——这就是 4GB 卡能碰 70B 的数学原理。

代价也在这张图里写得很清楚：每一层都要经历一次"读盘 → 搬入显存 → 计算 → 释放"，磁盘 I/O 和 PCIe 传输取代 GPU 算力成为新瓶颈。所以两个细节要留意：一是首次推理会做拆分落盘，必须确保 Hugging Face 缓存目录有充足磁盘空间，否则会在中途失败；二是把权重文件放在 NVMe 固态盘上，比放在机械盘或网络盘上快出一个数量级，这几乎是决定体验的关键变量。

**▌ 动手验证**

```bash
# 1. 安装（建议先建虚拟环境，避免污染现有推理栈）
python3 -m venv .venv && source .venv/bin/activate
pip install airllm

# 2. 先确认磁盘余量：逐层拆分会额外占用与模型同量级的空间
df -h ~/.cache/huggingface

# 3. 最小可运行示例：加载模型并做一次短文本生成
cat > demo.py << 'EOF'
from airllm import AutoModel
model = AutoModel.from_pretrained("meta-llama/Meta-Llama-3.1-8B-Instruct")
inputs = model.tokenizer(["用一句话解释什么是分层加载推理"],
                         return_tensors="pt", return_attention_mask=False)
out = model.generate(inputs.input_ids.cuda(), max_new_tokens=32,
                     use_cache=True, return_dict_in_generate=True)
print(model.tokenizer.decode(out.sequences[0]))
EOF

# 4. 另开一个终端盯住显存曲线，验证峰值是否被压在"单层"量级
watch -n 1 nvidia-smi

# 5. 记录三个指标做横向对比：首次拆分耗时 / 加载耗时 / 每 token 生成耗时
time python3 demo.py
```

验证标准有两条，缺一不可。第一条是**显存**：第 4 步里 `nvidia-smi` 显示的峰值应当明显低于"模型总大小"，而是稳定在单层量级上下浮动——这是分层加载真的生效的直接证据。第二条是**时间**：第 5 步要老老实实记下首 token 延迟和后续生成速度，因为这才是你要付的账单。

**评估这类低显存推理方案的正确姿势，是先拿一个你显存本来就装得下的中等模型（比如 8B）跑一遍做基线，量出"分层加载比常规加载慢多少倍"，再决定要不要用这个倍数去换 70B 的可行性**——直接上 70B 会让你分不清"慢"是模型大导致的还是方案本身的开销。三个已知边界要提前避坑：部分 gated model 仍需配置 Hugging Face token 才能拉取；叠加 4bit/8bit 压缩要额外装 bitsandbytes；macOS 路线只支持 Apple silicon，Intel Mac 不在支持范围内。

**▌ 对比选型**

| 对比维度 | airllm | 4bit 量化 | 云 API |
|---|---|---|---|
| 显存需求 | 单层量级 | 模型量级 | 无 |
| 生成速度 | 慢（I/O 瓶颈） | 快 | 快 |
| 数据流向 | 全本地 | 全本地 | 出本机 |
| 适合场景 | 离线验证与批处理 | 本地日常推理 | 线上实时服务 |

选型建议：手里只有 4-8GB 消费级显卡、又需要在本地离线验证超大模型能力的开发者，airllm 是目前门槛最低的路子；显存够用（比如 24GB 跑 13B/30B）就直接上 4bit 量化，速度体验完全不是一个层级；要做线上实时服务，老老实实用云 API 或专用推理卡。三者可以组合：用 airllm 在本地选型验证，选定后再决定是量化本地部署还是上云。

### 2. 【i-have-adhd：给编码智能体加一个先说下一步的输出风格插件】（⭐ 约 1.63 万 Star，周增约 5,012）

> 📍 **导语**
>
> 用编码智能体久了会发现一个很微妙的损耗：它答得不错，但答得太长。你问"这个测试为什么挂了"，它先花三段介绍这个测试框架的设计哲学，再花两段铺垫可能的原因分类，最后才在第七段告诉你改哪一行。信息是对的，可你要的那句话被埋在八百字里，每次都得自己扒。
>
> ayghri/i-have-adhd 的解法朴素得有点好笑：它不改模型、不加工具，只给智能体挂一套输出风格规则——先给行动、步骤编号、压住跑题、报具体分钟数、错误直接说、列表最多五项、不写开场寒暄和结尾客套。名字听起来像个玩笑，实际瞄准的是所有人都在忍受的"AI 车轱辘话"。
>
> 它在 2026-08-04 的 weekly Trending 上显示 16,298 星、918 forks，窗口新增 5,012 星——一个不写一行功能代码的规则包，一周涨了五千星，本身就说明这个痛点有多普遍。需要先说清楚的是：项目名只是个自嘲式的比喻，它不做任何注意力相关的诊断或医疗判断，纯粹是改智能体的说话方式。

**▌ 它是什么**

i-have-adhd 是一个给编码助手用的输出风格插件/技能包，不是独立应用。它以插件形式装进 Claude Code、以技能形式被 Codex 调用，作用范围只有一个：约束智能体回答的组织方式。它的全部"代码"本质上是一份规则文档（SKILL.md），把"怎样算一个好回答"写成智能体能执行的硬约束。

它和"在提示词里加一句别啰嗦"的区别在于稳定性与可复用性。你在对话里说"简短点"，模型会短两轮然后打回原形，而且换个项目、换个会话就要重说一遍；插件是常驻约束，装一次处处生效，不依赖你每次记得提醒。

它和"换一个更强的模型"的区别在于方向。更强的模型往往更啰嗦——它知道得更多，就更想把知道的都说出来。冗长不是能力问题，是默认输出偏好问题，只能靠外部约束扳正。这也是这类"风格技能"近期在 GitHub 上集中冒头的原因：大家发现，调教输出格式的性价比，比等下一代模型高得多。

**▌ 它解决了什么问题**

具体场景：你在排查一个线上问题，一分钟能看三条日志的节奏，把报错贴给智能体。它回你一屏半的文字：先复述你的报错（你知道），再科普这个错误码的含义（你也知道），然后列出五种可能原因并各配一段解释（其中三种明显不适用），最后给出修改建议。你真正需要的是最后那 30 个字，却要为前面的 800 字付出阅读时间、上下文窗口和 token 费用。

这个损耗有三重：**时间上**，每次回答你都要做一次人肉信息提取；**成本上**，冗长输出直接换算成 token 账单，一天几十次对话下来不是小数；**协作上**，如果你把智能体的输出粘进 issue 或群里，同事还要再扒一遍，浪费被复制放大。

没有这类插件时，常见应对是在提示词里反复追加"直接给结论""不要解释""用列表"，但这类零散指令有两个毛病：一是每个项目都要重写一遍，二是模型遵守几轮就漂回默认风格。i-have-adhd 把这些散落的要求整理成一套成体系、可分发、可 fork 修改的规则，一次配置长期生效。它解决的不是"AI 会不会答"，而是"AI 答得能不能直接用"——在人机协作频次已经变得很高的今天，这个边际收益每天都在复利。

**▌ 原理拆解**

```
你提出问题（如"这个测试为什么挂了"）
  ↓
插件注入: 把风格规则挂进智能体的系统上下文
  ↓
规则约束（生成时同时生效）:
    ① 先给行动，不做背景铺垫
    ② 步骤编号，便于逐条执行
    ③ 列表最多五项，逼出优先级排序
    ④ 报具体分钟数，不说"很快"
    ⑤ 错误直接说，不用委婉包装
    ⑥ 砍掉开场寒暄与结尾客套
  ↓
输出: 一段可以直接照做的短回答
```

理解它的关键在于"约束前置"和"逼出取舍"两点。约束前置意味着规则在生成那一刻就生效，而不是生成完再让你去删——后者你已经付过 token 和阅读成本了。逼出取舍则更妙："列表最多五项"这条规则表面是限长，实际是强制排序。模型列十项的时候可以不思考优先级，被限制到五项，它就必须判断哪些真正重要——限制反而提升了回答质量，这是这套规则里最值得借鉴的设计。

"报具体分钟数"同理，它把"这个改动很快"这种无法验收的表述，逼成"大约 10 分钟"这种可以对照现实校准的承诺。需要清醒的是它的能力边界：它改的是表达层，不是推理层。智能体本来就判断错的东西，加了这个插件只会错得更简洁、更斩钉截铁——因为"错误直接说"这条规则会去掉原本的模糊限定词。它也不会替你确认命令是否安全，该复核的还得复核。

**评估这类风格插件的正确姿势是做同题 A/B，而不是只看开启后的单次输出**。因为"回答变短了"是必然的，真正要验证的是"变短之后信息密度有没有下降"。建议选三类任务各测一次：一个简单修 bug（看是否够直接）、一个需要权衡的设计问题（看是否因限长而丢掉关键权衡）、一个你已知正确答案的问题（看简洁化会不会把正确的犹豫变成错误的笃定）。第三类最能暴露这套规则的副作用。

### 3. 【reverse-skill：把逆向与授权安全测试拆成有顺序的智能体技能路由包】（⭐ 约 1.77 万 Star，日增约 2,310）

> 📍 **导语**
>
> 让编码智能体做安全分析，最大的问题不是它不会，而是它太爱试。你给它一个待分析的 APK，它可能上来就随机敲一串工具命令，工具没装就换一个，换到能跑为止——过程无序、结论无据、报告无法复核。对安全工作来说，"结论对不对"和"结论怎么来的"同样重要，一个没有证据链的发现，在评审时等于没有。
>
> zhaoxuya520/reverse-skill 想解决的正是这件事。它是给 Claude Code、Codex CLI、Cursor、Cline 等编码智能体用的安全技能路由包，覆盖 APK、二进制、前端 JS 加密和 CTF 等场景。核心设计是"先检查工具，再按方法、脚本、证据和报告路径组织工作"——把安全分析从"凭感觉试命令"变成一条有顺序、留痕迹的流水线。
>
> 它在 2026-08-05 的 GitHub 日报里排到第 2，17,735 星、当日新增 2,310、2,440 forks；08-04 的 daily 榜显示 15,777 星、窗口新增 2,446。**必须前置声明的边界**：项目明确面向逆向工程、**已获授权**的渗透测试与安全研究，没有授权的目标不该拿来试，这既是项目自己的要求，也是使用者的法律底线。

**▌ 它是什么**

reverse-skill 是一个技能路由包，本身不是扫描器、不是漏洞库，也不替你执行攻击。它做的是"编排"：把安全分析这件事按场景拆成若干技能（APK 分析、二进制分析、前端 JS 加密还原、CTF 解题等），每个技能内部规定了该用哪些工具、按什么顺序、每一步要留下什么证据。智能体接到任务后，由它决定走哪条技能路径。

它和"直接让智能体跑安全工具"的区别在于有没有方法论。裸跑的智能体没有工具清单意识，装没装 jadx、有没有 frida，它要试了才知道；reverse-skill 的第一步是**工具检查**——先刷新工具索引、生成 `skills/tool-index.md`，让智能体在动手前就知道这台机器上有什么武器、缺什么。这一步看起来平淡，实际把"半途报错重来"的返工率压下去一大截。

它和传统自动化扫描器的区别则是定位不同。扫描器输出的是规则命中的告警列表；reverse-skill 输出的是一条人可复核的分析路径。它的价值不在"发现更多"，而在"发现得可追溯"。

**▌ 它解决了什么问题**

真实场景：你要分析一个自家 App 的加固方案是否有效（这是典型的授权内工作）。传统流程是人肉走一遍：解包、看壳、脱壳、反编译、找关键类、动态 hook 验证、写报告——每一步换一个工具，工具的安装、版本、参数各不相同，中间产物散落在几个临时目录里。等你写报告时，常常想不起某个结论是从哪一步得出的，只好回头重跑。

把这套流程交给智能体，如果没有约束，问题会更糟：它可能跳过脱壳直接反编译（拿到一堆乱码）、可能用了一个版本不兼容的工具（输出为空却继续往下推）、可能给出一个听起来合理但没有任何中间产物支撑的结论。**安全场景里，"看起来合理"是最危险的输出**——它会让人对一个不存在的发现投入排查成本，或者对一个真实风险放松警惕。

reverse-skill 的价值就在这里：它用 Evidence → Finding → Path → report 的固定链路，强制每个结论都挂在具体证据上。你在报告里看到"这个接口的签名算法可被还原"，能顺着链路找到是哪个文件、哪段代码、哪次动态验证支撑了这个判断。对需要把结果交给评审、交给甲方、交给合规的人，这条链路就是工作能不能被采信的分界线。

**▌ 原理拆解**

```
输入: 待分析目标（APK / 二进制 / 前端 JS / CTF 题目）
  ↓
前置闸门: 确认 scope、授权范围与网络配置（没有授权就不该继续）
  ↓
工具检查: 刷新工具索引 → 生成 skills/tool-index.md，明确可用/缺失工具
  ↓
技能路由: 按目标类型选择对应技能路径（APK / 二进制 / JS 加密 / CTF）
  ↓
有序执行: 方法 → 脚本 → 证据留存，每步产物落到固定路径
  ↓
结论组织: Evidence（证据）→ Finding（发现）→ Path（路径）→ report（报告）
  ↓
输出: 带完整证据链、可被第三方复核的分析报告
```

理解它的关键是三个"前置"。**授权前置**：把 scope 与授权确认放在流程第一步，而不是事后补——这是安全工作的合规基线，也是把工具用在正道上的机制保障。**工具前置**：先索引后执行，避免智能体在无效命令上空转，也让"这个结论为什么没得出"变得可解释（因为缺某个工具，而不是因为不存在漏洞）。**证据前置**：不是分析完再补材料，而是每一步执行时就把产物落到固定路径，报告是从证据自动汇聚出来的，不是回忆出来的。

需要清醒认识的成本：它对环境要求不低。README 列出的基本前置是 JDK、Node.js 22.12+、Python 3.x，再加一个能执行这些技能的编码智能体；若要覆盖完整的 Kali 工具链，安装成本还会显著上升。另一个容易被忽略的点是许可证——主仓库是 MIT，但其中不同子项目有各自的许可证，用于商业交付前必须逐个确认。

### 4. 【OpenLogi：用 Rust 做本地优先的罗技外设控制，不要账号也不带遥测】（⭐ 约 8,156 Star）

> 📍 **导语**
>
> 有一类软件的存在感很奇怪：你不想装，但不装就少一半功能。厂商配套的外设驱动软件就是典型——为了给鼠标侧键绑一个快捷键，你得装一个几百 MB 的客户端，注册一个账号，接受一份隐私条款，让它常驻后台、开机自启、定期联网。功能本身可能只需要往设备发几个字节。
>
> AprilNEA/OpenLogi 是一个用 Rust 写的本地优先 Logitech Options+ 替代品。它能改按键、DPI、SmartShift、应用级配置和部分键盘 RGB，通过 HID++ 协议访问 Logi Bolt、Unifying、蓝牙和 USB 外设，**不要求罗技账号，也不带遥测**。它在 2026-08-04 的 Rust Trending daily 上显示 8,156 星、211 forks、窗口新增 88 星——增速不算炸裂，但这类"把厂商客户端替换掉"的项目往往长尾很长，因为痛点不会过期。
>
> 在这期以 AI 为主的榜单里，它是难得一条硬件方向的项目，也是"本地优先"这个理念少见的可触摸样本：你能拔掉网线，亲手验证它是不是真的不需要云。

**▌ 它是什么**

OpenLogi 是一个开源的罗技外设配置工具，用 Rust 实现，定位是官方 Logitech Options+ 的本地优先替代品。它直接通过 HID++（罗技外设的私有 HID 扩展协议）与设备通信，支持 Logi Bolt 接收器、Unifying 接收器、蓝牙和 USB 四种连接方式，覆盖按键重映射、DPI 调整、SmartShift 滚轮模式、应用级配置切换，以及部分键盘的 RGB 控制。

它和官方客户端的核心差异有三条，条条都是设计取向而非功能多寡：**不要账号**（配置存本地，不做云同步）、**不带遥测**（不上报使用数据）、**Rust 单体实现**（没有内嵌浏览器内核，资源占用低）。换句话说，它把"配置一个鼠标"这件事还原成本来该有的样子——一次本地的 USB/蓝牙通信，而不是一次需要身份认证的云服务调用。

需要明确的是它与厂商的关系：OpenLogi 与 Logitech 没有隶属关系，是社区实现。这既意味着它不受厂商产品节奏约束，也意味着新设备的支持要靠社区跟进，官方不会为它背书。

**▌ 它解决了什么问题**

具体痛点有三层，从轻到重。**第一层是资源**：为了几个键位映射，后台常驻一个吃内存的客户端，笔记本用户尤其能感觉到——风扇、续航、启动速度都要为它让路。**第二层是账号与隐私**：一个鼠标配置工具为什么需要我注册账号？为什么需要联网？对企业内网、涉密环境、或者单纯注重隐私的人，这不是洁癖而是硬性障碍——很多合规环境根本不允许装带遥测的第三方客户端，结果就是花钱买的外设只能用出厂默认配置。**第三层是可用性**：厂商客户端的更新节奏、系统兼容、账号服务可用性都不由你控制，哪天服务变更或旧设备被移出支持列表，你的配置就悬空了。

没有替代品时，多数人的选择是"忍"——装上官方客户端、注册账号、然后尽量不去想它在后台干什么。少数人走极端：完全不配置，用出厂默认。OpenLogi 提供的第三条路是：把配置能力从云端拉回本地，让"改一个侧键"重新变成一次一次性的本地操作。

它的普遍性比想象中大。罗技外设在开发者群体里的占有率相当高，而"想配置但不想装官方客户端"几乎是一个共识性抱怨。这也解释了为什么一个功能范围并不宽的工具能进 Trending：它戳的不是新需求，是一个被忍耐了很久的旧需求。

**▌ 原理拆解**

```
输入: 你的配置意图（改侧键 / 调 DPI / 切 SmartShift / 应用级配置）
  ↓
设备发现: 枚举 Logi Bolt、Unifying、蓝牙、USB 四类通道上的外设
  ↓
协议层: 通过 HID++ 私有扩展协议构造特性请求
  ↓
下发: 把配置写入设备（而非只存在于宿主软件里）
  ↓
本地持久化: 配置文件留在本机，不做云同步、不上报遥测
  ↓
输出: 设备行为按新配置生效，断网亦然
```

理解它的关键是"配置写到哪里"。HID++ 允许把一部分设置写入设备自身，这意味着配置的生效不依赖宿主软件常驻——这正是"本地优先"能落地的技术基础，也是你可以断网验证的原因。而应用级配置（不同 App 用不同键位）这类需要感知前台窗口的功能，则必然依赖一个本地 agent 在跑，无法完全脱离宿主。

这个区别决定了它在不同系统上的表现差异，也是必须提前知道的边界：Linux 的应用级配置依赖 X11/XWayland，纯 Wayland 环境下前台窗口检测能力受限；Linux 还需要正确的 udev 规则和后台 agent 才能访问 HID 设备。Windows 支持是较新的移植，成熟度低于其他平台。RGB 与按键捕获能力则取决于具体设备型号——HID++ 各代特性集不同，不是所有设备都暴露同样的能力。最后，项目仍在积极开发中，尚不算稳定版本，重要工作设备建议先在次要设备上试。

### 5. 【GitHub Actions 供应链加固：SHA 钉死、OIDC 免密与最小权限三道闸】

> 📍 **导语**
>
> GitHub Actions 好用得有点危险。往 `.github/workflows` 丢一个 YAML、推上去，就有东西跑起来了——这个极低的门槛让它成为绝大多数团队的默认 CI/CD 引擎，也埋下了它最大的坑。devopsness 在 2026-07-08 的那篇实践指南里说得很直白：生产环境里的 Actions 问题，绝大多数不是缺功能，而是**蔓延、权限过宽、以及复制粘贴出来的工作流各自漂移**，直到每个仓库的行为都不太一样。
>
> 更要命的是，CI 是软件供应链上权限最高的一环。它能读你的代码、拿你的云凭证、往生产推镜像。一个被过度授权的 `GITHUB_TOKEN`、一个用浮动 tag 引用的第三方 action、一个把用户输入直接插进 `run:` 的步骤，任何一处都足以让攻击面从"某个仓库"扩大到"整个云账号"。
>
> 这一条不讲某个项目，讲的是三道能立刻加上、且几乎不需要架构改动的闸门：**权限最小化、凭证免密化、依赖不可变化**。三条加起来，改动量约等于每个工作流多写十几行 YAML。

**▌ 它是什么**

这套做法的本质，是把 GitHub Actions 从"一堆按需写的 YAML"当成"一个有安全默认值的平台产品"来管。三道闸各自负责一类风险：

**第一道是 `permissions`（权限最小化）**。GitHub 自动注入的 `GITHUB_TOKEN` 默认权限往往远超一个 CI 任务真正需要的范围。正确做法是从零起授——在工作流或 job 级别显式声明 `permissions`，只给这个 job 实际用到的那几项。这被 devopsness 称为"多数仓库里性价比最高的一处安全改动"。

**第二道是 OIDC（凭证免密化）**。别再把长期有效的云访问密钥塞进 GitHub Secrets。OIDC 让 Actions 用一个短时令牌去云厂商换临时凭证，AWS、GCP、Azure 三家都已有标准接法。密钥不存在，就不存在泄露。

**第三道是 SHA 钉死（依赖不可变化）**。第三方 action 用 `@v4` 这种浮动 tag 引用，意味着 tag 背后的代码可以被重新指向——你昨天审过的代码和今天跑的可能不是同一份。改用完整 commit SHA 引用，引用即快照。

**▌ 它解决了什么问题**

先看第一道闸对应的事故形态。一个只需要读代码跑测试的 CI job，却持有可写权限，那么任何能影响这个 job 执行内容的人——提 PR 的外部贡献者、被投毒的某个依赖、一段拼接了用户输入的脚本——都可能借它的手写回仓库。**权限过宽的本质，是把"谁能改代码"的边界，悄悄扩大成了"谁能影响 CI"**。

第二道闸对应的是凭证生命周期。长期云密钥存在 Secrets 里，它的暴露面是所有能触发工作流、能看日志、能改工作流的人的并集，而且一旦泄露，在你察觉并轮换之前一直有效。OIDC 换来的临时凭证生命周期以分钟计，泄露的窗口小到几乎没有利用价值。

第三道闸对应的是供应链投毒。你 `uses:` 一个社区 action，等于把这段代码放进你权限最高的执行环境。用 tag 引用时，上游作者（或者拿到其账号的人）把 tag 重新指向一个新 commit，你的下一次构建就会静默执行新代码，没有任何 PR、没有任何 review。这不是理论风险，而是近年供应链攻击的常见路径。

还有两个高频陷阱值得单列。一是 **fork PR 的特权泄露**：安全模式是在 `pull_request` 上做**不带 secrets** 的构建与测试，需要凭证的特权操作放到维护者批准之后再执行；`pull_request_target` 除非你完全清楚它的安全含义，否则不要用。二是 **脚本注入**：把 `${{ github.event.issue.body }}` 这类用户可控内容直接拼进 `run:`，等于允许任何人在你的 runner 上执行命令。

**▌ 原理拆解**

```
事件触发（push / pull_request / schedule）
  ↓
闸门一 · 权限最小化: permissions 从零起授，只给本 job 用到的项
  ↓
闸门二 · 凭证免密: id-token: write → 向云厂商换取短时临时凭证
  ↓
闸门三 · 依赖不可变: 所有第三方 action 以完整 commit SHA 引用
  ↓
危险输入隔离: 用户可控内容不进 run:；fork PR 不给 secrets
  ↓
环境审批: Environments + required reviewers 卡住生产部署
  ↓
安全门禁: CodeQL 扫描 + Dependabot 依赖更新作为合并前置
  ↓
输出: 一条权限可解释、凭证可短命、依赖可追溯的流水线
```

可直接抄的最小配置：

```yaml
permissions:
  contents: read          # 从零起授，只给读代码

jobs:
  deploy:
    permissions:
      id-token: write     # OIDC 必需
      contents: read
    steps:
      # SHA 钉死：注释里保留可读版本号，便于人工审阅
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789:role/github-deploy
          aws-region: us-east-1
```

三道闸的顺序不是随意排的：**权限最小化是地基**（它决定了后面所有步骤能造成的最大破坏半径）、**OIDC 是把最值钱的资产移出仓库**、**SHA 钉死是防止执行内容被偷换**。三者互补，任何一条单独上都留有明显缺口——比如只做 SHA 钉死而权限仍然过宽，一旦某个被钉死的 action 本身有漏洞，破坏半径依然很大。

前瞻一点：据 devtoollab 的整理，GitHub 2026 年的安全路线图里有一项 workflow lockfile，会自动用 commit SHA 钉住直接与传递的 action 依赖。在它落地之前，上面这套手工清单覆盖的正是同一片地面。

**▌ 动手验证**

```bash
# 1. 先摸底：找出仓库里所有用浮动 tag 引用的第三方 action
grep -rn "uses:.*@v[0-9]" .github/workflows/ | grep -v "actions/"

# 2. 把某个 tag 解析成完整 commit SHA（以 checkout v4.2.2 为例）
gh api repos/actions/checkout/git/refs/tags/v4.2.2 --jq '.object.sha'

# 3. 检查哪些工作流没有显式声明 permissions（这些就是权限过宽的候选）
grep -L "permissions:" .github/workflows/*.yml

# 4. 排查脚本注入风险：用户可控内容是否直接进了 run:
grep -rn "github.event.issue.body\|github.event.pull_request.title" \
  .github/workflows/ | grep -A2 "run:"

# 5. 改完后开一个 PR 验证：CI 应正常通过，且 job 日志里
#    能看到 OIDC 换取临时凭证成功、没有任何长期密钥被引用

# 6. 反向验证权限闸门是否真的生效（关键一步）：
#    临时在一个测试分支上让 job 尝试一个未被授权的操作（如写 issue），
#    确认它因权限不足而失败，而不是悄悄成功
```

验证标准的重点在第 6 步。前五步都是"改了配置"，只有第 6 步能证明"配置真的在管事"。一个常见的自欺是：声明了 `permissions: contents: read`，但因为某处 job 级别覆盖或复用工作流继承，实际生效的仍是宽权限——不做反向测试就发现不了。

**评估 CI 加固效果的正确姿势，是做一次"越权尝试"并确认它失败，而不是只检查 YAML 里有没有写那几行**。同理，OIDC 也要看日志里确实完成了令牌交换，而不是回退到了某个还没删干净的旧密钥。建议的推进节奏：先在一个低风险仓库把三道闸全部落地并跑通，形成一份模板，再向其他仓库推广；一次性全量改造容易在半路被某个卡点阻塞，最后不了了之。

**▌ 对比选型**

| 对比维度 | 三道闸加固 | 默认配置 | 只做 SHA 钉死 |
|---|---|---|---|
| 凭证泄露风险 | 无长期密钥 | 高 | 高 |
| 供应链投毒 | 引用即快照 | 无防护 | 已防护 |
| 改动成本 | 每流水线十几行 | 零 | 很小 |
| 适合场景 | 有生产部署的团队 | 个人玩具项目 | 过渡方案 |

选型建议：只要你的流水线碰得到云凭证或生产环境，三道闸都应视为必做项，投入产出比极高；纯个人的玩具仓库可以先只做 SHA 钉死与 `permissions: contents: read` 两条，成本近乎为零。要避免的反模式是"只做看得见的那条"——很多团队钉死了 action 却仍在 Secrets 里放长期 AK/SK，等于给最贵的资产留着门。

### 6. 【GitHub Actions 可复用工作流：用 workflow_call 把五十个仓库的 CI 收成一份】

> 📍 **导语**
>
> 团队规模一大，CI 就会长出一种奇怪的病：五十个服务仓库，五十份 YAML，看起来都差不多，但每一份都被某个人在某个深夜改过一点。有的用 Node 18、有的 20；有的跑 lint、有的忘了；有的加了缓存、有的每次从头装依赖。平时相安无事，直到安全团队说"所有流水线都要加一个强制密钥扫描步骤"——这时你才发现，这个需求要开五十个 PR，改五十份略有差异的文件。这类推广，通常推到一半就没人跟进了。
>
> 另一头是钱和时间的浪费。没配缓存，每次构建白白花两到四分钟装依赖；没配并发组，十分钟内推三个 commit 就排三条流水线，前两条跑完时早就过时。devtoollab 给的经验数字很有说服力：**加上并发组和依赖缓存这两项，通常能把运行时间砍掉 40%-60%**，而且不需要任何架构改动。
>
> 这一条讲的就是这两件事：用 `workflow_call` 收敛重复，用缓存、并发组和矩阵分片压掉时间。

**▌ 它是什么**

可复用工作流（Reusable Workflow）是 GitHub Actions 提供的一种"工作流即库"的机制。你在一个中心仓库（惯例是组织下的 `.github` 仓库）里定义一份带 `workflow_call` 触发器的工作流，声明它接受哪些 inputs 和 secrets；其他仓库用 `uses:` 引用它，自己的 YAML 就只剩薄薄几行。

它和"复制粘贴 YAML"的区别是**单点变更**。逻辑集中在一处，改一次、发一个新 tag，所有消费方通过 Dependabot PR 把 `@v3` 升到 `@v4` 就完成了升级——而且这个升级是可 review、可测试、可回滚的，不像五十个手工 PR 那样质量参差。

它和 **Composite Action（复合动作）** 的区别是粒度。可复用工作流复用的是**整个 job**（含 runner 选择、环境、权限）；复合动作复用的是**一串步骤**，更轻，适合"装环境 → 构建 → 推镜像"这种步骤序列。判断标准很简单：要共享的是一整个作业就用前者，只是几个步骤就用后者。

至于提速三件套——依赖缓存、并发组、矩阵分片——它们是正交的加速手段，和复用机制可以同时使用，而且都是加几行配置的事。

**▌ 它解决了什么问题**

第一个问题是**漂移**。devopsness 把它列为 Actions 头号麻烦源：复制到每个仓库再各自微调，时间一长没有两份是一样的。漂移的代价不在平时，在你要做横向变更的那一天——安全加固、Node 版本升级、构建产物签名，每一次都变成一场五十个 PR 的战役。把可复用工作流当成一个有 changelog、有语义化版本的**产品**来维护，整个组织才能一起前进而不是各自漂开。

第二个问题是**浪费**。没有缓存，每次构建都重新下载全部依赖，大项目每次多花两到四分钟；乘上一天几十次构建、几十个仓库，烧掉的是真金白银的 runner 分钟数。没有并发组，快速连推三个 commit 就产生三条流水线，前两条从启动那刻起就已经过时了。

第三个问题是**串行测试拖慢反馈**。要在三个操作系统 × 两个 Node 版本上验证兼容性，串行跑要六倍时间；矩阵让它们并行，总耗时约等于最慢的那一格。测试套件本身很大时，还能用 `--shard=1/4` 这类分片参数把一个套件拆到多台 runner 上跑——Vitest、Jest、Playwright 都支持。

这三件事的共同点是：**收益立竿见影，改动却小得不像话**。这也是为什么它们常年出现在各家最佳实践清单的最前面——不是因为高深，而是因为总有人没做。

**▌ 原理拆解**

```
中心仓库 org/.github
  └─ .github/workflows/node-ci.yml   ← on: workflow_call，声明 inputs/secrets
        ↑ uses: my-org/.github/.github/workflows/node-ci.yml@v3
        │
服务仓库（薄壳，只传参数）
  ↓
执行时叠加三层提速:
   ① 缓存: setup-node 的 cache: 'npm'，key 基于 lockfile 哈希
   ② 并发组: 同分支新 run 自动取消旧 run
   ③ 矩阵: OS × 版本并行，大套件再按 --shard 分片
  ↓
升级路径: 中心仓库发 v4 → Dependabot 给各仓库开 PR → 逐个 review 合入
```

三个配置细节决定成败，值得逐条记住。

**缓存 key 必须绑定 lockfile 的哈希**，比如 `hashFiles('**/package-lock.json')`，绝不能用日期或分支名——用错 key 的后果是缓存永远命中不了（白配）或者永远不刷新（拿到过期依赖，比没缓存更坑）。`setup-node`、`setup-python`、`setup-go`、`setup-java` 都内置了 `cache:` 参数，能用内置的就别直接上 `actions/cache`。另外配一个 `restore-keys` 作为回退，能让新 lockfile 首次运行时也吃到部分缓存。

**并发组在 PR 和主分支上的策略要相反**。PR 用 `cancel-in-progress: true`，把同一个 PR 的多次推送收敛成一条活跃流水线；主分支部署要用 `false`，否则一次部署跑到一半被新提交打断，可能留下半推上去的烂摊子。

**定时任务要错峰**。`on: schedule` 走 UTC 时间，整点是全球高峰，可能被延迟最多 15 分钟；把 cron 设在非整点（比如 `17 2 * * 1`）能拿到稳定得多的触发时间。

对 monorepo 还有一条：用 `paths` 过滤或 `dorny/paths-filter` 做差分构建，只构建和测试真正变更的包；配合 `fetch-depth: 1` 的浅克隆，能把大仓库的 checkout 时间也压下来。

**▌ 动手验证**

```yaml
# 1. 中心仓库 org/.github/.github/workflows/node-ci.yml
on:
  workflow_call:
    inputs:
      node-version: { type: string, default: "20" }
    secrets:
      NPM_TOKEN: { required: false }
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ inputs.node-version }}
          cache: npm            # ← 提速点①：内置缓存
      - run: npm ci && npm run lint && npm test -- --ci
```

```yaml
# 2. 服务仓库 .github/workflows/ci.yml（薄壳）
name: CI
concurrency:                     # ← 提速点②：PR 上取消过时的 run
  group: ci-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
on:
  pull_request: { branches: [main] }
jobs:
  ci:
    uses: my-org/.github/.github/workflows/node-ci.yml@v3
    with:
      node-version: "20"
```

```bash
# 3. 量化验证：改造前后各跑三次，取中位数对比
gh run list --workflow=ci.yml --limit 10 \
  --json displayTitle,conclusion,startedAt,updatedAt

# 4. 验证缓存真的命中：在 job 日志里搜 "Cache restored"
#    首次运行必然 miss，第二次起应当 hit —— 第二次仍 miss 说明 key 配错了

# 5. 验证并发组：对同一个 PR 连推两次，
#    第一条 run 应当立刻变成 cancelled，而不是两条并行跑完
```

验证标准要盯三个可观测信号，缺一个就说明某处没配对：**缓存命中**（第二次运行的日志里出现 cache restored，且依赖安装步骤耗时明显下降）、**旧 run 被取消**（连推两次时第一条状态变 cancelled）、**总时长下降**（第 3 步的中位数对比应当能看到量级明显的缩短，devtoollab 给的经验区间是 40%-60%）。

**评估 CI 提速的正确姿势是量中位数而不是看单次，且必须分别确认三个信号**——因为总时长下降可能只来自其中一项，另外两项配错了你却以为都生效了。可复用工作流则要额外验证一次**升级链路**：在中心仓库发一个 v4 tag，确认消费仓库能通过 Dependabot 收到升级 PR 并顺利合入。这条链路跑不通，"单点变更"的收益就不成立。经验阈值：相似流水线达到三个以上仓库时，引入可复用工作流开始划算；低于这个数，维护中心仓库的开销可能还大于收益。

**▌ 对比选型**

| 对比维度 | 可复用工作流 | 复合动作 | 复制粘贴 YAML |
|---|---|---|---|
| 复用粒度 | 整个 job | 一串步骤 | 无 |
| 横向变更 | 改一处发新 tag | 改一处 | N 个 PR |
| 引入成本 | 需建中心仓库 | 低 | 零 |
| 适合场景 | 三个以上同类仓库 | 共享步骤序列 | 单仓库项目 |

选型建议：组织内有三个以上流水线高度相似的仓库，就该把可复用工作流建起来，并按产品方式维护版本与 changelog；只是想共享"装环境—构建—推镜像"这几步，复合动作更轻、更好调试；单个仓库的项目直接写就行，不要为了复用而复用。提速三件套则不分规模，任何项目都建议第一天就配上——它们几乎没有引入成本，却是收益最确定的一笔投入。
