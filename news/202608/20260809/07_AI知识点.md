### 1. 【PagedAttention与连续批处理：用操作系统分页思路把推理吞吐做上去】

> 📍 **导语**: 有一个反直觉的事实：大模型在线服务的瓶颈，很多时候不在算力，而在显存被浪费掉了。传统推理框架给每个请求按"最大可能长度"预留一整块连续显存，用户实际只生成了 200 个 token，剩下的 3800 个 token 的空间就干晾在那里，谁也用不了。真实测量显示，这类系统的 KV Cache 有效利用率常常只有两到四成，也就是说你买的 A100 有一大半显存在给空气发工资。2023 年伯克利团队用一个在操作系统里躺了半个世纪的老办法——虚拟内存分页——把这个问题解决了，那篇论文催生了今天几乎所有人都在用的 vLLM。到了 2026 年，这条路线继续往上长：蚂蚁 Ling-3.0-flash 接入 SGLang HiCache 与 Mooncake 分级缓存架构，长输入场景下首 token 延迟（TTFT）直接降低 60% 到 80% 以上；美团 LongCat-2.0 在五万卡国产集群上跑通万亿参数，靠的也是 PD 分离部署与 KV-cache 切分。理解 PagedAttention 与连续批处理，是理解现代推理引擎为什么长这样的第一课。

---

**🧠 深度解析**

**▌ 它是什么**

PagedAttention 是一种 KV Cache 的显存管理方式：把每个序列的 KV Cache 切成固定大小的小块（block，典型 16 个 token 一块），这些块在物理显存里可以散落在任何地方，再用一张"块表"（block table）记录逻辑块号到物理块号的映射，注意力算子按块表去 gather 数据。连续批处理（continuous batching，也叫 in-flight batching 或 iteration-level scheduling）是与之配套的调度方式：调度器不再等一整批请求全部生成完才换下一批，而是在**每一步解码之后**重新决定这一批里该有谁——完成的序列立刻退出腾出显存，排队的新请求立刻插进来。

它**不是**模型压缩或近似计算。PagedAttention 不改变任何数值结果，同一个 prompt 在开与不开的情况下输出完全一致，它纯粹是内存布局与调度层面的工程改造。它也**不是**"批越大越好"的简单加法——批大了 KV Cache 就吃紧，调度器要在吞吐与单请求延迟之间连续权衡。适用边界要说清楚：在高并发、请求长度差异大的在线服务里收益极大；在单请求离线批量推理、或者所有请求长度都一样的场景里，收益会显著缩水。历史脉络上，Orca（OSDI 2022）先提出了 iteration-level scheduling，Kwon 等人在 SOSP 2023 的 PagedAttention 论文补上了显存侧的另一半，两者合起来才构成今天的标准形态。

**▌ 它解决了什么问题**

先算清楚旧方案的浪费。假设你用一个 13B 模型，把 max_seq_len 设成 4096，那么每接一个请求就要预分配 4096 个 token 的 KV Cache 空间。这里同时存在三种浪费：**内部碎片**（用户只生成 200 token，3896 个槽位空置）、**外部碎片**（请求来来去去后，显存被切得七零八落，剩余总量够但没有足够大的连续块）、以及**预留浪费**（正在生成中、尚未用到的那部分空间无法借给别人）。vLLM 论文测得这类系统的实际 KV 利用率仅 20.4% 到 38.2%。

更糟的是静态批处理带来的**队头阻塞**：一批 8 个请求里有 7 个生成 50 token 就结束了，剩下 1 个要生成 2000 token，那 7 个已完成的槽位得空转 1950 步。GPU 在算，但算的是 padding。

PagedAttention 把浪费压到了 4% 以下，连续批处理消除了队头阻塞。原论文报告的收益是：在相同的延迟约束下，吞吐相比 HuggingFace Transformers 提升 14–24 倍，相比当时最好的 Orca 系统提升 2–4 倍。还有一个附赠好处是**前缀共享**：一百个请求用同一段 system prompt，这段 prompt 的 KV 物理块只存一份，各请求的块表指向同一处，引用计数管理，需要分叉时才写时复制。这在 Agent 场景下尤其值钱，因为 Agent 的每一轮调用都带着同样一大坨工具定义和系统指令。2026 年百度公开的一份全链路优化方案更进一步，把 KVCache 存储压缩到行业平均水平的 14%，长序列推理成本降低 60%。

**▌ 原理拆解**

**第一层：直觉理解。** 想象一家酒店。旧办法是：客人预订时说"我最多可能住 30 天"，前台就把连续的 30 个房间号整段锁死给他，哪怕他住 3 天就走。房间号还必须连号，否则系统认不出来。结果就是酒店明明有大量空房，新客人却因为"找不到连续 30 间"而被拒之门外。PagedAttention 的做法是：房间按天分配，住一天给一间，房间号完全不用连续，前台手里拿一本花名册记着"张三的第 1 天在 305、第 2 天在 712"。这本花名册就是块表。而连续批处理相当于把"每天早上统一办理入退房"改成"随到随办、随走随清"。

**第二层：技术流程拆解。** ① 服务启动时按 `gpu_memory_utilization` 预先把显存切成大量固定大小的物理块，建立空闲块池。② 请求到达，prefill 阶段一次性算出 prompt 的 KV，按需申请若干块并登记进该序列的块表。③ 每一步 decode 生成一个新 token，如果当前最后一块还没写满就直接追加，写满了才向池子申请新块——申请粒度是块而不是整段，所以碎片被限制在"最后一块的未满部分"，期望浪费只有半块。④ 注意力 kernel 执行时，先读块表，把散落的物理块地址收集起来做非连续访存，这一步是 PagedAttention 自定义 CUDA kernel 的核心工作。⑤ 调度器在每个 iteration 重排 batch：完成的序列释放全部物理块回池，等待队列里的新请求按策略入场。⑥ 显存告急时触发抢占，两种策略——把低优先级序列的块 swap 到 CPU 内存，或者干脆丢弃并在需要时重算（recompute），后者在 prompt 短时更划算。关键参数是 `block_size`（太小则块表开销与 kernel 访存开销上升，太大则内部碎片回潮）、`max_num_seqs`（并发上限）与 `max_num_batched_tokens`（单步 token 预算，直接控制 prefill 与 decode 的抢占关系）。

**第三层：核心机制。** 真正的设计洞见是把**逻辑连续性与物理连续性解耦**，这正是虚拟内存的思想内核。一旦解耦，三件此前做不到的事同时变得可能：动态增长（不必预知最终长度）、跨序列共享（copy-on-write 的前缀复用、以及 parallel sampling 时 n 个候选共享同一段 prompt 的物理块）、以及细粒度抢占（可以只换出一部分块）。2026 年的演进沿着"分层"继续走：SGLang HiCache 把不常访问的 KV 块下沉到 CPU DRAM 甚至 SSD，Mooncake 则把 KVCache 做成独立的存算分离池，让 prefill 集群与 decode 集群分开部署、各自按自己的瓶颈扩容——prefill 是算力密集、decode 是访存密集，硬绑在一起必然有一头浪费。所以"分页"这个抽象一旦立住，后面的分级、分离、复用就都是水到渠成的延伸。

**▌ 动手验证**

```python
# pip install vllm
from vllm import LLM, SamplingParams

llm = LLM(
    model="Qwen/Qwen2.5-1.5B-Instruct",
    gpu_memory_utilization=0.85,   # 预留给 KV 块池的显存占比
    max_model_len=4096,
    block_size=16,                 # 每个物理块承载 16 个 token 的 KV
    enable_prefix_caching=True,    # 打开前缀共享，相同 system prompt 只算一次
)

# 故意构造长度极不均匀的请求，观察连续批处理如何避免队头阻塞
prompts = ["用一句话解释注意力机制。"] * 4 + ["写一篇 800 字的散文，主题是雨。"] * 4
outs = llm.generate(prompts, SamplingParams(max_tokens=1024, temperature=0.7))
print([len(o.outputs[0].token_ids) for o in outs])   # 短请求先返回，不等长请求
```

预期：短请求的 token 数远小于长请求，但整批耗时接近"最长那条单独跑"的时间，而非各条时间之和。注意 vLLM 需要 CUDA 环境；把 `enable_prefix_caching` 关掉再跑一次，相同 system prompt 场景下 TTFT 会明显变长，这就是前缀共享的直接体感。

### 2. 【1-bit极限量化：27B模型压到3.9GB塞进手机的代价与边界】

> 📍 **导语**: 2026 年 7 月中旬，加州理工衍生的初创公司 PrismML 放出了一个叫 Bonsai 27B 的模型：基于阿里 Qwen3.6 27B 基座，通过原生 1-bit 量化把 270 亿参数压到约 3.9GB，在 iPhone 17 Pro 上跑出每秒 11 个 token，在 RTX 5090 上每秒 163 个 token，15 项基准测试保留了全精度模型约 90% 的性能，苹果公司正在评估这项技术。几乎同期，腾讯混元 Hy3 这个 295B 的 MoE 旗舰，BF16 权重接近 600GB，1bit 极限量化版 IQ1_M 把它压到 85.5GiB——缩小 6.7 倍，一张 96GB 显卡就能部署。这两个数字放在一起，意味着一件此前被认为不可能的事：模型精度这个维度上还有巨大的水分可以挤，而且挤到只剩一个符号位，模型居然还能用。但"还能用"三个字背后的代价是什么、边界在哪里，才是工程师真正需要搞清楚的部分。

---

**🧠 深度解析**

**▌ 它是什么**

量化（Quantization）是把神经网络权重（有时还包括激活值）从高精度浮点映射到低比特表示的技术。1-bit 量化是它的极限形态：每个权重只用 `{-1, +1}` 两个取值表示，配合分组缩放因子还原幅度信息；稍微宽松一点的 1.58-bit 用 `{-1, 0, +1}` 三值，多出的"0"提供了稀疏能力。这里有一个必须区分的关键概念：**PTQ（训练后量化）**是拿一个训好的模型直接压，成本极低；**原生低比特 / QAT（量化感知训练）**是从预训练阶段就让模型知道自己将来要被压成 1-bit，训练过程中就适应这种约束——Bonsai 用的是后者，这也是它能在 1-bit 下保住 90% 性能的根本原因。

它**不是**剪枝。剪枝是把不重要的参数整个删掉，模型结构变稀疏；量化保留全部参数，只是每个参数的表达精度降低。它也**不是**无损压缩——任何低于 8-bit 的方案都必然有精度损失，问题只在于损失落在哪些能力上。适用边界很清晰：内存受限场景（端侧部署、单卡跑超大模型、显存成本敏感的推理集群）收益巨大；如果你本来显存就够用、追求最后那一两个点的精度，量化是纯亏。历史脉络：GPTQ（2022）用二阶 Hessian 信息做逐列误差补偿，AWQ（2023）发现只要保护约 1% 的显著权重通道就能大幅减小损失，这两个把 4-bit PTQ 变成了工业标配；BitNet b1.58（2024）证明了原生 1.58-bit 训练在一定规模上可以匹配 FP16；2026 年 8 月 4 日挂出的 arXiv:2608.04048《Recurrent Residual Quantization》（NeurIPS 2026 投稿）又提出用递归残差做渐进式多精度表示，让同一份权重可以按需截断成不同比特。

**▌ 它解决了什么问题**

痛点只有两个字：显存。一个 295B 的 MoE 模型 BF16 权重 598GB，意味着你至少要 8 张 80GB 的卡才装得下，还没算 KV Cache。这不是钱的问题，是很多团队根本拿不到八卡机的问题。量化后的账变成这样：Hy3 的 4bit 版本体积 169.9GiB，两张推理卡就能承载；1bit 的 IQ1_M 版本 85.5GiB，单张 96GB 卡搞定。硬件门槛从"八卡服务器"降到"一张卡"，这是数量级的可及性改变。

端侧的账更极端。27B 模型 BF16 要 54GB，任何手机都别想；压到 3.9GB 之后，一台内存 8GB 起步的旗舰手机就能装下，而且是完全离线运行、数据不出设备。

代价呢？公开实测给出了相当诚实的画像。Hy3 的 4bit 版本在 Agent 能力、多语言代码、工具调用等任务上贴近满血模型效果，基本可以放心用；1bit 版本在长文理解、Agent 与代码方向"保持良好，只有小幅回落"——注意这个措辞，它承认了回落。Bonsai 27B 的 90% 性能保留率同样说明还有 10% 的差距。规律是：**知识密集、需要精确记忆细节的任务对量化最敏感**（比如冷门事实问答、精确数值计算），而**依赖模式与流程的任务最耐压**（对话流畅度、代码结构、工具调用格式）。还有一个容易被忽略的正向效应：Hy3 量化版开启 MTP 投机解码后，接受率稳定在 60% 左右，解码速度提升约 50%——模型变小之后，验证阶段变快，投机解码的收益也跟着放大。

**▌ 原理拆解**

**第一层：直觉理解。** 把量化想成把彩色照片印到报纸上。报纸只有黑白油墨（1-bit），但通过网点密度和分区调整曝光，远看依然认得出是谁的脸。关键在于"分区"：如果整张照片只用一个曝光值，暗部和亮部必然有一头糊掉；把照片切成很多小方块，每块单独定一个曝光值（这就是**分组缩放因子**），还原度立刻上一个台阶。1-bit 量化里，符号位负责"这个权重是推还是拉"，分组缩放因子负责"推拉的力度有多大"。而原生 1-bit 训练则相当于：摄影师从按快门的那一刻就知道这张照片将来要印报纸，于是刻意加大反差、避开中间灰调。

**第二层：技术流程拆解。** PTQ 路线：① 准备一个几百条样本的校准集，前向一遍收集各层激活的分布；② 按组（group_size 常取 64 或 128）计算 scale 与 zero_point；③ 执行权重量化；④ 误差补偿——GPTQ 逐列量化，每量化一列就用 Hessian 逆矩阵把引入的误差摊到尚未量化的列上；AWQ 则先按激活幅度找出约 1% 的显著通道，对这些通道做等价缩放变换来保护它们。原生 1-bit / QAT 路线：训练前向时对权重做 `W_q = sign(W) × scale`，反向传播时用 **STE（Straight-Through Estimator，直通估计器）** 把梯度绕过不可导的 sign 函数直接传给一份保留在 FP 精度的"影子权重"，影子权重持续累积微小更新，只在前向时才被二值化——这一招是所有极低比特训练的通用骨架。RRQ 的递归残差思路是：先做一次粗量化得到残差 `R = W − Q₁(W)`，再对 R 量化得到 Q₂，如此叠加，最终 `W ≈ Q₁ + Q₂ + Q₃ + …`，部署时想要几比特就截断到第几级。关键参数是 group_size（越小精度越好但元数据开销越大）与是否保留敏感层高精度（embedding 层、lm_head、以及第一层和最后一层通常不压或少压）。

**第三层：核心机制。** 有两个问题值得深究。其一，**为什么 1-bit 还能 work**。答案是大模型权重存在极高的冗余，而且信息主要编码在**方向**而非精确幅度上：一个权重矩阵乘以向量的结果，很大程度上由各权重的符号模式决定，幅度差异可以由分组缩放因子近似补偿。此外二值化带来一个隐含好处——矩阵乘法退化成加减法，理论上可以省掉乘法器，这是 BitNet 系列真正想要的硬件红利。其二，**量化误差从哪来**。主要来自 **outlier（离群通道）**：LLM 的激活分布里存在少数幅度比其余大出一两个数量级的通道，如果用统一的 scale，这些离群值会把量化范围整个撑开，导致绝大多数正常权重挤在极少数几个量化格子里。AWQ 保护显著通道、SmoothQuant 把激活的离群幅度"搬"到权重侧，本质都是在处理同一件事。这也解释了为什么 PTQ 直接压到 1-bit 会崩而 QAT 不会：QAT 允许模型在训练中主动把权重分布调整成对二值化友好的形态，而 PTQ 只能被动接受既有分布。

**▌ 动手验证**

```python
# pip install transformers bitsandbytes accelerate
import torch
from transformers import AutoModelForCausalLM, BitsAndBytesConfig

name = "Qwen/Qwen2.5-1.5B-Instruct"

def load(cfg=None, dtype=torch.bfloat16):
    m = AutoModelForCausalLM.from_pretrained(
        name, quantization_config=cfg, torch_dtype=dtype, device_map="cuda")
    return m.get_memory_footprint() / 1024**3   # GB

nf4 = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",          # 正态分布优化的 4-bit 数据类型
    bnb_4bit_use_double_quant=True,     # 对量化常数再量化一次，每参数再省约 0.4 bit
    bnb_4bit_compute_dtype=torch.bfloat16,
)
print(f"BF16 : {load():.2f} GB")
print(f"NF4  : {load(nf4):.2f} GB")     # 应约为 BF16 的 1/3~1/4
```

### 3. 【Reranker与后期交互：召回之后靠什么把对的那条排到第一】

> 📍 **导语**: 做 RAG 的人大多有过同一种挫败：明明知识库里有那段话，模型就是没答对。查日志一看，那段话确实被召回了——排在第 17 位，而你只把 top-5 塞进了 prompt。这类失败几乎不会体现在"召回率"指标上，因为召回率说"我找到了"，但决定成败的是"我把它排到第几"。向量检索天生就不擅长精排：query 和文档各自被压成一个几百维的向量，全部交互只发生在最后一次点积，否定词、数字、年份、实体名这些决定性细节在压缩过程中被抹平了。于是搜"2025 年不含税营收"，回来的是"2024 年含税营收"——向量看它们像极了。解决办法是级联：让便宜的模型负责"别漏"，让昂贵的模型负责"排对"。这一层昂贵的模型就是 Reranker，而 ColBERT 代表的"后期交互"则提供了介于两者之间的第三种可能。

---

**🧠 深度解析**

**▌ 它是什么**

Reranker（重排序模型）通常指 **Cross-Encoder（交叉编码器）**：把 query 和候选文档拼成一个序列 `[CLS] query [SEP] document [SEP]` 一起送进模型，让两者在每一层、每个注意力头上充分交互，最后输出一个标量相关性分数。它在检索流水线里是第二级，输入是第一级召回的几十到几百个候选，输出是重新排好序的前几名。

**后期交互（Late Interaction）**是 ColBERT 提出的第三条路：query 和文档各自独立编码，但不压成单个向量，而是保留 **token 级的向量矩阵**；打分时对 query 的每个 token，去文档的所有 token 向量里取最大余弦相似度（MaxSim），再把这些最大值加总。交互发生在最后，但粒度是 token × token。

它**不是** embedding 模型的替代品，而是级联中的下游环节——Reranker 无法凭空找回第一级没召回的内容，所以整条链路的召回率上限由第一级决定。它也**不是**必然带来提升：如果第一级召回质量已经很高、或者 top-k 里根本就没有正确答案，重排只是白白增加延迟。适用边界上，候选数从 100 缩到 5 这类"精挑细选"场景收益最大；对延迟极度敏感（要求端到端 50ms 内）或候选池达到百万级无法逐一打分的场景要谨慎。历史脉络：BERT 时代的 monoBERT、monoT5 奠定了 cross-encoder 重排范式；ColBERT（SIGIR 2020）与 ColBERTv2（2021）提出并优化了后期交互；此后 bge-reranker、jina-reranker、Cohere Rerank 等把它产品化；2026 年 8 月 arXiv 上仍在讨论静态 embedding 在混合检索中的边际价值（arXiv:2608.02112），说明"怎么组合多路信号"依然是活跃问题。

**▌ 它解决了什么问题**

Before：单塔向量检索。文档在离线阶段被编码成一个向量存进向量库，查询时把 query 也编码成一个向量做近似最近邻搜索。这套方案的优势是快到极致——百万级文档毫秒返回，因为文档侧的计算全部离线做完了。代价是**交互被推迟到了不可挽回的地步**：query 向量和文档向量各自形成时，都不知道对方是谁。文档编码器必须把整段话压成一个"通用摘要向量"，它不可能预知用户会问哪个细节。

After：三级级联。第一级用 BM25（稀疏，擅长精确词匹配、专有名词、编号）+ 稠密向量（擅长同义改写、跨语言）并行召回，各取 top-100；第二级用 RRF（Reciprocal Rank Fusion）把两路结果融合成一个列表；第三级用 cross-encoder 对这 100 条逐一精算，取 top-5。公开基准上的效果差距相当明确：BEIR 这个跨 18 个数据集的零样本检索评测里，BM25 的平均 nDCG@10 约在 0.44 一线，主流稠密双塔在 0.45–0.50 区间，而叠加 cross-encoder 重排后普遍能再提 5 到 10 个点，在部分子集上把 BM25 的表现直接翻上一个台阶。

代价也很实在：双塔在线只需一次向量编码加一次 ANN 查询，通常个位数毫秒；cross-encoder 要对 k 个候选各做一次完整前向，k=100 时即便用小模型也要几十到几百毫秒，而且**无法离线预计算**——因为分数依赖于具体的 query。ColBERT 正是在这个缝隙里找位置：文档侧的 token 向量可以离线算好，在线只需算 query 侧再做 MaxSim，速度接近双塔，精度接近 cross-encoder，代价是索引体积膨胀（每个文档要存几百个向量而非一个），ColBERTv2 用残差压缩把这部分成本压下去了一大截。

**▌ 原理拆解**

**第一层：直觉理解。** 招聘流程。第一级像 HR 用关键词过简历（BM25），"必须写着 Python"——快，但会漏掉写了"PyTorch 工程经验"却没写 Python 的人。第二级像用一个岗位画像向量做粗匹配（双塔）——能理解同义，但把每份简历压成一句话总结，细节全丢。第三级是面试官逐份精读，把 JD 的每条要求和简历的每段经历对照着看（cross-encoder）——最准，但一天只能看几十份。ColBERT 是"逐条打勾"：把 JD 拆成十条要求，每条去简历里找最对应的那一句，打个分，再把十个分加起来——比总结向量细得多，又不用真的面试。

**第二层：技术流程拆解。** ① **混合召回**：query 同时走 BM25 与向量库，各取 top-100。② **融合**：RRF 的公式是 `score(d) = Σ_r 1/(k + rank_r(d))`，其中 k 常取 60。它只看排名不看原始分数，因此天然免疫"BM25 分数和余弦相似度不在一个量纲"的问题，这是它比加权求和更常用的原因。③ **去重与截断**：同一文档的多个分块合并，保留最高分那块或做窗口扩展。④ **精排**：cross-encoder 对每个 (query, doc) 对做一次前向，输出 logit 作为分数。为了控延迟，这一步通常批量化并用小模型（bge-reranker-base 只有 278M 参数）。⑤ **组装 prompt**：取 top-3 到 top-5。关键参数是召回 k（太小则重排无米下锅，太大则延迟爆炸，经验值 50–100）、RRF 的 k（越大越平滑，越小越信任头部）、以及重排后的 n（受生成模型上下文预算约束）。

**第三层：核心机制。** 三种范式的本质区别可以用一句话概括：**交互发生在哪一层，以及能不能离线算**。双塔的交互发生在最后一层之后（一次点积），因此文档侧完全可预计算，代价是表达力被压缩到一个向量的信息容量里。Cross-encoder 的交互发生在**每一层的每个注意力头**，query 的每个 token 都能读到文档的每个 token 并反复迭代，表达力最强，代价是完全不可预计算——换个 query 就要全部重算。ColBERT 的后期交互是精妙的折中：它把交互推到最后但保留了 token 粒度，所以文档侧仍可预计算，而 MaxSim 这个算子在语义上对应"这个查询词在文档里有没有找到最好的落点"，这恰好捕捉了词级精确匹配的信号——正是纯向量最欠缺的那一块。理解了这个谱系，选型就不再是玄学：**你能接受多大的在线计算量，就往交互谱系上走多远**。

**▌ 动手验证**

```python

from rank_bm25 import BM25Okapi

docs = [
    "公司2024年含税营业收入为12.3亿元。",
    "公司2025年不含税营业收入为15.8亿元。",
```

### 4. 【E-GRM动态CoT触发：让奖励模型学会该快则快该深则深】

> 📍 **导语**: 一个很少被摆到台面上的效率黑洞：在 RLHF / RLVR 的训练循环里，奖励模型的调用次数是策略 rollout 数的数倍，它的延迟直接卡住整条流水线。而 2026 年主流的生成式奖励模型（GRM）为了判得准，会先走一遍完整的思维链再给分——问题是，判断"1+1=2 这个回答对不对"也要先来一句"Let's think step by step"，这钱花得实在冤枉。腾讯混元团队发表于 ACL 2026 的 E-GRM 给出了一个漂亮的解法：先用不同温度并行短解码 5 次，看这 5 个答案一致不一致；一致说明模型心里有数，直接出分；不一致才触发深度推理。在 RM-Bench、RMB、RewardBench 三个基准上，约 58% 的样本被智能路由到"直答"，**延迟降低 62%，准确率不降反升**。准确率为什么会升，是这个方法里最值得琢磨的一层。

---

**🧠 深度解析**

**▌ 它是什么**

先厘清两个层次。**GRM（Generative Reward Model，生成式奖励模型）**指的是：不再给基座模型接一个标量回归头去预测分数，而是让它以生成文本的方式输出评判——可以是打分、可以是排序、可以是一段批评意见。它的好处是能复用基座的全部推理能力，还能给出可读的判断理由；带 Chain-of-Thought 之后，在数学推理、代码生成这类需要真正验算的领域效果显著。**E-GRM** 是在 GRM 之上加的一层调度机制，核心叫"动态 CoT 触发"：用一个极便宜的探测步骤判断当前样本值不值得走 CoT。

它**不是**模型蒸馏或换小模型——模型本身没变，变的是同一个模型在不同样本上分配多少推理算力。它也**不是**多模型路由（把简单题丢给小模型、难题丢给大模型），而是**同一模型的两种推理模式**之间切换，因此不需要额外维护第二套权重，工程侵入性极低。适用边界：奖励模型服务、RLVR 训练中的在线打分、LLM-as-a-Judge 批量评测这类"同一个模型要被调用海量次、且样本难度分布不均"的场景收益最大；如果你的样本难度高度集中在中间地带，探测步骤自身的成本就摊不回来。历史脉络上，这条线从 InstructGPT 时代的标量 RM 出发，经过 LLM-as-a-Judge、带自我批评的 GRM，走到了 2026 年的"自适应推理预算"阶段，与 test-time scaling 恰好是一体两面——后者说"多花算力换质量"，前者说"该花的时候才花"。

**▌ 它解决了什么问题**

Before：一刀切。所有 (prompt, response) 对进来都走完整 CoT，简单样本和困难样本消耗同等算力。在 RL 后训练场景里这个开销尤其致命，因为奖励模型处在训练循环的关键路径上——策略每生成一批 rollout 就要等奖励模型全部打完分才能算优势、更新参数，奖励模型慢一倍，整个训练就慢一大截。

After：E-GRM 的三基准实测给出了明确数字——约 58% 的样本被路由到直答，**延迟降低 62%**，同时**准确率还有提升**。

准确率为什么会升？这是最反直觉也最有价值的一点。一般认为跳过思考只会让判断变差，但实际上简单样本上强行要求 CoT 会引发**过度思考（overthinking）**：模型本来一眼就知道答案是对的，被逼着写一段推理，写着写着给自己讲出了一个似是而非的反例，最后把正确判断推翻了。这种"想多了想歪了"在评判类任务上非常常见，因为评判往往依赖直觉性的整体判断而非逐步演绎。跳过 CoT 反而保住了这部分样本的正确率。这一观察与 2026 年 8 月 arXiv 上另一项工作形成呼应——arXiv:2608.02089 提出了一个"可观测性阶梯"来衡量推理摘要到底泄露了多少真实推理过程，同样指向"思维链的长度与它的真实信息量并不成正比"这个判断。

**▌ 原理拆解**

**第一层：直觉理解。** 老中医看病。望闻问切一眼能定的，直接开方；拿不准的才让你去做一堆检查。难点在于"怎么知道自己拿不准"。E-GRM 的办法很朴素：找五个学徒，各自独立说个结论，不许商量。五个人说的一样，那基本就是这个了；五个人各说各话，说明这病确实棘手，得请专家会诊。妙处在于——问五个学徒的成本，远低于直接请专家会诊一次。

**第二层：技术流程拆解。** ① 输入一个 (prompt, response) 对。② 用**不同温度参数并行解码 5 次**，注意这一步只要短答案（比如直接输出分数或"更好的是 A/B"），不要推理链，因此每次解码只有寥寥几个 token。③ 统计这 5 个答案的一致性，可以用多数票占比，也可以用答案分布的熵。④ 一致性高于阈值 → 直接采纳多数答案，流程结束。⑤ 一致性低于阈值 → 触发完整 CoT 路径，让模型逐步分析后再给分。⑥ 输出最终分数。关键参数有三个：**并行解码次数 k**（5 是判别力与成本的经验折中，太少信号噪声大，太多边际收益递减）、**温度**（太低则五次输出必然雷同、探测失效，太高则连简单题也会分歧）、**一致性阈值**（这是整条效率—精度曲线的旋钮，调高则直答比例低、省得少但保守，调低则省得多但可能在中等难度样本上误判）。工程上一个重要细节：这 5 次短解码可以塞进同一个 batch 并行执行，在 GPU 上几乎是一次前向的成本，这才是它划算的根本原因——**探测的边际成本远低于一条长 CoT**。

**第三层：核心机制。** 底层原理是**把自洽性当作不确定性的免费代理**。Self-Consistency（Wang 等 2022）原本的用法是：多次采样，投票选出现最多的答案，以此提升准确率。E-GRM 把它反过来用——投票结果本身它不一定要，它要的是**投票的分散程度**。分散度高说明模型在这个样本上的输出分布是平的，也就是没把握；分散度低说明分布尖锐，模型很确定。这个信号是采样过程的副产品，不需要额外训练任何东西。

沿着这条思路可以看到 2026 年一整片相关工作在做同一件事：让模型输出的不只是一个点估计，而是一个能反映把握程度的分布。COLM 2026 的《Start Classifying: Categorical Critics for LLM Reinforcement Learning》（arXiv:2608.02181，2026-08-03）就把 RL 里的 critic 从回归改成分类，理由正是分类头天然给出一个概率分布，比一个标量回归值携带了多得多的不确定性信息。而语义熵那条线走的也是同一个方向，只是把不确定性建在语义等价类上而非表面 token 上。可以说，**"让模型知道自己不知道"已经从一个安全议题，变成了一个效率议题**——一旦有了可靠的置信度，你就能据此分配算力。

**▌ 动手验证**

```python
# pip install transformers torch
import torch
from collections import Counter
from transformers import AutoTokenizer, AutoModelForCausalLM

name = "Qwen/Qwen2.5-1.5B-Instruct"
tok = AutoTokenizer.from_pretrained(name)
model = AutoModelForCausalLM.from_pretrained(name, torch_dtype=torch.bfloat16, device_map="auto")

def probe(question, k=5, temp=0.9):
    """并行短解码 k 次，返回答案一致性（多数票占比）"""
    msg = [{"role": "user", "content": question + "\n只回答一个词，不要解释。"}]
    ids = tok.apply_chat_template(msg, add_generation_prompt=True, return_tensors="pt").cuda()
    out = model.generate(ids, max_new_tokens=8, do_sample=True, temperature=temp,
                         num_return_sequences=k)                      # 同一 batch 并行 k 次
    ans = [tok.decode(o[ids.shape[-1]:], skip_special_tokens=True).strip() for o in out]
    top = Counter(ans).most_common(1)[0][1]
    return top / k, ans

for q in ["1+1等于几？", "把一根绳子对折三次后剪两刀，得到几段？"]:
    c, a = probe(q)
    print(f"一致性={c:.0%}  → {'直答' if c >= 0.8 else '触发CoT'}  样本={a}")
```

预期：简单题一致性 100%，走直答分支；带陷阱的题目一致性明显下降，触发 CoT 分支。注意温度设为 0 会让一致性恒为 100%、探测失效，必须采样；k 次生成用 `num_return_sequences` 在同一 batch 里完成，这样才能体现"探测很便宜"这一前提。

**▌ 对比选型**

| 对比维度 | E-GRM 动态触发 | 固定 CoT 的 GRM | 标量奖励模型 |
|---------|---------------|----------------|-------------|

| 公开收益 | 延迟降 62% | 基线 | 最快但判别弱 |

| 接入成本 | 无需改权重 | 需 CoT 数据训练 | 需训练回归头 |

### 5. 【视觉Token压缩：一张图凭什么吃掉大模型几千个token】

> 📍 **导语**: 你上传一张 1080p 的截图给多模态模型，它可能要花掉三千到八千个 token 才"看"完这张图——比一整页密密麻麻的文字还贵。这在偶尔问一句"图里是什么"的时候无所谓，但 2026 年 Agent 开始接管屏幕操作之后，问题彻底变了性质：一个 GUI Agent 完成一次订票要连续看几十屏截图，一个视频理解任务按 1 fps 采样十分钟就是 600 帧。视觉 token 挤占的是与文本共享的同一个上下文窗口，而注意力还是平方复杂度。于是"一张图到底该值多少 token"从一个学术问题变成了产品能不能跑起来的问题。这个领域的解法分成三条清晰的技术路线，各有各的死穴，而 2026 年的主流做法是把它们叠着用。

---

**🧠 深度解析**

**▌ 它是什么**

要先理解视觉 token 从哪来。VLM（视觉语言模型）的标准结构是三段式：图像先被切成固定大小的 patch（常见 14×14 像素一块），经 ViT 编码成一串特征向量；这串特征通过一个 **connector（连接器，也叫 projector 或 resampler）**变换到 LLM 的 hidden 维度，成为"视觉 token"；最后与文本 token 拼在一起送进 LLM。视觉 token 压缩，就是在这个 connector 前后想办法减少这串 token 的**个数**。

它**不是**降低输入分辨率。降分辨率是在像素层面丢信息，小字直接糊掉；压缩是在特征层面做聚合或筛选，理论上保留了更高分辨率下提取到的信息。它也**不是** KV Cache 量化——量化压的是每个 token 占多少比特，压缩减的是 token 的数量，两者正交、可以叠加。适用边界必须讲清楚：**文档 OCR、表格识别、图表读数、GUI 元素定位这类任务对 token 数极度敏感**，压过头会直接看不清；而自然场景描述、图像整体分类、情感判断这类任务的容忍度高得多，压掉 80% 也几乎不掉点。历史脉络：BLIP-2（2023）的 Q-Former 用 32 个可学习 query 把任意图强压成 32 个 token；LLaVA 走极简路线，用一个 MLP 直接投影，336×336 输入产生 576 个 token；NaViT（2023）提出 patch n' pack，让模型原生支持任意分辨率与长宽比；Qwen-VL 与 InternVL 系列则把动态分辨率与 2×2 pixel shuffle 组合成了今天最常见的配方。

**▌ 它解决了什么问题**

先把账算清楚。336×336 的图，patch 大小 14，切出 24×24 = **576 个 token**。这还是低分辨率。换成动态分辨率支持 1080p，图会被切成多个 tile 分别编码，token 数轻松涨到 **3000–8000**。视频更夸张：1 fps 采样十分钟视频是 600 帧，即便每帧只留 64 个 token 也是 38400 个 token，一个 128K 上下文的模型光看视频就用掉三成窗口。

Before 的三个后果非常具体：其一，**上下文被挤占**，留给对话历史和工具定义的空间不够；其二，**首 token 延迟飙升**，prefill 阶段要处理几千个视觉 token，用户点了发送之后要干等好几秒；其三，**成本按 token 计费**，一张图的钱抵得上一篇长文。

After 的三条路线各有其量化收益：**pixel shuffle** 把 2×2 相邻 patch 在通道维拼接，一步把 token 数降到 1/4，且是纯粹的空间重排、理论上不丢信息；**Q-Former / Perceiver Resampler** 直接把 token 数固定成 32 或 64，与输入分辨率彻底解耦，压缩比可以做到几十倍；**注意力剪枝**（FastV 这类）在 LLM 的浅层统计每个视觉 token 收到的注意力，把低分的直接丢弃，公开结果显示在层 2 之后剪掉一半视觉 token，主流基准上的掉点普遍控制在 1–2 个点以内，且**完全不需要重新训练**——这一点对已经部署的模型极具吸引力。

**▌ 原理拆解**

**第一层：直觉理解。** 让你向电话那头的人转述一张照片。你不会逐像素念，会说"左上角一个穿红衣服的人，中间一张木桌，桌上有三个杯子"。三条技术路线对应三种转述策略：**合并相邻的**（把地图缩小一档，四个小格并成一个大格，细节少了但布局还在）、**挑重要的**（拿荧光笔在照片上划重点，没划到的部分之后不再提）、**按固定表格填**（不管什么照片，都回答同样 32 个问题："主体是什么""背景是什么""有几个人"——输出长度恒定，但表格里没问到的信息就永远丢了）。

**第二层：技术流程拆解。** ① 图像 → patch embedding → ViT 编码，得到 N 个视觉特征。动态分辨率方案在这一步就开始省：按图像实际尺寸决定切几个 tile，小图少切、大图多切，而不是统统 resize 到固定大小。② connector 压缩，三条路线的具体做法：**(a) Pixel shuffle / pooling**——把空间上相邻的 2×2 共 4 个 patch 特征在通道维度拼接成 1 个，通道数变 4 倍，token 数变 1/4，无参数、无需学习，纯张量重排。**(b) Q-Former / Resampler**——设置 M 个可学习的 query 向量，通过 cross-attention 从 N 个视觉特征里"提问式"抽取信息，输出恒定 M 个 token，M 与 N 无关。**(c) 训练后剪枝**——先让所有视觉 token 进入 LLM，在第 K 层（FastV 取 K=2）统计每个视觉 token 从后续文本 token 处收到的注意力总和，保留 top-p、丢弃其余，后面各层不再计算它们。③ 线性投影到 LLM hidden 维度。④ 与文本 token 序列拼接。关键参数：压缩比、剪枝发生的层号（太浅则视觉信息还没被 LLM 聚合、误剪风险高；太深则前面几层的算力已经花掉、省不下多少）、以及是否额外保留一张全图缩略图（thumbnail）来提供全局视野——多 tile 方案里如果不给缩略图，模型容易只见树木不见森林。

**第三层：核心机制。** 为什么视觉 token 能压而文本 token 不能？因为**信息密度差了一个量级**。一个文本 token 是经过人类语言千百年压缩优化的产物，几乎每个都携带实质语义；而相邻的图像 patch 高度冗余——一整片天空、一面白墙，几十个 patch 说的是同一件事。研究反复观察到一个现象：进入 LLM 的前几层之后，绝大部分注意力质量迅速集中到少数视觉 token 上，其余 token 收到的注意力接近于零。这个经验规律正是免训练剪枝能生效的全部依据。

核心取舍则是**压缩比与细粒度空间定位之间的张力**。Q-Former 这类固定长度方案在"图里第三行写了什么字""按钮在左边还是右边"这类任务上会明显退化，因为 cross-attention 把空间排布彻底打散了，32 个 query 向量里没有任何显式的坐标信息。Pixel shuffle 完整保留了空间排布（第 i 个输出 token 就对应原图第 i 个 2×2 区域），代价是压缩比被死死钉在 4 倍，想再压就得再来一次 pixel shuffle，而 4×4 合并会让小字直接不可读。这就是为什么 2026 年的主流配方是**三者叠加**：动态分辨率负责"信息量按需给"，pixel shuffle 负责"固定 4 倍无损重排"，浅层剪枝负责"按内容动态再砍一刀"——每一层各解决一个维度的冗余。

**▌ 动手验证**

```python
# pip install transformers qwen-vl-utils accelerate

from PIL import Image

    proc.image_processor.min_pixels, proc.image_processor.max_pixels = lo, hi
```

### 6. 【LoRA之后：DoRA、PiSSA与LoRA+各修好了低秩微调的哪一处】

> 📍 **导语**: LoRA 早就是微调的默认选项了，但只要你认真做过对比实验，大概都遇到过同一个尴尬：LoRA 跑出来的效果，总是比全参微调差那么两三个点，而且那两三个点怎么调超参都补不回来。很长一段时间里，这个差距被归因于"秩太低、容量不够"，解法是把 r 从 8 调到 64 再调到 128——结果往往是显存涨了、效果没涨。2024 年到 2026 年间集中出现的一批工作给出了完全不同的诊断：**瓶颈不在容量，在优化动力学**。LoRA+ 说两个矩阵的学习率不该一样，PiSSA 说初始化选错了子空间，DoRA 说权重更新的两个自由度被绑死了，rsLoRA 说缩放因子的量纲从一开始就写错了。四篇论文各修一处，互不冲突，而且 peft 库里全都只是改一两行参数的事。搞清楚它们各自在修什么，比盲目调 r 有用得多。

---

**🧠 深度解析**

**▌ 它是什么**

LoRA（Low-Rank Adaptation）的做法是：冻结预训练权重 W₀，只训练一个低秩增量 ΔW = BA，其中 B 是 d×r、A 是 r×k，秩 r 远小于 d 和 k；前向计算为 `h = W₀x + (α/r)·BAx`。训练完可以把 BA 加回 W₀，推理时零额外开销。

四个变体各改一处：**LoRA+** 给 A 和 B 设不同学习率，`η_B = λ·η_A`，论文建议 λ 取 16 量级。**PiSSA** 换初始化——对 W₀ 做 SVD，用前 r 个主奇异值与奇异向量初始化 A、B，剩余部分作为冻结残差。**DoRA** 把权重分解成幅度与方向两部分，`W = m · V/‖V‖`，只对方向 V 施加低秩更新，幅度 m 单独训练一个向量。**rsLoRA** 把缩放因子从 α/r 改成 α/√r。

它们**不是**互相替代的竞品，而是正交的修补，可以叠加使用。也**不是**"参数更少所以必然更弱"——这几篇工作的共同贡献恰恰是证明了差距来自训练过程而非表达能力上限。适用边界要讲清楚：指令微调、风格适配、领域术语适配这类"调整已有能力的表达方式"的任务，LoRA 系列表现优秀；而**注入大量全新知识**（比如让模型学会一门它完全没见过的语言、或做大规模继续预训练），低秩增量天然吃力，该上全参就得上全参。历史脉络：Hu 等 2021 提出 LoRA；2023 年 QLoRA 把基座压到 4-bit，让 65B 模型在单张 48GB 卡上可调，微调门槛塌方式下降；2024 年 LoRA+、DoRA、PiSSA、rsLoRA 密集出现；到 2026 年，这些变体已经和量化（QDoRA）、MoE（每个专家挂一套 LoRA）深度融合进主流训练栈。

**▌ 它解决了什么问题**

先看 LoRA 本身解决的问题，账很直白。全参微调一个 7B 模型：BF16 权重 14GB + 梯度 14GB + AdamW 的一阶二阶动量各 28GB（FP32）≈ **84GB 起步**，单张 A100 都塞不下。LoRA 只有 ΔW 有梯度和优化器状态，可训练参数常见占比 0.1%–1%，显存直接掉到十几 GB；QLoRA 再把基座量化到 4-bit，65B 模型单卡可调。这是从"必须有八卡机"到"一张消费卡"的门槛坍塌。

但代价就是那两三个点。四个变体公开报告的收益如下：**DoRA** 论文在 LLaMA 系列的常识推理套件上，7B 规模比 LoRA 高约 3.7 个点、13B 高约 2.9 个点，在 LLaVA 的视觉指令微调上也稳定占优，而且在**低秩下优势最明显**——r=4 时 LoRA 已经明显掉队，DoRA 还能顶住。**PiSSA** 论文报告在 GSM8K 数学任务上，同样的 r 下比 LoRA 有大幅提升（LLaMA-2-7B 从四十出头提到五十以上量级），且收敛曲线在前几百步就明显分开。**LoRA+** 在同等训练成本下报告约 1%–2% 的性能提升与最高约 2 倍的收敛加速，且不增加任何参数量——它改的只是 optimizer 的参数分组。**rsLoRA** 解决的是另一类问题：用原始 α/r 缩放时，r 越大缩放越小，导致增大 r 反而学不动，这解释了很多人"调大 r 没效果"的困惑；换成 α/√r 之后，大 r 才真正开始兑现容量优势。

**▌ 原理拆解**

**第一层：直觉理解。** 把 LoRA 想成给一台已经调校好的机器外挂一组小旋钮。三个变体各自发现了一个安装缺陷。**PiSSA 的发现**：这组旋钮初始时接在随机位置上（A 高斯初始化、B 全零），训练前期大量步数都花在"把旋钮挪到有用的传动轴上"这件事上——不如一开始就把它们直接焊在机器最主要的几根主轴（SVD 主奇异方向）上。**LoRA+ 的发现**：这两个旋钮天生不对称（一个从零开始、一个不是），却被拧以同样的速度，其中一个实际上一直转得不够——该给它更大的传动比。**DoRA 的发现**：调整一台机器本来有两个独立自由度——"往哪个方向调"和"调多大力"，LoRA 只提供了一个混在一起的旋钮，两个自由度被绑死了，应该把力度单独拆成一个旋钮。

**第二层：技术流程拆解。** 基础 LoRA：A 用 Kaiming 或高斯初始化，B 初始化为全零，保证训练起点 `ΔW = BA = 0`，模型行为与预训练完全一致。各变体的具体改动：① **LoRA+**：在构造 optimizer 时把 A、B 分成两个 param group，给 B 组的 lr 乘以 λ（16 是论文的经验推荐，实践中 8–32 都合理）。② **PiSSA**：对每个目标权重矩阵做 SVD 得到 `W₀ = UΣVᵀ`，取前 r 个分量构造 `A = √Σ_r · V_rᵀ`、`B = U_r · √Σ_r`，冻结残差 `W_res = W₀ − BA`；训练起点同样等价于原模型，但梯度从第一步起就作用在主成分子空间上。③ **DoRA**：把权重写成 `W = m · (W₀ + BA)/‖W₀ + BA‖_c`，其中下标 c 表示按列做范数归一化，m 是一个长度为列数的可训练向量；这样"方向"由低秩项负责、"幅度"由 m 负责，两者独立更新。④ **rsLoRA**：缩放因子 α/r → α/√r。关键参数：**r**（8–64 是主流区间，配 rsLoRA 后大 r 才值得试）、**α**（惯例设成 2r）、**target_modules**（只挂 q_proj/v_proj 是老习惯，实践反复验证挂上全部线性层——含 k、o、gate、up、down——效果明显更好，代价是可训练参数翻几倍但绝对量仍然很小）、**lora_dropout**（小数据集上 0.05–0.1 有用）。

**第三层：核心机制。** DoRA 的理论依据是全文最漂亮的一段实证。作者把全参微调与 LoRA 的权重更新分别做幅度—方向分解，然后画出两者变化量的散点图：**全参微调呈现明显的负相关模式**——要么幅度改动大而方向改动小，要么方向改动大而幅度改动小，两者被独立地按需调节；而 **LoRA 的幅度与方向变化几乎正相关地同步上升**，说明它根本没有独立调节这两者的手段，只能"一起动"。DoRA 把它们显式解耦之后，散点图的形态立刻贴近全参微调。这是一个"先诊断再开药"的典范。

PiSSA 的机制则是**初始化决定了低秩子空间的搜索起点**。LoRA 的 BA 从零出发，梯度需要很多步才能把这个低秩子空间转到有用的方向上，而且不保证转得到最优的那个；PiSSA 直接从 W₀ 的主奇异子空间起步——那本来就是这个权重矩阵中能量最集中的方向——相当于跳过了整段搜索。LoRA+ 的依据来自无穷宽网络的尺度分析：由于 A、B 在初始化上不对称，若用同一学习率，B 的更新量在特征学习（feature learning）意义下会系统性偏小，导致有效学习率失配，这个失配随模型宽度增大而恶化，所以模型越大 LoRA+ 越有用。三者互不冲突，peft 库里可以同时打开。

**▌ 动手验证**

```python
# pip install peft transformers
from transformers import AutoModelForCausalLM
from peft import LoraConfig, get_peft_model

base = "Qwen/Qwen2.5-0.5B-Instruct"
targets = ["q_proj","k_proj","v_proj","o_proj","gate_proj","up_proj","down_proj"]

cfgs = {
    "LoRA":  LoraConfig(r=16, lora_alpha=32, target_modules=targets),
    "rsLoRA":LoraConfig(r=16, lora_alpha=32, target_modules=targets, use_rslora=True),
    "DoRA":  LoraConfig(r=16, lora_alpha=32, target_modules=targets, use_dora=True),
    "PiSSA": LoraConfig(r=16, lora_alpha=32, target_modules=targets,
                        init_lora_weights="pissa"),   # 首次加载会跑 SVD，稍慢
}
for name, cfg in cfgs.items():
    m = get_peft_model(AutoModelForCausalLM.from_pretrained(base), cfg)
    t = sum(p.numel() for p in m.parameters() if p.requires_grad)
    a = sum(p.numel() for p in m.parameters())
    print(f"{name:7s} 可训练 {t/1e6:6.2f}M / 总计 {a/1e6:7.2f}M = {t/a:.2%}")

# LoRA+ 不是 config 项，而是 optimizer 分组：
# groups = [{"params": A_params, "lr": 1e-4}, {"params": B_params, "lr": 16e-4}]
```

预期：四者可训练参数占比均在 1% 上下，DoRA 因多出幅度向量 m 而略高一点点。PiSSA 初始化时会对每个目标矩阵做一次 SVD，模型越大越慢，属正常现象；注意 PiSSA 训练完保存时要用 `save_pretrained(..., path_initial_model_for_weight_conversion=...)` 做转换，否则残差部分对不上。

| 对比维度 | LoRA | DoRA | PiSSA |
|---------|------|------|-------|
| 修补点 | 基线 | 解耦幅度与方向 | 主奇异子空间初始化 |
