# 开发语言

### 1. 【Python 3.14 模板字符串 t-strings 与实验性 JIT 编译器落地，注入防护与运行提速兼得】

**导语**：Python 3.14 于 2025 年 10 月正式发布，并在 2026 年 8 月推进到 3.14.7 维护版。本次最值得关注的语言层变化有两点：其一是模板字符串字面量 t-strings（PEP 750），它把"字符串构造"从即时渲染的普通字符串升级为可拦截、可改写的模板对象，为 SQL/XSS/Shell 注入防护打开全新思路；其二是实验性 JIT 默认开启、尾调用解释器加入，让 CPU 密集型脚本在中位基准上获得 12%–18% 的提速。对 Web 后端与 AI 工具链的迁移影响相当温和，几乎不需要破坏性改动，属于"渐进式红利"，新项目现在就可以把 3.14 作为默认版本。

**它是什么**：Python 3.14 由 Python 软件基金会（PSF）发布。核心新特性包括：模板字符串字面量 t-strings（PEP 750）、延迟注解求值（PEP 649，用更优雅的方式取代 3.10 的字符串注解）、子解释器进入标准库（PEP 734）、尾调用解释器（在 Clang 19 及以上构建时，pyperformance 几何均值快 3%–5%）、以及默认开启的实验性 JIT（x86-64/ARM64 下中位提速 12%–18%）。此外，签名体系从 PGP 切换到 Sigstore（PEP 761），并首次提供官方 Android 二进制。需要强调的是，自由线程构建在 3.14 中正式从实验转为受支持（PEP 779），但本篇聚焦语言可见特性，而非 GIL 本身。与 3.13 相比，3.14 在语言表面改动克制，真正的价值落在"安全构造"与"解释器性能"两条线上。

**解决什么**：字符串注入（SQL 注入、XSS、Shell 注入）长期因 f-string 即时渲染而难以在构造期拦截——值在拼进字符串的同时就被固化，安全处理器无从介入；注解在装饰器执行时就立即求值，经常引发循环引用与 import 副作用报错，尤其在大型框架的元类与装饰器链中尤为痛苦。t-strings 让模板在渲染前保留"静态片段 + 插值"两部分，可被自定义安全处理器改写或参数化，把注入风险挡在字符串诞生之前；延迟注解把求值推迟到真正被读取时才发生，消除了大量 import-time 的崩溃。JIT 与尾调用解释器则直接降低了解释执行的热点开销，让纯 Python 的计算脚本不再那么"慢"。

**原理拆解**：t-string 的语法与 f-string 完全一致，但返回的不是 str，而是一个 Template 对象：
```python
name = "alice"
q = t"SELECT * FROM users WHERE name = {name}"
# q 是 Template，保留了静态片段与插值值两部分
def safe_sql(t):
    sql = t.parts[0]          # 静态 SQL 骨架
    params = list(t.values)   # 插值值，单独传递
    return sql, params        # 交给驱动做参数化绑定
```
延迟注解方面，函数的 `__annotate__` 改为返回一个可延迟调用的函数，mypy/pyright 按需求值而非装饰即求。JIT 采用复制式（copy-and-patch）技术，在热点字节码上生成机器码，无需引入 LLVM 之类重型依赖，因此分发体积与启动开销都可控。

**动手验证**：先装好 3.14.7：
```bash
pyenv install 3.14.7
python3.14 -c "name='alice'; q=t'Hi {name}'; print(type(q).__name__)"  # 输出 Template
python3.14 -m test -m test_tstrings   # 跑官方 t-strings 测试套件
```
对比 3.13：在同一段 CPU 循环上用 pyperformance 测速，开启 JIT（`PYTHON_JIT=1`）观察 3%–18% 的提升；再用 `python3.14 -c "import sys; print(sys._is_gil_enabled())"` 确认当前构建形态（标准版为 True，自由线程版为 False）。建议把关键依赖先在 3.14 下跑一轮测试，确认无行为偏移后再切默认版本。

**对比选型**：
| 方案 | 注入防护 | 运行时开销 | 成熟度 |
|------|----------|------------|--------|
| f-string + 手动转义 | 靠人工经验 | 低 | 高 |
| t-strings（PEP 750） | 可在构造期拦截 | 低 | 语法稳定，处理器生态待建 |
| ORM 参数化 | 强 | 中 | 高 |

三种方案并非互斥：t-strings 更适合在轻量工具与脚本里做"构造期可审计"的字符串拼装，正式业务仍建议配合 ORM 参数化。综合来看，3.14 的 t-strings 让"安全地拼字符串"第一次成为语言级能力，值得在新项目中逐步采用。

### 2. 【Go 1.27 泛型方法终于落地，json/v2 与后量子加密入标准库】

**导语**：Go 1.27 于 2026 年 8 月按期发布，最大亮点是开发者等待了整整四年的泛型方法（issue #77273）终于落地——方法现在可以声明属于自己的类型参数。配合 encoding/json/v2 全新 JSON 包、crypto/mldsa 后量子签名、uuid 等新标准库，以及正式可用的 Goroutine 泄漏分析，这一版被称作"工具箱大换血"。对存量代码几乎零破坏，因为它继续坚守 Go1 兼容性承诺，绝大多数现有程序无需任何修改即可编译运行，是典型"加能力不加负担"的版本。

**它是什么**：Go 1.27 由 Go 团队发布，距离 1.26 正好半年。语言层可见变化主要有三处：泛型方法（方法可携带类型参数）、函数类型推断泛化、结构体字面量字段选择器放宽。标准库新增 encoding/json/v2（API 与性能全面重写的 JSON 包）、crypto/mldsa（ML-DSA 后量子数字签名，对应 NIST FIPS 204）、uuid、以及实验性 simd。运行时层面，小型对象分配提速最多 30%，goroutineleak 分析正式可用。工具链新增 go doc pkg@version、go fix modernizers、go mod tidy 自动合并 require 等，整体让"半年一更"的 Go 在表达力与安全性上同时前进一步。

**解决什么**：过去泛型只能加在函数与类型上，容器类型若想提供"按任意键类型取值"的方法，必须借助包级函数或笨拙的类型参数，表达力受限且调用不够自然。泛型方法让 `Container[T].Get[U]()` 这类写法成为可能。json/v2 解决了旧 json 包在结构体标签语义、流式处理、性能上的长期积弊；mldsa 应对量子计算对现有签名的潜在威胁，让标准库跟上后量子密码学节奏；goroutine 泄漏分析则帮助团队定位被遗忘的后台协程，这类问题过去只能靠 pprof 人肉排查。

**原理拆解**：泛型方法在方法接收者之后、参数之前插入类型参数列表：
```go
type Set[T comparable] struct{ m map[T]struct{} }

// 泛型方法：求交集，元素类型可不同于接收者
func (s Set[T]) Intersect[U comparable](o Set[U]) Set[any] {
    result := Set[any]{m: map[any]struct{}{}}
    for k := range s.m {
        if _, ok := o.m[any(k)]; ok { result.m[k] = struct{}{} }
    }
    return result
}
a := Set[int]{}   // 调用：a.Intersect[string](b)
```
编译器为不同实例化生成单态化代码，零运行时反射开销。json/v2 用新的 `omitzero` 标签与 `json.MarshalerV2` 接口取代旧的 `MarshalJSON`，避免了指针判空歧义，并显著改善了大结构体的编解码吞吐。

**动手验证**：
```bash
go version               # go1.27
go doc encoding/json/v2  # 查看新包文档
```
迁移旧 JSON 代码：
```go
import json "encoding/json/v2"
type User struct {
    Name string `json:"name,omitzero"`
}
b, _ := json.Marshal(User{Name: "x"})
```
对存量项目跑 `go vet` 与 Goroutine 泄漏分析（`GODEBUG=goroutineleak=1 go test ./...`），观察是否出现泄漏告警。建议先把 json/v2 在边缘服务试点，确认与现有编解码行为一致后再全量切换。

**对比选型**：
| 能力 | Go 1.26 | Go 1.27 |
|------|---------|---------|
| 泛型方法 | 不支持 | 支持（#77273） |
| JSON 标准库 | encoding/json | 新增 encoding/json/v2 |
| 后量子签名 | 无 | crypto/mldsa |
| 小对象分配 | 基线 | 最多快 30% |

总体看，1.27 是表达力与安全性的双重增强，且向后兼容良好。泛型方法特别适合写通用容器与算法库，过去必须用反射或代码生成的场景如今可以落到类型系统里，可读性显著提升；json/v2 适合对序列化性能敏感的服务，尤其是字段多、吞吐高的网关与中间件；mldsa 则适合金融、政务等需要面向未来合规签名的系统。值得一提的是，泛型方法虽好，但会让 API 表面更复杂，库作者在公开接口上应谨慎暴露类型参数，避免把复杂度转嫁给调用方。对于大多数业务项目，建议先用 json/v2 与 goroutine 泄漏分析这类"开箱即得"的能力，泛型方法则在通用的基础库里逐步采用，既享受表达力又不至于过早增加维护负担。

### 3. 【TypeScript 7 用 Go 重写编译器，全量构建提速 8–12 倍但生态暂卡 6.x】

**导语**：TypeScript 7（在路线图上原属 6.x，内部代号 Native）于 2026 年 7 月 8 日随 Go 重写的编译器登陆，全量构建提速 8–12 倍——VS Code 的完整类型检查从 125.7 秒骤降到 10.6 秒。但 7.0 暂未提供稳定的编程式 API，导致 typescript-eslint、ts-jest、ts-morph，以及 Vue/Svelte/Astro/Angular 背后的模板检查器被卡在 TS 6，需要等 7.1 补齐接口后才能顺滑升级。这是一个"快得惊人但需分阶段迁移"的版本，团队应评估自身工具链依赖再决定升级时机。

**它是什么**：TypeScript 7 是 TypeScript 编译器用 Go 重新实现的版本，由 Microsoft 团队发布。核心变化是编译器后端从 Node.js/JS 切换为原生 Go 二进制，类型检查（type-check）与代码生成（emit）路径被大幅并行化。官方基准显示完整构建获得 8–12 倍提速，增量构建亦有数倍提升。7.0 仅交付命令行 tsc 与原生语言服务，省略了原本面向工具的 programmatic API（如 ts.createProgram 的完整稳定契约），因此依赖编译器内部 API 的生态工具需等待 7.1。语言本身（语法、类型系统）与 tsconfig 语义基本保持不变，用户几乎无需改写代码。

**解决什么**：大型 TypeScript 代码库（如 VS Code、Azure、Office）全量类型检查动辄数分钟，CI 流水线与本地编辑反馈都因此变慢，拖慢整个迭代节奏。Go 原生编译器把 CPU 密集的检查下沉到多线程原生代码，消除了 JS 单线程与 GC 停顿带来的迟滞。它修复的是"规模导致的编译墙"，而非新增类型语法——这意味着升级收益主要落在"等待时间"上，而不是语言能力的扩张，对超大型单体仓库的收益最为明显。

**原理拆解**：旧编译器在 Node 中单线程遍历 AST 做绑定、检查、emit；新实现用 Go 的 goroutine 把各源文件检查并行化，并复用共享符号表：
```ts
// 用户代码与配置完全不变，仅替换编译器
{
  "compilerOptions": {
    "strict": true,
    "target": "ES2022"
  }
}
```
迁移只需升级 typescript 版本与编辑器插件；但因 7.0 无稳定 API，下列依赖内部接口的用法需暂缓：
```ts
import * as ts from "typescript";
const program = ts.createProgram(files, opts); // 依赖内部 API，7.1 才稳
```

**动手验证**：
```bash
npm i -D typescript@7
npx tsc --version     # 7.0.x
time npx tsc -b       # 记录耗时，与 TS 6.x 同项目对比
```
对纯 tsc 构建的项目可直接升级；若项目用到 typescript-eslint 或 ts-jest，建议先固定 TS 6，等 7.1 发布编程式 API 后再切。可在 CI 中并行保留 6.x 与 7.0 两条构建，量化提速收益后再决策。另外，升级后建议用 VS Code 自带的性能面板验证编辑器内的类型检查响应是否真的变快，把"体感提速"也纳入验收，而不是只看命令行上的冰冷数字。

**对比选型**：
| 维度 | TS 6.x | TS 7.0 |
|------|--------|--------|
| 构建速度 | 基线 | 8–12 倍 |
| 编程式 API | 稳定 | 暂缺（7.1 补） |
| 生态工具兼容 | 全 | 部分卡在 6.x |

结论很清晰：如果你的项目只用 tsc 做类型检查与打包，升级 7.0 几乎零成本且收益巨大，动辄数分钟的 CI 有望压缩到几十秒；若深度依赖编译器 API 做代码生成、规则检查（如自定义 babel 插件、AST 转换器、类型提取工具），则需要等 7.1 补齐稳定接口再动。建议在升级前用 `npm ls typescript` 盘点依赖树，凡是用了 `ts.createProgram`、`ts.transpileModule` 等内部 API 的包都要标红。需要强调的是，7.0 的提速主要来自原生并行化，对纯类型检查占比高的项目收益最大，而对"编译后基本是 JS 搬运"的小型项目收益相对有限。把"工具链是否依赖内部 API"作为升级与否的一票否决项，可以避免踩进生态不兼容的坑，让提速红利安全地落入团队账户。

### 4. 【Rust 1.98 发布：derive 快路径变更或悄悄改变你的排序结果】

**导语**：Rust 1.98 于 2026 年 8 月 20 日发布，最需开发者警惕的一处变化是：当 Ord 已派生时，derive(PartialOrd) 会新增一条"复用 Ord 结果"的快路径，可能改变那些"两份排序实现语义不一致"类型的比较结果。它不会让任何代码编译失败，而是悄悄改变 sort 的顺序——升级后务必复查与排序相关的逻辑，别等到线上数据错乱才回头查。这种"静默语义漂移"比编译错误更难排查，因此值得专门写一篇提醒。

**它是什么**：Rust 1.98 由 Rust 团队按六周节奏发布。本版语言层改动温和，但标准库 derive 宏行为有微调：derive(PartialOrd) 在检测到 Ord 已派生时，直接复用 Ord 的结果作为快路径，跳过原有的逐项比较。另外社区一度误传 c_variadic 在 1.98 稳定——实际上其稳定 PR 挂在 1.99.0 里程碑，于 1.98 分支之后才合入，属于下一版内容。其余为常规库与工具链改进，整体仍遵循 Rust 一贯的"小步快跑、尽量向后兼容"哲学，只是这一处 derive 行为需要额外留意。

**解决什么**：对绝大多数"Ord 与 PartialOrd 语义一致"的类型，快路径减少了比较指令、提升了排序吞吐，是正向优化。问题出在少数边界：若某类型以非标准方式手动实现了 Ord，却又让 derive 生成 PartialOrd，两者语义分歧时，旧的逐项比较与新的复用 Ord 会给出不同顺序。Rust 借此统一派生语义、消除冗余比较，但代价是存量"不一致实现"会产生行为漂移——这正是需要开发者主动复查的地方，而非编译器帮你报错。

**原理拆解**：
```rust
#[derive(PartialOrd, Ord)] // 两者一致，快路径安全
struct Point { x: i32, y: i32 }

#[derive(PartialOrd)]      // 仅 PartialOrd，仍走逐项比较
struct Wrapper(i32);

// 危险组合：手动 Ord 与 derive PartialOrd 语义不一致
impl Ord for Weird { /* 自定义顺序 */ }
#[derive(PartialOrd)]      // 1.98 起复用 Ord 快路径，结果可能变化
struct Weird(i32);
```
升级后运行 `cargo test` 中排序相关断言，或用 `cargo +1.97 test` 对照，定位行为漂移。关键是找出"手动 impl Ord + derive PartialOrd"的类型。

**动手验证**：
```bash
rustup update stable        # 拉取 1.98
cargo +1.98 build
# 针对排序单测做版本对照
cargo +1.97 test sort::    # 旧版行为
cargo +1.98 test sort::    # 新版行为，关注差异
```
建议：在 CI 中保留一份 1.97 对照测试，捕捉悄然变化的顺序，避免回归悄悄混入。对核心数据结构，应补充排序不变量测试，使语义变更在测试阶段即可暴露。如果项目体量较大，可借助 `cargo bisect-rustc` 这类工具在疑似排序回归时快速定位到具体版本，把排查时间从数小时压缩到几分钟，是处理此类静默语义变更的实用手段。

**对比选型**：
| 版本 | derive(PartialOrd) 行为 | 升级风险 |
|------|--------------------------|----------|
| 1.97 及之前 | 逐项比较 | 低 |
| 1.98 | Ord 存在时复用快路径 | 排序语义可能变化 |

总体建议：1.98 对绝大多数项目是安全的常规升级，唯一需要动作的是排查"Ord 与类型语义不一致"的代码。可以用 grep 定位 `impl Ord` 与 `#[derive(PartialOrd)]` 共存的 struct，对它们补一组排序断言后再升。更稳妥的做法是在团队的 lint 规则里加入"禁止手动 impl Ord 同时又 derive PartialOrd"的提示，从源头避免语义分歧。对于已经发布到 crates.io 的库，建议在发布前额外跑一遍 1.97 与 1.98 的双版本 CI，确保排序行为一致；一旦发现顺序漂移，应优先修正手动 Ord 实现，使其与字典序预期相符，而不是依赖旧版逐项比较的"巧合"行为。把排序不变量写进测试，是把"静默语义变更"变成"可见失败"的最有效手段，也是成熟 Rust 团队应对小版本语义微调的标准姿势。

### 5. 【Python 3.15 RC1 带来惰性导入与 frozendict，自由线程 ABI 终于稳定】

**导语**：Python 3.15 于 2026 年 8 月 4 日进入 RC1，距离 10 月 1 日正式版仅一步之遥。两大语言层新特性最受关注：惰性导入（PEP 810）削减 import 重项目的启动耗时，内置 frozendict（PEP 814）提供一等公民的不可变字典类型。自由线程构建也借 PEP 803 拿到稳定 ABI，让 C 扩展轮子真正可跨版本分发。对"启动慢、配置共享难"的工程痛点，这是一次精准补强，且继续保持了 Python 一贯的平滑演进节奏。

**它是什么**：Python 3.15 由 PSF 发布（RC1 于 2026-08-04）。新增内容包括：惰性导入（PEP 810，import 时延迟真正加载模块到首次使用）、frozendict 内置不可变字典（PEP 814）、自由线程稳定 ABI（PEP 803，3.15 前不再改动 ABI，C 扩展可发布 cp315t 轮子）。性能方向聚焦"启动效率与性能自省"。需要澄清：自由线程仍非默认构建，单线程开销约 1%–8%，PEP 803 解决的是"扩展轮子兼容性"，而非把 GIL 默认关掉。换言之，这一版把"自由线程能实用"的最后一公里铺平了，但默认开关依旧留给你自己决定。

**解决什么**：大型应用（CLI 工具、IDE 插件、import 重的服务）启动时被一次性加载全量依赖拖慢，很多模块其实首屏用不到；frozendict 长期只能靠第三方库（如 pyfrozen）或 typing 的 MappingProxyType 曲线救国，既不便携也不够"原生"。惰性导入把昂贵模块推迟到真正调用时才加载，缩短冷启动时间；frozendict 为配置、缓存键、跨线程安全共享提供了语言级不可变类型，让"不可变"成为字典的一等能力而非外加约束。

**原理拆解**：
```python
# PEP 810 惰性导入：模块在首次属性访问时才真正加载
from importlib import lazy_import
lazy_import("heavy", ["heavy"])   # 此刻不执行 heavy 的顶层代码
heavy.do()                         # 真正的 import 发生在此行

# PEP 814 内置不可变字典
d = frozendict(a=1, b=2)
d["c"] = 3       # TypeError: frozendict is immutable
hash(d)          # 可哈希，可作 dict 键或 set 元素
```
自由线程稳定 ABI 让 numpy/pandas 等可发布带 t 后缀的轮子，免除每个版本重编译的麻烦，是自由线程走向生产的关键拼图。

**动手验证**：
```bash
pyenv install 3.15.0rc1
python3.15 -c "from importlib import lazy_import; lazy_import('os'); print('deferred')"
python3.15 -c "d=frozendict(x=1); print(hash(d))"
python3.15t -c "import sys; print(sys._is_gil_enabled())"  # False 表示自由线程构建
```
对照 3.14 启动耗时：`python3.15 -X importtime app.py` 与 `python3.14 -X importtime app.py` 对比差异。建议在 CLI 入口场景优先试用惰性导入，观察冷启动改善。若担心惰性导入掩盖了循环依赖，可在测试环境用 `python -W error::ImportWarning` 把隐藏的导入问题提前暴露，确保延迟加载不会在运行时才抛出本可早发现的错误。

**对比选型**：
| 特性 | 3.14 | 3.15 RC1 |
|------|------|----------|
| 惰性导入 | 无 | PEP 810 |
| 不可变字典 | 仅靠第三方 | 内置 frozendict |
| 自由线程 ABI | 不稳定 | 稳定（PEP 803） |

综上，3.15 的价值在于"启动更快、不可变更原生、自由线程可落地"。对 import 重的服务（如 CLI、serverless 函数、IDE 插件），惰性导入能直接削减冷启动；对需要跨线程共享配置、做缓存键的场景，frozendict 免去了引入第三方库的负担，也避免了 MappingProxyType 的语义歧义。需要提醒的是，惰性导入并非免费——首次真正使用时仍要付出加载成本，因此不适合"几乎每次启动都会用到"的热路径模块，更适合"按需、偶尔"的沉重依赖，用空间换时间的逻辑要反过来想。自由线程 ABI 稳定虽是里程碑，但默认仍非开启，团队若要上自由线程，仍需确认整条依赖树都有 t 后缀轮子，否则进程会悄悄退回 GIL。建议在 RC 阶段就把关键服务跑一轮 3.15 兼容性验证，正式版一出即可平滑升级，不必等到被迫迁移的那天。

### 6. 【动态语言在 AI 编程基准中完胜：Ruby/Python/JS 比静态语言快 1.4–2.6 倍】

**导语**：2026 的一次大规模基准测试（Yusuke Endoh 用 Claude Code 在 13 种语言实现简化版 Git，每种跑 20 次、共 600 次）显示：动态语言 Ruby/Python/JavaScript 在 AI 编程场景下，比静态类型语言快 1.4–2.6 倍、成本低约一半，且 600 次运行中唯一的失败出现在 Rust 与 Haskell。这个结果把"类型系统对编程 Agent 的真实价值"推到了语言选型的新变量位置，值得每一个用 AI 写代码的团队重新审视——当写代码的人变成 Agent，"可读性"与"安全感"的权重可能要重新分配。

**它是什么**：该基准以"用 Claude Code 从零实现简化版 Git（init/add/commit/log/status/diff/checkout/reset）"为统一任务，13 种语言各执行 20 次。动态组含 Python、Ruby、JavaScript、Perl、Lua；静态组含 TypeScript、Go、Rust、C、Java；函数式组含 Scheme、OCaml、Haskell。测量维度为成本、耗时、代码行数与通过率。结果排名：Ruby $0.36/73s、Python $0.38/75s、JavaScript $0.39/81s 居首；TypeScript $0.62/133s、C $0.74/156s、Haskell $0.74/174s 垫底，Rust 与 Haskell 各出现测试失败。需要指出，该基准测量的是"Agent 生成代码的效率"，并非运行时性能或大型可维护性。

**解决什么**：它回答了一个 2026 年高频的工程决策——"让 AI 编程 Agent 用哪种语言最划算？"传统选型强调类型安全与运行性能，但 Agent 靠"写→运行→读错→修"的紧密循环自我纠错，编译期安全网反而变成昂贵的重试开销。这份基准为"AI 原生开发"提供了量化依据，提示我们在评估语言时要把"Agent 迭代成本"纳入权重，尤其对大量使用 Copilot/Claude Code/Cursor 的团队，语言选择直接影响研发账单。

**原理拆解**：为什么动态语言更便宜？① token 效率：相同功能动态语言代码更短（Python 235 行 vs C 517 行），生成的 token 更少；② 无编译循环：动态语言免去 compile→type-error→fix 的往返，Agent 在运行时错误上同样能自我修复；③ 训练语料：Python/Ruby/JS 占比高，模型更熟练。代价也清晰：加类型检查后 Python/mypy 慢 1.6 倍、Ruby/Steep 慢 2.6 倍——类型注解本身就在消耗推理算力，说明类型系统的"安全红利"在 Agent 场景被部分抵消。

**动手验证**：可低成本复现思路：
```bash
# 用 Claude Code 对每个语言执行同一 prompt 实现 mini-git
for lang in python ruby javascript typescript go rust; do
  claude -p "实现简化版 git: init/add/commit/log" --language $lang
done
# 记录每次 token 成本与耗时，每种跑 20 次取均值
```
观察现象：静态语言因配置（Cargo.toml/tsconfig）与类型报错重试，单轮迭代显著拉长，且更易触发失败重试。建议在团队内部用真实业务任务跑一轮小样本对照，而非只看基准平均数。

**对比选型**：
| 语言 | 成本 | 耗时 | 通过率 |
|------|------|------|--------|
| Ruby | $0.36 | 73s | 100% |
| Python | $0.38 | 75s | 100% |
| JavaScript | $0.39 | 81s | 100% |
| Go | $0.50 | 102s | 100% |
| TypeScript | $0.62 | 133s | 100% |
| Rust | $0.54 | 114s | 95% |

结论需辩证看待：动态语言胜在"Agent 迭代成本"，但静态类型在十万行以上代码库、公共库接口、并发安全上的优势依旧成立，基准本身也坦承未测量代码质量与可维护性。务实做法是——用 Agent 快速原型、写一次性脚本、做探索性开发时选动态语言（Ruby/Python/JS），能显著降低 token 账单与等待；而长期维护的核心系统、对正确性要求极高的金融与基础设施代码，仍应按传统标准选静态类型，因为类型系统在人类协作与大规模演进中的价值，并不会因为 Agent 能自我纠错而消失。对团队而言，更聪明的策略是"分层"：原型与胶水层用动态语言求快，稳定与接口层用静态语言求稳，让两类语言各自发挥长处，而不是被一份基准报告牵着走。选型最终要服务于"人 + Agent"共同维护的真实系统，而非某一项单一指标。
