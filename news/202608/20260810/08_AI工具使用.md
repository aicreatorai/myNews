### 1. 【AI 命令行技能封装：把反复敲的提示词做成一条斜杠命令】

> 📍 **导语**：用命令行智能体久了，你会发现真正拖慢自己的从来不是模型不够聪明，而是你每天都在重新打同一段话。要它写提交信息，你得交代一遍团队的提交规范；要它整理变更日志，你得再说一遍格式要求；要它做安全检查，你得把关注项从头列一遍。这段"多段落开场白"平均三五百字，一天敲七八次，一周就是两三个小时纯打字。社区在 2026 年 8 月初集中总结出的一批被低估的用法里，排在最前面的就是自定义斜杠命令——把那段反复交代的指令写成一个文件，之后只需要敲一个词。它的价值不只是省打字：手打的提示词每次都有细微差别，产出质量就跟着漂移；固化成文件之后，同一件事的输入变成完全一致的，输出才谈得上稳定，也才谈得上团队共用。这条讲清斜杠命令、技能包与项目记忆文件三者的分工，以及怎么在半小时内把自己最高频的三个任务封装掉。

**▌ 它是什么（工具速览）**

这里说的是当下主流命令行智能体（Claude Code、Codex CLI、Gemini CLI、以及各类开源平替）都提供的同一类能力，只是叫法略有差异，理解它得先把三样容易混淆的东西分开。

第一样是**项目记忆文件**，也就是仓库根目录下那份 `CLAUDE.md` / `AGENTS.md`。它的特点是**每次对话自动加载**，写的是长期不变的项目规矩：技术栈、测试命令、代码风格、禁止事项。它回答的是"你在什么环境里干活"。

第二样是**自定义斜杠命令**。它是放在 `.claude/commands/`（或对应工具的命令目录）下的一个 Markdown 文件，文件名就是命令名。它**不自动加载，你敲了才生效**，写的是某一类任务的完整作业指导书。它回答的是"这件事该怎么做"。

第三样是**技能包（Skills）**。它比斜杠命令更重，可以带脚本、模板、参考资料，适合把一整套流程连同配套文件一起分发。Codex 的 Skills、Figma 团队内部做的 `/figjam-builder` 都属于这一类——设计师把"从各系统拉数据、按固定格式铺成一块看板"的整套指令封进去，之后一句话就能跑。

三者的关系是：记忆文件管环境，斜杠命令管任务，技能包管可分发的完整流程。绝大多数人只用了第一样，把第二样的位置留给了每天重打的那几百字。

**▌ 它解决了什么问题**

第一是重复打字的时间损耗。多段落提示词一天敲七八次，本身就是一笔不小的开销，而且这段时间产出为零。

第二是输入漂移导致的质量不稳。手打的提示词今天写了"注意并发安全"、明天忘了写，产出质量随之波动，你却会误以为是模型状态不好。固化成文件后，输入是常量，输出才可归因。

第三是团队之间的水平差。同一个任务，资深工程师写的提示词和新人写的差出一个量级。把提示词做成可提交进仓库的文件，等于把老手的经验变成了全组默认配置——这也是企业侧把提示词集中管理的核心动机。

第四是流程无法被评审。散落在各人终端历史里的提示词，没法被 review、没法被版本控制、改坏了也不知道是谁改的。放进仓库之后，它和代码一样走分支和评审。

第五是跨工具迁移。今天用这个 CLI、明天换那个，如果指令都在脑子里，换一次就要重建一次；如果都是纯文本文件，换工具基本只需要改目录位置。

**▌ 原理拆解**

理解三件事，你就知道一条斜杠命令该怎么写才好用。

第一，**它本质上就是一次文本注入**。你敲 `/commit-msg`，工具读取对应文件的内容，把它当作这一轮的提示词发出去。所以它没有任何魔法，写得好不好完全取决于文件里那段文字。这条推论很实用：**先在交互式会话里把提示词调到满意，再原样复制进文件**，不要凭空直接写文件。

第二，**参数占位符决定了它能不能复用**。多数工具支持在文件里写 `$ARGUMENTS`（或类似占位）来接收调用时传入的参数。没有占位符的命令只能干一件死事；有了它，`/review src/auth.py` 和 `/review src/pay.py` 就是同一条命令的两次调用。**判断一条命令值不值得封装，看它有没有可参数化的变化点**。

第三，**斜杠命令要和无头模式配合才发挥最大价值**。命令行智能体都提供 `-p "prompt"` 这类一次性执行的参数，配合 `--output-format json` 可以把结果吐给下游脚本解析。这意味着同一份指令文件既能在交互会话里手动调用，也能挂进定时任务或提交钩子里自动跑。**能被脚本调用的提示词，才算真正脱离了"人在场"的依赖**。

还有两条实践约束值得提前知道。其一，命令文件不要写太长。塞进两千字的规范，每次调用都要吃掉这些上下文，成本和干扰同步上升；真正长的规范应该放进记忆文件或让它按需读取参考文档。其二，涉及写操作的命令要在文件里显式写清边界，例如"只改指定文件，不要动测试目录"。**权限允许清单（allowlist）配合命令文件，比每次弹窗点确认更安全**——因为反复弹窗最终会训练你闭着眼睛点同意。

**▌ 动手验证**

场景：把"根据暂存区变更写一条符合团队规范的提交信息"封装成 `/commit-msg`。

第一步，建目录并写命令文件。在仓库根目录执行：

```bash
mkdir -p .claude/commands
cat > .claude/commands/commit-msg.md <<'EOF'
读取当前 git 暂存区的变更（运行 git diff --cached），
生成一条符合下列规范的提交信息：

格式：<type>(<scope>): <subject>
type 只能是 feat/fix/docs/refactor/test/chore 之一
scope 用改动最集中的模块目录名，无法判断则省略
subject 不超过 50 字符，用祈使句，句尾不加句号

正文部分（可选，与标题空一行）：
- 只写"为什么这么改"，不要复述 diff 里已经能看到的内容
- 涉及破坏性变更时，必须以 BREAKING CHANGE: 开头单独一段

规则：
暂存区为空时直接回答"暂存区为空"，不要编造。
只输出提交信息本身，不要任何解释、不要代码块包裹。
EOF
```

第二步，验证它确实被识别。启动会话后输入 `/`，命令列表里应该能看到 `commit-msg`。看不到多半是目录位置不对，先检查这一项再折腾别的。

第三步，加参数化版本。再写一个 `.claude/commands/review.md`，第一行写 `请评审文件：$ARGUMENTS`，后面接评审清单（安全、边界条件、错误处理、命名）。之后 `/review src/auth/login.py` 就能定点评审。**这一步是从"省打字"升级到"可复用"的分界**。

第四步，把它接进自动化。先在终端裸跑一次确认可用：

```bash
git add -A
claude -p "$(cat .claude/commands/commit-msg.md)" --output-format json
```

能拿到结构化结果，说明这条指令具备了被脚本调用的资格。之后就可以把它挂进 `prepare-commit-msg` 钩子，或者放进 CI 里做变更日志汇总。

第五步，配权限允许清单，减少无意义弹窗。在 `.claude/settings.json` 里：

```json
{
  "permissions": {
    "allow": ["Bash(git status)", "Bash(git diff:*)", "Bash(npm test)"]
  }
}
```

只放只读和已知安全的命令。**千万别为了省事直接放开全部 Bash**——确认疲劳的解法是缩小确认范围，不是取消确认。

第六步，把 `.claude/commands/` 提交进仓库，让全组共用。之后谁改进了提示词，走 PR 评审合并，所有人下次拉代码就自动生效。

第七步，一周后做一次清理。统计自己实际用过哪几条，没用过的删掉。**命令列表膨胀到二十条以后，找命令的时间就超过打字的时间了**，控制在五到八条最舒服。

关键心得：这套做法真正改变的不是速度，而是把"我脑子里那套做事标准"从口头传承变成了可提交、可评审、可复用的资产。

**▌ 对比选型**

| 决策维度 | 斜杠命令 | 项目记忆文件 | 每次手打 |
|---------|---------|------------|--------|
| 加载时机 | 敲了才生效 | 每轮自动加载 | 手动 |
| 适合内容 | 单类任务流程 | 长期项目规矩 | 一次性需求 |
| 能否传参 | 支持占位符 | 不支持 | 天然灵活 |
| 团队共用 | 可提交评审 | 可提交评审 | 无法沉淀 |

选型建议：一天做不到一次、且每次要求都不同的活，直接手打最快；每周重复三次以上、要求基本固定的任务，立刻封装成斜杠命令；需要连带脚本、模板、参考文档一起分发给别的团队的整套流程，才值得升级成技能包。三者不冲突，成熟的仓库里通常是一份记忆文件加五六条斜杠命令的组合。

### 2. 【沉浸式翻译加术语表：把外文资料读成可引用的双语底稿】

> 📍 **导语**：读外文资料这件事，绝大多数人的做法还停留在"整页丢进翻译工具，得到一整页中文"。这个做法有两个隐蔽的代价：一是你彻底失去了对照原文的能力，译得对不对无从判断；二是专有名词每次翻得都不一样，同一个术语在第一段叫"检索增强"、第三段叫"检索强化"，等你要引用时就得回头逐个核对。真正把外文阅读效率拉起来的，不是更强的翻译模型，而是三件配套的小事：段落级双语对照、可自定义的翻译引擎、以及一份属于你自己的术语表。沉浸式翻译这类浏览器插件之所以在技术圈渗透率高，靠的正是这三样都能自己配——它默认接的是普通机器翻译，但真正的用法是把它的后端换成你自己的大模型接口，再挂上术语表和领域提示词。这条讲清这套配置怎么做、术语表为什么是质量分水岭、以及它和整页翻译、原生 AI 浏览器分别该怎么分工。

**▌ 它是什么（工具速览）**

沉浸式翻译是一款浏览器扩展（同时提供移动端与桌面客户端），核心形态是**双语对照**：它不替换原文，而是在每个段落下方插入译文，原文和译文上下相邻。这个形态看起来只是个交互选择，实际决定了它的全部定位——你随时能回看原文，所以它适合"需要为内容负责"的阅读，而不是"看个大概"的浏览。

它的能力可以分四块。第一块是网页正文的段落级对照翻译，支持按域名设置自动触发。第二块是文档翻译：PDF、EPUB 都能保留排版做对照。第三块是视频字幕的双语显示。第四块，也是被用得最少却最关键的一块——**自定义翻译服务**：除了内置的几家机器翻译，它允许你填入任意兼容 OpenAI 接口格式的服务地址、密钥和模型名，也就是说你可以让 DeepSeek、通义、Kimi 或者你本机跑的模型来做翻译。

配套的还有两项：**自定义提示词**（可以给翻译加上"这是机器学习论文，术语按学术惯例翻译"这类领域约束）和**术语表**（强制指定某些词的固定译法）。这两项加上自定义引擎，才是它区别于普通翻译插件的地方。

**▌ 它解决了什么问题**

第一是译文不可核验。整页翻译最大的问题是你无法判断哪句译错了。段落对照让核验成本降到接近于零——读着不对劲，眼睛往上一扫就是原文。

第二是术语漂移。同一份资料里同一个概念被翻成三种说法，是机器翻译的常态。这在随便看看时无所谓，在你要把内容整理成报告并引用时就是灾难，因为读者会以为你在说三件事。

第三是领域语境缺失。通用翻译引擎不知道你在读什么领域，`transformer` 到底是变压器还是那个模型架构、`attention` 是注意力机制还是关注度，全靠猜。领域提示词把这个上下文补上。

第四是成本与隐私。内置翻译服务对长文档有额度限制，而接自己的模型接口，成本可以压到很低；如果接的是本机模型，内容根本不出网，这对读内部资料的人是硬需求。

第五是从"读过"到"能用"之间的断层。看懂了但没沉淀，一周后等于没读。双语底稿加上固定术语，才有可能被直接引用进你的文档。

**▌ 原理拆解**

理解三层机制，你就知道它什么时候翻得好、什么时候会翻车。

第一层是**分段送译**。它把网页正文切成段落，逐段发给翻译服务。这个设计带来一个重要推论：**每段之间是相互独立的，没有共享上下文**。所以代词指代跨段就会断，前一段说的"该方法"，下一段翻译时它并不知道指的是什么。应对方式是在自定义提示词里补一句领域背景，让每段都带着同样的先验，而不是指望它自己串起来。

第二层是**术语表的注入位置**。术语表不是后处理替换，而是被拼进提示词一起发给模型的。这意味着两点：术语表越长，每段的开销越大，因此**术语表要精不要全**，只放那些会造成理解偏差的关键词，几十条足矣，几百条会显著拖慢；另外因为是软约束，模型偶尔仍会不遵守，重要术语建议在提示词里再强调一次。

第三层是**自定义引擎的速率限制**。接自己的接口后，一篇长文会瞬间发出几十上百个并发请求，很容易被服务端限流，表现就是页面上一片"翻译失败"。**遇到大面积失败先降并发，而不是换引擎**——这是最常见的误判。

还有一条关于版式的：它依赖网页的正文结构来判断哪些是要翻的段落。结构规范的文章站点效果很好；用大量绝对定位、内容嵌在画布里的页面，它可能整段抓不到。这类页面只能退回到整页翻译或者复制文本处理。

最后是分工问题。**对照翻译解决的是"读"，不解决"整理"**。读完之后的摘要、结构化、横向对比，仍然要交给对话工具或工作台。把翻译插件当成阅读环节的基础设施，而不是全流程方案，预期才摆得正。

**▌ 动手验证**

场景：接下来两周要读三十篇英文技术资料，产出一份带准确术语的综述。

第一步，装好扩展后先改默认引擎。进入设置的"翻译服务"，添加自定义 AI 服务，按这个结构填：

```
接口地址：https://api.deepseek.com/v1/chat/completions
模型名称：deepseek-chat
API Key：你的密钥
每秒最大请求数：3
每次请求最大段落数：10
```

后两项是关键。默认值偏激进，先按上面这个保守值跑通，再往上调。

第二步，写领域提示词。在自定义服务的提示词设置里填：

```
你是技术文档译者。将以下英文翻译成简体中文。
领域背景：机器学习与软件工程。
要求：
1 专有名词、模型名、库名、命令保留英文原文，不要翻译
2 首次出现的技术概念用「中文（English）」形式给出
3 保持原文的段落结构与列表层级，不要合并或拆分
4 语气用陈述句，不要添加原文没有的解释性内容
只输出译文，不要任何前言后语。
```

第三条很重要。不写这句，它会把三个短句合成一段"更通顺"的中文，你再想和原文对齐就困难了。

第三步，建术语表。在术语表设置里逐条添加，只放会引起歧义的：

```
transformer → Transformer（不译为"变压器"）
attention → 注意力机制
grounding → 事实锚定
hallucination → 幻觉
inference → 推理（不译为"推断"）
alignment → 对齐
```

第四步，做一次对照抽检。随便打开一篇资料，挑三段自己看得懂的，对照原文核实译文有没有加料、有没有漏句。**这一步必须在批量读之前做**，否则你会带着一批不知道准不准的译文往下走。

第五步，配自动触发。把常读的几个域名设为自动翻译，其余保持手动。全站自动开着既费钱也影响加载速度。

第六步，处理 PDF 与长文档。文档翻译走单独入口，注意它同样受速率限制影响，一份长 PDF 建议单独跑、不要和网页翻译同时进行。

第七步，把术语表纳入版本管理。设置里可以导出配置为文件，把它放进你的笔记库或仓库，团队共用同一份术语表——**这是让一个组产出口径一致的最低成本做法**。

关键心得：翻译质量的上限不由模型决定，由你给它的领域约束和术语表决定。花二十分钟配好这两样，之后三十篇资料的阅读体验都会不一样。

**▌ 对比选型**

### 3. 【Ollama 与 LM Studio：把开源模型装进本机让敏感资料不出网】

> 📍 **导语**：有一类需求，再好用的云端模型也接不住：合同条款、客户名单、财务报表、未公开的源代码——这些内容一旦贴进公共对话框，就等于交了出去。见过最让人后怕的案例是一家做招投标的公司，员工图省事把标书正文粘进免费 AI 里润色，报价、技术方案、商务条款一次性全出去了。这类场景的唯一解法是让模型跑在自己的机器上。过去这件事的门槛在于显卡和折腾成本，但到 2026 年，两个变化把门槛拉平了：一是小参数模型的能力足够覆盖翻译、摘要、分类、格式转换这些日常活；二是 Ollama 和 LM Studio 这类工具把"下载—加载—提供接口"压缩成了一条命令或几次点击。更关键的是它们都提供兼容 OpenAI 格式的本地接口，意味着你现有的插件、脚本、工作流几乎不用改就能切换过去。这条讲清两者怎么选、本机到底能跑多大的模型、以及哪些活适合交给它、哪些别指望。

**▌ 它是什么（工具速览）**

两个工具解决同一件事——在本机运行开源大模型——但形态和适合的人完全不同。

**Ollama** 是命令行优先的工具。装好之后一条 `ollama run qwen3:8b` 就能把模型拉下来跑起来，模型文件、量化版本、运行参数它都替你处理好了。它的核心价值在于**默认在本地 11434 端口起了一个兼容 OpenAI 格式的服务**，任何能填接口地址的客户端都能直接指过来。它还支持用 `Modelfile` 定义自己的模型变体：固定系统提示词、调好温度和上下文长度，打包成一个可以分发的名字。

**LM Studio** 是图形界面优先的工具。它把模型发现、下载、硬件适配、参数调节都做成了可视化面板，会根据你的内存和显存提示"这个模型你跑得动/跑不动"，对不熟悉命令行的人友好得多。它同样能一键开启本地服务器，提供相同格式的接口。

两者不冲突，很多人是这样分工的：用 LM Studio 试模型、比效果、调参数，选定之后用 Ollama 常驻后台给各类工具供能。

硬件上有个粗略的换算可以记：**模型参数量（B）乘以量化位数除以八，大致是所需显存/统一内存的下限，再留三成余量**。所以 8B 的四位量化模型大约需要 5–6GB，16GB 内存的笔记本能舒服地跑；32B 的模型则需要 20GB 以上，属于工作站级别。

**▌ 它解决了什么问题**

第一是敏感数据不能出网。这是本地模型不可替代的理由。财务、法务、招投标、源代码、客户个人信息这几类内容，用公共账号处理在很多公司是明令禁止的。

第二是长期成本。批量任务——比如把两千条工单分类、把三百份文档各出一段摘要——按接口计费会积少成多，而本地跑的边际成本只有电费。

第三是可用性与稳定性。云端服务限流、排队、临时不可用是常态。挂在流水线里的节点一旦依赖外部服务，整条流程的稳定性就被它拉低了。

第四是可定制。本地模型可以固定系统提示词、可以微调、可以做成只干一件事的专用版本，不受服务商的策略调整影响。

第五是离线可用。出差、飞机上、内网环境里，本地模型是唯一还能工作的选项。

**▌ 原理拆解**

要用好本地模型，得先接受一个前提：**它不是云端旗舰模型的免费替代品，而是另一类工具**。理解四点，你就知道该把什么活交给它。

第一，**量化是用精度换空间**。把模型权重从 16 位压到 4 位，体积降到四分之一，代价是输出质量的轻微下降。经验规律是：四位量化在摘要、分类、翻译、格式转换这类任务上几乎感觉不到差别；在多步推理、代码生成、长链条逻辑上差距会明显放大。**所以选型的第一问不是"能跑多大"，而是"这个任务对推理深度的要求有多高"**。

第二，**上下文长度直接吃内存**。模型加载本身占一块，上下文缓存另占一块，且随着对话变长持续增长。很多人遇到的"跑着跑着变慢甚至崩掉"，原因就是上下文超了。实操上把上下文设成任务实际需要的长度即可，不要一上来就拉满。

第三，**统一内存架构在这件事上有结构性优势**。苹果 M 系列这类内存与显存共享的机器，不需要独立显卡就能加载较大的模型，这也是为什么本地模型这两年在 Mac 用户里普及得更快。传统台式机则受限于显卡显存，超出部分要靠内存兜底，速度会掉一个量级。

第四，**接口兼容性是它真正的杠杆**。因为暴露的是标准格式接口，你的翻译插件、笔记工具、自动化流程只要能填自定义地址，改一行配置就能从云端切到本地。**这条决定了本地模型不是一个孤立玩具，而是可以直接嵌进现有工作流的组件**。

最后一条规律来自落地经验：**不要一步切换，要分层**。把任务按敏感度分成三档——公开内容走云端强模型，内部一般内容走本地模型，高敏内容只走本地且断网。这种分层比"全部本地化"现实得多，也比"全部云端"安全得多。

**▌ 动手验证**

场景：让本机跑一个模型，接管敏感文档的摘要和翻译，且完全不出网。

第一步，装 Ollama 并跑通第一个模型：

```bash
# macOS / Linux
curl -fsSL https://ollama.com/install.sh | sh

# 拉一个中文能力不错的中小模型并直接对话
ollama run qwen3:8b
```

第一次会下载几个 GB，之后就是本地加载。能对上话，说明环境通了。

第二步，确认本地接口在工作。另开一个终端：

```bash
curl http://localhost:11434/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "qwen3:8b",
    "messages": [{"role":"user","content":"用一句话说明你运行在哪里"}],

  }'
```

能拿到 JSON 回复，说明它已经可以被任何支持自定义接口的工具调用了。**这一步是整套方案的枢纽，务必先跑通再往下走**。

第三步，做一个专用模型变体。新建 `Modelfile`：

```

PARAMETER temperature 0.2
PARAMETER num_ctx 8192

你是内部文档摘要助手。

只依据给出的原文，原文没有的内容一律不补充，
无法判断的写"原文未提及"。不要输出任何前言后语。
"""
```

然后构建并调用：

```bash
ollama create doc-sum -f ./Modelfile
ollama run doc-sum
```

之后所有人调 `doc-sum` 拿到的都是同一套行为，不用各自再写提示词。

第四步，把现有工具切过来。以上一条讲的翻译插件为例，自定义服务里把接口地址填 `http://localhost:11434/v1/chat/completions`、模型填 `doc-sum` 或 `qwen3:8b`、密钥随便填一个非空字符串即可。改完之后，翻译内容不再离开本机。

第五步，做一次严格的断网验证。**这一步很多人跳过，但它是"以为不出网"和"确认不出网"的区别**：物理断网或关闭网络后再跑一次任务，仍然有正常输出，才算数。

第六步，做一次能力对照。挑五份真实文档，分别用本地模型和你常用的云端模型各跑一遍，逐条比对差距。差距在可接受范围内的任务类型固定交给本地，差距明显的老实回云端。

第七步，做资源守护。给它设一个合理的上下文长度，并观察内存占用；如果是长期常驻，把它设成开机自启的后台服务，避免每次手动开。

关键心得：本地模型的价值不在"更强"，而在"可以毫无顾虑地把任何东西喂给它"。这份心理上的松弛，本身就会显著提高你使用 AI 的频次。

| 决策维度 | Ollama | LM Studio | 云端旗舰模型 |
|---------|--------|-----------|------------|
| 上手方式 | 命令行一条命令 | 图形界面点选 | 注册即用 |

### 4. 【通义听悟做会议纪要：从一段录音到可指派的待办清单】

> 📍 **导语**：会议纪要是所有办公场景里投入产出比最差的一件事。一场两小时的评审会，整理纪要要花一小时，整理完还经常漏掉最关键的那句"这个下周三之前给我"。有团队做过统计，五个人的行政团队每月花在会议纪要和公文整理上的时间是一百二十小时，接入语音转写加大模型的方案之后降到二十小时。但这个降幅不是买个工具就自动发生的——直接把转写稿丢给模型说"帮我总结一下"，你会得到一段读起来很专业、但和会上真正决定的事对不上的漂亮文字。转写只解决了"字被记下来"，从字到"谁在什么时候要交什么"，中间还差三个关键动作：说话人分离、结构化模板、以及待办的强约束提取。这条以通义听悟为例（讯飞听见、飞书妙记同理），讲清这条链路怎么搭、纪要为什么会失真、以及哪一步必须保留人工。

**▌ 它是什么（工具速览）**

通义听悟是阿里云推出的音视频内容处理工具，定位不是单纯的语音转文字，而是"从音视频里提取可用信息"的一整条链路。它的形态包括网页端、客户端和会议软件插件。

它的能力分四层，理解这个分层很重要，因为质量问题往往出在某一层而不是整体。

最底层是**语音识别**：把音频转成文字，中文识别精度是它的强项，同时支持中英混合。第二层是**说话人分离**：把连续的文字切成"发言人 1 说了什么、发言人 2 说了什么"，你可以给每个发言人改成真名。第三层是**结构化提取**：自动生成全文摘要、章节速览（把两小时切成几个议题段落）、以及关键词。第四层是**待办事项提取**：从对话里识别出承诺和任务。

它还提供实时记录模式（边开会边出文字）和音视频文件上传模式（会后处理），以及和翻译结合的双语字幕。对经常和外部开英文会的人，最后这项省事不少。

同类里，讯飞听见在纯中文识别精度上长期处于第一梯队，飞书妙记的优势是和文档、日历天然打通。选哪个的核心不是精度差那一两个百分点，而是**你的纪要最终要落到哪个系统里**。

**▌ 它解决了什么问题**

第一是整理工时。这是最直接的收益，两小时会议的整理时间从一小时压到十几分钟。

第二是漏记关键承诺。人工记录时注意力有起伏，会议后半段的待办最容易漏。机器不会走神，全程覆盖率是稳定的。

第三是"谁说的"这个信息丢失。纯转写稿是一大段连续文字，事后完全分不清哪句是谁说的，而责任归属恰恰依赖这个。说话人分离补上的正是这块。

第四是长会议的可检索性。两小时的录音，事后想确认某个细节只能重听。有了带时间戳的文字和章节划分，定位一个片段是几秒钟的事。

第五是跨语言会议。外部英文会议，实时双语字幕加会后中文纪要，比会后找人翻译快一个量级。

**▌ 原理拆解**

要让纪要真正可用，必须理解三个失真环节。

第一个是**识别层的失真**。专业术语、公司内部黑话、人名，是识别错误的重灾区。"复购率"被识别成"复购力"、产品代号被识别成谐音词，这类错误会一路传导到摘要里，而且因为读起来很通顺，你根本发现不了。应对方式是**用工具的热词/自定义词表功能，把公司产品名、部门名、常用术语提前录进去**。这一步的收益远大于事后校对。

第二个是**摘要层的幻觉**。模型做摘要时有很强的"补完"倾向：会上只是有人随口提了一句"要不要考虑接第三方支付"，摘要里可能变成"决定接入第三方支付"。这类错误极其危险，因为纪要是有决策效力的文档。**根本原因在于提示词里没有区分"讨论到"和"决定了"**，必须在模板里显式约束。

第三个是**待办提取的口径**。一句"这个我看看"算不算待办？"下周之前"到底是哪天？机器只能按字面理解。因此待办提取必须设定明确规则：只有同时出现"负责人 + 动作 + 时间"三要素的才算待办，缺一律进"待确认"区，而不是让它自己脑补一个负责人。

还有一条关于流程设计的：**纪要不该是终点，而应该是入口**。整理出来的待办如果只是躺在一个文档里，一周后仍然没人做。成熟的做法是把这条链路接下去——转写、提取要点和待办、写入协作文档、推送给对应负责人，形成闭环。这也是这类工具值得接进自动化流程的原因：它的输出天然是结构化的，适合作为下游节点的输入。

最后一条现实约束：**录音质量决定上限**。多人抢话、远场拾音、背景噪音大，识别精度会断崖下降，后面所有环节都白搭。会前把设备摆到桌子中央、提醒大家一次一个人说，比事后调任何参数都管用。

**▌ 动手验证**

场景：两小时项目评审会，会后二十分钟内产出一份带责任人和截止时间的纪要。

第一步，会前配热词表。在工具的热词/自定义词汇设置里录入：

```
产品代号：星岚、云枢、天池
部门简称：研发中心、增长组、交付一部
高频术语：留存率、复购率、灰度发布、回归测试、埋点
关键人名：（把与会者名单全部录入）
```

这一步两分钟，能消掉后面八成的识别错误。

第二步，录音时把设备放桌子中央，会议开始前让每个人说一句话（"我是张三，负责增长"），方便后续给说话人标注真名。

第三步，上传录音，等转写完成后**先做说话人标注再做摘要**。顺序反了的话，摘要里全是"发言人 3"，责任归属就丢了。

第四步，用固定模板生成纪要。把转写稿连同这段提示词一起交给模型：

```
以下是一场项目评审会的带说话人转写稿。请按固定结构输出纪要。

【会议信息】日期、时长、参会人（从转写稿里能识别到的）

【已决事项】
- 只写会上明确形成结论的事项，格式为「结论 + 谁拍的板」
- 判定标准：有人明确表态"就这么定/同意/按这个来"才算
- 只是被讨论、未形成结论的，一律不要放进这一节

【讨论未决】
- 被提出但没有结论的议题，附上主要分歧点

【待办事项】
- 必须同时具备 负责人 / 具体动作 / 截止时间 三项才能列入
- 格式为「负责人 | 做什么 | 截止时间 | 原话出处（时间戳）」
- 三项缺任意一项的，放进下面的「待确认」节，不要推测补全

【待确认】
- 缺要素的疑似待办，写清缺的是哪一项

规则：
只依据转写稿内容，不要补充任何背景知识和常识性推断；
转写稿里明显是识别错误的词，原样保留并在后面用（?）标注，不要自行改正。
```

倒数第二段的"讨论到 vs 决定了"区分，是这套模板最值钱的部分；最后一句关于识别错误的处理同样重要——**让它标出可疑处，比让它"猜一个通顺的词"安全得多**。

第五步，人工核对三处：已决事项逐条回听时间戳确认、待办的截止时间是否有原话支撑、待确认区的每一条当场找人问清楚。这一步大约五分钟，是整个流程里唯一不能省的。

第六步，把待办落进任务系统。手动录入也行，接自动化流程也行——关键是让它离开文档，进入有提醒机制的地方。

第七步，把纪要发回群里并附一句"有异议请在今天下班前提出"。**给纪要设一个确认截止时间，它才具备事实效力**。

关键心得：这套流程真正省下的不是打字时间，而是"会后谁也想不起来到底定了什么"这件事的返工成本。而它能不能省下这笔成本，取决于你有没有在模板里把"讨论"和"决定"分开。

**▌ 对比选型**

| 决策维度 | 通义听悟 | 讯飞听见 | 飞书妙记 |
|---------|---------|---------|---------|
| 中文识别 | 强，支持中英混 | 精度第一梯队 | 够用 |
| 说话人分离 | 支持并可改名 | 支持 | 支持 |
| 下游打通 | 阿里云生态 | 独立性强 | 文档日历直连 |

选型建议：团队已经在用飞书，直接用妙记，纪要落进文档和任务的链路最短；对识别精度要求极高（访谈、庭审、多方言场景），讯飞听见更稳；需要把转写结果接进自动化流程、作为下游节点输入的，通义听悟这类提供完整接口能力的更合适。三者的模板设计思路完全通用，换工具不用重学。

### 5. 【CodeRabbit 代码评审：让 AI 在合并前把问题拦在 PR 里】

> 📍 **导语**：AI 写代码这件事已经不稀奇了，稀奇的是没人认真处理它带来的副作用——代码产出速度翻了几倍，评审能力却一点没涨。结果是 PR 排队越来越长，评审的人越来越敷衍，最后大家默认"能跑就合"。这个缺口正在被一类工具填上：接在代码托管平台上的 AI 评审机器人。它在你提 PR 的那一刻自动开始读改动、逐行留评论、给出可以一键采纳的修改建议。CodeRabbit 是这类工具里配置粒度最细的一个，同时命令行智能体也提供了自己搭一套的路子——把变更内容管道给 CLI，让它按你的清单过一遍。这两条路的取舍很有意思：前者省心但要接权限，后者可控但要自己维护。这条讲清 AI 评审到底能查出什么、查不出什么，以及怎么配置才不会变成"每个 PR 下面三十条没人看的废话"。

**▌ 它是什么（工具速览）**

CodeRabbit 是一个接在代码托管平台（GitHub、GitLab 等）上的 AI 代码评审服务。装好之后，每当有人开 PR，它会自动做四件事。

第一是**生成变更摘要**：用自然语言说明这个 PR 改了什么、影响了哪些模块，有时还会给出一张流程变化示意。这对评审人的价值被低估了——很多 PR 描述写得极敷衍，摘要至少保证了阅读的起点。

第二是**逐行评论**：针对具体行给出问题描述和修改建议，多数建议可以直接点按钮采纳成一次提交。

第三是**对话式追问**：你可以在评论区直接回复它，让它解释理由、换一种改法、或者告诉它这条不适用。

第四是**规则配置**：通过仓库根目录下的 `.coderabbit.yaml` 定义评审重点、忽略路径、语言偏好、以及要接入的静态检查工具。

另一条路是自建。命令行智能体的无头模式让这件事只需要几行脚本：取出变更、管道给 CLI、附上评审清单、把结果输出到 PR 评论。社区流传的那套自动化评审脚本本质就是 `git diff` 加一段结构化提示词。它的优势是评审标准完全由你定义、代码不经过第三方服务；代价是要自己维护脚本和 CI 配置。

**▌ 它解决了什么问题**

第一是评审带宽跟不上产出速度。AI 辅助编码之后，人均 PR 数量明显上升，而评审人数没变。机器评审补的是这个缺口里最机械的那部分。

第二是低级问题占用了人的注意力。命名不一致、缺空指针判断、日志里打了敏感字段、错误被吞掉——这些问题不需要资深工程师来发现，但如果没人拦，它们就会消耗资深工程师的时间。

第三是评审质量因人而异。同一个 PR 交给不同的人，反馈深度差很多；心情不好或赶进度时，可能就是一句"LGTM"。机器评审至少保证了一条稳定的基线。

第四是新人缺乏即时反馈。新人提交后要等半天甚至一天才有人看，反馈链路太长学不到东西。即时的逐行评论把学习周期压缩到分钟级。

第五是跨语言与陌生模块。评审人对某个语言或某个模块不熟时，很难给出有价值的意见。机器不受这个限制。

**▌ 原理拆解**

用好这类工具，关键在理解它的能力边界，否则很容易走向两个极端：要么全信、要么全关。

第一，**它看到的是 diff，不是整个系统**。它知道你这几行改了什么，但未必知道这个函数在别处被怎么调用、这个字段在数据库里有什么约束。所以它擅长发现"这段代码自身的问题"，不擅长发现"这段代码和系统其它部分的冲突"。**架构层面的问题，机器评审基本查不出来，这部分永远是人的活**。

第二，**它的高价值区间是有明确规则的问题**。空指针、资源未释放、异常被吞、SQL 拼接、硬编码密钥、日志打印敏感信息——这些有确定判据的问题它命中率很高。而"这个抽象合不合理""要不要拆成两个服务"这类判断，它给的意见往往看起来有道理但缺乏依据。

第三，**噪音是这类工具最大的失败模式**。默认配置下它可能对每个 PR 留二三十条评论，其中大半是风格建议。两周之后所有人都会自动无视它的评论，工具就等于没装。**解法是主动收窄评审范围**：把格式和风格类的检查交给格式化工具和静态检查器（它们是确定性的、零误报的），只让 AI 关注逻辑、安全和边界条件。这条原则可以概括成一句话——**能用确定性工具查的，就别用模型查**。

第四，**它必须是建议而不是闸门**。让 AI 评审具备阻塞合并的权力，是常见的踩坑：一旦它误报，整个团队就被卡住，很快就会有人加参数绕过它，绕过一次之后这道防线就名存实亡了。正确定位是：它提意见，人做决定。

还有一条关于成本和隐私的：托管型服务需要把代码交给第三方读取，对代码敏感的团队要走自建路线或选支持私有部署的方案。这不是功能问题，是准入问题，得在选型第一步就明确。

**▌ 动手验证**

场景：给一个正在快速迭代的仓库配上 AI 评审，两周内让它稳定产出有效意见而不制造噪音。

第一步，先把确定性检查做好，再上 AI。这一步顺序不能反：

```bash
# 以 Python 项目为例，先让格式与静态检查兜住风格层
pip install ruff
ruff check --fix .
ruff format .
```

风格问题被机械工具解决掉之后，AI 才有空间去看真正需要判断的东西。

第二步，配置评审范围。在仓库根目录建 `.coderabbit.yaml`：

```yaml
reviews:
  profile: chill            # 先用保守档，减少噪音
  request_changes_workflow: false   # 只提建议，不阻塞合并
  high_level_summary: true
  path_filters:
    - "!**/*.lock"
    - "!**/dist/**"
    - "!**/migrations/**"
  path_instructions:
    - path: "src/api/**"
      instructions: >
        重点检查：入参校验是否完整、错误是否被静默吞掉、
        是否有未处理的边界情况、日志中是否打印了敏感字段。
        不要提出命名风格与格式类建议。
    - path: "tests/**"
      instructions: >
        只检查断言是否真的验证了行为，忽略风格问题。
```

`request_changes_workflow: false` 这一行是最重要的：**先让它当顾问，不要让它当门卫**。

第三步，跑三个真实 PR 做效果校准。逐条给它的评论打标签：有效 / 无效 / 风格噪音。统计比例，无效和噪音超过一半就继续收窄 `path_instructions`。

第四步，如果代码不能出网，改走自建路线。核心脚本很短：

```bash
#!/usr/bin/env bash
set -euo pipefail

DIFF=$(git diff origin/main...HEAD)
[ -z "$DIFF" ] && { echo "无变更"; exit 0; }

printf '%s' "$DIFF" | claude -p "$(cat <<'EOF'
以下是一个 Pull Request 的完整 diff。请按此清单评审：
1 空指针与未初始化引用
2 异常被捕获后静默吞掉
3 输入未校验直接进入查询或命令拼接
4 硬编码的密钥、令牌、内网地址
5 日志或错误信息中打印了敏感字段
6 并发场景下的共享状态写入

输出格式：每条一行，「文件:行号 | 风险等级(高/中/低) | 问题 | 建议改法」
规则：
只报清单内的六类问题，不要提命名与格式建议；
不确定的不要报，宁可漏报也不要凑数；
没有发现问题时只输出一行"未发现清单内问题"。
EOF
)" --output-format json > review.json
```

"宁可漏报也不要凑数"这句必须写。**模型有很强的"必须找出点什么"的倾向，不加这句它会为了显得有用而制造噪音**。

第五步，把它接进 CI，输出到 PR 评论。注意给它只读权限，不要给它写代码或合并的权限。

第六步，建立一条反馈通道。团队在无效评论下回复"这条不适用，因为……"，定期把这些反馈汇总进 `path_instructions`。**这套配置是要养的，不是配一次就完事的**。

第七步，一个月后做一次复盘：统计有多少个真实缺陷是它先发现的。如果这个数字接近零，就该重新审视配置或者干脆关掉——**装了不看的工具比没装更糟，它会给人一种"已经有检查了"的虚假安全感**。

关键心得：AI 评审的价值上限，取决于你有没有把它的关注点收窄到"人容易漏、机器容易查"的那一小块。什么都让它看，等于什么都看不见。

**▌ 对比选型**

| 决策维度 | 托管型 AI 评审 | 自建 CLI 评审 | 静态检查工具 |
|---------|--------------|-------------|------------|
| 接入成本 | 授权即用 | 需写脚本配 CI | 一条命令 |
| 代码是否出网 | 需授权第三方 | 可全内网 | 完全本地 |
| 误报情况 | 需调配置 | 取决于提示词 | 几乎无误报 |
| 擅长问题 | 逻辑与安全 | 自定义清单 | 风格与语法 |

选型建议：风格、格式、语法层面的问题一律交给静态检查工具，这是零误报且免费的；逻辑、安全、边界条件这类需要理解意图的问题才交给 AI；代码不允许出网的团队走自建路线，用命令行智能体加一份评审清单即可。无论哪条路，都不要让 AI 拥有阻塞合并的权力——架构合理性和业务正确性，仍然只能由人判断。

### 6. 【即梦 AI 指令式修图：把抽卡出图变成一句话精确改图】

> 📍 **导语**：用 AI 出图这两年，多数人的体验可以概括成"抽卡"：写一段提示词，生成四张，都不太对，改两个词再来四张，反复十几轮，最后挑一张勉强能用的。这个过程之所以低效，根本原因在于**整图重绘**——每一次生成都是从头画一张新图，上一张里你满意的部分也一起没了。真正把效率拉上来的转折点不是模型画得更好看，而是交互方式从"重新生成"变成了"局部修改"：这张图整体我要，只把桌上那个杯子换成笔记本，别的一个像素都别动。即梦这类国产工具在 2026 年把这套指令式编辑做得相当完整——局部重绘、扩图、消除、参考图控制、多图融合，都能用一句中文指令触发。这条讲清指令式修图和抽卡式生成的机制差别、指令该怎么写才精确、以及它和节点式工作流各自的适用边界。

**▌ 它是什么（工具速览）**

即梦 AI 是字节跳动旗下的 AI 创作工具，覆盖图片生成、图片编辑、视频生成几大块。这里只聚焦其中最实用也最容易被忽略的一块——**图片编辑**。

它的编辑能力可以分成五类，每一类对应一种典型需求。

**局部重绘**：涂抹选中图中一块区域，只让这块区域按新指令重新生成，其余部分保持原样。这是最核心的一项。

**智能消除**：选中不想要的元素（路人、水印、多余的物件），让它填补成合理的背景。

**智能扩图**：把一张构图太紧的图向外扩展，模型补出画面外的内容。做封面时把竖图改成横图，这一项极省事。

**参考图控制**：上传一张参考图，指定让它参考构图、参考风格、或参考人物特征，再结合文字指令生成。这解决了"风格描述不清楚"这个老问题——直接给图比写一百个形容词准。

**多图融合**：把两张图的元素合成一张，比如把 A 图的人物放进 B 图的场景。

另外有一个大幅提升效率但常被忽略的功能是**智能画布**：它把生成、编辑、扩图、拼接放在同一块无限画布上，你可以在一张图旁边直接派生变体，所有中间版本都保留着，方便对比和回退。

**▌ 它解决了什么问题**

第一是整图重绘导致的成果丢失。抽卡最痛的不是画得不好，是这一张的人物对了但背景错了，重新生成之后人物又变了。局部编辑把"已经对的部分"锁住。

第二是提示词描述能力的天花板。很多视觉要求根本没法用文字准确表达——某种特定的构图、某种质感、某个人物的长相。参考图控制绕开了语言这个瓶颈。

第三是修图的技能门槛。抠图、消除、扩展背景，用传统图像软件做需要专门训练。指令式操作把这些压缩成涂抹加一句话。

第四是版本管理的混乱。抽卡产出几十张图散落在下载文件夹里，事后完全分不清哪张是哪个版本的衍生。画布形态天然保留了派生关系。

第五是中文语境的适配。国际工具对中文指令的理解、对中式审美和中文排版的处理，长期是弱项。这也是国产工具在本地场景里更好用的主要原因。

**▌ 原理拆解**

理解三件事，你就知道为什么有的指令一次就成、有的改十次都不对。

第一，**局部重绘的本质是带上下文的填充**。模型看到的是：你涂掉的那块区域（要重画）、以及周围没涂的部分（作为上下文）。它要生成的内容必须和周围衔接得上。这条推论直接指导涂抹范围：**涂太小，模型没有腾挪空间，生成的东西会被挤变形；涂太大，会连带改掉你本来满意的部分**。经验值是比目标物体外扩一圈，把它的影子和接触边缘也涵盖进去。

第二，**指令要描述"最终画面应该是什么"，而不是"你要做什么改动"**。这是最常见的失误。写"把杯子删掉"，模型不知道那个位置该出现什么，可能补出一片诡异的糊斑；写"桌面上是空的木质桌面，有自然的木纹和轻微反光"，它就知道该画什么。**动词式指令给模型的信息量远小于名词式描述**。

第三，**参考图的作用维度必须显式指定**。同一张参考图，你可以要它的构图、要它的配色、要它的笔触、要它的人物特征。不指定的话模型会自己权衡，结果往往是"哪个都像一点，哪个都不到位"。**明确说清"只参考构图，不要参考配色"，成功率立刻上一个台阶**。

还有两条实操规律。其一，**分步改比一次改准得多**。一句话里塞三个修改要求（换背景、改衣服颜色、加一个物件），模型大概率只完成其中一两个。拆成三次，每次只改一件事，总耗时反而更短。其二，**扩图要一次扩一小段**。想把竖图扩成宽幅横图，一次扩到位会让模型在缺乏上下文的区域瞎编；分两三次每次扩一部分，每次都有前一次的结果作参考，连贯性明显更好。

最后是边界：**它擅长的是视觉调整，不擅长精确的文字与数字**。图里要出现准确的中文标题、精确的数据标签、规范的品牌标识，仍然要在设计软件里加文字层。指望模型把一行字画对，是这类工具最常见的期望错配。

**▌ 动手验证**

场景：把一张手机拍的产品照，改成能直接放进方案里的横版配图。

第一步，先明确终点再动手。写下三句话：最终尺寸、最终风格、必须保留的元素。跳过这一步就会陷入越改越乱。

第二步，先消除干扰项。上传图片进入编辑，涂抹背景里的杂物，指令这样写：

```
涂抹区域：替换为干净的浅灰色纯色背景，
带有从左上到右下的柔和渐变，无任何物体、无阴影、无纹理。
保持画面中央的产品完全不变。
```

注意最后一句。**每条指令末尾都加一句"保持某某不变"，是降低误伤概率最有效的做法**。

第三步，扩图成横版，分两次做。第一次：

```
向左右两侧各扩展画面，延续现有的浅灰渐变背景，
保持光线方向与原图一致（光源在左上方），
不要在扩展区域添加任何新的物体或文字。
```

看结果满意再做第二次扩展。**一次扩到位是这一步最常见的翻车原因**。

第四步，用参考图统一风格。上传一张你方案里已有配图作为参考，指令：

```
参考上传图片的配色方案与光影风格，
只参考配色和打光，不要参考其构图与物体，
将当前图片调整为同一视觉风格。
```

明确写"只参考什么、不要参考什么"，这句是成败关键。

第五步，做局部精修，一次只改一件事：

```
涂抹区域（产品右下角）：添加一道柔和的落地投影，
方向与左上方光源一致，边缘虚化，透明度约百分之二十，
不要改变产品本身的任何细节。
```

第六步，文字一律不在这里做。导出图片后，到设计软件或演示工具里叠加文字层。**图上的字交给模型画，几乎必然出错**，这是硬边界不是技巧问题。

第七步，做输出前检查三项：手部与文字等易崩区域有没有明显异常、放大到实际使用尺寸后细节会不会糊、图里有没有意外出现的水印或伪造标识。第三项在对外使用时尤其要看。

第八步，把有效的指令存成模板。你会发现自己反复用的就那么五六句（消除背景、扩图、加投影、统一风格），存成一份文本随手复制，比每次现写快得多。

关键心得：指令式修图真正的技巧不在词藻，而在**每次只改一件事、每次都说清哪些不要动**。掌握这两点，改图从抽卡变成了可预期的工序。

**▌ 对比选型**

| 决策维度 | 即梦指令修图 | 节点式工作流 | 传统图像软件 |
|---------|------------|------------|------------|
| 上手门槛 | 涂抹加一句话 | 需搭节点 | 需专业训练 |
| 单次精修 | 快且直观 | 偏重 | 最精确 |
| 批量一致产出 | 较弱 | 强项 | 需动作脚本 |
| 中文指令理解 | 针对中文优化 | 依赖模型 | 不涉及 |

选型建议：单张图的临时修改、方案配图、社交内容，指令式修图最快；同一套参数要跑几百张、需要严格复现的产线型需求，节点式工作流才划算；涉及精确文字排版、印刷规格、品牌视觉规范的最终交付，仍然要回到设计软件。常见的组合是：模型出素材，设计软件做定稿。
