### 1. 【Xcode 27 打通 ACP 协议：第三方编码 Agent 直连 IDE，补全全程端侧】

> 📍 **导语**：Xcode 27 beta 5（Build 27A5237l）于 8 月 10 日推送，内置 Swift 6.4，预计随秋季新机进入稳定通道。这一代 Xcode 最值得关注的不是某个单点功能，而是把 AI 能力拆成了三层可插拔架构：内置 Agent、任意兼容 Agent Client Protocol（ACP）的第三方 CLI、以及只能问答的 Chat Provider。配合新增的 Device Hub，编码 Agent 第一次可以自己跑测试、自己看预览、自己在模拟器上验证改动，而行内补全则完全跑在本机神经网络引擎上，源码不出机器。

**核心信息**

Xcode 27 的 AI 能力分层很清晰。第一层是内置 Agent，Apple 直接把 Anthropic、Google、OpenAI 的模型接进了工作流，支持交互式规划（Agent 先列方案、开发者确认后逐步执行）、多轮 Q&A、以及能渲染 Markdown 并把代码变更与预览并排展示的画布。第二层是自定义 ACP Agent——ACP 是一个开放协议，作用类似 LSP：LSP 标准化了编辑器与语言服务器的通信，ACP 标准化了编辑器与编码 Agent 的通信，传输方式为 stdio。Xcode 27 原生实现了 ACP，因此任何兼容该协议的 Agent CLI 都能挂进来，截至 2026 年 8 月官方注册列表已收录 37 个以上 Agent。第三层是 Chat Provider，可以接 Ollama 本地模型或 DeepSeek API，但只能聊天，碰不到项目文件。

注册路径是 Settings → Intelligence → Agents → Add an Agent，需要填 Agent 名称、可执行文件绝对路径（用 `which` 拿到）与启动参数，Interpreter 留空。几个常见 Agent 的启动参数形如：

```bash
# 各家 ACP Agent 的启动方式差异不小，注册时按官方文档填
codebuddy --acp
qwen --acp
opencode acp
copilot --acp
gemini --experimental-acp
```

Agent 模式与 Chat 模式的边界必须分清：Agent 能自主读写文件、运行构建、看报错再修，是闭环工作流；Chat 本质上仍是一个聊天窗口。Xcode 27 还支持用插件扩展自定义 skill，通过 Model Context Protocol 引入日常工具，GitHub 与 Figma 是首批实现无缝安装的合作方。Beta 3 之后的 Release Notes 里，Coding Intelligence 一栏记录了 Xcode 的 build 与 test MCP 工具改为向外部 MCP 客户端发送动态活动状态，而不再是静态文本；同时明确了一个已知问题：如果 plan-mode 的确认条在 Agent 仍在流式输出时弹出，点击 Yes/No 可能在未完成的回合上再触发一个新回合，导致会话状态错乱，规避办法是等输出结束再确认。

**影响判断**

真正的分水岭在硬件与协议两侧。硬件侧，Xcode 27 是第一个仅支持 Apple Silicon 的版本，Intel Mac 彻底出局，beta 3 起要求 macOS Tahoe 26.4 或更高；换来的是安装包体积比 Xcode 26 缩小约 30%、启动与配置更快，Xcode Cloud 构建最高提速一倍并新增 Metal 与 visionOS 构建支持。这意味着仍在用 Intel 机器做本地开发或自建 CI 的团队，必须先完成机器更替才能谈升级，采购与调试周期要提前排。协议侧，ACP 的意义是把"换 AI 工具等于换生态"的锁定关系打开了：以前各家 IDE 与 AI 工具走私有协议，现在至少在 Xcode 这一侧，模型与 Agent 成了可替换组件。对国内团队来说这条尤其实际——受合规与网络条件限制，接本地或国产 Agent 往往是唯一可行路径，而 ACP 让这件事从"魔改插件"变成了填三个字段。建议的落地顺序是：先在非核心仓库试跑一个 ACP Agent，观察它在 Device Hub 里的自验证能力是否真能减少来回描述屏幕状态的成本，再决定是否推广到主干。需要提防的风险是 Agent 自主运行时长变长后的失控面：它能改文件、跑构建，也就意味着一次错误的规划可能污染工作区，权限模式与沙箱隔离应当在推广前先定好。

### 2. 【Liquid Glass 兼容开关被移除：iOS 27 界面适配再无退路】

> 📍 **导语**：iOS 26 时代 Apple 给开发者留过一条缓冲通道——在 Info.plist 里写入 `UIDesignRequiresCompatibility`，即使用最新 SDK 打包也能保留旧版界面。到了 iOS 27 与 Xcode 27，这个开关被完全忽略。更关键的是，它不是孤立事件：UIScene 生命周期从"未来会强制"变成了"现在不迁移就崩"，App Store Connect 也新增了缺失启动屏的拒审码。三项 SDK 级硬约束叠在一起，构成了近年 Apple 推得最狠的一次强制迁移。

**核心信息**

第一项是 UIScene。iOS 26 时期用最新 SDK 构建，调试器里会打印"UIScene lifecycle will soon be required. Failure to adopt will result in an assert in the future"。按 Apple 技术说明 TN3187，从 iOS 27 起，用最新 SDK 构建且未迁移到场景生命周期的应用会在启动时断言失败，直接崩在 AppDelegate 之前。修法是 Info.plist 必须包含 `UIApplicationSceneManifest`，并提供实现了 `scene(_:willConnectTo:options:)` 的 SceneDelegate，把启动逻辑从 AppDelegate 搬过去。这一项应当排在最前面处理，因为它是唯一会导致应用起不来的改动。

第二项是启动屏。iOS 27 引入 ITMS-90870 拒审码：用 iOS 27 SDK 或更高版本构建的应用必须在 Info.plist 中声明启动屏，App Store Connect 会检查 `UILaunchStoryboardName`、`UILaunchStoryboards`、`UILaunchScreen`、`UILaunchScreens` 四个键中至少存在一个。近几年新建的工程大多已具备，容易踩坑的是老项目和从别的模板迁移过来的工程。

第三项才是 Liquid Glass。它约束的是系统原生控件，而非强行改写应用全部页面——自绘页面、品牌配色、独立实现的特殊按钮仍保留设计主权。但导航栏、底部标签栏、弹窗、滑动控件会自动切到新材质，重编译即生效，没有开关可关。实际会坏在两类地方。一是硬编码的栏高：Liquid Glass 的标签栏浮在内容之上并随滚动收缩，`safeAreaInsets` 本身会变，写死 49pt 的偏移会让按钮行沉到栏后面。

```swift
// 旧写法：按标签栏高度硬抬
VStack { WallpaperCanvas(item: item); ActionBar(item: item).padding(.bottom, 49) }

// 新写法：让系统告诉你需要留多少
VStack { WallpaperCanvas(item: item) }
    .safeAreaInset(edge: .bottom) { ActionBar(item: item) }
```

二是自定义不透明背景：用 `UINavigationBarAppearance` 的 `configureWithOpaqueBackground()` 加品牌色，会与玻璃材质互相打架，渲染出没人设计过的浑浊结果，需要改为让材质透出内容或改用系统提供的容器样式。

**影响判断**

一个流传很广但不准确的说法是"2027 年 4 月起 App Store 会拒绝未适配 Liquid Glass 的构建"。截至 7 月末，Apple 的 Upcoming Requirements 页面与 WWDC26 的 App Store 指南都没有列出这条，唯一在执行的 SDK 底线是自 2026 年 4 月 28 日起提交必须用 Xcode 26 及 iOS 26 SDK 构建。也就是说，工程量是真的，挂在上面的那个截止日期是想象出来的——真正的实际期限是今年秋季正式版落地那一刻，因为那时重编译就会改变外观。测试策略上有一条容易被忽略：Liquid Glass 是 GPU 实时渲染系统，镜面高光、内容实时采样与随运动的形变在模拟器里无法完整还原，Mac 上看着正常的界面到真机上可能不可读或错位，因此必须准备覆盖各档位的少量真机做回归。一个更普适的教训是：凡是把栏高、安全区数值当常量写死的代码，这次会坏，下一次某个东西开始浮动或收缩时还会再坏一遍。趁这轮迁移把这些常量清掉，收益会持续到下一个大版本。

### 3. 【Foundation Models 框架转向可插拔：端侧 3B 模型与结构化输出】

> 📍 **导语**：Xcode 27 随 iOS 27 SDK 一并开放的 Intelligence Frameworks，把 Apple 的 AI 栈拆成了两层：上层是 Foundation Models 框架，下层是 Core AI Framework 引擎。变化的关键在于 Foundation Models 现在暴露出一个语言模型协议，除系统端侧模型与私有云计算外，还能接第三方模型与本地 MLX 模型；配合 Dynamic Profiles，模型行为可以在不发版的前提下更新。对开发者而言，这意味着"用哪个模型"第一次从核心业务逻辑里被剥离了出去。

**核心信息**

先说端侧模型本身的规格边界，这决定了它能干什么。系统语言模型约 30 亿参数，量化到 2 bit，每个会话上下文窗口 4096 tokens，拉丁语系约 3-4 个字符一个 token，中日韩文字约一个字符一个 token。它内置于操作系统，不增加应用体积，无需 API 密钥，可用设备为搭载 A17 Pro 及更新芯片的 iPhone 与 M 系列的 iPad、Mac。它被调优的方向是摘要、实体抽取、文本分类、文本撰写、标签生成、游戏对话；不擅长的是数学与计数、代码生成、复杂多步推理与世界知识。把它当成一个"本地语义处理器"而不是"本地 ChatGPT"，选型时才不会错配。

工程上有三个必须掌握的模式。第一是可用性检查，任何调用前都要走一遍：

```swift
import FoundationModels
let model = SystemLanguageModel.default
switch model.availability {
case .available: break
case .unavailable(.deviceNotEligible):          break  // 设备不支持
case .unavailable(.appleIntelligenceNotEnabled): break  // 用户未开启
case .unavailable(.modelNotReady):               break  // 模型仍在下载
case .unavailable: break
}
```

第二是引导式生成。与其让模型吐 JSON 字符串再解析，不如用 `@Generable` 定义 Swift 类型，让约束解码直接产出合规实例，`@Guide` 可以给字段加语义描述与取值约束——数值走 `.range(1...10)`、数组走 `.count(3)`、字符串走 `.anyOf([...])` 或正则。这条把"解析不可靠 JSON"这个老问题从工程链路里删掉了。第三是工具调用：实现 `Tool` 协议，声明 name、description 与 `@Generable` 的 Arguments，把日程、地图或后端触发包成模型可调用的能力，创建会话时用 `LanguageModelSession(tools: [...])` 注入，并对 `LanguageModelSession.ToolCallError` 做兜底。此外还有快照流式输出，可以把结构化结果的增量推给界面，做实时渲染。

**影响判断**

真正的战略变化是"模型提供方可替换"。以前把端侧模型写进业务代码，等于把一个能力天花板焊死在版本里；现在协议化之后，同一套业务逻辑可以在系统端侧模型、私有云计算、第三方云模型与本地 MMLX 模型之间切换，甚至通过 Dynamic Profiles 在线调整行为。这让"端侧优先、云端兜底"的分级架构第一次可以写得干净：短摘要、标签、意图分类交给端侧，长文档与复杂推理路由到云端，切换点只存在于配置而非代码。落地时要盯住三处风险。一是 4096 tokens 的会话上下文非常紧，做长文摘要必须自己切块并管理中间状态，否则会静默截断。二是可用性分支不是可选项：设备不合格、用户未开启 Apple Intelligence、模型仍在下载都是常态，缺少兜底的功能在真机上会大面积不可用，产品侧需要接受"这个功能只对部分用户存在"。三是不要把它当作零成本方案的全部——虽然没有按 token 计费，但持续推理会带来发热与耗电，长时任务仍应上云。学习优先级上，`@Generable` 与 `@Guide` 的约束建模比提示词技巧更值得先花时间，因为它决定了输出能否直接进类型系统；其次是 Tool 协议，它是把系统智能接入自家业务的唯一正规入口。

### 4. 【HarmonyOS 7 智能体框架 2.0：应用 Skill 化与 GUI 操控开放】

> 📍 **导语**：HDC 2026 上，HarmonyOS 7（API 26）开发者 Beta 亮相，主题词是"意图即服务"。它把端侧大模型放进了系统底层，并通过升级到 2.0 的鸿蒙智能体框架开放二十余项系统级 AI 能力。对开发者最直接的影响是两件事：业务能力可以封装成 Skill 被系统 AI 小艺直接调用；GUI 操控能力对外开放，应用可以完成页面跳转与控件交互，从被动等用户点击变成能自主完成任务的智能体。这不是一次版本迭代，而是开发范式的位移。

**核心信息**

智能体接入的骨架是三段：注册智能体、端侧模型推理、意图与 Skill 的匹配路由。注册部分用 ArkTS 声明能力与参数 schema，供系统做意图匹配：

```typescript
import { agentService } from '@kit.AgentKit';

@agentService.AgentExtension
export default class MarathonAgent extends agentService.AgentExtension {
  declareCapabilities(): agentService.Capability[] {
    return [{
      id: 'sign_up.marathon',
      description: '报名某场马拉松赛事',
      inputSchema: {
        type: 'object',
        properties: {
          race:     { type: 'string', description: '赛事名称' },
          date:     { type: 'string', description: '比赛日期' },
          location: { type: 'string', description: '举办城市' }
        },
        required: ['race', 'date']
      }
    }];
  }
}
```

环境要求相对明确：DevEco Studio 5.x 及以上以支持 HarmonyOS SDK 26，系统 SDK 为配套 HarmonyOS 7 开发者 Beta 的 SDK 26，相关套件包括 Agent Framework Kit（智能体框架）与 MindSpore Lite Kit、CANN Kit（端侧推理），运行设备建议用带 NPU 加速的麒麟芯片真机而非模拟器。端侧的另一张牌是记忆：日程、位置、习惯、偏好等两百余项系统级用户数据在本地持久化，配合全天候智能感知引擎，让系统助手随使用逐步贴合个人偏好。而 A2UI 与 GUI 操控能力让智能体可以读取屏幕、模拟点击、调用无障碍服务——换句话说，即便一个应用没有开放任何接口，也能被智能体调度，端侧"看屏操作"成了通用手脚。系统底座同步升级：方舟引擎搭载性能大模型，实现系统资源的 AI 动态调度，冷启动、页面流转与多设备协同性能进一步优化；渲染侧新增沉浸光感组件，支持光线勾勒、材质渲染与非线性动效；主题开发开放熄屏显示、互动锁屏、动态材质等接口。

**影响判断**

Skill 化改造的本质是分发入口的重新划分。过去用户找服务的路径是打开应用、进入页面、完成操作；Skill 化之后，语音或意图直接命中能力，中间的界面层被系统绕过。这对开发者是双刃剑：好处是获客路径变短、长尾能力可能被系统主动调起；代价是流量分配权与用户注意力的第一现场上移到了系统助手，应用有可能退化成后端能力池。更值得警惕的是 GUI 操控——"没有开放接口的应用也能被智能体调度"，意味着不主动接入并不等于免受影响，反而可能被以最不可控的方式（读屏 + 模拟点击）驱动。因此更务实的策略是主动定义好 Skill 的粒度与边界：把明确、幂等、参数清晰的能力开放出去，把涉及支付、隐私与不可逆操作的环节保留在自有界面内，并要求二次确认。工程节奏上，当前是开发者 Beta，API 与行为仍会变动，建议先用一个非核心能力打通注册与意图匹配全链路，摸清 schema 描述质量对匹配准确率的影响——描述写得含糊，意图路由就会错配，这部分几乎没有捷径，只能靠真机反复调。技能储备上，ArkTS 之外，端侧推理套件与意图建模会成为鸿蒙开发者今年最具区分度的能力。

### 5. 【DevEco Code 进入鸿蒙工具链：AI 故障分析随 Beta2 上线】

> 📍 **导语**：如果说智能体框架改变的是应用运行时，那 DevEco Code 改变的是开发时。新版 DevEco Studio 配套了鸿蒙编程智能体 DevEco Code，集成开发知识库，支持 AI 辅助编码、问题诊断、代码重构与 Skill 一键生成；而 HarmonyOS 7 API 26 Beta2 更进一步，把 AI 辅助的应用故障分析做进了 IDE，用于发现与定位稳定性问题。与此同时，26.0.0 Beta1/Beta2 的行为变更清单在 8 月 4 日完成更新，存量应用的兼容基线随之改写。

**核心信息**

AI 故障分析的定位是压缩平均修复时长。它直接集成在 DevEco Studio 环境内，走本地推理以保证代码与日志隐私，模型面向历史崩溃日志与栈回溯模式做过针对性调优，输出的是根因分析报告并给出代码级修改或配置调整建议。工程上它挂在系统的 FaultLogger 服务上实时拦截运行时异常，栈回溯解释支持 ArkTS 与 C/C++ 双栈——这一点对混合栈应用意义不小，过去 native 崩溃的定位往往要人工在两套符号表之间来回比对。相比 Crashlytics 一类云端方案，它的差异化在于系统级集成与设备侧推理，代价是生态覆盖面仅限鸿蒙。

真正需要逐条比对的是行为变更。按官方 26.0.0 Beta1 与 Beta2 汇总（更新时间 2026-08-04），影响面较大的几类是：ArkTS 侧 JSVM 支持 Wasm 解释器，jitless 默认行为发生变更，async 函数类型判定得到修复，ConvertXML 的 `fastConvertToJSObject` 修复了解析时丢失同级 text 节点的问题；ArkUI 侧 NodeAdapter 的 `onAttachToNode` 回调触发时机变更，鼠标事件 `rawDeltaX/rawDeltaY` 返回值变更，`LayoutPolicy.matchParent` 在父组件为 Row、Column、Flex 时单方向设置的子组件布局行为变更，`@ReusableV2` 复用的 reuse 属性支持动态复用标识，组件阴影模糊半径规格变更，Beta2 又追加了 List 组件 `onScrollVisibleContentChange` 事件行为变更；ArkWeb 侧 Beta2 变更了 Cookie 存储目录；权限侧 `ohos.permission.READ_IMAGEVIDEO` 权限变更全量生效，Network Kit 的 `getUidRxBytes`、`getUidTxBytes` 接口权限收紧。UX 层面同样有硬性影响：表单类组件触摸热区最小高度变更，内置文本组件样式优化，Dialog、Toast、AlphabetIndexer 与文本选择菜单默认开启沉浸式系统材质，半模态居中弹窗最大高度变更。生效规则要分两类读——一部分标注"全部生效"，无论目标版本都会命中；一部分标注 `targetSdkVersion ≥ 26.0.0` 才生效，可以通过暂不提升目标版本来推迟。

**影响判断**

这两条线合起来给出的信号是：华为正在把 AI 从"辅助写代码"推进到"辅助维护代码"。故障分析比代码补全更难，也更有价值——补全错了顶多浪费几秒，根因分析错了会把团队引向错误方向，所以它的实际效果高度依赖对本地崩溃语料的拟合程度，短期内更适合当作首轮筛查而非结论。落地建议是搭一个 API 26 Beta2 的测试工程，把过去半年真实的崩溃与稳定性缺陷回灌进去，看它对已知答案的命中率如何，再决定要不要进主干流程。行为变更的处理次序也应当明确：先扫"全部生效"那一档，因为它无法通过不升目标版本规避；再排 `targetSdkVersion ≥ 26.0.0` 的一档，按业务优先级排进迭代。触摸热区最小高度与默认沉浸式材质这类 UX 变更最容易被漏掉，因为它们不报错也不崩溃，只是让界面在真机上悄悄错位一两个像素或对比度不足，必须靠视觉回归而非单元测试来兜。工具链 AI 化在缩短从想法到 HAP 上线的周期，但它同时提高了对基线纪律的要求：变更清单不逐条对，AI 也救不回来。

### 6. 【Android 17 大屏可调整尺寸强制生效：竖屏锁定失效与 Compose 优先】

> 📍 **导语**：Android 17 稳定版已于 6 月 16 日在 Pixel 落地，对应 API 37，Google 给它的定位是"adaptive-first"。最容易让团队措手不及的一条是：应用一旦以 API 37 为目标，在最小宽度大于 600dp 的设备上，系统会直接忽略清单里的方向与尺寸限制。竖屏锁定这个多年惯用的"安静修法"就此失效，而 Google Play 要求目标为 API 37 的期限是 2027 年 8 月——听起来遥远，但 Android 17 设备上的用户今天就已经在撞上这件事。

**核心信息**

被忽略的具体是四个清单属性——`android:screenOrientation`、`android:resizableActivity`、`android:minAspectRatio`、`android:maxAspectRatio`，运行时调用 `setRequestedOrientation()` 同样会被丢弃，按 Play 分类判定的游戏例外。后果并不含蓄：布局被拉伸、相机预览旋转后没做补偿、动画裁切到屏幕外、从未在竖屏视口之外测过的组件直接错乱。大量应用多年来用 `resizeableActivity="false"` 当补丁，这些应用在新一代折叠屏硬件上已经是坏的，而开发者往往不知道，因为他们不在折叠屏上测。同时配套改了另一件事：大屏上常见的配置变更不再默认重建 Activity，也就是说假定每次尺寸变化都会走一遍 `onCreate()` 的代码需要搬家。

```kotlin
class MainActivity : ComponentActivity() {
    override fun onConfigurationChanged(newConfig: Configuration) {
        super.onConfigurationChanged(newConfig)
        // 别再假定每次 resize 都有全新的 onCreate()
        updateLayoutForWindowSize(newConfig.screenWidthDp)
    }
}
```

正确的适配路径不是改一行清单，而是用 `WindowSizeClass` 做断点决策、保证旋转与折叠时的状态保留、并在折叠、展开、分屏三种姿态下逐一测试。除此之外，API 37 还带来一批需要真实工程量的改动：新增 `ACCESS_LOCAL_NETWORK` 运行时权限，此前对用户完全隐形的局域网扫描（mDNS 发现、投屏、IoT 设备扫描）现在需要显式申请；运行时施加严格内存上限并会终止超限进程，R8 与配置分析器从可选项变成必需项；以 SDK 37 为目标时 `android.os.MessageQueue` 走无锁实现，减少掉帧并加快初始化，但反射私有字段的代码会出问题；ART 引入分代垃圾回收，短生命周期对象无需全堆扫描即可回收；`static final` 字段变成真正的 final，用反射或 JNI 改写会抛错甚至崩溃。交互层面则是 App Bubbles 与 Bubble Bar 让任意应用可被长按变成浮动窗口，桌面模式下的画中画从只读变成可交互，Continue On 能把手机上的任务接力到附近平板。

**影响判断**

Google 在开发者活动上给出的方向更值得注意：Compose 优先，新代码与新功能建议直接用 Compose 写，Fragments、RecyclerView、ViewPager 只接收关键修复，Views 体系即将进入维护模式；新增的 AppFunctions 库允许把带注解的 Kotlin 代码转成可被端侧助手发现的函数调用，相当于 Android 侧的端侧工具协议。支撑这套判断的数字是活跃大屏设备已突破 5.8 亿，覆盖折叠屏、平板、桌面窗口、电视、车机与 XR。落地节奏建议这样排：本周就在 Android 17 模拟器上跑一遍自家应用，开自由窗口模式手动缩放，看什么先坏；然后按"必须改"排序——大屏自适应、`ACCESS_LOCAL_NETWORK`、以及仍在 ExoPlayer 2 的团队向 Media3 的迁移；系统联系人选择器、验证码短信延迟一类属于低成本或对规范应用透明的改动，按常规迭代节奏消化即可。最容易犯的错是把 2027 年 8 月当作起跑线：真正的成本在自适应 UI 审计，那是按迭代周期计的工作量，而不是一个发版前的检查项。技能优先级上，`WindowSizeClass` 与自适应导航的建模能力，今年对 Android 开发者的区分度会高于任何单一新 API。

### 7. 【Compose Multiplatform 1.12.0：Hot Reload 接入 MCP 让 Agent 自验 UI】

> 📍 **导语**：JetBrains 交付 Compose Multiplatform 1.12.0，三个看点集中在为 AI 编程助手提供官方工具链支持、补齐 Web 端字体渲染短板、以及重构桌面端窗口管理 API。其中最具方法论意义的是 Compose Hot Reload 新增的实验性 Model Context Protocol 服务器——它给 AI 助手装上了眼睛和手，让 Agent 改完代码能自己确认是否生效，而不是等开发者用文字描述屏幕上发生了什么。

**核心信息**

MCP 服务器的能力清单是：触发重载、截屏、检查语义树、模拟点击与文本输入、读取应用日志。这些拼起来构成一个闭环——Agent 改代码、确认热重载成功、看渲染结果、捕获运行时异常、继续迭代修复，整个过程不需要人把界面状态翻译成自然语言。这解决的是 AI 辅助 UI 开发里最真实的摩擦：过去要在对话里说"左边那个按钮没对齐"，现在它自己截图就能看到。需要注意这个功能仍是实验性的，工具列表与连接方式要查 Compose Hot Reload 官方文档。

Web 端补的是字体回退。此前应用字体未覆盖的字符会渲染成替换字形，也就是俗称的"豆腐块"。1.12.0 引入按需下载匹配的 Noto 字体子集并对受影响文本重新组合的机制，日文、阿拉伯文、天城文与 emoji 无需手工打包字体即可正确显示，代价是字体拉取完成前可能短暂出现豆腐块。桌面端引入位于 `androidx.compose.ui.window.v2` 包的实验性 v2 窗口与对话框 API，能选择窗口出现在哪块屏幕、提供自定义定位与尺寸逻辑（含基于内容固有尺寸的逻辑）、设置最小与最大窗口尺寸、把对话框相对父窗口定位；更重要的是它把窗口状态变更的异步本质显式化了，区分"请求的状态"与"当前实际状态"：

```kotlin
val windowState = rememberWindowState(
    initialBoundsProvider = WindowBoundsProvider(
        positionProvider = WindowPositionProvider.CenteredOnScreen,
        sizeProvider = WindowSizeProvider.Fixed(DpSize(400.dp, 200.dp))
    )
)
```

用 `WindowSizeProvider.Unconstrained` 则可以让窗口初始尺寸贴合内容，同时保留内容在用户放大窗口时用 `fillMaxSize()` 撑开的能力。跨平台层面，Skiko 携带的 Skia 从 Milestone 144 升到 150，顺带解决了自带 Skia 库的应用（例如 Chromium 系）在 iOS 上的重复符号冲突；iOS 端惰性布局滚动性能改善，列表项的失活操作被移出绘制阶段，绘制阶段更快结束，滚动更顺。

**影响判断**

升级前必须先看依赖链条。Compose BOM 2026.08.00 于 8 月 12 日交付，带来核心模块的 Compose 1.12，而 Compose 1.12 把 compileSdk 提到 API 37，并要求 Android Gradle Plugin 至少 9.1.1——AGP 落后的构建必须先完成升级才能采用当前 Compose 线，这属于典型的升级排序问题，不能跳步。Kotlin 侧当前稳定版为 7 月 14 日的 2.4.10，是缺陷修复版本；能力性变化在 6 月 3 日的 2.4.0：语言侧稳定了上下文参数与显式后备字段，Kotlin/Native 支持把 Swift 包作为依赖并默认启用并发标记清除垃圾回收，Kotlin/JVM 支持 Java 26。"Swift 包可作依赖"这一条对跨平台决策的分量最重——它决定了共享 Kotlin 模块是能直接消费 iOS 生态，还是必须手写桥接。生态数据上，klibs.io 收录的社区库从此前的三千五百余个增长到 8 月的四千一百个以上。选型判断可以更直接一些：共享逻辑的回报快于共享 UI，网络、模型、校验与离线同步这一层的同一个缺陷否则要在两端各修一遍且修法不同；共享 UI 的回报出现在设计体系本来就统一、且产品不靠平台原生质感竞争的场景，代价是 iOS 包体相比同等 SwiftUI 实现约多出 9MB——这是一笔真实但不大的开销，真正的成本在团队形态与界面惯例上。
