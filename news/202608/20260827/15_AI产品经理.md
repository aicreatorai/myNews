### 1. 【PM 写 prompt 的协作：把产品需求转译为可复用的提示词资产】

**导语**
很多团队把"写 prompt"当成工程同学的临时手艺活：产品口头描述需求，研发现编一段提示词丢进模型，跑通就上线，跑不通再改。这种"一次性提示词"在项目早期看似高效，一旦功能要迭代、要多人协作、要跨版本回归，就会迅速失控——没人记得某段提示词为什么这么写，改一个字全盘行为漂移，新同事接手只能从头猜。对 AI 产品经理而言，提示词不应是临时脚本，而应被视为和组件、接口文档同等重要的"产品资产"，需要被命名、被评审、被版本化。

**它是什么**
把"写 prompt"升级为"提示词资产管理"，核心是把产品需求结构化地转译为模型可消费的输入，并让它在团队内可复用、可追溯、可版本化。业界已经沉淀出若干框架：例如 CRISP 框架（Context 上下文、Role 角色、Instruction 指令、Specifics 细节、Parameters 参数）强调用固定槽位拆解需求，避免遗漏关键约束；Atlassian 提出的"Golden Prompts（黄金提示词）"概念，指那些被跨职能团队（产品、设计、研发、支持）共同认可并复用的标准提示词，类似设计系统中的"主组件"。换句话说，提示词资产 = 被命名、被评审、被版本管理、能被他人直接调用的产品构件，而不是某个人本地记事本里的一行文本。

**解决什么**
它解决三类典型痛点。第一，协作黑盒：产品说不清需求，研发猜着写提示词，验收时双方对"好"的标准不一致，返工来回扯皮。第二，返工浪费：同一功能在多端、多模型上重复写提示词，缺少统一基线，每次都从零造轮子。第三，回归风险：模型或需求一变，旧提示词行为不可复现，线上悄悄劣化却无人察觉。将提示词资产化后，产品可以像维护 PRD 一样维护"提示词规格"，据 CSDN 工程复盘，建立跨团队提示词库后提示词返工率可下降约 67%，因为大部分场景直接复用已验证的 Golden Prompts 而非从零编写，新功能也能站在既有资产上组合而非重写。

**原理拆解**
资产管理有四个可操作支柱。① 结构化模板：用 CRISP 这类槽位把"角色 / 上下文 / 任务 / 约束 / 输出格式 / 负面约束"固化，产品填槽、模型消费，降低对个人的依赖。② 提示词注册表（Prompt Registry）：集中存放命名提示词，每条带 owner、用途、适用模型、变更日志，类似内部 API 目录。③ 版本化（SemVer）：提示词像代码一样打 v1.0.0 / v1.1.0，重大行为变化跳主版本，便于灰度与回滚，出问题一键切回旧版。④ 跨职能评审：Golden Prompts 需产品、研发、合规共同签署，类似 API 契约评审。traversaal.ai 的实践指出，system prompt 本质上是"产品决策的外化"——哪些语气、哪些边界、哪些不许做，都是产品判断，必须显性沉淀而非藏在研发脑子里，否则决策权与责任错位。

**动手验证**
你可以本周就在团队里落地最小版本：① 建一个共享文档或内部库，命名前 5 条高频提示词（如"摘要生成""分类打标""客服话术"）；② 用 CRISP 五槽位重写它们，补上"输出格式"和"禁止项"两个最易被忽略的槽；③ 给每条打 v0.1.0 并标注 owner；④ 在下一个需求里强制"先查注册表、无则新建并评审"的规则；⑤ 一个月后统计复用率与返工次数。若复用率超过 40% 且返工明显下降，说明资产化已生效，可再引入自动评测集给每条提示词配回归用例。

**对比选型**
- 临时手写提示词：快但不可复用，适合一次性 PoC 与探索。
- CRISP 结构化模板：轻量、上手快，适合中小团队建立纪律。
- Golden Prompts + Prompt Registry：治理强、可跨职能复用，适合多产品多模型的企业。
- 全量 Prompt Ops 平台（含版本、A/B、监控）：能力最全但成本高，适合规模化 AI 产品线。
PM 不必一步到位，从"模板 + 注册表"起步即可，等复用需求出现再上平台。

### 2. 【AI 功能的效果度量：用任务成功率替代模糊的"好用"】

**导语**
"这个功能 AI 好不好用？"——这是 AI 产品经理被问得最多、却最难回答的问题。因为"好用"是主观感受，无法直接汇总成指标、无法回归、无法向老板汇报。当模型从 demo 走向生产，必须用可量化、可拆解、可归因的指标替代体感，其中最关键的一个就是"任务成功率（Task Success Rate, TSR）"。没有硬指标，AI 功能的价值永远停留在"感觉变好了"，经不起预算审视。

**它是什么**
任务成功率指：在给定一组真实用户任务上，AI 功能端到端正确完成的比例。它不同于"准确率"（单条样本对错），而是站在用户目标视角——例如"帮我把这封邮件改成正式语气并发送"，TSR 看的是整件事有没有达成，而非某一句话生成得漂不漂亮。与之配套的还有首次解决率、人类接管率、任务时长、满意度等。theneuralbase.com 强调，TSR 是少数能跨越"模型能力"和"产品体验"的桥梁指标：模型再强，若交互设计让用户无从纠错、找不到入口，TSR 仍会低，因此它逼着产品去关注全链路而非只盯模型。

**解决什么**
它解决"实验室好看、线上拉胯"的普遍落差。多个工程复盘指出，同一功能在受控 lab 环境与真实 production 之间的 TSR 差距常达 15–30 个百分点——因为生产里有长尾输入、多轮纠偏、工具调用失败、网络超时等 lab 看不到的噪声。bananalabs.io 引用 Gartner 预测：到 2027 年约 42% 的 agentic AI 项目会因"无法证明业务价值"而被弃用，根因往往是没建起 TSR 这类硬指标。没有度量，就无法证明 ROI，预算就会被砍；而有了 TSR，产品能说清"这个功能让任务完成率从 60% 提到 85%"，价值一目了然。

**原理拆解**
度量体系分三层。① 定义"任务"：把功能拆成可枚举的用户目标（如"生成周报""改写标题""查订单"），每个任务有清晰的成功判据，最好可机器判定。② 采集两路数据：线上埋点算生产 TSR；离线用固定评测集算 lab TSR，二者之差即"现实鸿沟"，差越大说明交互/工具链问题越重。③ 归因：TSR 低时拆成"模型错 / 交互错 / 工具错 / 数据错"，分别归责，避免盲目换模型。taskade.com 建议给每个任务配"金丝雀用例"持续监控，zonflip.com 则补充六个配套指标（完成率、接管率、重试率、时长、满意度、成本）共同刻画体验，单一指标容易被操纵，组合才稳。

**动手验证**
① 列出你功能的前 10 个高频任务，给每个写清"成功"的判定条件（尽量可自动校验）；② 抽 50 条真实线上会话人工标注 TSR 基线；③ 同时用评测集跑 lab TSR，算出差距；④ 若差距大于 20 个百分点，优先查交互与工具链路而非盲目换模型；⑤ 把 TSR 设为双周看板指标并设提升目标。注意要给不同用户分群（新用户/老用户）分别看，新用户 TSR 低往往是引导问题而非能力问题。

**对比选型**
- 满意度 / NPS：易收集但有滞后与主观偏差，只能做辅助指标。
- 单条准确率 / 相似度：技术视角，但和用户是否达成目标脱节。
- 任务成功率 TSR：用户目标视角、可归因，最推荐作为主指标。
- 业务指标（转化、留存）：终极证明，但噪声大、归因难，需配合 TSR 定位。
建议 TSR 为主、满意度与业务指标为辅，三层互补。

### 3. 【AI 评测集建设：用可复用评测集驱动模型验收与回归】

**导语**
AI 功能上线前，你怎么确认"这次模型没变差"？靠人工试几条？靠感觉？当功能迭代频繁、模型供应商还会悄悄升级，没有一套固定评测集，你永远在拿生产环境当实验室，用户成了小白鼠。评测集（evaluation set）是 AI 产品的"测试套件"，是质量守门员，更是产品与研发之间关于"什么叫好"的共同契约。

**它是什么**
评测集是一批预先标注、覆盖典型与边界场景的输入—预期输出对，用于每次模型或提示词变更后的自动化验收与回归。它分几类：golden set（黄金集，最核心场景，必须全过）、回归集（历史出过错的用例，防止复发）、对抗集（越狱、长尾、噪声）。业界经验规模：masterprompting.net 给出梯度——内部助手级约 50 例即可起步，单垂直功能约 200 例较稳，生产级多场景需 500+ 例才能覆盖长尾。评测集不是一次建完，而是随线上失败持续生长的活文档，越用越值钱，是典型"复利型"资产。

**解决什么**
它解决三大风险。① 静默劣化：模型供应商升级后准确率掉了 5%，无人察觉，直到客诉爆发。② 回归：你为 A 场景修好，却把 B 场景改坏，没有评测集就发现不了。③ 验收扯皮：研发说"模型没问题"，产品说"体验变差"，无共同判据，会议变成各说各话。有了评测集，每次变更跑一遍分数，低于阈值禁止发布，争议用数据说话。futureagi.com 将其定位为"持续评估（continuous evaluation）"的基础设施，与 CI/CD 同等级，是 AI 产品工程化的标志。

**原理拆解**
mlflow.org 给出评测集落地的六步法：① 收集真实输入（从日志采样，而非拍脑袋编造，否则偏离真实分布）；② 标注预期（人工或强模型评审，关键场景必须人审）；③ 定义评分器（精确匹配 / LLM-as-judge / 规则校验，按任务选）；④ 建流水线自动跑，接入发布门禁；⑤ 设阈值与拦截规则；⑥ 把失败用例回流成新评测项，形成正循环。kuizhuokj.com 补充"五步工程法"：先定场景边界，再分层（简单/中等/困难），再写判据，再自动化，最后做看板。关键是"评分器可解释"——不能只给个总分，要能看出错在哪类任务，否则无法指导改进。常见评分陷阱有三个：一是 LLM-as-judge 自身有偏好，需用多个裁判交叉验证；二是只评"像不像标准答案"忽略"是否可用"，应加业务判据；三是评测集老化，半年不更新就会和实际流量脱节。建议每月用线上失败样本回流刷新，保持集子与真实分布的同步。

**动手验证**
① 从本周线上日志抽 50 条真实请求建 v0.1 评测集，优先覆盖黄金场景；② 对每条写"成功判据"，能机检的尽量机检；③ 用规则 + LLM 双评分器跑基线分；④ 接入发布前门禁：分数降超过 2 个百分点则拦截；⑤ 每发现一个线上 bad case，就补一条进集，月内扩到 200 条。注意标注成本：可先用强模型标初稿、人工抽审，把单价压下来，否则集子会停滞。

**对比选型**
- 人工试跑：零成本但不可复现，仅适合 PoC。
- 单 golden set（50 例）：轻量起步，覆盖核心场景。
- golden + 回归 + 对抗三层（200–500+ 例）：生产推荐，可防静默劣化。
- 全自动化持续评估平台：能力最强，适合多模型多团队。
自 v0.1 起步，按失败率驱动扩集最经济，别追求一步到位。

### 4. 【AI 能力封装为 API 的产品化：从内部功能到可调用服务】

**导语**
团队做出了一个惊艳的"AI 总结"功能，嵌在自己的产品里。隔壁业务线听说后也想用，于是复制代码、各接各的模型、各算各的成本——三个月后出现了五个版本、三套账单、两次线上事故。AI 能力一旦被多个场景需要，就必须从"功能"升级为"API 产品"：对外提供稳定契约，对内统一治理，否则规模化的代价是混乱。

**它是什么**
AI 能力 API 产品化，指把模型能力（如摘要、抽取、分类、Agent 执行）封装成有版本、有 SLA、有鉴权、有计量、有计费的独立服务，供内部或外部调用方消费。techment.com 提出"企业级 AI API 成熟度模型"：L0 脚本级（硬编码在应用里）→ L1 服务化（独立部署）→ L2 网关化（统一路由/限流/观测）→ L3 产品化（文档、配额、计价、市场）。很多团队卡在 L1，缺的正是产品化思维：把"能调通"当成"能交付"，忽略了契约稳定、成本可见与生命周期管理这些产品基本盘。

**解决什么**
它解决"重复造轮子 + 成本黑盒 + 供应商绑定"。developer.baidu.com 的案例显示，把通用 AI 能力抽成 API 后，某业务开发周期从 23 人天降到 3 人天，因为调用方不再关心模型、部署、鉴权。genaimlinstitute.com 指出，API 化后配合 Prompt 缓存可降 50–90% 推理成本，且"提示词即资产"可跨业务复用。更重要的是解耦：模型供应商一换，只需网关改路由，调用方代码零改动，把"供应商风险"从每个业务线收敛到一处，合规与成本也第一次变得可审计、可管控。对外部商业化而言，API 化还是规模化的前提——没有稳定契约就无法对外售卖，客户集成要的是"契约不变"，而非"模型最新"，产品化思维恰恰是把"技术能力"翻译成"他人可依赖的服务"。

**原理拆解**
产品化有五个构件。① 契约：明确输入输出 schema、错误码、版本号，向后兼容地演进。② 网关：LLM Gateway 作为控制面，统一路由、限流、预算、观测（zylos.ai 2026 研究：37% 企业已在生产跑 5+ 模型，网关成必备基础设施）。③ 计量：Token 级输入/输出/缓存分项计费，财务可审计，避免"一笔糊涂账"。④ 治理：虚拟密钥 + RBAC + 审计日志，满足合规，出问题可定位到调用方。⑤ 计价：内部核算或对外售卖，让成本显性。网关选型上，Bifrost 以 11μs 开销、原生 MCP 见长；Portkey 强在合规护栏；Kong 适合已有 Kong 栈；Cloudflare 零运维但不可私有化， regulated 场景慎用。

**动手验证**
① 挑一个被至少 2 个业务想要的能力，定义 OpenAI 兼容的输入输出契约 v1；② 接一个 LLM 网关做路由 + 限流 + Token 计量；③ 发虚拟密钥给第一个调用方，跑两周看调用量与成本曲线；④ 建内部"能力目录"页面，标注 SLA 与单价，降低发现成本；⑤ 收集反馈迭代到 v1.1。注意版本弃用策略：旧版本要留至少 1 个周期的迁移期并提前通知，否则调用方会"被 breaking"而失去信任。

**对比选型**
- 硬编码调用：最快但不可复用，禁止生产多用。
- 独立微服务（L1）：可复用但缺治理，适合单业务。
- 网关化（L2）：路由/限流/观测齐全，推荐基线。
- 完整 API 产品（L3）：含文档/配额/计价/市场，适合平台型组织。
按"被几个业务需要"决定走到哪一级，≥2 即该 API 化，别过度设计。

### 5. 【AI 功能的定价策略：token、结果与席位三类产品化定价】

**导语**
你的 AI 功能做出来了，老板问："怎么收费？"你说"按调用次数吧"——结果大客户疯狂刷接口把你打崩，小客户嫌贵不来。AI 功能的成本结构与传统软件完全不同：边际成本随每次推理真实发生（GPU、Token），定价必须既能覆盖变动成本，又能让客户感知价值。2026 年业界已演化出清晰的几类模式，选错模式轻则亏本、重则丢客户。

**它是什么**
AI 定价主要有六大模式，可归纳为三类逻辑。① 用量型：按 token 计费（如 OpenAI 式 input/output token）或按 API 调用次数，成本可转嫁但客户账单波动大。② 价值型：按"结果"计费，例如 Intercom Fin 对每个"解决的对话"收 0.99 美元，Sierra 按达成的业务结果定价并已做到 2 亿美元 ARR；CSDN qcx23《19 AI 定价模式全解(2026版)》将其列为高价值场景首选。③ 订阅/席位型：固定月费或按席位的 Copilot 式，预测性强、易采购。此外还有混合式（订阅含额度 + 超额 token）与按成功分润，本质是前三类的组合。

**解决什么**
它解决"成本不可控"与"价值不对齐"。纯 token 计费让客户怕账单爆炸而却步，销售周期被财务吓得拉长；纯订阅又让供应商在重度用户上亏本，毛利被最大的客户吃穿。GitHub Copilot 在 2026-06-01 转向"用量计费 + 订阅包"混合，正是为平衡二者。stigg.io 与 solvimon.com 的调研均指出，按结果定价在客服、销售等"省人即省钱"场景转化最高，因为客户付的是省下的钱的一部分，而非模糊的"AI 使用费"，价值锚点清晰。cloudzero.com 强调定价必须和 FinOps 联动，否则毛利为负还不知道，看似营收涨实则贴钱。

**原理拆解**
定价设计四步。① 算清单位经济：单次推理成本（含缓存命中率）是多少，目标毛利多少，P95 成本别漏算。② 对齐客户价值感知：客户是因"用得多"还是"办成事"付费更愿意？前者用量型，后者结果型。③ 选主模式 + 护栏：如订阅保底 + token 封顶，避免账单休克引发流失。④ 持续调：solvimon.com 建议用打包实验（packaging experiment）测价格弹性，小步快跑。a16z 报告亦指出，2026 年"按结果/按成功"的 AI 定价正在从先锋走向主流，尤其 Agent 类能直接归因产出的产品，越能归因越敢按结果收。

**动手验证**
① 算你功能单次推理中位数成本与 P95 成本，留出缓存优化空间；② 访谈 5 个客户：他们愿为"次"还是"结果"付费，并探查愿意披露用量数据的程度；③ 设计"基础订阅 + 超额 token 封顶"混合包，给客户确定性；④ 小范围 A/B 两档价，看转化与毛利；⑤ 接 FinOps 看板监控单位经济，月内调一次。注意区域与行业差异：国内客户偏好包月、海外 SaaS 接受用量，定价包要本地化。还要警惕"免费试用陷阱"——若按结果计费却让试用期内结果无限免费，重度试用用户会直接击穿毛利，应在试用中设额度上限。定价不是一次性决策，而是随单位成本下降（模型更便宜、缓存更优）持续让利给客户、巩固粘性的一门长期经营。

**对比选型**
- 纯 token / 调用：成本可转嫁，客户有账单焦虑，适合开发者 API。
- 纯订阅 / 席位：易采购，重度用户亏本，适合内部提效工具。
- 按结果：价值对齐最强、转化高，但归因难，适合客服/销售。
- 混合（订阅 + 封顶 token）：兼顾双方，2026 最主流推荐。
按"能否清晰归因业务结果"选主模式，再用护栏兜底。

### 6. 【AI 原生交互范式：从点击 GUI 到意图驱动的自然语言交互】

**导语**
我们用了四十年图形界面：菜单、按钮、表单、标签页。现在用户开始直接说"帮我把上季度绩效整理成发给老板的邮件"。当 AI 能听懂意图、调工具、产出结果，界面就该从"人适应软件结构"翻转为"软件适应人的意图"。这就是 AI 原生（AI-native）交互范式，它不是给旧界面加个聊天框，而是重做信息架构。

**它是什么**
AI 原生交互指：以自然语言意图为主入口，界面动态组装工具、数据与流程来响应，而非用户自己在不同页面间导航。elite-x.tech 的 2026 UX 趋势报告称，67% 的 SaaS 公司正在把对话式 UI 集成进产品；AI-native 不是"加个聊天框"，而是用意图（Intent）替代导航（Navigation）——用户表达目标，系统路由到正确能力。sitarainnovations.com 称之为"Intent-as-an-Interface"：传统界面是名词（资源）组织的，AI-native 界面是动词（目标）组织的。典型形态有命令面板 + AI（Linear、Raycast）、内联助手（Notion、Figma）、对话式导航（Perplexity、ChatGPT Canvas）、预测式 UI（Spotify、Netflix）。

**解决什么**
它解决"功能越多、人越迷路"。传统 GUI 的功能增长靠加菜单，用户认知负荷线性上升，老用户也常找不到深层功能；AI-native 把多步流程压成单次意图表达。Nielsen Norman Group 研究（elite-x.tech 引）：遵循透明、可控、可纠错最佳实践的 AI 增强界面，复杂任务完成时间平均降 35%。lazarev.agency 的 Accern Rhea 案例：把研究平台做成"命令行式输入 + 生成式 UI（图表随提示词自组装）"的混合决策系统，成为其八位数收购的催化剂；Pika AI 把对话层放在搜索框下"意图形成的瞬间"，显著降低搜索时间，证明入口位置比功能本身更影响采用率。

**原理拆解**
落地四原则。① 意图捕获：在用户最自然的位点放入口（搜索框下、命令面板），而非藏二级菜单，降低表达门槛。② 生成式 UI：界面随意图动态生成（图表、面板），不是固定页，减少为"不存在的页面"而做的导航。③ 透明与可控：展示 AI 推理步骤、置信度、提供手动覆盖——boldlynames.com 的 Taitor 案例证明"展示解题过程"比"给完美答案"更建立信任，黑箱会引发焦虑与弃用。④ 渐进披露：别一次性堆所有 AI 能力，按需要显现，避免认知过载。错误模式是"把 AI 埋在不透明交互后"，用户只看到输入和输出，中间黑箱导致不信任。

**动手验证**
① 选你产品里一个"三步以上、用户常放弃"的流程（如建报表）；② 在其入口加自然语言意图框，后端路由到现有能力，不重写底层；③ 输出用生成式组件而非新页面，随意图变化；④ 显式展示 AI 在做什么、给"重做/改方向"按钮，保留降级到传统 GUI 的通道；⑤ 用 5 个真实用户测任务时长，对比旧 GUI，目标降 30%+。同时关注无障碍：语音/多模态入口能覆盖行动不便用户，但必须保留可视化兜底，不能只做对话。

**对比选型**
- 传统 GUI：可控、可学习，但功能多则迷路，适合确定性任务。
- 加聊天框（套壳）：易做但割裂，AI 与主线脱节，不推荐为主。
- 对话式导航：意图直达，适合探索/研究类，需强纠错。
- AI-native 意图驱动（生成式 UI + 透明可控）：2026 范式，适合复杂多步流。
先挑一个高放弃率流程做"意图入口"试点，而非全量重做，控制风险。
