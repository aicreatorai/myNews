### 1. 【Go 1.27 进入 RC：泛型方法首次登场与 json/v2 重写】

> 📍 **导语**：Go 团队在 2026 年 7 月 8 日放出 1.27 的第二个候选版本（RC2），并计划于 2026 年 8 月推出正式稳定版。这是自 Go 1.18 引入泛型以来类型系统变动最大的一次：方法终于可以声明自己的类型参数，容器与迭代库长期被迫用顶层函数绕开的痛点被消除。同一版本还重写了使用量极高的 encoding/json 包、把后量子签名 ML-DSA 收进标准库，并把小于 80 字节的小对象分配成本最多降低约 30%。对以稳定著称的 Go 而言，这是一次相当密集的更新。

**▌ 它是什么？**
Go 1.27 是 Go 语言的第 27 个主版本，目前处于发布候选阶段（RC2 于 2026-07-08 公布，紧随两次安全修复）。它的核心是一组语言层与标准库的协同升级：语言层面引入了"泛型方法"（generic methods），即方法声明可以拥有独立于接收者类型的自有类型参数；标准库层面把历史最悠久的 encoding/json 重写为 v2（encoding/json/v2），新增 crypto/mldsa 后量子签名包、标准库 uuid 包，以及实验性的 simd 向量化包。运行时层面则通过按尺寸特化的分配器把小对象分配提速最多约 30%，并把 goroutine 泄漏剖析器（goroutineleak）从实验状态毕业为正式能力。

**▌ 它解决了什么问题？**
泛型方法解决的是"方法无法携带自有类型参数"这一 Go 泛型设计里被抱怨最久的缺口。在 1.27 之前，只有顶层函数与类型本身可以是泛型；若想给某个类型的方法加上独立于接收者的类型参数，就只能写成包级函数，破坏了 API 的内聚与可发现性。json/v2 则解决旧包默认宽松、对非法 UTF-8 与重复键默不作声的问题——新默认在解码时直接拒绝无效 UTF-8 与重复对象键，并提供了流式读写的原生路径。后量子 crypto/mldsa 解决的是"长期敏感数据面临量子计算威胁"的合规与前瞻需求，把 FIPS 204 的 ML-DSA 签名与 TLS 1.3 的 ML-KEM1024 密钥交换直接做进标准库。

**▌ 核心原理拆解**
泛型方法的实现允许在方法声明中直接写 `func (c *Cache) GetAs[T any](key string) (T, bool)`，编译器为该方法单独做单态化，类型参数与接收者类型相互独立；唯一限制是接口方法仍不得声明类型参数，因为那会与接口派发的编译模型冲突。json/v2 把 API 按用途拆分：编码侧有 Marshal / MarshalWrite / MarshalEncode，解码侧有 Unmarshal / UnmarshalRead / UnmarshalDecode，流式与读写路径成为一等公民，并统一接受可变参数 Options；旧 encoding/json 包在底层已改为由 v2 实现支撑，因而大多数项目无需改动 import 路径即可获得更严格的行为。分配提速来自 size-specialized allocation：对小于 80 字节的对象按尺寸类别走特化例程，减少通用的 mallocgc 开销。goroutineleak 剖析器则在 runtime/pprof 中增加新的 profile 类型，专门捕获永久阻塞在不可达同步原语上的 goroutine。

**▌ 动手验证**
下面用泛型方法重写一个类型安全的缓存读取器：
```go
type Cache struct{ data map[string]any }
// Go 1.27：方法拥有自己的类型参数
func (c *Cache) GetAs[T any](key string) (T, bool) {
    var zero T
    v, ok := c.data[key]
    if !ok { return zero, false }
    t, ok := v.(T)
    if !ok { return zero, false }
    return t, true
}
user, ok := cache.GetAs[User]("uid-1") // 调用点即获得类型，无需手动断言
```
升级到 1.27rc2 后，可运行 `go test` 并打开 pprof 的 goroutineleak 视图确认无泄漏 goroutine；用 `go build` 配合 json 解码重复键样本验证严格默认是否生效。

**▌ 对比与选型**
| 维度 | Go 1.26 | Go 1.27 |
|------|---------|---------|
| 方法泛型 | 不支持 | 支持（接口方法除外） |
| JSON 默认 | v1 宽松 | v2 严格（拒非法 UTF-8/重复键） |
| 后量子签名 | 需第三方 | 标准库 crypto/mldsa |
| UUID | 需第三方 | 标准库 uuid |
| 小对象分配 | 基线 | 最多快约 30% |
| goroutine 泄漏检测 | 外部工具 | 内置 goroutineleak |

选型建议：容器、客户端、配置加载等库应尽快验证泛型方法带来的 API 简化；依赖旧 JSON 宽松默认的服务需先补齐测试再升级；对长期数据安全敏感的后端，可借 1.27 启动 PQC 就绪评估。

### 2. 【TypeScript 7.0 面世：原生 Go 移植带来约十倍编译提速】

> 📍 **导语**：微软在 2026 年 7 月 8 日将 TypeScript 7.0 推向正式可用（GA），距离 6 月 18 日的候选版约三周。最大的变化不是新语法，而是底层重写：编译器与语言服务被逐行移植到 Go 语言（代号 Corsa），借助原生代码速度与共享内存并行，类型检查相比 6.0 平均提速约 10 倍。VS Code 的完整类型检查从 125.7 秒降到 10.6 秒（11.9 倍），带错文件打开延迟从 17.5 秒降到 1.3 秒（13 倍）。代价是 7.0 暂时不带公开编译器 API，依赖 Vue/Svelte/Astro 模板类型服务的工具需等到 7.1。

**▌ 它是什么？**
TypeScript 7.0 是 TypeScript 语言的重大基础设施版本：微软把沿用多年的、以 TypeScript 自举并编译到 JavaScript 的实现，整体移植到 Go。官方强调这是"port（移植）"而非"rewrite（重写）"——新代码库镜像旧结构，类型检查逻辑与 6.x 在语义上严格一致，并通过了十年积累的测试套件。终端入口由 tsc 变为 tsgo（`npx tsgo --version` 显示 7.0.0），普通应用代码无需改源码即可升级。它把多核并行带到类型检查这一长期单线程瓶颈上，并收紧了一批默认配置。

**▌ 它解决了什么问题？**
TypeScript 在大型代码库上的最大痛点是编译与编辑器响应慢：CI 全量类型检查动辄上百秒，打开一个带错文件也要十几秒。7.0 用原生 Go 实现替换 JS 运行时，消除 V8 启动与 GC 抖动，并用共享内存并行跑多个类型检查 worker，从根本上压缩等待时间。另一类问题是历史包袱：许多现代项目早已手动开启 strict、esnext、noUncheckedSideEffectImports，但默认仍停留在 commonjs/es5/自动加载全部 @types。7.0 把这些现代默认值直接固化为新项目默认，使 tsconfig 显著瘦身。此外，原生实现占用的内存更少，编辑器里的重命名、跳转定义与重构在超大型代码库上也更跟手，开发者日常交互不再被后台类型检查拖慢，整体协作体验明显轻快。

**▌ 核心原理拆解**
提速来自两层：其一是语言切换——Go 编译为原生机器码，启动与吞吐远优于 Node 上的 JS；其二是并行——tsgo 支持 `--checkers N` 同时跑 N 个类型检查 worker，`--builders N` 并行项目引用构建，二者可在 monorepo 中叠加到最多 16 个并发检查器；`--singleThreaded` 用于调试。并行结果靠 `stableTypeOrdering`（默认开启且不可关闭）保证确定性。默认值变化包含：strict 默认 true、module 默认 esnext（不再是 commonjs）、target 移除 es5（地板为 ES2015）、types 默认空数组（不再自动加载所有 @types）、移除 AMD/UMD/SystemJS 与 moduleResolution: node10。关键的兼容性限制：7.0 暂不提供稳定的程序化编译器 API，因此把 TypeScript 嵌入自身语言服务的工具（如 Vue 的 Volar、Svelte、Astro 的模板检查）暂时无法迁移，需等 7.1（预计 2026 年 10 月）。微软同时发布兼容包 @typescript/typescript6，提供 tsc6 可执行文件，让 7.0 与 6.0 API 并行共存。

**▌ 动手验证**
安装预览/稳定版并执行原生检查：
```bash
npm install -D typescript        # 现已指向 7.0
npx tsgo --version               # 7.0.0
npx tsgo --checkers 4            # 4 个并行类型检查 worker
npx tsgo --build --builders 4    # 并行项目引用构建
```
在现有项目上先用 `tsc6` 跑一遍 6.0 语义，再用 `tsgo` 跑 7.0，对比带错文件打开延迟与全量检查耗时，验证语义一致（仅提速）。

**▌ 对比与选型**
| 维度 | TypeScript 6.0 | TypeScript 7.0 |
|------|----------------|---------------|
| 实现语言 | TypeScript(JS) | Go（移植） |
| 全量检查速度 | 基线 | 约 8–12 倍 |
| 编辑器开错延迟 | 基线 | 约 13 倍 |
| 并行类型检查 | 无 | --checkers / --builders |
| 默认 strict | 否 | 是 |
| 公开编译器 API | 有 | 暂缺（待 7.1） |

选型建议：纯应用代码可立即升级拿提速；使用 Vue/Svelte/Astro/MDX 模板工具链的项目应暂缓到 7.1，或在过渡期用 @typescript/typescript6 并行共存。

### 3. 【Rust 1.97 发布：v0 符号改名默认开启改写崩溃栈可读性】

> 📍 **导语**：Rust 团队在 2026 年 7 月 9 日推出 1.97.0 稳定版，七天后又紧急发布 1.97.1 修复一处 LLVM 误编译。1.97 最受关注的是把 v0 符号改名（symbol mangling）方案在稳定版默认开启，结束了长达约八年的迁移：崩溃栈里泛型单态化的真实类型签名将直接可读，而不再是一串哈希。伴随而来的还有 Cargo 原生接管"警告即错误"策略、链接器输出前置暴露，以及一批位运算与常量上下文 API 的稳定化。

**▌ 它是什么？**
Rust 1.97.0 是 Rust 的常规六周节奏稳定版，但它在工程治理与可调试性上落了几个关键能力。头号改动是 v0 symbol mangling 成为稳定默认：编译器把函数（如 `Vec::push`）编码为链接器安全的唯一名字时，不再丢弃类型信息、只用哈希去重，而是保留真实的泛型实参与类型。与此同时，Cargo 新增对"警告是否导致构建失败"的原生控制，无需再借助 `RUSTFLAGS=-Dwarnings` 这类会搅动构建缓存的临时手段；链接器原本被静默吞掉的 stderr 现在作为 `linker_messages` 警告暴露。

**▌ 它解决了什么问题？**
老的符号改名方案源自接近 Itanium ABI 的古老格式，它在泛型实例信息保留、一致性与可读性上都有历史包袱：当程序在凌晨崩溃、回溯穿过一长串单态化泛型时，栈帧里只有不透明的哈希，开发者要猜到底是哪一次实例化炸了。v0 让回溯直接显示具体签名，把生产环境排障从"猜谜"变为"读名"。Cargo 的警告策略则解决了 CI 中硬拦警告时破坏底层构建缓存的问题——团队终于能把"警告纪律"当作工作流配置，而非编译器黑魔法。

**▌ 核心原理拆解**
符号改名是编译器把 `Vec::<u32>::push` 这样的 Rust 路径转成链接器可接受的扁平字符串的编码规则。旧方案为求唯一性用哈希，丢弃了可读性；v0 则保留实际泛型实参与类型，回溯时还原出可读签名。v0 自 Rust 1.59 起就以 `-Csymbol-mangling-version=v0` 存在，并在 2025 年 11 月成为 nightly 默认，1.97 只是把它在 stable 默认翻转，过渡相对平滑。这也意味着崩溃上报、性能剖析与栈还原等上下游工具需要以 v0 为准，旧 nightly 上仅存的 legacy 方案已被规划移除，把 v0 视为永久现实是正确的心智模型。Cargo 的 deny warnings 现在落在配置层，允许 `allow` 临时静音或 `deny` 在 CI 拦截，且不影响 build cache。配套稳定化的位运算 API 包括 `isolate_highest_one` / `isolate_lowest_one`（提取单个置位）、`highest_one` / `lowest_one`（定位边界位）、整数与 NonZero 上的 `bit_width`，以及 `char::is_control` 进入常量上下文。

**▌ 动手验证**
本地验证工具链是否理解 v0：
```rust
fn main() {
    let v: Vec<u32> = vec![1, 2, 3];
    println!("{}", v.first().unwrap());
    panic!("boom to inspect backtrace");
}
```
升级前后分别编译并触发 panic，对比回溯：升级前应看到 `_RNvNtNtCs...` 一类哈希串，升级后看到 `Vec<u32>::...` 的可读签名。再用 GDB 10+ / 新版 LLDB 确认能正常 demangle；若 CI 仍依赖老旧固定工具链，需先在隔离环境验证符号化路径。

**▌ 对比与选型**
| 维度 | Rust ≤1.96 | Rust 1.97 |
|------|-----------|-----------|
| 符号改名默认 | 旧 Itanium 风格 | v0（可读泛型） |
| 警告即错误 | RUSTFLAGS 黑魔法 | Cargo 原生 deny/allow |
| 链接器消息 | 静默吞掉 | 作为 linker_messages 暴露 |
| 位运算 API | 多需手写 | isolate/highest/lowest/bit_width 稳定 |
| 旧调试器兼容 | 天然支持 | 需更新至支持 v0 的版本 |

选型建议：泛型密集的 Web 框架、异步运行时、游戏引擎应优先升级以获益；但凡依赖二进制符号化的可观测管线，先确认 GDB/LLDB/rustc-demangle 已支持 v0 再切，避免排障时看到原始乱码。

### 4. 【Julia 1.12 发布：互递归类型落地与墙钟采样剖析器】

> 📍 **导语**：Julia 1.12 系列在 2026 年持续迭代，当前稳定线已达 1.12.5/1.12.6，长期支持（LTS）线为 1.10.10，而 1.13 已越过特性冻结进入 alpha2。1.12 在类型系统与可观测性上补了关键能力：长期难以干净表达的互递归类型（mutually recursive types）终于获得支持，编译器新增跨过程别名感知的 MustAlias 分析来更准地传播类型；同时内置了不依赖调度状态的墙钟采样剖析器，并迎来基于编译器自身类型推断的 JETLS 语言服务器。

**▌ 它是什么？**
Julia 1.12 是 Julia 语言的一个特性发布，定位在科学计算、数值仿真与可复现研究的主力版本。它带来的语言特性包括：互递归类型——两个或多个类型相互引用（常见于树与图结构）；编译器运行时改进包括 MustAlias 分析（把变量到其别名的类型信息更好传播，并已扩展到过程间，实现别名感知的联合拆分）；工具链改进包括新增墙钟剖析器（wall-time profiler），以及把终端信息库 terminfo 默认内置。生态侧则出现了 JETLS，一个直接构建在编译器类型推断上的语言服务器。

**▌ 它解决了什么问题？**
互递归类型此前在 Julia 中表达起来别扭，树与图这类自引用数据结构要么借助间接层、要么牺牲清晰度；1.12 让这类相互引用类型可以自然声明。MustAlias 分析解决的是"编译器看不见别名之间类型一致"导致的优化受限问题——例如加载不可变结构体的字段总能拿到同类型值，跨过程扩展后能在泛型代码里做更精准的联合拆分。墙钟剖析器解决的是 I/O 密集任务难以被现有采样剖析器覆盖的盲区：旧剖析器多按任务调度状态采样，墙钟采样则不关心任务是否正在运行，能稳定捕获阻塞与争用。

**▌ 核心原理拆解**
互递归类型通过允许类型定义互相引用实现，相关 PR 在 2025 年底进入实现、于 1.12 周期合并。MustAlias 是别名分析的一种：编译器证明某变量与其别名指向同一存储，从而把对别名的类型知识前推到原变量；其过程间版本让"基对象与其字段同时传给被调函数"时也能做联合拆分，相关 PR 历时三年多逐步合入。墙钟剖析器以固定频率对调用栈采样，不论任务处于运行、阻塞还是等待 I/O，因而能暴露被传统按调度采样忽略的争用热点（PR #55889）。InteractiveUtils 新增 `@trace_compile` 与 `@trace_dispatch` 宏，分别开启 `--trace-compile` 与 `--trace-dispatch` 的追踪。默认构造器生成从 C/flisp 迁移到 Julia 自身，是为未来无 flisp 引导（JuliaLowering）做准备。

**▌ 动手验证**
用互递归类型表达树与图，并启动墙钟剖析：
```julia
# 互递归类型：节点与边相互引用
mutable struct Node
    edges::Vector{Edge}
end
mutable struct Edge
    to::Node
end
# 墙钟抽样剖析 I/O 密集代码
using Profile
Profile.init(delay=0.01)
@profile begin
    fetch.(fill(HTTP.get("https://example.com"), 50))  # 伪代码示意
end
Profile.print()
```
借助 JETLS（要求 Julia 1.12+）可在 VS Code 中获得编译器驱动的实时诊断。

**▌ 对比与选型**
| 维度 | Julia ≤1.11 | Julia 1.12 |
|------|------------|-----------|
| 互递归类型 | 受限/间接 | 原生支持 |
| 别名类型传播 | 基本 | MustAlias（过程间） |
| 墙钟剖析 | 无 | 内置 wall-time profiler |

### 5. 【Kotlin 2.2 发布：上下文参数预览与守卫条件转正】

> 📍 **导语**：Kotlin 2.2.0 把多项长期实验特性推向稳定，并预览了被称为"隐式上下文传递"新答案的上下文参数（context parameters）。守卫条件（guard conditions）、非局部 break/continue、以及多美元符号字符串插值从实验转正为稳定；Kotlin/Wasm 升到 Beta，Kotlin/Native 切换到 LLVM 19。在 2026 年，它进一步巩固了 Kotlin 作为 Android 与多平台首选语言的地位，Compose Multiplatform 与 Ktor 同步成熟。

**▌ 它是什么？**
Kotlin 2.2.0 是 JetBrains 维护的 Kotlin 语言的一个特性版本，包含语言、编译器、JVM/Native/Wasm/JS 多后端与标准库的协同更新。语言层面最值得关注的有两件事：其一，上下文参数作为预览特性登场，取代更早的实验特性"上下文接收器（context receivers）"，让函数与属性声明在周围上下文中隐式可用的依赖；其二，一批既有实验特性转为稳定，包括守卫条件、非局部 break/continue、多 `$` 字符串插值。编译器侧统一了警告管理；标准库中 Base64 与 HexFormat API 转正稳定。

**▌ 它解决了什么问题？**
上下文参数解决的是"如何优雅地传递很少变化却多处共享的隐式依赖"这一经典问题——如服务、配置、日志器，以往要么手动逐层透传，要么借助依赖注入框架。上下文参数让这些依赖声明在 `context(users: UserService)` 中，函数体内直接按名字取用，无需把上下文作为接收者。守卫条件则解决了 `when` 表达式中"先判空/先匹配再处理"的样板：稳定后可用 `guard` 提前退出，减少嵌套。非局部 break/continue 让 lambda 内的控制流跳出外层循环更自然；多 `$` 插值则让字符串模板里嵌套 `${}` 时更清晰。

**▌ 核心原理拆解**
上下文参数用 `context(name: Type)` 语法声明，区别于旧的 context receivers：它不把上下文作为接收者引入函数体，而是按参数名访问成员，因此迁移工具可辅助从 context receivers 切换。上下文敏感解析（context-sensitive resolution）则在预览中允许在已知期望类型处省略枚举/密封类成员的类型名（如 `when(problem) { CONNECTION -> ... }` 而非 `Problem.CONNECTION`）。JVM 侧默认开启 `-Xjvm-default=all-compatibility` 生成默认接口方法，简化 Java 互操作；Kotlin/Native 换用 LLVM 19 并新增内存消耗追踪与调整能力；Kotlin/Wasm 成为独立编译目标并支持按项目配置 Binaryen。标准库 Base64 与 HexFormat 在多年孵化后转正稳定。

**▌ 动手验证**
启用上下文参数预览（Gradle）：
```kotlin
kotlin {
    compilerOptions {
        freeCompilerArgs.add("-Xcontext-parameters")
    }
}
```
用法示例：
```kotlin
interface UserService { fun log(m: String) }
context(users: UserService)
fun outputMessage(message: String) {
    users.log("Log: $message")   // 直接按名取用上下文
}
```
在 `when` 中体验守卫条件简化嵌套，并用多 `$` 插值写 `${"value is ${x}"}` 验证可读性提升。守卫条件把"先判空/先匹配再处理"的样板压平，避免在分支深处反复 `if (x == null) return`：
```kotlin
// 守卫条件：先匹配/判空再处理，减少嵌套
fun classify(x: Int?): String = when {
    guard x != null else -> "null"
    x > 0 -> "positive"
    else   -> "non-positive"
}
```
多美元符号插值则让字符串模板里再嵌套 `${}` 时减少转义困扰，写复杂动态文案时可读性更高；它与上下文敏感解析一起，降低了 Kotlin DSL 与 Compose 组件的语法噪音，使库作者能用更少的样板表达更丰富的语义。

**▌ 对比与选型**
| 维度 | Kotlin 2.1 | Kotlin 2.2 |
|------|-----------|-----------|
| 上下文传递 | context receivers(实验) | context parameters(预览) |
| 守卫条件 | 实验 | 稳定 |
| 非局部 break/continue | 实验 | 稳定 |
| Kotlin/Wasm | 更早阶段 | Beta |
| Native 后端 | 旧 LLVM | LLVM 19 |
| Base64/HexFormat | 实验 | 稳定 |

选型建议：构建 DSL、库或 Compose 组件的团队应评估上下文参数以简化隐式依赖；守卫条件与非局部控制流可立即用于新代码；JVM 默认接口方法变更需检查依赖旧实现的 Java 互操作代码。

### 6. 【Swift 6 严格并发默认开启：数据竞争在编译期被消除】

> 📍 **导语**：Swift 6 把"数据竞争安全（data-race safety）"作为 Swift 6 语言模式下的默认行为，把以往只能在完整并发检查标志下才报警的数据竞争问题，直接变为编译期错误。这意味着多个线程共享并修改同一份数据时，编译器会在构建阶段拦下潜在竞态，而不是留到运行时偶发崩溃。到 2026 年 WWDC26，Swift 6.4 又补上了所有权（ownership）相关的不可拷贝类型与新的 Iterable 协议，使高性能类型也能享受通用协议能力。

**▌ 它是什么？**
Swift 6 是 Apple 的 Swift 语言主版本，最具标志性的变化是引入 Swift 6 语言模式，在该模式下默认开启数据竞争安全。它基于既有的并发模型：用 actor 保护可变状态、用 Sendable 描述可安全跨隔离边界共享的数据。Swift 6 还带来类型化抛出（typed throws，指定错误具体类型而非 `any Error`）、Swift Testing 测试框架、以及用 Swift 重新实现的跨平台 Foundation（JSONDecoder、URL、Calendar 等核心类型在 Linux/Windows 上与 Apple 平台共享实现）。WWDC26 展示的 Swift 6.4 进一步把所有权特性推进：Equatable/Comparable/Hashable 可用于不可拷贝类型，关联类型也可不可拷贝或不可逃逸。

**▌ 它解决了什么问题？**
数据竞争是并发程序里最常见也最难复现的错误：多个线程同时读写共享数据，轻则结果错乱，重则崩溃。Swift 5.10 在"完整并发检查"标志下已能捕获许多竞态，但仍有不少误报，且默认关闭。Swift 6 把这些检查默认开启，并把大量误报去除——例如一个非 Sendable 的 `User` 在主 actor 创建后整体传给另一个 actor，编译器能证明离开原隔离域后不再被共享，从而不再报警。类型化抛出则消除了无谓的类型擦除与装箱，让错误契约更精确。所有权相关的不可拷贝类型让高性能类型（如文件句柄、GPU 资源）无需引用计数即可安全传递。

**▌ 核心原理拆解**
数据竞争安全的核心是隔离域（isolation regions）与 Sendable 证明：编译器分析程序流，证明某值在被送到另一隔离域后原域不再引用它，就不要求它满足 Sendable；否则报错。`sending` 关键字（SE-0430）显式标注跨隔离域传递的值；全局变量与静态变量在 Swift 6 起被要求并发安全（SE-0412）。类型化抛出把 `throws` 泛化为 `throws: Failure`，错误以具体类型出现在 catch 块，避免 `any Error` 的装箱。`for` 循环在 6.4 支持新的 Iterable 协议，以借用（borrow）而非拷贝方式遍历不可拷贝元素，且可逐批（span）取元素、可在循环中抛出错误，排他性检查禁止遍历时修改。

**▌ 动手验证**
开启 Swift 6 模式并观察严格并发检查：
```swift
actor DataService {
    func fetch() -> String { "data" }
}
func callActor() async {
    let service = DataService()
    let data = await service.fetch()
    // Swift 6 严格检查 data 是否 Sendable
    print(data)
}
// 类型化抛出示例
func parse() throws(ParseError) -> Int { 0 }
do { let n = try parse() } catch let e: ParseError { print(e) }
```
使用 Xcode 或 Swift 6 工具链新建模块并逐步迁移：先让依赖 unchanged，再用 `@MainActor` 标注 SwiftUI 视图，借助编译器提示逐处修复竞态警告。

**▌ 对比与选型**
| 维度 | Swift 5.10 | Swift 6 |
|------|-----------|---------|
| 数据竞争检查 | 需手动开完整检查，误报多 | 默认开启，误报大幅减少 |
| 错误类型 | any Error（擦除） | 支持 typed throws |
| 全局变量 | 不强制并发安全 | 要求并发安全(SE-0412) |
| 测试框架 | XCTest | 新增 Swift Testing |
| 跨平台 Foundation | 仅 Apple | Linux/Windows 共享实现 |
| 所有权(6.4) | 无 | 不可拷贝类型+Iterable |

选型建议：新项目直接以 Swift 6 语言模式起步；存量项目可按模块逐步迁移，借助编译器提示修复竞态；依赖 Objective-C 桥接或大量非 Sendable 类型的老代码应预留迁移窗口，避免一次性开启引发大面积报错。
