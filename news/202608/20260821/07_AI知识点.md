### 1. 【投机解码 Speculative Decoding：用小模型猜、大模型一次验的提速术】

> 📍 **导语**：大语言模型的自回归生成本质上是串行的——每生成一个 token 都要跑一次完整前向传播，而解码阶段又被显存带宽死死卡住，GPU 大量算力闲置。投机解码（Speculative Decoding）由 DeepMind 的 Leviathan 等人在 2023 年 ICML 提出，如今已成为 vLLM、TensorRT-LLM 等推理引擎的标配加速手段。它的核心洞见是：用一个又小又快的草稿模型先"猜"出若干 token，再由大模型一次性并行验证，在数学上保证输出分布与原始大模型完全一致——无损提速 2 到 3 倍。理解它，是读懂现代推理优化的第一把钥匙。

**▌ 它是什么**
投机解码是一种"草稿-验证"（draft-then-verify）的并行解码范式。它不改动目标大模型本身，而是额外引入一个参数量小一个量级的草稿模型（draft model，如 0.5B～1B），让它以极低成本自回归地先生成 γ 个候选 token；随后把这一串候选一次性喂给目标大模型，目标模型用一个前向传播同时算出每个位置的真实概率分布并完成验收。它最常见的误区是以为这是"近似加速"——其实标准拒绝采样保证最终输出分布与单独用目标模型解码严格相同，零质量损失。它适用于解码阶段是瓶颈的场景（对话、代码补全），而在 Prefill 阶段（一次性处理长 Prompt）几乎无收益。历史上它脱胎于 2023 年 Leviathan 等人的论文，后来又演化出 Medusa（用多头预测代替草稿模型）、Lookahead Decoding（用 n-gram 免草稿）等变体。Octomil 等端侧框架还给出"无草稿"的 Lookahead 退化方案：用主模型自身的 n-gram 模式并行猜测，虽加速较小（1.3–1.5x）但零额外显存。

**▌ 解决什么**
Before：自回归解码每步只产出 1 个 token，目标模型每个 token 都要把全部权重从显存读一遍，计算单元利用率常常不足 10%，在 7B 模型上单次生成延迟可能高达数秒，长文本更糟。After：草稿模型批量吐出 5～7 个候选，目标模型一次前向全部验证，验证 N 个 token 的成本约等于生成 1 个 token 的成本。只要草稿接受率超过 50%，就能净加速。量化数据：vLLM 实测代码补全场景从 30 tok/s 提到 75 tok/s（2.5x），通用对话 1.8x，创意写作 1.3x；Octomil 的端侧方案用 0.5B 草稿模型在手机上拿到 1.8～2.2x 加速，1B 草稿模型在 8GB+ 设备上达 2.2～2.8x。最近 DeepSeek、Llama 系列的开源推理栈都已内置投机解码，长推理链场景收益尤为明显。自适应前瞻（adaptive lookahead）还会根据近 32 个 token 的实时接受率动态增减 γ（2～10 之间），易猜的常见短语多猜、难的推理步骤少猜，进一步逼近理论上限。

**▌ 原理拆解**
第一层（直觉）：就像你让实习生先起草一整段方案，老板只做一次审阅就批量签字通过或圈出要改的那一处——比老板逐字手写快得多。
第二层（流程）：① 草稿阶段：草稿模型以温度采样自回归生成 γ 个 token，记录每步概率分布 q；② 验证阶段：把原始输入拼接 γ 个草稿 token 送入目标模型，得到每个位置的真实分布 p；③ 逐位验收：对第 i 位草稿 token x，以概率 min(1, p(x)/q(x)) 接受，若拒绝则从残差分布 max(0, p−q) 重新采样并终止本轮；④ 从最后接受位置继续下一轮。这样循环直到达到目标长度。
第三层（核心机制）：验收之所以无损，靠的是拒绝采样（rejection sampling）。若草稿概率 q 高于目标概率 p，直接接受即可；若 q 低于 p（即目标更"想要"这个 token），以 p/q 的概率接受，否则从归一化的残差分布里补一个 token，从而精确还原目标模型的边缘分布。其数学本质是：最终每个位置输出的边缘分布等于目标模型 p，与草稿模型无关。因此这是"无损"而非"近似"。同时，因为验证是单次批处理，显存带宽瓶颈被绕过——小模型猜得多、大模型只做一次"批量裁判"。

**▌ 动手验证**
用 Hugging Face transformers 的最小可运行骨架（节选自 coddykit 教程，TinyLlama 作草稿、Llama-3.1-8B 作目标）：
```python
from transformers import AutoModelForCausalLM, AutoTokenizer
import torch, torch.nn.functional as F

draft = AutoModelForCausalLM.from_pretrained("TinyLlama/TinyLlama-1.1B-Chat-v1.0").eval()
target = AutoModelForCausalLM.from_pretrained("meta-llama/Llama-3.1-8B-Instruct").eval()

def verify(input_ids, gamma=5):
    # 草稿阶段：自回归猜出 gamma 个 token
    d_in = input_ids.clone(); drafts, qprobs = [], []
    for _ in range(gamma):
        with torch.no_grad():
            p = F.softmax(draft(d_in).logits[:, -1, :] / 0.7, -1)
        t = torch.multinomial(p, 1); drafts.append(t.item()); qprobs.append(p.squeeze())
        d_in = torch.cat([d_in, t], 1)
    # 验证阶段：目标模型一次前向验收
    with torch.no_grad():
        out = target(torch.cat([input_ids, torch.tensor([drafts])], 1))
    for i, dt in enumerate(drafts):
        q = qprobs[i]; pk = F.softmax(out.logits[0, input_ids.size(1)-1+i, :] / 0.7, -1)
        if torch.rand(1) < min(1.0, pk[dt].item() / q[dt].item()):
            input_ids = torch.cat([input_ids, torch.tensor([[dt]])], 1)   # 接受
        else:
            break  # 拒绝后从残差重采样（此处省略）
    return input_ids
```
注意：生产环境直接用 vLLM 的 `--speculative-model` 参数即可，无需手写；草稿模型与目标模型 tokenizer 必须一致，否则验收会失效。

### 2. 【KV Cache 与 PagedAttention：以显存换时间的解码加速器】

> 📍 **导语**：自回归生成时，第 t 步的 Query 要和之前所有 token 的 Key/Value 做注意力计算。若每次都重算历史 token 的 K/V，复杂度是 O(t²)，完全不可行。KV Cache 把每层、每个历史 token 的 K/V 矩阵缓存下来，把每步计算降到 O(t)，是 Transformer 推理的基石。但随着上下文拉长，KV Cache 显存暴涨——7B 模型、2048 token、FP16 下就要约 1GB，70B 长上下文场景占比超 50%，成为并发数的硬瓶颈。vLLM 的 PagedAttention 借鉴操作系统分页，把显存碎片打掉，吞吐提升 2～4 倍。这是每个做推理部署的人必须吃透的工程知识点。

**▌ 它是什么**
KV Cache 是 Transformer 解码时在每一层缓存的 Key/Value 张量。解码阶段每来一个新 token，只需算它的 Q/K/V，历史 K/V 直接读取，避免重复计算。它不是"缓存加速"的锦上添花，而是自回归生成的必选项。常见误区是以为 KV Cache 只吃算力——实际上在 decode 阶段它才是显存占用的大头（7B 模型 GPU 显存里 KV Cache 可占 33%）。它的适用边界在长上下文、高并发服务；短 Prompt 单次问答收益有限。工程上又衍生出 GQA（分组查询注意力，把 KV 头数砍到 1/4～1/8）、MQA，以及把 KV Cache 量化到 INT8/FP8 省显存的做法。PagedAttention（Kwon et al., SOSP 2023）则是 vLLM 的核心创新：把传统"按最大长度连续分配"改成"按块（block）分页分配"，像虚拟内存一样按需分配物理页，既消除碎片又支持请求间前缀块共享。

**▌ 解决什么**
Before：传统推理为每个请求预留"最大序列长度"的连续显存，哪怕实际只用了 1/3，剩余全浪费；多请求并发时碎片严重，经常"明明还有显存却 OOM"。After：PagedAttention 把 KV Cache 切成固定大小的块（如 16 token/块），逻辑序列连续、物理块可不连续，请求间还能共享前缀块（prefix caching）。效果：显存浪费从 60～80% 降到接近 0，并发请求数提升 2～4 倍。量化数据：data-dynamics.io 实测启用 PagedAttention + 连续批处理（continuous batching）后吞吐提升 2～4x；prefix caching 对共享系统提示的长 Prompt 把首 token 延迟（TTFT）降低 50～80%。Octomil 的端侧方案还进一步用注意力权重打分驱逐低分块、把冷块压缩到 INT4/INT8 甚至溢写到闪存（flash spill），在 8GB 内存手机上把可用上下文从约 250 token 拉到约 2500 token，彻底改变了端侧长上下文的可行性边界。

**▌ 原理拆解**
第一层（直觉）：像餐厅给每位客人预留整张长桌，哪怕只坐一人也占满——PagedAttention 改成"按人发小圆桌、随到随拼"，翻台率自然高。
第二层（流程）：① Prefill 阶段处理 Prompt，算好并落盘所有 token 的 K/V 块；② 每个新 token 解码时，只算自身 Q/K/V，从历史块读取 K/V 做注意力；③ PagedAttention 把逻辑块号映射到物理块号表，注意力计算跨物理不连续块进行 gather；④ 序列增长时动态分配新块，结束或驱逐时回收；⑤ 共享前缀的请求指向同一组只读块，零拷贝复用。
第三层（核心机制）：显存占用公式约为 Memory = 2 × L × B × H × d_h × (S_prefill + S_decode) × bytes。KV Cache 随序列长度线性增长，这是解码阶段内存带宽瓶颈的根源。GQA 通过让多个 Query 头共享一组 KV 头，把 KV 头数降到 1/4～1/8，等比例削减显存；INT8/FP8 量化再把每元素字节数减半或降为 1/4。PagedAttention 的块表（block table）机制与操作系统页表同构，因此能像虚拟内存那样把碎片化的物理块拼成连续逻辑视图，从根本上消灭"外部碎片"导致的 OOM。

**▌ 动手验证**
手写一个带 KV Cache 的多头注意力前向（节选自 51cto 推理加速指南）：
```python
import torch, torch.nn as nn, torch.nn.functional as F

class MHAWithCache(nn.Module):
    def __init__(self, d=512, h=8):
        super().__init__(); self.h = h; self.dk = d // h
        self.wq = nn.Linear(d, d, bias=False)
        self.wk = nn.Linear(d, d, bias=False)
        self.wv = nn.Linear(d, d, bias=False)
        self.wo = nn.Linear(d, d, bias=False)
    def forward(self, x, past=None, use_cache=False):
        B, S, _ = x.shape
        Q = self.wq(x).view(B, S, self.h, self.dk).transpose(1, 2)
        K = self.wk(x).view(B, S, self.h, self.dk).transpose(1, 2)
        V = self.wv(x).view(B, S, self.h, self.dk).transpose(1, 2)
        if past is not None:                      # 拼接历史 K/V 缓存
            K = torch.cat([past[0], K], 2); V = torch.cat([past[1], V], 2)
        scores = (Q @ K.transpose(-2, -1)) / self.dk ** 0.5
        out = (F.softmax(scores, -1) @ V).transpose(1, 2).reshape(B, S, -1)
        return self.wo(out), (K, V) if use_cache else None

m = MHAWithCache().eval()
prompt = torch.randn(1, 10, 512)
with torch.no_grad():
    _, cache = m(prompt, use_cache=True)          # Prefill：初始化缓存
tok, cache = m(prompt[:, -1:], past=cache, use_cache=True)  # Decode：只喂新 token
```
注意：生产推理用 vLLM/TensorRT-LLM 自动管理分块，无需手写；缓存张量要放在正确设备上，且 past_key_values 的序列维必须与当前输入对齐，否则拼接会维度报错。

| 显存利用 | 碎片多浪费大 | 近零浪费 | 降1/4–1/8 |

### 3. 【旋转位置编码 RoPE：让注意力只看相对距离的位置注入法】

> 📍 **导语**：Transformer 的注意力本身是置换不变的——打乱输入词序，输出只是跟着重排，模型并不知道"谁在前、谁在后"。位置编码就是给模型注入顺序感的机制。传统正弦 PE、BERT 可学习 PE 用"加法"把位置向量叠到词嵌入上，绝对位置混杂进注意力分数，超长文本外推极差。2021 年 Su 等人提出的旋转位置编码（RoPE）改用"乘法"：对 Query、Key 向量按二维分组做位置相关的正交旋转，数学上保证旋转后的点积只取决于 token 的相对距离。如今 LLaMA、Qwen、Mistral 全系标配，配合 YaRN、LongRoPE 把上下文从 8K 外推到 128K 甚至百万级。

**▌ 它是什么**
RoPE（Rotary Position Embedding）是一种把位置信息编码进注意力权重的方案。它不额外加向量，而是在每个注意力头里，把 Q、K 的特征维度两两一组，按 token 位置 m 施加角度为 m·θ_i 的二维旋转。一个常见误区是以为"位置编码都是加一个向量"——RoPE 是乘性的旋转变换，且只对 Q、K 旋转，V 全程不参与。它的适用边界是现代长上下文语言模型；对超短固定长度任务，简单绝对编码也够用。历史上它受复数域相位旋转启发：把二维向量看作复数 z=a+bi，旋转等价于乘 e^(i·m·θ)。相对位置不变性（差角公式）是其最核心的理论保证。LLaMA/Qwen/Mistral 全部采用，Qwen3 还在旋转前加了 QK-Norm 稳定数值；扩展方案 YaRN、Dynamic NTK、LongRoPE 进一步优化长度外推，使开源模型能"免重训"处理超长上下文。

**▌ 解决什么**
Before：绝对位置编码把"位置 5"和"位置 10"当成两个独立可学习向量，模型得自己摸索两者关系；一旦推理长度超过训练长度，位置向量从未见过，直接失效。相对位置编码（如 Transformer 原版 sinusoidal）虽好，但计算开销大、外推弱。After：RoPE 让注意力分数天然只看 Δ=n−m（相对距离），模型对"相隔多远"有几何直觉；且旋转频率对任意位置都可计算，训练 8K 的 Llama-3-8B 套 YaRN 即可平滑扩展到 32K，困惑度几乎不涨。量化数据：OSS AI Hub 指出 RoPE+YaRN/LongRoPE 是当今开源模型无需从头重训就能跑 128K–1M 上下文的原因；CSDN Qwen3 详解提到 Qwen3 把 base 从 10000 调到 500000，减缓高频旋转、提升长文本能力。相比绝对 PE，RoPE 在长文档理解、代码库级生成上优势显著，且旋转是预计算常量、零可学习参数、推理开销极低。

**▌ 原理拆解**
第一层（直觉）：把每个 token 的方向想象成钟面上的指针，位置越靠后，整组指针就多转一个角度；两个指针做点积时，它们夹角的余弦只和"相差几格"有关，和"从哪格开始"无关——这就把相对距离烘焙进了注意力。
第二层（流程）：① 对 Q、K 每个注意力头，把 head_dim 维（须为偶数）按相邻两维分成 d/2 组；② 第 i 组的基础频率 θ_i = base^(−2i/d)（原版 base=10000）；③ 位置 m 的总旋转角 ϕ = m·θ_i，预计算全部位置的 cos/sin 缓存复用；④ 旋转操作 q_embed = q·cos + rotate_half(q)·sin，其中 rotate_half 把后半维取负拼到前半；⑤ 旋转后的 Q、K 进入缩放点积注意力，V 不动。
第三层（核心机制）：设 Q 在位置 m 旋转、K 在位置 n 旋转，二者共轭内积的实部只含 (n−m)·θ_i 一项——由三角差角公式保证，与绝对位置 m、n 无关。这就是"相对位置不变性"。同时，随着 |Δ| 增大，余弦加权和自然衰减（Abel 求和），远距离 token 的交互被隐式弱化，形成内置的长程衰减。高频组（i 小）旋转慢、捕捉远距离依赖，低频组捕捉局部依赖，从而具备多分辨率式的频率分解能力。

**▌ 动手验证**
Hugging Face 风格的 RoPE 应用最小实现（节选自 Ultralytics 与 CSDN Qwen3 详解）：
```python
import torch

def rotate_half(x):
    x1, x2 = x.chunk(2, dim=-1)
    return torch.cat((-x2, x1), dim=-1)         # 对应旋转矩阵的 [-sin, cos] 项

def apply_rope(q, k, cos, sin):
    # q,k: (batch, heads, seq, head_dim)  cos,sin: (1,1,seq,head_dim)
    q_embed = q * cos + rotate_half(q) * sin    # 完整二维旋转展开
    k_embed = k * cos + rotate_half(k) * sin
    return q_embed, k_embed

# 预计算位置相关的 cos/sin（base=10000, head_dim 为偶数）
def precompute_rope(seq_len, head_dim, base=10000.0):
    inv_freq = 1.0 / (base ** (torch.arange(0, head_dim, 2).float() / head_dim))
    pos = torch.arange(seq_len).float()
    freqs = torch.outer(pos, inv_freq)          # (seq, d/2)
    return freqs.cos()[:, None, :].repeat(1, 2).unsqueeze(0).unsqueeze(0), \
           freqs.sin()[:, None, :].repeat(1, 2).unsqueeze(0).unsqueeze(0)

cos, sin = precompute_rope(10, 64)
q = torch.randn(1, 4, 10, 64); k = torch.randn(1, 4, 10, 64)
q_r, k_r = apply_rope(q, k, cos, sin)
print(q_r.shape, "RoPE 已注入 Q/K，V 保持不变")
```
注意：绝大多数情况直接用 HuggingFace 内置实现，不要手写自定义 RoPE；不同模型 base 频率、是否 QK-Norm 顺序不同，需对齐官方配置，否则位置语义会错位。

### 4. 【智能体记忆机制：把上下文窗口变成可检索的分层记忆】

> 📍 **导语**：一个朴素的事实常被忽视：GPT、Claude、Gemini 在每次 API 调用之间都不携带任何状态，所谓的"记忆"全是应用层工程 trick——把历史消息每轮重新塞回 Prompt。但上下文窗口是有限的"工作台"（RAM），不是硬盘。Chroma 的 Context Rot 研究测试 18 个前沿模型发现，随输入变长，准确率在触及标称上限前就非均匀下跌 30～50%。2026 年，Agent 记忆已成为一门真正的工程学科：借鉴认知科学的分层记忆（工作/情景/语义/程序），用"常驻上下文核心 + 外部可检索存储 + 显式遗忘策略"的架构，把无状态模型变成能跨周、跨月记住用户与任务的真正助手。

**▌ 它是什么**
Agent 记忆机制是让无状态语言模型具备"跨会话持续学习"能力的一整套架构。它借用认知科学对人类记忆的划分：工作记忆（上下文窗口，当前能直接看到的）、情景记忆（过往具体事件/对话的日志）、语义记忆（提取出的稳定事实与用户偏好）、程序记忆（可复用的技能与工具使用模式）。一个常见误区是把"上下文窗口"等同于"记忆"——它只是易失的工作台，会话结束即清空，且塞太多反而稀释注意力。它的适用边界在需要个性化、长期任务、多智能体协作的场景；一次性问答不需要。理论渊源是 2023 年伯克利的 MemGPT（把 LLM 当操作系统：窗口是 RAM、外部存储是磁盘、用工具调用分页换入换出），其继任者 Letta 把它做成了状态化 Agent 运行时。2026 年 Mem0、Zep、Letta 等托管/开源方案让这套架构可被快速集成，CoALA 框架则把四种记忆类型标准化为通用词汇。

**▌ 解决什么**
Before：没有记忆的 Agent 每轮重新自我介绍、重复犯同一个错、忘了上周的偏好；把完整历史全灌进 Prompt 既贵又在长文本上失准（Context Rot）。After：分层记忆让 Agent 只把当下相关的少数记忆检索进窗口。量化数据：Mem0 的《2026 State of AI Agent Memory》报告显示，全上下文方案准确率 72.9% 但需 17 秒响应、26000 token/对话；选择性记忆检索（Mem0）牺牲 6 个百分点准确率，却换来 91% 延迟下降与 90% token 削减，达到生产可用。VentureBeat 的"观察式记忆"（被动从轨迹中挖掘可复用事实而非显式写入）相对 RAG 降本 10 倍且长上下文基准更优。Zylos 的隔离子 Agent 上下文研究更显示，子 Agent 上下文隔离相比共享上下文把任务成功率提升 90.2%——因为每个角色都从清晰、最小化的上下文推理，而非被巨大嘈杂的共享历史锚定。

**▌ 原理拆解**
第一层（直觉）：像新人入职，零星信息先贴便利贴（工作记忆），重要的慢慢记进脑子（语义）、把流程变成本能（程序）、把经历写进周报（情景），年底桌上的便利贴早清了，但 Wiki 和肌肉记忆还在。
第二层（流程）：① 写入（Write）：对话中每轮进入工作记忆， salient 事实同时写入外部向量/图存储；② 检索（Retrieve）：后续轮次用当前 query 的 embedding 做相似度搜索，拉回 top-k 相关记忆注入窗口；③ 压缩/驱逐（Compact/Flush）：窗口将满时，旧轮次被摘要（Anthropic compaction）或按 FIFO 丢弃（LlamaIndex），腾出空间；④ 提升（Promote）：Jeremy Daly 强调"记忆提升"是最高风险操作——会话级观察提升到用户/租户级需闸门（如会话→用户仅允许偏好与草稿，会话→全局运行时永不），否则会出现"先例中毒"（个案例外被当成永久策略）。
第三层（核心机制）：记忆的本质是"决定这轮模型该看什么、其余放哪"。向量检索按语义相关而非关键词召回，但 blunt——不区分时效性、权威性、任务阶段，因此生产系统要叠加近因加权、来源排序、显式状态。CoALA 框架把四种记忆类型标准化为词汇，Generative Agents 用"近因+重要性+相关性"三分数检索，MemoryBank 用艾宾浩斯遗忘曲线做衰减，Zep 则用时序知识图谱记录"事实何时为真"。

**▌ 动手验证**
一个最小的分层检索记忆骨架（节选自 dev.to Agent Memory 教程）：
```python
import numpy as np

class Memory:
    def __init__(self):
        self.store = []                      # 外部语义记忆（向量库）
    def write(self, text, vec):
        self.store.append({"text": text, "vec": np.array(vec)})
    def retrieve(self, query_vec, top_k=3):
        if not self.store: return []
        sims = [np.dot(query_vec, m["vec"]) for m in self.store]
        idx = np.argsort(sims)[-top_k:][::-1]   # 按语义相似度取 top-k
        return [self.store[i]["text"] for i in idx]

mem = Memory()
mem.write("用户偏好靠窗座位和素食餐。", [0.9, 0.1])   # 写入长期语义记忆
hits = mem.retrieve([0.85, 0.15])                      # 用"订去 Delhi 的机票"检索
print("\n".join(hits))    # 输出: 用户偏好靠窗座位和素食餐。
```
注意：生产环境用 Chroma/Mem0/Zep 等托管库，嵌入模型要与检索查询同源；写记忆要带时间戳与来源，便于近因加权与遗忘策略，避免把过期偏好当成当前事实召回。

|------|---------------|---------|---------|---------|
| 存什么 | 当前对话 | 过往事件 | 稳定事实 | 技能流程 |

### 5. 【上下文工程 Context Engineering：决定每步该往窗口里塞什么】

> 📍 **导语**："Prompt 工程问的是：指令怎么措辞？上下文工程问的是：这一步模型该看到什么、又该把什么挡在门外？"2025–2026 年，随着长上下文 Agent 落地，Context Engineering 从一句 buzzword 变成生产级纪律。Anthropic 把"决定保留、摘要还是丢弃哪些 token"称为上下文工程的真功夫，并指出窗口填满后准确率会"腐烂"（context rot）。Slack 工程团队的原则甚至极端到"不在 Agent 调用之间传递任何消息历史"，每个子 Agent 只收与其角色相关的结构化摘要。理解它，是让 Agent 在长任务里不跑偏、不超预算、不互相污染的关键。

**▌ 它是什么**
上下文工程是在 Agent 每一步推理前，主动决定"上下文窗口里装什么"的系统化纪律，是上下文窗口（易失工作记忆）的运行时管理学科。它和 Prompt 工程的区别在于层级：Prompt 工程优化"一句话怎么说"，上下文工程优化"整个工作台此刻陈列了哪些信息"。一个常见误区是以为"窗口越大越好、全塞进去最稳"——Zylos 与 Chroma 的研究都表明，过长且杂乱的上下文反而让模型注意力失准、延迟与成本飙升。它适用于多轮、多工具、多子 Agent 的生产系统；一次性简单问答不必上这套。实践源头是 Anthropic 在 Claude 平台推出的 memory tool 与 context editing（临近 token 上限时自动清掉过期工具结果），以及 MemGPT/Letta 的"分页换入换出"思想，其目标始终是把"信号密度"而非"信息总量"最大化。

**▌ 解决什么**
Before：把整段对话、全部检索文档、所有工具输出原样堆进 Prompt，结果一是超窗口、二是无关细节淹没关键信号、三是每个子 Agent 都背着跨任务的历史噪音。After：上下文工程用"压缩（窗口内）+ 外部记忆（跨会话）"双层架构治理。量化数据：Mem0 基准中全上下文需 17 秒/26000 token，选择性检索降到约 1.5 秒/2600 token（延迟降 91%、token 减 90%）；Zylos 引述 Morphllm 分析，子 Agent 上下文隔离相比共享上下文把任务成功率提升 90.2%，主因是各角色始终从"连贯、最小化"的上下文推理，而非被巨大嘈杂共享历史锚定。Slack 三条通道架构（Director's Journal / Critic's Review / Critic's Timeline）显式隔离，避免"确认偏误注入"（子 Agent 拿到太多历史会锚定旧结论而非基于当前证据重新推理），这正是对上下文工程纪律的极致践行。

**▌ 原理拆解**
第一层（直觉）：上下文窗口像厨师的砧板——上面堆满无关食材，切菜就慢且易切错；好厨师每步只把当前这道菜要用的摆上案板，其余收进冰箱（外部记忆），需要时再取。
第二层（流程）：① 范围裁剪（Scope）：按角色/租户/隐私模式决定每个 Agent 能看到的信息边界，父 Agent 的工作集不向子 Agent 传播；② 压缩（Compaction）：窗口内用摘要、FIFO 丢弃、context editing 把旧内容瘦身；③ 外部化（Externalization）：大多数信息不进窗口，除非 Agent 主动检索；④ 隔离（Isolation）：子 Agent 拿全新上下文与范围化任务描述，输出当作带溯源的"工具结果"而非继承父权威的指令；⑤ 治理（Governance）：记忆提升设闸门，防止个案例外变永久策略。
第三层（核心机制）：上下文工程的核心权衡是"召回 vs 噪声 vs 成本"。RAG 是无状态检索（会话结束即忘），状态化记忆是跨会话、建模"Agent 学到了什么"；两者互补。提取模式比存储模式更关键——VentureBeat 的"观察式记忆"持续从轨迹中蒸馏事实，比事后总结产出更高质量记忆，相对 RAG 降本 10 倍。Anthropic 的 context editing 则在运行时动态剔除过期工具结果，把 token 预算留给当下真正相关的信息。

**▌ 动手验证**
一个窗口溢出时的滚动摘要骨架（节选自 dev.to 教程）：
```python
def build_context(history, window=6, llm=None):
    """窗口满时保留最近 window 轮原文，旧轮摘要成紧凑笔记"""
    recent = history[-window:]
    older = history[:-window]
    if older and llm is not None:
        summary = llm(f"Summarize this conversation so far:\n{older}")
        return [f"Summary so far: {summary}", *recent]   # 边界有界、要点不丢
    return recent

# 多 Agent 隔离：父只传结构化摘要，不传原始历史
def delegate(subagent, task, summary):
    return subagent.run(task, context=summary)   # 子 Agent 拿到的是摘要而非全量历史
```
注意：生产用 Anthropic context editing、Mem0、Letta 等托管能力；裁剪顺序要保留系统指令与最近轮次，避免把"初心"和"当前任务"误删导致失忆或跑偏，同时要注意不要过度压缩导致关键约束丢失。

| 作用域 | 运行时全局 | 单条指令 | 查询时 |
| 状态性 | 含跨会话记忆 | 无状态 | 无状态 |

### 6. 【GRPO 群体相对策略优化：不养 Critic 的轻量强化学习】

> 📍 **导语**：大模型预训练后还必须经过强化学习对齐（RLHF），否则不会可靠地遵循指令、拒绝有害请求、或一步步推理。过去两年的标配是 PPO（近端策略优化），但它要同时养活策略模型、参考模型、奖励模型、价值模型四个大模型，70B 上训练光显存就压垮中小团队。2026 年 1 月 DeepSeek-R1 论文把 GRPO（Group Relative Policy Optimization）推上主舞台，它干脆砍掉价值网络（Critic），改为"对同一问题并行采样多个答案、组内互相打相对分"，在保持 PPO 级效果的同时把显存砍掉近一半、训练提速明显，已成为 DeepSeek、Gemini 等后训练的首选算法。

**▌ 它是什么**
GRPO（Group Relative Policy Optimization，组相对策略优化）是一种面向 LLM 后训练的强化学习算法，是 PPO 的轻量化替代。它同样以 SFT 模型为起点，走"采样→打分→优势估计→策略更新"的闭环，但最大的不同是：完全移除价值网络（Critic/Value Model），改用"同一 prompt 的多个采样回答（一个组）做组内相对标准化"来估计优势。一个常见误区是以为 GRPO 不需要奖励信号——它仍要奖励模型或规则打分，只是不再需要一个独立的、和奖励模型同尺寸的 Value 模型。它适用于有明确对错或可用规则评分的任务（数学、代码、事实问答），在资源受限、想快速迭代时尤佳；复杂综合任务且资源充足时 PPO 仍稳健。它源自 DeepSeekMath（2024）与 DeepSeek-R1（2026-01）的工作，并在 GLM、Qwen 等社区广泛采用，成为"推理模型"训练的核心引擎。

**▌ 解决什么**
Before：PPO 在 LLM 上"状态"是 token 序列、"动作"是选 token，需要 4 个模型同时跑——策略(7B–70B)+参考(同尺寸冻结)+奖励(1B–13B)+价值(同奖励尺寸)，70B 训练总计数百 B 参数常驻显存，工程复杂、成本高、小团队玩不起。After：GRPO 砍掉 Value 模型，省下近一半核心显存与反向传播计算，吞吐更高、更适合大规模并行采样。量化数据：阿里云案例分析某开源社区在 7B 模型上用 GRPO，训练时间从 3 天缩到 1.5 天；aitoolskit 指出 GRPO 已取代 PPO 成为 DeepSeek-R1、Gemini 后训练的首选。一个有趣的副作用是"思维链涌现"——模型在组内竞争中自发学会把推理步骤写清楚（CoT），因为直接蒙答案很难当上"优等生"，写出步骤更易拿高分；且这种并行采样只发生在训练阶段，上线推理仍是单次生成，不影响速度。值得注意的是 GLM-5.2 在 2026 年又从 GRPO 切回 PPO 换得稳定性提升，说明两者各有取舍。

**▌ 原理拆解**
第一层（直觉）：PPO 像给学生配了"私人教练"（Critic）评估每道题的预期难度来算优势；GRPO 像一场小组赛——同一道题让模型并行写出 4～8 个答案，用规则或奖励模型打分，算出小组平均分，高于平均分的就是"优等生"拿正奖励，低于的就是"待改进"拿负奖励，省掉了那个教练。
第二层（流程）：① Rollout：对每个 prompt 复制 G 份，当前策略并行采样 G 个回答 {o_1…o_G}；② 打分：用奖励模型或规则函数（答案对错、代码能否跑通、格式/长度/重复惩罚）给每个回答标量分 {r_1…r_G}；③ 组内优势：计算组均值与标准差，A_i = (r_i − mean) / std，组内相对好坏即优势；④ 策略更新：构造带 KL 约束的 clip/GRPO 损失，用参考模型限制 actor 别偏离 SFT 太远；⑤ 循环直到收敛。
第三层（核心机制）：GRPO 的优势估计靠"组间对比基线"代替学习到的价值基线，因此无需 Value 模型。其损失近似 L = E[ log π_θ(a|s) · R̂(a) ]，其中 R̂(a) 是归一化（均值中心化/排名）后的相对奖励。minimind3 的实现显示，GRPO 代码中 num_generations>1（PPO 中为 1），同一 prompt 复制多份正是组内比较的来源；KL 项用参考模型的对数概率差约束，防止奖励黑客（reward hacking）——即模型靠输出冗长废话骗过高分而不真正变好。

**▌ 动手验证**
参考 minimind3 的 GRPO 组内采样骨架（节选）：
```python
import torch

# Rollout：同一 prompt 复制 G 份，并行采样多答案
prompt_ids = torch.tensor([[1, 2, 3]])
G = 8
batch = prompt_ids.repeat_interleave(G, dim=0)        # [G, P]
completions = policy_model.generate(batch, max_new_tokens=256, do_sample=True)

# 打分：规则 + 奖励模型（示意）
rewards = []
for resp in completions:
    score = 0.5 if 20 <= len(resp) <= 800 else -0.5   # 长度规则
    score += 1.0 if "</think>" in resp else -0.5      # 思维链格式
    score += reward_model.get_score(resp)              # 外部 RM
    rewards.append(score)
rewards = torch.tensor(rewards, dtype=torch.float32)

# 组内相对优势
adv = (rewards - rewards.mean()) / (rewards.std() + 1e-6)   # 关键：组间标准化
print(adv.shape, "组内优势已算好，无需 Value 模型")
```
注意：GRPO 依赖同一 prompt 的多条采样，批大小实际放大 G 倍，要预留显存；规则奖励要与任务对错强相关，否则优势估计失真，模型可能学会"讨好规则"而非真正提升能力。
