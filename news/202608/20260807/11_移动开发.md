### 1. 【SwiftUI 新功能：Document API、可重排容器与工具栏可见性优先级】

> 📍 **导语**：苹果在 WWDC26 的 SwiftUI 专场里，把这一代框架升级的重点放在了"把过去要手写一大堆胶水代码的能力，变成系统级一等公民"。本次更新覆盖三块最常被抱怨的领域：基于文档的应用首次拿到一套完整的磁盘读写与快照差异 API；列表与网格获得了声明式的拖拽重排能力；工具栏则新增可见性优先级、溢出菜单与滚动自动最小化等精细化控制。配合 Liquid Glass 设计语言，多数改动无需改代码即可获得新外观，但文档类与重排类能力需要开发者主动接入才能吃到红利。对长期用 UIKit 写文档型 App 的团队而言，这是一次值得认真评估的迁移窗口。

---

**📱 深度报道**

**▌ 更新全景**

这一批 SwiftUI 更新的核心逻辑是"补齐声明式框架下原本只能靠命令式代码绕路的场景"。文档 API 是其中分量最重的一块：过去要做 PixelMator Pro、Pages 这类文档型应用，开发者往往得自己维护文件读写、自动保存、编辑状态指示等一整套机制，SwiftUI 现在通过 `DocumentGroup` 场景与 `WritableDocument` / `ReadableDocument` 协议，把磁盘读写、快照比对、进度上报统一收口。呈现层则新增了可在任意视图上实现的轻扫操作、扩展的呈现 API，以及 `AsyncImage` 的缓存改进与 Observable 类型的惰性状态初始化。工具栏体系变化尤其值得关注：`visibilityPriority` 让关键按钮在空间不足时仍保持可见，`ToolbarOverflowMenu` 把不常用操作收进溢出菜单，`toolbarMinimizeBehavior(.onScrollDown)` 让导航栏随滚动自动让位，开发者终于能精细控制"什么永远显示、什么可被隐藏"。

**▌ 技术细节深解**

文档 API 的写法围绕"快照"展开。文档类型遵循 `WritableDocument` 后，通过 `snapshot` 方法返回当前内容的结构化快照，再由遵循 `DocumentWriter` 协议的写入器落盘，整个过程 `nonisolated` 且 `async`，可在后台执行以避免阻塞主线程：

```swift
struct PageSnapshot: Codable {
    let background: Data
    let stickers: [(id: UUID, x: Double, y: Double)]
}

struct StickerDocument: WritableDocument {
    typealias FileWrapper = PageSnapshot
    func snapshot(contentType: UTType) throws -> PageSnapshot { /* 收集状态 */ }
    func fileWrapper(snapshot: PageSnapshot, configuration: WriteConfiguration) throws -> FileWrapperType {
        // 仅写入发生变化的包内部分，并借助 Foundation Subprogress 上报进度
    }
}
```

可重排容器则简单得多：在 `ForEach` 上挂 `reorderable` 修饰符、在容器上挂 `reorderContainer`，剩下的拖动交互与动画由系统接管，同一段代码在 `List` 与 `LazyVGrid` 上通用。底层实际借助开源的 `swift-collections` 提交排序变更，开发者只需把差异应用到自己的数据源数组。

**▌ 开发者迁移指南**

文档类应用若从 UIKit 迁移，建议先定义清楚"快照"结构，把原有模型对象映射成可序列化快照，再逐步替换文件读写路径，自动保存与编辑指示器由系统提供，无需自行实现。重排能力对既有的拖拽手势代码是直接替代，但要注意它依赖 `ForEach` 的确定性标识，数据源若用索引而非稳定 ID，会出现错位。工具栏新修饰符属于纯增量，可逐页试点。最低部署版本会随新系统抬高，需支持旧系统的项目要用 `if #available` 隔离。

**▌ 生态与竞品对比**

Flutter 的 `ReorderableListView` 早已提供拖拽重排，SwiftUI 这次相当于追平了声明式重排体验；但文档型 API 是自成一派的苹果特色，跨平台框架很难直接对标。Jetpack Compose 的 `Reorderable` 也提供类似能力，方向一致。对国内团队而言，文档类能力在笔记、画板、办公类应用中价值最高，值得优先验证。

---

**🤖 开发研判**

🔮 **技术趋势**：SwiftUI 正从"能写界面"走向"能写完整应用类型"，文档、重排、工具栏这些过去命令式 stronghold 被逐个收编，声明式覆盖范围继续扩大。

📊 **开发者决策影响**：新项目若涉及文档或集合重排，建议直接采用新 API，省下的胶水代码可观；存量 UIKit 文档应用可评估增量迁移，但不必赶首发。掌握快照思维比记忆具体协议更重要。

⚠️ **适配风险**：文档 API 的破坏性在于它重塑了"数据与磁盘"的关系模型，存量项目若数据模型与快照结构差异大，迁移成本不低；快照粒度过粗还会导致无效重写，需要精细设计。

💡 **学习优先级**：先吃透 `DocumentGroup` 与快照模型，再补重排与工具栏修饰符；`swift-collections` 的 `OrderedSet` 等类型值得顺手掌握。

### 2. 【SwiftData 2 稳定化：CloudKit 同步、历史追踪与轻量迁移落地】

> 📍 **导语**：SwiftData 自 iOS 17 作为 Core Data 的继任者登场后，前两代始终被开发者诟病"还差一口气"——尤其是跨设备同步与迁移体验不够成熟。随着 iOS 19 上 SwiftData 2 的成熟，CloudKit 同步、History Tracking、Composite Indexes 与 Lightweight Migration 均已稳定，加上与 Observation 框架的深度整合，它终于具备了承载生产级持久化需求的能力。对用 Core Data 跑了很多年的成熟项目，以及从零起步的新应用，这意味着持久化层可以少写大量样板代码，但要真正用好，仍需要理解它的模型演进与迁移策略。

---

**📱 深度报道**

**▌ 更新全景**

SwiftData 2 的稳定化可以拆成四个支点。其一是 CloudKit 同步从试验走向可用，私有数据库与共享数据库的同步配置被大幅简化，配合 `@Model` 宏声明的模型即可自动获得云端一致性；其二是 History Tracking，让开发者能查询某段时间内模型对象的变更轨迹，这对实现协作编辑、撤销重做、增量同步至关重要；其三是 Composite Indexes，复合索引让多字段组合查询的命中效率显著提升，过去只能靠单字段索引近似的场景有了正解；其四是 Lightweight Migration，模型字段增减时不再强制写冗长的映射策略，系统能在多数情况下自动完成迁移。与 Observation 框架的整合则是底层红利：`@Model` 宏声明的属性变更会被精确追踪，只有依赖该属性的视图才会刷新，避免了 Core Data 时代 `NSFetchedResultsController` 的笨重刷新逻辑。

**▌ 技术细节深解**

模型声明依旧走 `@Model` 宏，但 SwiftData 2 在查询与索引上给了更明确的入口。复合索引通过 `#Index` 宏声明，查询则用 `@Query` 配合谓词：

```swift
@Model
final class Note {
    @Attribute(.unique) var id: UUID
    var title: String
    var body: String
    var createdAt: Date
}

#Index<Note>([\.title, \.createdAt], name: "title_created")

@Query(filter: #Predicate { $0.title.contains("草稿") },
       sort: \.createdAt, order: .reverse)
var drafts: [Note]
```

History Tracking 的价值在协作场景最明显：通过 `HistoryToken` 记录变更断点，下次同步只需拉取该 token 之后的事务，避免全量比对。Lightweight Migration 则允许在不破坏既有用户数据的前提下新增可选属性、重命名字段，系统依据模型版本差异自动生成迁移计划，开发者仅在结构性大改时才需手写 `SchemaMigrationPlan`。

**▌ 开发者迁移指南**

从 Core Data 迁移的项目，第一步是把 `NSManagedObject` 子类改写为 `@Model` 结构体或 final class，注意 SwiftData 的模型默认是值语义友好的引用类型，关系建模需显式声明 `Relationship`。CloudKit 同步上线前要确认数据模型满足 CloudKit 的限制（如单字段大小、关系深度），否则同步会静默失败。索引不是越多越好，复合索引应只加在真正高频的组合查询上。建议为生产环境保留一个 `HistoryToken` 持久化点，作为增量同步与审计的锚。

**▌ 生态与竞品对比**

Realm、MMKV 等第三方方案在极致性能场景仍有优势，但 SwiftData 2 的最大卖点是"零额外依赖 + 苹果原生同步"。与 Jetpack Room（配合 DataStore）相比，两者都走向声明式与编译期安全，但 SwiftData 的 CloudKit 一体化是安卓侧没有的对应物。对国内团队，若业务无需跨安卓共用持久化层，SwiftData 2 已足够撑起绝大多数场景。

---

**🤖 开发研判**

🔮 **技术趋势**：苹果在持久化层面的目标很明确——让本地存储与云端同步成为"默认能力"而非"高级选项"，SwiftData 2 是这条路上的关键成熟节点。

📊 **开发者决策影响**：新项目应优先采用 SwiftData 2，迁移成本低于 Core Data 且未来可平滑拿到云端能力；存量 Core Data 大型项目可局部试点，逐步把新模块切过去。掌握 `@Query` 与索引设计比背 API 更有长期价值。

⚠️ **适配风险**：CloudKit 同步在弱网与冲突合并上的行为仍需实测，多设备同时编辑的冲突解决策略要提前设计；Lightweight Migration 虽自动，但字段语义变更（如类型改变）仍可能触发不可自动迁移的硬冲突。

💡 **学习优先级**：先掌握 `@Model` 与 `@Query` 的查询模型，再补索引与 History Tracking，最后才是 CloudKit 同步的冲突处理；Observation 框架原理是底层基础。

🔗 **信息来源**：youngju.dev《现代移动开发 2026 完全指南：SwiftData 2 与端侧 AI 集成》（2026-05-16）/ Apple Developer《SwiftData 文档与示例》（2026）

### 3. 【HarmonyOS 7 API 26 网络与性能新能力：冷启预建链、QUIC 长连接与弱网直播优化】

> 📍 **导语**：在 HarmonyOS 7（API 26）面向开发者的能力清单里，一组偏底层的网络与性能改进值得移动开发者重点关注：冷启动网络预建链、基于 QUIC 的长连接，以及面向直播场景的弱网优化方案。这些能力不显山露水，却直接决定用户在"点开 App 到首屏可交互""刷直播卡不卡""地铁里能不能稳住连接"这些体感上的成败。对国内高频交易、短视频、直播类应用而言，接入这套能力往往不需要大改业务代码，却能换来可感知的启动与弱网体验提升，是性价比很高的适配项。

---

**📱 深度报道**

**▌ 更新全景**

这组能力的设计目标是"把连接这件事在系统层做厚"。冷启网络预建链指的是应用进程冷启动时，系统在网络建链环节提前并行预热的机制，把原本串行的 DNS 解析、TCP/TLS 握手尽量压缩到首屏渲染之前完成，从而降低"白屏等待"。QUIC 长连接则是用基于 UDP 的 QUIC 协议替代部分传统 TCP 长连接，利用 0-RTT 或多路复用特性，在切换网络、弱信号环境下比 TCP 更扛抖动、更不容易被队头阻塞拖垮。弱网直播优化方案则针对上行与下行在丢包、延迟波动时的表现，给出了一套可配置的缓冲与重传策略。三者叠加，对应的是移动端最经典的三类痛点：首屏慢、连接抖、直播卡。对开发者来说，这些能力大多以系统 API 或配置项形式提供，不必重新实现网络栈。

**▌ 技术细节深解**

在 ArkTS 侧，弱网优化通常会以请求配置参数的形式暴露，开发者按场景声明容忍度即可，而非手动管理重传：

```typescript
// ArkTS：声明弱网友好的请求配置（示意）
const req = http.createHttp();
const options: http.HttpRequestOptions = {
  method: http.RequestMethod.GET,
  connectTimeout: 3000,
  readTimeout: 8000,
  // 启用系统级弱网优化与 QUIC 长连接复用
  usingProtocol: http.Protocol.QUIC,
  expectDataType: http.HttpDataType.STRING
};
req.request(url, options, (err, data) => { /* ... */ });
```

冷启预建链更多是系统侧行为，开发者能做的是确保首屏关键请求走系统推荐的建链路径，避免在应用层自行做多余的序列化阻塞；并配合启动性能埋点，验证预建链是否真的把首字节时间压了下来。QUIC 长连接的收益在"频繁小请求 + 网络切换"场景最明显，例如即时通信的心跳、feed 的轮询，建议把这类长生命周期连接迁移到 QUIC。

**▌ 开发者迁移指南**

接入顺序建议：先埋点建立基线（首屏时间、首字节、直播首帧、卡顿率），再逐项开启能力并对比。冷启预建链通常无需改代码，重点在验证效果；QUIC 长连接需要在客户端声明协议偏好，并确认服务端支持 QUIC，否则会回退到 TCP；弱网优化参数要按业务容忍度调，过度激进的缓冲反而增加延迟。务必在地铁、电梯、隧道等真实弱网环境做回归，模拟器无法还原信号抖动。

**▌ 生态与竞品对比**

苹果侧有 Network.framework 与 `URLSession` 的 HTTP/3 支持，谷歌侧有 Cronet 与 QUIC 生态，鸿蒙这次是把类似能力下沉到系统层并给出统一入口。对国内多端团队，现实做法是把"弱网优化开关"做成平台抽象层的一个配置项，让 iOS、Android、鸿蒙各自映射到本平台的等价能力，避免业务代码里散落平台判断。

---

**🤖 开发研判**

🔮 **技术趋势**：移动网络优化正从"应用自己造轮子"走向"系统提供标准能力"，鸿蒙把 QUIC 与弱网优化做成系统级选项，符合这一方向。

📊 **开发者决策影响**：短视频、直播、交易类应用应把这组能力排进本季度适配；收益是体验级而非功能级，难以直接量化收入，但留存与口碑受影响明显。掌握系统网络 API 与启动性能分析方法，比记忆具体参数更重要。

⚠️ **适配风险**：QUIC 收益高度依赖服务端协同，单方面改客户端若服务端不支持会静默回退；弱网参数调错可能让正常网络下反而变慢，必须灰度验证。

💡 **学习优先级**：先建立启动与弱网性能的测量体系，再学系统网络 API 与协议偏好配置，最后才是具体参数调优；抓包与网络时序分析是必备基本功。

### 4. 【鸿蒙 Harmony Intelligence 端侧 AI 开放：图像超分 Skill 与 Agent 开发框架】

> 📍 **导语**：鸿蒙在 2026 年把"端侧 AI"从营销话术推进到了可调用能力层。华为开发者联盟近期上线的 Harmony Intelligence 开放能力，第一期就放出了图像超分这类可直接调用的端侧 AI Skill，并围绕 App 与 Agent 开放了 Skill、Agent 及一整套 AI 开放能力。对移动开发者而言，这意味着不必自己训练或部署模型，就能把"老照片变清晰""实时图像增强"这类过去要接云端或自研的能力，以系统级 API 的形式嵌进应用。更关键的是，它把 Agent 开发框架标准化了——开发者可以用统一方式声明智能体、挂载技能、接入分发，而不是每家各写一套。

---

**📱 深度报道**

**▌ 更新全景**

Harmony Intelligence 的开放逻辑是"能力原子化、调用标准化"。图像超分是典型的第一批原子能力：输入一张低分辨率图，端侧直接输出增强结果，过程不依赖网络，隐私友好且延迟低。这类能力被封装成 Skill，开发者通过声明式接口调用，系统负责把请求路由到合适的端侧模型。围绕 Agent，鸿蒙提供了从开发、接入到分发的完整体系——开发者可以在小艺开放平台上创建自己的智能体，用简单的 UI 控件让用户获取服务，具备自主进化能力的智能体甚至能创建和分享个人专属 Skill。对应用侧来说，这意味着"AI 功能"不再是一个独立模块，而是可以像调用系统相机、定位一样，作为基础能力被组合进业务流程。

**▌ 技术细节深解**

从工程视角，端侧 AI Skill 的调用通常呈现为"声明意图 + 拿到结果"的薄封装，底层模型推理由系统托管：

```typescript
// ArkTS：调用系统图像超分能力（示意）
import { ai } from '@kit.HarmonyIntelligence';

async function upscale(src: image.PixelMap): Promise<image.PixelMap> {
  const task = ai.createImageTask('image-super-resolution');
  return await task.run({ input: src, scale: 2 });
}
```

Agent 侧则更偏"编排"：开发者定义智能体的触发条件、可挂载的 Skill 列表、与用户交互的入口，系统负责把自然语言意图映射到对应 Skill 并回传结果。相比自己接大模型 API，这种方式的优势是端云协同由系统调度——简单任务走端侧、复杂任务可委托云端，开发者无需关心路由细节。对中小团队，这大幅降低了"做出一个能用的 AI 功能"的门槛。

**▌ 开发者迁移指南**

接入端侧 Skill 属于增量改造，不破坏现有架构，但有三处要处理：一是权限与能力声明，端侧 AI 能力通常需要在配置中显式申请，未申请时调用会静默失败；二是结果一致性，端侧模型在不同设备上算力不同，超分等能力要设计降级路径，老设备拿不到理想效果时要有兜底；三是隐私合规，尽管数据不出端，仍要在隐私政策中说明使用了端侧 AI 处理。Agent 类能力建议在真机验证意图命中率，模拟器无法还原真实语音或文本入口。

**▌ 生态与竞品对比**

### 6. 【Flutter 的 AI 集成双引擎：GenUI SDK 与 Dart/Flutter MCP Server】

> 📍 **导语**：当跨平台框架的竞争从"性能追平原生"转向"AI 原生体验"，Flutter 在 2026 年给出了一套与 AI 深度绑定的工具链：一是 GenUI SDK（alpha），让 AI 智能体不是返回一段文字，而是基于你已有的 widget 目录，用 JSON 描述直接生成可交互的图形界面；二是 Dart/Flutter MCP Server（实验性），把 Flutter 的开发工具暴露给 Cursor、GitHub Copilot、Claude Code 等 AI 助手，让它们能分析错误、解析符号、跑测试、管依赖。前者改变了"App 内部如何呈现 AI 结果"，后者改变了"开发者如何写 Flutter 代码"，两条线合起来，是 Flutter 拥抱 AI 原生开发的关键落子。

---

**📱 深度报道**

**▌ 更新全景**

GenUI SDK 的定位是"AI 生成 UI 的编排层"。传统做法里，AI 回复是一段文本或 Markdown，要变成界面还得开发者手写映射。GenUI 的思路是：你把自己的 widget 目录注册给 SDK，AI 智能体在运行时返回一个基于这些 widget 的 JSON 描述，SDK 负责把它渲染成真实界面，并把用户交互产生的状态变化回传给智能体，形成一个高带宽的交互回路。这避免了"AI 生成任意 HTML 然后套壳"带来的样式失控，因为所有可见元素都来自你受控的 widget 库。Dart/Flutter MCP Server 则是开发侧的提效：AI 助手通过标准 MCP 协议接入你的工程，能读懂编译错误、跳转到符号定义、执行测试、搜索 pub.dev、格式化代码，相当于把 Flutter 专家经验装进编码助手。

**▌ 技术细节深解**

GenUI 的核心是"widget 目录即设计系统"，AI 不再自由发挥，而是从你声明的组件里挑选组合：

```dart
// 注册受控 widget 目录（示意）
final genui = GenUI(catalog: [
  WidgetSpec(name: 'ProductCard', props: {'title': String, 'price': double}),
  WidgetSpec(name: 'PrimaryButton', props: {'label': String}),
]);

// AI 返回的 JSON 描述，由 SDK 渲染而非手写映射
final ui = await genui.render({
  'type': 'ProductCard',
  'props': {'title': '鸿蒙手记', 'price': 29.0}
});
```

MCP Server 侧则是把 `flutter analyze`、`flutter test`、`dart doc` 等命令封装成 AI 可调用的工具，编码助手在对话中就能定位 `Widget` 类型不匹配、缺失 `const` 构造函数等问题，而不只是给一段泛泛建议。两条线一个是运行时、一个是开发时，共同把 AI 嵌入 Flutter 的全生命周期。

**▌ 开发者迁移指南**

GenUI 目前是 alpha，建议只在内部工具或低风险页面试点，切勿让它直接生成涉及资金、权限的核心流程界面——受控 widget 目录必须严格审计，避免 AI 组合出意料之外的交互。MCP Server 则可立即接入团队已有的 AI 编码工作流，收益是即时的错误定位与测试执行。要留意 GenUI 生成的 UI 仍要过无障碍与性能检查，不能因为"AI 生成的"就豁免质量门禁。对存量项目，建议先把 widget 目录梳理成可声明的形式，为 GenUI 做准备。

**▌ 生态与竞品对比**

React Native 借助庞大的 JavaScript AI 生态（OpenAI SDK、LangChain.js、Vercel AI SDK 原生可用）在"云 AI API"集成上占优；Flutter 则押注"受控生成 + 工具链 MCP"，走的是更可控的路线。SwiftUI 侧也有类似 AI 辅助趋势但更封闭。对团队选型：若重视 AI 生成 UI 的可控性与品牌一致性，Flutter 的 GenUI 路线值得关注；若重度依赖云端 LLM 编排，RN 的 JS 生态仍是更顺的选择。

### 7. 【端侧 vs 云端：移动应用集成大模型推理的框架选型】

> 📍 **导语**：2026 年，"App 里要不要有 AI"已经不是问题，"AI 跑在哪、用什么框架接"才是真问题。移动端大模型集成分裂出两条清晰路径：端侧推理让模型在设备本地跑，隐私不出端、延迟低、可离线、零单请求成本；云端推理把重活交给服务器的大模型，擅长长上下文与复杂多步任务。Production 级应用几乎都用混合策略——常规任务端侧搞定，重活甩给云端。对开发者而言，选错框架意味着要么包体积爆炸、要么体验卡顿、要么账单失控。Core ML、ML Kit、TensorFlow Lite、ExecuTorch、ONNX Runtime 各自适用不同场景，本文从工程视角做一次落地选型梳理。

---

**📱 深度报道**

**▌ 更新全景**

端侧推理的适用面在 2026 年显著拓宽：文本分类、简单摘要、图像分类、语音输入等任务，已能在骁龙、天玑、Apple Neural Engine 等 NPU 上稳定跑出亚百毫秒响应。Framework 侧，iOS 有 Core ML 与原生 Foundation Models 框架，安卓有 ML Kit 与 LiteRT（原 TensorFlow Lite），跨平台则有 ONNX Runtime 与 ExecuTorch（PyTorch 官方移动端方案）。云端侧，React Native 因 JavaScript 生态完整，OpenAI、Anthropic、LangChain.js、Vercel AI SDK 均可原生集成，几乎零封装成本；Flutter 侧则靠 `google_generative_ai` 等官方包直连 Gemini，或用 HTTP 调 REST。混合架构成为主流：端侧做实时过滤与轻任务，云端做复杂推理与知识更新，两者通过统一的状态管理层衔接。

**▌ 技术细节深解**

端侧集成的典型形态是"加载量化模型 + 委托加速"。以 ExecuTorch 在设备上跑 PyTorch 模型为例，关键是把计算委托给 NPU/GPU 后端，而不是 CPU 兜底：

```kotlin
// 安卓侧 ExecuTorch 推理（示意）
val module = Module.load("model.pte")
val input = Tensor.fromFloatArray(floatArrayOf(/* 特征 */))
val output = module.forward(input)   // 委托 NPU 执行，硬件加速
val result = output.toFloatArray()
```

选型判断可以收敛成一张表：追求隐私与离线 → 端侧（Core ML / LiteRT / ExecuTorch）；追求云端 LLM 编排与 Agent → RN + LangChain.js 或 Flutter + 官方生成包；需要跨平台一致且重视觉 AI（检测、姿态）→ Flutter + TFLite/ML Kit。包体积是端侧方案的隐形杀手：一个 200MB 的 TensorFlow 模型打进 App，会显著拉低转化率，量化到 INT4/INT8 与按需下载是必要手段。

**▌ 开发者迁移指南**

先按"任务复杂度"切分：把延迟敏感、数据敏感、可离线的任务定为端侧，把需要长上下文、最新知识、多步推理的任务定为云端。端侧项目要尽早做模型量化与懒加载，把大模型放到按需下载而非首包；云端项目要把流式响应、错误降级、限流做成标配，避免云端抖动拖垮整个 App。混合架构要设计统一入口，让业务代码不感知 AI 跑在哪。务必在低端机上验证端侧推理的发热与帧率，NPU 满载下的体验衰减往往被旗舰机测试掩盖。

**▌ 生态与竞品对比**

iOS 的 Core ML 与 Foundation Models 在端侧体验最顺，但封闭；安卓 LiteRT/ML Kit 覆盖广但有碎片化；跨平台 ONNX Runtime 胜在统一，ExecuTorch 胜在 PyTorch 原生。RN 在云端 AI 集成上生态最成熟，Flutter 在端侧视觉 AI 上更稳。对国内团队，还要考虑合规与数据出境：涉及敏感数据的任务，端侧或境内云是更稳妥的选择，不能一概上境外大模型。

🔮 **技术趋势**：移动 AI 集成正从"接一个大模型 API"演进为"端云协同的分层架构"，框架选型的核心变成"哪些任务留在端、哪些上云"，而非"用不用 AI"。
