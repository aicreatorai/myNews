### 1. 【Context7：把版本锁定的库文档实时注入 LLM 上下文，根治"模型用过时的 API"】

> 📍 **导语**
>
> 你有没有遇到过这种事：让 Claude 帮你写一段 Next.js 或 LangChain 代码，它信心满满地调了一个 API，结果一跑就报错——因为它学的是两年前的旧版本，而库早就改了签名。问题不在模型笨，而在于它"背"的是训练时截止的那份文档，跟不上快节奏的库迭代。upstash/context7 想解决的正是这个"文档过期"痛点：它作为一个 MCP 服务器，把各主流库**当前版本、带版本号锁定**的官方文档实时拉进你的 prompt，让模型永远用上对的 API。在 awesome-mcp.tools 的 2026 年 MCP 服务器榜单里，它以 54,000+ Star 排在第四，是开发者接入 MCP 生态后最常被推荐的第一个"知识型"服务器。

**▌ 它是什么**

Context7（仓库 `upstash/context7`，配套客户端 `@upstash/context7-mcp`）是一个由 Upstash 维护的开源 MCP 服务器，核心职责是用一条命令把"正确的库文档"喂给大模型。它的工作单位是"库 + 版本"：你告诉它"我要 React 18 的文档"，它就去抓取 React 18 这一确切版本的官方文档，转成模型友好的片段注入上下文，而不是笼统地塞一堆无关内容。

它本质上是一个**文档检索与版本对齐中间件**。传统做法里，开发者要么手动把库的 README 贴进 prompt（费 token、易过期），要么让模型靠训练记忆（易 hallucinate 到旧 API）。Context7 把"取哪份文档、取哪个版本"这件事自动化、协议化——任何兼容 MCP 的客户端（Claude Code、Cursor、Cline、VS Code 插件等）都能通过标准协议调用它，无需为每家客户端单独写适配器。

它和向量库 RAG 的区别在于：RAG 检索的是你私有的、可能杂乱的文档切片，而 Context7 检索的是**权威的、版本锁定的、由社区维护抓取 pipeline 的官方文档**。这是一种"专家知识源"而非"通用检索器"的定位。

**▌ 它解决了什么问题**

第一个问题是**模型用过期 API**。像 Next.js、React、LangChain、Vite 这类演进极快的库，半年就能换一套推荐写法。模型训练数据截止后学到的旧签名，在最新版里往往是错的。Context7 让"文档跟着版本走"，从根本上消除这类幻觉。

第二个问题是**手动搬运文档的笨重**。过去为了用对新 API，你得自己打开文档站、复制相关段落、粘进对话，既占上下文又容易粘错章节。Context7 把它变成一次性的协议接入，之后模型自己会按需取文档。

第三个问题是**多客户端重复适配**。团队里有人用 Claude Code、有人用 Cursor、有人用 Cline，如果每个工具都要单独接文档源，维护成本翻倍。MCP 标准化后，同一套 Context7 服务器对所有客户端通用。

第四个问题是**版本漂移导致的协作混乱**。一个项目锁定了库 A 的 2.x，另一个项目用 3.x，文档写法天差地别。Context7 的版本锁定让"这个项目该用哪份文档"变得显式、可控，而不是靠开发者记忆。

**▌ 原理拆解**

```
开发者在 prompt 里标注需要某库文档（或 Agent 自动触发）
  ↓
MCP 客户端（Claude Code / Cursor / Cline…）
  ↓ MCP 协议调用
Context7 服务器（upstash/context7-mcp）:
    1. 解析请求：库名 + 版本（如 react@18、next@14）
    2. 从文档抓取 pipeline 取该版本官方文档（Markdown / 站点）
    3. 切片 + 相关性筛选，控制注入 token 量
    4. 返回版本对齐的文档片段
  ↓
注入模型上下文
  ↓
模型基于"对的版本"生成代码 → 显著降低 API 误用
```

理解 Context7 的钥匙是**"版本"是关键第一公民**。它不检索"最新"，而是检索"你指定的那个版本"。这背后的工程取舍是：文档质量比数量重要，且只有和项目实际依赖版本一致的文档才有用。抓取 pipeline 由社区持续维护主流库的文档源，保证覆盖度；而注入时对 token 总量的裁剪，则保证不会因为塞太多文档而撑爆上下文。模型这边无需任何改动，它只是"恰好拿到了正确的参考资料"。

**▌ 动手验证**

```bash
# 1. 准备 Node.js（MCP 客户端以 npx 方式拉起）
node --version        # 预期：>= 18

# 2. 【核心验证一·最小接入（以 Claude Code / Cursor 的 MCP 配置为例）】
#    在客户端 MCP 配置里加入：
#    {
#      "mcpServers": {
#        "context7": { "command": "npx", "args": ["-y", "@upstash/context7-mcp"] }
#      }
#    }
#    预期：客户端重启后识别到 context7 工具

# 3. 【核心验证二·让模型用对版本 API】
#    提问："用 context7 取 next@14 的 App Router 文档，写一个服务端组件"
#    预期：生成的代码使用 next@14 的当前写法（如 async 组件、cookies() 返回 Promise）
#    对比：若不接 Context7，模型可能写出 next@12 的旧写法

# 4. 【核心验证三·版本锁定的差异可见】
#    分别请求 react@17 与 react@18 的 useEffect 文档
#    预期：两次返回的片段在 API 细节上有可见差异，证明"版本"确实生效
#    若两次返回完全一致，说明版本参数被忽略，需检查客户端传参

# 5. 【边界验证·上下文占用】
#    观察注入后的 token 占用，确认文档片段被裁剪到合理规模
#    预期：不会把整本文档库塞进来；关键 API 段落被优先保留
```

验证标准盯四条。**第 3 步的"版本差异可见"是最关键的一条**——如果 react@17 和 react@18 返回完全一样，说明版本锁定没生效，那它和让模型自己编没区别。第一条是能接：第 2 步客户端识别到工具。第二条是**真能用对**：第 3 步生成的代码贴合指定版本。第四条是**不撑爆**：第 5 步确认注入被裁剪，否则上下文成本失控。

**▌ 对比选型**

| 对比维度 | Context7 | 手动贴 README | 自建库文档 RAG |
|---|---|---|---|
| 文档来源 | 官方、版本锁定 | 人工复制 | 自建索引 |
| 版本对齐 | 显式指定版本 | 看运气 | 需自己维护 |
| 接入成本 | 一条 npx 配置 | 每次手动 | 较高 |
| 适合场景 | 快迭代库的正确调用 | 临时小抄 | 私有文档为主 |

选型建议：你频繁调用 Next.js、React、LangChain 等演进快的库，且受够模型写出过期 API，Context7 是接入成本最低、收益最立竿见影的方案，先接成 MCP 服务器试一周；如果你主要处理的是私有内部文档，那应该上通用 RAG 而不是 Context7；如果只是偶尔查一个 API，手动贴一次 README 也没问题。**分水岭是：你的痛点是"库文档过期"，还是"没有文档可查"。**

### 2. 【agent-skills：Addy Osmani 出品的面向 AI 编程 Agent 的生产级工程技能库】

> 📍 **导语**
>
> 你让编码 Agent 帮你做代码审查、写测试、做性能优化，它往往给出"像那么回事但不够专业"的泛泛建议——因为它缺少领域里那些"老手才知道"的套路。Google 工程大师 Addy Osmani 开源的 `addyosmani/agent-skills`，想解决的就是这个"Agent 不够专业"的问题：它把一批经过实战打磨的**工程技能与工作流**打包成技能包，直接喂给 Claude Code、Cursor 这类编程 Agent，让它们按"生产级"标准做事。在 2026-08-10 的 GitHub Trending 归档里，它以 85,721 Star、单日 +659 的势头出现在榜单上，是"技能即资产"这一 2026 年 Agent 工具主线的代表项目之一。

**▌ 它是什么**

`addyosmani/agent-skills` 是一个用 JavaScript 编写的开源技能库，定位是"为 AI 编码 Agent 提供的生产级工程技能与工作流"。它和单纯的一篇提示词不同：每个技能是一份结构化的、可被执行的工作流说明，覆盖代码审查、测试生成、性能优化、可访问性检查等工程场景。

它的角色是**"专家经验的外挂"**。Agent 本身有通用能力，但缺的是某个垂直领域里的标准动作清单——比如"做前端性能审计时应该按哪些指标逐条检查"。agent-skills 把这些清单固化下来，Agent 加载后就能像资深工程师一样按步骤执行，而不是凭感觉发挥。

项目出自 Addy Osmani 之手，这本身是一层质量背书：他是前端性能与工程实践领域的权威，技能库里沉淀的正是他本人长期倡导的工程方法论。这种"名人效应 + 实战方法论"的组合，让它迅速在编程 Agent 用户群里扩散。

**▌ 它解决了什么问题**

第一个问题是**Agent 输出不够"生产级"**。通用 Agent 写代码能跑，但常常不符合团队的工程规范、缺少边界检查、测试覆盖不全。技能库把"什么是合格交付"的标准动作显式化。

第二个问题是**经验不可复用**。团队里某个高手总结的"审查清单"通常只存在他脑子里或某篇 wiki 里。技能包让这套经验变成可被任何 Agent、任何成员调用的资产。

第三个问题是**跨 Agent 不一致**。同一个任务，今天用 Claude Code 做、明天用 Cursor 做，结果质量飘忽。统一的技能库让不同客户端执行同一类任务时遵循同一套标准。

第四个问题是**上手门槛**。新手开发者不知道"好的代码审查应该看什么"，技能库相当于一个随时在线的资深导师，按标准流程带他走一遍。

**▌ 原理拆解**

```
开发者在 Agent 中触发某个工程任务（如"审查这个 PR"）
  ↓
Agent 加载对应技能（来自 agent-skills 技能包）
  ↓
技能作为结构化工作流注入上下文:
    定义目标 → 分解检查项 → 逐步执行 → 产出结构化报告
  ↓
Agent 按技能规定的步骤（而非自由发挥）完成任务
  ↓
输出符合"生产级"标准的产物（审查意见 / 测试 / 优化建议）
```

理解它的钥匙是**"技能是约束，不是建议"**。普通提示词是软性的——模型可以听也可以不听；而一个设计良好的技能包，把任务拆成强制的步骤序列与 checklist，Agent 必须逐条走完才能交付。这把"模型的能力上限"和"交付的质量下限"解耦：即使模型发挥一般，只要遵循技能流程，产出也能达到基本专业线。这也是 2026 年"技能协议化"浪潮的核心思想——用结构化经验补足模型的随机性。

**▌ 动手验证**

```bash

git clone https://github.com/addyosmani/agent-skills.git
cd agent-skills
#    预期：仓库克隆成功，内含各技能目录

# 2. 【核心验证一·把某个技能接入你的 Agent】
#    按 README 把技能目录挂载到 Claude Code / Cursor 的技能加载路径
#    预期：Agent 能识别到该技能（如 code-review 技能）

#    在 Agent 中发起："用 code-review 技能审查当前分支的改动"
#    预期：返回按检查项逐条列出的审查意见（性能/安全/可维护性），而非泛泛一句"看起来不错"

#    用同一技能分别对两个不同 PR 做审查
#    预期：两份报告遵循同一套检查维度，质量基线一致

# 5. 【边界验证·技能可裁剪】
#    尝试只启用你团队关心的检查项（如只保留安全与性能）
#    预期：可通过配置裁剪技能范围，避免噪音
```

验证标准盯四条。**第 3 步的"逐条审查而非泛泛而谈"是最关键的一条**——技能库的价值就在于把模糊的"帮我看看"变成结构化的专业审查。第一条是能接：第 2 步 Agent 识别到技能。第二条是**真专业**：第 3 步输出有检查维度、有具体位置。第三条是**一致**：第 4 步不同 PR 质量基线稳定。第四条是**可裁剪**：第 5 步能按需开关检查项。

| 形态 | 结构化技能包 | 文本指令 | 文档 |

### 3. 【Browser-Use：教 AI Agent 像人一样点击、输入、浏览网页的开源框架】

> 📍 **导语**
>
> 你想让 Agent 帮你"去这个网站把价格抄下来""在那个后台导出报表"，但它既不会开浏览器、也不认得页面上的按钮。过去要让 AI 操作网页，要么写脆弱的 XPath 脚本（页面一改就崩），要么依赖专用 API（很多网站根本没有）。`browser-use/browser-use` 想解决的就是这个"Agent 看不见、点不了网页"的痛点：它让 AI Agent 像人一样自主浏览网站——读页面、识别元素、点击、输入、翻页，把任意网页变成 Agent 可操作的界面。在 rpabotsworld 的 2026 年开源 Agentic AI 榜单里，它以 107,000+ Star 位列第八，是"给 Agent 装上眼睛和手"这一趋势里最纯粹的网页操作代表。

**▌ 它是什么**

`browser-use`（仓库 `browser-use/browser-use`）是一个用 Python 编写、MIT 协议的开源框架，核心能力是**赋予 AI Agent 自主操作真实网站的能力**。它处理的是"网页理解 + 动作执行"的完整闭环：Agent 不再是只能调用一个写死的 API，而是能面对任意网页，自主决定"下一步该点哪里、填什么"。

它把浏览器自动化从"脚本驱动"升级为"智能体驱动"。传统自动化（如 Selenium 脚本）需要开发者预先写好"先点这个 id、再填这个框"的死路径；Browser-Use 让模型自己看懂页面、自己规划动作序列，因此更能应对页面结构变化。它天然适配各类需要"从网页取数/操作网页"的场景：竞品监控、表单填报、数据抓取、网站回归测试等。

它是一个 Agent 能力底座，而非一个成品应用——你把它嵌进自己的 Agent 工作流，它负责"网页这层"的执行，上层由你的 Agent 决定目标。这种"专注一件事并做到开源生态里最好"的定位，让它成为许多 Agent 项目的默认网页操作层。

**▌ 它解决了什么问题**

第一个问题是**网页对 Agent 不可见**。很多任务的最终动作发生在网页上（下单、导出、填报），但 Agent 只会调 API，遇到没有 API 的网站就束手无策。Browser-Use 把网页变成 Agent 的直接操作面。

第二个问题是**传统脚本太脆**。Selenium/Playwright 写死的定位器，一旦前端改版就失效，维护成本高。Browser-Use 让模型动态理解页面，抗变动能力更强。

第三个问题是**跨网站复用难**。为每个网站单独写自动化不现实。Browser-Use 提供统一的"看—想—做"接口，换网站只需换目标描述，不用重写脚本。

第四个问题是**人工重复操作**。大量白领工作是在网页上点来点去（查价格、填表单、导数据）。把这些交给会浏览网页的 Agent，能释放可观人力。

**▌ 原理拆解**

```
Agent 给出高层目标（如"查竞品 A 官网的旗舰款价格"）
  ↓
Browser-Use 控制真实浏览器加载页面
  ↓
页面理解:
    解析 DOM / 可访问性树 → 识别可交互元素（按钮/输入框/链接）
    把页面状态 + 可选项翻译成模型能懂的描述
  ↓
模型决策:
    基于目标与当前页面，选择下一步动作（点击/输入/翻页/提交）
  ↓
执行动作 → 页面状态变化 → 重新理解
  ↓ 循环直至目标达成
```

### 4. 【Scrapling：自适应反检测网页抓取框架，为 AI Agent 提供可靠的实时网络数据】

> 📍 **导语**
>
> 你的 Agent 需要实时网页数据——股价、舆情、商品库存、竞品动态——但你写的爬虫要么被 Cloudflare 一把拦下，要么网站一改版就抓不到。2026 年的 Agent 越能"思考"，越卡在"取不到干净数据"这一环。`Scrapling` 想解决的就是这个"抓取不可靠"的老大难：它是一个自适应网页抓取框架，从单次请求到全站爬取都能扛，靠反检测与自适应解析让抓取在真实对抗环境下依然稳。在 coddykit 的 2026 年 GitHub 热门 AI 开发工具盘点里，它以 59,500+ Star、单周 +1,100 的势头上榜，被点名"特别适合需要从网页收集实时数据的 AI Agent"。

**▌ 它是什么**

`Scrapling` 是一个用 Python 编写的开源网页抓取框架，定位是**为对抗性真实环境设计的自适应抓取器**。它和普通爬虫库（requests + BeautifulSoup）最大的不同，在于内建了"反检测"与"自适应解析"两层能力：反检测让请求更像一个真实浏览器，降低被风控拦截的概率；自适应解析让选择器在页面结构微调时仍能定位到目标内容，而不是一改版就失效。

它的能力跨度很宽：既能发一次请求抓一个字段，也能编排成全站级 crawl。这种"小到单点、大到全网"的统一接口，使它既能服务轻量 Agent 的即时取数，也能支撑大规模数据采集管线。它对 AI Agent 的特别价值在于——Agent 的决策质量高度依赖"喂进来的数据干不干净、及不及时"，而 Scrapling 正是那个把杂乱网页变成结构化可靠数据的入口。

它和 Browser-Use 是互补关系：Browser-Use 让 Agent "像人一样操作网页"，偏交互；Scrapling 让开发者"稳定地把网页数据抓回来"，偏采集。一个 Agent 系统里，前者负责操作、后者负责取数，常常搭配出现。

**▌ 它解决了什么问题**

第一个问题是**反爬拦截**。现代网站普遍部署 Cloudflare、Akamai 等防护，朴素请求直接 403。Scrapling 的反检测层（如浏览器指纹伪装、请求节奏控制）提高通过率。

第二个问题是**页面改版即失效**。传统爬虫靠写死 XPath/CSS 选择器，前端一重构就抓空。自适应解析在结构微调时仍能命中目标，降低维护频率。

第三个问题是**数据供给不稳拖垮 Agent**。Agent 再聪明，喂给它过期或残缺的网页数据，结论也是错的。Scrapling 把"数据入口"做可靠，是 Agent 可靠性的上游保障。

第四个问题是**采集规模难伸缩**。有的任务只要一个价格，有的要爬全站。Scrapling 统一接口覆盖两种极端，开发者不必为不同规模换工具。

**▌ 原理拆解**

```

  ↓
请求层（反检测）:
    浏览器级指纹伪装 / 合理请求头与节奏 / 规避基础风控
  ↓
获取渲染后的页面内容
  ↓
解析层（自适应）:
    不依赖单一死选择器，结合多策略定位目标字段
    页面结构微调时自动回退到备选定位逻辑
  ↓
结构化输出（JSON / 字段表）
  ↓
供 Agent / 数据管线消费
```

理解它的钥匙是**"反检测保住请求、自适应保住解析"两条防线**。很多框架只解决其中一条：有的能伪装请求但解析写死，页面一改还是废；有的解析聪明但请求太"机器味"直接被拦。Scrapling 把两者都做进框架，才在真实对抗环境里站得住。自适应解析的实现思路类似"多证据定位"——不只信一个 XPath，而是综合文本特征、位置、上下文多重信号去锁定字段，单一信号失效时其他信号能补位，这正是它抗改版的核心。

> 你每天都在用 Claude Code、Cursor、Codex 写代码，但有没有觉得：同一个 Agent，别人的用起来又快又准，你的却总在重复踩坑、跑无用工具、记忆混乱？问题往往不在模型，而在"怎么驾驭 Agent"这套上层工程。`affaan-m/ECC` 想解决的就是这个"Agent 没被优化"的问题：它是一个 Agent Harness 性能优化系统，针对 Claude Code、Codex、OpenCode、Cursor 等编程 Agent，从**技能（skills）、本能（instincts）、记忆（memory）、安全（security）**四个维度做优化，并引入"研究优先"的开发循环让 Agent 自己迭代自己的提示词与工具策略。在 dibi8 的 2026 年开源 Agent 周榜里，它以 223,000 Star 高居第一，被点名"对每天用编程 Agent 的开发者，能立刻带来效率提升"。

**▌ 它是什么**

`affaan-m/ECC`（Agent Harness 性能优化系统）是一个开源的、面向编程 Agent 的上层优化框架，核心是对你已经在用的编码 Agent 做"调校"，而不是再造一个 Agent。它把优化拆成四个维度：

- **Skills（技能）**：把高频、可复用的操作固化成技能，减少每次从零推理；
- **Instincts（本能）**：把"遇到某类情况该怎么做"的隐性偏好沉淀成可加载的规则；
- **Memory（记忆）**：让 Agent 跨会话保留有用的上下文与经验，不重复踩坑；
- **Security（安全）**：在优化效率的同时守住权限与操作边界。

它最独特的一点是**"研究优先（research-first）开发循环"**：Agent 不只是被动执行，而是会主动研究"我现在的提示词和工具用法是不是最优的"，然后迭代改进自己。这让 ECC 不只是一个配置模板，而是一个让 Agent 持续自我调优的元层。

它和 deer-flow 这类"从零造 harness"的项目不同——ECC 站在你已有 Agent 的肩膀上做增量优化，接入成本更低，适合"我已经用着 Claude Code，只想让它更聪明"的开发者。

**▌ 它解决了什么问题**

第一个问题是**Agent 重复踩坑**。没有记忆与技能沉淀，每次新会话都从零开始，同样的错误反复犯。ECC 用 memory + skills 把经验留住、复用。

第二个问题是**工具调用效率低**。Agent 常常调用无用工具、走弯路。instincts 层把"什么情况用什么工具"的直觉固化，减少试错。

第三个问题是**提示词不是最优**。大多数人的 Agent 配置是随手写的，远没到最优。research-first 循环让 Agent 自己研究发现并改进提示词与策略。

第四个问题是**效率与安全的拉扯**。一味追求快容易越权乱改。ECC 把 security 作为四大维度之一，优化时不牺牲安全边界。

**▌ 原理拆解**

```
开发者日常使用 Claude Code / Cursor / Codex（已接 ECC）
  ↓
ECC 四个优化维度持续作用:
    Skills  → 高频操作固化，免重复推理
    Instincts → 情境→动作 的隐性规则沉淀
    Memory → 跨会话保留经验，避免重复踩坑
    Security → 权限与操作边界约束
  ↓
Research-First 循环（元层）:
    Agent 研究当前提示词/工具策略是否最优
      ↓ 发现改进点
    迭代更新 skills / instincts / 提示词
      ↓ 自我调优，闭环
  ↓
Agent 表现随时间持续提升（越用越聪明）
```

理解 ECC 的钥匙是**"它优化的是'怎么用 Agent'，而非'Agent 本身'"**。模型能力是给定的，但"如何组织技能、如何沉淀本能、如何管理记忆、如何守住安全"是一层可工程化的上层。research-first 循环则是点睛之笔：它让这层优化不是一次性的静态配置，而是一个会自我审视、自我改进的活系统。这呼应了 2026 年 Agent 领域的一个共识——真正的竞争不在"用什么模型"，而在"怎么让 Agent 越用越聪明"。

**▌ 动手验证**

```bash
# 1. 准备（Node.js，且已安装某编程 Agent 如 Claude Code / Cursor）
node --version && claude --version        # 预期：版本正常

# 2. 获取 ECC
git clone https://github.com/affaan-m/ECC.git
cd ECC
#    按 README 将其优化层接入你的 Agent（通常作为配置/插件加载）

# 3. 【核心验证一·技能与记忆是否生效】
#    让 Agent 先做一次某类任务，再在新会话做同类任务
#    预期：第二次明显更快/更准，且复用了第一次沉淀的技能与记忆
#    若两次毫无差别，说明 skills/memory 没接上

# 4. 【核心验证二·本能规则可加载】
#    配置一条 instinct（如"改生产配置前必须先确认"）
#    预期：Agent 在相应情境下主动遵循该规则
#    若规则被无视，说明 instincts 层未生效

# 5. 【核心验证三·research-first 自我调优】
#    观察运行一段时间后，Agent 是否主动改进了提示词/工具策略
#    预期：能观察到策略迭代的痕迹（如更高效的任务拆解）
#    若始终静止不变，说明 research 循环没跑起来

# 6. 【边界验证·安全不被牺牲】
#    尝试一个危险操作（如删除重要文件）
#    预期：Security 维度拦截或要求确认，不因追求效率而放行
```

验证标准盯四条。**第 3 步的"跨会话复用"是最关键的一条**——如果第二次和第一次毫无区别，说明 memory/skills 形同虚设，ECC 的核心价值没落地。第一条是能接：第 2 步优化层加载成功。第二条是**真沉淀**：第 3 步经验被复用。第三条是**本能生效**：第 4 步规则被遵循。第四条是**安全守住**：第 6 步危险操作被拦，证明优化不以牺牲安全为代价。

**▌ 对比选型**

| 对比维度 | ECC | deer-flow | 手写 Agent 配置 |
|---|---|---|---|
| 定位 | 已有 Agent 的性能优化层 | 从零造 SuperAgent harness | 手动调提示词 |
| 接入成本 | 低（叠加在现有 Agent 上） | 高（整套服务栈） | 极低但无系统 |
| 自我调优 | research-first 循环 | 依赖编排逻辑 | 无 |
| 适合场景 | 想让现有 Agent 更聪明 | 想建完整 Agent 平台 | 临时小调 |

选型建议：你已经深度使用 Claude Code / Cursor / Codex，想**低成本让它们更快更准更不易踩坑**，ECC 是叠加式优化里星标最高、维度最全的选择，先接入观察跨会话复用是否生效；如果你要从零搭一个企业级 Agent 平台，deer-flow 这类完整 harness 更合适；如果只是偶尔调一句提示词，手写配置也够。**分水岭是：你要"调校已有 Agent"，还是"重建 Agent 系统"。**
