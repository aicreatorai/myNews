### 1. 【Apache Flink 2.2.1 发布：实时数据管道架构的 production-grade 实践】

> 📍 **导语**：2026年5月15日，Apache Flink 社区发布 2.2.1 维护版本，包含44个bug修复和安全漏洞修补。结合2.2.0在AI函数、向量检索、物化表等方向的重大升级，Flink 正式从"流处理引擎"演进为"实时AI数据基础设施"。本文深度解析基于 Flink 2.2 构建生产级实时数据管道的架构设计、性能调优参数和踩坑经验。

---

**⚙️ 深度工程解析**

**▌ 场景与痛点**

随着大模型应用全面落地，实时数据管道面临三类新需求：
1. **Embedding实时更新**：用户行为向量需在秒级写入向量数据库，支撑RAG实时检索
2. **特征实时刷新**：推荐/风控模型的在线特征需要端到端延迟 < 100ms
3. **多模态数据流**：文本、图像、音频数据的统一流处理框架

传统方案（Kafka Streams + 自研算子）的瓶颈：
- 缺乏原生向量计算支持，Embedding推理需外部调用，序列化开销大
- 状态后端（State Backend）在大规模场景下GC压力显著，checkpoint 频繁超时
- 批流一体语法不统一，ETL代码需要维护两套

某电商实时推荐场景数据：日处理消息量 120亿条，Kafka分区数 2048，Flink作业并行度 512。升级前，checkpoint 超时率 8.3%，P99 延迟 2.1s。

**▌ 架构设计**

Flink 2.2 的核心架构升级围绕"AI-Native Stream Processing"展开：

```
数据源层
  ├── Kafka (Flink Kafka Connector 2.2: 支持 incremental fetch)
  ├── Pulsar (新增 exactly-once 语义保证)
  └── CDC (MySQL Binlog → Debezium → Flink)
        ↓
采集层 (Source API - 统一批流Source)
  ├── 新增 AI Function 算子：内置 Embedding 推理（支持本地/远程）
  ├── Vector Collector：向量聚合窗口，支持 HNSW 索引增量构建
  └── Unified Source API：批流作业代码复用率 > 85%
        ↓
处理层 (Window & State)
  ├── 物化表（Materialized Table）：SQL 声明的持久化状态表，自动维护变更日志
  ├── State Backend 优化：RocksDB state backend 支持零拷贝读取，减少序列化
  └── Checkpoint 优化：Unaligned Checkpoint 支持细粒度对齐，超时率降低60%
        ↓
输出层 (Sink API)
  ├── 向量数据库 Sink：Milvus/Qdrant 原生连接器（社区贡献）
  ├── Data Lake Sink：Iceberg Sink 支持 CREATE TABLE AS 语法
  └── 监控输出：Prometheus Sink + 自定义 Metrics Reporter
```

**关键设计决策**：

| 决策点 | 选型 | 理由 |
|--------|------|------|
| State Backend | RocksDB + 零拷贝优化 | 大规模状态（>100GB）场景，堆外内存管理优于堆内 |
| Checkpoint 策略 | Unaligned + 增量 | 反压场景下，aligned checkpoint 容易超时 |
| 部署模式 | Application Mode on K8s | 资源隔离优于 Session Mode，恢复速度快于 Per-Job |
| AI函数部署 | 本地嵌入模型（ONNX） | 避免远程推理网络延迟，P99 降低 40ms |

**▌ 工程实现要点**

**核心配置示例（生产级参数）**：

```yaml
# flink-conf.yaml 关键参数
state.backend: rocksdb
state.backend.rocksdb.use-management-loader: true
state.backend.rocksdb.memory.managed: true
state.backend.rocksdb.block.cache-size: 2gb

# Checkpoint 配置
execution.checkpointing.mode: EXACTLY_ONCE
execution.checkpointing.unaligned: true
execution.checkpointing.storage: s3://flink-checkpoints/
execution.checkpointing.max-concurrent-checkpoints: 1

# AI Function 配置
ai.function.embedding.model: "text-embedding-3-small-onnx"
ai.function.embedding.batch-size: 32
ai.function.embedding.local-cache-size: 10000
```

**性能调优关键参数**：

- `taskmanager.memory.managed.fraction: 0.5`（RocksDB状态后端需要足够的托管内存）
- `taskmanager.numberOfTaskSlots: 4`（匹配 CPU 核心数，避免超线程争抢）
- `parallelism.default: 128`（根据 Kafka 分区数设置，建议 1:1 或 2:1）

**踩坑经验**：
1. **RocksDB 内存泄漏**：Flink 2.2.0 存在 RocksDB native memory 统计不准确的 bug，导致 TaskManager OOM。2.2.1 已修复，务必升级
2. **Unaligned Checkpoint 与 Savepoint 不兼容**：使用 unaligned checkpoint 后，从 savepoint 恢复会失败。解决：定期做 aligned checkpoint 用于跨版本迁移
3. **AI Function 算子序列化**：Embedding 模型权重需要在每个 TaskManager 本地加载，避免每次 checkpoint 序列化模型参数（使用 `transient` 标记）

**▌ 方案对比**

| 对比维度 | Flink 2.2 | Spark Streaming | Kafka Streams |
|---------|-------------|----------------|---------------|
| 延迟 | 毫秒级（event-time） | 秒级（micro-batch） | 毫秒级 |
| 状态管理 | RocksDB/Heap，支持TB级 | 仅堆内，受限 | RocksDB，规模受限 |
| AI原生支持 | ✅ 内置AI函数+向量检索 | ❌ 需外部调用 | ❌ 需外部调用 |
| 批流一体 | ✅ Unified API | ✅ 但语法差异大 | ❌ 仅流处理 |
| 运维成本 | 中（需K8s经验） | 高（资源消耗大） | 低（嵌入应用） |
| 适合团队 | 中大型（专人运维） | 大型（批处理为主） | 小型（简单流处理） |

**▌ 关键数据与效果**

| 指标 | 优化前（Flink 1.18） | 优化后（Flink 2.2.1） |
|------|----------------------|------------------------|
| Checkpoint 超时率 | 8.3% | 1.2% |
| P99 端到端延迟 | 2100ms | 180ms |
| 状态恢复时间 | 12min | 3min |
| 向量推理吞吐 | 800 records/s | 3200 records/s |
| 资源成本（同等吞吐） | 基准 | 降低 35% |

### 2. 【湖仓一体选型实战：Iceberg vs Delta Lake vs Hudi 2026版深度对比】

> 📍 **导语**：截至2026年，Apache Iceberg、Delta Lake、Apache Hudi 已成为企业构建湖仓一体架构的三大主流开源表格式。本文基于2026年3月最新生产数据，从ACID事务性能、Schema演进成本、引擎兼容性、云原生支持四个维度，给出可落地的选型决策框架。

---

**⚙️ 深度工程解析**

**▌ 场景与痛点**

某企业数据平台升级场景：原有 Hive 数仓面临三大痛点：
1. **Schema 变更成本高**：新增列需要重写全表，TB级分区表耗时数小时
2. **ACID 缺失**：并发写场景（Spark + Flink 同时写同一表）导致数据不一致
3. **时间旅行需求**：合规审计要求能查询任意历史时点数据，Hive 无法实现

技术团队在 Iceberg、Delta Lake、Hudi 三者间选型，核心约束：
- 数据规模：单表最大 50TB，日均增量 200GB
- 计算引擎：Spark（批处理）+ Flink（流写入）+ Trino（OLAP查询）
- 部署环境：AWS S3 + K8s

**▌ 架构设计**

三大表格式的核心架构差异：

**Iceberg 架构特点**：
- 元数据采用分层设计：Metadata File → Manifest List → Manifest File → Data File
- 支持 Hidden Partitioning：查询无需指定分区字段，引擎自动 pruning
- 引擎无关设计：任何支持 Iceberg SPI 的引擎均可读写

**Delta Lake 架构特点**：
- 事务日志（Delta Log）采用顺序追加模式，每笔事务写一个 JSON 文件
- 与 Spark 深度绑定（Delta Lake 由 Databricks 主导），其他引擎支持较弱
- 支持 DLT（Delta Live Tables）：声明式 ETL 管道

**Hudi 架构特点**：
- 核心概念：Timeline + Instant，支持三种写模式（Copy-On-Write / Merge-On-Read / Bulk Insert）
- 原生支持增量处理：可查询自某时间点以来的变更数据（Incremental Read）
- 与 Flink 集成最深入：Hudi 是三者中唯一支持 Flink 流式写入生产级的表格式

```
写入路径对比：

Flink → Iceberg Sink
  支持：EXACTLY_ONCE，支持 CDC 入湖
  限制：增量读取（Incremental Read）需配合 Flink 1.18+

Flink → Hudi Sink  
  支持：COW + MOR 两种模式，增量读取成熟
  限制：小文件合并需独立调度

Flink → Delta Sink
  支持：1.18+ 支持，但 EXACTLY_ONCE 有已知问题
  限制：生产环境建议用 Spark 写入 Delta
```

**▌ 工程实现要点**

**Iceberg 生产部署关键配置**：

```sql
-- 创建 Iceberg 表（Spark SQL）
CREATE TABLE telemetry.iot_events (
    event_id STRING,
    device_id STRING,
    event_time TIMESTAMP,
    metric_name STRING,
    metric_value DOUBLE
) USING iceberg
PARTITIONED BY (days(event_time))
TBLPROPERTIES (
    'write.format.default' = 'parquet',
    'write.parquet.compression-codec' = 'zstd',
    'write.metadata.delete-after-commit.enabled' = 'true',  -- 自动清理旧元数据
    'history.expire.max-snapshot-age-ms' = '259200000'     -- 3天
);
```

**Flink 流式写入 Iceberg 配置**：

```java
// Flink DataStream API
IcebergSink.Builder<T> sinkBuilder = IcebergSink.forRowData(inputStream)
    .setCatalog(catalog)
    .setTable(table)
    .setWriteParallelism(128)
    .setUnalignedCheckpoints(true)  // 配合 Flink checkpoint 策略
    .build();
```

**踩坑经验**：

1. **Iceberg 小文件问题**：流式写入会产生大量小文件，需配置自动压缩（Spark Structured Streaming `compaction.interval.ms`）或独立调度 `CALL catalog_name.system.rewrite_data_files('table')`
2. **Delta Lake 的 Spark 锁定**：非 Spark 引擎（如 Trino）读取 Delta 表时，若存在未完成的 Spark 事务，会出现读取不一致。解决：配置 `delta.logRetentionDuration = "30 days"` 定期清理
3. **Hudi MOR 模式的读放大**：Merge-On-Read 模式在读时合并 log 文件，OLAP 查询延迟高。建议：近 7 天数据用 COW，历史数据用 MOR + 定期 COMPACTION

**▌ 方案对比**

| 对比维度 | Iceberg 1.6 | Delta Lake 3.2 | Hudi 1.0 |
|---------|-------------|----------------|----------|
| **ACID 事务** | ✅ 完整支持 | ✅ 完整支持 | ✅ 完整支持 |
| **Schema 演进** | ✅ 零重写 | ⚠️ 部分重写 | ⚠️ 部分重写 |
| **引擎兼容性** | Spark/Flink/Trino/Presto/Dremio | Spark（主）/Trino（读）/Flink（实验性） | Spark/Flink（深度集成）/Presto |
| **流式写入成熟度** | ⭐⭐⭐⭐ | ⭐⭐ | ⭐⭐⭐⭐⭐ |
| **增量读取** | ✅ 支持 | ✅ 支持（Delta Sharing） | ✅ 原生支持（核心优势） |
| **云原生 S3 性能** | ⭐⭐⭐⭐⭐（元数据优化） | ⭐⭐⭐⭐ | ⭐⭐⭐ |
| **社区活跃度** | 高（Apache顶级项目） | 中（Databricks主导） | 中（Apache顶级项目） |
| **运维复杂度** | 中 | 低（Databricks托管） | 高（需调优MOR/COW） |

**选型决策树**：

```
是否需要 Flink 流式写入？
  ├── 是 → 选 Hudi（MOR模式）或 Iceberg
  └── 否 → 继续
             是否需要多引擎读取（Trino/Presto）？
                ├── 是 → 选 Iceberg（引擎兼容性最佳）
                └── 否 → 用 Delta Lake（Spark生态最优）
```

**▌ 关键数据与效果**

某电商用户画像平台迁移效果（从 Hive 到 Iceberg）：

| 指标 | Hive 方案 | Iceberg 方案 | 提升 |
|------|-----------|-------------|------|
| 日均增量写入延迟（P99） | 不支持流式 | 45s | — |
| Schema 变更时间（新增列） | 3.5h（全表重写） | 0s（元数据操作） | 100% |
| 查询性能（7天范围扫描） | 基准 | 提升 60% | Z-ordering 优化 |
| 存储成本 | 基准 | 降低 22% | Zstd 压缩 + 小文件合并 |
| 并发写入冲突率 | 12%/天 | 0% | ACID 事务保证 |

### 3. 【向量数据库生产选型：Milvus vs Qdrant vs Weaviate 性能与架构深度解析】

> 📍 **导语**：随着RAG系统从概念验证走向生产部署，向量数据库的选型直接决定了应用的检索性能、运维成本和扩展上限。本文基于2026年4-5月最新 benchmark 数据，从架构设计、查询性能、分布式能力、运维成本四个维度，深度对比三大主流开源向量数据库。

---

**⚙️ 深度工程解析**

**▌ 场景与痛点**

某金融科技公司构建智能客服知识库系统，技术要求：
- 文档规模：500万篇产品文档 + 200万条历史对话（合计约 30GB 向量数据）
- 查询 QPS：峰值 2000 QPS（工作日 9:00-18:00）
- 延迟要求：P99 < 50ms
- 过滤条件：需支持按产品类型、发布时间、文档来源等元数据过滤

初始方案采用 ChromaDB（单机版），问题：
- 数据量超过 1000万向量后，HNSW 索引构建时间 > 2小时
- 不支持分布式，单机内存瓶颈（128GB 物理内存上限）
- 元数据过滤性能差，组合过滤条件查询延迟 > 500ms

**▌ 架构设计**

**Milvus 2.x 架构**：

```
Client SDK (Python / Java / Go)
        ↓
Proxy 层（无状态，可水平扩展）
        ↓
MixCoord（混合协调者：替代独立的 rootcoord + indexcoord + datacoord）
        ↓
QueryNode（查询执行节点，支持 GPU 加速）
        ↓
IndexNode（索引构建节点，支持 IVF / HNSW / DiskANN）
        ↓
DataNode（数据写入节点，支持流式写入）
        ↓
对象存储（S3 / MinIO / Azure Blob）
```

核心特性：
- 存储与计算分离：索引存对象存储，QueryNode 按需加载
- 支持 GPU 加速：IVF 索引的 brute-force 搜索可在 GPU 上执行，吞吐提升 10x
- 支持 DiskANN：十亿级向量场景，内存需求降低 80%

**Qdrant 架构**：

```
Rust 实现，无 JVM 开销
        ↓
Memory Mapped 存储引擎（.mmap 文件）
        ↓
HNSW + 自定义量化索引（Scalar Quantization / Product Quantization）
        ↓
gRPC + REST 双协议支持
        ↓
Raft 共识协议（分布式模式，企业版）
```

核心特性：
- Rust 实现：内存安全 + 无 GC 停顿，P99 延迟稳定
- Payload 过滤：元数据过滤与向量搜索融合执行，性能优于"先过滤后搜索"模式
- 单机性能极强：10万向量查询延迟 < 5ms（Benchmark 数据）

**Weaviate 架构**：

```
Go 实现，模块化设计
        ↓
模块化索引引擎（支持 HNSW + 倒排索引融合）
        ↓
模块系统（AI 模型模块：text2vec-openai / text2vec-huggingface）
        ↓
GraphQL 查询接口（支持混合检索：向量 + BM25 + 图遍历）
        ↓
Schema-based 数据模型（类似 MongoDB 的 Collection 概念）
```

核心特性：
- 内置 AI 模块：可在数据库内直接调用 Embedding 模型，减少数据传输
- 混合检索：向量检索 + 关键词检索（BM25）融合排序
- 知识图谱集成：支持跨 Collection 的图查询

**▌ 工程实现要点**

**Qdrant 生产部署配置（推荐）**：

```yaml
# docker-compose.prod.yml
version: '3.8'
services:
  qdrant:
    image: qdrant/qdrant:v1.13.4
    ports:
      - "6333:6333"
      - "6334:6334"
    volumes:
      - ./qdrant_storage:/qdrant/storage
    environment:
      - QDRANT__SERVICE__HTTP_PORT=6333
      - QDRANT__SERVICE__GRPC_PORT=6334
    deploy:
      resources:
        limits:
          memory: 64G   # HNSW 索引需要常驻内存
    ulimits:
      memlock:
        soft: -1
        hard: -1
```

**索引构建策略对比**：

| 索引类型 | 适用场景 | 内存需求 | 查询延迟 | 构建时间 |
|---------|---------|---------|---------|---------|
| HNSW（Milvus/Qdrant/Weaviate均支持） | 中等规模（<1亿），追求低延迟 | O(N × M × d) | <10ms | 中 |
| IVF_FLAT（Milvus） | 大规模（>1亿），可接受稍高延迟 | O(N × nlist) | 10-50ms | 快 |
| DiskANN（Milvus） | 十亿级，内存受限 | O(N × d) / 5~10 | 50-100ms | 慢 |
| Scalar Quantization（Qdrant） | 内存受限，可接受微量精度损失 | 降低 75% | <5ms | 快 |

**踩坑经验**：

1. **Milvus 的 Knowhere 引擎内存泄漏**：Milvus 2.4 之前版本存在 GPU 索引构建时显存不释放的 bug。解决：升级至 2.5+ 或禁用 GPU 索引
2. **Qdrant 的 HNSW 参数调优**：`m=16, ef_construct=200` 是通用配置，但高维向量（>1024维）建议 `m=32`，否则召回率显著下降
3. **Weaviate 的模块版本锁定**：text2vec-openai 模块版本需与 Weaviate 主版本严格匹配，升级前务必检查兼容性矩阵

**▌ 方案对比**

| 对比维度 | Milvus 2.5 | Qdrant 1.13 | Weaviate 1.25 |
|---------|------------|-------------|---------------|
| **实现语言** | Go + C++ | Rust | Go |
| **分布式架构** | 存储计算分离，成熟 | 企业版支持（开源版单机） | 内置分布式，Raft共识 |
| **十亿级支持** | ✅ DiskANN | ⚠️ 需企业版 | ⚠️ 需调优 |
| **GPU加速** | ✅ 完善 | ❌ 不支持 | ❌ 不支持 |
| **混合检索** | ✅ 标量过滤 + 向量 | ✅ Payload过滤融合 | ✅ 向量+BM25融合 |
| **单机10万QPS延迟** | 8ms (P99) | 4ms (P99) | 12ms (P99) |
| **运维复杂度** | 高（多组件） | 低（单机二进制） | 中 |
| **适合团队** | 大型（有专职运维） | 中小型（简单部署） | 中型（需混合检索） |

**▌ 关键数据与效果**

某电商 RAG 系统（知识库规模：800万文档片段）生产数据：

| 指标 | Qdrant（选型结果） | Milvus | Weaviate |
|------|-------------------|--------|----------|
| P99 查询延迟 | 7ms | 15ms | 22ms |
| 写入吞吐（峰值） | 12,000 vectors/s | 18,000 vectors/s（GPU） | 8,000 vectors/s |
| 内存占用（800万 × 768维） | 28GB | 32GB | 35GB |
| 召回率@10（Recall@10） | 0.97 | 0.98 | 0.96 |
| 运维成本（人天/月） | 2 | 8 | 5 |

### 4. 【ML Pipeline 工程化：MLflow vs Kubeflow 全生命周期管理架构对比】

> 📍 **导语**：机器学习从实验到生产的"最后一公里"始终是工程痛点。MLflow 和 Kubeflow 作为两大主流 MLOps 平台，在模型训练、版本管理、部署监控等环节各有侧重。本文基于2026年最新版本（MLflow 2.18 / Kubeflow 1.9），从架构设计、适用场景、运维成本三个维度给出生产级选型建议。

### 5. 【Feature Store 工程实践：Feast + Tecton 特征平台架构与选型指南】

> 📍 **导语**：特征工程是机器学习系统中技术债务最严重的环节——相同特征被不同团队重复计算、线上线下特征计算逻辑不一致、特征血缘不可追溯。Feature Store（特征平台）通过将特征定义为可复用、可版本管理的资产，系统性解决这些问题。本文深度解析 Feast（开源）和 Tecton（企业级）的架构设计、适用场景和落地路径。

---

**⚙️ 深度工程解析**

**▌ 场景与痛点**

某互联网金融公司风控模型特征管理现状（引入 Feature Store 前）：
- 特征数量：1200+ 特征，分布在 15 个模型的训练/推理流程中
- 特征重复计算：相同特征（如"用户近30天交易金额"）被 8 个模型独立计算，逻辑略有差异
- 线上线下不一致：训练时用 SQL 计算，推理时用 Python 重新实现，结果差异导致模型效果下降 5-8%
- 特征血缘缺失：某特征计算逻辑变更后，无法评估影响范围，只能全量重训

**引入 Feature Store 后的目标架构**：
- 特征定义一次，训练和推理复用同一套逻辑
- 特征自动物化到在线存储（Redis），推理时 P99 延迟 < 5ms
- 特征血缘可追溯，影响评估自动化

**▌ 架构设计**

**Feast（开源，Go + Python）架构**：

```
Feature Registry（特征注册中心）
  ├── feature_views.py：特征视图定义（数据源 + 变换逻辑）
  ├── entity.py：实体定义（如 user_id, item_id）
  └── feature_service.py：特征服务（特征分组，用于模型输入）
        ↓
Offline Store（离线特征存储）
  ├── 支持：BigQuery / Redshift / Snowflake / DuckDB（本地开发）
  └── 用于：训练数据生成（Point-in-Time Join）
        ↓
Online Store（在线特征存储）
  ├── 支持：Redis / DynamoDB / SQLite（本地开发）
  └── 用于：推理时低延迟特征获取
        ↓
Feature Server（特征服务）
  ├── Python SDK（push / get_online_features）
  └── REST API（gRPC 在 Roadmap 中）
```

**核心概念：Point-in-Time Join**

Feast 的核心价值在于自动处理训练数据的时序拼接：

```python
# 定义特征视图
driver_stats_fv = FeatureView(
    name="driver_stats",
    entities=[driver_id],
    ttl=timedelta(days=7),
    schema=[
        Field(name="conv_rate", dtype=Float64),
        Field(name="acc_rate", dtype=Float64),
    ],
    online=True,
    source=driver_stats_table,  # 数据源（Batch/Stream）
    tags={"team": "risk"},
)
```

**Tecton（企业级，SaaS + 私有部署）架构**：

```
Tecton Platform（比 Feast 更高层抽象）
  ├── Declarative Feature Definition（Python DSL）
  │     ├── Batch Feature：定时物化（如每日计算昨日特征）
  │     ├── Stream Feature：实时计算（如过去5分钟交易次数）
  │     └── On-Demand Feature：推理时计算（如两个特征的比值）
  ├── Feature Pipeline Orchestration（内置 Airflow 风格的调度）
  ├── Feature Monitoring（特征值分布监控，漂移告警）
  └── Feature Lineage（完整血缘图，支持影响分析）
```

**Tecton 的核心优势**：
- 内置调度：特征物化自动调度，无需外部 Airflow
- 多模态特征：Batch + Stream + On-Demand 统一框架
- 企业级监控：特征值分布监控、漂移检测、告警集成

**▌ 工程实现要点**

**Feast 生产部署配置**：

### 6. 【RAG 数据工程：从文档解析到向量索引的生产级流水线架构】

> 📍 **导语**：RAG（检索增强生成）系统的效果上限由数据质量决定，而非模型能力。生产级 RAG 的数据工程涉及文档解析、分块策略、索引构建、检索优化四个核心环节，每个环节的工程决策直接影响最终回答质量。本文基于2026年5月最新实践，给出可落地的端到端 RAG 数据流水线架构设计。

---

**⚙️ 深度工程解析**

**▌ 场景与痛点**

某企业知识库 RAG 系统（文档规模：200万份 PDF/Word/HTML，合计约 500GB）：
- **解析层问题**：PDF 解析丢失表格结构，代码块被拆散，OCR 错误率 12%
- **分块层问题**：固定大小分块（512 tokens）导致语义断裂，跨块引用的答案不完整
- **索引层问题**：纯向量检索召回率低（Recall@5 < 0.7），关键词检索（BM25）无法处理同义词
- **端到端效果**：用户问题"如何申请报销"的回答准确率仅 65%

**▌ 架构设计**

**生产级 RAG 数据流水线四层架构**：

```
L1: 文档解析层（Document Parsing）
  ├── PDF 解析：PyMuPDF（速度快）+ Unstructured（结构保留好）
  ├── Office 文档：python-docx / openpyxl（表格需特殊处理）
  ├── HTML 清洗：BeautifulSoup + Readability.js（提取正文）
  └── 多模态：表格 → 转换为 Markdown 表格；图片 → OCR + 图片描述（VLM）
        ↓
L2: 分块与增强层（Chunking & Enhancement）
  ├── 语义分块：按标题层级分割（Markdown 标题感知）
  ├── 重叠分块：相邻块重叠 10-20%（保证跨块引用完整）
  ├── 元数据增强：标题路径（Breadcrumb）、文档来源、最后更新时间
  └── 摘要增强：对每个块用 LLM 生成摘要，用于粗召回
        ↓
L3: 索引构建层（Indexing）
  ├── 向量索引：Embedding（text-embedding-3-small）+ HNSW 索引（Qdrant）
  ├── 关键词索引：BM25（Elasticsearch / Lucene）
  ├── 图谱索引：实体抽取（NLP）→ 知识图谱（可选，复杂场景）
  └── 混合索引：向量 + BM25 + 元数据过滤融合
        ↓
L4: 检索与重排层（Retrieval & Reranking）
  ├── 粗召回：混合检索（向量Top-20 + BM25 Top-20）→ 合并去重
  ├── 精排：Cross-Encoder Reranker（如 BGE Reranker）
  ├── 上下文压缩：LLMLingua（压缩冗余 token，降低推理成本）
  └── 答案生成：Final Prompt = System Prompt + Reranked Context + User Query
```

**关键设计决策**：

**分块策略对比**：

| 策略 | 适用场景 | 优点 | 缺点 |
|------|---------|------|------|
| 固定大小（512 tokens） | 通用文档 | 实现简单 | 语义断裂 |
| 语义分块（标题感知） | 技术文档/手册 | 保持语义完整 | 需文档结构良好 |
| 递归分块（Recursive） | 无结构文档 | 自适应 | 可能过细 |
| 命题分块（Proposition） | 问答知识库 | 每个命题独立 | LLM 调用成本高 |

**▌ 工程实现要点**

**文档解析生产代码（PyMuPDF + Unstructured 混合）**：

```python
import fitz  # PyMuPDF
from unstructured.partition.pdf import partition_pdf

def parse_pdf_hybrid(file_path: str) -> list[dict]:
    """混合解析：表格用 PyMuPDF 提取，正文用 Unstructured"""
    elements = []
    
    # 第一步：Unstructured 提取结构元素
    unstructured_elements = partition_pdf(
        filename=file_path,
        strategy="hi_res",  # 使用 OCR 处理扫描件
        infer_table_structure=True,
    )
    
    for elem in unstructured_elements:
        elements.append({
            "content": elem.text,
            "type": elem.category,  # Title / NarrativeText / Table / Image
            "page": elem.metadata.page_number,
            "bbox": elem.metadata.coordinates,
        })
    
    return elements
```

**语义分块 + 向量化写入 Qdrant**：

```python
from sentence_transformers import SentenceTransformer
from qdrant_client import QdrantClient

model = SentenceTransformer("BGE-m3")
qdrant = QdrantClient(host="localhost", port=6333)

def build_rag_index(documents: list[dict]):
    """构建混合索引：向量 + 稀疏（BM25）"""
    for doc in documents:
        # 语义分块（按 Markdown 标题分割）
        chunks = semantic_chunk(doc["content"], max_tokens=512)
        
        for i, chunk in enumerate(chunks):
            embedding = model.encode(chunk["text"])
            
            qdrant.upsert(
                collection_name="knowledge_base",
                points=[{
                    "id": f"{doc['id']}_{i}",
                    "vector": embedding.tolist(),
                    "payload": {
                        "text": chunk["text"],
                        "doc_id": doc["id"],
                        "title_path": chunk["title_path"],  # 面包屑导航
                        "source": doc["source"],
                        "updated_at": doc["updated_at"],
                    }
                }]
            )
```

**混合检索 + Rerank 实现**：

```python
from rank_bm25 import BM25Okapi
import numpy as np

def hybrid_retrieval(query: str, top_k: int = 10) -> list[dict]:
    """向量检索 + BM25 混合，Rerank 后返回"""
    
    # 1. 向量检索（Qdrant）
    query_vector = model.encode(query).tolist()
    vector_results = qdrant.search(
        collection_name="knowledge_base",
        query_vector=query_vector,
        limit=top_k * 2,
        score_threshold=0.7,
    )
    
    # 2. BM25 检索
    bm25 = BM25Okapi(corpus_tokens)  # corpus 需预构建
    bm25_scores = bm25.get_scores(query.split())
    bm25_top = np.argsort(bm25_scores)[-top_k*2:]
    
    # 3. 合并去重（RRF: Reciprocal Rank Fusion）
    merged = rrf_merge(vector_results, bm25_top)
    
    # 4. Rerank（Cross-Encoder）
    from sentence_transformers import CrossEncoder
    reranker = CrossEncoder("BGE-reranker-v1.5")
    reranked = reranker.rank(query, [m["text"] for m in merged])
    
    return reranked[:top_k]
```

**踩坑经验**：

1. **Embedding 模型版本锁定**：BGE-m3 升级至 v2.0 后，向量维度从 1024 变为 1536，旧索引无法兼容。解决：在 Qdrant Collection 元数据中记录模型版本，模型升级时全量重建索引
2. **大文档的上下文溢出**：长文档分块后，关键上下文可能被分割在不同块中。解决：实施"命题分块"——用 LLM 将每个段落改写为独立命题，每个命题包含足够上下文
3. **BM25 的中文分词问题**：默认 BM25 按空格分词，中文需要先用 jieba 分词。解决：构建 BM25 索引前，对中文 corpus 做 jieba 分词
